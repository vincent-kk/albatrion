When a `controls.injectTo` or `controls.derived` write names a value for a field that is already leaving when the write is applied (for example a caller gate change and the source write in the same `node.batch()`), the named value is now kept for the field, as it is when the field became inactive in an earlier update. The field's exit policy runs first: a value the write names replaces the result of `unsetOnInactive` or `inactiveValue`, and a field the write omits keeps what that policy left. Before, the field kept its previous value and the written value was lost. This holds however the write names the field: through its parent object, by the field's own path (`{ '../y': value }`), or by a path below an object that becomes inactive in the same update. It also applies to the fields of a virtual group, including a group inside such an object, and to a field that a lower-ranked rule of the same update makes inactive. When several rules name the field or its container, the higher-ranked rule decides, as in separate updates. A rule that closes the gate in the same round as the write is not such a case: the write lands on the still-active field and its exit policy then applies to that value. This also preserves a value written through a whole parent object, array, or virtual group when the default exit policy retains the field. When a later rule of the same update makes the field active again, its exit is cancelled: no exit policy runs and the named value is written to the field; a field the write does not name keeps its value. If the revived field leaves again and finishes the update inactive, the second exit runs its policy before retaining the declarative value. If the second exit is also cancelled, the declarative value remains live. A `controls.injectTo` or `controls.derived` value for a field that is already inactive now also wins over a value the caller wrote to that field in the same update or `node.batch()`, as it does when the two writes are separate updates; before, the caller value was kept.
