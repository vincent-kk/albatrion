# Error Reference

## Error guards and code comparison {#guards}

Use `isJSONSchemaError`, `isSchemaFormError`, `isUnhandledError`, and `isValidationError` for the four sibling error classes. Each guard uses instanceof for its own class; a native error from your code or a plugin is not automatically one of them. The package exports these guards, not the four constructors.

Compare group-qualified `error.code` or record.code with `FormErrorCode` / `FormWarningCode` members so the compiler checks names. A `ValidationIssue` is a verdict item, not one of these exception classes. Native adapter bind and pointer failures are described in [AJV configuration](./validation#ajv-configuration) and [guard compilation](./validation#guard-compilation).

## onError occurrences and origins {#occurrences}

`onError` is an occurrence channel, not the current issue list or a resolution notification. The callback receives level, group-qualified code, message, origin, and optional path/schemaPath/details/error/componentStack. Infer the callback parameter type from `FormProps['onError']`. Do not write back to the same Form from its onError observer.

| origin   | Operation                                                                                                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| load     | Input-map pattern configuration failures; construction, mount, reset, rebuild, or validator-replacement load chains                              |
| write    | Value/state/array/context/external-issue writes and their notification listeners                                                                 |
| validate | Whole-schema compile, verdict, result delivery, and their listeners                                                                              |
| submit   | Degraded submission rejection or a failure before the verdict first captured by native submit; excludes the schema verdict and onSubmit failures |
| render   | User FieldInput and renderer exceptions caught by render boundaries, and render warnings                                                         |

An already open chain retains its outer origin through nested writes/resets; tree-construction occurrences are always load. Initial external-errors application is load, later prop replacement is write, and a validator execution or compilation failure already reported inside submit retains validate origin. For schema verdicts and callback failures, see [submission](#submission). Some development console warnings have no onError record, so those channels need not match.

An explicit input-map pattern such as `^/invalid[` that cannot compile reports one committed record with `level: 'error'`, `code: FormErrorCode.FieldInputMap` and `origin: 'load'`, including in StrictMode. An invalid initial map keeps the load fallback. An invalid live replacement preserves the current tree and last valid map. Replace the map reference to re-evaluate it; a new invalid key reports once, and a valid map recovers without remounting the Form.

A user `FieldInput` that throws while rendering reports `FormErrorCode.RenderFailed` with `origin: 'render'`, even when the thrown error itself carries `FormErrorCode.FieldInputMap`. Its render boundary isolates that input subtree.

## Rejections, listeners, and host failures {#host-failures}

A validate/submit caller can receive one aggregate rejection while onError receives individual occurrences; records do not contain that aggregate rejection itself. Validation-result listener failure is callerless even during explicit validate, so the promise may resolve while the host receives an error.

Callerless failure delivery unfolds only well-formed, nonempty MultipleErrors bundles, in element order and depth-first. Arrays need stable integer length from 1 through 2^32−1 and own indices; each traversal shares a 1,000,000-element inspection budget. Malformed, unreadable, cyclic, revisited, length-changing, or over-budget bundles are opaque leaves retaining identity, so the host can receive the bundle itself.

Engine validation waves, automatic OnChange, and load flush preserve handler-first failure order. Failures reported by native submit and the load slot preserve original-first order; the native schema verdict follows the separate [reveal flow](#submission). React/render boundaries record the original thrown value. Capture suppresses only valid already-reported bundles; unreadable metadata falls back to one fixed-message record containing the original value. These details matter when correlating host failures with onError rather than counting them as separate root causes.

## Submission failures and native Enter {#submission}

An accepted submission passes the captured emitted value to `onSubmit`, awaiting its promise. An imperative `formRef.current.submit()` or `useFormSubmit` call rejects an invalid schema verdict with a validation error carrying `FormErrorCode.SchemaValidationFailed` and does not automatically reveal errors. Catch its rejection in event handlers; use [revealErrors](./validation#visibility) when that flow needs to reveal untouched fields.

A native submission, from Enter in a field or a submit button inside the Form, handles the Form's own invalid schema verdict without calling `onSubmit`. That verdict reaches neither `onError` nor the host error sink. The Form reveals errors as `revealErrors()` does and requests focus on the first eligible invalid node.

The committed error-display policy is the latest Form `errorVisibility` prop, falling back to the FormProvider and then AfterEditAndTouch. If it is `ErrorVisibility.Never`, native submission neither reveals nor focuses. A node's own `ErrorVisibility` still overrides error display; see [visibility and policy lifetime](./validation#visibility). A Form-level `disabled` or `readOnly` permits reveal but prevents focus. A verdict arriving after reset, rebuild, validator replacement, or unmount is discarded; focus also requires the same mounted load after reveal.

Focus candidates have their own `node.errors`, are present under present ancestors, are neither disabled nor read-only, and do not set `FieldNodeState.ErrorVisibility` to false. The first candidate below the root in tree preorder wins; the root is used only when no descendant qualifies. Tree order matches screen order with default rendering; a custom layout can differ. The request uses the [focus targets](./api-reference#form-handle). If the chosen input cannot take focus, focus stays where it is and no later candidate is tried. This includes an input-level disabled override, an omitted input, an error fallback, or an input suspended during the reveal commit. Nested virtualization gates open to the exact target; pending-focus cancellation and other limits follow [virtualization](./api-reference#virtualization).

Degraded diagnostics reject submission with `FormErrorCode.SubmitWhileDegraded`. On the native path, degraded and validation-unavailable failures reach `onError` and then the host sink; an identical compilation failure already reported by the Form reaches only the sink. An `onSubmit` exception or rejected promise reaches only the host sink, without `onError`, even if it is a validation error thrown by application code. Imperative callers receive these rejections instead of forwarding them to the host sink.

Enter submission follows the native form algorithm. Include a submit button when there are several text-like fields. A form with a single blocking text input and checkboxes may submit without a button; do not generalize that case to multiple text inputs. A button outside the form needs an explicit handle call or native form association.
