# Core Concepts

## Shape, interpretation, validation {#shape-value-validation}

The form engine builds fields from participating declarations. Constraints such as `minimum` and `minItems` belong to the validator: they do not clamp every write or manufacture array data. Type interpretation can convert a value when the conversion is unambiguous. An ambiguous or unconvertible value remains a misfit for the consumer and validator to handle.

Choose between the [active and visible controls](./schema-reference#controls) for existence and display, then consult [validation visibility](./validation#visibility) for issue routing and presentation.

## Node types and strategies {#node-types}

| Node                                             | Meaning                                                                         |
| ------------------------------------------------ | ------------------------------------------------------------------------------- |
| StringNode / NumberNode / BooleanNode / NullNode | Terminal values; integer uses NumberNode                                        |
| ObjectNode / ArrayNode                           | Child nodes in branch strategy, or one whole-value input in terminal strategy   |
| UnionNode                                        | Terminal node for multiple non-null kinds                                       |
| VirtualNode                                      | Synthetic branch grouping existing sibling properties through `options.virtual` |

Virtual nodes are layout groups, not conditional branches. Object/array strategy follows explicit `options.terminal` first, then a component in `presentation.FieldInput`, then branch strategy. See [strategy invariants](./schema-reference#terminal-strategy).

## Array data and array UI {#arrays}

`minItems` does not create array entries during initialization, reset, or reactivation. The core built-in array input can show empty UI slots toward that minimum, capped by `maxItems`; an entry becomes data when its slot receives input. It chooses an empty slot's control from its active item schema, falling back to `prefixItems[index]` before `items`. It hides the add button at `maxItems` and shows remove buttons independently of `minItems` when not readOnly. UI plugins supply their own array behavior; see the [tuple example](./examples/tuple-arrays) for the Antd6 input.

A root empty array emits `[]`. `omitEmpty` removes empty values during propagation to a parent; it does not remove the root. See [value rules](./schema-reference#value-states) for nullable and overwrite behavior and the [array output example](./examples/array-output-filters).

## Rendering and configuration lifetime {#rendering}

A Form's `children` replaces automatic root layout. Omitted inputs are not inserted elsewhere automatically. Rendering the same path twice creates two inputs. Built-in inputs that initialize from defaultValue and retain their own drafts do not mirror another input's typing until refreshed. A custom controlled input can instead follow the current value prop and synchronize both renderings immediately.

The default group assembles the [registered Label and ErrorMessage parts](./api-reference#renderer-parts), so replacing a slot changes its presentation without copying the group layout. Branch legends still use the field name directly, and labels are omitted for array-item leaves; a LabelRenderer does not change those titles or add those omitted labels.

Renderers, `formatError`, input definitions, and input maps apply after mount when their immutable references change. Input selection preserves values, state and external errors; input DOM is preserved while both its selected component and its owning ancestors stay unchanged. Replacing a parent input recreates its descendants’ DOM and uncommitted drafts, even when their selected components are unchanged. A renderer replacement rebuilds the UI subtree it owns. See [configuration lifetime](./api-reference#configuration-lifetime).

## Measure the work your form performs {#performance}

For a large form, choose a [validation mode](./validation#modes) based on the measured cost of compilation and explicit validation/submission. Rendering can dominate even when validation is deferred; evaluate [virtualization](./api-reference#virtualization) against the time until all inputs are available.

`onChange` runs synchronously. Wrap expensive consumer state updates in React `startTransition` when appropriate and measure the result in your application. CSS containment needs an intentional size and a layout check; adding a wrapper alone is not a performance guarantee.
