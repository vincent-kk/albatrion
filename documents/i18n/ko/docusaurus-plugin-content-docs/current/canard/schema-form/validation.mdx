# 검증



## 검증 모드와 실행 시점 {#modes}

기본값은 `ValidationMode.OnChange | ValidationMode.OnRequest`입니다. `None`은 검증을 끄고 `OnRequest`는 변경에 따른 자동 판정을 생략합니다. 검증이 켜진 모드에서 명시적 `validate()`, `submit()`은 즉시 시작하며 호출 시점의 값 snapshot을 검사합니다.

자동 OnChange 검증은 다음 프레임 뒤 시작하고 연속 입력의 trailing 실행을 유지하며 마지막 실제 자동 실행부터 100ms 상한을 둡니다. 입력 debounce는 FieldInput이 담당합니다. 프레임 API 부재·숨김 문서·정지 프레임에서는 task·100ms timer fallback을 사용합니다.

root load마다 다음 프레임 뒤의 검증 슬롯 하나를 예약합니다. `None`은 compile을 생략하고 `OnRequest`는 compile만 준비하며 OnChange 초기 판정은 이후 write 요청이나 명시적 root 판정이 대체하지 않을 때만 실행합니다. 자동 load compile 실패는 채택한 트리를 유지하고 validate-origin 발생과 host 실패를 보고하며 reset·rebuild의 동기 예외로 다시 던지지 않습니다.

초기의 빈 오류 배열은 판정 전일 수 있으므로 판정이 필요하면 `validate()`를 기다리십시오. 자식 검증 요청은 대기 중인 전체 폼 요청을 취소하지 않습니다.

## 원시 오류와 오류 표시 {#visibility}

`ShowError.Always`·true는 항상, `Never`·false는 전혀 표시하지 않으며 `Edited`, `Touched`는 해당 interaction flag를 요구합니다. 기본 `EditedTouched`는 둘 다 필요합니다. 노드의 `FieldNodeState.ErrorVisible`은 이 정책을 덮어씁니다. `handle.showError(true)`는 Form 정책을 강제하고 false는 prop 정책으로 돌려주므로 반드시 숨긴다는 뜻은 아닙니다.

OnChange에서는 새로 표시 적격이 된 오류를 release까지 보류하며 마지막 release 이후 계속 적격이어야 합니다. 부적격에 따른 숨김은 즉시 적용합니다. release는 pending true→false 정착, quiet post-paint 이력 drop, 수락한 명시적 root 판정, dispose 때 발생합니다. OnRequest·None은 이력 없이 현재 적격성을 사용합니다.

하나의 public batch·subtree walk는 첫 상태만 기록하지만 React batch 안의 별도 public 쓰기는 중간 상태도 기록할 수 있습니다. React remount·가상화는 노드 적격성 이력을 지우지 않으며 context가 계속 바뀌면 새 오류 표시도 계속 지연될 수 있습니다.

`node.errors`, `getErrors()`, 함수 children, `Form.Render`는 표시 정책과 별개로 원시 오류를 제공합니다. 숨김 필드는 값과 오류를 유지하며 inactive 경로는 출력에서 빠지고 off-branch 검증 이슈는 건너뜁니다.

React-only disabled 토글, 지연된 presence commit, release와 paint 사이의 쓰기는 hold를 생략하거나 1~2프레임 전 판정을 보이게 할 수 있습니다. 업무 흐름은 원시 오류로, 표시는 렌더러의 적격성 결정으로 처리하십시오.

## ValidationIssue와 메시지 {#issues-messages}

공개 `ValidationIssue`는 `dataPath`(JSON Pointer이며 root는 `''`), 선택적인 `keyword`, `message`, `schemaPath`, `rejectedKey`, `details`, 검증기별 `source`를 가집니다. 이는 데이터이며 [오류 참조](./error-reference)의 예외 클래스와 구분합니다.

keyword·기본 메시지는 `presentation.errorMessages`, 애플리케이션별 형식은 `formatError(error, node, context)`를 사용하십시오. keyword 항목은 문자열이나 detail 값별 사전입니다. 프로그램의 판정에는 검증기의 원시 오류를 사용하며 표시 형식은 판정을 바꾸지 않습니다. `errors` 또는 노드 external-error 메서드로 전달한 외부 오류도 원시 오류 목록에 참여합니다.

## 검증기 객체 계약 {#validator-contract}

`validatorFactory`는 `compile(root)`와 동기 `compileGuard(root, pointer)`를 가진 객체이며 `release(root)`, `dialect`는 선택 사항입니다. `compile`은 순서 있는 오류·null 또는 그 promise를 반환하는 함수를 만듭니다. throw는 검증 판정이 아니라 실행 실패입니다. `compileGuard`는 동기 boolean predicate를 반환하며 전체 스키마 compile보다 먼저 실행될 수 있습니다.

엔진은 compile·compileGuard·release에 같은 소유 root copy를 전달합니다. `$ref`, `$id`, anchor 문맥을 보존하고 전달된 schema와 값을 변경하지 마십시오. nonboolean guard 결과·compile 실패·throw는 그 gate를 실패시키며 전체 스키마 compile 실패가 guard를 되돌리지는 않습니다. release는 cache에서 root를 내보낼 때 실행하고 등록하지 않은 root에도 멱등이어야 합니다. 양쪽 dialect를 알고 `$schema`가 다르면 `DialectMismatch`로 보고합니다.

같은 `$id`의 서로 다른 live root도 격리해야 하며 엔진은 ID를 다시 쓰지 않습니다. `already exists` 또는 `resolves to more than one schema` 문구를 포함한 실패만 `duplicateSchemaId`로 분류하고 다른 root 해제 뒤 한 번 재시도합니다.

guard는 `$async`, 비동기 keyword·format, host 밖의 데이터에 의존하는 keyword(`$data`, 부모·형제 데이터)를 지원하지 않습니다. AJV 플러그인은 remote ref를 다운로드하지 않으므로 root 내부나 bound instance에 참조 schema를 준비하십시오. 검증 라이브러리가 허용하더라도 custom keyword는 값을 변경하면 안 됩니다.

## AJV 버전과 dialect {#ajv-entries}

| 패키지 진입점 | 기본 dialect / 설정 |
| --- | --- |
| `@canard/schema-form-ajv6-plugin` | Draft-07; `allErrors: true`, `nullable: true`, `verbose: true`, `format: false` |
| `@canard/schema-form-ajv7-plugin` | Draft-07; `allErrors: true`, `strict: false`, `validateFormats: false` |
| `@canard/schema-form-ajv8-plugin` | Draft-07; `allErrors: true`, `strictSchema: false`, `validateFormats: false`, `allowUnionTypes: true` |
| `@canard/schema-form-ajv8-plugin/2019` | Draft 2019-09 |
| `@canard/schema-form-ajv8-plugin/2020` | Draft 2020-12 |

선택한 진입점의 `plugin`을 import하여 등록하십시오. 검증기는 `plugin.validator`입니다. AJV 6의 Draft-04·06에는 맞는 instance·meta-schema·schemaId 설정이 필요합니다. 기본 식별자는 `$id`이며 `schemaId: 'id'`·`'auto'`는 Draft-04 `id`도 인식합니다. AJV 7의 2019-09는 해당 constructor를 bound instance에 사용해야 합니다. AJV 8의 제공 진입점은 Draft-04·06의 완전 지원을 보장하지 않으므로 해당 dialect를 지원하는 검증기를 선택하십시오.

기본 제공 설정에서는 format 검증이 꺼져 있으므로 `format: 'email'`만으로 이메일 판정을 기대하지 마십시오. 필요한 format을 갖춘 instance를 구성하십시오. AJV 6의 JSONPath 오류 위치는 JSON Pointer로 정규화하고 AJV 7·8은 원래 pointer 경로를 사용합니다. 모든 어댑터는 `ValidationIssue`를 제공하며 root 오류는 `dataPath: ''`입니다.

번들러 없는 Node ESM에서 AJV 7 기본 import는 constructor 대신 interop namespace일 수 있습니다. 기본 플러그인을 사용하거나 해당 모듈 환경에 맞게 AJV constructor를 해석한 뒤 custom instance를 만드십시오.

## binding과 instance별 어댑터 {#ajv-configuration}

사용자 AJV 8 instance를 만들 때에는 소비자 애플리케이션에 `ajv@8.17.1`을 설치하십시오. 플러그인 자체의 AJV 의존성이 애플리케이션의 `import Ajv from 'ajv'` 버전을 정하지는 않습니다.

첫 compile·등록 전에 한 번 bind하십시오. 재bind는 지원하는 수명주기가 아닙니다. `coerceTypes`, `useDefaults`, `removeAdditional`은 기존 binding을 바꾸기 전에 거부합니다. native `ValidatorBindRefusedError`는 group·code metadata를 가지며 코어 `UnhandledError` instance가 아니므로 `isUnhandledError`로 분류하지 마십시오.

AJV 6·7의 bind는 새 root registry를 시작합니다. AJV 8은 이미 등록된 root를 release까지 그 root를 등록한 instance에 연결합니다. Form별 완전한 어댑터에는 `createValidator(ajv, options?)`를 사용하고 render 밖에서 생성하거나 안정된 의존성으로 memoize하십시오. 여러 어댑터는 값을 변경하지 않는 AJV instance 하나를 공유할 수 있습니다.

`createValidatorFactory(ajv)`는 compile 함수만 반환하므로 `validatorFactory`에 직접 전달하면 객체 계약을 만족하지 않습니다. AJV 6·7 factory는 임시 schema를 compile·제거하고 비동기 결과를 오류 또는 null로 정규화합니다. AJV 8은 release까지 root 등록을 재사용합니다.

```tsx
import Ajv from 'ajv';
import { Form } from '@canard/schema-form';
import { createValidator } from '@canard/schema-form-ajv8-plugin';

const ajv = new Ajv({ strictSchema: false, validateFormats: false });
ajv.addKeyword({
  keyword: 'isEven',
  type: 'number',
  schemaType: 'boolean',
  validate: (enabled: boolean, data: number) => !enabled || data % 2 === 0,
});
const validatorFactory = createValidator(ajv);
const schema = { type: 'number', isEven: true } as const;

export function EvenNumberForm() {
  return <Form jsonSchema={schema} validatorFactory={validatorFactory} />;
}
```

어댑터 참조를 안정적으로 유지하십시오. [검증기 교체는 Form 트리를 다시 만듭니다](./api-reference#configuration-lifetime).

## guard compile과 root 수명 {#guard-compilation}

AJV 어댑터 세 가지는 모두 `plugin.validator.configure({ directGuardCompile })`를 지원하며 기본값은 true입니다. true이면 self-contained guard를 직접 compile하고 false이면 이후 compile을 root pointer로 보냅니다. 생략한 옵션은 유지하고 기존 predicate는 바꾸지 않으며 bound AJV 설정도 변경하지 않습니다.

reference·identifier 키 또는 root·guard의 `$schema`가 있으면 direct를 선택해도 root-pointer compile을 사용합니다. root 다른 부분의 code-generation 오류가 root-pointer guard를 실패시킬 수 있지만 직접 compile한 self-contained guard에는 그 오류를 전파하지 않습니다.

guard sibling instance는 bound dialect·format·keyword를 유지하면서 `allErrors: false`, `validateSchema: false`를 사용합니다. root meta-schema 검사는 bound `validateSchema` 정책에 따른 전체 검증의 일입니다. guard 밖이나 안의 meta-only 위반은 별도 guard meta 검사를 만들지 않지만 strict·custom keyword·code-generation 검사는 적용합니다. strict compile 실패는 true·false 대신 `GuardFailed`로 두 조건 분기를 모두 끕니다.

`$id`가 있는 root는 격리 등록하고 ID 없는 whole root는 임시 copy를 사용합니다. self-contained direct guard는 AJV에 root를 등록할 필요가 없습니다. release는 root 등록·compiled 결과·direct guard를 정리하며 미등록 root에는 no-op입니다. schema가 아닌 pointer는 root ID·pointer details를 가진 native `GuardPointerNotSchemaError`, code `GUARD_POINTER_NOT_SCHEMA`를 던집니다.

## AJV 7·8 dynamic·recursive guard 범위 {#dynamic-guard-scope}

조건에 dynamic scope가 필요하지 않으면 정적 `$ref`, 재사용 `$defs`, `properties` 아래 `if`를 우선하십시오. guard가 전체 검증과 동등하려면 관련 진입마다 첫 anchor binding이 같고 검증 context를 재현할 수 있으며 선택한 함수가 동기여야 합니다.

dynamic vocabulary instance이고 root에 dynamic·recursive 키가 있으면 어댑터는 root-pointer guard compile 전에 anchor table을 준비합니다. chain은 root와 pointer 경로의 `$id` resource이며 바깥부터 읽고 각 이름은 가장 바깥 선언 resource에서 먼저 binding합니다. schema keyword를 따라 수집하며 `const`, `enum`, `default`, `examples` 데이터, nested resource, guard 자체 subtree는 내려가지 않습니다. resource의 다른 assertion은 guard 판정에 더하지 않습니다. Draft-07은 dynamic 키를 무시하고 이 table·검사를 적용하지 않습니다.

`if` 안의 inline reference는 chain resource 또는 guard 안의 lexical ancestor에서 binding해야 하며 없으면 compileGuard가 실패합니다. 선택한 선언의 `$async: true`도 거부합니다. 다음 조건은 동등성을 제한하거나 지원하지 않습니다.

| 조건 | 결과 |
| --- | --- |
| 같은 schema 위치를 여러 dynamic scope로 진입 | guard 하나는 lexical chain을 사용하거나 compile에 실패하며 동등성 지원 밖입니다 |
| chain 밖 resource가 먼저 binding하거나 URI 진입이 on-path resource를 건너뜀 | 전체 검증과의 동등성을 지원하지 않습니다 |
| sibling·descendant·guard 내부 `$defs`에만 binding 존재 | inline binding을 제공하지 못합니다 |
| resource root 밖의 `$recursiveAnchor: true` | chain table에 들지 않으며 필요한 binding이 없으면 수정 방향과 함께 거부합니다 |
| 2019-09 non-root 외부 recursive anchor와 guard 내부 ancestor anchor 공존 | guard·전체 검증이 다를 수 있어 지원하지 않습니다 |
| dynamic·recursive ref fragment `#/...` | anchor 이름이 아니므로 compileGuard가 거부하며 위치에는 정적 `$ref`를 사용합니다 |
| 현재 static `$anchor`와 외부 dynamic anchor 충돌 | AJV·guard가 specification의 static 처리 대신 dynamic table을 사용할 수 있습니다 |
| custom keyword subschema 또는 guard 내부 `$defs`를 `$ref`로만 실행하는 선언 | dynamic chain 수집에서 인식하지 않습니다 |
| nested resource inline anchor의 상대 ref | guard는 해당 resource base URI, 전체 검증은 root base URI를 사용할 수 있습니다 |
| chain 밖 resource의 runtime anchor | 전체 검증에 누출될 수 있으나 guard에는 없으며 chain 안 sibling 선언은 수집합니다 |
| 전체 검증이 아직 실행하지 않은 chain resource 선언 | guard는 수집하므로 enclosing-function fallback과 다를 수 있습니다 |
| 전체 검증이 `$id` 없는 resource를 건너뜀 | guard·전체 검증이 다를 수 있습니다 |
| AJV가 dynamic-ref bookending을 검사하지 않음 | guard도 따르며 최초 대상이 dynamic anchor인지 별도로 보장하지 않습니다 |
| compile 때 root anchor flag 없음 | 둘 다 table 조회 없이 enclosing compiled-function fallback을 유지합니다 |
| DynamicRef가 `#`로 시작하지 않음 | 전체 검증·guard 모두 compile에 실패합니다 |
| anchor 이름이 `constructor`, `toString`, `__proto__` 등 Object.prototype과 충돌 | AJV plain-object table 처리로 binding하지 못합니다 |

이는 어댑터의 조건이며 임의 dynamic scope의 동등성을 보장하지 않습니다.
