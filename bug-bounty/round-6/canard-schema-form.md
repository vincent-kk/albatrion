## 1. A batched Merge into an inactive object deletes keys supplied by an earlier write in the same batch.

- Severity: medium. Partial updates silently lose retained data when the application batches writes into a gated nested object while it stays hidden. The hunter rates this high; the final rating is medium because the input requires a batch, a gated object and partial writes while it is hidden.
- Affected public API: `FormHandle.node`, `FieldNode.batch` and `FieldNode.setValue` with Merge or Overwrite options.
- Contract violated: `packages/canard/schema-form/src/core/engine/write/DETAIL.md:71` requires recursive merging of declared branch-object children and preservation of omitted inactive sources; `packages/canard/schema-form/src/core/engine/write/DETAIL.md:75` requires caller-write order transparency. `packages/canard/schema-form/src/core/engine/types/value.ts:27` defines Merge as retaining omitted object keys. The gate stays false throughout, so no intermediate reaction explains the difference.
- Root cause: `packages/canard/schema-form/src/core/engine/write/utils/chain/utils/mergeMarkedValue.ts:28-35` first spreads incoming values shallowly and repairs nested merges only for live children in `node.childrenByName`. An inactive declared object has no live child, so its later partial object replaces the earlier value before replacement-origin metadata can preserve it.
- Relation to earlier rounds: same class as [round 3 item 5](../round-3/canard-schema-form.md), composed writes versus sequential writes, with a different inactive-child input.
- Reopens an earlier fix: [round 3 item 5](../round-3/canard-schema-form.md), `839789720`.
- Regression of an earlier fix: no. Static inspection of the predecessor also shows a shallow spread; this input is outside the earlier pinned examples.
- Watch list: yes, inactive-address retention and the two-layer batch contract, counted once.
- Reproduction: `r6-retention/publicMerge.test.tsx`, "a Form batch keeps an inactive address value when the next Merge omits its key", writes `{ held: { a: 'user entry' } }` through `/box`, then merges `{ box: { held: { b: 'later entry' } } }` through the root. After revival, actual `box.held` is `{ b: 'later entry' }`; expected `{ a: 'user entry', b: 'later entry' }`. Both React projects fail. The three `mergeAfterWhole.test.ts` rows lose the earlier scalar/list on empty Merge; `ownership.test.ts` finds 141 mismatches in 1,000 fixed-topology sequences, supporting this one cause.
- Confidence: high; public Form probes on React 19 and React 18, with internal tree-fixture support.

## 2. A batch with an unrelated write and an identity updater or emptying child write deletes a null object.

- Severity: medium. A nullable object changes from meaningful null to absent when a second batched write empties a child or returns its unchanged value. The hunter rates this high; the final rating is medium because it requires a batch, a nullable object and an emptying or identity write under it.
- Affected public API: `FormHandle.node.batch`, nested `FieldNode.batch`, `findNode(...).setValue` with a value or updater, and `FormHandle.getValue`.
- Contract violated: `packages/canard/schema-form/docs/agents/skills/schema-form-skill/knowledge/nullable-branch-nodes.md:13` preserves null, empty and unset distinctions; its line 26 says emptying a child preserves a null parent, and line 31 treats the empty string as emptying under default projection. `packages/canard/schema-form/src/core/engine/write/DETAIL.md:75` and line 79 require ordered caller writes and the correct updater view; `packages/canard/schema-form/src/core/engine/settle/DETAIL.md:135` permits ancestor promotion only for an emitted child value.
- Root cause: `packages/canard/schema-form/src/core/engine/write/utils/chain/utils/replaceAtPath.ts:38-39` replaces any nonobject ancestor with `{}`. `packages/canard/schema-form/src/core/engine/write/utils/chain/composeBatchValue.ts:38` overlays the mark before checking whether the child emits anything, and `packages/canard/schema-form/src/core/engine/write/utils/chain/readBatchValue.ts:63` exposes that invented object to later updaters. Settlement then omits the empty object.
- Relation to earlier rounds: same class as [round 3 item 5](../round-3/canard-schema-form.md) and the round 5 caller-layer follow-up; the mechanism is nonobject reconstruction rather than Merge scope.
- Reopens an earlier fix: no. The responsible reconstruction belongs to `c5c7c453b`, rather than the neighboring bounty Merge repair.
- Regression of an earlier fix: yes, case (a), the caller-layer specification row at `../round-5/FIXES.md:393`, associated with caller-view fix `c22d48c43` at line 224. The code predates that row; this does not claim the fix introduces the defect. The ancestor-Overwrite reaction limit at line 521 does not cover an explicitly null parent whose child is emptied.
- Watch list: yes, the caller layer of the two-layer batch contract and declarative value placement.
- Reproduction: `r6-batch/publicCallerLayer.test.tsx`, "an unrelated batch write and identity updater keep an initially null object", starts at `{ other: false, o: null }`, writes `other=true`, then applies `/o/n.setValue(v => v)` in one batch. Actual `{ other: true }`; expected `{ other: true, o: null }`. The empty-string variant and flat/nested null-parent variants fail on both React versions; sequential controls pass. `callerLayer.test.ts` also shows a later parent updater receiving `{ n: undefined }` instead of null.
- Confidence: high; public Form probes on React 19 and React 18, plus internal construction using public node methods.

## 3. Separately bundled client applications give their Forms the same document identifiers, so a label click changes another application's field.

- Severity: medium. Labels and accessibility references reach the wrong form when widgets or micro-frontends each load their own `react-dom`; a click silently writes into the other application.
- Affected public API: `Form`, `Label`, `Form.Label`, `FieldInputProps.inputId` and `getInputId`, including title identifiers and `aria-labelledby`.
- Contract violated: `.changeset/schema-form-scoped-identifiers.md:25-29` promises document-wide label and accessibility reference resolution, while lines 21-25 request distinct `identifierPrefix` values only for independent server-rendered roots. `packages/canard/schema-form/docs/agents/skills/schema-form-skill/knowledge/field-input.md:160` and `documents/docs/canard/schema-form/api-reference.mdx:103` retain that server-rendered-only condition.
- Root cause: `packages/canard/schema-form/src/providers/WorkspaceContext/components/WorkspaceContextProvider.tsx:25` derives scope only from `formatSegment(useId())`. Each separately loaded `react-dom` copy starts its own client counter at the same value. `packages/canard/schema-form/src/providers/WorkspaceContext/DETAIL.md:13` delegates independent-root prefixes to the host, leaving consumer guidance narrower than this requirement.
- Relation to earlier rounds: same class as [round 3 item 1](../round-3/canard-schema-form.md); confirms the independent-bundle open lead in [round 5](../round-5/canard-schema-form.md).
- Reopens an earlier fix: [round 3 item 1](../round-3/canard-schema-form.md), `633ef8c8e`.
- Regression of an earlier fix: no. Path-only identifiers also collide before that fix.
- Watch list: yes, document identifiers.
- Reproduction: `r6-core-react/separateRenderers.test.tsx`, "independent client applications keep Form ids unique without SSR prefixes", loads fresh renderer copies sharing one React. Actual duplicate React 19 identifiers include `_r_0_:/agree~label` and `_r_0_:/agree~input`; React 18 also duplicates its identifiers. "a label in the second client application toggles only its own form" produces `{ first: { agree: true }, second: {} }`, expected `{ first: {}, second: { agree: true } }`. Independence controls and distinct-prefix controls pass.
- Confidence: high for behavior; medium for classification. React's host-level prefix mechanism resolves the collision, so the owner may choose a documentation fix.

## 4. An inline error formatter and a state-writing error callback report one throwing renderer about 27 times.

- Severity: low. One failure causes repeated reporting and production console errors, bounded by React's render limit; the same formatter with a stable identity reports once.
- Affected public API: `Form` and `FormProvider` props `formatError` and `onError`, with a throwing `FieldRenderer`.
- Contract violated: `packages/canard/schema-form/docs/agents/skills/schema-form-skill/knowledge/validation-ux.md:190` describes one retry when the formatter is replaced. `documents/docs/canard/schema-form/core-concepts.mdx:37` describes isolation, and the formatter has no stable-identity requirement comparable to context at `packages/canard/schema-form/docs/agents/skills/schema-form-skill/knowledge/field-input.md:153-156`. Equivalent formatter behavior gives one versus 27 records.
- Root cause: `packages/canard/schema-form/src/components/FieldProxy/utils/getRendererBoundary/components/FormatterErrorBoundary.tsx:29-42` clears `hasError` on every formatter identity change. A throw invokes `onError`, its state update creates a new inline formatter, and the renderer retries until React stops the cycle.
- Relation to earlier rounds: new class, retry identity feeding back through a reporting callback; related to [round 3 item 12](../round-3/canard-schema-form.md).
- Reopens an earlier fix: no. The report identifies `927f50024` without an earlier reopened finding.
- Regression of an earlier fix: no.
- Watch list: no.
- Reproduction: `r6-core-react/errorCycle.test.tsx`, "a throwing FieldRenderer with an inline formatError and an onError that stores records renders a bounded number of times", gives 28 renders and 27 records, expected at most 3 renders and 1 record. The measurement is stable at 50 and 450 milliseconds. A stable formatter gives one record, and a throwing FieldInput is not retried.
- Confidence: high for behavior; medium for classification; public Form rendering on both React projects.

- Root cause: `packages/canard/schema-form/src/core/engine/__tests__/virtualStorageModel.round-five.test.ts:43` classifies by `count`, but line 47 constructs `fields = [...names, 'object']`. Both groups use the expanded list at lines 106 and 108, so a zero-class seed produces a one-constituent group. Class labels and operation quotas do not check actual arity.
- Relation to earlier rounds: new class, profile class labels disconnected from generated schema dimensions. The acknowledged array operation-6 no-op is a different model and is excluded.
- Reopens an earlier fix: no. `539214756` appends the object, and `c0d45ecfc` introduces the class claim; neither is an earlier numbered zero-group repair.
- Regression of an earlier fix: no. The bounded profile already appends the object when its zero-class claim is introduced.

- Reproduction: `r6-batch/profileReachability.test.ts`, "the PR profile constructs the zero-constituent group its class list names", records actual constructed arities `[1, 2, 3, 4, 5, 6]`, expected inclusion of zero through five. ## Hypotheses checked and not bugs

- Retained row values relocate correctly after insert/remove and two exits; retired array positions do not resurrect. Unmaterialized positions follow the documented first/default candidate rule for oneOf, anyOf and allOf. Independent inactive scalar Merge keys retain both writes.
- Natural transition and hostWheel budget failures discard automatic writes and permit later revival of original retained values. Subtree reset restores loaded inactive arrays in plain and batched calls. Parent whole-write omission followed by exit preserves measured default/const-declaration sources.
- Own-address, parent-object and virtual-group writes survive revival and a second exit across 24 combinations, including clear policies that correctly skip resolver invocation. Nonempty strings, nulls, objects and arrays route consistently.
- Live-parent derived writes and equivalent injections agree for inactive, leaving and revived children. Transient defaults do not gain retention rights during same-settlement appearance and exit. Overlapping ancestor Merge, refused subtree reset and caught updater exceptions preserve earlier ownership. Typed Merge exposes earlier coerced values correctly.
- Separate application radio names remain isolated by their owning form. A retained node after `rebuild()` refuses writes without callbacks. Equivalent schemas and reset reuse the root. Static checks find portal submit/reset isolation, recursive context pair tracking, consistent non-ASCII pointer resolution and the documented draft-04 identifier policy; nested native forms remain unsupported.
- Earlier specification probes preserve absent virtual tuple positions, loaded hidden reset values, typed updater views, structural-boundary settlement and retained-write rankings. React 18, React 19, StrictMode and Activity agree on tested reset/reactivation behavior. Independent-model omissions and candidate limits recorded in round 5 remain excluded.
