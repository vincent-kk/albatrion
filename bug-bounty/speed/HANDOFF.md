## 어기면 안 되는 규칙

- **동작을 바꾸지 않습니다.** 속도 변경만 합니다. 동작 결함을 발견하면 고치지 않고 `issues/`에 기록합니다.
- **테스트와 단언을 고치지 않습니다.** 모든 패키지의 `src/__tests__/` 공개 테스트가 수정 없이 통과해야 합니다.
- **`master`, PR #344, 배포를 건드리지 않습니다.** 강제 푸시를 하지 않습니다.
- **개선 PR의 대상 가지는 `1.0.0/optimize`입니다.**
- 커밋 메시지와 PR 본문은 영어로 쓰고, 공동 작성자 줄이나 세션 줄을 넣지 않습니다. 소비자가 관찰할 수 있는 변화가 없으면 changeset을 만들지 않습니다.
- 프로덕션 코드와 주석에서 패키지 밖 문서(이 디렉터리 포함)를 가리키지 않습니다.
- 플러그인은 얇은 래퍼로 유지합니다. 구조를 바꾸는 재설계는 Vincent의 승인이 필요합니다.
- Vincent에게는 한국어 높임말로, 완전한 문장으로 답합니다.

## Vincent이 정한 판단 기준

- **허용 폭.** 기준 연산 시간이 1마이크로초 미만이면 1.35, 1~5마이크로초면 1.10, 그 밖에는 1.03입니다. 배수가 100배 수준이면 절대 시간과 무관하게 문제입니다. 한 번의 실행에 호출을 여러 번 담은 행은 호출 한 번의 시간으로 판단합니다.
- **패키지별 중요도.** 중요한 것은 기반 도구(`@canard/schema-form`, `@winglet/common-utils`, `@winglet/react-utils`, `@winglet/json`, `@winglet/json-schema`)이며 위 허용 폭을 그대로 적용합니다. 화면 플러그인(`antd5`, `antd6`, `mui`, `antd-mobile`)과 가끔 쓰는 도구인 `@slats/agents-assets-sync`는 1.5배까지 수용하고, 통상적인 낭비만 걷어냅니다. 이 둘은 진단 빌드와 수정별 귀속을 하지 않습니다. 플러그인에서는 동작 무결성이 속도보다 중요합니다.
- **"동작 변경 없음"의 선.** 사용자가 넘긴 객체에 대한 동작(결과, 오류의 종류와 메시지, 접근자 읽기, 프록시 트랩, 키 순서)은 같아야 합니다. 내부 장부에 대한 내장 메서드 호출 횟수는 계약이 아닙니다. 다만 어떤 경우에도 호출이 끝나지 않는 상황은 만들지 않습니다.
- **수정 비용.** 초과가 바운티 수정에 필요한 작업임을 측정으로 보이면 수용됩니다. 보이는 방법은 그 작업을 뺀 진단 빌드를 재고, 그때 실패하는 테스트를 적는 것입니다. 진단 빌드는 커밋하지 않습니다.
- **작은 차이.** 몇 퍼센트의 초과를 더 좁히는 데 큰 노력이 든다면 값과 근거를 보고하고 수용 여부를 묻습니다. 우선순위 1에서는 3~9%의 잔여 초과를 수용했습니다.
- **결정이 필요한 세 경우**(구조 변경이 필요함, 동작 결함을 발견함, 줄일 수 없는 초과)에는 스스로 한 번 더 검토하고, 그래도 풀리지 않으면 `issues/`에 별건 문서로 기록한 뒤 다음 일로 넘어갑니다.
- **보고 방식.** 중간 단계는 한두 문장으로만 알리고, 측정이 끝날 때마다 속도표(행, 기준 시간, 전, 후, 대조군, 판정)를 보여 줍니다.

## 변경 하나를 다루는 순서

순서를 바꾸지 않습니다. 정상 동작을 먼저 보장하고, 그 안에서 속도를 올립니다.

1. 프로파일을 떠서 가장 큰 원인을 찾습니다(`--profile`).
2. 가장 작은 변경을 만듭니다.
3. **측정 전에** 패키지 타입 검사와 전체 테스트를 통과시킵니다.
4. 빌드하고 잽니다. 탐색은 6라운드, 판단은 12라운드, 보고할 수치는 24라운드입니다.
5. 최솟값과 10번째 백분위가 모두 기준 시간의 2% 넘게 좋아진 변경만 남깁니다. 프로파일을 따른 시도가 두 번 연속 효과가 없으면 멈춥니다.
6. 남은 차이는 진단 빌드로 귀속합니다.
7. 구현자와 다른 에이전트가 독립 검증을 합니다. 옛 빌드와 새 빌드를 공개 진입점으로 구동해 결과와 관찰 가능한 사건의 기록을 비교하는 차이 검사이고, 일부러 심은 차이를 잡아내는지도 확인합니다. 우선순위 1에서는 이 검증이 여섯 건 중 세 건에서 실제 결함을 잡았습니다. 건너뛰지 않습니다.
8. lint, typecheck, test, build, `build:verify:types`를 통과시키고 `1.0.0/optimize` 대상 PR을 엽니다. 본문에 전후 표를 넣습니다.
9. `gh pr update-branch`로 가지를 최신으로 만든 뒤 CI를 기다립니다. CI 계획은 PR 가지의 스크립트로 만들어지므로 이 단계가 필요합니다. 통과하면 rebase 병합하고, 커밋 메시지를 바로잡아야 하면 squash 병합합니다.
10. 작업 트리와 가지를 지우고, 결과와 `STATUS.md`를 갱신해 커밋합니다.

작업자에게 주는 같은 내용의 영어 지침은 `../../../albatrion-speed/specs/loop.md`입니다(저장소 밖).

## 측정 도구

도구는 `benchmarks/compare`이고 사용법은 `benchmarks/compare/README.md`, 설계 근거는 `benchmarks/DESIGN.md`입니다. 이 캠페인의 행 정의는 `rows/`, 원자료는 `results/`입니다.

```sh
node benchmarks/compare/run.mjs --rows bug-bounty/speed/rows --rounds 24 \
  --a ../albatrion-speed/beta --b ../albatrion-speed/opt \
  --only p1-14,p1-12 --out bug-bounty/speed/results/<이름>
```

- 판정은 최솟값과 10번째 백분위가 모두 허용 폭 안이면 통과입니다. 기준을 두 번 잰 대조군이 0.98~1.02를 벗어나면 그 실행은 무효이고, 다시 잽니다.
- 도구는 통과, 초과, 무효만 냅니다. 허용 폭과 수정 비용은 표를 만들 때 적용합니다.
- 측정은 기계 전체에서 한 번에 하나만 돕니다. 도구가 `/tmp/benchmarks-compare.queue`와 `/tmp/benchmarks-compare.lock`으로 순서를 잡으므로, 손으로 따로 프로파일을 뜨지 않습니다.
- 마이크로초 미만 행과 일부 렌더 행은 실행마다 흔들립니다. 한 번의 통과나 초과로 단정하지 않고 다시 잽니다.

저장소 밖 `../albatrion-speed/`에 있습니다(이 저장소 기준 상대 경로는 `../albatrion-speed`).

| 트리         | 내용                                                                                    |
| ------------ | --------------------------------------------------------------------------------------- |
| `beta`       | 기준 `1c77ced57`의 빌드입니다.                                                          |

| `head`       | 후보 `d78e45c6b`의 빌드입니다. 개선 전 값을 잴 때 씁니다.                               |
| `opt`        | `head`의 복제본에 병합된 개선을 덮어 빌드한 것입니다. `.speed-ref`가 반영한 커밋입니다. |

`opt`를 최신으로 만드는 방법은 다음과 같습니다. 병합된 패키지의 소스를 덮어쓰고 그 패키지만 다시 빌드합니다.

```sh
cd ../albatrion-speed
REF=$(git -C ../albatrion rev-parse origin/1.0.0/optimize)
git -C ../albatrion archive $REF packages/winglet/common-utils | tar -x -C opt
echo $REF > opt/.speed-ref
```

그다음 `opt` 디렉터리에서 `yarn workspace @winglet/common-utils build`를 실행합니다. **지금 `opt`에는 마지막 `clone` 변경(PR #689)이 반영되지 않았으므로 재개할 때 이 절차부터 합니다.**

트리가 사라졌다면 해당 커밋을 새 디렉터리에 체크아웃하고 `yarn install`과 전체 빌드를 해서 다시 만듭니다. `beta-am543`은 `beta`를 복제한 뒤 `packages/canard/schema-form-antd-mobile-plugin/node_modules/antd-mobile`에 5.43.0의 실제 사본을 둡니다.

## 작업 방식

- 구현, 측정, 검증은 작업자 에이전트에게 맡기고, 조정하는 쪽은 판단과 기록을 맡습니다. Orca 작업자를 쓸 때는 `orca orchestration worker-start --spec-file <명세> --worktree new-child --name <이름> --agent claude --model <모델> --effort high`로 시작합니다. 명세의 예는 `../albatrion-speed/specs/`에 있습니다(`t33-clone-generator.md`가 구현, `t34-verify-clone-keys.md`가 검증).
- 작업자 명세에는 목표, 읽을 파일, 순서, 제약, 결과물 형식을 모두 적습니다. 작업자는 대화 기록을 모릅니다.
- 작업자는 단계마다 작업 트리 루트의 `SPEED-REPORT.md`(커밋하지 않음)에 기록하고, 효과가 확인된 변경은 바로 커밋하고 푸시합니다. 세션이 끊겨도 디스크와 원격에서 이어갈 수 있어야 합니다.
- 작업자가 보고한 수치는 원자료 `run.json`과 대조한 뒤에 씁니다.
- `git`, `gh`, `yarn`, `orca`는 셸 호출 하나에 단독으로 실행합니다. 파이프, `cd`, 환경 변수 접두를 붙이면 훅이 막습니다.
- 임시 스크립트는 저장소 밖에 두고 끝나면 지웁니다. 작업 트리와 가지는 묶음이 병합되면 바로 지웁니다.
