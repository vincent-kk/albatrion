# style-utils 우선순위 2: 남은 초과분은 수정 비용

## 대상

`p2c-12`~`p2c-17` (200개 규칙 시트를 압축 입력으로 주입하는 행). 한 작업이 11~710 µs이므로 한도는 1.35입니다.

## 값

24라운드, 후보 `7de3ceac9`, 대조 0.998~1.004. 원자료는 `results/style-utils-p2-fix-a`, `-fix-b`입니다.

## 귀속

진단 빌드 두 개로 남은 차이를 전부 수정 작업에 귀속했습니다 (6라운드, 대조 0.996~1.004).

| 뺀 부분 | 그 부분의 몫 (기준 대비) | 빼면 실패하는 테스트 |
| --- | --- | --- |
| 준비 단계와 문맥 인식 압축 | 0.6배~1.75배 | 9개 (R3-ST-1, R3-ST-2, R5-ST-1, R5-ST-2, 문장만 있는 CSS) |
| 새 범위 지정기 | 0.58배~2.28배 | 27개 (R1-ST-1, R1-ST-2, R3-ST-6, `:root`와 `:host` 토큰) |

기준 구현은 `indexOf`로 `{`, `}`, `,`만 찾았기 때문에 문자열, 주석, 이스케이프, 중첩 그룹 안의 구두점을 잘못 읽었습니다. 수정된 구현은 CSS 토큰을 실제로 읽어야 하므로 규칙 하나당 일이 늘었습니다.

## 남은 선택지: 재설계

준비와 범위 지정을 한 번의 순회로 합치는 방법이 있습니다. 진단 빌드로 본 상한(한 단계만 남긴 값)은 `p2c-13` 5.15, `p2c-16` 3.46, `p2c-12` 2.90, `p2c-15` 3.29, `p2c-14` 1.72, `p2c-17` 2.19로, 합쳐도 모든 행이 1.35를 넘습니다. 구조 변경이므로 승인 없이는 하지 않았습니다.

같은 CSS에 대한 결과를 관리자별로 기억하는 방법은 제안되었으나 채택하지 않았습니다. 행이 캐시 적중만 재게 되고, 처음 주입하는 비용은 그대로 남기 때문입니다.

Vincent가 현재 값을 수정 비용으로 수용했습니다. 두 순회를 합치는 재설계는 아래 후속 작업으로 따로 진행합니다.

## 후속 작업 (Vincent 승인)

준비와 범위 지정을 한 번의 순회로 합쳤습니다(PR #696). 압축을 생략한 문서 시트가 평면 규칙으로만 이루어지면 범위 지정기가 한 번의 순회로 처리하고, 그 밖의 입력과 2^20 코드 단위 이상인 시트는 기존 두 단계 경로를 그대로 탑니다.

24라운드, 대조 0.998~1.003. 원자료는 `results/style-utils-single-pass-f1-a`, `-f1-b`, `-d2-p107`입니다.

| 행 | 기준 시간 | 합치기 전 | 합친 뒤 (min/p10) |
| --- | --- | --- | --- |
| `p2c-12` | 11.1 µs | 5.01 | 3.22 / 3.21 |
| `p2c-13` | 12.1 µs | 5.18 | 3.28 / 3.25 |
| `p2c-14` | 31.6 µs | 2.36 | 2.23 / 2.23 |
| `p2c-15` | 11.7 µs | 3.98 | 2.61 / 2.61 |
| `p2c-16` | 12.0 µs | 4.39 | 2.58 / 2.59 |
| `p2c-17` | 708 µs | 3.08 | 3.07 / 3.08 |

`p2c-17`은 압축이 글자를 바꾼 뒤에 범위를 지정하므로 합치지 않았습니다. 합치려면 압축 순회 안에 범위 지정기를 넣어야 하는데, 두 읽기 방식이 달라 같은 결과를 보장할 수 없습니다.

독립 차이 검사는 790,521개 입력(합친 경로 303,837개)에서 차이 0건입니다. 첫 검사에서 규칙 하나가 약 670만 코드 단위를 넘을 때 기존 경로만 `RangeError`를 던지는 차이가 나와, 길이 제한을 넣어 닫았습니다. 남은 차이는 호출자가 이미 JS 스택 한계에서 4프레임 이내일 때뿐이며 계약 밖으로 판단했습니다.

모든 행이 여전히 1.35를 넘으며, 남은 값은 위 수용 결정에 따릅니다.
