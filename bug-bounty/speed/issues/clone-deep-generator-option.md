# `clone` 깊은 복제는 1.06이 남고, 줄이는 방법 하나는 결정이 필요합니다

- **종류** — 줄이지 못한 초과와, 판단이 필요한 개선 선택지입니다.
- **행과 경과** — 우선순위 1의 `clone` 깊은 복제 행입니다. 기준 시간은 40.8마이크로초이고 기준은 1.03입니다. 개선 전 1.174 / 1.178에서 개선 후 1.058 / 1.063이 됐습니다(24라운드, 대조군 1.002 / 1.002).
- **남은 비용의 위치** — 프로파일로는 깊은 경로에서 사전 키를 내주는 생성기입니다.
- **선택지** — 생성기를 없애고 키 배열을 색인으로 도는 변경을 만들어 쟀습니다(가지 `perf/common-utils-speed-2`의 커밋 `50bfe1577`, 병합하지 않음). 이 변경을 넣으면 0.964 / 0.955로 통과합니다(24라운드, 대조군 1.004 / 0.996. 이 수치는 실시간 대상 확인을 넣기 전의 대입 경로와 함께 잰 값입니다).
- **걸리는 점** — 생성기는 `Object.keys`와 `getOwnPropertySymbols`가 돌려준 내부 배열을 배열 반복자 규약으로 소비합니다. 그래서 프로그램이 `Array.prototype[Symbol.iterator]`나 생성기 프로토타입의 `next`를 전역으로 바꿔 두면 지금은 그 호출이 관찰되고, 변경 뒤에는 관찰되지 않습니다. 결과 값과 오류, 사용자 객체의 접근자와 프록시 트랩은 같습니다. 재귀 구간(깊이 256 미만)은 이미 색인 반복이라 같은 호출을 하지 않습니다.
- **같은 종류의 차이가 이미 병합된 변경에도 있습니다** — 이번 개선은 내부 장부 객체에 대한 내장 메서드 호출을 여러 곳에서 바꿉니다. `equals`와 `cloneLite`는 내부 `WeakMap`·`WeakSet`을 `Map`·`Set`으로 바꿨고, `clone`은 결과 객체에 대한 `Object.defineProperty` 호출을 줄였으며, `json-schema`는 `new URL('')` 호출을 건너뜁니다. 모두 내장 객체를 전역으로 바꿔 둔 프로그램에서만 보이는 차이입니다. 저는 "사용자가 넘긴 객체에 대한 동작은 같아야 하고, 내부 장부에 대한 내장 메서드 호출 횟수는 계약이 아니다"를 기준으로 삼았습니다. 생성기 변경도 이 기준으로는 허용되지만, 사용자 입력에서 나온 키 배열을 다루는 자리라서 보수적으로 제외하고 결정을 남깁니다.
- **권고** — 위 기준을 확인해 주시면 생성기 변경을 별도 PR로 넣습니다. 기준을 더 엄격하게 잡으신다면 이미 병합된 변경 중 해당 부분도 함께 알려 주십시오. 되돌릴 범위를 정리하겠습니다.
- **결정** — Vincent이 권고를 수용했습니다. 기준은 "사용자가 넘긴 객체에 대한 동작은 같아야 하고, 내부 장부에 대한 내장 메서드 호출은 계약이 아니다"이며, 생성기 변경은 별도 PR로 넣습니다.
- **결과** — PR #689로 병합했습니다. 행은 0.989 / 0.983으로 통과합니다. 독립 검증(2,864개 입력)에서 사용자가 넘긴 객체에 대한 차이는 없었습니다. 전역으로 바꾼 `Object.keys`가 배열이 아닌 값을 돌려주는 경우는 계약 밖으로 두되, 항상 끝나도록 `Array.from`으로 바꿔 읽습니다.
