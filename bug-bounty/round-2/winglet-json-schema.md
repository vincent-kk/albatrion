# @winglet/json-schema 버그 바운티 2라운드 결과

2라운드에서 새로 확인된 문제는 1건입니다. 1라운드 문서([`../round-1/winglet-json-schema.md`](../round-1/winglet-json-schema.md))의 4건은 고쳐진 것으로 보고 제외했습니다. 재현 테스트는 메인 세션에서 다시 실행해 같은 실패를 확인했습니다.

재현 테스트: [`probes/winglet-json-schema/`](probes/winglet-json-schema/)

- 실행하려면 파일을 `packages/winglet/json-schema/src/__bounty__/r2-json/`에 복사한 뒤 `yarn workspace @winglet/json-schema test --run src/__bounty__/r2-json/`를 실행합니다.
- `scanner.r2.test.ts`(테스트 이름이 `K`로 시작)에서는 `K12`만 실패하고, 나머지는 대조 테스트입니다. `resolver.r2.test.ts`(테스트 이름이 `R`로 시작)는 모두 통과하는 대조 테스트입니다.

## 1. 비동기 리졸버가 거부된 `load` 결과를 URI별로 영구히 캐시해, 일시적인 실패 하나가 그 리졸버를 계속 쓸 수 없게 만듭니다

- 심각도: 낮음에서 중간. 같은 리졸버로 다시 스캔해도 `load`가 다시 호출되지 않고 같은 오류가 반복됩니다.
- 영향받는 공개 API: `createReferenceResolverAsync`.
- 어긋난 계약: `packages/winglet/json-schema/docs/en/SPECIFICATION.md:107`은 대기 중인 요청과 완료되었거나 없음으로 끝난 결과만 공유한다고 적고, 로더 오류는 전파된다고만 적고 있습니다. 실패 결과를 캐시한다는 내용은 없고, 재시도는 호출자의 로더가 맡는다고 되어 있습니다.
- 원인: `createReferenceResolverAsync.ts`의 17행과 25행부터 32행에서 거부된 Promise가 `pending` 맵에 그대로 남고, 지우는 코드가 없습니다.
- 1라운드와의 관계: 1라운드 1번(조회 순서에 따라 결과가 달라지는 지연 색인)과 같은 종류입니다. 캐시가 이전 호출의 이력에 따라 결과를 바꿉니다.
- 재현: `K12`. 첫 번째 `load`는 예외를 던지고 두 번째 `load`는 성공하도록 만들었습니다. 같은 리졸버로 두 번째 스캔을 하면 실제 결과는 `{ second: 'network down', calls: 1 }`이고, 기대 결과는 `{ second: 'ok', calls: 2 }`입니다. 스캐너 인스턴스 자체는 다시 쓸 수 있었습니다.
- 확신도: 중간. 명세가 실패 캐시에 대해 명시적으로 말하지 않으므로, 의도된 동작이라면 명세에 그렇게 적는 것이 정리 방향입니다.

## 버그가 아니라고 확인한 가설

- 스캐너는 10,000단계 `properties` 중첩, 10,000단계 `allOf` 중첩, 리프에서 mutate로 전체 복사를 강제하는 경우를 모두 처리합니다. 내장 리졸버로 색인한 경우, 깊은 대상을 같은 자원 안에서 인라인하는 경우, 다른 자원의 깊은 대상을 준비하면서 URI를 다시 쓰는 경우도 스택 오버플로 없이 통과합니다(`K1`부터 `K6`까지).
- 넓은 스키마의 처리 시간은 거의 선형으로 늘어납니다. 하나의 정의를 참조하는 속성 1만 개와 4만 개, 서로 다른 정의 1만 개와 4만 개, `$id` 1만 개와 4만 개, 데이터 키워드가 붙은 교차 자원 참조 2,500개와 1만 개를 비교했고, 모두 입력 배율보다 시간 배율이 8배 미만이었습니다(`K7`, `K7b`, `K7c`, `R2`).
- 스캐너 동작은 명세대로입니다. enter와 exit의 중첩 순서가 어휘 순서를 따르고 같은 entry 객체가 전달됩니다(`K8`). `maxDepth`는 루트를 0으로 세며 경계를 포함합니다(`K9`). 실행 중인 인스턴스에 다시 `scan`을 호출하면 `scan-in-progress`가 나고 바깥 스캔 결과는 보존됩니다(`K10`). 비동기 스캐너에 동시 스캔을 걸면 두 번째만 거부됩니다(`K11`). 비동기 콜백이 예외를 던진 뒤에도 인스턴스를 다시 쓸 수 있습니다(`K12b`). mutate가 루트를 `false`로 바꾸면 결과로 `false`가 캐시되고(`K15`), 다시 스캔하면 이전 출력 캐시가 무효화됩니다(`K16`).
- 순환 참조도 명세대로입니다. 세 자원에 걸친 `$ref` 순환은 `cycle` 결과로 끝나고(`K13`), 자원 간 상호 재귀는 동기와 비동기 모두에서 끝납니다(`K13b`). 스키마 위치 사이의 물리적 순환은 `schema-cycle` 오류가 나고, 데이터 키워드 안의 순환은 복사할 때 멈추지 않습니다(`K14`, `K14b`).
- 리졸버 동작도 명세대로입니다. 내장 자원 안 포인터의 정규 URI는 그 자원 기준으로 만들어지고, 앵커와 포인터 별칭은 같은 URI를 공유합니다(`R1`, `R1b`). 요청 캐시는 호스트 자원별로 분리됩니다(`R3`). 참조 순서를 바꿔도 결과가 같습니다(`R4`). 상대 주소나 이미 등록된 자원에는 `load`를 호출하지 않습니다(`R5`). `$id`와 검색 키가 다른 문서도 검색 키로 찾을 수 있습니다(`R6`, `R6b`).
- `InferValueType`은 소스를 읽어 검토했고, 다중 타입 배열, null만 있는 타입, `nullable`, 열린 객체와 교차 타입 처리에서 문서와 어긋나는 점을 찾지 못했습니다. 타입 검사 재현은 작성하지 않았습니다.
