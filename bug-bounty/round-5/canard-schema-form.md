## 1. A virtual group whose earlier constituent is inactive reports a shortened tuple, so writing its own value back throws and a widget that edits the documented tuple deletes the following stored field.

- Severity: medium. Stored data is silently deleted, or the group's own value is refused, in a plausible layout: a virtual group where a constituent other than the last has an `active` gate, such as `country`, `state` (United States only) and `city`. A grouped FieldInput that reads `value` as `[country, state, city]` shows the city in the state slot; picking a country writes `undefined` into `city`, so the submitted data loses the city; `node.setValue(node.value)` throws `INVALID_VIRTUAL_NODE_VALUES`.
- Affected public API: the virtual group's `value` (the FieldInput `value` prop and `FormHandle.findNode(...).value`), `FieldNode.setValue` on a virtual node, the virtual FieldInput's `onChange`, and `node.children` of a virtual node.
- Contract violated: `docs/agents/skills/schema-form-skill/knowledge/virtual-schema.md:26` ("tuple ordered by `fields`") and `:36` (`node.children[i]` is ordered like `fields`); `src/core/engine/DETAIL.md:11` (an inactive field keeps its tuple position and storage address); predictability: a node's own value is a valid input, and an identity updater gives the same result inside a batch, where `readBatchValue` builds the full tuple, as outside one.
- Root cause: `src/core/engine/settle/utils/compute/childSelection/selectChildren.ts:132-147` builds a virtual node's children from the siblings that are present and skips an absent one (`if (!sibling) continue;` at `:140`); `src/core/engine/behaviors/virtualBehavior/utils/tuple/assembleVirtualTuple.ts` builds the tuple from those children, so later values move forward; the write side indexes by `fields` (`assertVirtualWriteShape.ts:19` requires `fields.length` entries, and `markWrite.ts:86-100` writes `values[index]` to `fields[index]`).
- Relation to earlier rounds: same class as round 4 items 2, 3 and 14 (round 4 class 34, virtual paths as storage addresses).
- Reopens an earlier fix: no; `git log -L` shows `b63bac7f0`, `5528e4026` and `2d7d72d82`, none of them a bug bounty fix.
- Regression of an earlier fix: no.
- Watch list: yes, virtual and alias paths as storage addresses and batch marks.
- Reproduction: `r5-core/virtualNeighbors.test.ts` (unit), a schema with `country`, `state` (`active: '../country === "US"'`) and `city`, loaded with `{ country: 'KR', city: 'Seoul' }`: "the tuple keeps the city at position 2, the position of city in fields" gives `['KR', 'Seoul']`, expected `['KR', undefined, 'Seoul']`; "writing the group its own value back leaves the stored fields unchanged" throws `INVALID_VIRTUAL_NODE_VALUES`; "an identity updater on the group gives the same value outside a batch as inside" throws outside the batch; "a widget that edits position 0 (country) as the documented tuple keeps the city" gives `{ country: 'JP' }`, expected `{ country: 'JP', city: 'Seoul' }`. `r5-core/publicForm.test.tsx` (render and React 18), "choosing a country in the grouped widget keeps the stored city": the widget shows `["KR","Seoul"]` and `getValue()` gives `{ country: 'JP' }`. The all-active control passes.
- Confidence: high; public `Form` on React 19 and 18, plus `buildFieldNodeTree` and `mountFieldNode` driven through public methods. The main session read the cited lines.

## 2. A draft-04 embedded `id` resource resolves its inner `#/definitions/…` against the document root unless something else builds the resource index first.

- Severity: low. It needs a draft-04 compound document; then the form builds a different field from the one the validator checks. With the AJV 6 plugin on `schemaId: 'auto'`, the form builds a number field with default `1` while the validator requires a string, and `validate()` reports a type error the user did not cause.
- Affected public API: `Form` with a `jsonSchema` whose `$schema` is draft-04 and that embeds resources with `id`; the AJV 6 plugin with `createValidator(new Ajv({ schemaId: 'auto' }))`.
- Contract violated: BLUEPRINT-030 in `src/core/engine/blueprint/buildNodes/DETAIL.md:89` (draft-04 declares resources with `id`, and `#` pointers are relative to the containing resource), set by the round 4 item 1 decision; the round 3 item 15 decision that the form and the validator use the same schema; draft-04 core section 7.2; predictability: `$ref: '#/definitions/address'` and `$ref: 'address.json'` build different fields, and reordering sibling properties changes both.
- Root cause: the resource index is built only when a pointer walk meets a string `$id` (`src/core/engine/blueprint/buildNodes/utils/references/resolveReference.ts:45-50`) or a non-root declaration has a string `$id` (`.../utils/declarations/collectDeclarations.ts:58-59`). The round 4 fix taught `getResourceIndex.ts:51-53` to read draft-04 `id`, but these triggers still look only for `$id`, so a draft-04 document builds the index only through a non-fragment reference (`resolveReference.ts:32`), lazily, and templates resolved before that stay cached from the root walk.
- Relation to earlier rounds: round 3 item 15, round 4 item 1, round 1 class 18.
- Reopens an earlier fix: round 4 item 1, commit `12457f2cf`; the trigger lines last changed with the round 3 item 15 commits `73e47569b`, `53a05f27e` and `b3b10604e`.
- Regression of an earlier fix: no; before `12457f2cf` the pointer spelling already built `kind: 1`, and the identifier spelling failed to load.
- Watch list: yes, fragment `$id` and identifier dialects in the compiler.
- Reproduction: `r5-core/draft04Resources.test.ts` (unit): "draft-04 `id` resource reached by JSON pointer resolves its inner #/definitions/kind locally" gives `{ home: { kind: 1 } }`, expected `'house'`; "with the ajv6 plugin bound to schemaId "auto" (README), the loaded form validates its own default" gives value `kind: 1` and `validate()` `[['/home/kind', 'type']]`; "the same draft-04 document gives the same field whichever sibling reference is listed first" fails (pointer first: both `kind: 1`; reversed: both `'house'`). `r5-core/publicForm.test.tsx`, "the reference #/definitions/address builds the resource-local string kind": `{ home: { kind: 1 } }` with no `onError`. The controls pass (draft-07 `$id`, draft-04 by identifier, plain AJV 6 reference).
- Confidence: high; public `Form` on React 19 and 18, and the AJV 6 plugin through its `dist`.

## 3. A rebuilt `context` that holds an `Error` whose own enumerable property reaches a cycle makes the context comparison loop without end.

- Severity: low. The page hangs, but the input is rare: a context object rebuilt on every render that holds a fresh `Error` with a cyclic graph.
- Affected public API: the `context` prop of `Form` and `FormProvider`.
- Contract violated: the round 4 item 7 decision that context comparison terminates for every cycle kind; `docs/agents/skills/schema-form-skill/knowledge/field-input.md:153-154` (context is compared by content). It goes past the cycle limit of `@winglet/common-utils` `equals`, because this package decided that its own comparison terminates.
- Root cause: `src/providers/hooks/contextSnapshot/utils/areContextsEqual.ts:105` hands values whose tag is in `COMPARABLE_TAGS` (`:5-14`, which includes `[object Error]`) to `equals`, which recurses into an Error's own enumerable keys without the visited-pair tracking that round 4 added to `areContextsEqual`.
- Relation to earlier rounds: round 4 item 7 (the same function, another branch); round 4 class 36.
- Reopens an earlier fix: round 4 item 7 (`a2041ad0e`, `09ee0f93e`) and round 3 item 7; `git log -L 105,105` shows only `682b37de1` (round 3 item 7), which introduced the delegation.
- Regression of an earlier fix: no; before `682b37de1` the whole context went through `equals` and looped too.
- Watch list: yes, context comparison.
- Reproduction: `r5-core/contextErrorCycle.test.tsx` (render and React 18) builds the cycle through an enumerable getter that throws after 100,000 reads; "a Form whose rebuilt context holds an Error whose own enumerable property holds the graph re-renders in bounded time", the Error subclass row and the `FormProvider` row give `{ bounded: false }` with frames `areContextsEqual.ts:105`, `useContextSnapshot.ts:15` and `WorkspaceContextProvider.tsx:25` or `ExternalFormContextProvider.tsx:220`. The plain-graph control passes.
- Confidence: high for the behavior; medium that the owner treats this input as supported.

## 4. `resetSubtree()` on a virtual group leaves an inactive constituent's retained value unchanged.

- Severity: low. It needs four steps: edit a gated constituent, gate it off, reset the group, gate it on; the value that reappears is the discarded edit.
- Affected public API: `FieldNode.resetSubtree` on a virtual node.
- Contract violated: `src/core/engine/settle/DETAIL.md:19` (a virtual group reset restores the load-source tuple of its referenced fields); `src/core/engine/DETAIL.md:11`; the round 4 decision that virtual operations resolve to the real storage address; predictability: resetting the owning object restores the inactive constituent.
- Root cause: `src/core/engine/settle/utils/reset/resetFieldNodeSubtree.ts:20-26` reads every target's loaded value and writes the tuple as a load through the virtual node; `src/core/engine/settle/utils/input/markWrite.ts:86-100` distributes it only to the siblings that are present (`if (!sibling) continue;` at `:92`).
- Relation to earlier rounds: round 4 item 2 (the same entry point, with an inactive constituent as the neighboring input). Item 1 has the same skipped-sibling shape on the read side.
- Reopens an earlier fix: round 4 item 2, commit `f3a6cfdae`.
- Regression of an earlier fix: no; before `f3a6cfdae` the same reset erased both fields.
- Watch list: yes, virtual and alias paths as storage addresses and batch marks.
- Reproduction: `r5-core/virtualNeighbors.test.ts`, "resetting the virtual group restores both constituents like resetting the object that owns them": the group reset gives `afterOn: { start: 's0', end: 'e1' }`, while the object reset gives `{ start: 's0', end: 'e0' }`. The control passes.
- Confidence: high; internal build channel driven through public methods.

## 6. With `skipLibCheck: false`, the published React declarations fail with TS2694 for consumers on `@types/react` 18.0.0 to 18.2.5 (and 16.14 or 17.0 releases before 17.0.80), because they name results `import("react/jsx-runtime").JSX.Element`, which those type releases do not export.

- Severity: low. Type-checking only; with `skipLibCheck: true` those annotations silently degrade to `any`. The React peer ranges of these packages admit the affected type releases, and no document limits the `@types/react` version.
- Affected public API: the root declarations of `@canard/schema-form` (56 occurrences, for example `Form.Label` and `Form.ErrorMessage` at `dist/components/Form/Form.d.ts:108` and `:132`), the antd5 plugin (24, `dist/index.d.ts:2`), the antd6 plugin (24), the MUI plugin (21), the antd-mobile plugin (18), `@lerx/promise-modal` (14) and `@winglet/react-utils` (4). This item is the one home for all seven packages.
- Contract violated: the React peer ranges (`>=18 <20`, and `>=16.14 <20` for `@winglet/react-utils`) and the round 4 work on React 18 type compatibility.
- Root cause: under `"jsx": "react-jsx"` (`tsconfig.base.json:12`), TypeScript 5.9 declaration emit names inferred component results through the JSX import source's namespace; `@types/react` exports `JSX` from `react/jsx-runtime` only from 18.2.6 (and 17.0.80), while 18.0.0 to 18.2.5 ship `jsx-runtime.d.ts` as `import './';` alone. An explicit return type on the exported components avoids the reference.
- Relation to earlier rounds: round 4 class 40 (type requirements newer than the consumer configuration: round 4 AJV 8 item 5 and core items 19 and 20); it extends round 3's React 18 type check, which tested only 18.3.23.
- Reopens an earlier fix: no.
- Regression of an earlier fix: no.
- Watch list: no.
- Reproduction: `r5-release/olderReactTypes.test.ts` (unit) copies the installed `@types/react` 18.3.23 and replaces only `jsx-runtime.d.ts` and `jsx-dev-runtime.d.ts` with the 18.2.5 text: "the published React declarations type-check with @types/react 18.2.5 (skipLibCheck false)" reports TS2694 in the seven packages, expected none. - Confidence: high; built `dist` declarations with an emulated type package.

## Hypotheses checked and not bugs

- A batch that mixes `EnableAutomaticWrites` with plain writes on a `disableAutomaticWrites` form keeps the later writes when an earlier `injectTo` throws, reports once, and equals one-by-one calls (`r5-core/batchPartialFailure.test.ts`).
- A throwing `derived` rule does not make an independent rule depend on property order, and a following valid write recovers both orders (`r5-core/deriveChainFailure.test.ts`).
- Inactive fields named `constructor`, `toString`, `valueOf` and `hasOwnProperty` read as absent in expressions, `watch` and `find`, and an `injectTo` aimed at them leaves `Object.prototype` intact (`r5-core/inheritedNameReads.test.ts`).
- 600 seeded sequences over virtual groups in array items (group, field and item writes and resets, `insert`, `remove`, `push`, gates on and off) give the same value inside one batch as one by one (`r5-core/virtualDifferential.test.ts`).
- Static reading of earlier fixes: the nested `FormProvider` fix `decaaecc3` sets the inherited `pluginManager` on both contexts; structural plugin normalization (`bc590215e`, `75b916fbd`) reads the seven declared members and records the hash after success; the radio restore (`52574d3c7`, `7260105c8`) can only take the name of a renamed or removed row; the native reset handler (`93520e866`) ignores portal forms and honors `defaultPrevented`; `replaceAtPath` and `mergeMarkedValue` never store an inherited member. The remaining expression scanner cases fall under the decided path-first rule.
- `areContextsEqual` tracks cycles through `Map` values and compares `Set` members by reference.
- Identifiers (`r5-ids`): 4,000 seeded scope, path and key triples, including `~ / . :`, whitespace, control characters, surrogates, `~input`, `~label`, `~u0020` and numbers, produced no shared id (`resolverInjectivity.test.ts`, internal); two client roots with one React copy and no `identifierPrefix` keep distinct scopes, and label and option clicks stay in their own Form on React 18 and 19 (`clientRoots.test.tsx`); `insert(0)`, `remove(0)` and `insert(1)` followed by `remove(0)` keep ids unique, references inside their rows and radio selections, so round 4 item 6 holds (`arrayMoveReferences.test.tsx`); a `$defs` template used twice gives the same structure as two inline copies, overlapping `anyOf` branches build one node, a property declared in both `then` and `else` keeps ids unique, and a virtual group with `getInputId('end')` and `Form.Label` stays unique (`compositionIds.test.tsx`); the `#/`, `/./` and `/../` spellings of `Form.Label` label the same input, while `#/a%20b` does not resolve `/a b` because percent sequences are literal as the `formatSegment` JSDoc states (`formLabelSpellings.test.tsx`). The core `FieldInputString` lets `inputProps.id` override the input id; that is a consumer-supplied native attribute.
