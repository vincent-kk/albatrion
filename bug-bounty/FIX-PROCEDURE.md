# 버그 바운티 수정 절차

버그 바운티 라운드에서 확인된 항목을 고쳐 `1.0.0/bugbounty` 브랜치에 병합하는 절차입니다. 지휘 세션(coordinator)이 이 문서를 따르고, 작업자에게 보내는 작업 지시서는 이 문서의 규칙을 그대로 옮깁니다. 항목을 찾는 절차는 `.claude/skills/bug-bounty`가 다루며, 이 문서는 수정만 다룹니다.

## 역할과 모델

| 역할 | 에이전트와 모델 | 쓰는 때 |
|---|---|---|
| 지휘 | 메인 세션 | 계획, 작업자 질문에 대한 결정, 병합 |
| 구현 | Orca `claude`, 모델 `claude-opus-5-5` | 패키지 하나의 수정 전체 |
| 계획 검토 | Orca `antigravity`, 모델 `gemini-4-hydrogen-high` | 계획을 세우거나 크게 바꿀 때 |
| 어려운 문제 상의 | Orca `antigravity`, 모델 `gemini-4-argon-medium` | 지휘 세션이 스스로 정하기 어려운 설계 문제 |
| 빠른 검토와 벤치마크 재측정 | Orca `cursor`, 모델 `grok-4.7` | 작업자 보고 뒤, PR 전 |

- Argon은 사용량이 커서 medium 단계만 쓰고, 정말 어려운 문제에만 씁니다. high 단계는 쓰지 않습니다. Argon이 사용량 상한에 걸리면 Hydrogen으로 대체합니다.
- 일반적인 작업자 질문은 지휘 세션이 직접 정합니다.
- codex는 소유자가 쓸 수 있다고 알릴 때만 씁니다.
- 모든 작업자는 `/orchestration`(Orca)으로 시작하며, 지휘 세션은 작업자를 시작한 뒤 턴을 끝내고 Orca가 깨울 때 움직입니다. 메일함을 주기적으로 확인하지 않습니다.

## 작업 단위

- 패키지 하나에 구현 작업자 하나, 워크트리 하나, PR 하나입니다. 워크트리는 `1.0.0/bugbounty`에서 갈라진 Orca 하위 워크트리입니다.
- 구현 작업자는 동시에 8명까지 돌립니다. `@canard/schema-form` 타입 검사가 메모리 약 2.4GB를 쓰므로, 그 이상은 메모리 부족과 벤치마크 오염을 부릅니다.
- 같은 항목이 여러 패키지에 반복되면 선도 패키지가 먼저 고치고 나머지가 그 수정 형태를 따릅니다. AJV 플러그인은 `ajv8`이, UI 플러그인은 `antd5`가 선도합니다.
- 작업자는 자기 패키지 폴더와 `.changeset/`의 새 파일, 저장소 검사가 요구하는 생성 문서만 고칩니다. `bug-bounty/` 아래는 고치지 않습니다. 다른 패키지를 고쳐야 하면 멈추고 지휘 세션에 묻습니다.

## 작업자 절차

순서는 바꾸지 않습니다.

1. **준비.** 의존 패키지를 빌드합니다. 빌드 산출물은 커밋하지 않습니다.
2. **수정 전 벤치마크.** 고칠 함수의 일반적인(버그가 아닌) 입력 경로를 재는 벤치마크를 만들고, 고치기 전 코드에서 기준값을 기록합니다.
3. **실패하는 테스트.** 항목마다 재현 테스트를 패키지의 실제 테스트 위치로 옮기고, 고치기 전 코드에서 문서가 말한 이유로 실패하는지 확인한 뒤, 실패하는 테스트만 먼저 커밋합니다. 통과하거나 다른 이유로 실패하면 확인되지 않은 항목이므로 고치지 않고 보고합니다.
4. **수정.** 근본 원인을 가장 작은 변경으로 고칩니다. 문서화된 정책이 바뀌면 `DETAIL.md`를 코드보다 먼저 고칩니다. 수정 커밋은 테스트 커밋과 분리합니다.
5. **속도 조건.** 아래 절을 따릅니다.
6. **검사.** 패키지의 lint, 타입 검사, 전체 테스트를 실행합니다. PR용 CI가 건너뛰는 렌더, React 18, 프로덕션 테스트도 로컬에서 실행합니다. `scripts/ci/selectAffectedWorkspaces.mjs`가 고르는 소비자 패키지의 테스트도 실행합니다. `@winglet/*` 패키지는 `yarn workspace @albatrion/documents sync-winglet-docs:check`도 실행합니다.
7. **변경 기록.** 소비자가 볼 수 있는 독립된 변경마다 changeset을 하나 씁니다. 호환성이 깨지면 첫 문장에 밝히고 수정 전후 코드를 보입니다.
8. **보고.** push와 PR은 하지 않고 지휘 세션에 보고합니다.

## 속도 조건

- 비율은 일반 입력에서 수정 후 시간을 수정 전 시간으로 나눈 값입니다. 수정 전은 실패하는 테스트 커밋, 수정 후는 브랜치의 최신 커밋입니다.
- 수정 전과 후를 별도 프로세스로 번갈아 10회 이상 실행하고 중앙값을 씁니다.
- 목표는 1.00 이하입니다. 더 싼 알고리즘이 있으면 그것을 택합니다.
- 1.03까지는 측정 오차로 봅니다.
- 1.03을 넘는 것은 정확성에 꼭 필요한 연산일 때만 허용하고, 그때도 최소여야 합니다. 작업자는 추가된 연산, 피할 수 없는 이유, 측정하고 버린 더 싼 대안을 보고합니다. 그렇지 않으면 수정을 다시 합니다.
- 측정 면제: 문서만 고치는 수정, 렌더·할당·effect를 늘리지 않는 JSX 속성 한 줄 변경, 명령줄 플래그와 종료 코드 로직. 면제는 항목마다 이유와 함께 보고합니다.
- React 컴포넌트의 로직 변경은 뽑아낸 순수 함수나 100개 인스턴스 반복 렌더로 잽니다. 명령줄 도구는 프로세스 실행이 아니라 메모리 안의 핵심 함수를 잽니다.

## 결정 규칙

- 코드가 표준이나 공개 문서(README, `docs/`, SPECIFICATION)와 어긋나면 코드를 고칩니다. 기존 테스트가 어긋난 동작을 고정하고 있어도 같습니다. 그 테스트를 뒤집고 호환성 깨짐으로 기록합니다.
- 항목 제목이 문서 불일치이고 코드의 동작이 합리적이면 문서를 고칩니다.
- 확신도가 낮거나, 문서가 따지지 않은 방식으로 기존 소비자를 깨뜨릴 수 있거나, 공개 동작이 다른 두 수정이 가능하면 작업자가 선택지와 권고를 붙여 지휘 세션에 묻고, 그동안 다른 항목을 진행합니다.
- 자주 호출되는 경로에 검사를 추가해야 하는 수정은 속도 조건을 결정에 묶습니다. 가장 싼 검사로도 1.03을 넘으면 문서만 고치고 측정값을 보고합니다.
- 타입 오류를 캐스트로 누르지 않습니다. 항목이 뒤집는 동작을 고정한 테스트 외에는 기존 테스트를 약화하거나 지우지 않습니다.
- 패키지 문서가 "먼저 물어볼 것"으로 정한 변경(공개 타입에서 옵션 제거 등)은 소유자에게 묻습니다.

## PR 전 관문

1. 작업자 보고: 항목별 상태, 실패 커밋과 최신 커밋, 벤치마크 표와 재현 명령, 검사 결과, 뒤집은 기존 테스트, changeset, 남은 위험.
2. Cursor Grok의 독립 검토: 회귀 테스트가 실패 커밋에서 실패하고 최신 커밋에서 통과하는지, 속도 비율이 재현되는지, 무관한 변경이 없는지 확인합니다. 재측정은 한 번에 하나씩만 돌려 다른 작업의 부하가 섞이지 않게 합니다.
3. 검토에서 나온 수정은 해당 구현 작업자에게 돌려보냅니다.
4. 통과하면 작업자가 기준 브랜치 위로 리베이스하고 다시 검증한 뒤 push하고 `1.0.0/bugbounty`를 대상으로 PR을 엽니다.

## 병합

- CI가 통과하고 검토에 남은 지적이 없으면 지휘 세션이 병합합니다.
- 병합은 의존 순서를 따릅니다.
  1. `@slats/agents-assets-sync`, `@winglet/common-utils`, `@winglet/style-utils`
  2. `@winglet/json`, `@winglet/data-loader`, `@winglet/react-utils`
  3. `@winglet/json-schema`, `@lerx/promise-modal`
  4. `@canard/schema-form`과 `ajv8`, `ajv7`, `ajv6` 플러그인
  5. `antd5` 플러그인, 이어서 `antd6`, `mui`, `antd-mobile` 플러그인
- 앞 단계가 병합되면 뒤 단계 작업자는 리베이스하고 의존 패키지를 다시 빌드한 뒤 검사를 다시 돌립니다.

## 라운드 순환

수집과 수정은 번갈아 돕니다. 수집은 바운티 헌터 세션(`bounty-hunter`)이, 수정은 지휘 세션이 맡습니다.

1. **수정.** 지휘 세션이 `bug-bounty/round-N/`의 항목을 이 문서의 절차로 고쳐 모두 병합합니다.
2. **정리.** 라운드의 모든 PR이 병합되면, 그 라운드의 작업자를 닫고 워크트리와 브랜치를 지웁니다. 병합되지 않은 변경이 남은 워크트리는 지우지 않고 소유자에게 알립니다.
3. **인계.** 다음 라운드 문서가 없으면, 지휘 세션이 바운티 헌터 세션에 수정이 끝났다고 알리고 대기합니다. 알릴 때 수집이 끝나면 라운드가 정리된 경로(`bug-bounty/round-{n}` 형태)를 돌려 달라고 요청합니다.
4. **수집.** 바운티 헌터 세션이 새 HEAD에서 버그 바운티를 진행하고, 끝나면 경로를 지휘 세션에 알립니다.
5. **기록.** 지휘 세션이 전달받은 라운드 자료를 `1.0.0/bugbounty`에 커밋하고 올립니다.
6. 1번으로 돌아갑니다.

라운드가 거듭될수록 앞 라운드의 수정 위에 다시 손을 대게 되므로, 회귀를 막는 규칙을 더합니다.

- 수정을 시작하기 전에, 라운드의 재현 테스트를 현재 HEAD에서 다시 실행합니다. 수집 시점과 HEAD가 다르면 이미 고쳐졌거나 원인이 달라진 항목이 있을 수 있고, 그런 항목은 고치지 않고 보고합니다.
- 앞 라운드에서 추가한 회귀 테스트는 약화하거나 뒤집지 않습니다. 새 항목이 앞 라운드의 결정과 충돌하면 작업자는 멈추고 지휘 세션에 묻고, 지휘 세션은 소유자에게 알립니다.
- 작업 지시서에는 그 패키지에서 앞 라운드가 고친 항목과 내린 결정을 적어, 작업자가 같은 코드를 되돌리지 않게 합니다.
- PR 전 검토는 앞 라운드의 회귀 테스트가 모두 통과하는지, 앞 라운드에서 잰 벤치마크가 느려지지 않았는지도 확인합니다. 속도 비율의 기준은 그 라운드의 수정 전 커밋이며, 앞 라운드에서 얻은 속도 이득을 깎는 수정은 느려진 것으로 봅니다.
- 한 패키지의 수정이 다른 패키지에서 숨어 있던 결함을 드러내면, 뒤 단계 작업자가 리베이스할 때 실패하는 테스트와 수정을 함께 넣습니다.

## 소유자에게 남기는 것

- 커밋, PR 병합, 워크트리와 브랜치 같은 개발 환경의 관리는 지휘 세션이 합니다. 지휘 세션은 자기가 만들거나 전달받은 파일만 커밋하고, 작업 폴더에 있는 다른 세션의 미완성 변경은 건드리지 않습니다.
- 작업자 워크트리(`bb-*` 폴더)는 저장소 폴더 안에 생기므로 `.git/info/exclude`로 제외합니다. 커밋에 들어가면 하위 모듈 링크로 기록되어 기준 브랜치를 오염시킵니다.
- 지휘 세션은 결정이 공개 동작을 바꿀 때마다 무엇이 바뀌는지 소유자에게 알립니다.
