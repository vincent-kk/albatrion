# 03단계 노드·정착 성능 기록

이 문서는 03단계/PR-2의 측정값과 원인 분석을 **구현 완료 후 별도로 착수할 최적화 작업의 참고 자료**로 보존합니다. 현재 구현 단계에서 최적화를 진행하면 전체 원장의 계약과 단계별 구현을 흔들 수 있어, 추가 최적화는 구현이 끝난 뒤 별도 작업으로 요청합니다. [bench-report.md](./bench-report.md)의 `소유자 수용 (2026-09-30)`은 기록된 수치와 판정을 수용한 것이며 최적화의 승인이나 착수를 뜻하지 않습니다. 아래 원인 분리 실험은 폐기한 임시 복사본에서만 수행했고 실제 엔진은 변경하지 않았습니다.

## 지표, 환경, 재현

측정 기기는 MacBookPro18,2(M1 Max, 64 GB), Darwin 25.6.0입니다. 런타임은 Node.js 26.10.0/V8과 `/opt/homebrew/bin/bun` 1.4.2/JSC입니다. 이 문서의 벤치 실행은 서로 겹치지 않게 순차적으로 진행했습니다. 패키지 루트에서 다음 명령을 실행합니다.

```sh
node --import tsx bench/node-and-settle.bench.ts
/opt/homebrew/bin/bun bench/node-and-settle.bench.ts
```

`B1`은 혼합 10,000노드의 `value`·`type` 읽기, `B2`는 5,001노드 전체 트리의 잔존 힙/노드, `B3`는 숨은 맵 또는 구조, `B4`는 정착 읽기 자리의 수신자 레이아웃 대리값입니다. `B5`는 50필드 중 숫자 키 하나를 쓰고 루트 값을 관찰하는 처리량, `B6`는 청사진 준비 후 혼합 10,000노드의 생성·초기 로드 시간입니다. `18C-15`·`18C-67`·`18C-81`은 각각 활성 조각 수, 잠복 원본의 조상 깊이, 루트로 옮긴 게이트 수에 따른 비용입니다. 시간 측정은 새/레거시 각 100표본(준비 20회, `B6` 준비 5회), `B2`는 7표본 중앙값입니다. 처리량은 `1000/meanMs`입니다. 두 엔진은 한 프로세스에서 같은 입력을 받습니다. 전체 아홉 행의 기준선과 판정은 [bench-report.md](./bench-report.md)에 있습니다. `bench:baseline`의 `results/baseline.json`은 React/UI 작업과 입력·완료점이 달라 이 코어 수치와 직접 나누지 않습니다.

2026-09-30에 원본 스크립트를 Node 세 번, Bun 한 번 순차 실행했습니다. 괄호는 같은 실행의 레거시 값입니다. 범위는 Node 세 실행의 최소–최대이며 Bun은 한 실행이므로 변동 폭을 추정하지 않습니다.

`B3`와 `B4`는 재실행하지 않았습니다. 기존 판정은 V8의 `%HaveSameMap` 구현 8종/행 8종 동일, JSC에서는 프로토타입·필드 순서만 8/8 확인, 두 런타임 모두 `B4` 대리 레이아웃 1개이고 실제 IC 자리 수는 미측정입니다. `18C-15`·`18C-67`·`18C-81`의 최신 확정 100표본 수치는 [bench-report.md](./bench-report.md)의 아홉 행에 유지합니다.

`B1`의 Node 전체 스크립트 첫 두 실행에는 각각 5.26 ms와 7.79 ms의 새 엔진 단일 표본이 끼어 평균을 훼손했습니다. 세 번째의 최댓값은 0.145 ms였습니다. 같은 읽기 루프와 10,000노드 입력을 분리하여 준비 200회·측정 1,000표본으로 세 번 더 실행한 결과 새 엔진은 45,137–46,324회/s(중앙 표본 21.29–21.88 µs), 레거시는 32,152–33,125회/s(중앙 표본 30.33–30.71 µs)였습니다. 세 실행 모두 새 엔진이 36.3–44.1% 빠르므로 정상적인 정상 상태 읽기는 `guard:check`의 15% 하락 선 안입니다. 다만 원본의 100표본 평균은 드문 중단에 민감하며, 이 결과가 원본 세 실행의 불안정을 없애지는 않습니다. 분리 측정은 임시 벤치 복사본으로 수행했고 정식 스크립트는 수정하지 않았습니다.

## Bun에서만 역전되는 이유

다음 비율은 [bench-report.md](./bench-report.md)의 동일 실행 100표본 확정값을 계산한 것입니다. `새/레거시`와 `Bun/Node`는 처리량 비율입니다.

| 작업 | Node 새/레거시 | Bun 새/레거시 | 새 엔진 Bun/Node | 레거시 Bun/Node |
| --- | ---: | ---: | ---: | ---: |
| `B5` | 1.40× (66,390/47,454) | 0.51× (136,987/269,294) | 2.06× | 5.67× |
| `B6` | 1.15× (40.23/35.04) | 0.55× (49.33/88.99) | 1.23× | 2.54× |

이번 재측정에서도 방향은 같았습니다. `B5`의 Node 새/레거시는 약 1.31–1.38×, Bun은 0.66×이고, `B6`의 Node는 약 1.20–1.23×, Bun은 0.59×입니다. 특히 레거시의 Bun 이득이 새 엔진보다 큽니다. Bun의 `B5` 레거시 처리량은 기존 실행 269,294회/s에서 이번 실행 189,035회/s로 달라져 JIT 준비·측정 변동에도 민감합니다.

동일 소스의 임시 복사본에 타이머를 넣고 `B5` 10,000쓰기 및 `B6` 105로드(준비 5회 포함)를 각 런타임에서 순차 실행했습니다. 이 긴 실행은 원본의 100표본과 JIT 상태가 다르고 타이머 자체도 최적화에 영향을 주므로 아래 절대 시간을 원본 처리량으로 환산하지 않습니다. `생성`·`병합`은 `계산`에 포함되고, 레거시의 `루트 읽기`는 `객체 합성`을 포함합니다.

| 계측 단계 | `B5` Node µs/쓰기 | `B5` Bun µs/쓰기 | `B6` Node ms/로드 | `B6` Bun ms/로드 |
| --- | ---: | ---: | ---: | ---: |
| 새 엔진 표시 | 0.16 | 0.13 | 0.99 | 0.70 |
| 새 엔진 계산·호스트 바퀴 | 5.09 | 1.95 | 20.20 | 19.02 |
| └ 객체 `assemble` (`B5` 계산 내부) | 3.52 | 1.06 | — | — |
| └ 유효 스키마 병합 (`B6` 계산 중, 루트 포함) | — | — | 1.36 | 1.15 |
| └ 노드 생성 (`B6` 계산 중, 루트 포함) | — | — | 3.51 | 3.01 |
| 새 엔진 전이 | 0.11 | 0.08 | 1.67 | 0.78 |
| 새 엔진 커밋 | 0.81 | 0.43 | 4.80 | 1.77 |
| 새 엔진 작업 집합 해제 | 0.55 | 0.44 | 0.006 | 0.005 |
| 레거시 숫자 노드 쓰기 | 0.38 | 0.23 | 1.19 | 0.77 |
| 레거시 루트 객체 합성 (`B5` 읽기 내부) | 20.01 | 1.57 | 2.35 | 1.06 |
| 레거시 팩터리 전체의 재귀 중복 제거 시간 | — | — | 26.90 | 11.07 |

`B5`에서 레거시는 숫자 노드의 `setValue`→`NumberNode.__emitChange__`→부모 `BranchStrategy`의 초안 기록→루트 `value`의 지연 합성 경로를 탑니다. 계측한 10,020번의 루트 읽기는 합성을 10,020번 호출했지만 `BranchStrategy.__handleEmitChange__`는 측정 루프 안에서 0번 호출했습니다. 기본 `Overwrite`에는 `Batch`가 들어 있고, 루트 이벤트의 확정은 이 동기 루프 뒤에 남습니다. 따라서 `B5`는 양쪽의 루트 값 **관찰**은 확인하지만 레거시의 완전한 루트 커밋까지 같은 시점에 기다리는 시험은 아닙니다. 새 엔진은 매번 `markWrite`→`computeNode`→`transitionSettlement`→`commitSettlement`을 마칩니다.

레거시의 지연 합성은 50키 기존 값과 1키 초안의 `equals(base, draft)`를 거쳐, 병합된 객체에 `sortObjectKeys`를 적용합니다. 임시 복사본에서 이 두 단계만 차례로 건너뛰되 `B5` 관찰값은 유지하자 레거시 Node 총시간은 약 20.65→16.56→0.78 µs, Bun은 약 1.98→1.21→0.69 µs였습니다. 편집 자체가 JIT 코드 형태를 바꾸므로 이 차이를 두 함수의 독립 비용으로 더할 수는 없습니다. 별도 100,000회 소실험에서도 같은 50키/1키 `equals` 포함 경로는 Node 0.67 µs 대 Bun 0.031 µs, 객체 펼침·키 목록 준비를 포함한 50키 `sortObjectKeys` 경로는 Node 10.78 µs 대 Bun 0.77 µs였습니다. 둘 다 객체 키 열거·배열 생성을 포함합니다. 이 결과는 JSC가 레거시의 **객체 비교·키 정렬 코드 경로**를 이 입력에서 특히 빠르게 실행한다는 설명을 강하게 지지합니다. Node에서 레거시의 이 비용이 커서 새 엔진이 이기고, Bun에서는 그 비용이 크게 줄어 새 엔진의 동기 정착 비용이 드러납니다.

새 엔진의 `B5` 전이를 임시 복사본에서 생략해도 Bun 총시간은 약 3.69→3.44 µs에 그쳤습니다. 계측 시 커밋은 Bun 약 0.43 µs/쓰기이며 `revision`·`typeMismatch` 기록·`Refresh` 대상·잠복 원본 메모를 관리합니다. 이 계약 작업과 재사용 Map/Set, 키 순서 보존 합성이 비용에 기여하지만 전이 한 단계만으로 역전을 설명하지는 못합니다. `B6`에서는 새 엔진 계산이 Bun에서도 약 19 ms이고 레거시 팩터리 경로는 Node 26.90→Bun 11.07 ms로 크게 빨라져 같은 방향의 역전을 만듭니다. 새 엔진은 자식별 유효 선언 선택, 초기형 확인, 잠복 원본·경고등·revision 커밋도 수행합니다.

`BEHAVIORS[type][strategy]`는 생성 시 행을 고르는 구조이며 이후 `behavior.assemble`·`project` 호출이 있습니다. 레거시의 종류별 클래스·상속·직접 필드 쓰기와 비교하면 JSC의 코드 형태별 최적화 차이는 가능한 보조 원인입니다. 그러나 새 엔진의 `B5` 계산도 Node 5.09→Bun 1.95 µs로 빨라지므로 JSC가 행 디스패치 자체를 유독 느리게 한다는 단독 설명은 맞지 않습니다. 행 호출을 단일형으로 바꾼 통제 실험이나 두 엔진의 IC 계측은 없으므로 그 기여를 확정하지 않습니다. `B3`의 V8 동일 맵과 `B4`의 레이아웃 대리값은 JSC 숨은 맵 또는 메가모픽 IC를 증명하지 않습니다. `B2`는 새 엔진의 **잔존** 힙이 더 작다는 사실만 보이며, 임시 할당과 GC 중단은 직접 계측하지 않았습니다. 객체 키 열거가 할당을 포함하므로 JSC의 할당·GC 특성이 위 차이에 섞였을 가능성은 남습니다.
