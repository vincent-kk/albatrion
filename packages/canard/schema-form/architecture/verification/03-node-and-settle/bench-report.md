측정 환경: MacBook Pro (MacBookPro18,2, Apple M1 Max, 64 GB, arm64), Darwin 25.6.0; Node.js 26.10.0 (V8), Bun 1.4.2 (JavaScriptCore). 수정 후 전체 스크립트를 단독 순차 실행했다: `node --import tsx bench/node-and-settle.bench.ts`, `/opt/homebrew/bin/bun bench/node-and-settle.bench.ts`. 표의 표본 수는 런타임별 값이며, 새·레거시 쌍은 각각 그 수만큼 측정했다. 시간 행은 준비 20회 뒤 표본을 기록한다(B6 준비 5회). `results/baseline.json`은 `@aileron/benchmark-form`의 기존 `guard:check` 기준선이다. Form Rendering v2 516.75/s, Scale Interact Flat-50 70.82/s, Scale Render Flat-500 8.89/s이며 각 5회 반복 표본이다. UI 렌더·상호작용 하니스라 위 코어 행과 입력 및 완료점이 달라 수치를 직접 나누지 않았다. 판정에는 같은 실행의 레거시 쌍에서 얻은 100개 표본 처리량을 사용했다. 회귀 정의는 평균 처리량 15% 초과 하락 **동시에** Welch p<0.05이다.

B3의 숨은 맵 동일성은 V8 자식 프로세스에서 `--allow-natives-syntax`와 `%HaveSameMap`으로 직접 검사했다. Bun 1.4.2는 이 V8 고유 문법을 파싱하지 못해 `SyntaxError: Unexpected token '%'`가 발생하므로 JSC Structure 동일성을 직접 판정할 수 없다. Bun에서는 노드 8종과 동작 행 8개의 프로토타입 및 `Object.getOwnPropertyNames`의 순서가 각각 일치하는지만 확인했다. 이는 객체 모양의 대리 검사이며 숨은 맵 일치의 증거는 아니다.

03 최종 레거시 자료 `baseline/core-legacy-final.json`은 e5a6c8061에서 `yarn workspace @canard/schema-form bench:baseline`으로 측정되었다. 관련 참고값은 5필드 트리 생성 0.024320 ms, 파생 연쇄 입력+타이머 drain 1.333031 ms이다. 10,000노드 생성과 동기 키 입력의 직접 기준선은 그 자료에 없으므로 위 표의 동일 실행 쌍이 최종 판정 기준이다. 02 자료 `../02-foundation-and-blueprint/baseline/core.json`의 해당 값 0.024450/1.199042 ms는 #347·#349 전의 55ed75504 측정치이므로 최종 비교에 쓰지 않았다(LANDING-159).

느린 행의 원인과 범위: B2는 노드 객체 단독이 아닌 유효 스키마·런타임·출력 등을 포함한 전체 트리 힙 차이다. Bun의 힙 차이는 7개 독립 프로세스 표본으로 측정했다. B5는 양쪽 모두 호출 뒤 루트 값의 새 입력을 확인하며 이벤트 배달은 제외한다. 객체 키 조립의 반복 검색을 제거해 Bun 새 엔진은 이전 45,229/s에서 63,549/s로 측정되었지만, 같은 실행의 레거시 190,263/s보다 낮다. 남은 한 키 쓰기의 동기 기록·재계산·전이·커밋 비용은 B6의 자식 수 제곱 결함과 구별한다. B6는 동일 10,000필드 스키마·초깃값에서 청사진을 재사용한 새 엔진의 팩터리+로드와 레거시 `nodeFromJSONSchema`를 비교한다. 둘 다 자식 10,000개를 만든다. 수정 뒤 차이는 Node 1.70배, Bun 4.16배이며 내부 작업은 동일하지 않다.

B6의 수정 전 CPU 프로파일(Node `--cpu-prof --import tsx`, 총 4,878개 표본)은 `markWrite.ts` 3,317개, `getTransitionCap.ts` 878개, `assembleObject.ts` 71개였다. `markWrite`는 원본 키마다 전체 자식 선언에 `.some()`을 실행했고, `assembleObject`는 활성 키마다 누적 이름 배열에 `.includes()`를 실행했다. `getTransitionCap`은 게이트를 세며 노드별 선언 배열과 `flatMap` 결과를 만들었다. 수정은 선언 이름·조립 이름의 멤버십을 한 번 인덱싱하고 게이트를 임시 배열 없이 센다. 초기 로드 회귀 시험은 선언 이름 읽기가 1,000개에서 517,500회, 2,000개에서 2,035,000회였던 수정 전 경로에서 실패했고, 수정 뒤에는 2.2배 상한을 통과했다.

같은 혼합 평면 객체의 별도 순차 로드 측정 중앙값(ms, 크기마다 3회, 청사진 준비 제외): 자식 1,000/2,000/5,000/10,000개 순서로 수정 전 Node는 20.50/61.89/363.84/1,410.89, 수정 후 Node는 7.22/9.22/27.97/58.57, 수정 후 Bun은 6.08/10.94/29.66/56.83이었다. 단계 측정은 전체 B6의 100표본 평균과 일치할 필요가 없다.

수정 전 Node 2배 입력(5,000→10,000)의 3.88배 시간 증가가 수정 후 2.09배로 줄었다. 전체 B6 평균은 이전 Node 1,400.32ms/Bun 1,277.91ms에서 50.76/48.33ms로 줄었다. 별도 단계 측정에서 청사진 분석 1회는 이전 Node 75.5ms/Bun 91.5ms였고, 루트 팩터리 단독은 0.0085/0.0063ms였으며, 모두 B6 로드 비교에서 제외한다. 18C-15와 18C-81은 활성 조각과 게이트가 늘며 평가 작업이 증가한다. 18C-67은 입력을 미리 만들고 잠복 메모 갱신을 확인하지만 깊어진 전체 루트 쓰기도 포함한다.
