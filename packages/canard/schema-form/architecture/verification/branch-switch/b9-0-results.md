# B9-0 — 설계 Ⅲ 비용 지도와 정적 준비물 진단

H1의 차단 조건은 지지되며, 예산은 이번 창 단위 1,246µs·B5 단위 근사 환산 약 1,009.6µs로 예상 하한 1,100µs 아래의 경계입니다. H3의 일반 형제 경로 200~300µs 절감 예상은 뒤집히고 H5의 고정분 해석은 약화됩니다. H6는 비용 위치만 확인되고 크기는 B5 단위 근사 환산 약 2.0~2.8µs로 예상 3~8µs 아래라 미확정입니다. 실제 최적화 절감량은 이번 측정 PR의 판정 대상이 아닙니다.

제품 기준은 B11 병합 머리 `4d0fa4a12`입니다. 제품 변경 없이 computeNode·finalizeExits의 하위 비용, 준비된 경로의 형제 기울기, 정적 준비물이 막히는 조건, 행 시간과 단계 시간의 차이를 확인합니다. B5의 기준 `ad0be79ba`와 다르므로 과거 절대 시간과 이번 절대 시간을 동일한 제품의 A/B로 해석하지 않습니다.

## 입력과 검증

`src/**`는 기준 머리와 바이트가 같습니다. 지정 build를 두 번 실행해 `index.mjs`, `index.node.mjs`, `index.cjs`, `index.d.ts`의 SHA-256과 바이트 수가 같음을 확인했습니다. [빌드 대조](raw/b9-0/build-verification.json)가 기준과 최종 해시를 함께 보존합니다. 배포 산출물은 커밋하지 않습니다.

B6 장치와 이번 `wrapped` 번들은 같은 제품 입력에서 바이트가 같고 타이머 선언 경계도 같습니다. 새 함수·영역 타이머는 `supplemental`에만 있습니다. 별도의 `gap` 번들은 쓰기 진입과 커밋 뒤 배달을 계측하고, `diagnostic`은 시계 없이 캐시와 재사용 콜백을 읽습니다. [계측 manifest](raw/b9-0/stage-manifest-base.json)는 각 타이머의 소스와 scratch 변환 영역을 기록합니다. B11에서 제거한 `DetachedWriteAddress.retain`은 `absentSupplementalStages`에 명시하며 실제 함수가 있으나 0회 호출된 경우와 구별합니다.

도구 합성 검사·ESLint·`tsc --allowJs --checkJs --noEmit`을 통과했습니다. 무시간 smoke는 번들당 한 프로세스에서 여섯 행을 검사했습니다. 총 202동작이며, legacy oneOf-80의 120회 연속 쓰기로 이전 가드 오류의 원인도 확인했습니다. 마운트·값 검사와 sample 사이 macrotask 양보는 시간 구간 밖입니다. [무시간 적재 기록](raw/b9-0/untimed-load-check.json)은 PID와 행별 동작 수를 보존합니다.

## 프로토콜과 해석

여섯 행에 대해 ledger·supplemental·gap을 각 10개의 독립 프로세스로 실행하며 프로세스마다 20예열·100표본입니다. 모든 수치는 쓰기 한 번의 µs입니다. ledger 프로세스는 dist·unwrapped·wrapped·공개 0.16.1의 실행 순서를 회전하고, supplemental과 gap은 각각 unwrapped와 번갈아 실행합니다. 공개 0.16.1은 품질 기준으로만 사용합니다. 형제 fixture에서 x/y 기본값이 바뀌는 legacy와 기존 값을 유지하는 current의 차이는 그대로 검사합니다.

총시간은 프로세스 최소값들의 중앙값과 프로세스 중앙값들의 중앙값을 함께 보존합니다. 단계 표의 대표값은 프로세스별 표본 중앙값 10개의 중앙값입니다. 폭은 프로세스 중앙값의 최소~최대입니다. 개별 중앙값을 더한 값은 총합 중앙값과 같지 않습니다. 원시 각 표본에서는 중첩 타이머 self와 everythingElse의 합이 행 시간과 일치해야 합니다.

scoped self는 가장 가까운 기존 B6 경계에 추가 타이머의 self를 귀속합니다. 따라서 `computeNode/sameValue`는 기존 updateOutput 경계 아래의 sameValue와 구별합니다. 재귀 sameValue의 inclusive 합은 중복될 수 있어 비용 분할에는 self를 사용합니다. supplemental에는 추가 계측과 그에 따른 최적화 영향이 포함되므로 해당 시간을 그대로 제거 가능한 제품 시간으로 간주하지 않습니다.

leaf 기울기는 payload-12와 oneOf-80의 차이를 추가 들고 나는 잎 18개로 나눕니다. 일반 경로의 형제 기울기는 siblings-1000과 siblings-0의 차이를 1,000으로 나눕니다. 준비 경로는 oneOf-80에 형제 250개·1,000개를 추가하며 0→250, 0→1,000, 250→1,000을 함께 봅니다. oneOf 형상은 `row.siblings`를 보존하는 원래 fixture 생성기로 구성합니다.

## 정적 준비물 — 직접 진단

각 fixture의 첫 전환 쓰기 직후 루트 호스트를 읽었습니다. 콜백 횟수는 이후 두 번의 쓰기에서도 같았습니다. [정적 준비물 원시](raw/b9-0/static-preparation.json)는 시간 표본이 아닙니다.

분할은 정적 엔트리를 유지합니다. siblings에서 준비물을 막는 것은 동명 x/y의 복수 선언으로 `null`이 된 직접 계획입니다. 콜백 횟수는 일반 경로에서 쓰기당 `2 × (S + 2)`이며 준비 경로에서는 0입니다. 이 관찰은 H1의 원인 가설을 확인합니다. B2-P2 결과 문서 끝에 정정 문단을 덧붙였습니다.

## 이전 중단 창

기준 `699cbd733`에서 연 이전 창은 첫 ledger 프로세스의 공개 0.16.1 레인이 `INFINITE_LOOP_DETECTED`를 발생시켜 완료 프로세스 0/180으로 끝났습니다. [중단 기록](raw/b9-0/aborted-window/summary.json)은 새 창의 결과에 합치지 않습니다. 원인은 러너가 Promise 작업만 양보해 macrotask에서 초기화되는 배치 가드에 101번째 배치를 누적한 것입니다. 가드 상한 100이나 legacy 번들을 바꾸지 않고 canonical measurePair와 같은 타이밍 밖 `setTimeout(0)` 경계를 복원했습니다. 실제 창 재개는 B11 rebase·수정 커밋·새 무시간 smoke 이후 코디네이터의 명시적 허가를 받았습니다.

## 행 대 단계 차이와 everythingElse

원시 근거는 [단계 요약의 rowStageGap](raw/b9-0/stages.json)과 [gap 원시](raw/b9-0/row-gap.json)입니다. [B5 결과](b5-results.md)의 106.729 − 82.709 = 24.020µs는 서로 다른 러너의 차이였습니다. 진입·배달은 두 총시간 안에 모두 들어 있으므로 그 차이에 양의 항으로 더하면 안 됩니다.

이번 창의 같은 프로세스 짝에 대해 **row − wrapped = (dist − unwrapped) − (wrapped − unwrapped) + residual**을 사용합니다. 각 항은 프로세스 중앙값 차이들의 중앙값이며 독립된 중앙값 결합의 잔여를 유지합니다.

| 항                                                   | µs      |
| ---------------------------------------------------- | ------- |
| 같은 프로세스 paired row − wrapped                   | -15.760 |
| 빌드/장치 차이 dist − unwrapped                      | 16.365  |
| 타이머 효과 wrapped − unwrapped                      | 31.104  |
| 창 안의 잔여                                         | -1.021  |
| B5 차이                                              | 24.020  |
| B5 − 이번 paired 차이: 기준·러너·통계·창 사이 미귀속 | 39.780  |

항등식은 -15.760 = 16.365 − 31.104 + (-1.021)µs입니다. 전체 행 중앙 393.313와 wrapped 중앙 422.479를 단순히 뺀 값은 paired 통계와 다릅니다. 과거 24.020µs를 고정된 제품 누락 비용으로 볼 근거는 없으며, 역사적 차이의 미귀속 39.780µs를 이번 진입·배달 비용으로 채우지 않습니다.

| 기존 비교 장부 바깥 비용의 gap 진단                      | µs     |
| -------------------------------------------------------- | ------ |
| writeFieldNode 진입 전                                   | 4.250  |
| writeFieldNode self: 문맥·scratch·미계측 정착 작업       | 22.312 |
| runDeliveryWaves inclusive                               | 0.750  |
| deliverWave subscriber 경계                              | 0.000  |
| gap everythingElse                                       | 13.240 |
| gap everythingElse − 진입 전: 남은 사슬 종료·bookkeeping | 8.989  |

gap 번들은 writeFieldNode와 배달을 추가 경계로 꺼냈으므로 gap everythingElse 자체의 분할은 진입 전 + 남은 사슬 종료입니다. writeFieldNode self와 배달도 원래 비교 장부에서는 이름 없는 부분에 속합니다. fixture의 명시적 subscriber는 0이며 onChange는 no-op입니다. 일반적으로 deliverWave는 flushQueuedEvents에서도 실행되므로 subscriberWave가 항상 runDeliveryWaves에 포함되지는 않습니다.

## 설계 Ⅲ 가설에 미치는 영향

기존 예상은 [설계 Ⅲ 비용 모델](../../plan/branch-switch/design-iii.md)의 값입니다. 최적화를 실행한 A/B가 아니므로 아래 수치는 제거 가능한 후보 예산과 원인에 대한 판정입니다. 실제 절감량은 다음 PR에서 검증합니다. H3·H5·H6는 selfNetUs를 사용하며 작은 음수는 이득으로 계산하지 않습니다.
