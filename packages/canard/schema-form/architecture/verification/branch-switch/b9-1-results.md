## H1 — 정적 분할과 동적 선택

- 정적 준비물은 직접 계획이 null이어도 고유 정적 분할을 근거로 준비합니다. 고정 baseline은 재사용하고 동적 엔트리만 작성 순서로 선택합니다.
- 선택 중에는 고정 baseline을 읽을 수 있는 사적 동적 view를 사용합니다. 중간 게이트가 키를 열거할 때에는 일반 객체의 키 순서를 합성하며, 최종 공표는 일반 자체 속성 객체입니다. 최종 동적 이름·노드가 같으면 직전 structure와 children 참조를 그대로 씁니다.
- 형제 1,000의 실패 우선 시험에서 재사용 콜백은 **2,004 → 0회**, 자식 목록 비교는 **4 → 0회**입니다. 개선된 경로의 전체 `Object.assign`과 현재 호스트 `Object.values` 호출도 각각 **0회**입니다. 일반 모드와 verify 모드를 함께 검증합니다.
- 기존 준비물 8시험, load/reset·재진입·이동·실패 수명 7시험, 정적 분할 3시험, shared x/y의 skip·shadow 2시험이 통과했습니다. 숫자 키 순서와 예약 이름, 이전 structure·children 불변도 검증했습니다. 최종 전체 관문을 대신하는 수치는 아닙니다.
- verify 전용 이력 파일의 두 시험에서 선택 이력 25개와 바퀴 이력 15개의 방문 기록 외 관측 바이트가 유지되었습니다.
- 비용은 준비 시 O(S+K), 반복 선택 시 동적 K개이며, 구성원 변화 또는 중간 형상 열거에는 O(S+K)가 필요합니다. 준비물은 O(S+K)의 baseline·자식 목록·직전 선택 참조를 보유하고 정착의 동적 view는 O(K)입니다. 전체 조립의 잔여 선형 비용은 H2의 범위입니다.

## H8 — 존재 변화의 동적 후보 비교

- 정착별 동적 이름·형상 증인을 보관하고, 준비된 정적 자식이 바뀌지 않은 호스트는 동적 후보만 비교합니다. 이전 이름의 교체·이탈, 현재 이름의 진입, 투영 변화의 순서를 유지합니다.
- 형제 1,000의 실패 우선 시험에서 이전 structure 전체 키 열거는 **1 → 0회**입니다. 기존 투영 변화 시험 6개와 존재 읽기 시험도 같은 기대값으로 통과했습니다. 최종 unit·render·verify 전체도 통과했습니다.
- null 원본·호스트 진입 및 재진입·퇴장·소멸·증인 불일치에는 해당 호스트의 원래 전체 비교로 후퇴합니다. 선언 밖 키와 extras는 structure의 자식이 아니며, 분배 입력은 정적 준비물을 무효화해 원래 경로를 사용합니다. 투영 기준선은 계속 비교합니다.
- 정상 준비 경로의 비교는 동적 후보·투영 기준선 수에 비례하고, 정착별 증인 Map과 이름 참조만 일시 보유합니다. 원래 비교로 후퇴하면 기존 전체 형상 비용을 유지합니다.

## H4 — 정적 선언 조회와 required 배달

- 정적 선언 조회를 derive와 settle의 공통 부모인 engine의 구조 조회로 공유합니다. 부모의 경로·청사진과 자식 identity가 준비물의 증인과 일치하면 기존 ID 배열을 읽고, 그렇지 않으면 커밋 경로 조회로 후퇴합니다. 현재 정착의 선택 맵이 있으면 그 선택이 우선합니다. default는 control 계층의 같은 경로를 사용합니다.
- 수정 전 실패·수정 후 통과한 시험에서 정적 control/default 조회의 커밋 키 읽기는 **2 → 0회**, derive의 커밋 키 읽기는 **1 → 0회**입니다. 증인을 제거한 뒤의 커밋 후퇴와 현재 선택 우선도 확인했습니다.
- 코디네이터가 승인한 required 정책은 배열 identity가 같으면 최종 진입 자식만 계산하고, 다르면 기존 자식도 다시 계산합니다. 형제 1,000 전환의 기존 required 읽기는 **1,000 → 0회**이며 선언 키 계산은 **16회 이하**입니다. 배열 변화에 따른 기존 자식의 양방향 갱신과 같은 배열 아래 새 진입 자식의 required도 통과했습니다.
- 조회는 O(1)이고 새 ID 배열이나 영구 색인을 만들지 않습니다. required가 같은 경우의 임시 목록·필터는 정착의 진입 수에 비례하고, 배열이 다르면 기존 전체 자식 순회를 유지합니다.
- 첫 unit 전체 실행에서 직접 커밋의 required-only 방문 순서 1시험이 실패했습니다(3,893개 중 3,891 통과·1실패·1todo). 명시적인 이전 스키마가 현재 스키마 자체인 경우를 유효한 이전 required 증인으로 취급한 원인이었습니다. 이 경우만 전체 계산으로 후퇴하도록 수정하여 기존 방문 순서 9시험과 H4의 0회 상한 4시험을 다시 통과했습니다. 시험 기대값은 바꾸지 않았으며 수정된 머리의 최종 unit 전체는 3,892 통과·1todo·실패 0입니다.

## oneOf-80 증가분 귀속과 수정

보호 경계 초과는 11.604µs이고 A/B 중앙값끼리의 차이는 11.917µs입니다. ledger self는 selectChildren 33.792→41.605(+7.813), markCommitDeliveries 14.626→16.792(+2.167), computeNode 39.668→41.167(+1.498)µs입니다. primeHost는 3.042→1.708(-1.334), assembleObject는 10.459→10.020(-0.438)µs입니다. supplemental의 registerPresenceChanges는 13.750→13.895(+0.145)µs로 증가가 작았습니다. 함수별 중앙값과 행 중앙값은 각각 계산하므로 그 합은 일치하지 않습니다.

실제 oneOf-80 전환의 실패 우선 호출 수 시험은 최종 공표의 사적 view 열거 1→0, 내부 view 쓰기 trap 3→0, 일반 문자열 진입 후보 정렬 1→0을 확인했습니다. H8 collector에서 이전 전체 열거는 0입니다. 별도로 관측된 이전 형상 열거 1회는 바퀴 이전 DependencyIndex 등록에서 발생했으며 H8 fallback으로 귀속하지 않습니다.

계약 `769917e8a`·`0c5b1be78` 뒤 제품 `a3e955b73`에서 최종 형상을 baseline과 실제 dynamic target에서 직접 복사하고, 내부 엔트리 쓰기도 target에 직접 적용했습니다. 게이트 중간 형상 읽기는 기존 Proxy를 유지합니다. required의 부모별 O(E) 묶음은 보존하고, 정수 속성 이름이 있는 다중 진입 후보만 안정 정렬합니다. O(S+K) 새 형상 공표와 O(E) 일시 목록의 공간 차수는 변하지 않으며 새 영구 캐시는 없습니다. 일반/verify 모드 표적 60시험과 typecheck·lint가 통과했습니다. 수치 채택 판정은 새 관문과 허가된 창 3에서 확인합니다. [귀속 수치와 호출 수](raw/b9-1/window-3-corrections/attribution.json)를 보존합니다.

차분 검토의 P3도 반영했습니다. fallback 도달 시험은 이전 형상에서 정적 kind를 제거해 전체 비교만 그 이름을 찾도록 바꿨으며, 여덟 가드를 각각 제거한 변형이 모두 실패했습니다. 가드는 전부 복원했습니다. 종료 프로세스 기록은 상위 10개의 이름과 CPU 비율만 남기도록 장치를 고쳤고, 코디네이터 승인에 따라 창 1·2의 저장본도 같은 모양으로 줄였습니다. 쓰기 표본과 수치 원시는 바꾸지 않았습니다.
