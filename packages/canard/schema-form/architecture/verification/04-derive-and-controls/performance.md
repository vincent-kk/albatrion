# 04단계 파생·제어 성능 기록

## 환경과 재현

2026-10-01에 `19c8d320e`에서 MacBookPro18,2(M1 Max, 64 GB), Darwin/arm64의 Node.js 26.10.0/V8과 `/opt/homebrew/bin/bun` 1.4.2/JSC를 순차 재실행했습니다. 다른 벤치·시험은 측정과 겹치지 않았습니다. 패키지 루트에서 실행한 명령은 다음과 같습니다.

```sh
node --import tsx bench/derive-and-controls.bench.ts
/opt/homebrew/bin/bun bench/derive-and-controls.bench.ts
```

TEST-071은 새 엔진의 `sameValue`를 직접 재어 **비교 비용**을 판정합니다. 같은 입력을 터미널 객체 원천의 `controls.injectTo`에 실제로 써서, 매 쓰기마다 대상이 바뀌고 규칙이 한 번 발화하는지도 확인했습니다. 배열 사례는 객체 원천의 `items`에 든 10,000원소 배열입니다. 배열 노드 자체를 `injectTo` 원천으로 삼는 경로는 06단계 범위입니다. 객체 사례의 `items`는 키 10,000개의 객체입니다.

작은 원소는 깊은 노드 4개(원소 객체·`payload` 객체·`marker`·숫자 잎 1개), 큰 원소는 19개(숫자 잎 16개)입니다. 따라서 바뀌지 않은 9,999개 원소의 깊은 크기 비는 **19/4 = 4.75×**입니다. 한 원소 쓰기에서는 그 9,999개가 양쪽 값에서 같은 참조이고 마지막 원소만 새 객체입니다. 통째 교체에서는 모든 원소가 새 객체이되 앞의 9,999개는 깊게 같고 마지막 `marker`만 다릅니다. 입력 생성은 시간에서 제외했습니다. 두 사례 모두 `injectTo` 대상이 실제로 바뀝니다. 공유 원소를 감싼 접근 계측에서 `sameValue`의 깊은 방문은 0회여서 18C-50 지름길이 존재함도 확인했습니다.

비교 시간은 준비 40회 뒤 61표본의 중앙값이며, 대괄호는 10–90백분위 퍼짐입니다. 한 원소 비교는 표본당 20회, 통째 비교는 3회 묶어 타이머 비용을 나눴습니다. 단위는 µs/비교입니다. 별도의 끝까지 쓰기 시간은 준비 6회 뒤 31표본, 1회/표본입니다. 이 통합 시간에는 비교 이외의 정착·대상 쓰기도 포함되므로 28C-06의 비교 판정에 사용하지 않습니다.

끝까지 쓴 시간(µs/쓰기)의 중앙값은 Node 객체 한 원소 11691.21→25620.58, 배열 4483.92→17560.33, 통째 객체 16159.63→40721.96, 통째 배열 9080.67→33471.58이었습니다. Bun은 같은 순서로 6398.29→14110.00, 3348.83→11343.62, 9034.13→22357.29, 5566.96→19347.96이었습니다. 깊이가 커지면 비교 외의 정착 비용도 증가하므로 이 통합 시간을 `sameValue` 판정선에 대입하지 않습니다.

**소유자 수용 대기:** `TEST-071-whole` 객체는 두 엔진에서 선의 하한보다 작은 시간 비를 보였습니다. `sameValue`는 객체 양쪽에서 10,000개 키를 열거하고 키 순서를 확인합니다. 이 원소 크기와 무관한 비용이 작은 입력에도 들어가므로, 깊은 크기를 4.75배로 키웠을 때 총 비교 시간은 약 2배만 늘어난 것으로 보입니다. 이는 코드 경로와 측정값에 맞는 설명이며 프로파일로 비용을 분리한 인과 증명은 아닙니다. 공유 참조의 깊은 방문 0회와 `sameValue`의 참조 우선 반환을 확인했으므로 18C-50·SETTLE-043 지름길 부재 징후는 없습니다. 27라운드 답대로 이번 구현에서 최적화하지 않았습니다.

## 알려진 비용

단계를 가로지르는 속도 문제 목록은 [속도 문제 대장](../performance-issues.md)에 있습니다.

첫 로드에서 형제 노드 N개에 각각 `controls.active` 게이트가 있으면 비용이 대략 제곱으로 늘어납니다. 검증자 탐침은 선형 식 조회 비용을 제거한 `83ec3fc48`에서 1천/2천/4천/8천 노드 **180/601/2407/10633 ms**였고, `dc54794a5`와 03단계에서도 같은 차수였습니다. 검증자가 `d8d4b8e7b`의 n=4000 프로파일로 원인을 분리했습니다: `src/core/settle/utils/compute/selectChildren.ts:181-183`이 게이트로 즉시 바뀐 자식마다 `node.children`을 다시 만들고 출력을 다시 조립합니다(selectChildren 자체 34%, assembleObject 자체 27%). 게이트가 없으면 1천/2천/4천에서 15/22/49 ms입니다. 이 코드는 03(`0705217d5`)에서 왔습니다. 27라운드에 따른 구현 완료 뒤 최적화·소유자 판단 대상으로 기록하며, 이 수치를 TEST-071의 벤치 행이나 판정에 합치지 않습니다.
