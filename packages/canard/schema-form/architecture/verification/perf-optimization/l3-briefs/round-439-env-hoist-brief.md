## Hypothesis (from `verification/perf-optimization/nested-mount-diagnosis-439.md`, hypothesis 4 and the NODE_ENV finding, verifier-confirmed)

The built `dist/index.mjs` reads `process.env.NODE_ENV` at run time at 43 call sites (26 product source files, 46 occurrences; `src/__legacy__` excluded). In Node, each read is an environment lookup through the host; the diagnosis attributes 21~27 % of the nested-mount blueprint time to the lines that only read it, and the cost is paid under `NODE_ENV=production` as well (only the development-only bodies are skipped). The 0.16.1 bundle has no such reads. Change: in every product file that reads it, read once at module evaluation into a module-level constant and use that constant at the former call sites, keeping the bare `process.env.NODE_ENV` token in the constant's initializer so consumer bundlers still replace it statically and drop the development branches (`src/helpers/warning/utils/warnDevelopmentIssue.ts` documents this convention in its `@remarks`; update that sentence to describe the hoisted form). One constant per file, never a shared export (so every bundler folds it within the module). Behavior is identical unless `NODE_ENV` changes after the module is loaded, which the package does not support; state that in DETAIL. Expected effect: Node mounts lose the per-node read cost (nested-d6 ≈15 % of mount, oneOf ≈8~10 %, estimates); browser production bundles are unchanged.
