## F5b 조건별 표와 프로파일

### 측정 방법

기존 benchmark-form CLI의 `--fixture=array-push-remove-100` 필터를 사용했습니다. 실행 형태는 다음과 같으며, 전체 명령은 증거의 명령 기록에 있습니다.

```text
node --expose-gc --import tsx <benchmark-form>/src/index.ts --equivalent --mode=core --min-samples=100 --legacy=0.16.1 --fixture=array-push-remove-100 --out=<증거 루트>/raw/f5b-<조건>-r<회차>.json
```

기존 러너는 판별 표본마다 이미 `forceGc()`를 한 번 호출합니다. 따라서 (a) 기본 장치와 (b) 표본 전 강제 GC는 같은 설정이며, (b)를 독립적인 GC 정책 변경으로 해석하지 않았습니다. (c)는 증거 루트의 preload에서 명시적 `gc()`를 no-op으로 만들고 `--max-semi-space-size=64`를 추가했습니다. 자동 GC는 허용했습니다. 조건 순서는 1회차 a→b→c, 2회차 c→a→b, 3회차 b→c→a였으며, 각 프로세스 안에서는 기존 장치가 E0/E4를 AB/BA로 번갈아 실행했습니다.

## R3 분리 표

### 측정 방법과 귀속 범위

기존 러너는 Profiler `duration`만 보관하므로 CPU 표본을 Profiler 구간에 연결할 수 없었습니다. 브리프가 지정한 `render2.tsx`, `render3.tsx`, `formprof.mjs`, `rmount.tsx`를 읽었으며, React lane을 그대로 재현하는 `render2.tsx`와 `rmount.tsx`를 바탕으로 증거 루트에만 `tools/render.tsx`를 만들었습니다. 같은 fixture·Form·flushSync·준비 완료 확인·drainTicks·teardown 순서를 유지하고, `onRender`의 `startTime`과 `commitTime`을 추가로 저장했습니다.

각 fixture·판·회차마다 새 프로세스를 사용했습니다. 1회차는 10개 fixture를 E4로 실행한 뒤 E0로 실행했고, 2회차는 E0 다음 E4로 실행했습니다. 명시적 GC는 매 표본 전에 실행했습니다. 예열 10회와 teardown은 CPU 귀속에서 제외했습니다.

V8의 주 스레드 프로파일만 사용했습니다. tsx loader 스레드의 별도 프로파일도 보존했지만 귀속 합계에 넣지 않았습니다. `process.hrtime`과 `performance.now()`의 대응을 실행 전후에 기록했으며, 모든 42개 구간 프로파일의 대응 차이는 최대 19.085µs 미만이었습니다. 구간끼리 겹치지 않았고, 프로파일 시간축의 구간 포함도 확인했습니다.

### 배열 갱신 부호와 React 층 근거

`array-push-100 profiler-update`의 E4−E0 부호는 1회차 음수(−16.823ms, −11.423%), 2회차 음수(−16.620ms, −11.268%)였습니다. 이번 두 회차 안에서는 방향이 바뀌지 않았습니다. 다만 기존 M3의 양수 결과와는 방향이 다르므로 기존 느린 행의 회귀를 이번 창에서 재현했다고 말할 수 없습니다.

push의 react-dom self 차이는 약 −8.16ms/표본으로 번들 차이 약 −2.63ms보다 컸습니다. 1회차 `runWithFiberInDEV`는 E0 9715.39→E4 6776.03µs, `beginWork`는 4458.99→3370.51µs였습니다. push-remove도 `runWithFiberInDEV`가 16480.76→11255.88µs, `beginWork`가 6419.46→4654.83µs였고, react-dom 감소가 번들 감소보다 컸습니다. 이번 창의 감소 방향은 React 층의 감소가 더 크게 실린 결과입니다.

replace의 갱신은 양수 부호를 유지했습니다. schema-form self는 +2879.41/+3503.93µs였고 react-dom과 react를 합한 증가는 +4808.59/+5213.57µs였습니다. ## 한계

React Profiler의 `actualDuration`은 내부 렌더 작업의 합이며, `startTime..commitTime`은 그 작업을 감싸는 구간입니다. 두 값은 동일한 구간 목록이 아닙니다. 이번 계측은 commit 사이의 대기와 teardown을 제외했지만 구간 안의 스케줄링·부가 작업을 완전히 분리하지 못했습니다. 따라서 CPU 표는 해당 외곽 구간의 표본 추정치이며 `actualDuration`의 정확한 함수별 분해라고 주장하지 않습니다. R3-02처럼 방향이 설명되지 않는 행은 미확정으로 남겼습니다.

100µs 요청 간격의 V8 프로파일은 짧은 코어 상호작용과 경계 표본에 민감합니다. 구간 내 표본의 전체 간격을 배분한 값은 구간 길이보다 커질 수도 있으며, `(idle)`을 CPU로 해석할 수 없습니다. 원시 프로파일, 타임스탬프 선택 결과, 구간 경계 배분 결과를 모두 보존했습니다. 특히 FP 표를 짝지은 F5 표의 절대 CPU 분해로 사용하지 않았습니다.

CPU 프로파일을 활성화한 별도 창의 결과를 기존 M3의 비프로파일 측정과 같은 수치로 취급하지 않았습니다. 두 회차는 제한된 반복 확인이며, 다른 런타임·다른 크기·GC 단일 요인 효과·통계적 수용을 확인하지 않았습니다. 어느 행도 잡음으로 처리하지 않았습니다. `미입증`과 `방향 불안정`은 측정 규칙상의 표시입니다.

M3는 Node `v26.12.0`, 한 프로세스에서 두 판을 번갈아 적재하는 장치, `NODE_ENV=development`로 측정했습니다. 이번 창은 Node `v24.20.0`, R3의 판별 단독 적재, `NODE_ENV` 미기록 상태이므로 R3-02·R3-08·R3-12와 F5b의 M3 대비 비교에는 런타임 차이가 섞여 있습니다.
