## 읽은 것

**1. 잎 쓰기와 깊이 8까지의 중첩 잎 쓰기에는 크기 비례가 없습니다.**

- Node 폭 1000의 잎 쓰기는 0.16.1보다 98–99% 빠릅니다. 0.16.1은 쓰기마다 루트 값을 통째로 다시 만들기 때문입니다.
- 작은 폭(10)에서 Bun은 0.16.1보다 82–171% 느리지만, 절대값은 0.003–0.015 ms 차이의 쓰기 한 번 고정비입니다(P-60, 104라운드 수용).

**2. 객체 통째 쓰기는 하나만 바뀌어도 K개 전부를 표시·계산·비교합니다.**

- object-one-key와 handle-root에서 `markWrite`·`computeNode`·`updateOutput`이 키마다 한 번씩 돕니다.
- 값이 같은 잎도 dirty가 되기 때문입니다(`markWrite.ts:62`). 그래서 바뀌지 않은 키에 재계산 등록, 계산, 비교 넷이 붙습니다.
- 바뀐 것이 하나인데 일이 K에 비례하므로 GOAL-011 위반 후보입니다. 입력을 받는 이상 입력 크기 K의 비교 한 번은 피할 수 없지만, 그 비교 뒤의 일이 K배입니다.
- object-same-ref(바뀐 것 0)도 같은 일을 다 합니다(폭 1000에서 1.57 ms).

**3. Merge로 키 하나를 써도 호스트 전체를 다시 합성합니다.**

- 키 집합이 같아도 호스트가 형상 dirty가 되기 때문입니다(`markWrite.ts:135`).
- 그래서 증분 합성 대신 형상 경로 합성으로 가서, 자식 전부의 비교(`sameValue` 2,013회)와 `preserveReferences`를 합니다.

**4. object-all-keys의 K 비례는 바뀐 것의 크기이므로 준수입니다.** 배달 표시(바뀐 노드마다)와 계산도 계약이 요구하는 일입니다.

**5. 조상 사슬의 깊은 비교(`updateOutput.ts:31-43`)는 이 장면들에서 작습니다.** 층마다 키 넷이라 그렇고, 넓은 조상에서는 다를 수 있어 장면을 더 재야 합니다.

**6. 조사의 다른 후보는 이번 장면에 나타나지 않았습니다.** 잠복 원본 색인 다시 짓기, 불일치 메모 정렬, 나감 때 감시자 전체 훑기는 잠복 원본·불일치·게이트 토글이 있는 폼에서만 돕니다. 따로 장면을 만들어 잰 뒤 판정합니다.

## W4 — clear 뒤 소멸 마감의 아이템마다 `under` 조회(기록만, 폐기)

L2 설계의 W4입니다. 판정 기준은 370라운드("늘리는 코드가 지우는 비효율보다 크면 폐기하고 기록만")입니다.

**원인**

- clear(그리고 아이템 하나의 pop·`remove(0)`) 뒤 `finalizePerished`는 `prunePerishedPaths`를 부릅니다. 이 함수는 경로 저장소가 비어 있지 않으면 소멸 경로마다 `pathIndex.under`를 부릅니다(`settle/utils/transition/prunePerishedPaths.ts:21-49`).
- 정적 수 배열에서 이때 비어 있지 않은 저장소는 `inactiveMemo` 하나입니다. 그 항목은 루트 키 `""`이고, `finishStaticFirstLoad.ts:95`와 `updateInactiveValuesMemo.ts:136`이 늘 기록합니다.
- 이 항목은 아이템 아래에 있지 않으므로, 조회가 지울 것이 없습니다.
- 그 밖의 저장소(잠복 원본, 메타데이터, 선언, 규칙, 불일치), 비활성 메모, 경고는 `clearArrayRuntimePaths`가 이미 호스트 접두 단위로 지웠습니다(`clearArrayRuntimePaths.ts:57-97`).

**실측**

- `core/engine` 단위 시험 253개 파일에 탐침을 걸었습니다.
- `clearArrayRuntimePaths`를 거친 호스트의 소멸 마감은 79회, 소멸 경로는 29,190건이었고, 지울 항목은 0건이었습니다.
- 비용은 8천 clear에서 약 90 µs로, 5.74 ms의 약 1.6%입니다.

**폐기 사유**

- `itemCount === 0`만으로 건너뛰면 안전하지 않습니다. 일반 경로에서 아이템 수가 0인데 불일치 정리가 필요한 사례가 있습니다.
- 안전하게 건너뛰려면 정착 문맥에 새 칸(일괄 정리한 호스트 집합)을 두고, scratch의 생성·해제·전달, `applyArrayTail`의 표시, `finalizePerished` 조건을 고쳐야 합니다. 합쳐 약 12–14줄입니다.
- 그 안전 근거도 코드가 아니라 실측뿐입니다.
- 지우는 비효율에 비해 늘리는 코드와 위험이 커서 구현하지 않습니다(원장 관리자 동의).

### 발견 — `primeHost`의 대기 나감 조회는 도달 가능하다

**판정:** 도달 가능합니다. 다만 자연 경로는 지연된 SharedNodeConflict 하나뿐이고, 그 정착은 `finishSettlement.ts:108`에서 오류로 끝납니다.

**왜 그 경로 하나뿐인가**

- 대기 나감은 게이트 자식에 한정되지 않고, 밀려난 모든 이전 자식을 `[path, kind]` 키로 넣습니다(`selectChildren.ts:444`).
- 맵은 정착이 끝날 때만 비워집니다(`releaseSettlementScratch.ts:14`).
- `transitionSettlement.ts:198`과 `runDeriveRounds.ts:128`이 같은 문맥으로 `computeNode`를 다시 부릅니다. 그래서 둘째 패스의 `primeHost`(라운드 고리 전 1회, `computeNode.ts:99-164`)가 앞 패스의 대기 나감을 볼 수 있습니다.
- 보통의 게이트 나감은 `primeHost.ts:47`의 비게이트 기준선 필터에 걸려 닿지 않습니다.
- 배열 이름 바뀜은 첫 계산 전에 끝납니다(`arrangeFieldNodeItems.ts:169`).
- 반례는 종류가 다른 자식이 밀려나는 경우뿐입니다.

**최소 장면**

- 스키마: 루트 `on: boolean`, 그리고 `oneOf` 두 분기입니다.
  - 첫 분기: `controls.active: './on === true'`, `x: number`(기본값 1)
  - 둘째 분기: `x: string`
- 마운트 값은 `{ on: false, x: 'K' }`이고, `on`에 `true`를 입력합니다.
- 진행:
  1. 첫 계산이 비게이트 string `x`를 기준선에 둡니다.
  2. 선택이 number `x`를 먼저 받습니다. string 항목은 충돌을 기록하고 계속합니다(`selectChildren.ts:250`).
  3. 밀린 string `x`가 `["/x","string"]` 키로 대기 나감에 들어갑니다.
  4. 전이가 number의 기본값 1을 채우고 다시 계산합니다(`transitionSettlement.ts:96`, `:198`).
  5. 둘째 `primeHost`가 비게이트 string 키로 `:69`에서 적중합니다. 이전 자식이 이제 number라 `:70`이 그것을 고르고, `:72`가 대기 string 키를 지웁니다.
  6. 그 뒤 충돌 오류가 납니다.

**처리**

- 조회는 제거하지 않습니다. 실제로 적중하는 경로가 있기 때문입니다.
- 자연 장면은 시험으로 더하지 않습니다. 정착이 오류로 끝나 적중 전후에 관측 가능한 차이가 없고, 차이를 보려면 오류 경로 안쪽 상태를 들여다봐야 해서 test-validity 기준에 맞지 않습니다(편집자 결정).
- `settle-pending-exit-key`의 `primeHost` 사례는 조회 계약 확인용 합성 시험으로 유지합니다.

**도구:** codex 읽기 전용 조사(세션 `37b1356e…`)입니다. 메모리 안 탐침으로 맵 동작만 관찰했고, 항목을 주입하지 않았습니다.
