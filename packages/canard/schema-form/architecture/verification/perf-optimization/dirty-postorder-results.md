## 진단과 변경

기준 제품은 `47ad92cf39addbcfcb7fccc8e6a0482f9c040eb9`입니다. 루트 일괄 쓰기는 표시 단계에서 일반 DirtyPathSet 색인으로 모든 조상 접두 항목을 만들고, 바로 다음 등록 단계가 이를 지워 직접 부모–자식 에지 색인으로 다시 만들었습니다. 두 단계 사이에는 일반 색인의 소비자가 없었습니다. 진단은 이 버려지는 작업을 nested-d6 반복 쓰기의 주요 단일 낭비로 확인했습니다.

수정 1만 구현했습니다. `writeFieldNode`는 `!context.hasGates`이고 dirtyPaths가 아직 후위 모드가 아닌 DirtyPathSet일 때, `markWrite` 직전에 `beginPostOrder()`를 호출합니다. 공개 `isPostOrder` getter를 추가했으며 등록 경계의 기존 멱등 호출은 유지했습니다. 게이트 있는 정착과 결정 58의 술어, 소비 단계의 delete, 배달 페이로드는 변경하지 않았습니다. 계약 DETAIL을 먼저 커밋하고 시험, 구현 순으로 이어갔습니다.

쓰기 표시는 경로당 모든 접두 항목을 만들지 않고 아직 dirty가 아닌 조상까지 직접 에지만 연결합니다. 트리 생성 O(N), 잎 갱신 O(D), dirty 색인 메모리 O(dirty 노드)의 계약과 최초 후손 순서는 유지합니다. 새 노드별 저장 칸이나 상주 캐시는 없습니다.

측정 창이 끝난 뒤 번들 사본에서 DirtyPathSet의 공개 메서드만 감싸 호출과 색인 경로를 셌습니다. 시간은 재지 않았으며 성능 표본에 섞지 않았습니다. 후위 상태는 beginPostOrder/clear 호출로 추적했으며 비공개 필드를 읽지 않았습니다.

|---|---:|---:|---:|---:|---:|
| flat-1000 | 2,001 / 2,001 | 1,001 | 0 | 1,000 | 0 |

## 남는 비용과 한계

진단의 반복 쓰기 프로파일에서 남는 약 11 ms는 노드당 Set·Map 장부, 출력 합성, 커밋·배달 표시와 할당 비용에 분산되어 있었습니다. 이번 첫 쓰기 표의 nested-d6 B도 11.5627 ms이며, 이 값을 별도 진단의 반복 쓰기나 0.16.1 수치와 같은 창의 비교로 취급하지 않습니다. 소비한 노드의 자식 색인을 통째로 놓는 수정 2와 리스너가 있는 노드에만 공개 페이로드를 만드는 수정 3은 후속 후보이며 구현하지 않았습니다.

작은 행의 보정 폭은 크며 동치 범위 안은 동일 성능의 증명이 아니라 이 프로토콜에서 차이를 입증하지 못했다는 판정입니다. nested-d4·d5 마운트는 세 라운드의 일부만 폭을 넘어 미입증으로 남겼습니다. 마운트나 단일 입력의 개선을 주장하지 않습니다. 측정은 한 기계·한 창의 Node 코어 비용이며 React 렌더링·브라우저 입력·검증 비용과 상위 지연을 포함하지 않습니다. Bun은 관찰 동치만 확인했습니다.

승인 당시 코디네이터는 읽기 전용 Claude 진단 에이전트 하나에 CPU 작업 중지를 지시했고 다른 측정·빌드·시험은 없다고 확인했습니다. 이 작업에서도 창 안에서는 다른 빌드·시험을 실행하지 않았지만 운영체제와 다른 프로세스의 모든 간섭을 배제했다는 뜻은 아닙니다. 기존 FCA finding은 남은 구조 한계입니다. 관찰 준비 첫 실행의 상위 출력 디렉터리 부재는 측정 전에 mkdir로 바로잡았고 원래 도구를 바꾸지 않은 재실행이 통과했습니다.
