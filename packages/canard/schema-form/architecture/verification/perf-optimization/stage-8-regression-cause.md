# 8단계 브라우저 세 회귀의 원인 분석

[최종 브라우저 기록](./final-stage-8-browser.md)의 열린 원인을 정적 경로, 로컬 계측, 커밋 이분 탐색으로 대조했습니다. A와 B에는 루트 `if`의 일반 정착 경로 비용이 남고, C의 경과 회귀는 지연 컴파일과 측정 창의 중첩으로 설명됩니다. 이 기록은 원인 분석이며 수정 완료나 8단계 성능 승인 선언은 아닙니다.

## 측정 조건과 증거의 한계

2026-11-04 로컬 120 Hz 헤드리스 Chromium에서 기준 `7b49d62c7`(0.16.1)과 후보 `c10c71601`을 비교했습니다. 이분 탐색 보고서는 후보와 CI 기록 후보 `bd2141098` 사이에 엔진 소스 차이가 없음을 확인했습니다. 사례마다 10회 측정하고 2회 예열했습니다. Cursor 확장·파일 감시·Spotlight 외부 부하로 정숙 검사가 거부된 뒤 승인된 `CI=true` 실행을 사용했으며, 채택 실행의 동일 바이트 baseline/control 검사는 허용 띠를 통과했습니다. 실패·void 실행은 채택하지 않았습니다.

로컬 절댓값은 60 Hz CI와 직접 비교할 수 없습니다. 로컬 계측 전 if-flat none 비율 1.394, 최초 기준 비교의 첫 키 83.80/63.45 ms(약 1.32), if-flat validate 123.90/115.50 ms(약 1.07)는 CI 회귀 방향과 일치하지만 서로 다른 실행의 비율입니다. 첫 키 원인 실험의 즉시 입력 비율은 별도로 1.258입니다. 계측 오버헤드는 보정하지 않았고, 서로 다른 사례 중앙값의 차이에 별도 짝지은 통계 검정을 하지 않았습니다.

## 회귀 A — mount-if-flat-500-none

### 증거와 판정

CI 경과 +38 %는 로컬에서 같은 방향으로 재현된 실제 조건부 마운트 경로 비용입니다. 정적 분석의 `src/core/engine/blueprint/buildNodes/utils/declarations/collectSchemaCapabilities.ts:32–39`에서 루트 `if/then`은 `branchless=false`가 되고, `src/core/engine/blueprint/blueprint.ts:130–138`의 `staticFirstLoadEligible`에서 제외됩니다. 따라서 정적 첫 로드 대신 `computeNode.ts`의 일반 게이트 정착 경로를 탑니다.

로컬 계측에서 루트 계산 2회에 각각 2라운드, 총 4 wheel 라운드를 수행했습니다. 고유 자식은 501개였으며 `selectChildren` 4회가 다룬 선택 후 슬롯 합은 2,004개였습니다. 슬롯 합은 내부 루프의 실제 step 방문 횟수가 아닙니다. `primeHost`, 재귀 중복을 뺀 `selectChildren`, `updateOutput`의 표본별 합 중앙값은 12.80 ms로, 같은 후보 실행의 flat 대비 if-flat 차이 16.65 ms 중 76.9 %를 설명합니다. 각 단계 중앙값은 각각 5.00, 6.80, 1.15 ms이며 중앙값끼리 더한 값과 표본별 합의 중앙값은 다릅니다.

none 표본의 compile/validation은 0회여서 가드 컴파일을 원인에서 배제합니다. `prepareGateSelection.ts:28–44`의 계획 생성은 다중 oneOf/anyOf/allOf를 대상으로 하므로 단순 루트 if의 선택 테이블 작성도 지지되지 않습니다. 기준판은 `then.required`가 없는 이 fixture에서 조건 목록을 만들지 않았습니다.

### 이분 탐색 경계

판정은 같은 빌드의 `delta_X = if-flat none 중앙값 − flat none 중앙값`입니다. 0.16.1은 −0.25 ms였고, 마지막 정상 `e7e1b62a6`은 −8.10 ms, 그 직계 자식인 첫 불량 `b620da740`(#354, 공개 Form의 새 노드 트리 엔진 전환)은 +25.00 ms였습니다. 부모에서 자식으로 flat은 73.80 → 99.00 ms, if-flat은 65.70 → 124.00 ms로 모두 느려졌습니다.

차이는 #437에서 +33.40 ms, #438·#472에서 +33.30 ms, #499에서 +33.25 ms였고 #508에서 +66.45 ms, #522에서 +25.15 ms, 최초 후보 비교에서 +24.75 ms였습니다. #499에서 #508로 과거 빌드 flat은 98.80 → 73.75 ms로 줄었고, 같은 구간에서 flat none 표본의 컴파일은 1회에서 0회가 되었습니다. if-flat none은 #508까지 컴파일 1회가 남았고 #522부터 0회였으며, 차이도 +66.45 ms에서 +25.15 ms로 줄었습니다. 정적 첫 로드와 그 branchless 요건은 #354부터 있었으므로, 컴파일이 사라진 뒤 남은 약 +25 ms가 정적 첫 로드 적격성 차이와 맞습니다. 따라서 현재 잔존 원인은 정적 첫 로드 적격성의 구조적 차이이며, 후속 성능 커밋 하나로 환원하지 않습니다. 정적 보고서의 #508 최초 전환 추정은 이분 탐색에서 확인한 #354 경계로 대체합니다.

### 남은 범위

최초 불량의 과거 none 빌드는 선행 컴파일 1회를 수행했습니다. 이분 탐색은 해당 단언만 기록 후 통과시키고 나머지 검사를 유지했습니다. delta가 조건부 컴파일 비용까지 완전히 상쇄한다고 증명하지 않았으므로 최초 경계와 현재 잔존 기전은 구별합니다. 로컬 단계 시간을 CI 절대 차이 전체에 귀속하지 않으며, 일반 계산의 나머지 비용과 구조 고정 조건의 안전한 증명은 남아 있습니다.

## 회귀 B — mount-if-flat-500-validate

### 증거와 판정

CI 경과 +7 %·피드백 +10 %는 A와 같은 일반 경로 비용에 가드 준비 비용과 전체 검증 지연의 이득이 합쳐진 결과로 해석합니다. flat·nested·array 검증 마운트에서 관측된 이득이 일부 상쇄하는 방향이지만, 상쇄량을 별도로 확정하지 않았습니다. `readValidationEntry`의 `createValidatorCopy`는 authored root 전체를 한 번 복사하므로 O(N)이고, 이 fixture의 const 가드 자체 컴파일은 O(1)입니다. 전체 검증 컴파일과 가드 컴파일이 존재한다는 사실은 전체 500필드를 두 번 컴파일한다는 설명을 지지하지 않습니다.

### 이분 탐색 경계와 남은 범위

#354 경계의 과거 빌드에서 검증 조건부 마운트는 115.65 → 132.25 ms로 증가했습니다. 독립 이분 탐색은 하지 않았으므로 이 사례만의 최초 불량을 확정하지 않습니다. A를 따르는 회귀로 분류하되 가드 등록 내부의 추가 walk/clone과 최종 +7 %·피드백 +10 %의 함수별 기여율은 미확정입니다.

## 회귀 C — first-key-flat-500-validate 경과

### 증거와 판정

CI 경과 +28 %의 주원인은 측정 창 중첩입니다. 현재 트리에는 없는 0.16.1의 `packages/canard/schema-form/src/core/nodes/AbstractNode/utils/ValidationManager/ValidationManager.ts:198–203`은 생성자에서 전체 컴파일을 수행하지만 후보는 `scheduleLoadValidation.ts`와 `scheduleAfterValidationFrame.ts`를 통해 첫 프레임 뒤 작업으로 옮깁니다. 하네스는 첫 paint에서 키를 보내며, `durationMs`는 드라이버 호출 직전부터 `afterCorePaint` 완료까지입니다.

500필드 컴파일은 즉시 후보 표본에서 중앙값 31.85 ms였고 10/10 표본에서 입력 경과 창과 겹쳤습니다. 즉시 경과는 66.60 → 83.80 ms, 비율 1.258이었습니다. 첫 paint 뒤 500 ms를 기다리고 load 검증 기록과 pending run 0을 확인한 지연 입력에서는 중첩 0/10, 경과 41.80 → 42.85 ms, 비율 1.025로 잡음 폭 안이었습니다. 대기 시간은 경과에 포함하지 않았습니다. 예약된 load 컴파일의 중첩을 확인한 것이며 첫 키가 컴파일을 시작했다고 주장하지 않습니다.

### 이분 탐색 관측 경계

과거 빌드 첫 키는 #499의 44.60 ms에서 #508의 80.50 ms로 증가했습니다. 이는 #508의 지연 도입과 일치합니다. 독립 이분 탐색은 하지 않았지만 관측한 5d1348ed1(#499)과 212967e0f(#508)는 직계 부모·자식입니다. 다만 첫 키에는 판정 규칙을 정하지 않았고 각 커밋은 채택 실행 1회이므로 이 경계는 관측 수준입니다. 정적 보고서의 #522·#508 후보 추정 중 관측 구간은 #508과 맞습니다.

### 남은 범위

경과 회귀가 사라져도 모든 입력 지표가 같다는 뜻은 아닙니다. 지연 입력의 로컬 `blockingMs`는 3.90 → 5.95 ms, `feedbackCommittedMs`는 10.05 → 12.35 ms로 각각 약 2 ms 느렸습니다. 피드백 차이 2.30 ms는 문턱 2.00 ms를 조금 넘고 동일 바이트 대조군도 기준보다 1.65 ms 높았으므로, 블로킹 잔여보다 약한 증거입니다. CI 즉시 입력에서는 블로킹과 피드백이 개선되었으므로 이 잔여 비용은 CI에서 미확인 상태로 남깁니다. 현재 경과 사례는 컴파일 지연과 키 지연을 함께 측정하므로 load 검증 완료 뒤 입력하는 변형을 재측정하거나 두 입력 시점을 함께 보고해야 합니다.

## 수정 방향과 8단계 결론 — 구현하지 않았습니다

가장 작은 수정 방향은 `blueprint.ts:130`의 정적 첫 로드 적격성을 “branchless”와 “첫 로드 구조 고정”으로 분리하는 것입니다. `collectSchemaCapabilities.ts:32`의 전역 branchless 의미를 약화시키지 않고, 루트 then/else가 자식의 존재·종류·required를 바꾸지 않는 경우에 한해 정적 조립을 허용하는 좁은 증명을 추가하는 방향입니다. 선택된 선언과 overlay, 오류 및 validator 부재 의미를 유지하고 증명 실패 시 일반 경로로 돌아가야 합니다. `then.required`가 없다는 이유만으로 다른 제약을 무시해서는 안 됩니다.

A는 이처럼 구조가 고정된 루트 if에서도 발생하는 실제 엔진 비용이며 B는 같은 경로를 따릅니다. C의 경과 증가는 키 처리 자체의 지연 증거로 사용할 수 없으므로 측정 창을 분리해야 합니다. 수정과 재측정, 지연 입력 잔여 비용 확인이 남아 있으므로 원인 설명만으로 8단계 전체 성능을 승인하지 않습니다. 이 커밋은 제품·벤치마크 코드를 변경하지 않으며, 로컬 실험의 계측 변경은 커밋하지 않았습니다.

## 결말

[최종 실행 41871054743](https://github.com/vincent-kk/albatrion/actions/runs/41871054743)은 PR #544와 PR #545를 포함한 `b039c3187`을 0.16.1과 비교했습니다. 위 분석은 당시의 계측·판정으로 보존하며, 수정·재측정과 남은 범위의 결론은 이 절과 [최종 브라우저 기록](./final-stage-8-browser.md)을 따릅니다.

- A의 반복 자식 선택은 [PR #544](https://github.com/vincent-kk/albatrion/pull/544)의 구조 고정 루트 if 첫 로드가 줄였고, 노드별 빈 Map 할당은 [PR #545](https://github.com/vincent-kk/albatrion/pull/545)가 제거했습니다. 최종 `mount-if-flat-500-none`은 148.150 → 181.800 ms(+22.7 %)입니다. 0.16.1은 `flattenConditions.ts`의 `thenRequired?.length` 검사 때문에 `then.required`가 없는 이 fixture의 then-entry와 조건 맵을 만들지 않으며 `minLength` overlay를 적용하지 않았습니다. 현재 엔진은 이를 적용하므로 같은 작업량의 비교가 아닙니다. 위 none 표본의 compile 0회는 하네스가 `compile`만 세고 `compileGuard`를 세지 않은 결과였습니다. 수정 빌드의 로컬 120 Hz 계측에서 flat 대비 동기 엔진 차이 24.40 ms 중 7.90 ms가 조건 가드 컴파일이었고 나머지 대부분은 일반 정착 경로였으므로, 가드 컴파일을 원인에서 배제한 위 판단은 바로잡습니다. 검증기 없는 literal guard evaluator와 전용 root loader는 설계·리뷰했지만 공개 validator-plugin 계약 변경과 세 번째 마운트 경로가 필요하여 8단계에서는 채택하지 않았습니다. 조건을 건너뛴 버전과의 격차를 줄이기 위한 복잡도를 늘리지 않고 올바른 조건 처리를 유지합니다.
- B에도 PR #544와 PR #545의 경로·할당 축소가 적용되었습니다. 최종 `mount-if-flat-500-validate`의 경과는 시도 2에서 265.000 → 281.550 ms(+6.2 %)이며, 검증기는 첫 프레임 전 73.200 → 0.000 ms, 뒤 13.300 → 82.200 ms로 이동했습니다. 가장 긴 Long Task는 167.500 → 139.000 ms로 줄고 창 안 합은 167.500 → 227.000 ms로 늘었습니다. 한 프레임의 경과 차이와 작업 이동을 확인한 결과이며, 과거 함수별 미확정 기여율을 새 수치로 추정하지 않습니다.
- C는 입력 시점을 분리한 최종 하네스에서 확인했습니다. PR #544와 PR #545가 첫 키의 로드 컴파일 중첩을 제거한 것은 아닙니다. 즉시 첫 키는 147.200 → 188.900 ms(+28.3 %)이지만, 로드 검증 완료 뒤 첫 키는 77.450 → 74.700 ms(−3.6 %)로 잡음 폭 안입니다. 블로킹은 즉시 입력 −25.2 %, 로드 완료 뒤 입력 −27.8 %이며, 피드백도 각각 −8.9 %, −8.4 %입니다. 따라서 로컬에서 남았던 블로킹·피드백 비용은 이번 CI에서 회귀로 확인되지 않았고, 입력 시점 분리와 재측정 항목을 닫습니다.

8단계의 원인 분석과 재측정 기록은 이 결과로 마칩니다. 검증이 꺼진 조건부 마운트의 조건 가드 컴파일과 일반 정착 비용은 위 계약·경로 복잡도 때문에 수용한 알려진 비용으로 남깁니다.
