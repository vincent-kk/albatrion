# Round 439 nested 마운트 청사진 초선형 초과분 귀속 진단

## 요약

nested d6 청사진 단계의 d3 단가 대비 초과분은 3.358 ms입니다. `encodeLeaf` 0.664 ms(이 초과분의 19.8 %)는 경로 길이 비용으로 확인되었습니다. 키 Map 조회 줄(`src/core/engine/blueprint/buildNodes/buildNodes.ts:39-40`) 1.166 ms(34.7 %)는 깊이와 크기에 따라 오르지만, 그 경로 길이 몫은 미확정입니다(0~1.166 ms, 기울기 추정 약 0.5±0.4 ms, 0에서의 거리는 1.3 σ). 노드 수가 비슷한 nested d5(V=1365, 키 약 192자)는 0.337±0.035 µs/V이고, flat-1000(V=1001, 키 약 103자)은 0.353±0.034 µs/V이며, flat-2000은 0.398±0.036 µs/V입니다. 약 1.9배 긴 키가 단가를 올리지 않았습니다. log2 V에 대한 가중 기울기는 flat 0.0182±0.0075, nested 0.0323±0.0073이므로, flat의 크기 기울기가 nested 상승의 약 56 %를 설명합니다. d4를 기준으로 하면 이 줄의 d6 초과분은 0.545 ms로 줄고, d3→d4 단계 0.305→0.457 µs/N이 그 큰 부분을 차지합니다. 노드 전체를 다시 도는 두 검사의 합은 0.699 ms(20.8 %)입니다. 나머지 0.832 ms(24.7 %)는 귀속 불가이며, 표준편차는 약 0.62 ms(1.35 σ)입니다. 가설 1의 기대 절감은 확인된 0.664 ms에 미확정 최대 1.166 ms를 더한 값입니다. 이 문서는 진단이며, 수용이나 구현 채택을 결정하지 않습니다.

## 원인

템플릿 키 문자열의 첫 Map 조회가 매 노드마다 일어납니다. 위치는 `src/core/engine/blueprint/buildNodes/buildNodes.ts:39-40`이며, E4 번들에서는 `<ns>/bundles/E4.mjs:2982`입니다. 이 줄의 시간 1.166 ms는 깊이와 크기에 따라 오릅니다. 그 시간 가운데 경로 길이가 차지하는 몫은 미확정입니다. 경로 길이 비용으로 확인된 항목은 `encodeLeaf` 0.664 ms입니다.

## 기전

1. `getTemplateKey`는 각 입력의 전체 `schemaPath`를 `encodeLeaf`로 인코딩한 뒤(`src/core/engine/blueprint/buildNodes/utils/references/getTemplateKey.ts:49`), 그 결과를 이어 붙여 `key`와 `boundKey`를 만듭니다(같은 파일 57·58행). 자식의 `schemaPath`는 부모 경로 전체에 `/properties/<이름>`을 덧붙여 만들어지므로(`src/core/engine/blueprint/buildNodes/utils/children/populateNodeChildren.ts:64`), 키 길이는 깊이에 비례합니다.
2. 이어 붙이기 자체는 문자열 조각을 연결만 하므로 비용이 거의 없습니다. 번들의 연결 줄(`<ns>/bundles/E4.mjs:2940`, `2941`, `2970`)의 표본은 모든 깊이에서 노드당 0.008 µs 이하였습니다.
3. 새로 만든 두 문자열은 `context.templates.get(boundKey) ?? context.constructing.get(key)`(`buildNodes.ts:39-40`)에서 처음 해시됩니다. 이때 V8이 연결 문자열을 평탄화하고 전체 문자를 해시한다는 해석은 줄별 표본 분포와 맞지만, 직접 확인하지 못했습니다. 이 줄이 경로 길이만큼의 작업을 낸다는 몫은 미확정입니다.
4. 이 fixture에서는 모든 경로가 서로 달라 모든 조회가 실패하므로, 매 노드가 이 조회를 수행합니다.
5. 같은 문자열을 다시 쓰는 `constructing.has(key)`(`buildNodes.ts:41`), `templates.set`·`constructing.set`(151행 부근, 번들 3046·3047행), `constructing.delete`(157행)는 표본이 깊이와 무관하게 평탄하였습니다. 번들 3046행의 노드당 값은 0.039·0.033·0.084·0.032 µs이고, 3047행은 0.043·0.052·0.030·0.024 µs였습니다. 이후 조회가 캐시된 해시를 쓴다는 해석은 미확정 목록에 있습니다.

- **증거와 판:** 증거는 `.seiri/tasks/size-diagnosis-437/`(이하 `<ns>`)의 기존 산출물만 사용하였고, 새 벤치마크는 실행하지 않았습니다. 프로파일 판은 `d9f4eb975`이며, 이후 병합은 청사진 코드를 바꾸지 않았습니다(`git diff --stat d9f4eb975 7039bce5a -- src/core/engine/blueprint`의 출력이 비어 있습니다).
- **프로파일 파일:** `<ns>/profiles/nested-d{3,4,5,6}-f4-mount.cpuprofile`과 동명의 `.json`(hrtime 구간과 반복 수)을 사용하였습니다. 반복 수는 d3 4934회, d4 1184회, d5 276회, d6 68회입니다. 비교용으로 `<ns>/profiles/flat-{50,100,500,1000,2000}-mount.cpuprofile`도 사용하였습니다.
- **표본 선별 기준:** 각 표본의 시간 길이를 hrtime 구간(`startUs`~`endUs`)과 겹치는 만큼만 계산하였습니다. 이는 `<ns>/tools/analyze.mjs`와 같은 방식입니다. 그 가운데 호출 스택에 `blueprint` 함수가 조상으로 있는 표본만 청사진 단계로 골랐습니다. 함수별 자체 시간은 표본의 가장 안쪽 함수에 귀속하였습니다. 줄별 시간은 그 노드의 자체 시간을 `positionTicks`의 줄별 틱 비율로 나누어 배분하였습니다.
- **정규화:** 작업 1회당 시간을 N(잎 수: 64, 256, 1024, 4096)으로 나누어 µs/N를 구하였습니다. flat 가족과 비교할 때는 노드 수 V로 나눈 µs/V를 썼습니다. V는 nested 85·341·1365·5461, flat 51·101·501·1001·2001입니다.
- **초과분:** 초과분은 (d6 µs/N − d3 µs/N) × 4096으로 계산하였습니다. 청사진 합계에 적용하면 (5.498 − 4.678) × 4096 = 3.358 ms로, 437 결과 문서의 값과 일치합니다.
- **표준편차 추정 근거:** 프로파일 간격은 `--cpu-prof-interval=1000`이었고(`<ns>/tools/finish-profiles.mjs:15`), 구간 안의 실제 평균 표본 간격은 약 1,505~1,509 µs였습니다. 구간 안 표본은 깊이마다 약 1,657~1,677개입니다. 작업 1회의 시간은 구간 길이를 반복 수로 나눈 고정값이므로, 함수별 값의 불확실성은 표본 수의 포아송 변동으로 보았습니다(상대 1표준편차 = 1/√표본 수). 청사진 합계는 단계 점유율의 이항 변동 √(p(1−p)/n)으로 계산하였습니다(p는 0.57~0.61이며 d5는 0.565, n≈1,660). 두 깊이의 차이에 대한 표준편차는 두 값의 표준편차를 제곱합의 제곱근으로 합쳤습니다. 이 추정은 단일 프로파일 안의 표본 변동만 반영하며, 프로세스 간 변동은 포함하지 않습니다. 표의 표본 수는 4~168입니다. 상대 1표준편차는 키 조회 줄 8~12 %, `visitShape` 16~23 %, `validateChildTargets` 26~50 %입니다. 줄 단위 포아송 표준편차는 하한입니다. 이웃한 줄 사이로 귀속이 옮겨지는 내용은 귀속 불가 절에 적습니다.
- **스크립트:** 계산 스크립트는 `{scratch}/bp.mjs`(함수별)와 같은 디렉터리의 `bp2.mjs`(줄별, flat 비교)입니다.

## 귀속

### 1. 확인된 경로 길이 비용: `encodeLeaf` 0.664 ms, 19.8 %

`encodeLeaf`(`getTemplateKey.ts:14-25`, `<ns>/bundles/E4.mjs:2908`)의 d6 초과분입니다. 깊이에 따라 0.291·0.308·0.394·0.453 µs/N로 단조 증가하고, 자식 경로가 부모 경로 전체를 다시 인코딩하는 기전과 맞습니다. 이 0.664 ms가 경로 길이 비용으로 확인된 몫입니다.

### 2. 경로 길이 몫이 미확정인 키 조회 줄: 1.166 ms, 34.7 %

키 Map 조회 1.166 ms는 `buildNodes.ts:39-40`에 있습니다. 깊이와 크기에 따라 오릅니다. 경로 길이 몫은 0~1.166 ms로 미확정이고, 기울기 추정은 약 0.5±0.4 ms이며 0에서의 거리는 1.3 σ입니다.

다만 키 조회 줄은 경로 길이가 거의 일정한 flat 가족에서도 노드 수가 커지면 오릅니다. 노드당 값은 다음과 같습니다(출처는 `<ns>/profiles/flat-*-mount.cpuprofile`, `<ns>/profiles/nested-*-mount.cpuprofile`).

| 가족 | 노드 수 V | `E4.mjs:2982` µs/V |
| --- | --- | --- |
| flat | 51 / 101 / 501 / 1001 / 2001 | 0.304 / 0.291 / 0.355 / 0.353 / 0.398 |
| nested | 85 / 341 / 1365 / 5461 | 0.230 / 0.343 / 0.337 / 0.442 |

노드 수가 비슷한 쌍에서 nested d5(V=1365, 키 약 192자)는 0.337±0.035 µs/V이고, flat-1000(V=1001, 키 약 103자)은 0.353±0.034 µs/V이며, flat-2000은 0.398±0.036 µs/V입니다. 약 1.9배 긴 키가 단가를 올리지 않았습니다. log2 V에 대한 가중 기울기는 flat 0.0182±0.0075, nested 0.0323±0.0073입니다. flat의 크기 기울기가 nested 상승의 약 56 %를 설명합니다. d4를 기준으로 한 이 줄의 d6 초과분은 0.545 ms이고, d3→d4의 0.305→0.457 µs/N이 큰 부분을 차지합니다. 현재 표본으로는 경로 길이 몫과 크기 몫을 가르지 못합니다.

### 3. 전체 노드 재순회: 0.699 ms, 20.8 %

`visitShape` 0.443 ms와 `validateChildTargets` 0.256 ms를 합한 값입니다. 두 함수는 청사진을 다 만든 뒤 모든 노드를 다시 도는 선형 코드입니다.

- `validateShape`가 모든 노드에 대해 `visitShape`를 호출하고(`src/core/engine/blueprint/validateShape/validateShape.ts:13`), 재귀는 각 간선을 한 번 지나므로 호출 수는 2V−1회입니다.
- `validateChildTargets`는 노드와 선언을 한 번씩 돌며 `readSchemaObject(...).controls`를 읽습니다(`src/core/engine/blueprint/validateChildTargets/validateChildTargets.ts:12`, `15`).
- 두 함수 모두 `src/core/engine/blueprint/blueprint.ts:78-79`에서 호출됩니다.

flat은 대조군이 아닙니다. flat에는 내부 노드가 하나뿐이어서 `complete`·`active` 집합이 자라지 않습니다(`validateShape.ts:11-12`, `visitShape.ts:23`·`33`·`43`). 다섯 크기 전체에 대한 기울기는 flat 0.0039±0.0035, nested 0.0120±0.0044입니다(flat은 nested의 약 33 %). nested에서는 `complete` 집합이 내부 노드 (N−1)/3개까지 자란다는 가설을 둡니다. 이 가설은 확정하지 못했습니다.

### 4. 귀속 불가: 0.832 ms, 24.7 %

이 몫의 순합은 0.832 ms이고 표준편차는 약 0.62 ms입니다(1.35 σ). 구성은 `appendChildEntries` 0.524 ms, `blueprint` 자체 0.325 ms, `collectDeclarations` 0.292 ms, 그리고 나머지 26개 함수의 순합(+0.372 ms와 −0.681 ms)입니다.

- `appendChildEntries`는 d3→d4에서 한 번 뛴 뒤 d4~d6에서 평탄합니다. 초과분 0.524 ms의 대부분은 환경 변수 줄 1975(+0.322 ms)와 개발 모드 전용 freeze 줄 1978(+0.224 ms)에 있고, 환경 변수 줄 1747은 −0.271 ms입니다.
- 환경 변수 줄의 합은 평탄합니다(1.689→1.697 µs/N).
- `blueprint` 자체와 `collectDeclarations`는 깊이에 따라 오르내립니다. `blueprint`의 3543행은 −0.296 ms, 3556행은 +0.234 ms로, 같은 방식으로 이웃 줄 사이에 귀속이 옮겨집니다.
- 프로세스마다 줄 단위 귀속이 이웃 줄로 옮겨지므로, 줄당 포아송 표준편차는 하한입니다.

따라서 이 몫의 원인은 확정하지 않았고, 귀속 불가로 둡니다.

GC와 유휴 시간은 이 나머지의 원인이 아닙니다. V8 프로파일에서 `(garbage collector)`와 `(idle)`은 루트 바로 아래 노드이므로, `blueprint` 조상을 요구하는 청사진 단계 선별에는 들어오지 않습니다. 참고로 마운트 전체에서 GC 자체 시간은 1.279·1.579·1.753·1.452 µs/N으로 단조롭지 않았습니다.

## 수정 가설

네 가설 모두 결정 58 실험이 아니며, 청사진 재사용도 아닙니다. 소유자가 정한 마운트별 청사진 재생성은 그대로 유지합니다. 기대 절감은 관측 차이에서 얻은 범위이며, 실제 절감량은 구현 후 같은 도구로 다시 측정해야 합니다.

### 1. 템플릿 키의 경로 interning

- **무엇을 바꾸는가:** `SchemaInput`에 내부 `locationId`를 추가합니다. id는 루트에서 시작하는 (부모 id, escape된 segment) 트라이로 부여합니다. `$ref`의 목표 경로(`getTemplateKey.ts`의 `resolveReference` 결과)도 같은 트라이를 통해 interning합니다. 템플릿 키에는 경로 문자열 대신 이 id를 사용합니다.
- **왜 관찰 결과가 같은가:** 키는 내부 값입니다. 동치 논증은 성립합니다. interning은 위치 문자열과 정확히 일대일이어야 합니다(같은 경로는 같은 id, 다른 경로는 다른 id). `$ref` 해석은 순수한 `{ $ref }` 스키마에만 적용됩니다(`src/core/engine/blueprint/buildNodes/utils/references/getTemplateKey.ts:45-48`). 게이트 서술자와 hostPaths는 문자열로 남으므로 `key`와 `boundKey`는 서로 다르게 유지됩니다. 이 조건에서 템플릿 공유와 `constructing` 재귀 판정은 현재와 같습니다.
- **기대 절감:** 확인된 0.664 ms에 미확정 최대 1.166 ms를 더한 값입니다. 확인된 몫은 `encodeLeaf`의 d6 초과분입니다. 키 조회 줄 1.166 ms의 경로 길이 몫은 미확정이므로 절감 근거는 약합니다.
- **위험:** `encodeLeaf`의 `JSON.stringify` 평탄화를 제거하면 그 비용이 나중 소비자로 옮겨질 수 있습니다. 이 이전은 확인하지 못했습니다. 따라서 측정은 마운트 전체여야 합니다.
- **측정 방법:** 437 도구로 측정할 수 있습니다(`profile.mjs`, `finish-profiles.mjs`, 같은 fixture). 다시 빌드한 E4 번들을 새 증거 경로에 복사한 뒤, 새 조용한 창에서 d3~d6 마운트 전체의 시간과 청사진 µs/N, `<ns>/bundles/E4.mjs`의 해당 줄을 함께 비교합니다.

### 2. 템플릿 재귀가 없으면 `validateShape`를 생략

- **무엇을 바꾸는가:** 전용 플래그를 하나 추가하고, `buildNodes.ts:41`의 `constructing.has(key)` 분기 안에서 세웁니다. 40행의 어느 `get`이 값을 돌려주었는지로 세우면 안 됩니다. `{ properties: { next: { $ref: '#' } } }`(`src/core/engine/blueprint/validateShape/__tests__/blueprint.recursion.test.ts:11`)에는 게이트가 없어 `boundKey`가 루트의 키와 같고, `templates.get`이 작성 중인 템플릿을 돌려주며 `constructing.get`은 평가되지 않습니다. `boundKey`가 `key`를 포함하므로(`getTemplateKey.ts:40`, `96`) 작성 중인 템플릿에 적중하면 `has(key)`는 항상 참입니다. 플래그가 없으면 `blueprint.ts:78`의 `validateShape`를 건너뜁니다. `staticFirstLoad`는 다른 이유로도 false가 되므로 재사용하면 안 됩니다.
- **왜 관찰 결과가 같은가:** 이 조건에서 검증은 조건부 통과입니다. 노드 사이의 순환은 만들어지는 중인 템플릿을 재사용할 때만 생깁니다. 완성된 템플릿을 재사용하면 순환 없는 공유만 생깁니다. `populateVirtualNodes`는 이미 있는 간선만 복사합니다(`src/core/engine/blueprint/buildNodes/utils/children/populateVirtualNodes.ts`). 배열은 `visitShape.ts:22`가 순회하지 않습니다. 다른 순환 경로는 없습니다. hit가 없으면 노드 그래프에 순환이 없으므로, `visitShape`는 `RecursiveShapeUnbounded`를 던질 수 없습니다.
- **기대 절감:** 0.815 ms(초과분 0.443 ms)입니다. 0.815 ms는 `visitShape`의 d6 전체(0.199×4096)입니다.
- **위험:** 플래그를 `has(key)` 분기 밖에 두면 `{ $ref: '#' }` 재귀를 놓칩니다. 분기 안에 두면 위 경로를 덮습니다.
- **측정 방법:** 가설 1과 같으며, 마운트 전체를 측정합니다.

### 3. 관련 controls가 없으면 `validateChildTargets`를 생략

- **무엇을 바꾸는가:** 선언을 수집하는 시점에 `controls.discriminator`나 `controls.fields`를 본 적이 있는지 플래그로 기록합니다. 플래그가 없으면 `blueprint.ts:79`의 호출을 건너뜁니다.
- **왜 관찰 결과가 같은가:** 이 가설은 성립합니다. 이 함수는 그 두 키가 있을 때만 오류를 던집니다(`validateChildTargets.ts:15` 이하). 선언은 `src/core/engine/blueprint/buildNodes/utils/declarations/collectDeclarations.ts:91-106`에서만 만들어집니다. 그 자리에서 `controls?.discriminator !== undefined || controls?.fields !== undefined`를 기록하면 조각, `$ref` 오버레이, 가상 선언(`populateVirtualNodes.ts:83`)을 덮습니다. 배열이 아닌 fields는 `src/core/engine/blueprint/buildNodes/utils/declarations/validateControlGroups.ts:68-69`에서 더 일찍 거절되므로, 빠지는 오류 경로는 없습니다.
- **기대 절감:** 0.332 ms입니다. 이는 d6 전체(0.081×4096)이고, 그중 초과분은 0.256 ms입니다.
- **위험:** 플래그를 선언 생성 지점 91-106행에 두면 조각·`$ref`·가상 선언이 빠지지 않습니다.
- **측정 방법:** 가설 1과 같으며, 마운트 전체를 측정합니다.

### 4. `process.env.NODE_ENV`를 모듈당 한 번 읽기

- **무엇을 바꾸는가:** `process.env.NODE_ENV`를 호출 지점 43곳마다 읽지 않고, 모듈당 한 번 읽어 상수에 둡니다. 이 가설은 NODE_ENV 절의 관찰에서 나왔습니다.
- **왜 관찰 결과가 같은가:** 실행 시점의 동작은 같습니다. 상수에 담아도 같은 프로세스 안에서는 같은 값을 봅니다.
- **기대 절감:** 초선형 초과분에 대한 기여는 0.033 ms로 재현되었습니다. 이 가설이 줄이는 것은 크기와 무관한 조회 비용과, 개발 모드에서만 남는 freeze 본문입니다. E4 절댓값과 E4/E0 배율 해석에 해당합니다.
- **위험:** 소비자 빌드에서 번들러의 죽은 코드 제거가 어떻게 되는지는 채택 전에 확인해야 합니다. 이 점은 열린 설계 항목입니다.
- **측정 방법:** 가설 1과 같으며, 마운트 전체와 E4/E0 배율을 함께 봅니다.

4. **437 창의 NODE_ENV가 비어 있었는지, 그 밖의 비운영 값이었는지는 확인하지 않았습니다.** 운영 값이 아니었다는 점은 NODE_ENV 절의 개발 모드 전용 줄 틱으로 확인됩니다.

7. **nested에서 `complete` 집합이 내부 노드 (N−1)/3개까지 자란다는 가설은 확정하지 못했습니다.** flat은 대조군이 아닙니다. macOS에서는 하드웨어 캐시 카운터 없이 이 가설을 확정할 수 없습니다.

환경 변수만 읽는 줄의 합은 0.80~0.91 µs/V이고, 청사진 시간의 21~27 %입니다. 예로 든 줄을 모두 합친 범위는 31~38 %이며, flat-50은 37.9 %입니다. 그 합은 다음과 같습니다(출처는 각 가족의 마운트 프로파일).

| 가족 | µs/V |
| --- | --- |
| flat (V=51~2001) | 1.289 / 1.168 / 1.256 / 1.213 / 1.204 |
| nested (d3~d6) | 1.271 / 1.297 / 1.266 / 1.273 |

dist는 빌드 시점에 `process.env.NODE_ENV`를 치환하지 않습니다. `<ns>/dist-E4/index.mjs`와 `<ns>/bundles/E4.mjs`가 실행 시점에 43곳에서 읽습니다. `NODE_ENV=production`으로 두면 개발 모드 전용 본문(freeze 등)만 빠지고, 읽기 비용은 남습니다. d6 프로파일에는 개발 모드 전용 본문 줄(1976-1978, 2430-2434, 3547-3557)에 틱이 있으므로, 437 창의 NODE_ENV는 운영 값이 아니었습니다. 하네스는 `spawnSync`에 환경을 넘기지 않습니다(`<ns>/tools/window.mjs`, `<ns>/tools/finish-profiles.mjs`). 0.16.1 번들(`<ns>/bundles/E0.mjs`)에는 `process.env` 읽기가 없습니다. 따라서 437의 E4/E0 배율에는 E4에만 있는 환경 변수 읽기 비용과 개발 모드 freeze 비용이 포함됩니다.

## 한계

이 진단은 437 측정 창의 크기당 단일 CPU 프로파일을 다시 분석한 것입니다. 새 측정이나 인과 실험은 아닙니다. 시간 귀속은 V8 표본 프로파일러만 사용하였고(99C-01), 호출 수는 ucount 계측 파일에서만 가져왔습니다. 수정 가설의 기대 절감은 관측 차이에서 얻은 범위이며, 실제 절감량은 구현 후 같은 도구로 다시 측정해야 합니다. 프로세스 간 변동은 크기당 프로파일이 하나뿐이어서 추정에 없습니다. NODE_ENV가 비어 있었는지 다른 비운영 값이었는지는 가르지 못했습니다.
