# 06단계 배열 성능 기록

## 환경과 재현

2026-10-01에 커밋 `f293efe18`의 worktree에서 MacBookPro18,2(M1 Max, 64 GB), Darwin 25.6.0/arm64, Node.js 26.10.0/V8과 `/opt/homebrew/bin/bun` 1.4.2/JSC를 순차 실행했습니다. 스크립트 실행은 서로 겹치지 않았습니다. 패키지 루트에서 실행한 명령은 다음과 같습니다.

```sh
node --expose-gc --import tsx bench/array.bench.ts
/opt/homebrew/bin/bun bench/array.bench.ts
node --import tsx bench/node-and-settle.bench.ts
/opt/homebrew/bin/bun bench/node-and-settle.bench.ts
node --import tsx bench/derive-and-controls.bench.ts
/opt/homebrew/bin/bun bench/derive-and-controls.bench.ts
```

`TEST-032`의 배열 잎 입력은 같은 10,000개 객체 아이템 중 `/5000/key`에 `setValue`를 120회(준비 20, 측정 100) 호출합니다. 입력 시간에는 트리 생성·청사진 분석을 넣지 않습니다. 두 엔진 모두 잎의 값을 매번 확인합니다. 레거시 루트 `value`의 해당 자리 값은 동기 시점에 마지막 잎 입력과 일치하지 않아 루트 확정까지 같은 시점에 기다린 비교는 아닙니다. 따라서 이 행의 큰 차이를 동등한 전체 커밋 비용의 배율로 읽지 않습니다. 루트 통째 쓰기는 1000개 객체 아이템 배열 두 개를 번갈아 `setValue`하고 루트의 500번 아이템을 매번 관찰합니다.

시간은 준비 20회 뒤 각 엔진 100표본의 중앙값입니다. 대괄호는 10–90백분위이고 단위는 µs/입력 또는 µs/쓰기입니다. 메모리는 `--expose-gc`/`Bun.gc(true)`로 GC한 별도 자식 프로세스 7개의 중앙값과 10–90백분위입니다. 입력 배열·스키마와 새 엔진의 청사진은 GC 전 준비해 차분에서 빼고, 루트 1 + 객체 아이템 10,000 + 숫자 잎 10,000 = 20,001개 노드로 나눴습니다. 잔존 트리·출력·런타임 부속 객체가 포함된 전체 트리 B/노드이며 노드 인스턴스 단독 크기는 아닙니다.

시간 두 행에서 표본별 처리량 평균의 레거시 대비 하락은 순서대로 Node 99.84%·71.53%, Bun 99.86%·92.11%입니다. Welch 통계량은 각각 106.53·19.79, 35.99·43.31(자유도 약 99–100)이므로 `TEST-072`의 처리량 −15% 초과와 p<0.05 선을 모두 넘습니다. 메모리는 같은 실행의 레거시보다 작습니다. `TEST-027`·실행 계획 I18에 따라 **NODE-053은 소유자 수용 대기**입니다. 수용 전에는 세 행 전체를 통과로 판정하지 않고, 지연 실체화 실패 대응도 이 단위에서 열지 않습니다.

잎 입력의 후보 비용은 새 엔진이 호출마다 동기 정착과 배열 출력 갱신을 끝내는 경로입니다. 레거시의 잎 값 관찰은 그 루트 확정까지 기다리지 않으므로 이 가설은 배율의 인과 분리가 아닙니다. 루트 통째 쓰기는 1000개 아이템 노드에 값을 위치별로 다시 쓰고 정착하는 경로가 후보입니다. 두 경우 모두 이번 계측은 단계별 CPU 시간을 분리하지 않았습니다. 느린 행은 [속도 문제 대장](../performance-issues.md)에 열어 두었습니다. 엔진을 최적화하거나 소유자 수용을 대신 적지 않았습니다.
