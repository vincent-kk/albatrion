# F-A의 array-100 갱신 회귀 진단

대상은 커밋 `c888bac6d`의 고정 사본에 F-A 패치(`fa.patch`의 src 부분)를 적용한 판과 기준 판입니다. 세션 122의 React 번들(`fa2-base`, `fa2-basex`, `fa2-change`)도 함께 썼습니다. 진단은 읽기 전용 Opus debugger가 했고, 저장소는 바꾸지 않았습니다. Node는 v26.10.0입니다. 도구와 원자료는 세션 scratchpad의 `fa-diag/`에 있습니다(`tools/counts.mjs`, `alloc.mjs`, `solo.mjs` 등). 부호는 판정 문서와 같게 기준 − 변경이고, 음수가 F-A가 느린 쪽입니다.

## 결론

**이 회귀는 F-A가 쓰기마다 일을 더 해서 생긴 것이 아닙니다. React 측정기가 두 번들을 한 프로세스에 함께 올리는 방식에서 생기는 순서 편향입니다.** 두 번들은 React와 jsdom을 함께 씁니다. 번들을 프로세스마다 하나만 올리면, gc가 있는 판정 조건에서 F-A의 첫 쓰기가 오히려 약 9 µs 빠릅니다.

## 근거

- **쓰기 1회당 계수(기준 / 변경).** F-A가 더 많은 것은 shallowEqual(memo 비교) 하나뿐입니다.
  - beginWork 219 / 207, 함수 렌더 32 / 32, 클래스 렌더 8 / 8, 문맥 읽기 68 / 64입니다.
  - bailout 152 / 136, 호스트 갱신 22 / 22, setProp 28 / 28, 커밋 1 / 1입니다.
  - shallowEqual 9 / 13, 마운트된 fiber 10,271 / 9,065입니다.
- **할당(기준 / 변경).** 마운트 65.12 / 63.93 MB, 첫 쓰기 222.3 / 219.7 KB, 두 번째 쓰기 157.4 / 157.4 KB입니다.
- **판정과 같은 방식**(두 번들을 한 프로세스에, F-A를 나중에 올림, gc 있음): 첫 쓰기 −4.3, −4.7, −5.0, −10.5 µs입니다.
- **올리는 순서만 바꿈**(F-A를 먼저 올림): F-A가 2.1 µs 느림, 2.6 µs 빠름, 5.8 µs 빠름으로 방향이 섞입니다.
- **A/A**(바이트만 다른 같은 코드): 나중에 올린 쪽이 첫 쓰기에서 6.0 / 8.8 / 17.3 / 14.7 µs 빨랐습니다. 순서를 바꿔도 나중 쪽이 11.5 / 23.0 / 12.5 µs 빨랐습니다. 측정기의 순서 편향이 F-A 효과보다 큽니다.
- **번들 하나만 올린 프로세스**(gc 있음, 기준과 변경을 번갈아 5쌍, 120표본): 첫 쓰기 중앙값은 기준 623.4 / 626.5 / 628.9 / 630.8 / 629.9 µs, F-A 623.7 / 618.9 / 617.3 / 623.0 / 619.8 µs입니다. F-A가 약 9 µs 빠르고, 4쌍에서 빠르며 1쌍은 같았습니다.
- **gc 없음 조건에는 별개의 실제 효과가 있습니다.** F-A는 마운트 때 1.18 MB를 덜 할당하고, 그 때문에 V8의 증분 마킹이 F-A의 쓰기 구간에 들어옵니다.
  - 마킹 작업은 F-A 쓰기 구간 60개 중 40개에 들어 있고, HEAD는 0개입니다. gc 있음 조건에서는 두 쪽 모두 0개입니다.
  - `--no-incremental-marking`을 켜면 첫 쓰기 차이가 −6 µs로 줄어듭니다.
  - 코드 비용이 아니라 GC 일정의 문제이므로, 제품 코드에서 고칠 대상이 아닙니다.
- **CPU 프로필**은 프로파일러 오버헤드와 GC가 지배해 결론을 내지 못했습니다. 자기 시간에서 두드러진 차이는 없었습니다.

## 고침 명세

1. **측정기(회귀를 없애는 고침).** React 짝 비교는 번들 하나만 올린 새 프로세스를 기준과 변경으로 번갈아 띄웁니다. 또는 두 번들의 로드 순서를 실행마다 바꾸고 두 순서의 평균을 보고합니다. A/A도 같은 방식으로 다시 만듭니다. 비용은 측정 시간이 늘어나는 것뿐입니다.
2. **gc 없음 열.** 제품 코드를 고칠 대상이 아닙니다. gc 있음·없음 두 열을 함께 보고하고, gc 없음 열에는 `--no-incremental-marking` 대조를 붙입니다.
3. **F-A 보완(선택).** `SchemaNodeProxy.tsx`의 `memo(ErrorBoundary)`는 비교가 매번 실패합니다. `children`이 렌더마다 새 엘리먼트이기 때문입니다. 이 memo를 지우고 ErrorBoundary를 직접 씁니다. 원래 아무것도 막지 못했으므로 동작은 같습니다. 필드당 fiber 1개와 쓰기당 shallowEqual 4회가 줄고, 시간은 1 µs 미만으로 추정합니다. 경계 위에서 bail을 되살리는 memo는 넣지 않습니다. 리비전을 prop으로 넘기지 않으면 errorMessage가 낡기 때문입니다.

## 확인하지 못한 것

- 두 번들을 함께 올릴 때 순서 편향이 생기는 V8 내부 경로는 밝히지 못했습니다. 가설은 공유 React와 jsdom의 피드백과 인라인 캐시가 먼저 올린 번들의 형태에 묶인다는 것입니다.
- 번들 하나만 올린 비교는 5쌍이고, 아홉 회차 판정은 하지 않았습니다.
- 고침 3의 시간 효과는 재지 않았고, 바인딩 계약의 원문과도 대조하지 않았습니다.
