# b3: payload 객체만 배달 경계에서 생성하는 좁은 변형

상태: **설계안, 구현하지 않음**. 86C-02의 재판정 대상입니다. 65C-03이 거절한 구독자 의존 revision 또는 커밋 스탬프로 revision을 역산하는 S4는 제안하지 않습니다.

## 유지할 경계

커밋은 지금처럼 리스너 유무와 관계없이 모든 배달 대상의 변경을 판정하고 각 비트 revision을 올립니다. 단조 commitNumber, 진단, 검증 스탬프, 전역 상태와 Refresh, 배달 대상 및 순서는 그대로입니다. 늦게 구독한 useSyncExternalStore 소비자는 읽기와 구독 사이의 revision 간극을 그대로 감지합니다.

변경은 커밋이 만드는 중첩 payload 객체의 생성 시점뿐입니다. 기존 pendingDelivery 봉투와 대상 집합은 유지하고, 봉투에 첫 previous 참조·최종 current 참조·종류별 존재 비트를 작업 기록으로 둡니다. branch의 local/emit도 개별 참조로 기록합니다. 새로운 노드 키 Map이나 11칸 스냅숏은 만들지 않습니다. 구체적인 record 필드 선언과 DETAIL 변경은 구현 승인이 난 작업에서 먼저 제시합니다.

dispatch가 파동의 대상과 리스너 목록을 고정하는 **동일한 경계**에서, 실제 리스너가 있는 사건에만 `{previous,current}`와 payload 비트 사전을 만들고 개발 빌드에서는 기존 범위대로 동결합니다. 이 작업은 첫 리스너 호출 **이전**에 해당 파동 전체에 대해 완료합니다. 앞 노드의 리스너가 flushSync로 다음 노드를 바꾸어도 이미 고정한 파동의 current가 달라져서는 안 됩니다. 한 사건의 모든 리스너는 같은 불변 payload를 봅니다. 옵션/source는 기존 커밋 선택을 그대로 기록합니다.

## 구독 전 변경에서 previous의 정확한 뜻

`previous`는 **그 노드의 마지막 완료된 통지 파동이 공표한 값**입니다. 통지는 특정 리스너가 읽은 횟수가 아니라 노드의 배달 경계입니다. 현재 `runDeliveryWaves`도 구독자가 없는 노드의 pendingDelivery를 소비하고, `deliverWave`가 그 중 실제 리스너가 있는 사건만 호출합니다. 이 기존 의미와 소비 시점을 유지합니다. 구독 자체는 통지가 아니므로 기준값을 바꾸거나 과거 사건을 재생하지 않습니다.

| 시간선 | 다음 관측 payload | revision |
| --- | --- | --- |
| 생성 A → 미구독 통지 완료 → B 커밋 → 구독 → B 파동 | previous=A, current=B | B 커밋 때 이미 증가 |
| 생성 A → B → C, 아직 첫 파동 전 → 구독 | previous=undefined, current=C | 각 커밋의 변경 비트대로 증가 |
| A 통지 완료 → 미구독 B 파동 완료 → 구독 → C 커밋·파동 | previous=B, current=C | A/B/C 각 커밋대로 증가 |
| A 통지 완료 → B → A, 한 파동에 병합 | 현재 구현과 동일한 마스크·previous=A·current=A | 각 커밋별 증가를 취소하지 않음 |
| A 통지 완료 → B 커밋 후 해제 → 파동 완료 → 재구독 → C | previous=B, current=C | 해제·재구독에 독립 |

미구독 파동도 봉투에 기록된 최종 참조를 기존 시점에 소비합니다. 값이 다시 변할 때 첫 기준은 그 완료값입니다. **최초 구독 때 현재 값으로 previous를 덮어쓰거나 마지막 실제 콜백 값만 기억하는 방식은 제외**합니다. 둘 다 구독 전 커밋과 파동을 합칠 때 현재 계약을 바꿉니다. 파동 고정 후 새 구독은 기존과 같이 다음 파동부터 참여하며, 콜백 중 해제·재구독 처리도 그대로입니다.

## 기대 절감과 비용

미구독 value 사건당 `{previous,current}` 1개와 payload 사전 최대 1개, branch value에서는 local/emit 포장 최대 2개를 생략합니다. 경로·스키마 payload도 실제 미구독 사건에 한해 각각 1개를 생략합니다. 여러 커밋을 한 파동에 합칠 때 구독 노드에서도 중간 포장을 생략할 수 있지만 첫 previous·최종 current 참조는 반드시 유지합니다. source/options와 pending 봉투, revision ledger 및 Set 등록 비용은 절감 대상으로 세지 않습니다.

시간 절감의 하한은 0이며, 상한도 `markCommitDeliveries`·`markSchemaNodeEvent` 전체를 없애는 시간이 아닙니다. 해당 함수 내 payload 생성·동결 몫만 해당합니다. 재측정 보고서의 delivery 배타 시간은 느슨한 외곽 상한이고 타이머로 분리하지 않은 객체 생성 몫을 실현 이득으로 주장하지 않습니다. 메모리는 미구독 사건의 단명 객체를 줄이는 대신 pending 봉투의 참조 칸을 파동 종료까지 유지합니다. 미구독 트리에서는 이득이 예상되며 대부분 노드가 구독되는 React 트리는 작거나 상쇄될 수 있습니다.

한 최초 커밋에서 모든 노드가 value 사건을 갖고 payload를 관측하는 구독자가 **전혀 없다는 가정**의 정적 할당 예산은 다음과 같습니다. 최초 previous는 undefined이므로 잎은 payload+비트 사전 2개, branch는 여기에 current의 local/emit 포장 1개입니다. 실제 할당 프로파일을 측정한 숫자가 아니며 구독 사건은 이 수에서 제외해야 합니다.

| 예시 형상 | 잎 / branch 수 | 생략 가능한 최초 payload 관련 객체 상한 | 개발 빌드 freeze 상한 |
| --- | ---: | ---: | ---: |
| flat-500 | 500 / 1 | 1,003 | 501 |
| nested-d5-f4 | 1,024 / 341 | 3,071 | 1,365 |
| array-1000 (아이템당 잎 3개) | 3,000 / 1,002 | 9,006 | 4,002 |

계산식은 `2 × 잎 수 + 3 × branch 수`이며 pending 봉투·옵션/source·revision 객체를 세지 않았습니다. 시간(ms) 기대치는 후속 할당 계측 전에는 미정입니다.

판정: **현행 계약을 유지하는 구현 후보로 검토 가능하나 승인·성능 검증 전 코드 적용 불가**. 후속 검증은 구독 시점 전후, 두 커밋 병합, A→B→A, 파동 중 flushSync와 해제, 비트별 revision, previous/current 참조, 동결, 오류·전역 상태 순서를 현재 구현과 차등 비교해야 합니다.
