# F-A'의 gc 없는 큰 배열 갱신 손실 진단

대상은 세션 129e의 React 번들입니다. 기준은 `r129-base`(HEAD, 제품 소스 `1a0176da3`)이고, F-A'는 `r129-fap`(HEAD에 `fa-prime.patch`를 더한 판)입니다. 두 번들의 SHA-256은 129d의 목록과 일치합니다. 진단은 읽기 전용 Opus debugger가 했고, 저장소는 바꾸지 않았습니다. Node는 v26.10.0이고, 모든 측정은 프로세스마다 번들 하나를 올려 기준과 F-A'를 번갈아 띄웠습니다. 도구와 원자료는 세션 scratchpad의 `fap-nogc-diag/`에 있습니다. 부호는 기준 − F-A'이고, 음수가 F-A'가 느린 쪽입니다.

## 결론

**손실은 증분 마킹 때문도 아니고, F-A' 코드가 쓰기마다 일을 더 해서 생긴 것도 아닙니다.** 쓰기 구간 안에서 젊은 세대 GC(Scavenge, 한 번에 약 2.5~3.9 ms)가 일어나는 표본의 비율이 F-A' 쪽에서 더 높아서 생긴 것입니다.

계기는 측정기 자체입니다. `tools/measure-react-pair-129.mjs:150`은 마운트와 쓰기 사이, 시계 밖에서 관측 digest(`canonical(getValue())`와 data-path 목록)를 만듭니다. 이때 array-1000에서 37.5 MB, array-500에서 19.5 MB를 할당합니다. F-A'는 마운트 할당이 8.8 MB(array-1000)와 4.4 MB(array-500) 적습니다. 그래서 이 읽기와 겹치는 젊은 세대의 채움 위상이 달라지고, Scavenge가 쓰기 구간에 들어가는 비율이 달라집니다. 이 비율은 실행 조건에 따라 방향까지 뒤집히므로, 코드의 성질이 아니라 할당 위상의 결과입니다.

- 마킹이 설명하는 몫은 0%입니다. `--no-incremental-marking`을 켜도 손실이 줄지 않았습니다.
- 손실의 약 95% 이상(array-1000)과 100%(array-500)는 Scavenge가 쓰기 구간에 들어가는 비율의 차이입니다.
- GC가 없는 표본만 보면 쓰기당 차이는 array-1000에서 −7.5~+16 µs, array-500에서 0~+26 µs로, 0 근처이거나 F-A'가 유리합니다.

## 근거

- **공식 129e 원자료의 분해**(블록 24, 표본 984개). 느린 갈래(Scavenge가 든 표본)의 비율과 빠른 갈래의 중앙값입니다.
  - array-1000: 비율 18.4% → 39.8%, 빠른 갈래 1.325 / 1.347 ms. 중앙값 차이 −171 µs 가운데 −164 µs가 비율 몫이고, 빠른 갈래의 이동은 −7.5 µs입니다.
  - array-500: 비율 32.9% → 46.5%, 빠른 갈래 0.980 / 0.974 ms. 중앙값 차이 −104 µs 가운데 −131 µs가 비율 몫이고, 빠른 갈래는 +26.5 µs로 F-A'가 빠릅니다.
- **GC 추적**(`--trace-gc`, 쓰기 구간 표지, perf_hooks gc 항목, 2쌍씩).
  - array-1000: Scavenge가 든 쓰기 구간이 기준 16/82, F-A' 21/82입니다. GC 없는 구간의 중앙값은 1,348 / 1,332 µs로 F-A'가 16 µs 빠릅니다.
  - array-500: 이 조건에서는 방향이 뒤집혀 기준 42/82, F-A' 31/82입니다. 전체 중앙값은 기준이 1.25 ms 느렸습니다. GC 없는 구간의 중앙값은 976 / 978 µs로 같습니다.
  - 쓰기 구간 안의 마킹 단계 작업은 평균 0~0.01 ms로 무시할 만합니다.
- **결정 대조.** 쓰기 직전(시계 밖)에 `gc({ type: 'minor' })`를 넣으면, 쓰기 구간 안의 GC가 array-1000에서 0/164건, array-500에서 1/164건이 됩니다. 이때 차이는 +6.7 µs와 +0.7 µs로 F-A'가 같거나 약간 빠르고, 손실은 사라집니다.
- **쓰기 전 읽기를 뺀 대조.** 측정기의 digest 읽기를 뺀 worker에서는 F-A'가 +45 µs(gc 패스 없음)와 −0.1 µs(gc 패스 있음)입니다. 그 읽기가 없으면 손실이 나타나지 않습니다.
- **쓰기 1회당 계수(기준 / F-A', 두 fixture 같음).** F-A'가 더 많은 계수는 하나도 없습니다.
  - 함수 렌더 32 / 32, 클래스 렌더 8 / 8, 커밋 1 / 1, 호스트 갱신 22 / 22, setProp 28 / 28, 이펙트 16 / 16, shallowEqual 9 / 9입니다.
  - beginWork는 1,119 / 1,103(array-500은 619 / 603)이고, 문맥 읽기는 68 / 64입니다.
- **할당.**
  - 마운트: array-1000 585 / 576 MB, array-500 294 / 289.5 MB입니다.
  - 쓰기 1회: GC를 넣지 않은 실행에서 F-A'가 18~56 KB(3~11%) 많았습니다. 그러나 추적 실행 하나에서는 606 / 578 KB로 방향이 반대였습니다.

## 측정 쪽 고침(제품 코드는 고칠 대상이 아님)

1. gc 없는 기록 열에 두 값을 함께 보고합니다. 쓰기 구간 안의 GC 비율(perf_hooks의 `gc` 항목)과, GC가 없는 표본의 중앙값입니다.
2. 측정기의 digest 읽기가 쓰기 직전의 젊은 세대를 채우지 않게 합니다. 읽기를 쓰기 뒤로 옮기거나, 읽기 뒤 시계 밖에서 minor gc를 넣은 대조 열을 둡니다.

## 확인하지 못한 것

- Scavenge가 동기 쓰기가 아니라 drain(setImmediate 네 번) 구간에 주로 일어나는 까닭을 밝히지 못했습니다. 쓰기 구간의 적중률(18~48%)이 쓰기 할당 대비 젊은 세대 비율(약 4%)보다 훨씬 높은 까닭도 밝히지 못했습니다. 가설은 digest 읽기가 만든 큰 문자열과 배열이 젊은 대형 객체 공간을 채운다는 것입니다.
- 쓰기 1회 할당이 F-A'에서 많은 출처는 확인하지 못했고, 방향도 한 실행에서는 반대였습니다.
- 쌍 수는 2~3쌍으로 적습니다. 결론은 주로 공식 984표본의 갈래 분해와 minor gc 대조에 기댑니다.
