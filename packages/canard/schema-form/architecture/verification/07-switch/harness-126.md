# 126회차 측정기 정정: 번들 하나 프로세스 짝 비교와 F-A'

이 문서는 125라운드 닫기 결정 125C-01의 (1)~(3)을 실행한 기록입니다. HEAD는 `9f92fef8578d70b6e34423c9753d2b285a4ac40f`이고, 모든 시간 측정은 `/opt/homebrew/bin/node`의 Node v26.10.0으로 했습니다. 번들·캐시·원자료의 루트 S는 `/private/tmp/claude-501/-Users-Vincent-Workspace-albatrion/c8aaf054-1ea7-43d3-b3c1-a4196f8407e1/scratchpad`입니다. 부호는 판정 문서와 같게 기준 − 변경이며, 음수는 변경 쪽이 느리다는 뜻입니다. 구간은 세션 119와 같은 xorshift seed 101, 1,999회 재표집의 99% 대응 중앙값 구간입니다.

## 결론

1. **React 짝 측정기는 이제 프로세스마다 번들 하나만 올립니다.** A/A 자체 점검(array-100 갱신, 10블록, 1,010쌍)에서 먼저 띄운 프로세스와 나중 프로세스의 차이는 +0.83 µs, 구간 [−3.21, 5.92]이었습니다. 한 프로세스에 두 번들을 올리던 방식의 편향(6.0~23.0 µs)은 보이지 않습니다.
2. **코어 측정기에도 작은 순서 편향이 있습니다.** 한 프로세스 방식에서 if-then OFF 첫 갱신은 먼저 올린 번들이 0.75 µs 빨랐고, 구간 [−1.33, −0.17]이 0을 포함하지 않았습니다. 방향은 React와 반대여서, 나중에 올리는 변경 번들이 그만큼 느리게 보입니다. 크기는 React 편향보다 한 자릿수 작지만, 이 행들의 A/A 하한(1.0~1.5 µs)과 같은 크기입니다.
3. **새 코어 모드(번들 하나 프로세스, ABBA)에서는 이 편향이 드러나지 않습니다.** 같은 A/A에서 if-then OFF 첫 갱신의 차이는 −0.13 µs, 구간 [−1.38, 1.29]였고, 두 순서의 중앙값 부호도 섞였습니다. 다만 프로세스 사이의 흩어짐이 더해져 구간이 넓어지므로, 편향은 설계로 상쇄한 것이지 0임을 증명한 것은 아닙니다.
4. **F-A'는 F-A에서 항상 실패하는 `memo(ErrorBoundary)`를 뺀 판입니다.** 필드당 fiber가 기준 대비 평면 24 → 20, 배열 21 → 17로 줄었습니다(F-A는 21, 18). 쓰기당 렌더 수와 재마운트는 F-A와 같습니다. 지정된 모든 검증이 통과했습니다.

## 1. React 짝 측정기

새 도구는 `tools/measure-react-pair-126.mjs`이고, 번들 진입점은 `tools/measure-react-pair-126.entry.tsx`입니다.

- **번들 준비(`--prepare`).** `prepare-react-bundles.mjs`에 선택 인자를 더해 그대로 씁니다. 선택 인자는 고정할 리비전, 진입점, 출력 이름, 그리고 `equivalentHarness`입니다. `equivalentHarness`를 켜면 `@canard/schema-form`은 그 판의 소스로, `react-dom/client`는 외부 production profiling 빌드로 해석합니다. 0.16.0은 외부로 두고, `mountEquivalentForm`의 `mountMs` 구간에 이벤트 루프 활성 시계를 붙입니다. 세션 122 어댑터가 원문 치환으로 하던 일을 도구의 인자로 옮긴 것입니다.
- **두 판의 해석 방식을 맞췄습니다.** 처음 만든 번들에서는 base(HEAD 고정)가 플러그인 해석을, change(작업 트리)가 기본 해석을 거쳤습니다. 그 결과 `sideEffects` 기반 트리 셰이킹이 change에서만 일어나 모듈 38개가 빠졌습니다. 이제 `equivalentHarness`에서는 두 판이 같은 명시 해석을 거치고, 두 번들의 모듈 차이는 F-A'가 지우고 더한 파일 두 개뿐입니다. 또 작업 트리에서 지워진 HEAD 파일이 패키지를 가져올 때는 외부 모듈로 표시하도록 고쳤습니다.
- **측정(`--pair <AA|change> <fixture> <run>`).** 측정 프로세스마다 번들 하나만 `new Function`으로 올립니다. 회차 r의 k번째 블록은 (k + r)이 짝수면 기준→변경, 홀수면 변경→기준 순서로 새 프로세스를 띄웁니다. 그래서 두 쪽의 프로세스 수와 먼저 뜬 횟수가 같습니다(ABBA). AA는 base 대 basex(base에 끝 주석 한 줄을 더한 사본), change는 base 대 change입니다.
- **유지한 것.** 판정 열은 네 번의 setImmediate 뒤 wall과 같은 구간의 이벤트 루프 활성 시간입니다. 예열 20회와 표본 101개, 시계 밖의 강제 gc를 유지했습니다. `--old-wait`는 `drainTicks(2)` 대기의 별도 기록 회차입니다.
- **단언과 비교.** 보정 회차에서 쓰기당 커밋 수를 관찰하고 1회임을 단언합니다. 모든 표본의 쓰기마다 그 보정값과 같은지도 단언합니다. 값·경로 digest는 프로세스 안의 모든 표본에서 같아야 하고, 두 쪽의 모든 프로세스 사이에서도 같아야 합니다.
- **기록.** 블록 k의 기준·변경 프로세스를 표본 순번으로 짝지어 `pair-*.json`에 둡니다. 열 이름은 세션 122 보고 도구가 읽는 `timing.base/candidate` 모양과 같고, 블록 순서대로 이어 붙입니다.

자체 점검은 `fap-base` 대 `fap-basex`의 array-100 갱신(쓰기 1회)으로 했습니다. 1회차는 2블록, 2·3회차는 4블록으로 모두 10블록이며, 기준이 먼저 뜬 블록과 사본이 먼저 뜬 블록이 5개씩입니다. 프로세스 20개, 쓰기 2,420회에서 커밋 수 단언 실패는 0회였고, digest는 모두 `83326f80c7b6…`로 같았습니다.

## 2. 코어 측정기의 순서 편향

### 한 프로세스 방식의 진단

`S/bundles`의 `c-head`와 `c-headx`는 리비전 `439fda321`의 표시를 달고 있어 현재 HEAD의 매니페스트 검사를 통과하지 못합니다. 그 사이 `schema-form/src`, `winglet`, `aileron`에는 바뀐 파일이 없습니다. 그래서 `prepare-patch-bundles.mjs`로 현재 HEAD에서 `S/bundles-126`에 다시 만들었고, 아홉 번들 모두 `S/bundles`와 바이트가 같았습니다. 측정에는 `--bundles=S/bundles-126`을 썼습니다.

기존 도구(`measure-verdict-121.mjs --pair`)로 행마다 c-head를 먼저 올린 AA와 c-headx를 먼저 올린 `headx:head`를 4회씩 돌렸습니다. 회마다 표본은 300개이므로 순서마다 1,200쌍입니다. 아래 값은 먼저 올린 번들 − 나중에 올린 번들이며, 양수면 나중 쪽이 빠릅니다.

| 행 | c-head 먼저 µs | c-headx 먼저 µs | 두 순서 합침 µs | c-head − c-headx µs |
| --- | ---: | ---: | ---: | ---: |
| if-then OFF update-first | −0.46 [−1.29, 0.25] | −1.08 [−1.92, −0.25] | −0.75 [−1.33, −0.17] | +0.25 [−0.29, 0.83] |
| if-then ON update-first | −0.21 [−1.33, 1.25] | −0.83 [−2.25, 0.37] | −0.42 [−1.37, 0.37] | +0.37 [−0.42, 1.37] |
| if-then OFF mount | −3.96 [−5.92, −2.04] | +1.75 [−0.13, 3.08] | −1.17 [−2.33, 0.13] | −2.75 [−3.96, −1.71] |
| oneOf-10 OFF mount | −1.92 [−7.50, 4.63] | +1.71 [−3.25, 5.08] | +0.21 [−3.75, 3.83] | −1.88 [−4.88, 2.87] |
| array-100 OFF update-first | −0.83 [−1.92, 0.29] | +0.67 [−0.54, 1.67] | −0.08 [−0.96, 0.83] | −0.79 [−1.54, 0.12] |

- **if-then 첫 갱신에는 순서 편향이 있습니다.** OFF는 두 순서 모두 음수이고 합친 구간이 0을 포함하지 않습니다. ON도 두 순서 모두 음수이지만 구간이 0을 포함합니다. 먼저 올린 번들이 0.4~0.8 µs 빠릅니다.
- **나머지 행에는 순서 편향이 보이지 않습니다.** 순서를 바꾸면 부호가 뒤집히므로, 차이는 순서가 아니라 번들의 정체나 소음입니다. if-then OFF 마운트에서는 c-head가 c-headx보다 2.75 µs 빨랐고, 순서를 바꿔도 같은 쪽이었습니다. 이 원인은 밝히지 못했습니다.
- **기존 판정에 미친 영향.** 코어 짝 측정기는 기준을 먼저, 변경을 나중에 올립니다. 그러므로 이 편향은 변경을 느리게 보이게 합니다. 세션 122에서 1c를 기각한 if-then 첫 갱신 회귀(OFF −1.79 µs, ON −2.08 µs)와 변경 2의 OFF 첫 갱신 회귀(−1.29 µs)는 이 0.4~0.8 µs를 품었을 수 있습니다. 다시 판정하지는 않았습니다.

### 새 모드: 번들 하나 프로세스

새 도구는 `tools/measure-core-pair-126.mjs`입니다. 측정 프로세스는 기존 측정기를 `measure-verdict-121.mjs --pair … --single=<base|candidate>`로 띄웁니다. `--single`을 주면 `measurePair121`이 그 쪽 번들 하나만 읽고 올리며, 공식 표본과 표본 순서·열·digest 처리는 기존과 같습니다.

- **프로세스별 절차.** 95C-01 절차를 그대로 지킵니다. 예열 20회, 표본 101개, 시계 밖의 강제 gc, gc 뒤 첫 빈 호출 쌍 버리기, 짝 빈 호출 꼬리를 유지합니다.
- **(ga) 검사.** 공식 표본과 빈 호출 대조 뒤, 같은 강제 gc 순서를 `@winglet/common-utils/scheduler` 감싸개 아래에서 한 번 더 돌려 모드별 경계 계수를 냅니다. 상위 도구가 프로세스마다 (ga)를 판정합니다. 보정 상수는 그 프로세스의 빈 호출 대조에서 얻고, 잡음 폭은 `report-verdict-121.mjs`와 같은 식입니다. 이를 위해 그 파일의 `bootstrap`을 내보내기로 바꿨습니다.
- **ABBA와 digest.** 블록 순서 규칙은 React 도구와 같습니다. 값 digest 계수는 두 쪽의 모든 프로세스 사이에서 같아야 합니다.
- **기록.** 블록 k의 두 프로세스를 표본 순번으로 짝지어 `pairRows121` 입력 모양(`summary`, `timings.base/candidate`)으로 저장합니다.

같은 다섯 행의 A/A를 행마다 3회 × 4블록으로 돌렸습니다. 모두 12블록이며 c-head가 먼저 뜬 블록과 c-headx가 먼저 뜬 블록이 6개씩이고, 순서마다 606쌍입니다. 프로세스 120개의 (ga)가 모두 통과했습니다.

| 행 | c-head 먼저 뜬 블록 µs | c-headx 먼저 뜬 블록 µs | 먼저 − 나중 합침 µs | c-head − c-headx µs |
| --- | ---: | ---: | ---: | ---: |
| if-then OFF update-first | +0.29 [−1.25, 1.88] | −0.46 [−2.17, 1.50] | −0.13 [−1.38, 1.29] | +0.33 [−1.00, 1.54] |

- **if-then 첫 갱신의 편향이 사라졌습니다.** OFF와 ON 모두 두 순서의 부호가 섞이고, 합친 구간이 0을 포함합니다.
- **대신 프로세스 사이의 흩어짐이 더해집니다.** 블록별 중앙값이 첫 갱신은 ±2~3 µs, 마운트는 ±10 µs로 흩어지고, oneOf-10 마운트에는 +108과 −122 µs인 블록이 하나씩 있었습니다. 마운트 행의 "먼저 − 나중"이 두 순서 모두 음수(−3~−4 µs)이지만 구간이 0을 포함하므로, 순서 편향이라고 판단할 근거는 없습니다.

## 3. F-A'

`S/fa.patch`의 `packages/canard/schema-form/src/` 부분을 작업 트리에 적용한 뒤 다음을 바꿨습니다.

- `SchemaNodeProxy.tsx`에서 `const RendererErrorBoundary = memo(ErrorBoundary)`를 지우고, 렌더러를 `<ErrorBoundary onError={onError}>`로 직접 감쌌습니다. `onError`는 그대로입니다.
- 같은 폴더의 DETAIL.md와 INTENT.md에서 "경계를 memo로 유지한다"는 문장을 "ErrorBoundary를 직접 쓰고 memo로 감싸지 않는다"로 고쳤습니다. fiber 순감소 목표도 3개에서 4개로 고쳤습니다.
- `renderCounts.test.ts`는 필드당 fiber 기대값만 21에서 20으로 바꿨습니다. 쓰기당 렌더와 격리 단언은 그대로 통과했습니다.

변경을 적용한 상태에서 실행한 검증은 다음과 같습니다.

- F-A 시험 `rendererBoundary.test.tsx`와 `renderCounts.test.ts`가 통과했습니다.
- `npx vitest run --project unit --project render --project react18 --reporter=dot`에서 461개 파일, 3,398개 시험이 통과했고 todo 1개가 있었습니다.
- `yarn test:production`(production 프로젝트)에서 9개 파일, 20개 시험이 통과했습니다.
