# 청사진 정적 분석 비용과 원본 코퍼스

`yarn node packages/canard/schema-form/architecture/verification/02-foundation-and-blueprint/blueprint-measure.mjs`로 실제 소스를 Vite SSR에 읽혔습니다. 서버 시작·모듈 로드는 측정 밖입니다. 각 입력에서 호출자 캐시 없이 같은 스키마의 청사진을 7회 새로 만들고 자식 연결 수를 단언했습니다. 결과는 런타임 노드 생성·정착 시간이 아닌 청사진 1회 분석 시간입니다.

| 소스 | Node | 원본 코퍼스 수용 | 공유 참조 100 / 1,000 / 5,000개의 7회 중앙값 |
| --- | --- | --- | --- |
| 19라운드 전 `36089c4f2` ([역사적 원자료](./blueprint-final-measure.json)) | 24.20.0 | 0/14 | 0.435 / 2.012 / 12.262 ms |
| 19라운드 후 `2aef1cbb5` ([새 원자료](./round19-blueprint-measure.json)) | 24.20.0 | **14/14** | 0.437 / 2.246 / 14.433 ms |

앞 행은 BLUEPRINT-039·045 E16이 적용되던 당시의 결과이며, TEST-067(b)의 최종 판정이 아닙니다. 새 행은 원본 `corpus.mjs` 14종을 변형 없이 넣어 모두 수용했습니다. 시험 파일도 원본을 직접 읽고 입력의 직렬화 값이 분석 전후 같은지 단언합니다.

서로 다른 시점의 단발 실행에서 1,000·5,000개 행은 각각 11.7%·17.7% 오래 걸렸습니다. 이 차이를 확인하려고 같은 Node 24.20.0 환경에서 이전 소스와 현재 소스를 독립 프로세스로 여섯 쌍 실행하고 순서를 AB/BA로 번갈았습니다. 각 프로세스의 7회 중앙값을 한 관측치로 보아 쌍별 현재/이전 비율의 기하평균을 냈습니다([12회 원자료](./round19-blueprint-paired.json)).

| 공유 참조 수 | 분석 노드 수 | 현재/이전 시간 비율 | 로그 비율의 95% t 구간 |
| --- | --- | --- | --- |
| 100 | 3 | 0.960 | 0.911–1.011 |
| 1,000 | 3 | 0.965 | 0.901–1.033 |
| 5,000 | 3 | 0.954 | 0.914–0.996 |

같은 환경의 교대 실행에서는 단발의 느림이 재현되지 않았습니다. 100·1,000개 구간은 1을 포함하므로 이 측정만으로 개선을 확정하지 않습니다. 19라운드의 `inferAllowedTypes` 분기 추론도 이 입력의 비용 경로에 없습니다. 루트·공유 `$defs`·잎은 모두 자기 `type`이 있어서 `resolveNodeTypes`가 `readAllowedTypes`의 결과를 사용하고 추론 호출을 건너뜁니다. 동일 참조의 뒤따르는 연결은 `buildNodes`의 템플릿 캐시에서 반환되므로 100개와 5,000개 모두 분석 노드가 3개입니다. 따라서 새 추론 규칙을 원인으로 한 느림이라는 근거는 없습니다. 6쌍의 작은 표본과 실행 환경의 변동은 남습니다.
