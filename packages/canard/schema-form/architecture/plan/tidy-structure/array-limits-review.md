# 배열 한도(`minItems`·`maxItems`)를 core가 다룰 때의 유익과 손해 — 대기열 53 검토 메모

> 2026-10-14, 원장 관리자. 301·302라운드 소유자 말(`../../reviews/round-301-owner-answers.md:8`, `round-302-owner-answers.md:7`)에 대한 답. 결정은 소유자 몫이며, 이 메모는 비교표다.

## 0. 소유자의 틀

- 값을 조절·제어하는 기능은 `controls`로 모았다. 그러니 "core는 값을 조작하지 않는다"(ADR 0013)가 한도 기능을 막는 것은 아니다.
- 노드는 올바르지 않은 타입의 값을 가질 수 있다(검증이 알림). 배열 개수도 그런 느낌으로 입력 컴포넌트(formType)의 일일 수 있다.
- 둘 다 가능하니 유익과 손해를 보자.

## 1. 지금 상태(사실)

| 항목 | 레거시(0.16) | 새 엔진(1.0.0-beta) |
| --- | --- | --- |
| `maxItems` 초과 `push` | 막음(`push(data?, unlimited?)`, `unlimited`로 우회) | 막지 않음. 기본 입력이 `maxItems`에서 추가 버튼만 숨김(`FieldInputArray.tsx:82`) |
| `minItems` 채움 | 생성·reset 때 아이템 기본값으로 채움. 예외가 많았다: null 배열·derived 배열은 안 채움, reset 플래그 전체 일치 때만 재충전, 채움이 `injectTo`를 발동하지 않게 `PreventInjection`(레거시 ArrayNode DETAIL 9–15·58–69행) | 채우지 않음(시험 고정: VALUE-034·WRITE-022·LANDING-116·LANDING-155) |
| 한도의 출처 | 정적 스키마 | 유효 스키마(게이트 분기 `then`/`else`의 기여를 셈, `resolveArrayLimits`) — 런타임에 바뀔 수 있음 |
| 문서 | — | SPECIFICATION en 986·998행이 아직 "미리 채움·reset 재충전"을 약속(결함, 정돈-E 문서) |

## 2. 두 길의 차이는 "어느 어휘의 뜻을 바꾸는가"다

- `minItems`·`maxItems`는 **JSON Schema 검증 키워드**다. core가 이것을 동작(채움·차단)으로 쓰면 검증 키워드가 조용히 변이(mutation)의 지시가 된다 — 같은 스키마를 다른 검증기·서버와 공유할 때 뜻이 갈린다.
- `controls.*`는 **폼 전용 어휘**라 JSON Schema 쪽 뜻이 없다. 제어를 여기에 두면 뜻의 이격이 생기지 않는다. 소유자의 "control로 다 모았다"는 틀이 바로 이 경계다.

## 3. core가 막지 않을 때(현행) 생길 수 있는 문제

| 문제 | 실제 영향 | 완화 |
| --- | --- | --- |
| 프로그램 `push`·`setValue`·derived·`injectTo`가 `maxItems`를 넘긴다 | 값은 들어가고 검증이 오류를 낸다. 수 노드에 문자열이 들어오는 것과 같은 부류 — 폼·노드·출력 일치 원칙은 지켜진다 | 검증 오류, `onError`. 기본 입력은 추가 버튼을 숨김 |
| `minItems`가 있는데 초기 입력이 0개로 그려진다 | **0.16과 가장 눈에 띄는 차이.** 사용자는 빈 칸 N개를 기대했다 | 입력 컴포넌트가 **값을 쓰지 않고** 빈 슬롯 N개를 그릴 수 있다(UI 전용 자리, LANDING-116의 "explicit slots remain editable"와 같은 모양). 기본 `FieldInputArray`에 넣으면 core는 그대로이고 UX만 돌아온다 |
| 이주 놀람 | 0.16 코드가 core 차단에 기댔다면 1.0.0에서 검증 오류로 바뀐다 | 이주 안내에 명시(지금 문서는 반대로 적혀 있음) |
| 한도 위반 상태가 "유효하지 않은 폼"으로만 남는다 | 제출은 거부되므로 데이터는 새지 않음 | — |

요약: 손해는 UX 기대(빈 칸 N개)와 이주 안내뿐이고, 둘 다 입력 컴포넌트와 문서로 메울 수 있다.

## 4. core가 막거나 채울 때 생길 수 있는 문제

| 문제 | 실제 영향 |
| --- | --- |
| 채움은 값을 만든다 | 출력에 `[undefined, undefined, undefined]`나 아이템 기본값이 생겨 `omitEmpty`·nullable·분기 배열·derived 배열과 얽힌다. 레거시가 쌓았던 예외 목록(null 배열 제외, derived 제외, reset 전체 일치, `PreventInjection`)이 settle에 다시 들어온다 — 새 엔진이 걷어낸 복잡도 그 자체 |
| 차단은 "쓰기가 조용히 안 됨"을 만든다 | 새 엔진의 쓰기는 일어나거나 던진다. `push`가 noop이면 새 거부 코드(경고 또는 오류)와 FormHandle 쪽 계약이 필요하다. derived·`injectTo`가 큰 배열을 쓰면 자르는가? 자르면 값 조작(ADR 0013 정면 충돌) |
| 한도가 런타임에 바뀐다 | `then`/`else`로 `maxItems`가 줄면 자르는가(데이터 손실), `minItems`가 늘면 채우는가(값 생성). 레거시는 정적 전략만 다뤘다. 새 엔진은 유효 스키마가 게이트마다 바뀌므로 이 질문을 피할 수 없다 |
| 검증과 두 겹 | core가 보장하면 검증의 `minItems`·`maxItems` 오류는 사실상 죽은 경로가 되어 "검증이 알린다"는 단일 원칙이 흐려진다 |

요약: 손해는 settle의 예외 복잡도 복귀, 쓰기 거부 계약 신설, 동적 한도의 미정 의미 셋이고, 셋 다 작지 않다.

## 5. 권고

1. **1.0.0은 현행(A)대로 둔다.** 근거는 §2의 어휘 경계(검증 키워드는 검증으로)와 §4의 비용. "노드는 잘못된 타입의 값을 가질 수 있다"는 소유자의 유비가 그대로 적용된다.
2. **UX 손해는 입력 컴포넌트에서 메운다.** 기본 `FieldInputArray`가 `minItems`만큼 빈 슬롯을 값 없이 그리는 것(UI 전용)과 `maxItems`에서 추가 숨김(이미 있음)을 1.0.0 범위로 둘지 소유자가 정한다 — 작은 PR이며 core 불변.
3. **제어가 필요하면 `controls` 어휘로 옵트인한다(B, 별도 라운드).** 예: `controls.itemLimits: 'enforce'` — 켠 노드에서만 `push`가 `maxItems`에서 경고 코드와 함께 거부되고 생성·reset 때 `minItems`까지 채운다. 기본은 끔. 동적 한도의 의미(줄면 자르지 않고 경고, 늘면 채움)를 그때 원장 항목으로 먼저 적는다.
4. **문서는 지금 고친다.** SPECIFICATION 986·998행과 같은 주장 전부(fairy08 조사 중), 이주 안내에 "core는 한도를 강제하지 않는다"를 적는다.
