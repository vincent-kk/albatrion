# 설계 최적화 — 정착 계산 단계와 캐시 계층 — ADR과 핵심 축

> ADR 본문은 권위가 아니다. 축은 원리·수락된 결정·목표다(PROCESS-034). 구현 중 현장 판단은 원리 원장으로 돌아와 한다(PROCESS-005). 성능 최적화 작업(`../perf-optimization/adr-and-axes.md`)은 "결정을 바꿔야 빨라지면 설계 변경이고 라운드가 먼저다"를 전제로 했다. 이 단계는 그 설계 변경이 목적이며, 소유자가 8단계 뒤 코어 설계 수정을 명시적으로 허용했다(LANDING-211). 그래도 순서는 같다: 바뀌는 결정은 코드보다 먼저 라운드 항목으로 들어간다(446라운드가 그 첫 라운드다).

## 이 단계가 지켜야 하는 축

| 축 | 원장 | 이 단계에서의 뜻 |
| --- | --- | --- |
| G6 비용은 변경에 비례 | GOAL-011, TEST-029, TEST-027 | 판정의 첫 기준. 형제 1,000개 호스트의 판별자 한 번에 형제 전부를 다시 고르는 것(`selectChildren.ts:53`), 게이트 있는 폼의 잎 쓰기에서 호스트 전체를 깊은 비교하는 것(`preserveReferences.ts:28-31`)은 바뀐 것의 크기가 아니라 폼 크기에 비례하므로 이 단계가 고치는 결함이다. "같은 값을 두 번 읽으면 같은 참조"는 그대로다 |
| P3 형상은 상태의 순수 함수, 출발점 고정 | GOAL-029, SETTLE-044, SETTLE-050 | 두 설계 모두 직전 커밋의 활성 집합에서 출발하지 않는다. 설계 Ⅱ의 비활성 슬롯은 "후보 풀"이지 "직전 형상"이 아니며 게이트 레지스트리에서 빠진다. 게이트 입력 메모(BLUEPRINT-053)는 입력이 같은 순수 술어의 결과를 기억하는 것이라 이력 의존이 아니다 |
| 게이트는 전부 다시 평가 — 완화 | BLUEPRINT-007, BLUEPRINT-053 | 역색인은 여전히 기각이다. 허용된 것은 게이트별 입력 메모(투영 참조·extras·context·존재가 같으면 술어를 부르지 않음, 던진 평가는 메모하지 않음)이고 넣을지는 벤치가 정한다. 소유자가 뒤집을 수 있다(대기열 63) |
| 형상을 떠난 노드는 떼어진다 | NODE-044, NODE-043, VALUE-031 | 다시 들면 새 인스턴스, 옛 참조의 읽기는 마지막 커밋으로 고정, 구독은 발화하지 않음. 설계 Ⅱ는 내부 슬롯을 유지하되 공개 `FieldNode`를 수명마다 새로 발급해 이 계약을 지킨다(NODE-060). 공개 노드 객체를 되살리는 안은 기각되어 있다 |
| 비용의 상한과 순회 범위 | SETTLE-017, SETTLE-047 | 2단계 정착은 형상 단계를 더럽혀진 독자 호스트로, 값 단계를 부모 사슬 한 번의 상향 조립으로 묶는다. 트리 전체 순회는 로드와 전체 교체 쓰기만이라는 상한은 그대로다 |
| 바퀴 안의 즉시 반영과 상속 overlay | SETTLE 영역(`design/03-settle-and-events.md:120·124`) | 한 바퀴 안에서 뒤 게이트가 앞 게이트의 투영을 즉시 본다는 계약과 상속 overlay는 2단계 정착이 깨면 안 된다. 게이트 입력은 요청이 올 때 투영한다(`pendingOutputs`·`readProjectedValue`의 일반화) |
| 청사진은 폼 생성 때 한 번, 재사용은 identity로 | BLUEPRINT-052, LANDING-204(438라운드 소유자 조건) | 같은 스키마 객체와 같은 술어 identity일 때만 재사용한다. 직렬화 키는 쓰지 않는다. 소비자가 스키마 객체를 변형했으면 `rebuild`로 강제 갱신한다 |
| 캐시 계층의 자리 | SURFACE-063, `src/core/INTENT.md`(core는 app을 import하지 않음) | 소비자 소유 키 캐시만 `src/app/cache`에 두고 바인딩이 core에 넘긴다. 엔진 파생 캐시는 엔진 안의 레코드 둘로 합친다. 상수 깎기 캐시와 전역 상태 금지(운영 원칙 14)는 그대로이며, 파생 레코드는 불변 청사진의 순수 함수라 그 금지의 대상이 아니다 |
| 한 파동, 커밋 뒤 통지, revision은 리스너 유무와 무관 | EVENT-006, ADR 0008 | 배달 후보 큐(H5)는 파동의 수와 순서를 바꾸지 않고 revision 비트 계수를 유지한다. 리스너 없는 노드를 건너뛰는 것은 payload 생성뿐이다 |
| 성능은 측정 | TEST-029, TEST-031, TEST-026, TEST-072, TEST-073 | 기준선은 같은 프로세스의 0.16.1 쌍이고 dist를 잰다(357라운드). 주장만 있는 개선은 병합하지 않는다(442C-03). 채택 규칙은 폭 (다)(443C-03) |
| 느린 행의 수용 | TEST-027 | D4 관문 수치 밖의 느린 행은 이유와 수치를 적어 소유자가 수용한다. 크기에 비례 이상으로 커지는 비용은 수용 대상이 아니다(56라운드) |
| 공개 계약 | SURFACE 영역, LANDING-209·210 | 이 단계가 더하는 공개 이름은 `FormHandle.rebuild` 하나다(SURFACE-063). 그 밖의 이름·형·반환형은 바뀌지 않는다 |
| G5 결정성 | GOAL-009 | 같은 입력에 같은 결과. 레코드·메모·큐는 결과를 바꾸지 않아야 하며 그 증명은 기존 시험 전체의 초록과 전후 배달 비교 차이 0이다 |

| 0008 이벤트 시스템 | 한 파동·커밋 뒤 통지·revision 원장은 그대로. 배달 후보 큐는 구현 방식의 변경이다 | EVENT-006 |

| 0016 채움 시점과 전체 교체 쓰기 | "노드가 생길 때 한 번"은 설계 Ⅱ에서 "비활성에서 활성으로 들어갈 때"로 읽히며 `entered` 집합이 그 뜻을 이미 가진다(`markWrite.ts:47-50`). `setValue(V)`가 V에 없는 경로의 raw를 잠복 raw까지 지우는 규칙은 비활성 슬롯 걷기로 같은 결과를 내야 한다 | VALUE-031, WRITE-007 |

## 축이 금하는 후보 (들어오면 멈춘다)

- 직전 커밋의 `active`에서 이어 출발하는 정착(SETTLE-044). 비활성 슬롯을 "직전 형상"으로 쓰는 것도 같다.
- 게이트의 읽기 경로를 뽑아 건너뛰는 역색인(BLUEPRINT-007). 입력 메모(BLUEPRINT-053)는 이와 다르다.
- 공개 노드 객체를 재진입 때 되살리는 것(NODE-044). 설계 Ⅱ는 핸들을 새로 발급한다.
- 시험 기대값을 바꿔야 통과하는 변경(동작 변경). 바꿔야 한다면 성능 변경이 아니라 사양 변경이므로 멈추고 소유자에게 묻는다(운영 원칙 12).
- 정착 단계의 순서 변경(SETTLE-001, ADR 0007).
- `FormHandle.rebuild` 밖의 공개 겉면 변경.
- 아이템 노드의 지연 실체화(NODE-053).

이 가운데 하나가 유일한 길로 보이면 코드를 바꾸지 않고 새 라운드 항목으로 올린다.
