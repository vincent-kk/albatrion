# 06 배열 — 실행 구조 결정

이 문서는 06 실행 계획([execution-plan.md](execution-plan.md))이 정한 구조 결정을 계획 없이 읽히도록 적는다. 모듈 경계, 의존 방향, 계약의 소유, 오래 남을 자리만 다룬다. 설계의 정본은 원장 `ledger/`이며, 이 문서와 원장이 어긋나면 원장이 이긴다. 경로 약어는 `CORE` = `packages/canard/schema-form/src/core`다.

## D1 배열 행은 `behaviors/arrayBehavior/` fractal이고, 구조 연산은 행의 순수 칸 하나를 거친다

- 맥락: 원장은 `arrayBehavior/`에 `branch/`·`terminal/`·`utils/`를 두고(LANDING-056·085), 배열 메서드는 단일 클래스에 두되 비배열에서 부르면 "행의 공유 칸"이 던져 겉면과 `dispatch`가 종류를 묻지 않게 한다(NODE-014). 오늘의 `Behavior`(`CORE/record/type.ts:82-97`)에는 그런 칸이 없다.
- 결정:
  - 새 fractal `CORE/behaviors/arrayBehavior/`가 `array.branch`·`array.terminal` 두 행을 낸다. 객체 행 `objectBehavior/`와 같은 모양이다.
  - `Behavior`에 순수 칸 `arrange(node, operation)`를 `declareChildren` 뒤에 더한다. 배열 행은 연산의 계획(branch: 새 자리마다 옛 자리 색인 또는 새 값, 무동작 여부, 반환 값의 출처; terminal: 원본 사본 위의 새 원본)을 돌려준다. 비배열 행은 behaviors 공유 organ의 거부 칸 하나를 같은 참조로 쓰고, 그 칸이 `SchemaFormError`(가칭 `ARRAY_METHOD_ON_NON_ARRAY`)를 던진다.
  - 계획의 적용(노드 생성·재사용·소멸, 이름·경로 바꿈, 스냅숏 자리, 정착)은 settle이 한다(D4).
- 까닭: 행은 계산 칸만 가진 공유 표이고 효과는 가장자리 한 곳에 둔다(seiri function-boundaries §2, NODE-006). 종류 분기를 행 표가 맡으면 겉면은 한 문장 위임으로 남는다(NODE-014, `SchemaNode/DETAIL.md`의 클래스 파일 규칙).
- 버린 것: 겉면 메서드가 `type`을 검사해 던지는 것(NODE-014가 막음). 행에 효과 칸을 두는 것(행이 settle을 가져와야 하고 NODE-009·016의 의존 방향을 깸). 동사마다 칸 다섯을 두는 것(칸이 늘어 모든 행의 키 순서 표가 커지고 같은 거부 함수를 다섯 번 둠).
- 결과: 모든 행의 칸 순서가 `interpret`, `assemble`, `project`, `finishInput`, `declareChildren`, `arrange`, `type`, `strategy`가 된다. `behaviors/DETAIL.md`와 행 표 시험이 함께 바뀐다.

## D2 아이템 자리 항목은 청사진이 만들고, 선언 경로는 템플릿 경로를 지킨다

- 맥락: 청사진은 배열 템플릿에 `item`(경로 `/arr/*`)과 `prefixItems[i]`(경로 `/arr/i`)를 두지만 `BlueprintChildEntry`를 만들지 않는다(`CORE/blueprint/utils/analyze/populateNodeChildren.ts:102-186`). 정착의 자식 선택(`selectChildren`·`primeHost`)은 항목의 이름·노드·선언으로 돈다. 원장은 선언 경로가 배열 단계마다 아이템 마디 하나를 둔다고 정했다(35C-08).
- 결정: 청사진 organ의 보조 하나가 배열 템플릿과 자리 i로 `BlueprintChildEntry`와 같은 모양의 항목을 만든다: 이름 `"i"`, 노드 `prefixItems[i] ?? item`, 선언은 속성 항목과 같은 방식으로 다시 묶되 선언 경로는 템플릿 경로 그대로. 템플릿·색인별로 지연 메모해 같은 자리는 같은 참조다. 청사진 없는 자리는 항목이 없다. 배열 행의 `declareChildren`이 이 보조로 아이템 수만큼 항목을 돌려준다.
- 까닭: 속성 항목을 만드는 규칙을 아는 곳이 청사진이다. 정착은 객체·배열을 같은 선택 기제로 다룬다(GOAL-006, NODE-026: 객체와 배열은 자식 집합의 출처만 다름).
- 버린 것: 행이 항목을 직접 만드는 것(행이 청사진의 선언 묶기 규칙을 복제함). 정착에 아이템 전용 선택 경로를 따로 두는 것(같은 게이트·생김·나감 기제가 둘이 됨).
- 결과: `blueprint/DETAIL.md`에 보조의 계약이 들고, 청사진의 분석 결과(`Blueprint`)는 바뀌지 않는다.

## D3 정체성 키·아이템 수·키 계수는 레코드 칸이다

- 맥락: 아이템의 React key는 생성 순서의 nonce `#n`이고(GOAL-073), 공개 `key`는 없다(SURFACE-054). 원장은 레코드의 `structure`에 "배열의 아이템 목록과 키 번호"를 둔다(NODE-004). 통째 쓰기의 새 아이템 수는 정착이 자식을 고르기 전에 알아야 한다.
- 결정: 레코드에 칸 셋을 더한다: 아이템의 정체성 키, 배열 branch 호스트의 아이템 수(청사진 있는 자리와 없는 자리를 합친 값 길이), 호스트의 키 계수(단조 증가, 되감지 않음). 모든 노드가 같은 고정 배치를 가지므로 비배열 노드에서는 빈 값이다. 아이템 목록 자체는 기존 `structure`(이름 = 위치)다.
- 까닭: 단일 클래스의 고정 배치(NODE-004·045). `structure`의 이름 열쇠가 곧 위치라 기존 선택 기제가 위치 잇기를 그대로 한다(NODE-051).
- 버린 것: `structure`의 열쇠를 `#n`으로 두는 것(경로·`find`·스냅숏이 위치를 읽어 모든 경로 열쇠 저장소와 어긋나고, 정수 열쇠와 섞이면 `Object.values` 차례가 바뀜). 키를 호스트의 별도 배열에 두는 것(이름 바꿈마다 두 목록을 함께 고쳐야 함).
- 결과: `record/DETAIL.md`에 칸과 노드당 메모리 비용이 든다. 벤치 "노드당 메모리"가 이 칸을 잰다.

## D4 위치가 밀리는 일은 정착 밖에서 한 번 하고, 경로 열쇠 저장소를 함께 옮긴다

- 맥락: 새 엔진의 런타임 저장소는 노드 객체 밖에서 모두 절대 경로나 `(path, kind)`를 열쇠로 쓴다: 대기 나감, 게이트 경로 색인, 잠복 원본과 메타데이터, `committedDeclarationIds`, 파생·나감 정책 규칙 기준값과 색인, `typeMismatchPaths`와 경로 메모, 로드 스냅숏 읽기. 이름을 바꾸는 보조(`record/utils/updateSchemaNodeNameAndPath.ts`)는 한 노드의 다섯 칸만 바꾸고 제품 호출자가 없다. 정착 안에서 이름이 바뀌면 대기 나감 열쇠가 충돌하고 같은 경로의 다른 노드가 상태를 이어받는다(코드 추적, 2026-10-01).
- 결정:
  - 정착 안에서는 아이템 이름을 바꾸지 않는다. 통째 쓰기는 이름 = 위치로 노드를 잇고 꼬리만 만들거나 소멸시킨다.
  - 구조 연산은 settle의 구조 진입 함수 하나가 정착 전에 적용한다: 새 아이템 목록, 자리가 바뀐 아이템과 자손의 이름·경로 바꿈, 모든 경로 열쇠 저장소의 옮김(경로 접두 메모는 무효화), 스냅숏 자리 맞춤, 생김·소멸 기록. 그 뒤 표시 → 계산 → 파생 → 전이 → 커밋을 한 번 돈다.
  - 이 일은 새 organ `CORE/settle/utils/structure/`에 둔다. 옮길 저장소의 목록은 시험 하나가 고정한다. 경로에서 다시 계산되는 색인(게이트 색인의 자리 L과 `watchPaths`)은 열쇠를 옮기지 않고, 옮길 하위 트리를 지운 뒤 새 경로로 다시 등록한다.
- 까닭: 정착 기제는 "경로는 정착 동안 고정"을 가정하고 있고, 그 가정을 지키면 대기 나감·채움 한 번·게이트 색인 규칙을 고치지 않아도 된다. 구조 연산은 호출자의 한 쓰기이므로(GOAL-028) 정착 한 번이다(WRITE-007).
- 버린 것: 정착 안에서 이름을 바꾸는 것(위 충돌). 경로 열쇠 저장소를 정체성 키 열쇠로 바꾸는 것(03·04의 모든 저장소와 경로 기반 원장 규칙 — 잠복 `(path, kind)`, 떼어진 쓰기의 살아 있는 경로 확인 — 을 다시 써야 하며 06의 범위를 넘음).
- 결과: `settle/DETAIL.md`에 구조 진입 함수와 "정착 중 경로 고정" 불변식이 든다. 구조 연산의 비용은 옮긴 아이템 하위 트리 크기와 저장소 항목 수에 비례한다(`remove(0)`은 O(배열 길이), WRITE-095의 O(배열 길이)와 같은 차수).

## D5 소멸은 나감과 다른 길을 탄다

- 맥락: 짧아진 통째 쓰기·`remove`·`pop`·`clear`·로드로 사라지는 아이템은 소멸이며 나감 정책·비움·원본 B 나감 기록이 없다(WRITE-036). 떼어진 참조 규칙은 그대로다(NODE-044). 게이트로 꺼진 아이템은 나감이다(35C-08). 오늘의 커밋은 대기 나감에 든 노드를 모두 나감으로 처리한다.
- 결정: 정착 작업 칸에 소멸 집합을 둔다. 소멸 노드는 커밋에서 NODE-044대로 떼어 읽기를 얼리고, 나감 정책·비움·잠복 보관을 건너뛰며, 그 경로 아래의 경로 열쇠 항목을 버린다. 게이트로 꺼진 아이템은 기존 나감 경로를 그대로 탄다.
- 까닭: 두 사라짐의 원장 규칙이 다르고, 자리가 남는가(나감) 없어지는가(소멸)로 갈린다(VALUE-034).
- 버린 것: 소멸을 나감 정책 "유지"로 흉내 내는 것(잠복 원본이 남아 `inactiveValues`에 뜨고 같은 경로의 새 아이템이 그 원본을 이어받음).
- 결과: `settle/DETAIL.md`의 나감 문단에 소멸이 따로 든다.

## D6 템플릿 경로는 정착이 실제 경로로 묶는다

- 맥락: 원장은 아이템 안의 식이 위치마다 한 번 컴파일되고 모든 아이템이 공유하며, 실행에서는 노드의 실제 경로가 기준점이라고 정했다(CONTROLS-080, 35C-08). 청사진의 역의존 표·게이트·규칙은 템플릿 경로(`/arr/*/x`)를 담고, 정착의 색인은 그것을 실제 경로처럼 쓴다(`CORE/settle/utils/write/getDependencyIndex.ts`, `getGateRegistry`, 파생 규칙 열쇠).
- 결정: 청사진은 바꾸지 않는다. `CORE/settle/utils/paths/`의 보조가 템플릿 경로를 실제 경로로 묶는다. 역의존 색인은 `*` 마디를 아무 색인과 맞추고 소유자 경로를 바뀐 경로의 색인으로 묶어 돌려준다. 게이트 등록과 자리 L, 파생 규칙의 원천·대상, 상태 키 층, 나감 정책 열쇠, `@` 맥락 소유자 목록은 노드의 실제 경로를 기준으로 한다. 다른 아이템을 가리키는 절대 경로는 배열 호스트 하위 트리에 기댄다(18C-13).
- 까닭: 원장이 묶기를 정착의 조회 변경으로 정했다(35C-08). `*`가 없는 경로는 묶기가 항등이라 03·04의 객체 동작이 바뀌지 않는다.
- 버린 것: 청사진이 아이템마다 선언을 펼치는 것(아이템 수만큼 청사진이 커지고 "위치마다 한 번 컴파일"을 깸).
- 결과: `settle/DETAIL.md`에 묶기 규칙이 든다.

## D7 `resolveArrayLimits`는 청사진의 공개 이름이다

- 맥락: behaviors와 behaviors 밖이 함께 쓰는 것은 청사진으로 간다(NODE-009). core는 배열 길이 제약을 강제하지 않고 유효 스키마로 노출한다(WRITE-022). 06 안에서는 쓰는 곳이 없다.
- 결정: 청사진 organ으로 옮기고 청사진 진입점이 이름으로 내보낸다. 입력은 유효 스키마의 `schema`다. 의도한 소비자(07·08의 입력 구성 요소)를 `blueprint/DETAIL.md`에 적는다. 레거시 사본은 09까지 그대로다(35C-04, LANDING-159).
- 까닭: seiri public-contract §1은 소비자 없는 수출에 의도의 기록을 요구한다.
- 버린 것: 07까지 옮기지 않는 것(LANDING-085·094가 PR-5에 배정).
- 결과: 청사진의 공개 이름이 하나 는다.
