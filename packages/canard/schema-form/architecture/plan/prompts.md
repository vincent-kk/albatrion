6. 실행 가능한 단계가 없으면 필요한 의존성이나 소유자 결정을 정확히 기록하고 간결하게 인계하세요. 무한히 상태를 조회하거나 새 작업을 만들어내지 마세요.

- 의미 있는 전환 시점과 컨텍스트 복구·인계 전에 기록을 남기세요. 원시 출력을 복사하기보다 보고서를 연결하세요. 이번 작업에 속한 파일·변경 구간만 명시적으로 stage하고 생성 번들과 컴파일 산출물은 제외하세요.

## 5. 계획 작성과 통과할 때까지 리뷰

1. 최초 작업을 이해한 뒤 seiri:write-plan을 사용하세요. 저장소의 계획 작성 방식을 명시하세요. 모든 요구사항을 구현 작업 및 관찰 가능한 검증과 연결하고, 비목표·의존성·소유권·계약·레거시 처리·위험·확인된 명령·기대 결과를 포함하세요.
2. 작업을 독립적으로 검증할 수 있는 단위로 나누되 개수를 임의로 고정하지 마세요. 중요한 선택은 3절의 원장 대조로 실행 전에 해결하세요. 스킬이 요구하는 구조적 결정은 계획 옆에 기록하되 아키텍처 원장을 덮어쓰지 마세요. 원장으로 판단 가능한 질문을 미결 소유자 결정으로 남기지 마세요.
3. 새로운 리뷰어(1절의 담당 배정대로 기본 antigravity)에게 최초 작업 원문, 관련 원장 항목, 저장소 규칙, 실행 계획, 게이트 원장, 불확실한 부분을 전달하고 seiri:review-plan을 수행하게 하세요. 문장뿐 아니라 저장소의 실제 상태와 요구사항 누락 여부를 확인하세요.
4. 판정과 실행 가능한 지적사항을 근거와 함께 기록하세요. 피드백을 원문과 대조하고 계획을 수정한 뒤 영향받는 주장들을 재리뷰하세요. 접근 자체가 틀렸다면 계획 수립으로 돌아가세요. 진행을 막는 지적이 모두 해소되고 cleared 판정을 받을 때까지 반복하세요.
5. 바뀌지 않은 범위의 유효한 리뷰 근거는 재사용하세요. 자기 검토를 독립 리뷰라고 부르지 마세요. 리뷰어를 사용할 수 없으면 한계를 기록하고 독립적으로 가능한 준비를 계속하되 통과했다고 주장하지 마세요.
6. 통과하면 곧바로 seiri:execute로 진행하세요. 일상적인 소유자 확인을 다시 요청하거나 계획을 보여준 뒤 멈추지 마세요.

## 6. 범위를 나눈 다중 에이전트 구현

- 집중 조사, 독립 리뷰, 서로 겹치지 않는 구현 단위, 최초 요구사항 대조 검증에 서브에이전트를 활용하세요. 조율 에이전트도 소스·diff를 직접 확인할 수 있으며 요약이 근거를 대신하지는 않습니다.
- 위임마다 저장소·worktree·브랜치, 원문 경로와 원장 ID, 수정 허용 파일, 입력·출력, 완료 기준, 검사, 보고 형식을 명시하세요. 리뷰어에게는 결과물과 요구사항을 전달하고 판정을 유도하지 마세요.
- 서브에이전트도 불확실성을 발견하면 3절의 원장 대조를 먼저 수행하고 가능한 해석과 근거를 보고하게 하세요. 조율 에이전트는 서브에이전트의 확인 요청을 그대로 사용자에게 전달하지 말고, 기존 계약 안에서 해결할 수 있는지 직접 판단하세요.
- 역할이 바뀔 때는 새 컨텍스트를 우선하세요. 구현자가 자기 작업의 유일한 검증자가 되어서는 안 됩니다. 파일마다 작성자는 한 명으로 제한하고, 인터페이스가 확정된 독립 단위만 병렬 처리하세요. 공유 로그, 통합, 커밋, push, PR 갱신은 조율 에이전트가 담당하세요.
- 보고는 발견사항, 변경 경로, 검사·결과, 근거 위치, 미해결 질문으로 간결하게 받으세요. 원시 로그나 대형 diff 전체를 조율 컨텍스트에 넣지 말고 필요한 부분을 확인하세요. 완료 보고는 주장이지 증명이 아닙니다.
- 단위마다 seiri:implement를 사용하세요. 구현 전에 소유 DETAIL 계약을 갱신하고, INTENT는 경계가 바뀔 때만 수정하세요. 필요한 새 fractal 문서는 코드보다 먼저 만들고 해당 단계의 문서 선행 커밋 요구를 따르세요.
- 진입점, organ 접근, 의존 방향, 테스트 위치, 현재 구조 설정을 지키세요. 테스트만을 위해 공개 API를 넓히거나 지적을 없애려고 규칙을 약화하지 마세요.
- 현행 원장의 레거시 이동·보존, import 제한, 엔진 전환 경계를 따르세요. 새 단위가 동작한다는 이유만으로 레거시를 삭제하거나 공개 연결을 전환하지 마세요.
- 버그 수정은 수정 전 회귀 검사가 의도한 이유로 실패하고 수정 후 통과함을 증명하세요. 리팩터링은 변경 전후의 동작 고정 근거를 보존하세요. 문서 작업은 문서 계약과 산출물을 검증하세요.
- 구현 중에는 단위 범위의 검사를 실행하세요. 원인 불명의 실패는 seiri:trace-cause, 간접 연결이 복잡한 코드는 seiri:trace-structure로 조사하세요. 반복 실패에는 원인 분석이나 재계획이 필요하며 임의의 재시도 횟수만으로 중단하지 마세요.

## 7. 최초 작업 대조 검증과 PR 생성

1. 독립 검증자와 seiri:verify를 수행하세요. 최초 기준선, 현재 정본, 통과한 계획, 실제 diff, 검증 근거를 전달하세요. 요구사항별로 충족·미충족·차단·해당 없음과 그 이유를 받으세요.
2. 산출물과 동작을 최초 요청, 원장, 불변조건, 검증 체크리스트와 대조하세요. 누락, 범위 확장, 회귀, 요구사항 약화를 찾아내세요. 테스트 통과만으로 완료를 판단하지 마세요.
3. 해당 단계가 정한 검사를 실행하세요. 관련 기존·신규 테스트, lint, 타입 검사와 strict 공개 타입 검사, 빌드·산출물 검사, 벤치마크, 기타 필수 게이트를 포함합니다. 현재 스크립트를 확인하고 루트 명령이 없으면 yarn workspace 명령을 사용하세요. 명령을 만들어내거나 문서에 언급됐다는 이유만으로 도구를 설치하지 마세요.
4. 해당 단계의 기존 검증 위치에 명령, 범위, 리비전, 종료 결과, 한계를 기록하세요. 변경되지 않은 유효 근거는 재사용하고, 수정 후에는 영향받는 검사와 필수 최종 게이트를 다시 실행하세요. 생략·미지원·판정 불가 결과를 PASS로 바꾸지 마세요.
5. 지정된 기준선과 방법으로 성능을 측정하세요. 성능 저하에 대한 소유자 수용 규칙을 따르세요. 빌드는 검사하되 생성 산출물을 소스 커밋에서 제외하세요.
6. 적용되는 seiri 게이트를 실행하세요. 전체 FCA 스캔은 아래 PR 경계에서 수행하세요. 해당 단계가 PR 생성 전 FCA 근거를 명시적으로 요구하면 여기서 한 번 실행하고 이후 변경으로 무효화되지 않는 한 재사용하세요.
7. 일반 리뷰 PR을 열기 전에 구현 검증 지적을 해결하세요. 실제 장애물은 정직하게 기록하고 막힌 작업을 완료라고 부르지 마세요.
8. 범위 내 변경을 커밋·push하고 확인한 base로 단계 PR 하나를 생성하거나 갱신하세요. 여러 줄 본문은 본문 파일이나 구조화된 인자로 전달하세요. 문제와 결과, 최초 완료 기준과 리뷰 체크리스트 및 근거, 검증·성능, 계획 이탈, 원장 불일치, 남은 PR 이후 검사를 포함하세요.
9. 실제 PR URL과 상황판 리뷰 상태를 기록하세요. 다음 절차가 끝날 때까지 PR을 draft로 유지하거나 후속 검사 대기임을 명확히 표시하세요. PR URL을 얻었다는 이유로 멈추지 마세요.

## 8. PR 이후 문서 보강·FCA 리뷰·수정

1. 영향받는 모듈에 filid:enrich-docs를 --include-detail --repair --auto-approve로 실행하세요. 이 요청은 해당 단계 안에서 근거에 따라 INTENT·DETAIL을 보완하는 작업을 승인합니다. 한정된 수정 계획을 보여준 뒤 스킬의 자동 승인 절차로 계속하세요. 정본 아키텍처 입력을 다시 쓰거나 범위를 넓히거나 버그에 맞춰 계약을 약화하지 마세요.
2. 설정된 프로젝트 루트에서 PR 경계의 filid:scan을 수행하고, 허용되는 경우 여전히 유효한 PR 이전 근거를 재사용하세요. 문서, 노드, 진입점, 경계, 의존 DAG, 검증 계약을 확인하세요. 경고와 기존 발견도 드러내세요. 분석이 불완전하거나 발견사항이 있는 스캔을 깨끗한 통과라고 부르지 마세요. 작업 단위마다 전체 스캔을 반복하지 마세요.
3. 새 리뷰어(1절의 담당 배정대로 기본 antigravity)에게 seiri:request-review로 독립적인 약식 리뷰를 맡기세요. 정확한 base·head 리비전, 최초 작업·원장 참조, 최종 diff, 검증 근거, 보강된 계약, FCA 발견을 전달하세요. 요구사항 충족, 정확성, 회귀, 경계, 테스트 유효성, 범위를 검토하세요. 약식은 보고를 집중한다는 뜻이며 완료 기준을 낮추는 뜻이 아닙니다. 별도의 무관한 전체 리뷰 파이프라인을 시작하지 마세요.
4. 발견을 ID, 심각도, 위치, 근거, 처리 결과로 추적하세요. seiri:receive-review로 피드백을 검증하세요. 확인된 범위 내 결함은 seiri:implement로 고치고, 오탐은 근거가 있을 때만 기각하세요. 계약 해석이 갈리면 3절의 원장 대조로 먼저 해결하고, 그 질문 조건에 해당할 때만 상신하세요. 무관한 기존 발견은 몰래 고치거나 숨기지 말고 이유와 함께 공개하세요.
5. 변경된 동작·문서·구조를 적절한 검사와 seiri:verify로 재검증하세요. 수정된 지적과 새로 영향받은 계약을 다시 리뷰하세요. 진행을 막는 발견이 해소될 때까지 반복하고 첫 수정만 적용한 뒤 멈추지 마세요.
6. 수정을 커밋·push하고 같은 PR의 제목·본문·체크리스트와 로그를 최종 구현에 맞춰 갱신하세요. 계획·원장 변경에 필요한 아키텍처 문서 검사는 ARCH/HANDOFF.md를 따르세요. 필수 CI·검사가 최종 리비전을 대상으로 하는지 확인하고 대기 중이거나 접근할 수 없는 검사는 명시하세요.
7. 최초 요구사항, 필수 검사, 문서 작업, 구조 발견, 리뷰 처리 결과를 모두 설명할 수 있을 때만 PR 이후 작업을 완료하세요. 차단하는 발견이 남아 있으면 단계는 진행 중입니다. 허용된 비차단 잔여 발견은 근거와 담당 주체를 기록하세요.
8. PR을 소유자 리뷰에 넘기세요. 실제 머지가 확인되기 전까지 PLAN의 상태는 리뷰로 유지하세요. 머지나 배포 없이 해당 finish 경로로 seiri 단계 워크플로우를 마무리하세요.

## 9. 다음 작업 진행 또는 인계

- PR 이후 절차를 마치면 디스크의 PLAN.md와 계획 README를 다시 읽고 선택 절차를 반복하세요. 기억한 단계 번호를 증가시키거나 오래된 상태·머지되지 않은 의존성에서 다음 작업을 시작하지 마세요.
- 컨텍스트 복구 후에는 최신 문서, 저장소의 실제 상태, 재개 기록으로 이어가세요. 리뷰 통과나 근거를 재사용하기 전에 원문·리비전 일치를 확인하세요. 사라진 임시 seiri 산출물은 보존된 기록에서 복원하되 확인하지 않은 성공을 주장하지 마세요.
