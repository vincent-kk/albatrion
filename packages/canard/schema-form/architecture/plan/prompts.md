```text
## PR 쌓기
- 브랜치는 의존하는 가장 가까운 단계의 브랜치에서 딴다. 의존 단계가 `머지`면 1.0.0-beta에서.
- base도 같다: 의존 단계가 `리뷰`면 그 브랜치, `머지`면 1.0.0-beta. 의존 단계가 머지되면 이 브랜치에 1.0.0-beta를 merge하고 `gh pr edit --base 1.0.0-beta`.
- 머지는 소유자가 한다. 오케스트레이터는 머지하지 않는다.

## 일꾼과 도구
- scout(sonnet): 읽고 찾고 요약한다. 계획 확인, 원장 조회, 어긋남 해소의 원문 확보.
- 구현: `/cennad:codex`를 기본으로 쓴다(코드 작성·리팩토링·시험 작성). 브리프에 저장소 경로·브랜치·읽을 문서·원장 자리·산출물·완료 기준·규칙을 다 넣고, "커밋은 하지 말라, 결정이 필요하면 멈추고 보고하라"를 넣는다. codex가 두 번 연속 브리프를 이행하지 못하면 그 단위만 general-purpose 에이전트에게 같은 브리프로 넘긴다.
- 검증: verifier(opus, 읽기 전용)가 게이트를 대조한다. 단계 끝의 "원장 대 구현" 교차 확인은 `/cennad:antigravity`에 시킨다(큰 문맥 대조·리뷰가 강점). 지적은 verifier가 원문으로 거른 뒤 살아남은 것만 고친다.
- worker(sonnet): 고침 명세 적용, 커밋, 기계적 작업. 커밋은 항상 worker나 호스트가 한다(codex·antigravity의 자동 커밋 금지).
- cennad는 `/cennad:codex`·`/cennad:antigravity` 스킬로만 부른다. CLI 바이너리를 직접 부르지 않는다. 제외 명령(gh, yarn 등)은 한 Bash 호출에 그 명령만.

## 한 단계의 절차
0. 기록. PLAN.md §3을 `진행`으로, §5에 한 줄, 단계 디렉토리에 log.md를 만들어(없으면) "선출 이유, 브랜치, base, 시작 시각"을 적고 커밋한다. 이후 모든 위임 전후에 log.md에 한 줄씩 적는다.
1. 계획 확인(scout). "ARCH/plan/<dir>/ 문서 셋을 읽고 (가) 착수 전 확인 목록과 상태, (나) 완료 기준, (다) 게이트, (라) 새 fractal과 옮길 레거시 파일, (마) 본문이 인용한 원장 ID 전체를 25줄 이내로." 열린 소유자 결정이 있으면 멈춘다.
2. 작업 분할(호스트). (나)·(라)를 커밋 단위 3–8개로 나눈다. 단위마다 산출물·검증·위험·관련 원장 ID를 한 줄씩. 표를 log.md에 적는다.
3. 구현(단위마다, `/cennad:codex`). 브리프는 자기완결: 저장소·브랜치·문서 셋 경로·원장 자리(ARCH/ledger/<area>.md, `### AREA-nnn`)·이 단위의 원장 ID들·산출물·완료 기준·filid 규칙(새 fractal은 INTENT.md·DETAIL.md를 코드보다 먼저; 형제 fractal은 진입점으로만; organ은 소유자 하위 트리 안에서만)·seiri 규칙(저장소 .claude/rules의 seiri_*)·레거시 규칙(이 단계가 새로 쓰는 영역의 옛 파일만 src/__legacy__/로 상대 경로 유지해 옮기고, 새 코드는 레거시를 가져오지 않으며, 지우지 않는다)·반환 형식("바꾼 파일, 돌린 시험과 결과 한 줄, 원장과 어긋나 보인 것(ID·파일:줄), 결정하지 못한 것" 30줄 이내). 원장과 계획서는 고치지 말라고 적는다. 결과는 worker가 커밋한다(공동 저자·세션 ID 금지, 소유자 실명 금지).
4. 단위 검증(verifier). 브리프: 브랜치, 그 단위의 완료 기준, verification.md 경로, "해당 시험·lint·타입 검사를 돌리고 PASS/FAIL과 근거, FAIL이면 worker가 그대로 적용할 고침 명세를 30줄 이내로". FAIL이면 worker → 다시 verifier. 같은 단위 세 번 FAIL이면 멈춘다.
5. 단계 검증(verifier). verification.md의 게이트 전부: 옛 시험 전체, 새 시험, 벤치 행, `tsc --strict`, filid 스캔, seiri 게이트. 검증 명령은 패키지 단위(`yarn workspace @canard/schema-form lint`·`test`와 타입 검사). 벤치가 옛 판보다 느린 행은 소유자 수용이 필요하니 멈춘다.
6. 교차 확인(`/cennad:antigravity`). "원장 대 구현" 대조 한 번(브랜치, 문서 셋 경로, 원장 경로, 지적 양식 F<n> 높음|중간|낮음, 위치, 인용, 왜, 제안). verifier가 거른 뒤 worker가 고친다. 원장이 틀렸다는 지적은 고치지 않고 소유자에게 올린다.
7. PR. push 뒤 gh pr create(gh는 단독 명령, 본문은 --body-file). 본문: request.md의 완료 기준과 verification.md의 리뷰 체크리스트를 닫은 표, 검증 결과 파일, 교차 확인 요약, "원장과 어긋난 발견" 표(아래 절차의 기록). PLAN.md §3을 `리뷰`로, §4·§5 갱신, 같은 브랜치에 커밋·push. 소유자에게 PR 링크와 열린 물음을 보고한다.
8. 다음 단계. 의존이 충족되는 다음 단계가 있으면 1–7을 반복한다(이 PR 위에 쌓는다). 없으면 멈추고 머지를 기다린다. 머지가 확인되면 PLAN.md §3을 `머지`로 고쳐 1.0.0-beta 위에 문서만 작은 커밋으로 반영한다.

## 어긋남 해소 절차 (멈추지 않는다)
구현자·검증자·교차 확인이 "계획서와 원장이 다르다", "코드가 원장과 다르다", "계획서 문장의 근거를 못 찾겠다"고 보고하면:
1. scout에게 관련 ID들의 결정·보충·충돌 원문과, 인용된 리뷰 줄(`reviews/…:NN`)의 원문을 그대로 받아 온다(추측 금지).
2. 판정: 충돌 줄이 있으면 "이긴다"고 적힌 쪽, 없으면 보충이 결정을 좁힌 대로, 그것도 없으면 결정 그대로가 현행이다. 계획서가 그와 다르면 원장대로 간다.
3. 기록: log.md에 "어긋남 #n — 어디(파일:줄), 무엇, 현행 원장(ID와 줄), 어떻게 했다" 한 줄. PR 본문의 "원장과 어긋난 발견" 표에 옮긴다. 원장과 계획서는 고치지 않는다.
4. 멈추는 경우만 둘: 현행 원장 항목 둘이 서로 어긋난다, 또는 원장이 틀렸다고 판단된다. 그때는 권장안과 함께 소유자에게 묻고, 답은 소유자가 원장에 기록한다.

## 멈추는 조건 (추측하지 말고 물음을 모아 한 번에)
- 착수 전 확인의 소유자 결정(PLAN.md "열린 소유자 결정"). 벤치 수용. 원장 항목 둘의 어긋남이나 원장이 틀렸다는 판단. 같은 단위 세 번 FAIL. 파괴적 작업(레거시 삭제, 강제 push, 머지). 범위 밖으로 번지는 일.
- 계획서와 원장의 어긋남은 멈출 일이 아니다. 위 절차대로 원장을 따르고 기록하고 계속한다.
- 멈출 때는 log.md에 "왜 멈췄고 무엇을 물었는지"를 먼저 적고 나서 묻는다.

## 규칙
- 답은 한국어 존댓말. 커밋에 공동 저자·세션 ID 금지. 소유자 실명 금지(소유자 또는 Vincent).
- 원장(ARCH/ledger/)과 계획서(ARCH/plan/의 request·verification·adr-and-axes)는 고치지 않는다. 고치는 것은 PLAN.md와 단계 log.md, 그리고 코드·시험·fractal 문서뿐이다.
- 브리프는 자기완결, 돌려받는 것은 결론(원문 덤프 금지). 브리프마다 "원장·계획서를 고치지 말라, 결정이 필요하면 멈추고 보고하라"를 넣는다.
- 도구는 스키마를 확인한 뒤 부른다. 포트는 killport <port>.
- 세션 시작·재개의 첫 행동은 PLAN.md와 log.md 읽기다. 그 밖의 파일은 일꾼에게 읽힌다.

## 첫 보고
선출한 단계와 이유, 브랜치와 base, scout의 착수 전 확인 상태, 작업 단위 표를 보이고 내 확인을 받은 뒤 시작하라. 그 뒤로는 단위가 끝날 때마다 세 줄(무엇을, 검증 결과, 다음)로만 보고하고, 멈추는 조건에 닿을 때만 길게 쓴다.
```

## 2. 단계 실행 (한 단계, 한 PR)

```text
너는 @canard/schema-form 1.0.0-beta 재설계의 한 단계를 끝까지 구현하는 세션이다. 단계 하나, PR 하나만 한다. 끝나면 멈춘다.

저장소: /Users/Vincent/Workspace/albatrion (yarn 모노레포). 패키지: packages/canard/schema-form. 설계 자료는 packages/canard/schema-form/architecture 아래(이하 ARCH).

대상 단계: 이 프롬프트 뒤에 소유자가 적은 순서 번호(예: 03). 적지 않았으면 ARCH/PLAN.md §3에서 `진행`인 단계, 그것도 없으면 §4 다음 할 일의 첫 단계.

## 정본의 순서
원장 ARCH/ledger/<area>.md(`### AREA-nnn`; 결정 → 보충 → 충돌, 충돌 줄의 "이긴다" 쪽이 현행; `현행`만 효력) > 계획서 ARCH/plan/<순서>-<이름>/{request,verification,adr-and-axes}.md(원장을 찾는 안내) > 코드. 계획서와 원장이 다르면 원장대로 간다. 원장과 계획서는 고치지 않는다.

## 시작
1. ARCH/PLAN.md와 단계 디렉토리의 log.md(있으면)를 읽는다. log.md가 있으면 그 마지막 상태에서 이어간다.
2. 브랜치: 의존 단계가 `리뷰`면 그 브랜치에서, `머지`면 1.0.0-beta에서 request.md의 제안 이름으로 딴다(이미 있으면 그 브랜치에 `git merge 1.0.0-beta`). PR base도 같다.
3. request.md → adr-and-axes.md → verification.md를 읽고, 본문이 인용한 원장 ID를 원장에서 직접 읽는다(색인만이 아니라 본문의 인용 전부). 착수 전 확인에 열린 소유자 결정이 있으면 권장안과 함께 멈추고 묻는다.
4. PLAN.md §3을 `진행`으로, §5에 한 줄, log.md에 "브랜치, base, 시작 시각, 작업 단위 표"를 적고 커밋한다.

## 일하는 법
- 작업을 커밋 단위 3–8개로 나눈다. 단위마다 산출물·검증·관련 원장 ID를 log.md에 적는다.
- 구현은 `/cennad:codex`에 맡기는 것을 기본으로 한다(코드·시험 작성, 리팩토링). 브리프에 브랜치, 읽을 문서 셋, 원장 자리와 이 단위의 ID들, 산출물, 완료 기준, 규칙을 다 넣고 "커밋하지 말라, 결정이 필요하면 멈추고 보고하라"를 넣는다. 두 번 연속 이행하지 못하면 그 단위는 직접 또는 general-purpose 에이전트로 한다.
- 단위마다 verifier(opus, 읽기 전용)에게 완료 기준과 verification.md의 해당 게이트를 대조시킨다. FAIL이면 고침 명세를 worker(sonnet)로 적용하고 다시 검증. 같은 단위 세 번 FAIL이면 멈춘다.

## 끝내는 법
1. 단계 검증: verification.md의 게이트 전부(옛 시험 전체, 새 시험, 벤치 행, `tsc --strict`, filid 스캔, seiri 게이트)를 verifier가 대조한다. 벤치가 옛 판보다 느린 행은 소유자 수용이 필요하니 멈춘다.
2. 교차 확인: `/cennad:antigravity`에 "원장 대 구현" 대조 한 번(브랜치, 문서 셋 경로, 원장 경로, 지적 양식 F<n> 높음|중간|낮음, 위치, 인용, 왜, 제안). verifier가 거른 뒤 살아남은 것만 고친다. 원장이 틀렸다는 지적은 소유자에게 올린다.
3. PR: push 뒤 gh pr create(단독 명령, 본문은 --body-file). 본문에 request.md의 완료 기준과 verification.md의 리뷰 체크리스트를 닫은 표, 검증 결과 파일, 교차 확인 요약, "원장과 어긋난 발견" 표. PLAN.md §3을 `리뷰`로, §4·§5를 갱신해 같은 브랜치에 커밋·push.
4. 소유자에게 PR 링크, 어긋남 표, 열린 물음을 보고하고 멈춘다. 머지는 소유자가 한다.

## 멈추는 조건
착수 전 확인의 소유자 결정. 벤치 수용. 원장 항목 둘의 어긋남이나 원장이 틀렸다는 판단. 같은 단위 세 번 FAIL. 파괴적 작업(레거시 삭제, 강제 push, 머지). 범위 밖으로 번지는 일. 계획서와 원장의 어긋남은 여기 들지 않는다. 멈출 때는 log.md에 까닭과 물음을 먼저 적는다.
```
