# 76라운드 — Vincent의 답 (새 단계 "정돈": 08 플러그인 뒤, 성능 최적화 앞에 소유자가 코드를 직접 보며 파일 구성·함수 이름·함수 로직을 손질한다)

2026-10-03. 소유자가 07 전환의 구현 코드를 훑어보며 "코드 동작엔 이상이 없으나 … 내가 짤만한 로직 구성이나 네이밍이나 파일 구성이 아닌 것 같다"고 했고, 그 손질을 성능 개선 전에 해야 하는지, 플러그인 개편과 성능 개선 사이에 두면 되는지 물었다. 원장 관리자는 성능 작업이 특정 파일·함수에 붙으므로 정돈이 앞서야 하고, 정돈이 공개 겉면(이름·형·훅)에 닿지 않으면 08 뒤·성능 개선 앞이 맞으며, 원장이 이름을 박아 둔 것(fractal 이름, 공개 API 이름, 사건 이름)을 바꾸는 결정은 소유자 라운드로 적어야 한다고 답했다. 소유자가 아래 답을 직접 주었다.

| 확인 | 물음(요지) | 답(원문) | 반영 |
| --- | --- | --- | --- |
| 정돈 단계의 신설과 자리 | 코드 정돈을 하나의 단계로 두고 08 플러그인 뒤·성능 최적화 앞에 놓으며, 그 범위는 공개 겉면이 아니라 내부(파일 구성·함수 이름·함수 로직)인가 | "그렇게 하자. 지금은 안할거고, 그 단계에서 내가 집중적으로 코드를 보면서 진행할게. 일단 단계만 구분해두렴. 큰 틀이나 인터페이스를 바꿀거같진 않고, 파일 구성이나 함수 이름, 함수 로직 등을 손댈거같아." (2026-10-03, 원장 세션) | 확정. (1) 새 단계 "정돈"을 둔다: 순서는 07 전환 → 08 플러그인 → 정돈 → 성능 최적화 → 09 정리·릴리스. 성능 최적화는 "08과 병렬"이 아니라 정돈 뒤에 시작한다(27라운드 소유자 답 "구현 완료 뒤 별도 작업"의 "구현 완료"에 정돈이 든다). (2) 범위는 내부다 — 파일 구성, 함수 이름, 함수 로직. 큰 틀(fractal의 경계와 의존 방향, LANDING-084)과 공개 인터페이스(SURFACE 영역, 공개 훅·형·사건 이름)는 바꾸지 않는다. 바꾸고 싶은 공개 겉면 항목이 나오면 그것만 따로 모아 08 앞에 처리한다. (3) 진행 방식은 소유자가 코드를 직접 보며 원칙(이름 규칙·파일 배치 규칙·로직 구성 규칙)을 정하고, 원장 관리자가 그것을 소유자 라운드로 먼저 적은 뒤 작업 세션이 코드 전체에 한 번에 적용한다. 동작 불변은 차등 시험(정착 결과·개정 대장·방출 값)과 기존 렌더·코어 스위트, 벤치 수치가 오차 안임으로 보인다. DETAIL·INTENT는 코드보다 먼저 고친다. (4) 지금은 착수하지 않는다 — 07·08이 끝난 뒤다. 03 코드의 열린 행 P-24·P-25는 성능 작업으로 넘어가기 전에 정돈이 그 파일을 만지므로 정돈에서 함께 처리할 수 있다 |

이 답으로 PLAN의 진행 표에 "정돈" 행이 들어가고 "최적화" 행의 "08과 병렬"은 "정돈 뒤"로 바뀐다. 계획서 디렉토리(`plan/<순서>-tidy/` 등)와 착수 문서는 그 단계가 열릴 때 쓴다. 다음 라운드 번호는 77이다.
