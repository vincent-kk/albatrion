목적: 소유자가 D-1–D-10을 판단하는 데 필요한 **이해·배경지식·장단점·제안·반론**을 항목마다 같은 틀로 모은다. 권고를 내지 않는다. D-7–D-10은 이미 결정됐으므로(`round-4.md` §4) 그 항목은 "결정의 귀결과 미정 세부"로 쓴다.

## D-1. 부모가 null이 되면 자식 원본을 어떻게 하는가

**이해.** nullable 객체(예: `shipping`)에 `null`을 쓰면 그 아래 자식(`address`, `memo`)의 편집 값을 지울 것인가, 숨겨 둘 것인가. 이슈 #338은 "지운다(빈 상태로 되돌린다)"로 정했고, 3라운드는 이를 폐기하려다 4라운드에서 "유지"로 기울었다. 부딪히는 자리는 둘이다. 사용자가 null을 잠깐 껐다 켰을 때 값이 돌아오길 바라는 경우와, 레코드 A를 보던 폼에 null인 레코드 B를 로드하는 경우다.

**배경.** JSON Schema는 `null`과 "속성 없음"을 구별하지만(core §4.2.1), null이 된 객체 아래의 UI 상태에 대해서는 침묵한다. 다른 라이브러리가 null 왕복에서 자식을 재초기화한다는 배경 조사의 주장은 **1차 출처에서 확인되지 않았다**(scout).

**시나리오 (소비자).** CRUD에서 A → B 전환. 유지안: `setValue(B)` 한 줄이면 화면이 빈 주소·B의 메모가 되고 부산을 입력하면 `{address: '부산', memo: B의 것}`이 저장된다. 폐기안: 리마운트 규율이 없으면 A의 서울·경비실 메모가 B의 화면에 남고, 부산만 고쳐도 A의 메모가 B로 저장된다(claude 실행, 3라운드 교차검증). 루트를 통째로 `Overwrite`해도 중첩 null에서는 막히지 않는다.

**장단점.**

| 옵션 | 개발자 | 사용자 | 구현·되돌림 (codex) |
| ---- | ------ | ------ | ------------------- |
| 유지 — null은 키 없는 전체 교체, 빈 상태는 로드 계약의 default | 한 줄로 안전. 특수 장치 없이 규칙 둘로 도출 | 실수로 null을 누르면 편집 값을 잃는다 | 중. 기존 blank 계약 테스트 0개 변경. 되돌림 높음(삭제한 raw는 복구 불가) |
| 폐기 — null 아래 원본을 남긴다 | 값이 돌아온다. 그러나 레코드 전환에 리마운트 규율이 필요하고 잊어도 에러가 없다 | 다른 레코드의 값이 새어 나올 수 있다 | 중. 테스트 ≥14개 뒤집힘(`ObjectNode.branch.nullable.blankState.test.ts:101`, `nullable.object-blank-state.render.test.tsx:31`). 측정: null 쓰기가 유지안 110 µs(자식 600개 default 주입) 대 폐기안 1.3 µs |

**제안 (결정이 아님).**
- 출처 기반 혼합: 사용자의 입력(자기 노드)에서 온 null은 잠복을 유지하고 `latent(path)`로 열람 가능하게, 호출자의 전체 교체에서 온 null은 지운다(F7·F26의 연장, claude).
- "되돌릴 수 있는 null 토글"을 입력 컴포넌트의 표준 예제로 제공 — 되돌리기는 자기가 토글임을 아는 컴포넌트의 몫.
- 문서 한 줄: "null은 '이 객체는 없다'는 명령이다. 숨기려면 `&active`를 쓴다."
- 제3안(devil `raw-round5-devil.md:13`): null은 전체 교체이되 **null 호스트 아래에서는 로드 계약이 일어나지 않고 자식이 존재하지 않는다** — 빈 양식은 객체로 돌아올 때 만든다. D-5 스위치와의 얽힘(§11 C-3)이 사라지는 대신 null인 동안 자식 입력이 그려지지 않는다.

**열린 질문.** `setValue(undefined)`의 정의는? 비nullable 객체에 null이 오면 `{}`로 볼 것인가 type 에러인가(4라운드 F1은 후자)? "복원"을 원하는 실제 사용자 요구가 있는가(#338에는 없다)?

**반론 (devil).** "빈 양식"은 D-1의 계약이 아니라 default 주입의 부산물이다 — `disableDefaultInjection`을 켜면 null 뒤 타이핑이 `{note:'again'}`이 되어 #338 셋째 단언이 사라진다(**실행** X3c). 24개 실패 테스트는 `minItems` 채우기 등 현재 blank의 다른 의미도 고정하므로 ADR 0013(core는 값을 고치지 않는다) 아래에서는 "유지"도 일부 깨진다(인용, codex). null 토글의 복원 책임이 플러그인마다 복제된다(추론). **§11 C-2·C-3 참조.**

## D-2. 조각 활성 계산 — 비단조 + 상한인가

**이해.** 조건부 섹션들이 서로의 조건을 바꿀 때, 한 번 켠 조각을 다시 평가해 끌 것인가(비단조), 켜진 것은 그대로 둘 것인가(단조). 4라운드는 비단조 + 상한(조각 수 + 1) + 정착 상태 칸을 권고했다. 부딪히는 자리는 부정 가드(`if not required x`)가 있는 단계와, 서버가 준 자기 모순 스키마다.

**배경.** 명세는 `if/then/else`·`not`·`dependentRequired`·`unevaluatedProperties`를 규정하지만 UI가 조각을 켜고 끄는 순환은 규정하지 않는다. 다른 라이브러리: RJSF·JSON Forms는 단일 패스, Formily·ngx-formly는 반복 상한이 있다(배경 조사 — 미대조).

**시나리오 (소비자).** 목록 편집기에 서버가 자기 부정 스키마를 보낸 경우. 비단조: 상한에서 멈추고 결과가 상한의 홀짝에 달린다(cap 2면 `{}` invalid, 3이면 `{x:1}` valid — 3라운드 교차검증의 claude 실행 `raw-crosscheck-decisions-claude.md:230`. 5라운드 devil X1의 실제 출력은 cap 2에서 `emit=undefined`). `{}`이면 필수 에러가 뜨는데 칸이 없어 제출 불가. 단조: 루프 없이 `{x:1}` valid.

**장단점.**

| 옵션 | 개발자 | 사용자 | 구현·되돌림 |
| ---- | ------ | ------ | ----------- |
| B 비단조 + 상한 | 검증기 판정과 일치. 새 표면(`settle`, 진단) 학습 필요 | 현실적인 부정 가드 조합이 맞는 형상에 닿는다 | 높. 측정: 가드 200개에서 A와 차이 없음(1,065 대 1,069 µs). 되돌림 중간 |
| A 단조 | 종료가 구조로 보장. 부정 가드 금지 규칙이 필요하고 서버 스키마엔 강제 불가 | then과 else가 동시에 켜지는 스키마에서 검증기와 어긋남 | 중. 되돌림 중간 |

이주: 오늘은 `then.properties`와 `not`을 읽지 않으므로(`flattenConditions.ts:44-61`) 어느 쪽이든 새 조건 필드가 등장한다.

**제안.** 청사진 단계의 정적 검사(가드 의존 그래프에 부정을 포함한 순환이 있으면 경고). 공개 모양 후보 `getSettleStatus()` / `onDiagnostic` / `UpdateSettle` 이벤트 — `onValidate`와 분리 명시. 상한 초과 시 단조 규칙을 한 번 더 적용해 고정하는 완화책(claude 4라운드 추론, 미실행). 제3안(devil `:34`): 상한 초과를 "결과"가 아니라 **차단 실패**로 다루고(커밋하지 않고 이전 커밋 유지 + 에러), 지원 범위 밖을 부정 순환만이 아니라 자기 참조 전부로 넓힌다.

**열린 질문.** `budget-exceeded` 상태에서 제출을 막는가, 알리기만 하는가? 진단의 청중은 개발자(수집기)인가 최종 사용자(배너)인가? 지원 범위 밖 스키마를 서버 팀에 알리는 경로는?

**반론 (devil).** 무관한 항상 켜진 조각 하나를 추가하면 자기 부정 조각의 방출이 `{}` → `{x:1}`로 뒤집힌다 — 상한 = 조각 수 + 1의 홀짝 때문(**실행** X1). 양의 자기 참조(`if required a then properties a`)는 지원 범위 안이면서 로드한 `a`를 방출에서 조용히 떨어뜨리고 `status = stable`이다 — 관측 수단이 울리지 않는 손실(**실행** X4).

## D-3. 금지 조각(`properties: {x: false}`, `not: {required: ['x']}`)

**이해.** 서버 스키마가 어떤 조건에서 필드를 금지할 때 폼이 (i) 숨기고 방출에서 뺄 것인가, (ii) 칸을 보이고 에러를 붙일 것인가, (iii) 아예 읽지 않고 검증기에 맡길 것인가(숨기려면 작성자가 `&active`로 명시). 4라운드 권고는 (iii)이며, 2라운드의 소유자 발언("값 조작은 알아야 값을 처리할 수 있다")과 반대 방향이다.

**배경.** 명세: `false` 서브스키마는 "항상 실패, `{not:{}}`와 같다"(core §4.3.2). 숨김·자동 삭제는 규정하지 않는다. "네 라이브러리 모두 에러로만 표시하고 자동 삭제하지 않는다"는 배경 조사의 주장은 **문서에서 확인되지 않았다**(scout).

**시나리오 (소비자).** 규칙을 어긴 옛 레코드를 CRUD에서 무편집 저장. (i): 조용히 `cardNo`를 삭제하고 유효해진다. 배타 쌍이면 두 값이 모두 사라지고 두 칸이 숨어 풀 수 없다(claude 실행, 3라운드). (ii)/(iii): 에러로 막히고 비우면 통과.

**장단점.**

| 옵션 | 개발자 | 사용자 | 구현·되돌림 |
| ---- | ------ | ------ | ----------- |
| (i) 비활성화와 같다 | 서버 스키마 그대로 숨김이 된다 | 값이 조용히 사라진다. 배타 쌍에서 교착 | 높. 되돌림 높음 |
| (ii) 보이고 에러 | 값을 고치지 않는다 | 고칠 수 없는 칸에 에러 | 높. 되돌림 높음 |
| (iii) 검증기에만 | core에 새 개념이 없다. 문구 매핑 없으면 원문 에러가 보인다 | 오늘과 같다(오늘도 then 안 금지는 읽지 않음). 단 최상위 `x:false`는 오늘 생성 시 throw(`schemaNodeFactory.ts:116`)라 새 동작 | 중(잔여 키 API 포함). 되돌림 높음 |

**제안.** (ii)의 좁은 형태(devil `:63`): 금지된 키의 입력을 만들되 비활성·읽기 전용으로 보이고 키 삭제 동작만 준다 — 고칠 수 없는 에러가 생기지 않는다. (iii) + 표시 규칙(`not.required` 에러를 자식으로 옮기고 기본 문구 "이 조건에선 비워야 합니다"), `formatError` 기본 번역에 `false schema` 추가. (i)가 필요한 작성자를 위한 코드모드(`x:false` → `&active` 부착). (i)를 고른다면 로드 시 제거를 통지하는 안전장치.

**열린 질문.** 2라운드 발언 "필드가 가려지며 값이 빠진다"는 작성자의 `&active`만 뜻하는가, 표준 `false`도 포함하는가? 실무 백엔드 계약에서 `x:false`는 거부용인가 숨김용인가? 잔여 키 UI는 기본 렌더러가 제공하는가 앱이 구현하는가?

**반론 (devil).** 본체 선언 + `then x:false` 조합에서 문자열을 비워도 `''`는 "없음"이 아니라 `false` 스키마에 걸린다(ajv 6·8 **실행**: `{x:''}` invalid) — 선언된 필드에는 삭제 동작이 없어 "고칠 수 없는 에러"가 살아남는다. F8의 `instancePath` 규칙은 `additionalProperties` 에러(`instancePath ""`, 키는 `params`에만)를 담지 못해 core가 ajv 고유 출력을 해석해야 한다(**실행**). **§11 C-4 참조.**

## D-4. 쓰기의 종류 — Overwrite(기본)·Merge, Refresh는 core 판단

**이해.** 객체를 쓸 때 말하지 않은 키를 지울 것인가(전체 교체) 지킬 것인가(부분 쓰기), 그리고 비제어 입력의 재읽기(리마운트) 시점을 호출자가 고를 것인가 core가 규칙으로 정할 것인가. 4라운드 권고: 공개 옵션은 `Overwrite`(기본)·`Merge` 둘, `Refresh`는 core가 출처로 판단(F7).

**배경.** 명세는 런타임 쓰기 방식에 완전히 침묵한다. Formily는 `setValues(values, strategy)`에 `'overwrite' | 'merge' | 'deepMerge' | 'shallowMerge'`를 두고 기본은 `'merge'`이며(scout 확정), Angular는 `setValue`(전체 구조 강제)와 `patchValue`(있는 것만)를 나눈다(확정).

**시나리오 (소비자).** JSON 편집기가 `port` 줄을 지운 객체를 통째로 돌려준다. Overwrite 기본: `port`가 없음이 되는데, 로드 주입(i)이 적용되면 `port: 80`이 즉시 복원돼 삭제가 불가능하다. Refresh를 호출자가 고르는 안: 비트를 빠뜨리면 캐럿·undo가 사라진다. Merge 기본: `Overwrite`를 명시하지 않으면 지운 키가 `8080`으로 복원된다.

**장단점.**

| 옵션 | 개발자 | 사용자 | 구현·되돌림 |
| ---- | ------ | ------ | ----------- |
| Overwrite 기본 + Merge | 오늘의 공개 표면과 같다(`value.ts:69-74`). Merge 누락이 흔한 실수(조용한 손실) | 재읽기를 신경 쓰지 않아도 된다 | 중. 테스트 ≥7(`RefreshAndDefaultValue.test.ts:58, 221`). 측정: Overwrite 37.9 µs(601 방문) 대 Merge 6.4 µs(2 방문). 되돌림 중간 |
| Merge 기본 | 부분 패치가 짧다 | 기본값 반전은 조용한 동작 변화 — 모든 `setValue(record)` 호출 점검 필요 | 중. 되돌림 중간 |
| 기존 10비트 유지 | 내부 사정이 공개 API에 남는다 | — | 높. 되돌림 높음 |

**제안.** 입력 계약 문서화(입력의 `onChange(v)`는 그 노드에 대한 Overwrite, 패치 입력은 Merge 명시). 개발 모드 경고(루트 Overwrite가 dirty 필드를 지울 때). README에 "어떤 쓰기가 무엇을 지우나" 표.

**열린 질문.** 입력의 객체 전체 쓰기는 "로드"인가(주입 (i)가 붙는가 — A2와 F25가 상충)? F7의 "자기 입력의 부분 쓰기"에 객체 전체 교체도 포함되는가? Merge는 깊은 병합인가(`BranchStrategy.ts:273-274`, 미실행)? 배열의 Merge ≡ Overwrite를 문서화하는가?

**반론 (devil).** `setValue(getValue())`가 항등이 아닌데 그 모드가 기본이다 — 제3안 "기본값 없음(mode 필수)"(**실행** X3a, 인용 claude `:352`·antigravity `:210`). **§11 C-6 참조.**

## D-5. 로드 시 default 주입을 끄는 스위치

**이해.** 폼이 값을 받을 때(생성·`reset`·`setValue`) V에 없는 키에 스키마 `default`를 채울 것인가, 이를 폼 단위로 끌 수 있는가. 소유자 방향: 뜻은 "초기값 조작 비활성화", 이름은 `disable…` 형태. 범위는 미정.

**배경.** 명세: `default`는 **어노테이션**이며 검증기가 적용하지 않는다(validation §9.2 — 배경 조사의 "§7.6.1"은 오류). JSON Forms는 기본 미주입(`createAjv`에 `useDefaults` 없음 — scout 확정), RJSF는 기본 주입이고 `experimental_defaultFormStateBehavior`(emptyObjectFields·arrayMinItems·mergeDefaultsIntoFormData·constAsDefaults 등)로 제어(확정).

**시나리오 (소비자).** 서버가 일부러 비운 `status`를 편집. 스위치 켬: 빈칸, 저장에 `status`가 없어 서버 계산값 보존. 스위치 끔(기본): `'draft'`가 채워지고 무편집 저장이 서버 값을 덮는다. **오늘의 `setValue` 경로는 주입하지 않으므로**(`current-null.ts:25-26`, claude) 새 계약은 기존 `setValue` 호출 전부의 동작 변화다 — round-3 요약이 말한 것보다 이주 범위가 크다.

**장단점.**

| 옵션 | 개발자 | 사용자 | 구현·되돌림 |
| ---- | ------ | ------ | ----------- |
| 기본 주입 + 끄는 Form 속성 | 속성 하나로 왕복 보존. 새 폼은 `defaultValue`를 주지 않는 규율 필요 | 새 폼에 기본값이 보인다 | 중. 생성·reset은 오늘과 같음(`getChildNodeMap.ts:69-70`, `Form.tsx:94,151`). 측정: 켬 138 µs / 끔 36 µs(default 리프 600개, 방문 1,202 → 601). 되돌림 중간 |
| 로드는 기본 미주입 | 편집 폼이 무조작 보존 | 새 폼의 기본값이 prop 유무에 따라 반전 | 중. 테스트 ≥8(`default-value.render.test.tsx:226`). 되돌림 중간 |

**제안.** 이름 후보 `disableDefaultInjection`(현), `disableLoadDefaults`, `disableDefaultsOnLoad`, `disableDefaultFill` — D-7 수정자와 어근 통일. 제3안(devil `:109`): Form 속성을 두지 않고 **호출 단위 옵션 하나를 양방향으로**(켜기·끄기) 둔다 — 두 스위치의 우선순위 문제(§11 C-5)가 사라진다. README에 "새 폼"·"편집 폼" 두 레시피. 빈 `defaultValue`에 개발 모드 경고.

**열린 질문.** 스위치를 켠 폼에서 특정 호출만 default를 받는 반대 방향 수정자가 필요한가? `push()`로 만든 새 아이템은 로드인가? V에 없는 중첩 호스트가 자식 default로 객체를 방출하는가(4라운드 §3.4 미확인)? `required` + `default` 필드가 빈 채 로드되면 에러 시점은?

**반론 (devil).** 호출 단위 옵션이 억제 방향뿐이라 속성을 켠 앱은 "새 레코드"에 default를 넣을 수단이 없다. 프로토타입은 `replacedHosts`가 있는 정착만 억제하므로(`loop-v4.mjs:1136`) 로드 직후 리스너 쓰기의 다음 정착에서 default가 들어온다(추론, codex 동일 우려). **§11 C-5 참조.**

## D-6. `virtual`의 자리

**이해.** `startDate`·`endDate`를 입력 하나로 묶는 `virtual`을 (a) `&virtual`로 옮기고 core에 값 없는 "참조 그룹" 노드 종류를 둘 것인가, (b) core에서 빼서 렌더 계층 바인딩으로 옮길 것인가, (c) 현행 유지(표준 `required`를 고쳐 쓰는 전처리 포함). 4라운드 권고는 (a). 최종 사용자의 화면은 세 안이 같고 개발자의 스키마·API만 다르다.

**배경.** `virtual`은 비표준이며 `required`에 가상 이름을 넣으면 표준 검증이 실패한다. RJSF `ui:field`, JSON Forms Layout/Group, Formily `VoidField`는 모두 데이터를 소유하지 않는 그룹을 둔다(배경 조사 — 미대조이나 널리 알려진 사실).

**시나리오 (소비자).** 서버 아이템 스키마에 FE가 묶음을 얹는 목록 편집기. (a)(b): 서버의 표준 `required`는 그대로, FE는 `&virtual`만 추가. (c): 묶음을 필수로 하려면 서버 `required`를 가상 이름으로 바꿔 서버 스키마와 갈라진다(ADR 0012 오버레이 없음).

**장단점.**

| 옵션 | 개발자 | 구현·되돌림 |
| ---- | ------ | ----------- |
| (a) `&virtual` + 참조 그룹 | 문법 교체뿐(`virtual` → `&virtual`), 묶음 API 유지. 새 노드 종류 필요 | 높. 테스트 ≥59(4파일 47 중 virtual 없는 2를 뺀 45 + 타 파일 6 + `flattenConditions` 8). 되돌림 높음 |
| (b) 렌더 계층 | core 단순화. 렌더러마다 9책임 재구현, 기존 계약(`find`, 부채질, Refresh) 깨짐 | 높. ≥59. 되돌림 높음 |
| (c) 현행 | 비용 0. ADR 0001 위반 영구 | 중. 되돌림 높음 |

**제안.** `required`의 묶음 이름 → 구성 필드 코드모드(C8). `required`에 `&virtual` 이름이 남으면 개발 모드 경고. `findNode('/period/startDate')` 별칭 경로 여부 명시. 묶음 `onChange` 길이 불일치 에러 문구.

**열린 질문.** 묶음의 `&active`를 구성 필드에 병합하는 오늘 동작을 유지하는가? `oneOf` 분기 안 묶음을 지원하는가(오늘도 노드가 안 생김)? 튜플 value의 참조는 언제 바뀌는가(리렌더 횟수)?

**반론 (devil).** 참조 그룹 노드는 P5(core는 렌더러를 모른다)의 반대편에 있는 렌더러 편의이며 하위 결정 5개를 core에 새로 요구한다. codex의 "(b)가 반드시 코드 중복을 강제하지는 않는다"(`raw-crosscheck-decisions-codex.md:221-223`)가 권고 표에서 빠졌다. 보존 테스트 16개 중 12개는 렌더 테스트라 (b)에서도 산다(인용·추론).

## D-7. `setValue(getValue())`의 멱등성 — 결정됨: (a) + 호출 단위 억제 수정자

**결정의 귀결.** 새 계약에서 `setValue(V)`는 로드이므로 지운 값에 default가 다시 채워진다. 오늘은 멱등이었다. 소유자는 "값을 씌우는 것"과 "기본값을 설정하는 것"이 다르다고 보고 호출 단위 수정자를 두기로 했다.

**시나리오.** 상태를 비우고 저장한 뒤 서버 응답 `{id, title}`로 `setValue(saved)`: 수정자 없음 → `'draft'` 복원, 다음 저장에 `status:'draft'`가 서버로 간다. 수정자 있음 → 빈칸 유지.

**이주.** 오늘 `setValue`는 주입하지 않으므로 기존 호출 전부가 새로 주입한다. 전수 점검이 필요하다("오늘의 `setValue(v)` = `setValue(v, Overwrite | 억제)`"). 측정: 스냅숏 비교 방식(b)은 185 µs 대 138 µs로 46 µs 추가.

**API 후보 (codex 스케치, 미확정).** `setValue(value, { mode?: 'Overwrite' | 'Merge'; disableDefaultInjection?: boolean })`. 이름 후보: 비트(`NoDefaults` / `SkipDefaults` / `DisableDefaultInjection`) 대 프리셋(`Restore` / `Hydrate` / `Sync`) 대 옵션 객체 `{ defaults: false }`. 재생성 마법사 레시피 `disableDefaultInjection={step > 1}`. 비멱등 감지 개발 모드 경고.

**미정 세부.** `Merge | 억제`의 뜻(전이 주입도 막는가 — F25는 전체 교체 정착으로 한정)? `reset()`에도 수정자가 필요한가(인자 없음, `type.ts:115`)? 입력의 `onChange(value, option)`이 수정자를 받는가? 타입 수준에서 무의미한 조합을 막는가?

**반론.** 억제는 로드·전이만 막고 이후 `injectTo`/derived 정착은 막지 않는다(devil). **§11 C-2·C-5·C-6.**

## D-8. 원본 없는 union의 판별 default — 결정됨: 암묵 default 없음

**결정의 귀결.** 판별 union 값이 비고 판별 프로퍼티에 명시 `default`가 없으면 분기를 고르지 않는다. 오늘과 같다(`ComputedPropertiesManager.ts:106`, `BranchStrategy.ts:735-739`). 판별 필드만 보이고 분기 필드는 고른 뒤 나타난다. 이 조합을 고정하는 테스트는 오늘 없으므로 신규 추가 대상.

**배경.** 명세: `oneOf`는 빈 객체를 전 분기 무효로 판정하고 기본 분기 규칙은 없다. RJSF는 매칭이 없으면 인덱스 0으로 폴백(`getFirstMatchingOption.ts` `return 0` — scout 확정), JSON Forms의 무선택은 소스를 찾지 못했다(미확인).

**시나리오.** 마법사 2단계 결제: 미리 고르려면 판별 프로퍼티에 `default: 'card'`를 명시. 손대지 않고 넘기면 `kind` 없이 저장(오늘과 같다).

**제안.** 문서 예제 "기본 분기를 원하면 판별 프로퍼티에 `default`". 선택 UI의 빈 상태 문구. 분기를 고르기 전엔 `required` 에러 없음 명시.

**미정 세부.** 명시 default를 호스트의 `properties.kind.default`에 쓰는가, 분기 안 `kind.default`에 쓰는가, 둘 다면 우선순위는? 판별식 없는 선택 가드 union의 빈 값에서 선택 UI는 무엇을 보이는가(ADR 0010 미작성)? 판별 필드만 있는 상태의 필수 에러 시점은?

**반론.** 선택 가드 union이 빈 폼에서 통째로 비어 보인다(devil). **§11 C-1·C-7.**

## D-9. `RequestRemount` — 결정됨: 사용자 도구로 유지

**결정의 귀결.** 서드파티 입력이 값 변경에 반응하지 않을 때 앱이 서브트리를 명시적으로 리마운트하는 탈출구가 남는다. 그 서브트리의 포커스·캐럿·내부 상태는 잃는다. 이주 없음(공개 이벤트 그대로, ADR 0008의 "제거 후보" 문장만 삭제). 제거였다면 테스트 3개 변경(`refresh.uncontrolled-value.render.test.tsx:278`).

**배경.** 마운트 생명주기는 명세 밖. RJSF·JSON Forms는 자체 API 없이 React `key`에 의존(배경 조사).

**제안.** `FormHandle.remount(path)`를 `focus`/`select`와 대칭으로. Refresh/Remount 비교표(누가 부르나 / 무엇이 다시 마운트되나 / 무엇을 잃나). 리스너 안에서 부르면 다음 파동에 배달됨을 명시.

**미정 세부.** `RequestRemount`가 `FormChildrenRenderer.tsx:17-21`의 재렌더 마스크에 들어 있어 서브트리 명령이 루트 render-prop을 다시 돌리며, 배달 집합(B3-2)은 조상 통지를 답하지 않는다(devil `:161`). 가상화로 지연 마운트된 노드에 Remount가 오면 드러내는가(T-3은 Focus·Select만)? 서브트리의 dirty·touched를 초기화하는가(추론: 유지)? `batch` 안 Remount의 배달 시점은?

**반론.** Refresh는 core 전용·비공개이고 Remount만 공개라, 사용자 도구는 가장 무거운 것 하나뿐이다(인용 `event.ts:74-75, 94-95`). Remount는 T-2·T-15·T-21이 지키는 상태를 모두 버린다. **§11 C-11.**

## D-10. 루트 `onChange` — 결정됨: 최외곽 동기 진입당 1회

**결정의 귀결.** 오늘은 매크로태스크를 취소·재예약해 한 번 부른다(`afterMicrotask.ts:18-28`). 새 설계는 쓰기를 일으킨 가장 바깥 동기 호출(핸들러, `setValue` 1회, `batch(fn)` 1회)이 끝날 때 최종 emit으로 정확히 한 번 부른다. 연속 `setValue` 두 번은 오늘 1회 → 결정 2회(`batch`로 1회 가능, 오늘 `FormHandle`에는 `batch`가 없다). 검증 요청도 진입당 1회(F28).

**배경.** 이벤트 스케줄링은 UI 구현 상세. RJSF는 키 입력마다 동기 발화, Formily는 batch 1회 + 토큰 기반 경합 처리(배경 조사 — 미대조).

**시나리오.** 제목에 "hello" 입력: 오늘 5회(핸들러 뒤 태스크), 결정 5회(각 핸들러 안에서 동기, tearing 0 — 4라운드 실행).

**API 후보.** `onChange?: (value, meta?: { commit, cause: 'mount' | 'input' | 'setValue' | 'reset' | 'array' })`(선택 인자라 기존 소비자 안 깨짐), `FormHandle.batch(fn)` 공개 + README 디바운스 레시피, `onListenerError?`. README의 `onChange` 타입 불일치 정리(`README.md:70` 대 `type.ts:52`).

**미정 세부.** 마운트 시 `onChange`를 부르는가(오늘은 준비 시 1회, `Form.tsx:135-139`)? `onChange` 안의 쓰기는 같은 진입에 합쳐지는가 새 진입인가(제어형 패턴의 수렴)? 값이 같고 참조만 새 커밋도 부르는가? `onChange`가 throw하면 `onListenerError`와 같은 통로인가?

**반론.** 배치 없는 `setValue` 3회 → `onChange` 3회·검증 요청 3회(오늘 1회, **실행** X5). (c)는 스파이크에 없다 — 프로토타입은 파동마다 부르고(`loop-v4.mjs:1217`) 리스너 되먹임에서 `onChange = 2`. 4라운드의 "tearing 0"은 F22(파동마다)의 증거이지 (c)의 증거가 아니다. 레이아웃 이펙트의 쓰기는 새 진입이므로 "한 수정에 한 번"이 "한 틱에 여러 번"이 된다(추론). **§11 C-8·C-9·C-10.**

## 12. 이 라운드가 고친 기록의 오류

- 배경 조사의 `default` 스펙 절 번호: §7.6.1이 아니라 validation §9.2.
- "다른 라이브러리가 null 왕복에서 자식을 재초기화한다", "네 라이브러리가 금지 조각을 에러로만 보인다"는 1차 출처에서 확인되지 않았으므로 근거로 쓰지 않는다.
- codex의 비용 표에서 "0*"(구별하는 기존 단언 없음)는 근거 파일(`round5/evidence.json`)에 항목이 없는 자체 판단이다(D-2·D-3·D-7·D-8).
- `round-4.md:113`은 D-7(b)를 "멱등"이라 적었으나 조건식과 맞지 않는다 — codex가 `semantics.mjs`로 반례를 확인했다(`{keep:1}` → `{keep:1, x:'D'}`, `raw-round5-cost.md:145`). `04-inherited-constraints.md`의 T-6·T-9에도 같은 부류의 잔존 문장이 있다(`:57`).
- 옵션과 무관한 공통 이주 비용: `flushOnMount: false`를 직접 쓰는 테스트 **26개(13파일)** 의 이관(`raw-round5-cost.md:11`). 어느 결정을 골라도 든다.
- 소비자 검토가 정정한 두 가지: `Form.reset()`은 "생성 시 V"가 아니라 현재 prop을 다시 읽는다(`Form.tsx:84-94, 151, 186`). "오늘도 없는 키에만 default"는 생성 경로에만 맞고 `setValue` 경로는 오늘 default를 넣지 않는다 — D-5·D-7의 이주 비용을 키운다.
