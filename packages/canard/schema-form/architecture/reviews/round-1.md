# 적대적 검토 1라운드

대상: 이 디렉터리의 ADR 0001–0011(2026-09-21 시점의 초안). 소유자의 지시 — "폭넓은 사례 조사와 여러 에이전트를 사용한 상호 공격으로 가장 깔끔한 아키텍처를 구성한다. 값이 바뀔 때마다 validator가 n번 호출되는 것이 걱정이다."

이 문서는 지적을 **검증한 뒤의 판정**을 기록한다. 리뷰어의 글은 증거이지 지시가 아니다.

## 2. 측정 — "값이 바뀔 때마다 validator가 n번 호출된다"

환경: Apple M1 Max, Node v24.20.0, ajv 8.17.1(`ajv/dist/2020`, `allErrors:false`, `$async` 없음), @cfworker/json-schema 4.1.1(`shortCircuit: true`). React·정착·전체 검증은 포함하지 않은 순수 호출 비용이다. 데스크톱 수치이며 모바일은 재지 않았다.

방법: 보정된 내부 배치(약 25 ms)를 재서 나누고, 2초 이상 데운 뒤 11회의 중앙값을 썼다(편차는 대부분 5% 미만). 이 측정을 되풀이할 때 지켜야 할 것 셋 — (1) **입력을 돌려 가며 넣는다.** 같은 인자를 반복하면 V8이 AJV 가드 호출을 루프 밖으로 빼내 0.7 ns가 나온다. (2) 결과를 체크섬에 누적해 소비한다. (3) 불변 갱신(M4)은 **경우마다 새 프로세스에서** 잰다. 한 프로세스에서 함께 재면 키 1,000개 객체의 쓰기가 1.1 µs가 아니라 119.6 µs로 읽혔다. tinybench는 1 µs 이상에서는 2–4% 안에서 일치했지만 100 ns 미만에서는 호출당 한 번씩 재기 때문에 4–6배 높게 나온다 — ADR 0009의 벤치가 나노초 단위를 다룰 때 같은 함정이 있다.

| 측정 | AJV (코드 생성) | cfworker (인터프리터) |
| ---- | --------------- | --------------------- |
| 좁은 가드 1회 (`{properties:{kind:{const}},required}`), 호스트 키 10 / 1,000개 | 5–19 ns / 14–58 ns | 325–393 ns / **14.5–15.8 µs** (호스트 폭에 비례) |
| 루트에 걸린 좁은 가드 200개, 쓰기 1회 | **7.9 µs** | **578 µs** |
| `contains` 가드 1개, 배열 10,000개, 일치 없음 | 190 µs | **4.5 ms** |
| `oneOf` 50분기, 마지막 분기 일치 (분기별 검증) | 1.25 µs | 23 µs |
| 같은 것을 판별식 Map 조회로 | 6.8 ns | — |
| 현재 방식의 에뮬레이션: `new Function` 식 200개 | 1.5–3.2 µs | — |

| 건너뛰기 전략 (AJV, 가드 200개가 모두 루트에 있고 무관한 필드에 키 입력) | 평가 횟수 · 시간 |
| ---- | ---- |
| s0 전부 평가 | 200 · 6.9 µs |
| s1 호스트 참조가 그대로면 건너뜀 (ADR 0005의 원안) | 200 · 6.9 µs — **효과 없음** |
| s2 가드가 읽는 최상위 키의 참조를 선형으로 비교 | 0 · 7.8 µs — 비교 비용이 평가 비용과 같다 |
| s2r 변경 경로 → 가드의 **역색인** | 0 · **13 ns** (가드 수와 무관) |

| 불변 갱신 (깊이 3의 리프) | 키 입력당 |
| ---- | ---- |
| 키 1,000개 객체를 지나는 경로 | 1.1 µs |
| 아이템 10,000개 배열을 지나는 경로 | 2.7 µs |

다른 출처의 측정: `compileGuard` 1개에 70 µs(claude)–270 µs(레드팀). 가드 200개면 폼 생성 시점에 14–54 ms. codex의 "루트 `const` 가드 1,000개 = 0.75 ms"는 일반 AJV 검증 함수(에러 객체 생성 포함) 기준이다.

**결론.**

1. AJV에서는 가드를 몇 번 부르느냐가 문제가 아니다. 가드 200개를 키 입력마다 전부 돌려도 8 µs다.
2. 걱정이 현실이 되는 곳은 둘이다: **인터프리터형 검증기**(같은 작업이 70배, `contains`는 키 입력당 4.5 ms)와 **컬렉션을 훑는 가드**.
3. ADR에 적은 "호스트 참조가 그대로면 건너뛴다"는 루트에 걸린 가드에 대해 아무 효과가 없다. 어떤 쓰기든 루트의 참조를 바꾸기 때문이다. 조건을 공통 조상으로 끌어올리라는 ADR 0002 규칙 6과 정면으로 충돌한다. 효과가 있는 것은 **역색인**뿐이다.
4. AJV에서 실제 비용은 호출이 아니라 **컴파일**이다. 폼 생성 시점에 동기로 치른다.
5. 불변 갱신의 복사 비용은 문제가 아니다. 레드팀이 현재 구현의 동기 쓰기 경로와 나란히 재서 같은 수준임을 확인했다.
6. 판별식 직접 비교(두 번째 평가기)는 AJV 기준으로 필요 없다.

## 4. 리뷰어 사이의 충돌

**가드는 어떤 값을 보는가 (Q3).**

- RC: Resolve 앞에 Normalize를 넣어 정제값을 본다.
- RL: raw를 보고 정제는 Commit에만 둔다. 비활성화를 비파괴로 만든다.
- L: 방출 투영을 보고, 순환은 분석 단계에서 정적으로 금지한다.
- C: canonical 값과 편집 상태를 분리하고, 가드가 읽는 투영을 명세하라.

갈리는 이유는 파괴적 가지치기다. 정제값을 보면 입력 도중 빈 문자열 하나가 조각을 끄고 데이터를 지우고, raw를 보면 형상이 판정과 다른 세계를 읽는다. R8(비활성화 = 투영)을 받아들이면 앞쪽의 해가 사라진다 — 조각이 잠깐 꺼져도 값은 보존되고 다시 켜지면 돌아온다. 그러면 **가드는 방출 투영을 본다**가 유일하게 일관된 답이다: 형상과 판정이 같은 값을 본다.

**`const`/`enum` 전용 직접 비교.** A는 기각(공허한 참 때문에 검증기와 어긋난다), C는 문법을 좁히고 동치를 증명하면 가능, L은 "폼이 `const`를 해석하지 말고 **검증기에게 미리 물어 채운 조회표**를 쓰라"(공허한 참도 검증기가 채운다). §2에 따르면 AJV에서는 필요가 없다. 도입한다면 L의 방식이다. 지금은 넣지 않는다.

## 5. 두 리뷰어가 독립적으로 도달한 대안

C("검증기 소유의 증분 평가 그래프 + 트랜잭션 편집 저장소")와 L("편집 상태 트리 + 순수 투영 그래프")은 같은 곳에 도달했다.

1. **유일한 쓰기 대상은 편집 상태다.** 셀은 입력 그대로의 값, 비활성인 동안 보존한 값, null 아래에서 기억한 쓰기를 담는다. 배열은 identity 목록을 갖는다.
2. **나머지는 모두 그 상태의 순수한 파생이다**: 파싱된 JSON, 가드의 결과, 방출 값(가지치기와 정제는 투영), 유효 스키마, `&` 표현식의 결과, 판정(비동기, revision 스탬프).
3. **순환은 분석 단계에서 금지한다**: "가드와 `&` 식은 자신이 존재나 값을 정하는 셀을 (전이적으로) 읽지 않는다." 위반은 폼 생성 시점의 에러다. 그러면 방출 값은 편집 상태의 **함수**가 되고, 반복도 반복 상한도 순서 의존도 없다.
4. 노드는 필요할 때 만드는 손잡이이고, 노드별 상태는 루트가 소유한 곁 테이블에 둔다.

이것은 ADR 0006·0007의 목표(값의 소유자는 하나, 동기, 한 길)를 버리지 않는다. 바뀌는 것은 둘이다: 소유의 대상이 "JSON 값 트리"에서 "편집 상태 트리"로 넓어지고, "고정점에 이를 때까지 도는 사이클"이 "위상 순서로 한 번 계산하는 파생 그래프"가 된다. R6·R7·R8·R12와 충돌 §4가 이 전환 하나로 접힌다.

대가: 비활성 값을 보존하는 메모리, 꺼진 분기에 남는 민감한 값에 대한 명시적 파기 정책, `&derived`의 의미가 쓰기에서 투영으로 바뀌는 것(사용자가 덮어쓰는 경우는 별도 셀), 디버깅에 그래프 검사 도구가 필요한 것, 층화 검사가 일부 합법 스키마를 거부하는 것(그 스키마들은 현재 설계에서도 진동한다).

## 6. 살아남은 주장

- **고정된 검증기 하나에 대한 ADR 0001.** 에러 라우팅이 실제 실패를 숨기는가로 공격했으나 실패했다 — 라우팅은 에러가 어디에 보일지만 정한다.
- **연언 구문(`allOf`, `if`/`then`/`else`, 중첩)에 대한 가드 → 조각 모델.**
- **"구조는 읽고 의미는 평가하지 않는다."** enum 좁히기, 조각의 기본값, required 표시, 배열의 min/max는 유효 스키마의 구조 읽기다.
- **불변 갱신의 복사 비용**(실측).
- **Derive의 자동 출처**는 단계로 정확히 표현된다(`injectTo`와의 비대칭 포함).
- **루트 단일 디스패처의 방향**(명세 6항이 붙는 조건으로).

## 7. 설계가 아직 묻지 않은 것 (리뷰어들이 제기, 미결)

1. 서버는 어떤 검증기·옵션·방언을 쓰는가. `$schema`가 없으면 무엇을 가정하는가. 서버가 OpenAPI 3.0(`nullable`, `discriminator`)이라면.
2. OpenAPI의 `readOnly` + `required`를 표준 검증기로 판정하면 생성용 폼은 제출할 수 없다.
3. **로드 후 그대로 저장하면 값이 같은가.** 가지치기·기본값 채우기·`omitEmpty`가 서버의 데이터를 바꿔도 되는가.
4. 비활성 경로에 쓰면 무슨 일이 일어나는가 — 거부, 보존, 즉시 가지치기.
5. 표준에서 `default`는 어노테이션이다. 사용자가 확인하지 않은 기본값을 서버로 보내는 것이 BE 소유 스키마에서 의도된 동작인가.
6. 따로 컴파일한 가드가 `$id` 기저 URI, `$dynamicRef`의 동적 범위에서 문맥 안의 평가와 같은 답을 내는가. 원격 `$ref`가 있으면 폼 생성이 비동기가 되는가.
7. 가드 예외·병합 오류·derive 예외 뒤에 사용자 입력과 revision은 어느 상태에 남는가.
8. **차등 테스트를 같은 플러그인으로 돌리면 동어반복이다.** 다른 구현체와 직렬화한 전송 값으로 재야 G1을 실제로 시험한다.
9. 분석 단계가 throw하는 BE 스키마를 FE가 고칠 수 없을 때, 오버레이(`00-goals.md` C1)로 판별식이나 배타를 선언할 수 있는가.
10. 같은 스키마로 만든 폼 N개(행마다 폼 하나)가 청사진과 컴파일된 가드를 공유하는가.
11. 성능의 절대 기준 — 기존 대비 회귀 방지만으로 충분한가. 10,000개 배열 타이핑의 p95, 메모리, 저사양 기기.
12. 타입이 조건에 따라 바뀌는 슬롯(`anyOf:[{type:'integer'},{type:'null'}]`, `type:['string','number']`)에서 노드 타입은 어떻게 바뀌는가.
13. 큰 정착(10,000개 로드)을 쪼개거나 `startTransition`에 태울 수 있는가.

## 9. 검토 뒤의 소유자 결정 (2026-09-22)

검토가 낸 네 가지 결정 사항에 대한 소유자의 답. §8의 "소유자가 정한다" 항목이 이것으로 닫혔다.

| 결정 사항 | 소유자의 답 | 반영 |
| --------- | ----------- | ---- |
| §5의 전환(편집 상태 트리 + 순수 투영)을 받는가 | **방향은 받되 형태를 바꿨다.** 중앙에 값을 두는 것은 허용. **데이터 모델을 따로 두지 않는다** — 노드가 React Fiber처럼 동작한다. 최적화와 라이프사이클의 단일화에는 동의. 자식을 가진 노드도 터미널 전략이면 값을 직접 쓴다. 노출 표면은 전략과 무관하게 같다. 읽기가 쓰기보다 잦은 구조에서 연산이 폭발하지 않아야 한다 | ADR 0006(2차안), 0007. 읽기는 메모의 필드 접근이고 계산은 쓰기 때 dirty 경로에서만 일어난다 |
| 가드는 어떤 값을 보는가 (§4의 충돌) | **방출 값.** "빈 문자열을 '있다'고 보는 게 오히려 이상하다. 그렇게 처리할 거면 omitEmpty를 끄면 된다" | ADR 0007. `open-questions.md` Q3 닫힘 |
| 계약을 검증기 프로필로 한정하는가 (R1) | **설정은 소비자의 책임.** 플러그인의 `bind`로 인스턴스를 주입할 수 있다. 기본값은 기본값이고 format 검사는 의지적으로 켠다. `&` 외에도 커스텀 키를 많이 쓰므로 strict를 무분별하게 열지 않는다 | ADR 0001, 0003, 0004. 부수 결과: strict가 기본이 아니므로 **`&` 키를 제거할 필요가 없다** — 검증기에 작성된 스키마를 그대로 넘긴다. R4(위치를 구분하지 못하는 제거)가 기본 경로에서 사라진다. 방언 선언 + 개발 모드 경고는 제안으로 남겼다 |
| 순환을 분석 단계에서 금지하는가 (§5-3) | **아니다. 돌려 보고 터뜨린다.** "injectTo나 derived의 무한루프 방어처럼. 몇 회 루프를 돌면 경고하고 error를 throw. react의 hook처럼. 애드훅한 방어보다는 돌려보고 터지는 걸 개발 단계에서 알려주는 게 낫다" | ADR 0007. 패스 상한, 동기 throw, 상한에 걸리면 계산을 버리고 커밋된 트리를 유지. R7(고정점이 둘 이상이면 터지지 않고 선언 순서로 정해진다)은 알려진 한계로 적었다 |

이 결정으로 §5의 대안 가운데 채택된 것: 저장은 한 곳·나머지는 계산, 비활성화는 방출에서의 제외, 판정의 revision. 채택되지 않은 것: 노드와 별개인 셀 트리, 정적 층화 검사, 필요할 때 만드는 손잡이 노드(큰 배열의 노드 생성을 늦추는 최적화는 ADR 0006 안에서 가능하다).

## 10. 2라운드에서 공격할 것

- ADR 0006(2차안)과 0007 — Fiber 방식의 작업 루프. 특히: 패스를 되풀이할 때의 비용과 상한의 값, 보류된 쓰기를 버린 뒤의 입력 컴포넌트 상태(비제어 입력의 DOM은 이미 바뀌었다), 배치 도중의 읽기가 무엇을 보는가, 쓰기 의도의 기록(S6)을 노드가 어떻게 드는가, `injectTo`의 입구.
- 아직 고쳐 쓰지 않은 ADR 0002(R9·R10), 0005(R11), 0011(R13·R14·R16) — 고쳐 쓴 뒤에 공격한다.
- 루트 디스패처의 최소 명세 6항(ADR 0008).
