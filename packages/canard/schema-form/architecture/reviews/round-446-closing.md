## 편집자 결정

- **446C-01 (설계 최적화 단계의 개시, 자리와 가지)**
  - 【추론】 소유자가 8단계 이후 작업을 명시적으로 허용했다(위 5행). 따라서 443C-01의 "8단계가 코어 로직 수정의 마지막 단계"와 `reviews/README.md` 운영 원칙 21의 앞 절("9단계에는 코어 로직 수정이 없고")은 이 라운드로 대체된다: 8단계 뒤, 9단계 앞에 **설계 최적화** 단계를 둔다. 9단계의 범위(문서 정리, 레거시 디렉터리 제거, 타입 보강, 릴리스 전 벤치 재실행, 릴리스 전환 시점)는 그대로이고 9단계 자체에는 코어 로직 수정이 없다. 계획서는 PROCESS-067대로 `plan/design-optimization/`의 문서 셋(`request.md`·`verification.md`·`adr-and-axes.md`)이며, 이 단계는 성능 최적화 작업(`plan/perf-optimization/`)의 게이트·측정 원칙·채택 규칙을 그대로 물려받고 "결정을 바꿔야 빨라지면 설계 변경이고 라운드가 먼저다"라는 그 계획의 전제만 바꾼다 — 설계 변경은 이 단계의 목적이며, 바뀌는 결정은 코드보다 먼저 라운드 항목으로 들어간다. 가지는 `feat/schema-form-design-optimization`이고 최종 PR #445가 병합되지 않았으므로 8단계 가지 `feat/schema-form-08-review-and-perf`의 끝 `6692e7f69` 위에 쌓으며, 이 단계의 PR은 그 가지를 base로 열고 #445가 `1.0.0-beta`로 병합되면 base를 `1.0.0-beta`로 옮긴다. 가설이나 작업 하나에 PR 하나, DETAIL 커밋이 코드보다 먼저, 네 관문·전후 배달 비교 차이 0·수정 전에 실패하는 새 시험·다른 모델 가족의 독립 검토 뒤 병합, 단계 루트 PR의 병합은 소유자 몫이라는 규칙은 그대로다.
- **446C-02 (진단과 설계 방향의 채택 — 설계 Ⅰ 먼저, 설계 Ⅱ는 관문 뒤, NODE-044 유지)**
  - 【추론】 속도 저하의 설계 수준 원인은 다섯이다: (1) 분기 전환이 서브트리를 떼어 잠복 저장소로 옮기고 다음 정착에서 노드를 다시 만든다; (2) 내부 식별자가 경로 문자열이다 — 다만 그 까닭은 노드 파괴만이 아니라 아직 없는 노드를 가리켜야 하는 게이트 읽기·의존 표식 때문이며, 노드 참조로 바꿀 수 있는 것은 노드가 생긴 뒤의 식별자뿐이다; (3) 배달은 변경 지점에서 비트가 기록되지만 커밋이 후보 집합 여섯의 합집합을 돌며 Set과 revision 원장 객체를 새로 만든다; (4) 게이트 재계산 단위가 호스트 전체이고 `hasGates`·`branchless`·`latentRaw.size === 0` 같은 전역 조건이 폼 전체의 빠른 경로를 끈다 — 형제 1,000개 호스트의 판별자 한 번에 형제 전부를 다시 고르고(`selectChildren.ts:53`), 게이트 있는 폼의 잎 쓰기에서 `preserveReferences.ts:28-31`이 호스트 전체를 깊은 비교한다; (5) 마운트는 범용 로드 정착이며 정적 첫 로드의 자격이 좁고 청사진 캐시는 Form이 넘기지 않는다. 쓰기 하나가 노드 3개만 건드리는 분기 전환에서 옛 판보다 2.7~4.8배 느리고 할당 29 KiB가 약 230개 함수에 퍼져 있으므로 상수 손질로는 닿지 않는다. 방향은 전면 재설계가 아니라 하위 체계 둘의 설계 수정이다. **설계 Ⅰ**(먼저): 청사진이 호스트마다 정적 엔트리·동적 엔트리와 게이트·독자 집합을 계산해 두는 호스트별 컴파일 계획과, 더럽혀진 독자 호스트의 동적 엔트리만 바퀴를 돌린 뒤 부모 포인터를 따라 한 번 상향 조립하는 2단계 정착 — 노드 수명과 식별자는 그대로라 기존 verify·shadow 모드로 동등성을 증명한다. **설계 Ⅱ**(판정 관문 뒤, 446C-06): 내부 슬롯은 비활성일 때도 자기 raw를 들어 잠복 저장소·pendingExits·revived·경로 키 스크래치를 없애되, 공개 `FieldNode`는 수명마다 새로 발급한다. 공개 노드 객체 자체를 유지하는 안은 NODE-044("다시 들면 새 인스턴스")와 `src/core/surface/__tests__/detached.test.ts:291`의 `expect(root.find('/group')).not.toBe(group)`, React 바인딩의 노드 identity 캐시에 어긋나므로 채택하지 않는다 — 소유자가 인터페이스와 동작을 바꾸지 않는다고 했다(위 2행). SETTLE-044·GOAL-029(형상은 상태의 순수 함수, 직전 활성 집합에서 출발 금지)는 두 설계 모두 그대로 지킨다. 근거는 교차검토 세 세션과 CPU 프로파일(`verification/design-optimization/profile-446.md`)이다.
- **446C-03 (청사진 캐시 — 스키마 객체 identity 키, 438라운드 조건의 충족)**
  - 【추론】 소유자가 청사진 재사용은 완전히 같은 스키마일 때만 뜻이 있고 직렬화 키는 낭비이므로 객체 주소를 키로 하라고 했다(위 2행). 이는 438라운드 소유자 조건 "스키마가 동일할때만 재사용, 스키마가 달라지면 청사진 재구성"을 객체 identity로 충족하며, 438C-03과 443C-01의 "청사진 재생성 유지"는 이 라운드로 대체된다. 엔진에는 이미 `blueprint(schema, options)`의 `options.cache`(`WeakMap<object, BlueprintCacheEntry[]>`, 스키마 객체 참조로 찾고 `isTerminal`·`isAtomic` 술어 identity가 같은 항목만 재사용, `src/core/engine/blueprint/types/blueprint.ts:110`)가 있고 `buildFieldNodeTree.ts:41`이 캐시 없이 부른다. 그러므로 core를 바꾸지 않고 Form 바인딩(`providers/RootNodeContext/utils/createRootLoad.ts`)이 캐시를 넘긴다 — core는 app을 import하지 않는다(`src/core/INTENT.md`). 항목 계약 하나만 바뀐다: 항목이 `warningsCollected` 불리언 대신 청사진 경고 목록을 보관해 새 소비자의 `collect`마다 재생한다(같은 스키마로 띄운 둘째 폼도 경고를 받는다). 첫 마운트 비용은 그대로이고 같은 스키마 객체의 재마운트·StrictMode 이중 마운트·여러 폼에서만 청사진 몫(첫 렌더의 약 43 %)이 사라진다. 소비자가 스키마 객체를 변형한 뒤 재마운트하는 경우는 청사진이 "작성 스키마를 변형하지 않는다"는 전제 밖이며, 그 경우의 강제 갱신은 446C-04의 폼 핸들 `rebuild`가 맡는다.
- **446C-04 (캐시 계층의 자리와 계약, 폼 핸들 `rebuild`)**
  - 【추론】 소유자가 캐시 계층을 플러그인 매니저처럼 `app/` 아래에 모으고 수명·갱신·멱등성·불변성과 강제 갱신을 요구했으며(위 3행), 강제 폐기는 폼 핸들에 더해 공개 API로 내자고 했다(위 4행). 엔진의 프로세스 전역 가변 상태는 약 55개이고 대부분 청사진(14개)이나 청사진 노드(17개)를 키로 하는 WeakMap이며 무효화·강제 재생성 경로는 검증기 캐시(`validation/utils/cache/validationEntries.ts`의 `$id` 밀어내기와 해제 대기열 8)뿐이다. 둘로 가른다. (가) 소비자가 소유한 객체(스키마, 검증기)를 키로 쓰는 캐시만 `src/app/cache` fractal로 모은다 — `app/plugin`과 같은 모양(`INTENT.md`·`DETAIL.md`·`index.ts`·`type.ts`, `utils/CacheManager.ts` static singleton과 `reset()`, `utils/createCacheDomain.ts`, 첫 도메인 `utils/blueprintCacheDomain.ts`). 도메인 계약: `resolve(key, build)`는 같은 키에 같은 참조(멱등), 값은 생성 뒤 바뀌지 않고 개발 모드에서 freeze(불변), `invalidate(key)`·`clear()`는 항목만 제거하고 기존 값을 고치지 않아 마운트된 폼은 옛 청사진을 끝까지 쓴다(강제 갱신), 항목에 생성 세대 번호를 적는다. 소비처는 Form 바인딩뿐이고 core는 app을 import하지 않는다. (나) 엔진이 소유한 불변 객체에서 파생되는 캐시는 엔진 안에서 레코드 둘로 합친다 — 청사진당 `getBlueprintDerived(blueprint)`(파생 규칙 표, 기능 색인, 의존 색인, 게이트 예산 색인, 컨텍스트 소유자, 가상 참조 색인, 순환 여부 등 14 슬롯)와 청사진 노드당 `getHostDerived(blueprintNode)`(선택 표, 직접 선택 계획, 정적 모양, 정적 id, 정적 게이트 목록, 선언 이름, 자식 항목 등 17 슬롯), 지연 계산. 설계 Ⅰ의 호스트별 계획은 이 레코드의 새 슬롯이다. (다) 전이하는 값 객체를 키로 쓰는 메모(`STABLE_SHAPES` 둘, `objectKeyCounts`, `TRIMMED`, `staticSpec`의 둘)는 모듈 범위에 두되 이름을 갈라 한 파일에 모으고, 살아 있는 노드를 키로 쓰는 메모(`getCommittedDeclarationKey`의 `KEYS`, `HOST_CAPS`, `watchValuesMemo`, `detachedReads`)는 런타임 레코드 필드로 옮긴다. (라) `gateSelectionTable.mode`·`gateWheelEvaluation.mode`는 한 파일의 `engineModes`로 합치고 `setMode()`가 파생 레코드를 비우며, 모드를 바꾸는 벤치 fixture는 복원까지 책임진다(`__benchmarks__/fixtures/observationIdentity/prepare.mjs:141`은 복원하지 않는다). (마) 공개 API는 `FormHandle.rebuild(option?)` 하나다: 이 폼의 스키마 항목을 폐기한 뒤 `reset(option)`과 같이 트리를 다시 만든다. 폐기만 하는 메서드는 이 폼이 remount 전까지 옛 청사진을 쓰고 다른 폼에만 영향이 가서 뜻이 닫히지 않는다. 같은 스키마 객체를 쓰는 다른 폼은 각자 다음 reset에서 새 청사진을 받는데, 이는 "소비자가 스키마 객체를 변형했다"는 강제 갱신의 전제와 맞다. 전체 폐기와 테스트용 `CacheManager.reset()`은 공개하지 않는다. `rebuild`는 공개 이름 추가라 `dist/index.d.ts` 대조와 공개 이름 스냅숏 갱신이 따르고 LANDING 이주 항목으로 기록한다.
- **446C-05 (게이트 입력 메모의 허용 — BLUEPRINT-007의 완화, 역색인 기각은 유지)**
  - 【추론】 BLUEPRINT-007은 게이트가 읽는 것을 뽑지 않고 전부 다시 평가하며 변경 경로에서 게이트로 가는 역색인을 기각했다. 소유자가 이 단계에서 설계 수정을 허용했으므로(위 4·5행), 게이트마다 마지막 입력값(투영 참조, extras, context, 존재 여부)을 기억해 입력이 같으면 술어를 다시 부르지 않는 **입력 메모**를 허용한다. 게이트는 입력의 순수 함수이므로 메모는 직전 활성 집합에서 출발하는 것(SETTLE-044, GOAL-029)이 아니며 형상의 순수성은 그대로다. 조건 셋: 던진 평가는 정착마다 기록되므로 메모하지 않는다; 메모 키는 새로 펼친 객체가 아니라 투영 참조다(`evaluateGate.ts:47-51`의 `if` 게이트는 호스트 전체를 읽으므로 루트 `if` 폼에서는 이득이 없다); 역색인은 여전히 기각이다. 넣을지는 벤치가 정한다(BLUEPRINT-007의 "남는 최적화" 절차와 같다). 이 완화는 소유자가 뒤집을 수 있으므로 `reviews/owner-queue-07.md`에 올린다.
- **446C-06 (단계 구성과 판정 관문)**
  - 【추론】 단계는 D0~D5다. **D0 측정 장치의 복원과 기준선**: 8단계 최종 측정(443b)의 47행 장치는 소실되었으므로(`verification/perf-optimization/README.md` 3절) 같은 프로세스에서 0.16.1과 새 판을 AB/BA로 번갈아 재는 코어 장치를 `verification/design-optimization/tools/`에 다시 만들고(마운트·단일 입력·분기 전환·일괄 입력의 canonical 행 여덟과 형제 N 분기 전환·게이트 폼 잎 쓰기 탐침, CPU 프로파일 스크립트 포함), 단계 시작 커밋에서 세 속도 표(마운트·단일 입력·setValue 일괄, 운영 원칙 20)를 잰다. **D1 국소 설계 수정 여섯**(가설마다 PR 하나): H1 청사진의 호스트별 정적 분할 사이드카로 게이트 호스트의 정적 형제를 다시 고르지 않음(`selectChildren.ts:53`·`primeHost.ts:53-113`·`selectEntryStep.ts:276`; `staticShape.ts:46`이 자식 하나의 게이트로 호스트 전체를 거절하는 것도 고친다), H2 바퀴가 돌지 않은 경로의 `preserveReferences` 깊은 비교 생략(`computeNode.ts:119-153`; `updateOutput.ts:72`가 같은 비교를 하므로 shadow 검증 뒤), H3 파동당 한 번 계산하는 문서 순서 인덱스(`compareDocumentOrder.ts:16-23`; 고정 정수가 아니라 파동별 캐시), H4 `writeFieldNode.ts:59`의 `latentRaw.size === 0` 조건을 대상 경로 범위로 축소, H5 `captureFieldNodeChange.ts:62`에 배달 후보 큐를 붙여 커밋의 여섯 집합 순회를 대체(revision 비트 계수는 리스너 유무와 무관하게 유지), H6 청사진 캐시 연결(446C-03). **D2 설계 Ⅰ**: 호스트별 컴파일 계획과 2단계 정착(446C-02); 한 바퀴 안에서 뒤 게이트가 앞 게이트의 투영을 즉시 본다는 계약(`design/03-settle-and-events.md:120`)과 상속 overlay를 그대로 지킨다. **D3 캐시 계층**(446C-04). **D4 판정 관문**: D0와 같은 장치·같은 창에서 세 표를 다시 재어, 분기 전환 oneOf-80 행과 일괄 입력 nested-d6-f4 행이 0.16.1의 1.5배 안에 들고 절대 시간이 각각 1 ms와 5 ms 아래이면 거기서 멈추고 9단계로 간다; 하나라도 넘으면 D5로 간다. **D5 설계 Ⅱ**(조건부): 슬롯 테이블과 수명별 핸들(446C-02); 자료구조가 바뀌어 shadow 모드로 증명할 수 없으므로 시나리오 스위트와, 비활성 참조의 읽기·구독·상호작용 상태·배열 itemKey·`find`·메모리 상한 여섯 의미에 대한 새 시험을 수정 전에 실패하도록 먼저 둔다.
