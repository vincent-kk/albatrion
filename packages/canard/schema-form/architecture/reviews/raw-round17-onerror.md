# 17라운드 — 4번(오류 채널 `onError`) 스웜 수렴과 게이트

2026-09-25. 소유자 지시(통보 4의 셋째 답, 원문): "4번은 이야기를 듣고보니, 모든 form 내부 error를 정리해서 출력할 수만 있다면, (warning / error 모두) onError 핸들러를 넣어도 괜찮을 것 같기도 해. 오히려, validate error 가 걸러진 에러 로깅용 전용 채널로 쓸 수 있겠어. 이거 에이전트들로 수렴을 시켜봐. 어떤게 나을지"

17라운드 소유자 답(`reviews/round-17-owner-answers.md`)의 통보 4를 받아, Form에 폼 내부의 오류와 경고를 받는 관찰자 채널을 둘지(안 B) 두지 않을지(안 A)를 스웜으로 수렴시킨 기록이다. 노드 구조 스웜(`reviews/raw-round17-node-structure.md`)과 병렬로 돌렸다. 원자료(도출과 반박의 묶음, 판정, 게이트 보고)는 세션의 임시 파일이었으므로 여기에 문장으로 옮기고 JSON은 붙이지 않는다. 모든 판정은 코드와 문서의 읽기 전용 판독이며 시험, 빌드, 네트워크는 쓰지 않았다. 살아 있는 문서의 반영 자리는 `adr/0014-error-policy.md`(4판)와 `08-design-a-to-z.md` §11.3·§12·§13이다.

## 1. 스웜의 짜임

- **도출 셋.** 목록 도출은 오늘 코드와 새 설계의 오류·경고 발생 자리를 모두 세어 채널로 보낼 수 있는지를 보았다. 소비자 도출은 핸들러를 다는 호스트의 자리에서, 런타임 도출은 React 실행 사실(렌더, 커밋, 이펙트, `componentDidCatch`, 서버 렌더)과 전달 시점에서 보았다. 셋 모두 안 B를 권했다. 소비자 도출만 이름 `onLog`, 경고의 개발 모드 한정, 핸들러가 기본 출력을 대신하는 안을 더했다.
- **반박 셋.** 도출마다 반박 하나를 붙였다. 목록 도출에는 공격 열셋과 빠진 점 여섯, 소비자 도출에는 공격 여덟과 빠진 점 다섯, 런타임 도출에는 공격 열넷과 빠진 점 다섯이 나왔고, 반박마다 목록에서 빠진 행 일곱을 짚었다.
- **판정 하나.** 도출과 반박을 결정 하나, 계약 열아홉 항목, 목록 50행, 버린 안 열여덟으로 모았다. 소유자 정책 질문은 비워 두었다.
- **게이트 하나.** 조건부 통과였고 지적은 열하나(R17G-1–R17G-11, 중간 다섯, 낮음 여섯)다. 에이전트는 모두 여덟이다.
- **규칙.** 규칙 1(소유자의 답을 모두 글자 그대로 만족하는 설계가 있으면 그것이 우선)과 규칙 2(정책 질문의 세 조건)는 `reviews/raw-round17-convergence.md` §1과 같다. 규칙 3은 ADR 0014의 "오류는 삼키지 않는다"이다. 핸들러가 있든 없든 기본 드러남은 같고, 삼키는 스위치는 없다.

## 2. 결정 — 안 B

17라운드 스웜 수렴(편집자 결정): 안 B를 택한다. Form 속성 `onError(record)`는 폼 인스턴스마다 하나 두는 관찰자 로깅 채널이다. 검증 결과를 뺀 폼 내부의 오류와 경고를 모두 같은 모양의 기록으로 받는다. 핸들러는 흐름을 바꾸지 못하므로, 핸들러가 던지지 않는 한 기본 드러남(사슬 끝 throw, 프로미스 거부, 주인 없는 오류 싱크, 개발 모드 콘솔)은 핸들러가 있든 없든 같다. 핸들러가 없으면 비용도 안 A와 같다. 이 결정은 ADR 0014 미결 둘째(E2)의 "관찰자는 오류 층의 사건만 받는다"를 대체한다. 게이트 뒤 소유자 확인 둘((가) 검증기 없음 알림의 `level`, (나) `@winglet/react-utils` 확장)은 17라운드 소유자 답으로 닫혔다(§7).

근거는 일곱이다.

1. **규칙 1.** 둘째 답의 고정 문장("onError 와 onValidate 를 섞는건 사용자 입장에서 엄청 햇갈립니다")을 지킨다. 노드 `errors`의 `ValidationIssue`, `onValidate`, `errors` 속성과 외부 오류(`src/components/Form/type.ts:54`·`:66`, `src/core/nodes/AbstractNode/AbstractNode.ts:816-839`), 제출 때의 `VALIDATION_ERROR.SCHEMA_VALIDATION_FAILED`(`src/components/Form/Form.tsx:117-123`)는 채널에 들이지 않는다. 셋째 답은 열린 말이지만 판단을 에이전트에게 맡겼다.
2. **규칙 2의 (가)는 거짓이다.** 투명성 가치(`08-design-a-to-z.md` §1), C2 "각종 에러들의 출력을 적당하게 제공", 10라운드 A-2 "form은 고지 의무만 진다", 14라운드 O-10 "경고만 일어나고 동작하는것처럼 보이는게 더 위험합니다", 둘째 답이 받아들일 수 있다고 한 3번(채널 하나, 모양 하나), 셋째 답의 방향이 모두 B를 가리킨다. 안 A로는 네 가지를 할 수 없다. 폼 식별과 문맥을 붙일 자리가 없고(이벤트 처리기를 뚫은 throw는 전역으로만 간다), 프로덕션의 경고를 프로그램으로 받을 길이 없으며(`src/helpers/warning/warnDevelopmentIssue.ts:26`), 통보 3의 검증기 없음처럼 거부하지 않는 알림이 콘솔 말고 갈 곳이 없고, 오류가 throw, 거부, 싱크, 콘솔의 네 갈래 모양으로 흩어진다. 서버 사이드 렌더링은 두 안 모두 클라이언트 하이드레이션에서 드러나므로 가르는 근거가 아니다.
3. **규칙 2의 (나)도 거짓이다.** 비용이 옵트인이다. 핸들러가 없는 프로덕션은 기록 객체, 메시지 서식, 경고 중복 집합, 정착 경고 판정, 청사진 경고 데이터를 만들지 않으므로 08 §16.2의 "프로덕션 비용 없이 추적성"을 지킨다. 오늘 코드는 프로덕션에서도 경고 검출과 서식을 돌린 뒤 버리므로(`src/core/nodes/ObjectNode/strategies/BranchStrategy/utils/getCompositionNodeMapList/utils/warnIfNullUnreachable.ts:25-38`, `src/helpers/jsonSchema/processAllOfSchema/processAllOfSchema.ts:38-44`) 핸들러가 없을 때 B는 오늘보다 싸다. 이 주장은 게이트 R17G-1의 고침(소비자 판정을 보고기의 `hasConsumer()`로 사건마다)을 전제로 선다.
4. **규칙 3.** 핸들러는 관찰자이고 반환값은 무시되며 삼키는 스위치는 없다. ADR 0014가 외부 조사에서 기각한 안("`onError` 하나로 보내고 없으면 throw")과 다르다.
5. **이름은 `onError`다.** 셋째 답이 글자로 쓴 이름이다. 첫째 답이 드러낸 함정(검증 오류로 읽힘)은 두 장치로 푼다. 선언의 문서 주석 첫 줄에 "검증 결과는 오지 않는다(`onValidate`). 경고도 온다"를 적고, 검증 결과 인터페이스의 `ValidationIssue` 개명(PR-4)이 `onError`의 공개(PR-7)보다 먼저 선다.
6. **대가.** B는 공개 표면을 넓힌다. 속성 하나, 기록 형, 코드 문자열 목록, 핸들러 예외의 경로별 규칙, 청사진 수집기 배관이 는다. 오늘 오류·경고 코드는 공개 계약이 아니다(`package.json:30-37`의 `exports`는 '.'뿐이고 `src/index.ts:16-21`은 판별 함수만 내보낸다). 가치 사이의 맞바꿈이 아니라 문서와 판 규칙의 일이다. 코드를 더하면 minor, 이름을 바꾸거나 없애면 major다.
7. **반박이 무너뜨린 곳을 고쳐 담았다.** 핸들러 예외가 `componentDidCatch`와 이펙트 밖으로 새던 길, 원시값이 `WeakSet`에 들어가지 못하는 틈과 같은 객체를 되풀이해 던질 때 적게 기록되는 문제, 경고의 중복 키, 청사진 캐시의 비용, 경고 코드가 오늘 공개되어 있다는 잘못된 전제, 가드 컴파일 실패의 환경별 시점, 묶음 오류의 동일성, 렌더 중 보증의 범위, `validate()` 거부 문구의 범위, 검증기는 있으나 컴파일이 실패한 경우의 층, 첫째 답의 효력을 잘못 읽은 점이다.

**소유자가 받는 것.** 폼에 `onError` 하나를 달면 그 폼 안에서 난 문제가 오류든 경고든 같은 모양의 기록(수준, 코드, 메시지, 위치, 원래 오류)으로 한 곳에 온다. 스키마 오류, 무한 루프에 해당하는 예산 초과, 리스너 예외, 사용자 입력 컴포넌트가 터진 것, 검증기가 없다는 알림이 모두 온다. 필드의 검증 결과는 오지 않고 지금처럼 `onValidate`와 필드 오류로만 간다. 핸들러가 던지지 않는 한 달든 안 달든 폼의 동작은 같다(핸들러가 던지면 그 예외도 원래 오류와 함께 드러난다). 폼 바깥에서 나는 `registerPlugin` 오류만 이 채널에 오지 않고 지금처럼 부른 쪽에 바로 던져진다.

## 3. 소유자 답과의 대조

- **R17-1 "나 허용. 망가진 값을 올리는게 더 위험하겠다".** 핸들러는 사슬 끝 throw, `degraded`, 제출 거부의 어느 것도 끄지 못한다. 식·가드 실패, 동적 `controls.injectTo` 대상 없음, 예산 초과, 되먹임·중첩 초과는 오류 층이므로 모든 환경에서 기록된다. 검증기는 있는데 전체 스키마 컴파일이 실패한 경우는 R17-1 나대로 모든 환경에서 거부하고 오류로 기록한다.
- **통보 3 "오류만 내보내고 거절은 하지 마시죠".** 검증기가 없으면 거부하지 않는다. 개발 모드 콘솔에 알리고, `onError`에는 모든 환경에서 트리마다 기록 하나를 보낸다. 기록의 `level`은 게이트가 정책 질문으로 올렸고(R17G-3) 소유자 답 (가)로 `warning`이 되었다. 이 답의 근거(검증 없이 폼만 그리는 사용예)는 검증기를 주지 않은 경우에만 닿으므로, 검증기를 주었는데 컴파일이 실패한 경우는 R17-1 나를 따른다.
- **통보 4 첫째 답 "다시 던지는 안은 좀 위험하긴 합니다만".** 두 오류를 융화하지 않고 채널을 가른다. "다시 던지는 안은 위험"은 E8(바운더리의 다시 던지기를 버림)과 함께 효력이 있다. B는 핸들러의 예외도 `componentDidCatch`와 이펙트 밖으로 내보내지 않는다.
- **둘째 답 "섞는건 … 엄청 햇갈립니다"(고정).** 검증 결과는 `onValidate`와 노드 `errors`에만, 폼 내부 사건은 `onError`에만 간다. 검증기 실행 실패(검증 함수의 throw, 요청 시점의 `$ref` 순환)는 입력의 판정이 아니고 `onValidate`로도 가지 않으므로 섞임이 아니다(E9). 경계는 `ValidateFunction`의 문서 주석 "입력의 판정은 돌려주고 던지지 않는다. 던지면 실행 실패다"로 못박는다. "스키마오류나 무한루프나 그런것들을?"에는 청사진 오류, 예산 초과, 되먹임·중첩 초과가 모두 기록된다고 답한다.
- **셋째 답.** 이름은 `onError` 그대로이고, `level`로 오류와 경고를 모두 받으며, 검증 결과는 빼고, 관찰만 한다. "모든"의 경계는 목록에 이름으로 적었다(폼 인스턴스 밖의 `registerPlugin`과 제외 행). "정리해서"는 오늘의 코드 체계(`BaseError`의 `<GROUP>.<SPECIFIC>`, `SCHEMA_FORM_WARNING.*`)를 잇는 코드 표를 README와 docs에 싣는 것으로 채운다.

## 4. 계약 요지(열아홉 항목, 게이트의 고침을 적용한 것)

| 항목 | 요지 |
| --- | --- |
| 이름과 자리 | Form 속성 `onError?: (record: FormErrorRecord) => void`. 기록 형 `FormErrorRecord`와 코드 형 `FormErrorCode`(문자열 리터럴 합집합)는 가칭이며 PR-4에서 확정한다. 렌더 계층이 속성을 소유하고 `useHandle`로 최신 속성을 부르므로 인라인 함수가 트리와 캐시를 다시 만들지 않는다. core는 React를 모르므로 트리를 만들 때 보고기 `{ report(record): void; hasConsumer(): boolean }`(가칭) 하나를 인자로 받는다. 렌더 계층의 `hasConsumer`는 부를 때마다 "최신 `onError` 속성이 함수임, 또는 `process.env.NODE_ENV !== 'production'`"을 돌려주고, core는 기록·서식·경고 판정 전에 매번 묻는다. 마운트 뒤에 핸들러를 새로 단 폼은 그 뒤의 사건부터 받는다(R17G-1). 선언의 문서 주석 첫 줄은 "폼 내부의 오류와 경고를 받는 관찰자. 검증 결과는 오지 않는다(`onValidate`). 반환값은 무시되고 오류를 막지 못한다" |
| 받는 것 | 폼 인스턴스에 묶인 오류 층과 경고 층의 사건 전부. 청사진 오류와 경고, 마운트 정착의 오류와 경고, 정착 오류와 경고(예산 초과, 식·가드 실패, 동적 대상 없음, 공유 충돌, 게이트 가진 분기 둘 이상 켜짐), 되먹임·중첩 초과, 리스너 오류(구독 리스너, `onChange`, `onStateChange`, `onDiagnosticsChange`, `batch` fn, 검증 결과 파동의 리스너와 `onValidate`), 호출자 오류(`Overwrite`와 `Merge`를 함께 준 `setValue`, 폐기된 노드에 대한 쓰기, `FormTypeInputMap` 패턴), `degraded` 동안의 제출 거부, 검증 불가(검증기는 있으나 컴파일 실패), 검증기 실행 실패, 바운더리가 잡은 렌더 오류, 검증기 없음과 조건부 스키마 경고, 렌더 계층 경고(가상화 꺼짐, `presentation` 키 의심) |
| 받지 않는 것 | 검증 결과 전부(노드 `errors`의 `ValidationIssue`, `onValidate`, `errors` 속성과 `setExternalErrors`·`clearExternalErrors`, 제출의 `VALIDATION_ERROR.SCHEMA_VALIDATION_FAILED`), 정착 추적, `diagnostics`의 상태 변화(원인 오류는 기록됨), 묶음 `SchemaFormError` 자체(구성 오류마다 기록), 핸들러 자신의 예외와 핸들러 안 쓰기의 거부, 호스트 `onSubmit`이 던지거나 거부한 것, 폼 인스턴스 밖의 `registerPlugin`(`UNHANDLED_ERROR.REGISTER_PLUGIN`), React 자신의 경고와 core가 감지하지 않는 렌더 중 쓰기. 같은 제출 거부라도 `degraded`는 기록되고 검증 실패는 기록되지 않는다(문서에 한 줄) |

## 6. 버린 안

| 안 | 버린 까닭 |
| --- | --- |

## 7. 게이트 열하나의 처분

게이트 판정은 조건부 통과였다. 안 B와 검증 오류의 분리는 기준에 맞고, 정책 질문이 비어 있는 것만 두 곳(R17G-3, R17G-4)에서 기준에 못 미쳤다. 두 곳은 소유자에게 올려 답을 받았다.

| 지적 | 심각도 | 요지 | 처분 |
| --- | --- | --- | --- |
| R17G-1 | 중간 | `useHandle`은 속성이 없어도 같은 함수를 돌려주므로 "보고 함수가 없으면 `undefined`"로는 소비자 유무를 알 수 없고, 핸들러 없는 프로덕션의 비용 주장이 깨진다 | 적용. core는 보고기 `{ report, hasConsumer }`(가칭)를 받고 사건마다 `hasConsumer()`를 묻는다. 마운트 뒤 단 핸들러는 그 뒤 사건만 받는다(§4 이름과 자리, 비용) |
| R17G-2 | 중간 | 검증기 없음과 조건부 스키마 경고를 "로드마다" 보내면 입력마다 `setValue(V)`를 넣는 제어형 폼에서 같은 경고가 입력마다 온다 | 적용. 트리마다 한 번(마운트는 준비 이펙트, 재생성 reset은 reset 사슬 끝). 같은 스키마 reset과 루트 전체 교체에서는 다시 보내지 않는다 |
| R17G-3 | 중간 | 검증기 없음 기록을 `warning`으로 둔 것은 통보 3 답의 글자("오류만 내보내고")와 어긋나는 읽기이므로 편집자 결정으로 둘 수 없다 | 소유자 답 (가) "(가) ㄱ warning으로."로 닫힘. 코드는 `SCHEMA_FORM_WARNING.VALIDATOR_MISSING`(가칭). ADR 0014 §1 오류 행의 "검증이 불가능하거나"는 "검증기가 있으나 검증이 불가능하거나"로 좁힌다 |
| R17G-4 | 중간 | `@winglet/react-utils`의 고차 구성 요소 시그니처 확장과 내부 ErrorBoundary 공개는 그 모듈 INTENT의 "Ask first"이므로 문서를 먼저 고치는 것으로 대신할 수 없다 | 소유자 답 (나) "확장 허용합니다"로 닫힘. 인자를 주지 않으면 오늘 동작 그대로이고, PR-7에서 그 모듈의 `DETAIL.md`를 먼저 갱신한 뒤 코드를 고친다 |
| R17G-5 | 중간 | 이 묶음만 옮기면 R17-1 나·통보 3 전파 전의 문장(ADR 0014 미결, 08 §11.3 검증기 행, 08 §14 검증기 행 등)과 모순이 남는다 | 한 번의 반영으로 닫힘. 17라운드 정리 명세 v3가 R17-1 나, 통보 3, R17-2 ㄴ, R17-3, 4번, 노드 구조를 한 적용에서 파일별 편집자 넷에게 나눠 옮겼다 |
| R17G-6 | 낮음 | 낡은 문장(`onError` 1회, 모든 경로의 `WeakSet`, "관찰자: 우리의 모든 오류가 렌더 밖에서 한 번", 선택적 보고 콜백)이 새 계약과 어긋난 채 남는다 | 적용. 사슬은 "기록마다 `onError`", 바운더리는 "렌더 때 보고 함수를 얻는 선택 인자", 09의 관찰자 문구와 PR-7 시험 항목을 새 계약으로, 08 §15의 모듈 수준 바운더리 행은 닫힘으로 표시한다 |
| R17G-7 | 낮음 | 시점 (1)이 입력 맵 정규화와 가상화 관리자 생성의 기록을 로드 객체에 모은다고 했으나 그 시점에 로드 객체가 없다 | 적용. (1)은 청사진과 마운트 정착만, 입력 맵은 (6), 가상화는 (7) |
| R17G-8 | 낮음 | 핸들러가 던져 새 묶음이 생기면 `aggregate ?? error`의 동일성이 깨지고, "달든 안 달든 동작이 같다"가 던지는 핸들러에서는 거짓이다 | 적용. 원래 드러날 값을 펼치지 않고 앞에 두고, 동일성이 깨지는 경우를 문서에 적으며, "핸들러가 던지지 않는 한"을 붙였다 |
| R17G-9 | 낮음 | 목록 행 몇이 사실이나 확정된 답과 어긋난다 | 적용(§5). `UNSET_ON_INACTIVE_ON_OBJECT` 행 삭제, `presentation.trim`은 `PRESENTATION_KEY_SUSPECT`의 둘째 경우, `FormProvider` 제외 문구 정정, 필드 바운더리의 감싸는 자리 셋, `EXPRESSION_THREW`의 출처, 청사진 오류의 재대조 경로, 설계 항목에서 생길 코드의 행 |
| R17G-10 | 낮음 | 루트 바운더리가 하위 트리를 버리면 같은 마운트의 정착 오류가 기록도 싱크도 없이 사라진다 | 적용. 보고기가 가장 최근 로드를 들고 있다가 루트 바운더리의 `componentDidCatch`가 그 로드의 오류 층 기록을 먼저 보낸다 |
| R17G-11 | 낮음 | `WeakSet`에 남은 값이 다른 렌더 실패의 전달을 가리고, 실패 기록 안의 `validate()`가 끝없는 비동기 반복을 만든다 | 적용. 두 경계를 문서에 적는다 |
