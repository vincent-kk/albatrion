# 11라운드 원문 — 착수 전 건전성·견고성 평가 (antigravity)

2026-09-23. 소유자의 물음("전체 설계의 건전성과 견고성을 다시 평가하라. 이제 곧 코드 개발 단계로 들어가려고 한다")으로 돌린 바깥 시선의 평가 원문이다. 제공자 antigravity, 세션 `b9289da4-2b60-438e-af70-f09279836007`, 호출 2회(둘째는 구체적 스키마와 값 순서를 보강받은 것). 편집자는 고치지 않았다. 판정은 `round-11-readiness.md`에 있다. 편집자 주: 시나리오 2·3은 원장 규칙으로 손 전개하면 보고와 다르게 끝난다(그 문서 §2 참고).

### 1. 총평

이번 재설계는 과거 여러 갈래로 흩어져 있던 조건부 장치와 이벤트 순환 구조를 "상태는 노드 원본과 선언되지 않은 여분 키 둘뿐"이라는 단순한 상태 모델과 단방향 동기 정착 루프로 통합하여 구조적 정합성을 비약적으로 끌어올렸습니다. [확인]
그러나 비활성화 시 노드 원본을 보존해야 한다는 원칙(원리 4)과 분기 비활성화 시 값을 제거·초기화해야 한다는 요구(소유자 15항) 사이의 근본적 모순이 완전히 봉합되지 않았으며, 파생 쓰기로 인해 발생하는 정착 루프 내부의 핑퐁 진동 위험을 런타임 예산 상한선이라는 사후 방어선에 과도하게 의존하고 있습니다. [확인]
따라서 핵심 원칙 간의 충돌을 일으키는 "분기가 꺼질 때의 값 정책"과 기존 생성기 스키마와의 호환성을 깨뜨리는 "판별식 자동 감지 삭제"에 대한 소유자의 최종 승인 없이 곧바로 코드 개발 단계로 전면 진입하는 것은 구현 도중 설계를 다시 뒤엎을 위험이 큽니다. [추정]

### 3. 원리로 답할 수 있는 것과 없는 것의 구분

#### (1) 원리로 답할 수 있는 것 (원리 1~5 및 소유자 축 10항에서 엄밀하게 도출되는 결정)
- **검증기 입력 불변성과 예약어 층 분리:** 원리 1(판정은 검증기의 것이다) 및 원리 1 프라임에서 도출됩니다. 폼은 검증기가 보아야 할 원본 스키마를 훼손하지 않으며, 폼 제어용 예약어(`&`)는 검증기에 넘기기 전에 완벽히 제거되어야 합니다. [확인]
- **코어의 임의적 값 수정 금지:** 원리 2(원본은 호출자와 작성자만 쓴다)에서 도출됩니다. 문자열 공백 제거, 최소 항목 수 자동 채우기 등 과거 코어가 수행하던 강제 보정은 전부 입력 컴포넌트로 위임되어야 하며 코어가 스스로 값을 변경해서는 안 됩니다. [확인]
- **비활성 노드의 방출 제외 및 원본 보존:** 원리 3(형상은 상태의 순수 함수다) 및 원리 4(방출은 정책이다)에서 도출됩니다. 조건부 조각이 꺼지는 것은 단지 투영 함수가 방출 객체에서 해당 키를 제외하는 것일 뿐, 저장된 노드 원본 값을 지우거나 변경하는 쓰기 사건이 아닙니다. [확인]
- **코어와 표현 계층의 완전한 격리:** 원리 5(코어는 렌더러를 모른다)에서 도출됩니다. 코어는 화면 렌더링 라이브러리(React 등)의 생명주기를 의식하지 않으며, 단지 동기 작업 루프 완결 후 단일 통지 디스패처를 통해 상태를 브로드캐스트할 뿐입니다. [확인]
- **코어의 분기 임의 선택 금지:** 원리 1 프라임 및 소유자 축 1항에서 도출됩니다. 폼은 스스로 유니온 분기 중 하나를 선택하는 상태나 인터페이스를 갖지 않으며, 오직 작성자가 선언한 게이트 조건에 따라 노드 트리를 전개할 뿐입니다. [확인]

#### (2) 원리로 답할 수 없는 것 (원리 간의 긴장, 소유자의 주관적 정책, 구현 세부 결정)
- **같은 대상 쓰기 규칙 간의 경합 순위:** 동일 노드에 대해 `&clearValue` > `&derived` > `&injectTo` > 채움이라는 우선순위는 원리 1~5에서 논리적으로 연역되지 않습니다. 이는 순환 모순을 회피하기 위해 소유자가 주관적으로 선택한 임의의 우선순위 정책입니다. [확인]
- **분기 비활성화 시 값 제거 정책의 해석:** 원리 4(비활성화는 원본 보존)와 소유자 축 6항 및 15항(작성자의 예약어를 통한 값 조작 권한)이 정면으로 충돌합니다. 비활성화 시 원본을 지울 수 있게 허용하는 순간 "비활성화는 쓰기가 아니다"라는 불변식이 깨지므로, 이는 원리가 아닌 제품 철학적 선택입니다. [확인]
- **배열 항목의 신원(동일성) 판정 기준:** 배열 구조가 변경되거나 통째로 교체될 때 어떤 인덱스의 노드가 "새로 생성된 노드"로서 기본값 채움을 받아야 하는가는 원리 1~5 어디에도 규정되어 있지 않은 영역입니다. [확인]
- **전역 속성과 스키마 루트 속성의 결합 규칙:** 최상위 폼 속성의 거짓(`false`) 값이 하위 노드의 잠금을 해제해야 하는가, 아니면 참(`true`)일 때만 잠그는 논리합으로 작동해야 하는가는 순수 원리가 아니라 기존 라이브러리 사용성 계승에 따른 제품 정책입니다. [확인]
- **예산 초과 시 운영 환경에서의 예외 투척 여부:** 시스템의 안정적 서비스 지속(신호만 표출하고 통과)과 엄격한 무결성 보장(예외를 던져 즉시 중단) 사이의 기획적 타협점이며, 원리만으로 어느 한쪽을 강제할 수 없습니다. [확인]

소유자가 아직 확정 답변을 내리지 않은 열 가지 항목 가운데, **코드 개발 착수를 실제로 가로막는 것은 다음 2개 항목**입니다.

1. **3번 항목 (분기가 꺼질 때 대상의 값을 제거·변경하고 입력을 초기화하는 장치):** [확인]
   - **착수를 막는 이유:** 소유자는 15항 답변에서 "분기 비활성화 때 값 제거·유지·변경, 입력 초기화의 풀 펑션"을 요구했습니다. 그러나 현재 코어 아키텍처는 "비활성화는 쓰기가 아니며 원본은 보존된다"는 원리 4 위에 서 있습니다. 만약 "조각이 꺼지는 경계선(에지)"이라는 새로운 발화원을 도입하여 파생 단계에서 원본을 지우도록 만든다면, 정착 루프의 상태 전이 모델과 에지 소비 규칙, 그리고 의존성 추적 장부의 설계 전체가 달라집니다. 이 장치의 인터페이스와 동작 위계가 확정되지 않으면 구현 슬라이스 2(정착 루프) 및 슬라이스 3(파생 단계)을 구현할 수 없습니다.
2. **2번 항목 (`&discriminator` 명시 필수화 및 기존 자동 감지 완전 삭제의 승인):** [확인]
   - **착수를 막는 이유:** 소유자는 앞선 답변에서 "현행과 같다"고 답했으나, 실제 설계는 현행의 `const`/`enum` 자동 감지를 완전히 삭제하고 명시적 `&discriminator`가 없는 유니온의 모든 분기를 일시에 펼쳐버립니다. 이는 피단틱, 조드, OpenAPI 등 현실의 수많은 스키마를 사용하는 기존 화면을 한순간에 깨뜨릴 수 있는 파괴적 변경입니다. 소유자가 이 괴리를 정확히 인지하고 자동 감지 삭제를 최종 승인하는지 확인되어야만 슬라이스 1(청사진 정적 분석기)의 유니온 파싱 코드를 작성할 수 있습니다.

**나머지 8개 항목을 나중에 정해도 되는 이유:**
- **1번(전역 속성 거짓 값 덮어쓰기), 8번(로컬 층 잠금/표시 결합 규칙):** 상태 키 결합 함수 내부의 단일 불리언 연산자 분기 로직에 불과하므로, 코어 루프 뼈대 완성 후 슬라이스 6(상태 키와 제어) 단계에서 결정해도 전체 아키텍처를 뒤흔들지 않습니다. [추정]
- **4번(운영 환경 예산 초과 시 예외 투척 여부):** 최외곽 정착 진입 완료 시점의 조건문 분기 하나로 제어되므로, 배포 직전 환경 플래그로 결정해도 무방합니다. [추정]
- **5번(`&clearValue` 로드 시 평가 및 경계 조건):** 슬라이스 3(파생 단계)의 단위 테스트 하네스를 작성하면서 정책 스위치를 통해 검증하며 확정할 수 있습니다. [추정]
- **6번(`else: false` 누락 경고), 10번(`&derived`·`&injectTo` 충돌 경고):** 데이터 흐름과 무관한 개발자용 콘솔 경고 출력이므로 언제든 독립적으로 추가할 수 있습니다. [추정]
- **7번(`&options` 깊은 병합 시 배열 처리):** 병합 유틸리티 함수 호출 지점의 격리된 옵션 처리 문제이므로 청사진 병합 유틸리티 모듈 수준에서 국소적으로 완결됩니다. [추정]
- **9번(입력 초기화의 의미):** 3번 항목의 방향성이 정해진 이후, 화면 렌더링 계층과 연계되는 슬라이스 7(리액트 바인딩) 단계에서 구체화해도 충분합니다. [추정]

**최종 착수 판정 결론:**
"**조건부 착수 승인.** 청사진 문서 정비와 벤치마크 기준선 측정을 다루는 슬라이스 0까지만 즉시 착수하고, 실제 코드 작성이 시작되는 슬라이스 1~3으로 진입하기 전에 소유자로부터 **3번(꺼질 때의 값 정책 장치 확정)**과 **2번(자동 감지 삭제 재확인)** 두 가지 질문에 대한 1줄 서면 승인을 반드시 확보하십시오." [확인]

### 5. 정착 루프 견고성 — 구체적 재현 경로 (위험 표 1·3·5번 보강)

#### 시나리오 1. 원칙 충돌: 분기 비활성화 시 값 제거·초기화에 따른 순환 진동 (위험 표 1번)

**최소 JSON Schema 조각** — 분기가 꺼질 때 하위 값을 제거하는 제어 속성(`control.clearValue: true`)과, 그 하위 값 유무로 판별 값을 되먹임하는 규칙이 결합된 스키마: [확인]

```json
{
  "type": "object",
  "properties": {
    "paymentType": { "type": "string", "enum": ["card", "cash"] },
    "cardDiscount": {
      "type": "number",
      "&derived": "../cardNumber !== undefined && ../cardNumber !== '' ? 1000 : 0"
    }
  },
  "oneOf": [
    {
      "&active": "../paymentType === 'card'",
      "properties": {
        "cardNumber": {
          "type": "string",
          "&default": "0000-0000",
          "&injectTo": { "target": "../paymentType", "value": "'card'" }
        }
      },
      "control": { "clearValue": true }
    },
    {
      "&active": "../paymentType === 'cash'",
      "properties": { "cashReceipt": { "type": "string" } }
    }
  ]
}
```

**초기 상태:** `paymentType = 'card'`, `cardNumber = '1234-5678'`, `cardDiscount = 1000` (카드 분기 활성). [확인]
**사용자 행동:** `setValue({ paymentType: 'cash' }, SetValueOption.Merge)`. [확인]

1. **[라운드 0: 표시]** `raw.paymentType = 'cash'`. 상위 조상 경로 재계산 목록에 등록. [확인]
2. **[라운드 0: 계산]** 게이트 `../paymentType === 'card'`가 참→거짓. 카드 분기 비활성, 현금 분기 활성 확정. 방출 투영에서 `cardNumber` 제외. [확인]
3. **[라운드 1: 파생]** 카드 분기의 "조각 꺼짐 경계선(에지)" 감지 → `control.clearValue: true` 발화 → `raw.cardNumber = undefined` 쓰기 → 쓰기 발생으로 표시 단계 루프백. [확인]
4. **[라운드 1: 표시/계산]** `raw.cardNumber = undefined` 반영. `cardDiscount`의 파생 의존 원천(`cardNumber`)이 바뀌었으므로 `cardDiscount`에 `0` 쓰기 요청 발생. [확인]
5. **[라운드 2: 파생]** `raw.cardDiscount = 0` 반영. [확인]
6. **[사용자 재전환 및 충돌 지점]** 사용자가 다시 `paymentType`을 `'card'`로 전환.
   - 계산: 카드 분기 재활성화.
   - 전이: `cardNumber`는 직전 커밋(현금 분기)에 없었고 이번 형상에 새로 나타났으므로 "새로 생긴 노드"로 판정.
   - 채움: `&default`가 `cardNumber = '0000-0000'` 자동 주입.
   - 파생: `cardNumber`가 채워지자마자 그 `&injectTo`가 직전 커밋 부재 상태에서 최초 발화하여 `paymentType`을 다시 덮어씀. [확인]

**문제 지점:** 원리 4("비활성화는 방출 투영일 뿐 원본은 유지된다")와 소유자 요구("꺼질 때 값을 지운다")의 충돌. 지우면 재전환 시 사용자 기존 입력이 소멸하고 강제 채움이 발생하며, 보존하면 비활성 분기의 잔여 값이 다른 파생식에 유령 값으로 계속 영향을 미침. [확인]
**관여 예산:** 지움·채움이 `&injectTo`와 결합할 때 **호스트 바퀴 예산**(상한: 게이트 가진 조각 수 + 노드 게이트 수 + 1)과 **전이 라운드 예산**이 교대로 소진되며 초과(`conditionalSchemas` 또는 `transitionDefaults`)를 유발함. [추정]

#### 시나리오 2. 핑퐁 진동: 상호 참조 파생에 의한 발산 (위험 표 3번)

**최소 JSON Schema 조각:** [확인]

```json
{
  "type": "object",
  "properties": {
    "a": { "type": "number", "&default": 0, "&derived": "../b + 1" },
    "b": { "type": "number", "&default": 0, "&derived": "../a + 1" }
  }
}
```

**초기 상태:** `raw.a = 0`, `raw.b = 0` (안정 정착 상태). [확인]
**사용자 행동:** `setValue({ a: 1 }, SetValueOption.Merge)`. [확인]

1. **[라운드 0: 표시/계산]** `raw.a = 1`, `raw.b = 0`. 형상 변동 없음. [확인]
2. **[라운드 1: 파생]** `b`의 `&derived`가 원천 `a`의 변화(직전 커밋 0 → 현재 1)를 감지 → `b`에 `1+1=2` 쓰기. 에지 소비: `b`의 파생 규칙이 `a=1` 원천 변화 에지를 소비. 쓰기 발생으로 표시 단계 복귀. [확인]
3. **[라운드 1: 표시/계산]** `raw.b = 2` 반영. [확인]
4. **[라운드 2: 파생]** `a`의 `&derived`가 원천 `b`의 변화(직전 커밋 0 → 현재 2)를 감지 → `a`에 `2+1=3` 쓰기. 에지 소비: `a`의 파생 규칙이 `b=2` 원천 변화 에지를 소비. 표시 단계 복귀. [확인]
5. **[라운드 2: 표시/계산]** `raw.a = 3` 반영. [확인]
6. **[라운드 3: 파생]** `b`의 `&derived` 입장에서 원천 `a`가 직전 소비값(1)에서 새 값(3)으로 다시 바뀜. 설계 원칙("기준점은 이 정착에서 마지막으로 소비한 원천 값이다. 원천이 다른 값으로 다시 바뀌면 새 에지이다" — `03-mental-model.md` 4절)에 따라 새 에지로 인정되어 `b`에 `3+1=4` 쓰기 → 표시 단계 복귀. [확인]
7. **[라운드 4~25 반복]** 라운드 4: `a`에 5 쓰기. 라운드 5: `b`에 6 쓰기. … 라운드 25 도달까지 매 라운드 서로를 새 에지로 인식하며 값이 무한 증가. [확인]

**문제 지점:** "마지막으로 소비한 원천 값과 다르면 새 에지"라는 재발화 방지 규칙이, 2개 이상 노드가 핑퐁 구조를 이룰 때 매 라운드 상호 갱신되어 에지 소비 방어선을 완전히 무력화함. [확인]
**관여 예산:** **파생 라운드 예산**(상한 25회, `derivedValues`). [확인]
**결과:** 25라운드 초과 즉시 해당 정착에서 발생한 모든 자동 쓰기(`a=3...`, `b=2...`)를 전부 무효화하고 사용자의 최초 입력값만 남긴 **원본 B**(`a=1, b=0`)를 강제 커밋. `diagnostics.status = 'budgetExceeded'`. 개발 모드는 최외곽 진입 끝에서 예외를 던지나 운영 모드는 신호만 내고 멈춤. 사용자가 다른 입력란을 건드릴 때마다 매 정착 25바퀴 진동이 영구 재발. [확인]

#### 시나리오 3. 경합 패배 에지 소비로 인한 조용한 정지 (위험 표 5번)

**최소 JSON Schema 조각** — 대상 `result`에 자기 파생(`&derived`)과 외부 주입(`&injectTo`)이 동시에 선언되고 중간 조건 플래그 `isOverride`가 동적으로 변하는 스키마: [확인]

```json
{
  "type": "object",
  "properties": {
    "sourceInput": {
      "type": "number",
      "&injectTo": { "target": "../result", "value": "../sourceInput" }
    },
    "isOverride": { "type": "boolean", "&derived": "../sourceInput > 100" },
    "result": {
      "type": "number",
      "&default": 0,
      "&derived": "../isOverride ? 999 : undefined"
    }
  }
}
```

**초기 상태:** `sourceInput = 10`, `isOverride = false`, `result = 10` (안정 상태). [확인]
**사용자 행동:** `setValue({ sourceInput: 200 }, SetValueOption.Merge)`. [확인]

1. **[라운드 0: 표시/계산]** `raw.sourceInput = 200`. 파생 전이므로 `local.isOverride = false`. [확인]
2. **[라운드 1: 파생 — 경합 발생 및 패배]**
   - `sourceInput`의 `&injectTo`: 원천 변화(10→200) 감지, `result`에 `200` 쓰기 후보 등록.
   - `isOverride`의 `&derived`: 원천 `sourceInput` 변화 감지, `isOverride`에 `true` 쓰기 후보 등록.
   - `result` 자신의 `&derived`: 직전 계산의 `isOverride`가 아직 `false`이므로 무쓰기 또는 유지.
   - 동일 대상 경합 시 설계 규칙("같은 대상에 대해 `&derived` > `&injectTo`. 진 쓰기는 버리고 그 에지도 소비한다. 소비하지 않으면 다음 라운드에 진 규칙이 이겨 순위가 무의미해진다" — `03-mental-model.md` 4절, 소유자 답변 9항 도출) 적용.
   - 결과: 경합에서 밀린 `&injectTo`의 쓰기 후보(200)는 버려지고, **`sourceInput=200`에 대한 `&injectTo`의 에지는 영구히 소비 완료 처리됨**. [확인]
3. **[라운드 2: 표시/계산]** `raw.isOverride = true` 반영. [확인]
4. **[라운드 2: 파생]** `isOverride=true`이므로 `result`의 `&derived`가 동작해 `result = 999` 씀. [확인]
5. **[이후 조용한 누락 발생]** 사용자가 `sourceInput`을 50으로 낮춤.
   - 라운드 1: `isOverride`가 `false`로 갱신.
   - 라운드 2: `isOverride=false`이므로 `result`의 `&derived`는 해제되어 더 이상 999를 강제하지 않음.
   - 작성자 의도: 제약이 풀렸으므로 `sourceInput=50`이 `result`에 주입되어야 함.
   - 실제 동작: 라운드 1에서 이미 `sourceInput=50`에 대한 `&injectTo` 에지가 평가되었으나 당시 `isOverride`의 잔여 영향으로 경합에서 패배해 버려졌고, **그 에지가 이미 소비되었음**. 따라서 라운드 2에서 `sourceInput`의 `&injectTo`는 재발화하지 않음. [확인]

**문제 지점:** "진 규칙의 에지도 소비한다"는 규칙 때문에, 동일 정착 루프 내 의존성 선후 관계(조건 플래그가 최종 계산되기 전의 중간 라운드)로 인해 일시적으로 경합에서 패배한 주입 쓰기가 영구히 기회를 박탈당함. 조건이 올바르게 정돈된 뒤쪽 라운드에서도 에지가 이미 소멸하여 침묵하며, 최종 방출 값에 사용자의 최신 입력이 반영되지 않은 채 정착이 끝남. [확인]
**관여 예산:** 어떠한 예산도 초과하지 않음. 호스트 바퀴/파생 라운드 예산이 전혀 소진되지 않고 2~3라운드 만에 **정상 안정(`diagnostics.status = 'stable'`) 상태로 조용히 종료**됨. 예외도 콘솔 경고도 없어 작성자와 사용자는 값 누락 사실 자체를 인지할 수 없음. [확인]
