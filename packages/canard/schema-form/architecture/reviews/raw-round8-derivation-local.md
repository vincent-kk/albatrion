### 1.2 분류: NARROWED

지워진 것은 넷입니다. (b) 투영은 7라운드에서 이미 지워졌습니다. 편집 가능한 입력의 레벨은 `03:90`과 T-2로 지워집니다. 쓴 주체에 따라 방아쇠를 가르거나 두 모드를 한 장치에 두는 안은 G4 `:54`로 지워집니다. `injectTo`와 로드 규칙이 다른 a1은 G4와 7라운드의 한 규칙 조건으로 지워집니다. a1과 a2 사이는 축이 가르지 못합니다.

**남는 한 문장(예/아니오):** "파생 필드는 사용자와 호출자가 무엇을 쓰든 언제나 식의 값이어야 하는가(그 입력은 읽기 전용)?" 예 → a2. 아니오 → a1이고, 그 로드 동작은 Q2의 답을 따릅니다.

**반대 가치와의 관계.** 로드 반대 가치에 "아니오"(로드한 값을 작성자 규칙이 덮지 않는다)로 답하면 **a2가 지워집니다.** 레벨은 정의상 로드한 파생 필드의 값을 그 정착에서 f(의존)으로 덮기 때문입니다. 그러면 a1 + fill이 남습니다. "예"면 위 한 문장이 그대로 남습니다.

- 소유자가 G2의 "지금의 표현력"을 공개 문서의 약속으로 읽는다고 확인하면, a1이 G2 위반이 되어 **a2로 도출됩니다.** 코드로 읽는다고 확인하면 a2가 식 기반 편집 가능 파생을 잃습니다. 그래도 `injectTo`가 그 동작을 함수로 떠맡으므로 a2가 곧바로 지워지지는 않습니다.

## 2. Q2 (D-27) — `injectTo`가 마운트·`reset`·호출자의 전체 교체에서 발화하는가

### 2.1 도출 사슬

1. **D-13(축, `round-7:34`):** 에지 발화의 기준은 직전 커밋입니다. D-13은 전이 주입(E2)과 `injectTo`(E3)를 **한 기준 규칙**으로 다뤘습니다.
2. **마운트에는 직전 커밋이 없습니다.** 그래서 D-13을 문자 그대로 적용하면 값이 있는 모든 원천은 "없음에서 바뀜"이고 발화합니다. 규칙을 더하지 않아도 이렇게 됩니다. 프로토타입의 기본값 근거도 같습니다(REPORT `:48`). 오늘 코드도 마운트에서 발화합니다. 생성자가 기본값을 `Default` 옵션으로 쓰는데(`StringNode.ts:43,117`), 그 옵션에는 `PreventInjection`이 없습니다(`value.ts:51`). 테스트도 마운트 뒤 `'from:seed'`를 단언합니다(`ObjectNode.branch.nullable.interface.test.ts:355-373`, 단언만 읽음).

4. **마운트가 아닌 전체 교체에 D-13을 문자 그대로 적용하면 `ref`가 됩니다.** 교체 전 커밋과 비교하는 것입니다. `03:83`은 "이력을 읽어 '방금 있던 키'를 구별하면 P3 위반"이라 합니다. 그래서 `ref`는 지워집니다(`round-7:63`, 실행 증거 X3L `REPORT:94`). 전체 교체에서는 기준을 교체 전 상태가 아닌 다른 것으로 정의해야 합니다. 후보는 둘입니다.
   - (fire) 기준을 **비웁니다**(없음). 마운트에서 D-13이 문자 그대로 내는 결과와 같습니다. 같은 D-13 규칙 아래의 다른 에지 장치인 전이 주입에 쓴 관례와도 같습니다(F4 "전체 교체는 전이 기준을 비운다", `adr/0007:79`, 증거).
   - (skip) 기준을 **로드 결과 자신으로** 둡니다. 이 관례는 마운트에서 D-13의 문자 그대로의 결과와 다릅니다. 그래서 마운트를 포함한 모든 로드에 새 정의("로드의 직전 커밋은 로드한 상태다")가 필요합니다.
5. **skip은 G2(`00-goals:38`)로 지워집니다.** 공개 문서는 `injectTo`의 용도를 "Initial copy, default seeding"이라 적습니다(`inject-to.md:10`). 오늘 코드는 마운트에서 그대로 합니다(2번의 테스트). skip이면 원천의 로드 값이나 `default`에서 대상을 초기화하는 표현이 사라집니다. 대상의 `default`는 원천에 따라 동적으로 정할 수 없으므로 대체 수단이 없습니다. 6. **fill은 초안 P2 아래에서 G4로 지워집니다.** `injectTo`의 쓰기는 대상에 대한 전체 교체입니다(`03:43`). fill은 로드일 때만 "없음인 대상에만" 쓰는 둘째 쓰기 모드를 만듭니다(G4 `:54`). fill을 받치는 문장은 `03:82` "있는 값을 고치지 않는다"뿐입니다. 그런데 그 줄은 D-5(core의 `default`)에 걸려 있고 근거가 P2 "core가 스스로 원본을 고치는 일은 없다"입니다. `injectTo`는 core가 아니라 작성자의 쓰기이고, 발화할 때마다 대상의 값을 덮는 것이 그 정의입니다. 그래서 `03:82`는 `injectTo`에 닿지 않습니다. `injectTo`를 늘 fill로 바꾸는 안도 있습니다. 이 안은 "once per change"(`inject-to.md:3`)의 뜻을 없애므로 G2로 지워집니다.

### 2.2 분류: NARROWED, 초안 축 아래에서는 fire

- skip은 G2와 D-13으로 **어느 경우에도 지워집니다.** `ref`와 마운트·reset별 규칙은 7라운드에서 이미 지워졌습니다.

**남는 한 문장:** "로드(마운트·`reset`·호출자의 전체 교체)에서는 작성자가 선언한 규칙도 호스트가 준 값을 덮지 않는다는 문장을 P2에 넣는가?" 아니오 → fire, 예 → fill.

## 3. Q3 (D-29) — 같은 자식에 `default`를 선언한 조각이 여럿일 때

### 3.1 도출 사슬

1. **D-12(축, `round-7:33`):** 승자는 "최종 형상의 유효 스키마가 가진 `default`"입니다. 그래서 Q3은 곧 유효 스키마(`node.jsonSchema`)의 병합 정책에서 `default`가 어느 쪽인가입니다. 이 질문은 `adr/0005:109`가 이미 소유자에게 남겼습니다.
2. **충돌은 동시에 활성인 연언 조각 사이에서만 납니다.** 같은 `oneOf`/`anyOf`의 분기는 둘이 함께 켜지지 않기 때문입니다(`adr/0002:53-54`, 증거). 예는 기본 `properties` 대 `then`, 또는 `allOf[i]` 대 `allOf[j]`입니다.
3. **G4(`00-goals:52`) "한 개념에 한 장치":** "함께 활성인 조각들이 같은 주석 키워드에 다른 값을 줄 때"는 한 개념이고, 유효 스키마의 병합기는 한 장치입니다.
   - 오늘 코드는 주석 무리(`title`·`description`·`$comment`·`examples`·`default`·`readOnly`·`writeOnly`·`format` …)를 한꺼번에 먼저-승으로 처리합니다(`constants.ts:8-20`, `default`는 `:13`).
   - 프로토타입의 나중-승은 `default` 하나에만 걸려 있습니다(`round-4-spec.md:36`, `LV4C:1121`). 그러면 `default`만 무리에서 떨어져 나와 규칙이 둘이 됩니다.
   - **`default` 혼자 나중-승인 안은 지워집니다.** 남는 질문은 무리 전체의 방향입니다.
4. **방향. 전순서의 존재는 방향을 정하지 않습니다.** 전순서(`adr/0002:51`, 증거)는 먼저-승과 나중-승 모두를 결정적으로 만듭니다. 설계 안의 선례도 갈립니다. 종류 충돌은 앞선 선언이 이깁니다(`adr/0005:64`). 그 밖의 키(`FormTypeInput`·`options`·`computed`·`&`)는 나중이 이깁니다(`adr/0005:109`, `processOverwriteFields`). D-14′의 후보 "선언 순서 첫 분기"(`round-7:58`)는 미결입니다.
5. **G3(`00-goals:43-48`):** 표준은 승자를 정하지 않습니다. JSON Schema에서 주석은 모두 수집되고 선택은 응용의 몫입니다(Validation 2020-12 §9.2, 원문 미열람). 그래서 G3은 가르지 못합니다.
6. **G8(`00-goals:92`) "독자적인 방식은 보편적인 방식이 목표를 해칠 때에만":**
   - json-schema-merge-allof는 "For meta keywords like title, description, $id, $schema, default the strategy is to use the first possible value if there are conflicting ones"라고 적습니다(npm·GitHub README 검색 요약).
   - RJSF는 `retrieveSchema`에서 이 라이브러리의 `mergeAllOf`로 합칩니다(rjsf-team/react-jsonschema-form 이슈 #5292와 #3258의 코드 인용).
   - Ajv `useDefaults`도 "없는 키에만 채움"이므로 평가 순서상 먼저 평가된 `default`가 이기는 효과를 냅니다. 이것은 실행하지 않은 추론입니다.
   - 먼저-승이 해치는 목표를 찾아봤습니다. G2 표현력은 잃지 않습니다. "조건일 때 T, 아니면 B"는 기본 `default`를 빼고 `then`/`else`에 나눠 적으면 됩니다. 그러므로 나중-승은 이름 붙일 수 있는 목표 없이 택하는 독자적 방식입니다.

주석 키워드 무리 전체에 먼저-승 규칙 하나를 둡니다. 결과는 오늘 코드와 같습니다.

## 4. Q4 (D-31) — 자동 쓰기의 고정점이 예산 안에 수렴하지 않을 때 무엇을 커밋하는가

### 4.1 무엇이 돌고 있는가

v4d의 모델은 x₀ = B(명시적 쓰기를 표시한 원본)이고, x_{k+1} = B ⊕ W(shape(x_k))입니다. 수렴은 x_{k+1} = x_k일 때입니다(REPORT `:27-29`, D-25 `round-7:103` 증거). 비수렴이란 예산(ROUND_CAP 25) 안에 그런 x가 없다는 뜻입니다. 이런 경우 **어떤 선택지도 P6 (i)을 만족할 수 없습니다.** "자동 쓰기는 최종 형상의 함수"(`round-7:42`)를 만족하는 상태가 정의상 없기 때문입니다. 그래서 도출은 "어느 선택지가 축 문장을 **문자 그대로** 어기는가"로 합니다.

### 4.2 도출 사슬

## 5. Q5 (D-32) — `extras`의 방출 순서

### 5.1 도출 사슬

1. **`extras`는 상태입니다.** "호스트가 받은, 어디에도 선언되지 않은 키"입니다(`03:24,34`). 축은 이 칸이 순서를 가지는지 말하지 않습니다.
2. **P3(`03:11`)는 이 질문에 닿지 않습니다.** P3의 대상은 형상, 곧 "어떤 조각이 켜져 있고 어떤 자식이 존재하는지"입니다. 키 순서는 형상이 아닙니다. 6라운드 #44가 말한 "삽입 순서 = 이력 → P3 위반"은 P3의 범위를 넘어선 읽기입니다. 순서를 칸의 상태로 두면, 그 순서는 쓰기가 만든 상태입니다. 원본 값이 쓰기의 결과인 것과 다르지 않습니다. `Merge`가 새 키를 뒤에 붙이는 것은 (직전 상태, 쓰기)의 결정적 함수이므로 G5(`00-goals:65`)도 지켜집니다.
3. **P2와 수락 결정 "core는 받은 값을 고치지 않는다"(`HANDOFF:27`)도 정렬을 지우지 못합니다.** 방출 때 정렬하는 것은 `raw`와 `extras`를 건드리지 않는 투영이고, P4(`03:12`)가 허용하는 종류입니다. 게다가 설계와 코드는 이미 선언 키를 스키마 순서로 재배열합니다(`adr/0007:55` 증거, `BranchStrategy.ts:246` → `sortObjectKeys.ts:274-281`). 즉 순서는 이미 "값이 아닌 것"으로 다뤄집니다. G1(`00-goals:19`)과도 무관합니다. JSON 객체는 순서가 없고(RFC 8259 §4, 원문 미열람) 검증 판정은 순서에 무관합니다.
4. **남는 판별자는 G8(`00-goals:92`)과 G6(`:75`)입니다.**
   - 정렬은 방출을 다시 만들 때마다 extra 수 k에 대해 O(k log k)입니다. 받은 순서를 두는 쪽은 추가 비용이 없습니다. G6이 약하게 받은 순서 쪽입니다.
   - JS/JSON 생태계의 관례는 받은 객체의 own-key 순서를 보존하는 것입니다. `JSON.parse`는 문서 순서를 보존하고, 전개와 `Object.assign`은 새 키를 뒤에 붙입니다(ECMAScript OrdinaryOwnPropertyKeys, 원문 미열람). 조사한 폼 라이브러리 가운데 데이터 키를 정렬한다는 문서는 없습니다. 다만 이것을 직접 조사하지는 않았습니다(`raw-round7-prior-art.md`에도 없음).
   - 오늘 코드도 그렇게 합니다. 선언 키를 스키마 순서로 놓은 뒤, 나머지 키를 입력 객체의 `Object.keys` 순서로 놓습니다(`sortObjectKeys.ts:284-292`). 입력은 `Overwrite`면 V 자체이고(`BranchStrategy.ts:230-231`), `Merge`면 `{...base, ...draft}`입니다(`:236`).
   - 정렬이 받은 순서 대신 막아 주는 목표는 없습니다(위 2·3). 그러므로 정렬은 G8의 "독자적 방식"입니다.
5. **실현 가능성의 제약.** 방출은 평범한 객체이므로 정수 모양의 키(`"1"`, `"2"`)는 어떤 규칙을 두어도 엔진이 앞에 오름차순으로 놓습니다. 그래서 규칙은 "ECMAScript own-key 순서"로 적어야 합니다. 이 제약은 선언 키의 "스키마 선언 순서"(`adr/0007:55`)에도 똑같이 걸립니다.

### 5.2 분류: DERIVED(확신 중)

받은 객체의 키 순서를 상태로 둡니다.
- `Overwrite`(마운트·`reset` 포함)면 V의 own-key 순서가 상태가 됩니다.
- `Merge`는 있는 extra 키의 자리를 지키고, 새 키를 그 호출의 V 순서대로 뒤에 붙입니다.
- `removeKey` 뒤에 다시 들어온 키는 끝에 섭니다.

### 5.3 생각을 바꿀 조건

소유자가 "방출은 키와 값의 **집합**만의 함수여야 한다(같은 집합이면 같은 직렬화)"를 원리로 세우면 정렬로 뒤집힙니다. 이는 P3를 형상에서 방출 전체로 넓히는 새 문장입니다.

### 5.4 결과

- 코드는 바뀌지 않습니다.
- Q14(`open-questions.md:86-88`)와 `adr/0007:55`의 "잠정"을 닫습니다. `adr/0007:55`에는 정수 모양 키의 예외를 한 줄 더합니다. 7라운드 §8 203·215행의 D-32 부분이 풀립니다.

### 5.5 가설 점검

- "받은 객체의 키 순서는 이력이 아니라 상태다": **맞습니다.** 다만 이는 모델링의 선택이고, 그 선택을 강제하는 것은 G8입니다.

## 6. Q6 (D-22′의 일부) — `settle.status`가 `budget-exceeded`일 때 제출을 막는가

### 6.1 도출 사슬

1. **G1(`00-goals:19`)의 보증은 어느 쪽에서도 지켜집니다.** 제출값과 검증값은 모두 `emit`입니다. P1(`03:9`) "폼의 판정 = `validator(작성된 스키마, 방출 값)`"가 그렇게 정하고, 오늘 코드도 그렇습니다(`Form.tsx:116-117`). 그래서 "폼이 통과시킨 값을 서버가 기각하는 일은 없다"는 예산 초과에서도 성립합니다. 차단이 G1을 지키려고 필요한 것은 아닙니다.
2. **G1 `:23`은 차단을 허용합니다.** "폼이 더 엄격해지는 것은 허용되지만, 표준 판정에 AND로 덧붙는 형태로만"이라 합니다. 폼 자신의 조건 하나를 AND로 얹는 차단은 이 모양에 맞습니다. 그러므로 "P1 ⇒ signal만"은 도출되지 않습니다. P1의 등식은 **판정**(값이 옳은가)에 관한 것입니다. `budget-exceeded`는 값의 옳고 그름이 아니라 엔진의 정착 상태에 관한 사실입니다.
3. **지워지는 차단은 셋입니다.**
   - (i) `budget-exceeded`를 **검증 에러 목록에 섞어서** 막는 것. 그러면 폼의 에러 목록이 검증기의 출력과 달라집니다. P1(`03:9`)과 G1 "판정의 동치"(`:19`)에 걸립니다. C2(`00-goals:103`)가 허용하는 것은 폼 수준의 **표시**이지 판정 목록의 변조가 아닙니다.
   - (ii) **core가** 막는 것. 제출은 Form 바인딩의 API입니다(`Form.tsx:114-125`, `FormHandle.submit` `Form/type.ts:127`). core는 렌더러의 명령을 모르고(P5 `03:13`), core 수준 관측은 루트 `settle` 읽기와 `UpdateSettle`로 도출돼 있습니다(`round-7:40`).
   - (iii) `settle`의 **모든** 비정상 상태에서 막는 것. 한 칸에는 예산 여러 개가 담깁니다(`adr/0008:77`, P7 재진술 `round-7:45`). 틱당 파동 상한은 리스너 쓰기를 거부하므로 통지되지 않은 쓰기가 남지 않습니다(`adr/0008:62`). `onchange-cap-exceeded`는 쓰기를 적용하고 검증도 요청합니다(`adr/0008:93`). 둘 다 커밋된 `emit`의 내용과 무관한 통지 예산입니다. 여기서 막으면 제출 가능 여부가 호스트의 리스너 코드에 달립니다. 그래서 차단을 택하더라도 그 조건은 커밋된 내용을 바꾸는 예산(호스트 바퀴, 자동 쓰기 라운드)으로 한정됩니다.
4. **signal 쪽으로 기우는 근거(지우지는 못함).**
   - 오늘 제출 관문은 검증기 판정뿐입니다(`Form.tsx:117-123`).
   - D-2의 소유자 열은 "프로덕션 **관측**"입니다(`HANDOFF:38`).
   - D-16(`round-7:36`)은 예산 초과에서도 프로덕션이 커밋 → 검증 → `onChange`를 평소대로 밟게 합니다.
   - C2의 소유자 말은 "에러들의 **출력**을 … 확장하자"입니다(`00-goals:103`).
   - signal만 두어도 호스트는 도출된 core 관측으로 스스로 막을 수 있습니다. 표현력을 잃지 않습니다. 반대로 기본으로 막으면, 검증기를 통과한 값을 제출하려는 호스트에게 끄는 옵션이 하나 더 필요해집니다.

## 7. 반대 가치 — "작성자가 선언한 규칙이 로드한 데이터를 덮어도 되는가"

- **P2가 이미 답하는가:** 초안 P2(`03:10`)는 쓰기 주체를 넷(D-11 뒤 다섯)으로 적습니다. 작성자에게 순위나 로드 예외를 두지 않습니다. "core가 스스로 원본을 '고치는' 일은 없다"는 **core**의 쓰기에 대한 문장입니다. 로드 계약의 "있는 값을 고치지 않는다"(`03:82`)도 D-5, 곧 core의 `default`에만 걸려 있습니다. `injectTo`는 발화할 때마다 대상의 있는 값을 덮는 것이 정의입니다(`03:43`, `inject-to.md:3`). 그러므로 **초안 P2 아래에서 답은 "예"입니다.** 권한 문제는 이미 닫혀 있고, 남는 것은 "로드가 발화 계기인가"라는 방아쇠 문제뿐입니다.
- **다만 P2 자체가 확인 대기입니다**(`03:107`; 7라운드 §4-2 `round-7:75`). 소유자가 P2를 확인하면서 "로드에서는 작성자 규칙도 호스트가 준 값을 덮지 않는다"를 더할 수 있습니다. 이 한 문장이 곧 반대 가치입니다.
- **의존 관계.**
  - Q2가 직접 걸립니다. 아니오 → fire, 예 → fill입니다. skip은 어느 쪽에서도 G2로 지워집니다.
  - Q1은 절반이 걸립니다. "덮지 않는다"를 더하면 a2가 지워지고 a1 + fill이 남습니다. 더하지 않으면 Q1의 한 문장이 남습니다.
  - Q3–Q6은 무관합니다. Q4의 β는 비수렴에서 작성자 쓰기까지 빼는데, 이는 로드 권한이 아니라 D-12에서 나옵니다.
- **G4 결합.** 이 문장을 더하면 로드에서의 자동 쓰기(`default`·`injectTo`·a1 `&derived`)가 모두 "없음에만"이라는 한 규칙이 됩니다. 더하지 않으면 `default`는 없음에만, 작성자 규칙은 덮어쓰기로 갈립니다. 이 갈림은 P2의 쓰기 주체 구분(core 대 작성자)을 그대로 따르는 것이므로 특수 경로가 아닙니다.
