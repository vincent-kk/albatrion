## 진술별 근거

**1. if/oneOf 비해석, const·enum 판별식 금지 — 충돌**
- 반영: adr/0002:16 "`if` 블록의 스키마로 값을 검증해, 통과하면 `then` 절을 자식에 적용한다." / 05:14 "폼은 `if`의 뜻을 해석하지 않는다" / adr/0009:90 "`const`/`enum` 판별식의 직접 비교는 넣지 않는다".
- E14(adr/0005:71-81)는 const/enum에서 식별합니다. adr/0005:79 "어떤 프로퍼티 이름 `k`를 **모든 분기**가 `const` 또는 `enum`으로 제약하면 후보다." 5단계 우선순위는 adr/0005:81 "(`discriminator.propertyName` > `required`에 포함 > 사전순)"입니다.
- 이 식별을 P1′ 안에 넣은 근거: adr/0005:90 "`const`/`enum`의 **값**을 읽는 것은 형상을 만드는 최소한의 읽기이므로 P1′ 안에 있다. 소유자: \"`oneOf`/`anyOf`에서 `enum`/`const`를 사용하는 폼 제어 같은 간단한 건 넣을 수도 있다.\"" 진술 1의 "쓰지 않는다"는 이 인용과 정면으로 반대입니다.
- 소유자 방향으로 기록된 문장도 반대입니다. adr/0002:17 "`oneOf`/`anyOf`는 `const`/`enum`을 쓰는 제한적 적용만 지원한다."
- 분기 선택의 현재 서술:
  - 판별식 분기는 값 가드입니다. adr/0002:39 "분기의 판별식 부분 + 그 프로퍼티의 `required` (**값 가드**)".
  - 비판별 분기는 선택 가드입니다. adr/0002:40 "`selection === i` (**선택 가드**, 폼 상태)".
  - 초기 선택: adr/0002:126 "값의 키 가운데 가장 많이 선언한 통과 분기를 고른다. 동점이면 앞의 분기."
  - 06:140 D-14 "선언된 키 수와 선언 순서만 쓴다."
  - 06:309 5.5 "(가) 선언 순서의 첫 분기를 폼이 고른다 … (나) 분기 없음."
  - 06:344 N2 "명령 `setSelectedBranch(index)`, 상태 칸의 공개 이름 `selectedBranch`."
- 모호점: "스키마를 사용하는 분기는 모두 if 블록"은 두 가지로 읽힙니다. 첫째는 `allOf`+`if/then` 관용구로, adr/0002:106이 이미 필수 지원이라고 적었습니다. 둘째는 `oneOf` 분기 안의 `if`인데, 이 경우 adr/0002:107 규칙 3과 부딪힙니다: "`if`만으로 분기를 구분한 `oneOf`/`anyOf`는 값 가드가 되지 못한다 … 둘 다 통과해 `oneOf`가 기각된다." "oneOf/anyOf도 블록 활성 여부만 본다"는 분기 전체를 검증기로 가드하는 방식으로 읽힐 수 있습니다. 그런 설계 문장은 없습니다.
- 닿는 항목:
  - 06:100 3.4 "판별식 식별을 위한 `const`·`enum` 값 읽기는 형상 읽기에 든다"를 진술 1이 뒤집습니다.
  - 4.4 D-14의 "키 수 점수"가 폼 자신의 분기 선택인지를 "활성화되는지만 본다"가 건드립니다.
  - 판별식이 사라지면 모든 union이 비판별이 되어 5.5의 범위가 모든 union으로 넓어집니다.
  - N2가 유일한 선택 경로가 됩니다.

**2. 조건 프로퍼티는 `properties`에 선언 — 새것**
- 요구하는 문장은 어디에도 없습니다. 반대 방향 문장: adr/0005:87 "기본 `properties`에 `k`가 선언되어 있는지는 묻지 않는다. **판별 프로퍼티 k는 union 호스트가 소유한다**".
- 받쳐 주는 문장: adr/0002:109 "기본 `properties`에 선언된 프로퍼티는 **항상 존재한다** — 끄는 조각이 없다."
- `extras`를 조건 입력으로 다룬 문장은 없습니다. 다만 가드는 방출 값을 보고(adr/0002:60), 방출에 `extras`가 들어갑니다(adr/0006:50, adr/0013:64 "스키마가 선언하지 않은 키는 방출된다"). 그래서 지금 설계에서는 미선언 키가 `if`를 움직일 수 있습니다.
- 강제 방식과의 긴장이 있습니다. 규칙을 검사하려면 `if`가 무엇을 참조하는지 읽어야 합니다. 그런데 adr/0005:52 "가드가 무엇을 읽는지는 기본적으로 뽑지 않는다", adr/0002:161 "경고하려면 `if` 내부를 읽어야 하므로 P1′와 닿는다", adr/0009:89 "폼이 `if`의 프로퍼티 이름을 읽어야 한다"가 그 반대편에 있습니다. 컨벤션으로만 둘지 개발 모드에서 검사할지는 정해지지 않았습니다.
- 닿는 항목:
  - §7 D-15(06:398 "`if`가 `x`를 요구하고 `then`이 `x`를 선언하는 부정 없는 순환")는 진술 2 아래에서 작성자 오류가 됩니다.
  - 4.15–4.17의 자기 가드 `default`에서는 x가 본체에 있어도 `then`의 `default` overlay로 순환이 남을 수 있습니다. 이 부분은 가설이고 실행하지 않았습니다.
  - 조건 필드가 항상 본체에 있으므로 5.3의 본체 대 조각 주석 키워드 대결이 반드시 생깁니다.

**3. then/oneOf/allOf/anyOf의 노드 선언 — 이미 반영**
- adr/0002:140 소유자 "then / else에서 신규 노드를 선언할 수 있어." / adr/0005:42 "\"`properties` 밖에도 노드가 있다\"는 … 청사진의 `declares`를 읽는 일반 경로가 된다." / adr/0002:37-40(`allOf` 항목, 분기) / 05:221.
- 진술 2 외의 선언 금지는 설계에 없습니다. adr/0005:62-64는 같은 이름 규칙이지 금지가 아닙니다.
- 닿는 항목: 5.3(조각이 선언한 주석 키워드가 본체를 덮는가).

**4. jsonSchema 변환에서 값 조작 금지 — 부분 반영, 전이 주입과 조건부 충돌**
- 반영:
  - adr/0013:24 "core는 받은 값을 고치지 않는다."
  - 03:49 "**비활성화는 쓰기가 아니다**"
  - adr/0002:88 "BE가 거부하려던 값을 폼이 조용히 지우는 것은 P2 위반이다"
  - adr/0002:118 "폼은 값을 만들지 않는다."
  - adr/0002:128 "초기 선택은 노드의 원본을 바꾸지 않는다."
- 전이 주입은 설계가 스스로 core의 값 쓰기라고 부릅니다.
  - 06:37 "코어가 스스로 하는 유일한 자동 쓰기다"
  - 06:38 "조각이 꺼짐에서 켜짐으로 바뀔 때 그 조각이 선언한 `default`를 넣는 것"
  - 03:45 "core (P2의 유일한 자동 쓰기) … 조각이 꺼짐 → 켜짐으로 바뀐 직후"
  - adr/0007:81 "core가 스스로 원본에 쓰는 것은 `default` 주입 하나다"
  - 설계의 정당화는 adr/0013:57 "있는 값은 고치지 않는다 — 주입은 \"없음\"인 키에만 간다"입니다.
- 진술 4의 "필드 노출 변환"이 없음인 키에 대한 `default` 채우기까지 포함하는지는 소유자의 읽기 문제입니다. 포함한다면 충돌입니다.
- 비활성 조각의 방출 제외(adr/0013:25 "예외는 하나다 — 비활성 노드의 값은 방출에서 빠진다")도 스키마가 방출 값을 바꾸는 경우입니다. 소유자가 이미 받아들인 적이 있습니다. adr/0013:12 "field가 가려지면서 node가 deactive 되면서 값을 빼내는 걸 제외하고는".
- 닿는 항목:
  - 4.2 D-12는 전이 주입이 존속할 때만 의미가 있습니다. 06:123 "승자는 최종 형상의 유효 스키마가 가진 `default`다."
  - 4.3의 반례 E2가 전이 `default`에서 생깁니다.
  - 4.11의 원본 B는 전이 주입을 포함한 자동 쓰기를 뺀 원본입니다.
  - 4.15–4.17과 3.6은 모두 전이 `default` 사례입니다.
  - 4.14 D-5와 N1 `DisableSchemaDefaults`는 끌 대상이 줄어듭니다.
  - 5.3은 켜질 때 주입할 `default`의 승자를 묻습니다.

**8. `&`·`injectTo` 예약어화, 위계·타이밍, 이름 통일 — 부분 반영**
