# 167라운드 닫기 — 감사 차이 4(onStateChange의 global state flag)는 두 판 모두 런타임이 false를 쓴 적이 없으므로 형만 0.16.0과 같은 `Readonly<Record<string, boolean | undefined>>`로 되돌린다(런타임 불변, 판정 세션 없음); 키가 사라지는 시점의 차이(0.16.0은 루트를 통째로 비울 때까지 남음, 새 판은 마지막 노드가 flag를 끄면 바로 사라짐)는 새 판을 유지한다 — 새 판이 "지금 그 flag를 가진 노드가 있는가"를 정확히 말하고, 옛 판의 남음은 additive patch의 한계였다

2026-10-12. 07b-1이 166라운드 (ㄱ)의 사실과 변경 범위를 올렸다. 사실: 0.16.0의 global state는 shallowPatch(base, input, additive = true)로만 갱신되고(dist/index.mjs:3497) additive 모드는 값이 truthy일 때만 키를 쓰므로(:3303-3307) setState({ dirty: false })의 false는 반영되지 않고 키는 true로 남으며, 키는 루트의 clearSubtreeState로 통째로 비울 때만 사라진다(:3514-3516, :3296) — 값은 true이거나 없음이었고 false는 런타임에 나온 적이 없으며 형은 boolean | undefined였다. 새 엔진은 키마다 truthy 노드 수를 세고(runtime.globalStateCounts) 수가 0이 되면 키를 지운다(`src/core/record/utils/publishGlobalStateDeltas.ts:15-20`) — 값은 true이거나 없음이고 false는 쓰지 않으며 형은 Readonly<Record<string, true>>다(`src/core/SchemaNode/type.ts:90`, 런타임 슬롯 `src/core/record/type.ts:348`). 노드 자신의 state(NodeStateFlags)는 새 판도 boolean | undefined이고 false를 받는다(`src/core/types/state.ts:29-34`); 바뀐 것은 global state뿐이다. 다른 의미 차이: 0.16.0은 한 번 켜진 global 키가 루트를 통째로 비울 때까지 남았고 새 엔진은 마지막 노드가 그 flag를 끄거나 형상에서 빠지면 키가 바로 사라진다(예: dirty였던 필드 하나를 setState({ dirty: false })로 되돌리면 0.16.0의 onStateChange는 { dirty: true }를 그대로 보고 새 판은 dirty 키 없는 객체를 받음). 변경 범위 제안: 형만 — SchemaNode.globalState를 Readonly<Record<string, boolean | undefined>>로, 문서 주석을 "값은 true 또는 없음으로 발행되며 형은 0.16.0과 같은 boolean | undefined"로; onStateChange는 SchemaNode['globalState']를 쓰므로 함께 바뀜; 런타임 슬롯의 Record<string, true>는 대입되므로 그대로; d.ts 차분 한 곳; 런타임 불변이라 방향 확인·정규화 비교·판정 세션 불필요; 검증은 d.ts 차분, 감사 runner에서 H18만 0.16.0 열과 같아짐, 세 값 전이 시험(없음 → true → 키 없음, state[flag] = false를 담은 소비자 코드의 컴파일); 파일은 커밋 1과 겹치지 않고 커밋 1의 비차단 반영 직후·측정 전에 끼워 넣음. 물음: 키가 사라지는 시점을 0.16.0처럼 남는 쪽으로 맞출지(07b-1은 새 판 유지를 권함; 맞추려면 쓰기 경로 런타임 변경과 판정 세션 필요).

### 167C-01 (1) 감사 차이 4의 고침은 제안대로 형만 바꾼다 — `Readonly<Record<string, boolean | undefined>>`, 문서 주석에 "발행되는 값은 true 또는 없음"을 적고, 검증은 d.ts 차분 한 곳·감사 runner H18·세 값 전이 시험이며 판정 세션은 없다; 166라운드 소유자 답("false도 유효값")은 형이 false를 받아야 한다는 뜻이고 두 판 모두 런타임은 false를 낸 적이 없으므로 이것으로 충족된다; (2) 키가 사라지는 시점은 새 판을 유지한다 — 0.16.0의 남음은 additive patch가 flag를 끄지 못한 한계의 결과이지 설계된 계약이 아니며, 새 판은 "지금 그 flag를 가진 노드가 있는가"를 정확히 말하므로 패키지 Design Values의 "일관되고 예측 가능한 동작"에 맞다; 이 차이는 onStateChange 소비자에게 보이는 동작 차이이므로 소유자에게 보고해 뒤집을 수 있게 하고, 뒤집히면 쓰기 경로 런타임 변경과 판정 세션으로 간다; (3) 의미 차이는 07b 문서 항목(개선-36)에 "global state 키는 마지막 노드가 flag를 끄면 바로 사라진다(0.16.0은 루트를 비울 때까지 남았다)"로 적는다; (4) 고침 커밋은 커밋 1의 비차단 반영 직후·측정 전에 끼워 넣는다

- 닫는 항목: TEST-070(보충), LANDING-204(보충)
- 결정:
  - 【추론】 166라운드에서 소유자가 바로잡은 것은 "false가 유효값인데 형이 그것을 없앴다"는 점이고, 사실 확인 결과 두 판 모두 런타임은 true 또는 없음만 냈으므로 형을 옛 판과 같게 돌리면 계약은 복원된다. 남는 차이는 "꺼진 flag의 키가 언제 사라지는가"인데, 옛 판에서 키가 남은 것은 additive patch가 false를 버린 부작용이라 옛 판 사용자도 그 값에 기대어 무엇을 했을 가능성이 낮고, 새 판 쪽이 정확하다. 다만 166라운드에서 소유자가 "옛 판이 내던 값을 새 판이 못 내는" 차이에 민감함을 보였고 이것은 그 반대(옛 판이 내던 낡은 값을 새 판이 안 냄)라 편집자가 정하되 보고한다.
