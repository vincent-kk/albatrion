### 86C-01 React 층 비교(85C-01 다)의 게이트 수치는 두 판에 같은 조건이 걸리는 React production 프로파일 빌드(`react-dom/profiling`)로 잰 것이고, 개발 빌드의 수치는 조건 차이(owner-stack 예산의 비대칭)를 적어 기록으로 둔다 — TEST-026의 "React 19, `<React.Profiler>`" 조건은 그대로이며 빌드만 둘 다에 공평한 것으로 고정한다

- 닫는 항목: TEST-026(보충)
- 결정:
  - 【추론】 TEST-026은 렌더 비교를 "React 19, `<React.Profiler>`의 커밋 수와 `actualDuration`"으로 정했고 빌드 종류는 적지 않았다. 비교의 뜻은 두 판을 같은 조건에서 견주는 것이므로, 한 판에만 걸리는 개발 빌드의 진단 비용(React 19의 owner-stack 예산: 1초 리셋, JSX 1만 개)이 수치를 가르면 그 조건은 비교에 맞지 않다. 그래서 85C-01 (다)의 게이트 수치는 `react-dom/profiling`(production 동작 + Profiler)로 두 판을 잰 것으로 하고, 개발 빌드의 수치는 같은 표에 "개발 빌드, owner-stack 예산 비대칭"을 적어 기록으로 둔다 — 소비자가 개발 중 보는 체감도 자료로 남기되 게이트에는 쓰지 않는다. 두 판의 진단 조건을 같게 통제하는 것은 React 내부 설정을 건드리는 일이라 택하지 않는다.
- 근거: TEST-026 "둘로 나눠 잰다. 코어(`node` 환경, 트리 생성·값 갱신·정착 시간)와 렌더(React 19, `<React.Profiler>`의 커밋 수와 `actualDuration`, `render-trace`의 번짐)"; 85C-01 (다); 07의 진단(배열 폼 React 층 초과 약 27 ms가 owner-stack 예산 분기의 차이, `branchless-phase-diagnosis.md`).

### 86C-02 순서는 코드 수준 후보(정적 첫 로드의 빠른 경로, 선언 재등록·경로 색인 공유, 빈 배달 작업 집합의 조건부 할당, 배열 렌더러의 memo 분리, 첫 로드의 형상·채움 순회 융합) → 재측정 → 구조 후보다 — 구조 후보 가운데 (b1) 청사진 분석을 최초 접근으로 미루는 것과 (b2) 즉시 전체 형상·채움을 지연 생성으로 바꾸는 것은 생성 때의 정적 오류(BLUEPRINT-001, ADR 0014의 생성 자리 포착)와 "생성이 곧 첫 정착"(GOAL-071 A3, P3)을 뒤집으므로 편집자가 열지 않고 재측정 뒤 남은 간극과 함께 소유자에게 올리며, (b3) 구독 노드만 payload는 65C-03의 거절이 그대로이되 `revision`은 모든 노드에서 그대로 올리고 EVENT-024의 `previous` 뜻을 지키는 좁은 변형이 있으면 설계안으로 올려 판단받는다

- 닫는 항목: BLUEPRINT-001(보충), GOAL-071(보충), EVENT-024(보충)
- 결정:
  - 【추론】 65라운드의 절차대로 구조 몫은 코드 전에 바꿀 설계와 뒤집힐 원장 항목을 올려 판단받고, 64라운드 위임은 "원장의 원칙대로"이므로 편집자가 열 수 있는 것은 현행 원칙 안의 변경뿐이다. (b1) 청사진의 정적 분석을 폼 생성 때 한 번 도는 것(BLUEPRINT-001)과 정적 오류를 생성 자리에서 잡아 대체 화면으로 가는 것(ADR 0014, 17라운드 스웜 수렴과 소유자 답 R17-1)은 "폼이 그려지기 전에 스키마의 잘못을 안다"는 계약이고, 분석을 최초 접근으로 미루면 그 오류가 어느 필드를 처음 만질 때 나타나므로 계약이 바뀐다 — 편집자가 열지 않는다. (b2) 즉시 전체 형상과 채움을 지연 생성·읽기 계산으로 바꾸는 것은 GOAL-071 "생성이 곧 첫 정착(A3)"과 상태 모형 P3(상태는 `raw`·`extras`, 나머지는 커밋된 계산값), `getValue`·`find`·렌더가 보는 시점의 계약을 뒤집으므로 역시 편집자가 열지 않는다. 둘은 코드 수준 후보와 재측정 뒤 목표(85C-01)에 못 미친 수치, 각 후보의 절감 상한(07의 보고서), 뒤집힐 항목 목록과 함께 소유자에게 올린다. (b3) 구독한 노드에만 `revision`·payload를 만드는 S4는 65C-03이 EVENT-001 #2("리스너 유무와 무관한 단조 카운터")·EVENT-007·EVENT-024를 뒤집는다고 거절했고 그 까닭은 그대로다; 다만 `revision`은 모든 노드에서 커밋 때 그대로 올리고(늦은 구독자의 갭 감지), 변하는 것은 "payload 객체의 생성 시점"뿐이며 EVENT-024의 `previous`("그 노드에 마지막으로 통지한 값")가 구독 전 변경에 대해 무엇이 되는지를 정의해 그 뜻을 지키는 좁은 변형이 있으면 07이 설계안으로 올리고 편집자가 판단한다 — 통지가 없던 노드의 payload를 미리 만드는 비용은 관측되지 않는 작업이므로 원칙 안에서 줄일 여지가 있다. 순서는 07의 권고대로 코드 수준 후보 → 같은 방법의 재측정 → (b3) 변형의 설계안 → 남은 간극은 (b1)·(b2)와 함께 소유자에게. EVENT-070 3번의 개발 모드 경고는 측정과 겹치지 않게 그 뒤에 넣는다.
