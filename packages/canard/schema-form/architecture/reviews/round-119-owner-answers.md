# 119라운드 — Vincent의 답 (React 바인딩 층은 컴포넌트 계층을 얇게 유지한다 — 계층이 깊어지면 그 자체로 지연이 크게 늘므로 옛 구현처럼 대부분의 기능을 훅에 넣고 스냅샷 ref 같은 기법으로 층을 더하지 않는다; 이 층의 분석은 코어와 달리 렌더 횟수와 리프레시 지연으로 한다)

2026-10-07. 118라운드의 React 층 진단이 실제로 늘어난 일을 "필드마다 fiber 계층 +5"(프록시의 Provider·경계 래퍼·경계, 필드 분리, 입력 경계의 세 층, 이중 구독, 자식마다 layout effect)로 가리고 경계 계층 축소(F2a·F2b)를 열자, 소유자가 옛 구현의 원칙을 말했다.

| React 층의 설계 원칙 | 필드당 컴포넌트 계층이 다섯 늘었다는 진단을 듣고 | "음 아, 이미 지나간거같은데, 그래서 이전 구현에서는 컴포넌트 계층을 얇게 가져가려고 노력을 많이 했었어. 컴포넌트 계층이 깊어지면 그 자체로 속도 지연이 엄청 늘어나서 말이야. 가능하면 컴포넌트 계층을 얇게 가져가는게 필요하고 이를 위한 snapshot Ref 라던가 하는 기법이 필요했었어. 이건 코어 레이어랑 다르게 랜더카운트와 리프레시 레이턴시를 분석해야해. 잘 알고있겠지만. 그래서 대부분 기능을 이전 구현처럼 hook에 넣고, 컴포넌트 계층을 얇게 유지할 필요가 있을거야" (2026-10-07, 원장 세션) | 확정. React 바인딩 층의 원칙: (1) 필드당 컴포넌트 계층을 얇게 유지한다 — 래퍼·경계·Provider·분리 컴포넌트로 층을 더하지 않고, 구독·메모·이펙트·경계 판정 같은 기능은 옛 구현처럼 훅과 스냅샷 ref(렌더 사이에 값을 ref에 두고 비교해 불필요한 렌더를 막는 기법)로 한 컴포넌트 안에서 처리한다; 계층이 꼭 필요한 자리(React가 요구하는 오류 경계 클래스, 문맥 제공)는 해석·소유 지점에서 한 번만 둔다(112C-01과 같은 방향). (2) 이 층의 성능 분석은 코어와 달리 시간만이 아니라 렌더 횟수(어느 컴포넌트가 쓰기 하나에 몇 번 렌더되는가)와 리프레시 지연(쓰기에서 화면 반영까지)으로 한다 — 118라운드의 컴포넌트·훅 단위 계수가 그 자리다. (3) F2a·F2b와 그 뒤의 후보(이중 구독, 자식마다 layout effect)는 이 원칙으로 설계한다: 목표는 필드당 계층을 옛 판 수준으로 되돌리는 것이며, 바인딩 계약(REACT-019·024, EVENT-039·040, 112C-01)은 그대로다. 이 원칙은 개선 단계의 React 층 정리에도 적용된다. |
| 노드 프록시 구조 | 얇은 계층 원칙을 기록한 뒤 | "그래. 이게 논리적으로나 구조적으로는 다중 컴포넌트를 구성하는게 맞는데, 리엑트 특성상 이게 너무 느리기도 하고, form 이 커질수록 진짜 기하급수적으로 느려져서 말이야. 그리고 각 컴포넌트는 개별 node의 이벤트로만 상태를 가지는 (일부 커스텀 override props를 제외하면. 기존 form 구현 참고) node proxy 구조를 가져야 고속성이 보장돼. 이건 거의 기존 구현이 정답에 가까울거야." (2026-10-07, 원장 세션) | 확정. (1) 논리·구조로는 다중 컴포넌트 구성이 옳으나 React의 특성상 계층이 깊으면 느리고 폼이 커질수록 기하급수로 느려지므로, 바인딩 층은 구조의 옳음보다 얇은 계층을 택한다. (2) 각 필드 컴포넌트는 노드 프록시 구조여야 한다 — 컴포넌트의 상태는 자기 노드의 이벤트(그 노드의 변경 비트·개정)에서만 오고, 부모·형제·전역 문맥의 변화로는 다시 렌더되지 않으며, 예외는 소비자가 넘기는 일부 커스텀 override props뿐이다(옛 구현의 `SchemaNodeProxy`가 기준). (3) 옛 구현이 이 자리의 정답에 가깝다: F2a·F2b와 뒤의 후보, 개선 단계의 React 층 정리는 옛 구현의 노드 프록시 구조를 기준으로 삼아 새 구현이 거기서 벗어난 자리(프록시 밖의 Provider·래퍼, 이중 구독, 자식마다의 이펙트, 부모의 렌더가 자식으로 전파되는 길)를 찾아 되돌린다; 바인딩 계약(REACT-019·024, EVENT-039·040, 112C-01)과 공개 API는 그대로다. 측정은 119라운드대로 렌더 횟수(부모 쓰기에 자식이 렌더되지 않음을 포함)와 리프레시 지연으로 한다. |
| 제어·비제어 호환과 속도 | 노드 프록시 구조를 기록한 뒤 | "그리고 이렇게 해야 제어컴포넌트-비제어컴포넌트 둘다 호환하도록 하면서 속도는 비제어에 준하게 만들 수 있단다" (2026-10-07, 원장 세션) | 확정. 노드 프록시 구조의 까닭: 각 필드가 자기 노드의 이벤트에서만 다시 렌더되면 소비자의 입력이 제어 컴포넌트든 비제어 컴포넌트든 같은 바인딩으로 호환되면서, 쓰기 하나에 그 필드만 렌더되므로 속도는 비제어에 준한다 — 부모나 전역 상태에서 값을 내려 주는 제어 구조는 쓰기마다 트리를 다시 렌더해 폼이 커질수록 느려진다. F2와 뒤의 후보의 판정에서 "쓰기 하나에 그 필드 하나만 렌더됨"이 이 원칙의 측정 가능한 형태다. |
| 컴포넌트 축과 갱신 축 | 원장 관리자의 반론 셋(깊이보다 전파가 원인, 경계는 훅이 될 수 없음, 옛 판의 미룬 커밋은 따라 하지 않음)을 들은 뒤 | "응 노드별로 라이프사이클을 따로 가져가서 노드트리가 모든 데이터를 관리하고, 실제로 리엑트 컴포넌트는 부모에 의해 렌더링은 되지만 리렌더링이나 상태변화, 업데이트 등은 노드에 의해 이루어지는거지. 이게 기존 설계의 컴포넌트 축 핵심이거든. 지금 만약 이벤트의 전파가 갱신영역을 최소화해서 진핸되는게 아니라 노드 트리 전반으로 퍼져나간다면 상당히 느려질거야. 아 그리고, 되도록이면 노드 트리 내에서 여러 웨이브로 업데이트가 이루어질 수 있잖아. 가능하면 그건 react에 영향을 안주었으면 하긴 해. 계산은 js에서 모델레벨에서 끝내고 fiber반영은 최소한으로 하도록 말이야. 이건 설계를 잘 해야 하긴 할텐데... fiber 반영과 dom 반영까지 가면 js 레벨 업데이트보다 압도적으로 시간을 쓰더라고. 물론, 어쩔 수 없는 경우(리엑트 컴포넌트가 값을 다시 쓰는 경우 등)는 제외지만." (2026-10-07, 원장 세션) | 확정. 두 축의 원칙. (컴포넌트 축) 노드 트리가 모든 데이터와 수명 주기를 갖고, React 컴포넌트는 부모가 처음 그리되 그 뒤의 다시 그리기·상태 변화·갱신은 자기 노드의 이벤트로만 일어난다; 쓰기 하나의 갱신 영역은 바뀐 노드의 컴포넌트로 최소화되어야 하며 트리 전반으로 퍼지면 안 된다. (갱신 축) 정착이 노드 트리 안에서 여러 웨이브로 돌더라도 중간 상태는 React에 닿지 않는다 — 계산은 JS 모델 수준에서 끝내고 fiber·DOM 반영은 최종 결과 한 번으로 최소화한다(fiber·DOM 반영이 JS 갱신보다 압도적으로 비싸다); 예외는 React 컴포넌트가 값을 다시 쓰는 것처럼 피할 수 없는 자리뿐이다. 새 엔진과의 대조: 갱신 축은 설계대로다 — 정착은 쓰기 안에서 모든 웨이브를 동기로 돌고 커밋에서 배달 집합의 revision을 한 번에 올리며(EVENT-007) React는 노드별 revision을 uSES로 읽으므로(REACT-024) 쓰기 하나에 커밋 하나다(118라운드: 옛 판 커밋 2, 새 판 1); 그러므로 옛 판의 미룬 커밋은 되돌릴 대상이 아니다. 컴포넌트 축의 격리(노드 단위 구독, 변경 비트)는 지키고 있고 벗어난 것은 필드당 계층과 이중 구독이며 F2와 뒤의 후보가 되돌린다. 확인할 자리 둘: 자동 Refresh(key 재마운트, 가장 비싼 fiber 반영)가 꼭 필요한 쓰기에만 나가는지(EVENT-042·071)와 배열 연산의 새 fiber 생성 비용 — 렌더 횟수 단언과 F2 측정이 함께 본다. |
| Refresh의 까닭 | 배열 폼의 버튼 재렌더 관측을 두고 다시 그리기와 Refresh의 차이를 짚으며 | "그게 rerender 랑 refresh 의 차이일거야. key를 업데이트 하는건 말한대로 가장 비싼 작업이라, 정말 꼭 필요할때만 쓰는게 맞는데, 대표적인게 비제어컴포넌트의 초기화야. 다만 각 노드에 어떤 종류의 formTypeInput 이 연결된건지 알 수 없으니까, 우리 form 차원에서는 기본값 되돌리기를 하는 경우(대표적으로 브랜치가 바뀌거나, active가 바뀌면서 새로 나타나는 등)에 잘 계산해서 제한적으로 refresh를 발화하도록 했었어. node event에도 이걸 만들어둔게, 사용자가 비싼 값을 내고서라도 해당 input을 다시 그리고자 할 수도 있잖아? 그런 용도로 쓰라고 만든거야. setValue 나 Reset 등 일부 이벤트에서 refresh 비트마스크를 쓴 이유지. 이건 이해했니? 비싸도 필요한 경우엔 쓸 수 있어야하는데. 남용되면 안되지만" (2026-10-07, 원장 세션) | 확정(원장과 일치, 까닭의 기록). Refresh(key 재마운트)는 가장 비싼 fiber 반영이라 꼭 필요할 때만 쓴다; 대표적 필요는 비제어 입력의 초기화(DOM이 값을 쥐고 있어 새로 만들어야 커밋된 값을 다시 읽는다); 폼은 노드에 붙은 입력의 종류를 모르므로 기본값으로 되돌리는 경우(분기 전환, active 변화로 새로 나타남 등)에 한해 제한적으로 낸다(EVENT-039·041·042·071, REACT-019); 소비자가 비싼 값을 치르고라도 입력을 다시 그리려 할 때 쓰도록 노드 이벤트의 공개 명령으로 두었고 setValue·Reset 등의 refresh 비트마스크가 그 자리다(EVENT-037·040). 7단계의 확인은 구현이 이 규칙보다 자주 내지 않는가(119라운드 (a): 쓰기 종류별 재마운트 횟수를 EVENT-042·071과 대조)이며, 112C-01의 경계 재마운트 결함이 같은 종류였다. |
| 구현 이격에 대한 소유자의 뜻 | Refresh의 까닭까지 기록한 뒤 | "그래. 원장 만들때 충분히 분석을 하긴 했는데, 이번에 구현 이격이 난걸 보고 좀 불안해진 모양이야. 벤치마크와 구현-원장-검증 핑퐁으로 이전보다 발전된 구현을 해주길 바라" (2026-10-07, 원장 세션) | 확정. 소유자의 바람: 벤치마크 → 진단 → 원장 판정 → 변경 하나에 차등·판정 하나 → 검증자 대조의 고리를 7단계 끝까지와 개선 단계에서 유지해, 옛 구현보다 발전된 구현에 이른다. 원장 관리자의 메모: 이번 이격(경계까지의 key 재마운트, 필드당 계층, 이중 구독, 마운트 때의 후보 계획)은 원장이 범위와 계약을 적어 두었기에 이격으로 판정될 수 있었고, 생긴 까닭은 구현이 "이 변경이 원장의 어느 문장을 구현하는가"를 매번 적지 않은 것이다; 지금은 감사 목록에서 자리마다 계약 유무를 적게 하여 고치며, 개선 단계 목록에 "원장의 바인딩·정착 계약마다 그것을 구현하는 코드 자리와 고정 시험을 짝지어 두는 역방향 색인"을 더해 재발을 막는다. |
