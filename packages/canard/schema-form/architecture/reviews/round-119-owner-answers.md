# 119라운드 — Vincent의 답 (React 바인딩 층은 컴포넌트 계층을 얇게 유지한다 — 계층이 깊어지면 그 자체로 지연이 크게 늘므로 옛 구현처럼 대부분의 기능을 훅에 넣고 스냅샷 ref 같은 기법으로 층을 더하지 않는다; 이 층의 분석은 코어와 달리 렌더 횟수와 리프레시 지연으로 한다)

2026-10-07. 118라운드의 React 층 진단이 실제로 늘어난 일을 "필드마다 fiber 계층 +5"(프록시의 Provider·경계 래퍼·경계, 필드 분리, 입력 경계의 세 층, 이중 구독, 자식마다 layout effect)로 가리고 경계 계층 축소(F2a·F2b)를 열자, 소유자가 옛 구현의 원칙을 말했다.

| React 층의 설계 원칙 | 필드당 컴포넌트 계층이 다섯 늘었다는 진단을 듣고 | "음 아, 이미 지나간거같은데, 그래서 이전 구현에서는 컴포넌트 계층을 얇게 가져가려고 노력을 많이 했었어. 컴포넌트 계층이 깊어지면 그 자체로 속도 지연이 엄청 늘어나서 말이야. 가능하면 컴포넌트 계층을 얇게 가져가는게 필요하고 이를 위한 snapshot Ref 라던가 하는 기법이 필요했었어. 이건 코어 레이어랑 다르게 랜더카운트와 리프레시 레이턴시를 분석해야해. 잘 알고있겠지만. 그래서 대부분 기능을 이전 구현처럼 hook에 넣고, 컴포넌트 계층을 얇게 유지할 필요가 있을거야" (2026-10-07, 원장 세션) | 확정. React 바인딩 층의 원칙: (1) 필드당 컴포넌트 계층을 얇게 유지한다 — 래퍼·경계·Provider·분리 컴포넌트로 층을 더하지 않고, 구독·메모·이펙트·경계 판정 같은 기능은 옛 구현처럼 훅과 스냅샷 ref(렌더 사이에 값을 ref에 두고 비교해 불필요한 렌더를 막는 기법)로 한 컴포넌트 안에서 처리한다; 계층이 꼭 필요한 자리(React가 요구하는 오류 경계 클래스, 문맥 제공)는 해석·소유 지점에서 한 번만 둔다(112C-01과 같은 방향). (2) 이 층의 성능 분석은 코어와 달리 시간만이 아니라 렌더 횟수(어느 컴포넌트가 쓰기 하나에 몇 번 렌더되는가)와 리프레시 지연(쓰기에서 화면 반영까지)으로 한다 — 118라운드의 컴포넌트·훅 단위 계수가 그 자리다. (3) F2a·F2b와 그 뒤의 후보(이중 구독, 자식마다 layout effect)는 이 원칙으로 설계한다: 목표는 필드당 계층을 옛 판 수준으로 되돌리는 것이며, 바인딩 계약(REACT-019·024, EVENT-039·040, 112C-01)은 그대로다. 이 원칙은 개선 단계의 React 층 정리에도 적용된다. |
