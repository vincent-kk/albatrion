# 제안 A에 대한 레드팀 공격

> **소유자 제안 원문**: *"그냥 jsonSchema 상의 글로벌 readOnly 와 disabled 스팩은 제거해버릴까? 생각보다 성가시네."* [확인]

### 1. 공격 논증 및 취약점 분석

#### (1) JSON Schema 표준 의미와 "중간 상속 없음"의 정면 충돌
* JSON Schema 표준에서 `readOnly: true`는 해당 어휘가 선언된 위치 이하의 인스턴스 전체에 대해 수정 불가를 선언하는 의미론을 가집니다[확인].
* 그러나 현재 원리 원장은 "글로벌과 로컬 두 층만 두고 중간 조상의 상속은 구현하지 않는다"(축 10항, 읽기 3)고 규정하고 있으며[확인], "객체 노드를 대상으로 한 잠금은 그 노드에만 걸려 사용자 입력이 없으므로 효과가 없다"고 못 박았습니다[확인].
* 제안 A에 따라 루트 스키마의 `readOnly`에서 "글로벌 잠금" 지위를 박탈하면, 루트는 객체 노드이므로 로컬 잠금만 걸리게 됩니다[추정]. 그 결과 **루트에 표준 키워드로 작성된 `readOnly: true`는 아무런 일도 하지 않는 무효 구문**이 됩니다[추정].

#### (2) 리프가 아닌 모든 노드에서 표준 `readOnly`의 전면 무력화
* 중간 복합 객체나 배열에 표준 `readOnly: true`를 지정하더라도 자식 필드들은 전혀 잠기지 않습니다[추정]. 표준 키워드 `readOnly`는 말단 노드에 일일이 선언할 때만 동작하게 되며, 백엔드 스키마 명세와의 심각한 불일치를 초래합니다[추정].

#### (3) 스키마 주도 폼 원칙의 붕괴 및 React 뷰 종속성 심화
* 제안 A가 수용되면 스키마 자체만으로는 폼 전체를 읽기 전용으로 잠글 수 있는 방법이 사라집니다[추정]. 오직 `<Form readOnly={true} />`를 통해서만 전역 잠금이 가능해집니다[추정]. 이는 P5 및 P1에 배치되며, 폼의 실행 능력을 React 컴포넌트 속성에 결속시키는 퇴행입니다[추정].

#### (4) 축 10항 및 읽기 3의 자가당착적 파기
* 소유자께서는 축 10항에서 *"글로벌 설정과 로컬 설정의 동시 제공과 경합은 기존과 같이 제공한다. rootJSONSchema도 props와 동치"*라고 선언하셨고[확인], 읽기 3에서 *"10항은 루트 스키마의 readOnly·disabled 같은 것을 가리킨다"*고 확정하셨습니다[확인]. 성가시다는 이유로 루트 스키마의 글로벌 지위를 삭제하는 것은 축 10항과 읽기 3을 스스로 형해화하는 모순입니다[추정].

#### (5) 대안(표준 키는 하위 트리 잠금, 예약 층 `&readOnly`는 해당 노드만)의 파탄
* 동일한 '잠금' 개념에 대해 접두사 `&` 유무에 따라 상속 범위가 달라지는 구조는 G4(하나의 개념에는 하나의 장치)를 위반합니다[추정]. "중간 조상의 상속은 구현하지 않는다"는 읽기 3의 합의를 파기하게 되어 하위 트리 전파 비용을 영구 부과하게 됩니다[추정].

### 2. 깨지는 장면 표 (제안 A)

| 번호 | 심각도 | 스키마와 값 순서 | 무엇이 깨지는가 | 어느 원리 |
| :--- | :--- | :--- | :--- | :--- |
| A-1 | 치명적 | `{"type": "object", "readOnly": true, "properties": {"name": {"type": "string"}}}`; 사용자가 `name`에 타이핑 | 루트 객체에 표준 `readOnly: true`를 명시했음에도 `name` 입력창이 활성화되어 수정 가능함. 스키마만으로 폼 전체를 잠글 수 없음 | P1, 축 10항, G1 |
| A-2 | 높음 | `{"properties": {"user": {"type": "object", "readOnly": true, "properties": {"email": {"type": "string"}}}}}`; `email` 수정 | 중간 조상 `user`의 표준 `readOnly`가 자식에게 상속되지 않고 객체 자체는 입력이 없어 선언이 무효화됨 | P1, 원장 §4 병합표 |
| A-3 | 중간 | 렌더러 없이 코어 단독 실행 시 루트 스키마 `readOnly: true` 주입 | React 속성을 줄 수 없는 순수 코어 환경에서 전역 잠금을 명령할 표준 경로가 소멸함 | P5 |

### 3. 권고와 이유
* **권고**: 제안 A를 기각하고, 루트 스키마의 `readOnly`·`disabled`를 글로벌 잠금으로 유지하되, Form 속성과 완전히 동일하게 **참일 때만 하위 전체를 덮는 OR 규칙**으로 일치시킬 것[추정].
* **이유**: 소유자께서 12라운드 1항 권고를 수용하시면서 *"false 일때는 로컬 동작을 보장한다"*라고 선언하셨습니다[확인]. 루트 스키마 키 역시 정의되었을 때 무조건 덮어쓰던 비대칭 동작을 버리고 Form 속성과 똑같이 `true`일 때만 덮는 대칭적 OR로 정리하면 복잡한 경합 문제가 즉시 해소됩니다[추정]. 이렇게 규정해야만 축 10항의 *"rootJSONSchema도 props와 동치"*가 성립합니다[추정].

### 4. 수용할 경우 원리 원장에서 바뀌는 문장
* §1.2 축 10항, §1.3 읽기 3, §4 병합표 상태 키 행이 "글로벌은 Form 속성만, 루트 스키마는 로컬로 강등, 스키마만으로는 폼 전체 잠금 불가"로 후퇴해야 합니다[추정].

# 제안 B에 대한 레드팀 공격

> **소유자 제안 원문**: *"조각이 꺼질때 해당 값을 '제거'할 것인지는 별도 옵션을 쓴다. 단, 기본값은 true, false 로 끌 수 있도록 한다. 이는 omitEmpty 와 동일하게, 빼는게 기본 동작이라고 가정한 구성이다."* / *"중복 선언시(부모선언 + 자식노드 자체 선언) 이를 병합하는게 아니라 덮어쓰는걸 고려했다. 하지만 이를 or 조건이나 체인으로 엮을 수 있나? 루프가 발생하면 form 을 터트리고 오류를 보여주면 된다."* [확인]

### 1. 공격 논증 및 취약점 분석

#### (1) P4와 P2의 정면 파괴: "비활성화는 쓰기"라는 변질
* 원장 P4: *"방출은 정책이다. 비활성 노드의 제외, omitEmpty·omitTrailing은 원본을 건드리지 않는 투영 규칙이며, 작성자가 고른다."*[확인] 원장 §3: *"비활성화는 쓰기가 아니다 — 조각이 꺼져도 원본은 그대로다(P4, 4항)."*[확인] ADR 0013 결론: *"비활성화(원본 보존)와 전체 교체(원본에도 적용)를 구분한 것이 답이었다"*[확인].
* 제안 B는 조각이 꺼지는 형상 사건이 원본을 파괴하는 암묵적 쓰기를 발화시킵니다[추정]. P3(형상은 상태의 순수 함수)와 P2(코어는 스스로 원본을 고치지 않는다)가 동시에 파괴됩니다[추정].

#### (2) 본체·형제 분기와의 공유 노드 파괴
* ADR 0002: *"존재는 활성 조각의 합집합이다."*[확인] 어떤 프로퍼티(`amount`)가 본체나 두 분기에 공통으로 선언될 수 있습니다. 분기 1이 꺼질 때 `amount`를 지우면 본체나 새로 켜진 분기 2가 공유하는 `amount`의 원본이 증발합니다[추정].

#### (3) 초기 로드 시 다형성 데이터의 즉각 증발
* 백엔드에서 카드와 계좌 정보가 모두 든 객체를 `setValue`로 로드하면 판별 값에 따라 한 분기만 켜지고 나머지는 꺼집니다[확인]. 꺼짐 시 제거가 로드에도 작동하면 폼을 열자마자 비활성 분기의 데이터가 삭제되고, 그대로 저장하면 백엔드 데이터가 사라집니다[추정]. `setValue(getValue())` 멱등성 파괴와 P2 "값은 받아들인다" 위반입니다[추정].

#### (4) 정착 안 비단조 게이트 진동 시 선제 삭제
* 호스트 바퀴는 게이트를 비단조 재평가합니다[확인]. 1바퀴에서 잠깐 꺼진 조각이 2바퀴에서 켜질 수 있는데, 즉시 지우면 중간 데이터가 유실되고, 최종 커밋 직전에만 지워도 그 쓰기가 파생을 재발화시켜 예산 초과를 유발할 수 있습니다[추정].

#### (5) 원본 B 및 `DisableAutomaticWrites`와의 정합성
* 꺼질 때 지우는 동작이 자동 쓰기라면 `DisableAutomaticWrites`로 억제되어야 하는데 그러면 "빼는 게 기본"이 무너지고, 내장 규칙이라면 원본 그대로 로드하려는 호출자의 권리가 박탈됩니다[추정].

#### (6) 노드 게이트(`&active: false`)로의 전파 시 사용자 경험 참사
* 노드 게이트는 조각 게이트와 같은 장치입니다(G4)[확인]. 따라서 `&active: false`로 필드가 가려질 때도 값이 지워져야 하고, 체크박스를 잠깐 해제했다가 다시 체크하면 작성해 둔 메모가 사라집니다[추정].

#### (7) `omitEmpty`와 제거의 동일시
* `omitEmpty`는 방출 투영 정책(P4)이고 원본을 건드리지 않습니다[확인]. 제안 B의 '제거'는 원본을 파괴하는 쓰기(P2)입니다[확인]. 둘을 동일시하는 것은 원장의 "한 사건이 두 칸에 걸치면 설계가 잘못된 것이다"에 걸립니다[추정].

#### (8) 중복 선언 시 '체인이나 루프' 발상의 구조적 불능
* OR로 엮으면 부모가 `false`(보존)를 선언해도 자식 기본값 `true`가 이겨 무조건 삭제되고, 자식 우선 덮어쓰기면 자식 기본값이 부모의 명시적 `false`를 언제나 덮습니다[추정]. 이는 정적 선언 경합이지 런타임 루프의 문제가 아닙니다[추정].

### 2. 깨지는 장면 표 (제안 B)

| 번호 | 심각도 | 스키마와 값 순서 | 무엇이 깨지는가 | 어느 원리 |
| :--- | :--- | :--- | :--- | :--- |
| B-1 | 치명적 | 본체 `amount` + `card`·`bank` 분기 모두 `amount` 공유; `card` 선택 → `10000` 입력 → `bank` 전환 | `card`가 꺼지며 공유 노드 `amount`가 제거됨 | P4, ADR 0002 |
| B-2 | 치명적 | 백엔드에서 `{type:"bank", cardNo:"1111", account:"2222"}` 로드 | 로드 시점에 `card`가 꺼져 있다는 이유로 `cardNo`가 즉시 삭제됨. 저장 시 백엔드 데이터 파실 | P2, ADR 0013 |
| B-3 | 치명적 | `card` 탭에서 입력 중 실수로 `bank` 클릭 → 즉시 `card` 재클릭 | 입력 중이던 카드번호·유효기간·CVC가 증발 | P4, 사용자 경험 |
| B-4 | 높음 | `hasMemo` 체크박스 + `memo`(`&active: "../hasMemo === true"`); 메모 입력 → 해제 → 재선택 | G4에 따라 노드 게이트에도 적용되면 메모가 삭제됨 | G4 |
| B-5 | 높음 | 정착 바퀴 1회차에서 잠깐 꺼졌다 2회차에서 켜지는 조각 | 중간에 원본이 삭제되거나, 지움 쓰기가 예산 초과 루프를 촉발 | P3, ADR 0007 §2 |

### 3. 권고와 이유
* **권고**: 제안 B(기본값 제거)를 기각하고 "비활성화 시 원본 보존, 방출 제외"를 기본값으로 유지. 꺼질 때 값을 제거·변경하는 동작은 작성자가 명시할 때만 발화하는 선택 기능으로[추정].
* **이유**: 데이터 무결성; 백엔드로 보낼 때 비활성 필드를 빼고 싶다는 요구는 이미 P4의 방출 정책으로 충족됨[확인]; 옵션은 조각 객체와 `&children` 안의 `control.onInactive: { clear: true }` 또는 `control.clearValue: true`로 국소적으로[추정].

### 4. 수용할 경우 원리 원장에서 바뀌는 문장
* P4·P2·§3 "비활성화는 쓰기가 아니다"·ADR 0013 분류표 87행이 전면 개정되어야 함[추정].
