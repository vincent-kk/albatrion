# 작업 루프 3차안 A·C 적대적 실행 리뷰

검토일: 2026-09-22. 대상은 `round-3-spec.md` A·C이며, 비교 기준은 `round-2.md` §4·§6·§7입니다. **현재 문구 그대로는 확정하기 어렵습니다.** 이전 활성 집합을 버리는 방향과 객체 로컬 메모는 기존 반례를 해결하지만, 수동 선택 상태·반복 대상·상한의 커밋 지점·null 전체 교체의 예외가 빠져 있습니다. 옵션 A에 관한 “불일치는 검증 오류로 드러난다”는 설명에는 실행 반례가 있습니다.

## 1. 실행 방법과 증거의 범위

저장소 루트에서 실행합니다.

```sh
yarn node packages/canard/schema-form/architecture/spikes/work-loop/codex3/run.mjs
```

Node에서 설치된 Ajv **8.17.1**의 `ajv/dist/2020`을 사용했습니다. 루트에는 Ajv 6이 있어서 ajv8 플러그인 위치를 기준으로 해석했습니다. `strict: false`, `allErrors: true`이며 `useDefaults`, `coerceTypes`, `removeAdditional`은 켜지 않았습니다. 모델이 기본값과 투영을 수행하고, Ajv는 **동일하게 작성된 원본 스키마**와 최종 JSON을 검증합니다.

실행 결과는 `PASS`, **18개 실험**입니다. 이는 아래 관측과 반례의 단언이 재현됐다는 뜻이며, 명세 전체가 통과했다는 뜻은 아닙니다. 전체 입력·출력·Ajv 오류는 [results.jsonl](../spikes/work-loop/codex3/results.jsonl)에 있습니다.

모델의 범위와 가정은 다음과 같습니다.

- [WorkLoop.mjs:111](../spikes/work-loop/codex3/WorkLoop.mjs#L111)은 무조건 조각에서 시작하여 선언 순서로 가드를 평가합니다. default는 누락 raw에만 주입하고, 객체 자식은 후속 가드가 읽기 전에 계산합니다. 이전 `active`는 입력으로 쓰지 않습니다.
- leaf raw와 extra를 한 객체로 모아 표시했습니다. null·잘못된 종류의 호스트 값은 별도 `override`로 표현했습니다. 이 분리는 A1/C2의 저장 위치 모순을 모델 내부에서 숨기지 않기 위한 표현입니다. 실제 구현의 슬롯 설계를 검증한 것은 아닙니다.
- `x-omitEmpty`, `x-omitTrailing`은 실행 모델의 방출 정책 표기입니다. 비어 있음은 이 실험에서 `''`, `null`, 빈 객체·배열로 정했고, 배열 끝의 null을 생략했습니다. 제품의 모든 omit 옵션을 재현한 것은 아닙니다.
- 단순 `properties`, `allOf`의 조건부 조각, `if/then/else`, 명시한 판별 키와 수동 union 선택을 모델링했습니다. B의 판별식 발견, `$ref`, 복잡한 중첩 applicator, 실제 UI·dirty 목록·복사 최적화·비동기 검증은 구현하지 않았습니다. 따라서 이 부분은 통과를 주장하지 않습니다.
- A4는 별도 leaf 파생 모델, A7은 별도 동기 통지 모델입니다. 명세가 갈리는 부분은 대안별로 실행했으며, 특정 대안을 명세의 유일한 구현이라고 주장하지 않습니다.
- 이하 `run.mjs:숫자` 등은 모두 `architecture/spikes/work-loop/codex3/` 아래 파일이며, `round-3-spec.md:숫자`는 리뷰 대상의 실제 줄 번호입니다. 실행에서 직접 확인하지 않은 권고는 **추론**으로 표시합니다.

### A3-1 — 반례: 함수의 입력에서 선택 상태가 빠졌습니다

`round-3-spec.md:53`은 “`emit`은 (작성된 스키마, 트리의 raw 전체)의 함수다”라고 합니다. 그런데 같은 문서 `:99`는 판별식이 없으면 사용자가 고르는 `select`를 사용합니다. ADR 0002 `:31`, `:36`, `:80`은 선택을 **폼 상태**로 두고, 초기 선택은 원본을 바꾸지 않는다고 명시합니다.

실행 스키마는 두 object 분기입니다. 첫 분기는 숫자 `a`를 required로 두고 `additionalProperties:false`, 둘째는 숫자 `b`에 같은 제약을 둡니다. 판별 const가 없으므로 수동 선택입니다.

```text
raw = {a:1, b:2}
selected = 0 → emit = {a:1}, Ajv valid=true
selected = 1 → emit = {b:2}, Ajv valid=true
두 실행의 전체 leaf raw는 동일합니다.
```

근거: `run.mjs:28`, `WorkLoop.mjs:111`, `results.jsonl:1`. 분기 선택 자체가 숨은 입력입니다. 이는 이전 commit의 active를 읽어서 생긴 문제가 아닙니다.

반면 S3-b의 두 반대 존재 가드에는 개선 효과가 있었습니다. raw `{a:'x',b:'y'}`에 도달하는 두 쓰기 순서와 세 이전 활성 집합을 조합한 6회 모두 `{a:'x'}`를 방출했습니다. 근거: `run.mjs:43`, `results.jsonl:2`.

**추론:** 주장은 `emit = F(schema, raw, selection)`으로 좁히거나, 선택 상태를 raw 전체에 포함하는 명시적 계약이 있어야 합니다. 현재 문서에는 선택 노드·선택 raw·reset 시 선택 복원 규칙이 없습니다. 값 가드만 있는 부분집합의 결정성을 전체 폼으로 확대하면 안 됩니다.

### A3-2 — 모순: 비활성 가드를 다시 보지 않으면 역순 체인이 멈춥니다

충돌하는 두 문장은 다음과 같습니다.

> `round-3-spec.md:40`, `:46`: “조각을 전순서로 순회한다.” / “한 바퀴가 끝났을 때 A가 바뀌었으면 2로 돌아간다.”

> `round-3-spec.md:55`: “반대면 최대 30바퀴이되 각 바퀴는 켜진 조각의 가드만 다시 돈다.”

30개의 조건 `required p_i → p_(i+1) default`와 입력 `{p0:0}`을 실행했습니다.

| 실행 해석 | 마지막 필드가 생긴 바퀴 | 변화 없음 확인까지 | 결과 |
| --- | --- | --- | --- |
| 선언 순서 = 의존 순서 | 1 | 2 | `p0`부터 `p30`까지 존재 |
| 역순, 모든 가드 재평가 | 30 | 31 | `p0`부터 `p30`까지 존재 |
| 역순, 첫 바퀴 뒤 켜진 가드만 재평가 | 추가 진행 없음 | 2 | `{p0:0,p1:1}` |

근거: `run.mjs:62`, `results.jsonl:3`. 즉 “1바퀴에 체인이 풀린다”는 **생산적인 계산 바퀴**에 대해서는 맞습니다. 하지만 A3 step 4의 종료 판정까지 세면 순방향도 2바퀴입니다. 역순 30단은 결과 완성까지 30, 종료 확인까지 31입니다.

새로 켜진 객체 `child`의 default `{}` 안에 `token:1`을 채운 뒤, 바로 다음 가드가 `child.token`을 읽어 `done:true`를 켜는 경우도 실행했습니다. 한 생산적 바퀴에서 `{seed:true,child:{token:1},done:true}`를 얻었습니다. 근거: `run.mjs:77`, `results.jsonl:4`. 이는 즉시 자식 계산이라는 처방을 지지합니다. 실제 dirty 목록 구현의 정확성은 별도 검증 대상입니다.

**추론:** 켜진 조각만 돌겠다는 절을 삭제하거나, 읽기 의존성에 따라 **아직 꺼진 가드도** 재평가하는 작업 목록으로 바꾸셔야 합니다. 후자는 현재 명세보다 추가적인 계약입니다.

### A3-3 — 통과: 판별 자식의 존재 교착은 풀립니다

분기에서만 `kind:'cat'`·`kind:'dog'`를 선언하는 union을 검사했습니다.

```text
{}              → emit {}, 활성 union 분기 없음, kind 자식 자체는 존재
{kind:'cat'}    → emit {kind:'cat',meow:true}
```

근거: `run.mjs:89`, `results.jsonl:5`. 빈 상태에서도 선택 필드가 존재하며, 사용자 선택이 raw에 들어가면 분기가 활성화됩니다. UI 렌더를 검사한 것은 아니고, 자식 존재와 가드 활성의 순환을 모델에서 검사했습니다.

이 통과는 판별 키가 정상적으로 식별됐고, 금지·omit과 충돌하지 않는 경우에 한정됩니다. A5의 우선순위 충돌까지 해결됐다는 의미는 아닙니다. 빈 raw에서 필드가 **존재하는 것**과 키가 JSON에 **방출되는 것**도 다릅니다.

### A3-4 — 통과: 비객체를 객체 가드에 직접 넣던 문제는 사라집니다

Ajv에 정규화된 가드 `{required:['kind'],properties:{kind:{const:'cat'}}}`를 직접 넣으면 다음과 같았습니다.

```text
guard(null) = true
guard(undefined) = true
guard(17) = true
guard([]) = true
guard({}) = false
```

모델에서는 null 호스트가 `{}`를 가드에 주므로 양쪽 union 가드가 모두 거짓이었고, scalar 호스트에서는 순회를 하지 않았습니다. 근거: `run.mjs:89`, `WorkLoop.mjs:75`, `WorkLoop.mjs:111`, `results.jsonl:5`.

**추론:** `properties`만 쓰고 `required`가 없는 임의의 `if`는 `{}`에서도 참일 수 있습니다. 그것은 작성된 객체 스키마의 의미이므로 없애면 안 됩니다. A3-4는 모든 공허한 참을 없앤다는 뜻이 아니라, 비객체 값을 객체 가드에 넘기는 오류를 없앤다는 뜻으로 읽어야 합니다.

### A3 step 4 옵션 A — 반례: 검증기가 불일치를 반드시 잡지는 않습니다

`round-3-spec.md:47`은 단조 활성 때문에 부정 가드가 어긋날 수 있으며 “그 어긋남은 검증기의 에러로 드러난다”고 합니다. 다음 입력은 마지막 문장을 반박합니다.

```json
{
  "type": "object",
  "properties": { "seed": {} },
  "allOf": [
    {
      "if": { "not": { "required": ["x"] } },
      "then": { "properties": { "a": { "default": "A" } } }
    },
    {
      "if": { "required": ["seed"] },
      "then": { "properties": { "x": { "default": 1 } } }
    }
  ]
}
```

```text
입력 {seed:true}
옵션 A → {seed:true,a:'A',x:1} → Ajv valid=true
옵션 B → {seed:true,x:1}       → Ajv valid=true
```

A의 두 번째 바퀴에는 첫 가드가 명확히 거짓입니다. 그래도 `a`를 유지합니다. 원본 스키마가 추가 속성을 허용하므로 Ajv는 `a`의 존재를 문제 삼지 않습니다. 활성 상태와 JSON Schema 평가의 불일치는 검증 오류 없이 남습니다. 근거: `run.mjs:109`, `results.jsonl:6`.

같은 스키마에 루트 `unevaluatedProperties:false`만 추가하면 다음과 같습니다.

```text
옵션 A → {seed:true,a:'A',x:1} → invalid: unevaluatedProperty='a'
옵션 B → {seed:true,x:1}       → valid
```

근거: `run.mjs:109`, `results.jsonl:7`. 옵션 A는 실제로 정상 종료했으며 상한에 걸린 결과가 아닙니다. 오류가 나더라도 첫 가드가 이미 거짓인 필드를 활성 상태로 유지하는 문제를 검증기가 고쳐 주지는 않습니다.

단조 옵션의 **종료 증명 자체**는 반박하지 않습니다. 고정된 유한 조각 집합에서는 새로운 조각을 켜는 횟수가 제한됩니다. 반박하는 것은 최종 활성 집합의 의미와 오류 관측에 관한 설명입니다.

### A3-5 / step 5 — 통과: 같은 호스트의 S5 진동은 사라집니다

기본 `a`가 있고, 앞 조각이 `required a → properties.a=false`, 뒤 조각이 `required a → b default 1`인 경우입니다.

```text
입력 {a:'kept'}
raw   = {a:'kept',b:1}
local = {a:'kept',b:1}
emit  = {b:1}
```

뒤 가드는 금지된 `a`를 여전히 보아서 `b`를 켰습니다. 금지 투영 때문에 같은 호스트에서 `a`의 존재 가드가 다시 꺼지는 진동은 없었습니다. 근거: `run.mjs:144`, `WorkLoop.mjs:97`, `results.jsonl:9`.

다만 범위를 분명히 해야 합니다. 부모의 local에는 자식의 **emit**이 들어갑니다. 부모의 `child.a required` 가드는 자식 local을 넣었을 때 true, 자식 emit을 넣었을 때 false였습니다. 따라서 “금지 조각은 피드백 바깥”이라는 설명은 **해당 호스트의 조각 계산 안에서만** 성립합니다. 부모 가드와 emit을 읽는 derive에는 금지 결과가 보입니다.

또한 원래 입력은 Ajv invalid였고, `{b:1}`은 valid였습니다. `round-2.md:86`의 S5에 적힌 “a를 보이고 검증기의 에러를 붙이는 것”과는 다른 선택입니다. 최신 A3는 제외 정책을 명시했으므로 이 차이를 A3의 실행 위반으로 분류하지 않았습니다. 기존 무효 입력을 방출에서 제거해 유효하게 만드는 정책을 수용하는지 별도 결정 기록이 필요합니다.

### A4 — 미정의: 마지막 쓰기를 받은 뒤 무엇을 커밋합니까

`round-3-spec.md:64`의 “값은 받아들이고 마지막 라운드의 트리로 고정한다”는 문장으로 다음 입력의 최종 트리를 하나로 정할 수 없습니다.

```text
초기 leaf raw=0
injectTo: 현재 emit을 읽어 raw := 1 - emit
상한: 25회 derive 평가
```

두 해석을 실행했습니다.

| 상한 처리 해석 | raw | emit | 마지막 derive가 읽은 값 |
| --- | --- | --- | --- |
| 마지막 쓰기는 수락, 다음 compute는 생략 | 1 | 0 | 0 |
| 마지막 쓰기 뒤 compute만 완료, 추가 derive는 생략 | 1 | 1 | 0 |

근거: `derive.mjs:2`, `run.mjs:159`, `results.jsonl:10`.

**추론:** 마지막으로 수락한 쓰기의 compute 완료를 커밋 조건으로 명시하고, 마지막 emit에 대한 읽기 전용 파생의 갱신 여부를 별도로 결정하셔야 합니다. 같은 라운드의 여러 inject가 한 대상을 쓸 때의 순서·충돌 규칙도 없습니다. 예를 들어 같은 emit에서 두 inject가 각각 `x:=1`, `x:=2`를 제안하는 입력은 어느 쪽을 커밋할지 답할 수 없습니다. 이 다중 writer 사례는 실행하지 않은 추론입니다.

## 3. 옵션 A와 B 중 무엇을 택할 것인가

**추론에 따른 권고: B를 더 나은 출발점으로 선택하겠습니다.** 선택 이유는 “상한이 있으면 정확하다”가 아니라, 고정점이 있는 일반적인 부정 조건에서 **최종 값에 대한 가드 판정과 활성 집합을 다시 일치시킬 수 있기 때문**입니다. A는 그런 경우에도 의도적으로 거짓인 가드를 유지합니다.

실행 증거를 함께 비교하면 다음과 같습니다.

| 사례 | A의 결과 / Ajv | B의 결과 / Ajv |
| --- | --- | --- |
| `not required x → a`, 이후 `seed → x` | `{seed:true,a:'A',x:1}` / valid | `{seed:true,x:1}` / valid |
| 위 스키마 + `unevaluatedProperties:false` | 같은 결과 / invalid(`a`) | 같은 결과 / valid |
| `not required x → x default`, then에서 x required | `{x:1}` / valid | cap=2: `{}` / invalid, cap=3: `{x:1}` / valid |

마지막 행의 원본 스키마는 다음과 같습니다.

```json
{
  "type": "object",
  "if": { "not": { "required": ["x"] } },
  "then": {
    "properties": { "x": { "default": 1 } },
    "required": ["x"]
  }
}
```

입력은 `{}`입니다. B는 x를 켜면 가드가 거짓이고, 끄면 다시 참이어서 고정점이 없습니다. cap=2와 cap=3 모두 상한에 걸렸습니다. A는 x를 유지하고 정상 종료했습니다. 근거: `run.mjs:129`, `results.jsonl:8`. **B가 언제나 A보다 좋은 JSON이나 valid 값을 낸다는 주장은 하지 않습니다.**

**추론:** B를 채택하더라도 현재의 “마지막 바퀴를 조용히 채택”을 의미상의 해결로 받아들여서는 안 됩니다. 다음 계약이 필요합니다.

1. 종료 이유를 `stable`과 `budget-exceeded`로 구분하고, 프로덕션에서도 관측 가능하게 해야 합니다. Json Schema valid와 엔진의 미정착 상태는 별개입니다.
2. 기본값은 누락 raw에만 쓰고, 분기 해제로 raw를 지우지 않아야 합니다. 매번 default를 재주입하거나 삭제하면 다른 상태 기계가 됩니다.
3. 상한 결과의 raw·local·emit·읽기 전용 파생이 어느 완료 지점에 대응하는지 정해야 합니다. A4의 미정의가 그대로 남으면 B의 마지막 바퀴도 믿을 수 없습니다.
4. 부정 가드 전체를 금지하거나 별도 의미를 부여하지 않는 한, 일반적인 모든 스키마에 고정점이 존재한다고 약속해서는 안 됩니다.

## 4. 검증 한계와 넘겨야 할 결정

이번 산출물은 독립 실행 모델과 리뷰이며 제품 소스·ADR을 수정하지 않았습니다. 별도 제품 빌드나 전체 워크스페이스 테스트는 이 모델의 증거로 대체할 수 없으므로 실행하지 않았습니다. 검증한 것은 위 Node 명령의 18개 실험, 원본 JSON Schema에 대한 Ajv 결과, 보고서의 파일·줄 번호입니다.

확정 전에 필요한 결정은 선택 상태를 포함한 함수 입력, 꺼진 가드의 재평가, 마지막 derive 쓰기의 커밋 지점, 판별 키의 투영 우선순위, null 전체 교체의 잠복 raw 처리, 자동 default 쓰기의 책임, extra의 저장 위치입니다. `resetSubtree()`의 초기값을 어디에 보관하는지와 수동 선택의 reset 정책도 본 모델에서는 증명하지 않았습니다. 통과로 적은 항목도 위 실행 범위를 넘어서는 보증은 아닙니다.
