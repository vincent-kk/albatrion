# 74라운드 — Vincent의 답 (레거시의 완전 분리: `src/__legacy__/`는 새 코드를 가져오지 않고 필요한 것은 사본으로 두며, 공개 호환 별칭은 07에서 끝낸다)

2026-10-02. 07 전환이 레거시 정리(U5)를 진행하는 가운데 소유자가 이 세션에서 물었다: 이번 단계가 끝나면 `<Form>`이 완전히 새 시스템으로 전환되고 레거시 폼과 새 폼이 완전히 분리되는가. 원장 관리자가 전환 뒤의 상태와 남는 연결고리 셋(LANDING-159 규칙 2의 레거시 → 새 코드 허용 목록, 레거시가 가져오는 새 `core/types`의 남는 형, 공개 호환 별칭 `JSONSchemaError`)을 설명하자 소유자는 "호환 명칭 없이 `__legacy__`는 거의 통째로 넘어갔으면 … 애매하게 연결고리가 있는 것보단 코드 복사본이 있어도 분리하는 게 낫지 않을까"라고 했고, 원장 관리자가 소유자 답으로 적을 문장 — "레거시(`src/__legacy__/`)는 새 코드를 가져오지 않는다. 필요한 것은 레거시 안에 사본을 둔다. 공개 호환 별칭은 07에서 끝낸다." — 를 풀어 물었다. 소유자가 아래 답을 직접 주었다. 이 답은 18라운드 편집자 결정(18C-49, LANDING-159 규칙 2)을 뒤집는다.

| 확인 | 물음(요지) | 답(원문) | 반영 |
| --- | --- | --- | --- |
| 레거시의 완전 분리 | 레거시는 새 코드를 가져오지 않고 필요한 것은 레거시 안에 사본을 두며 공개 호환 별칭은 07에서 끝내는 것으로 소유자 답을 적어도 되는가 | "예. 완전히 분리하세요. 저는 사실 패키지 레벨에서 분리를 할거라고 생각했는데, 이정도만 분리해도 괜찮겠네요" (2026-10-02, 원장 세션) | 확정. (1) LANDING-159 규칙 2(레거시 → 새 코드는 08 §17.2가 적은 곳만 허용)는 폐기되고 "레거시는 새 코드를 하나도 가져오지 않는다"로 바뀐다; 허용되던 가져오기(옛 `intersect*Schema`가 새 잎 교차 함수를, 옛 소비자가 청사진으로 옮긴 식 컴파일러를 가져오던 것)와 71C-01이 남겨 둔 새 `core/types`의 남는 형(event·state·value) 가져오기는 모두 `src/__legacy__/` 안의 사본으로 바꾼다. 규칙 1(새 코드 → 레거시 import 0)은 그대로이므로 결과는 양방향 import 0, 곧 `src/__legacy__/`의 완전 고립이다. 사본은 전환 뒤 빌드·시험 글롭에 묶이지 않고 PR-8이 디렉토리와 함께 지운다. (2) 공개 호환 별칭 `JSONSchemaError`(34C-02·50C-01, "PR-7까지")는 07의 전환 커밋에서 `src/index.ts`에서 빠지고 이주 안내에 적는다; 전환 뒤 새 `src/index.ts`에는 옛 이름의 별칭을 두지 않는다. (3) 패키지 수준의 분리(별도 패키지)는 하지 않는다 — 소유자가 디렉토리 분리로 충분하다고 했다. 07은 U5를 이 방향으로 보완하고(새 커밋), 점검 "새 코드의 레거시 import 0"에 "레거시의 새 코드 import 0"을 더한다 |

이 답으로 LANDING-159의 규칙 2와 그에 기댄 18C-49의 두 문장은 현행이 아니다. 다음 라운드 번호는 75이다.
