## 1. 소유자의 축 열 항목 (원문)

> 1. schemaForm은 jsonSchema 문법을 제안하지 않는다. 즉, if 블록에 어떤 표현식이 들어오던 무관하게, 현재 스키마 노드에서 해당 블록이 활성화 되는지만 본다. 그러므로 if 블록은 해석하지 않는다. 이는 oneOf / anyOf 도 마찬가지다. 그렇기 때문에 스키마폼에서 스키마를 사용하는 분기는 모두 if 블록을 사용하는 것을 컨벤션으로 사용하고자 한다. 이외 특수 문법(enum / const 등을 사용하는 등)은 쓰지 않는다. (추가해야할 근거가 있다면 상당한 이유로 제안하라)
> 2. if블록 등 컨디션 블록에서 컨디션으로 사용해야 하는 프로퍼티는 properties 에 선언되어야 한다. 이건 제약으로 가지고 가야할 듯 하다(실제 경합상황 해소를 위해)
> 3. then 블록이나 oneOf 블록, allOf , anyOf 등에서 프로퍼티 노드를 선언할 수 있다. 프로퍼티 노드 선언 제약은 if 블록에 포함되는 컨디션 필드 뿐이다.
> 4. jsonSchema 설정에 의한 form 변환 및 필드 노출 변환에서 값을 조작하지 않는다.
> 5. 각 노드에서 현재 필드가 가지는 제약(jsonSchema 조건)을 최신화하여 제공할 의무는 스키마폼이 진다. 예컨대 allOf 에 여러 if-then 블록으로 동일 필드에 여러 유효성 조건이 걸리면 이를 올바르게 해석하여 해당 노드가 출력할 수 있어야 한다 -> 각 node 의 jsonSchema 값은 input 을 표현할때의 중요한 제약조건으로 사용된다. 이외 다양한 추가 프로퍼티에도 적용되므로, 올바른 병합은 필수적이다. -> 유효성 조건 외 커스텀 필드 병합 방법에 대해서 고민해볼 필요가 있다.
> 6. injectTo 는 예외였지만(다이나믹 함수가 아니므로) & 로 시작하는 함수들에 대해서는 완전히 다른 규칙을 적용한다. 이 필드들은 실제로 form의 값을 "바꾸거나" 필드를 가리는 등의 작업을 할 수 있으며, 해당 노드의 상태 변경 등에 의해 값을 빼거나, 바꾸거나, 다른 노드애게 영향을 주는 등 다양한 확장 조작을 허용한다. 즉, 이쪽 규칙은 jsonSchema 와는 완전히 다르게, 실제 "값을 제어하는" 용도로 쓸 수 있다.
> 7. jsonSchema 와 & 문법 등은 서로 무관하나, jsonSchema 표현을 & 표현으로 대체할 수 있어야 한다(확장성을 위해). 경우에 따라서는 jsonSchema 로직과 동일한 로직을 &에 넣어야 할 수도 있고, jsonSchema 로직에 따라 동작하는 행위를 바꿀 수도 있다. 이는 유효성 검증과 무관하게, 값의 조작과 form 의 표현을 전담하는 계층으로 활용된다.
> 8. & 표현식과 injectTo 표현식은 모두 form 을 제어하는 특수 예약어로 취급되길 원한다. 지금은 위계도 사이클 타이밍도 미묘한데, 이걸 정리해서 명확한 동작 위계를 가져가길 바란다. 이름 컨벤션도 맞추고.
> 9. 기존 computed 와 &를 동시 제공하는건 일종의 선택지를 제공한 것이다. 제거해도 무방하나, 제공하는 방향을 선호한다.
> 10. 글로벌 설정식과 로컬 설정식의 동시 제공 및 경합도 기존과 같이 제공하길 바란다.

요약 발언(원문):

> 핵심은 최소한의 제약으로 jsonSchema 를 최대한 반영. ui제어는 최대한 & 로 처리 (&를 사용한 노드단위가 아닌 하위 노드 동시제어 문법도 있으면 좋겠음. 설계필요) 값변경도 전량 &와 injectTo로 처리(injectTo 도 & 패밀리로 넣어도 됨, 단 그럼 computed 이름을 바꿔야함) … jsonSchema 를 통한 ui 제어를 위해 if-then-else 를 쓰는거고. 결과적으로 jsonSchema 는 사후검증, schema-form 은 대상값을 만들면서 검증이라는 태생적 차이를 수정하기 위해서 & 패밀리를 쓰는거고, if-then-else 를 함께 써서 json 만으로도 동작하는 구조를 설계하는 것임.

> 지금은 논리적 적함성과 개념적 일관성, 예측가능성, 합목적성 등 이론적 지점을 중점으로 다룬다. 실제로 각 파트를 나눠서 개발을 진행할때 어차피 현장판단이 필요하므로, 이를 위한 원리 원장을 만드는게 목표다. 이때 단순히 말로만 정한게 아니라 실측과 샘플, 샌드박스 구성 등이 있으면 더욱 좋다.

## 2. 읽기 셋과 소유자의 답 (원문)

편집자가 열 항목의 뜻이 갈리는 곳 셋을 물었고, 소유자가 답했다.

**읽기 1.** `oneOf`/`anyOf`의 분기는 무엇으로 켜지는가.

> oneOf/anyOf 분기는 개별 노드의 &active 나 &visible 로 처리될거라 생각했음. 앞서 말했던 자식노드 전반에 대한 표시제어 기능이 추가되면 부모노드에서 선언할 수도 있고. 즉 oneOf anyOf 는 jsonSchema 의 분기 선언문이 아니라, 진짜 검증조건인거고, ui 표현식을 적절히 써야 의도대로 동작했으면 하는 것임. 다만, 이렇게 되면 기존 구현에서 oneOf 복수 브랜치 일치 문제가 재현되므로, oneOf / anyOf 내부에 if-then-else 구분을 넣을 수 있도록 확장하자는 제안임. &if 키워드를 살려야할지는 판단이 필요.

> 당연히 if-then-else 없이 oneOf anyOf 에 퓨어한 선언을 할 수도 있다. 이 경우에는 스키마베이스 폼 브랜치 제어는 안하고, & 패밀리로 제어할 책임을 사용자가 진다.

**읽기 2.** 4항의 "값을 조작하지 않는다"에 없음인 키를 채우는 것이 드는가.

> 없음인 키를 채움도 포함이다. default 값을 채우는것과 defaultValue 로 전달된 값을 채우는 것, 그리고 drived 나 injectTo 등으로 값을 채우는 것, 표현식으로 defaultValut를 계산하게 하는 것 등, 없는 값을 채우는 것과 있는 값을 바꾸는 것, 있는 값을 제거하는 것 모두 원리상 가능해야 한다. 이게 고려가 안되어있는거같아서 끊고 이야기한 것이다.

이어서 채우기의 원천과 시점:

> default 는 좀 특이하게 &default 가 아니게 선언도 가능할거같다. 표준 스키마 문법이니. 그러니 &default 가 있으면 그걸 쓰고, 없으면 default 를 쓴다. 다 없으면 채우지 않는다.

시점 질문(A: 노드가 생길 때 채운다 / B: 로드 때만 채운다)에 대한 답:

> 물어본건 A 여야 할거같은데. 그게 UX상 일관성이 맞아.

**읽기 3.** 10항의 "글로벌 설정식과 로컬 설정식"이 가리키는 것.

> jsonSchema 의 rootNode 에 설정하는 readOnly 나 deabled 같은걸 이야기한 것이다. 물론 그밖에 root 와 local 과 inherit 속성의 위계와 구성도 설계 대상이다.

**예약 층의 뜻(원문).**

> 추가로 visible 과 readOnly disabled 같은것도 있긴 하다. 참고로 pristine 는 값을 지우는 조건식이다. 즉, active 는 표시+값 존재 인거고, visible은 input 표시만 제어, pristine 는 해당 식이 true 가 될때 값을 빼는 역할만 한다.

이 가운데 `pristine`은 소유자가 곧 정정했다. 현행 공개 문서(`docs/agents/skills/schema-form-skill/knowledge/expressions.md`)대로 `pristine`은 값을 두고 `dirty`·`touched` 상태만 초기화하는 조건식이며, 값 지우기는 새 키 `&clearValue`로 둔다.

> 아 미안 그렇네 그건 dirty touched 를 초기화하는 플래그구나.... input을 남겨두고 값만 지우는건 없었나보네.... 이건 내 오해니, 신규 필드로 하자. 근데 옵션명이 만든사람도 햇갈리는거면 완전 잘못지은거 아닌가

## 3. 이번 세션에서 이미 정해진 것

### 3.1 채우기 규칙 A

없음인 키를 채우는 일은 **노드가 생길 때** 한 번 일어난다. 로드로 생길 때도, 조각이 나중에 켜져 생길 때도 같은 규칙이다. 원천은 `&default`(표현식) > `default`(표준 키워드) > 없음(채우지 않음)이다. "값이 빠질 때마다" 채우지 않는다. 그래서 `&clearValue`로 지운 값은 다시 채워지지 않는다.

이에 따라 4항의 "값을 조작하지 않는다"는 "조각의 켜짐·꺼짐은 **있는 값을 바꾸거나 지우지 않는다**"로 읽는다. 없음인 키를 채우는 것은 노드가 생기는 사건의 일부이며, 8라운드까지의 "전이 주입은 없음인 키에만"(`06-conclusions.md` 4.2)이 이 읽기에서 그대로 도출된다.

### 3.2 분기 컨벤션과 실측

폼은 `oneOf`/`anyOf`를 읽지 않는다. 분기의 필드는 노드가 되고, 그 필드를 언제 보이고 방출할지는 (가) 분기 안의 `if/then/else` 조각, (나) 예약 층(`&active` 등), (다) 둘 다 없으면 작성자 책임, 셋 가운데 하나다.

표준 검증기(ajv 8.17.1, draft-07과 2020-12 판정 동일; `../spikes/round9/REPORT.txt`)에서 실측한 사실:

| 배치 | 올바른 값 | 누락 값 | 어느 조건에도 없는 값 |
| --- | --- | --- | --- |
| `oneOf` 분기에 `if/then`만 | 거부 | 통과 | 거부 |
| `oneOf` 분기에 `if/then` + `else: false` | 통과 | 거부 | 거부 |
| `anyOf` 분기에 `if/then`만 | 통과 | 통과 | 통과 |
| `anyOf` 분기에 `if/then` + `else: false` | 통과 | 거부 | 거부 |
| `allOf` 항목에 `if/then`만 | 통과 | 거부 | 통과 |
| 최상위 `if/then` 하나 | 통과 | 거부 | 통과 |

귀결: `oneOf`/`anyOf`의 분기에 `if`를 쓸 때는 **`else: false`가 필수**다(없으면 `if`가 거짓인 분기가 공허하게 통과해 분기로 세어진다). `allOf` 항목과 최상위 `if/then`은 `else` 없이 된다. `allOf` + `if/then`은 어느 조건에도 맞지 않는 값을 거르지 못하며, 그 제약이 필요하면 작성자가 `enum`이나 `oneOf` + `else: false`를 쓴다. 이것은 검증기의 뜻이지 폼의 일이 아니다.

개발 모드 경고 후보(모두 `if`의 내용을 읽지 않고 키의 유무만 본다): `oneOf`/`anyOf` 분기에 `if`는 있고 `else: false`가 없음; 순수 분기끼리 같은 이름·다른 종류의 필드(노드 공유 규칙 ADR 0005 §3의 충돌).

| 키 | 표시 | 값 | 부류 |
| --- | --- | --- | --- |
| `&active` | 거짓이면 숨김 | 거짓이면 방출에서 제외(원본은 둔다) | 상태(참인 동안 유지) |
| `&visible` | 거짓이면 숨김 | 그대로 방출 | 상태 |
| `&readOnly`, `&disabled` | 잠금 | 그대로 | 상태 |
| `&watch` | 없음 | 없음. 의존 경로 선언 | 보조 |
| `&pristine` | 없음 | 참이 되면 `dirty`·`touched` 초기화. 값은 둔다 | 동작(전이 시점) |
| `&clearValue` | 없음 | 참이 되면 값을 뺀다 | 동작 |
| `&derived` | 없음 | 의존 값이 바뀌면 자기 값을 다시 계산해 덮는다 | 값의 출처 |
| `&injectTo` | 없음 | 자기 값이 바뀌면 다른 노드를 덮는다 | 동작 |
| `&default` > `default` | 없음 | 노드가 생길 때 없음이면 채운다 | 값의 출처 |
| `&children` | 자식 집합에 위 상태 키를 건다 | 같음 | 범위 |

값 조작 셋과의 대응: 없는 값 채우기 = `&default`/`default`; 있는 값 바꾸기 = `&derived`(자기), `&injectTo`(남); 있는 값 지우기 = `&clearValue`(원본에서), `&active: false`(방출에서).

## 4. 이번 라운드에서 도출할 것

각 항목은 "질문 → 축에서 무엇이 따라오는가 → 실행으로 확인한 것 → 남는 정책"의 순서로 답한다. 결정하지 않는다. 소유자에게 남기는 정책은 예/아니오로 답할 수 있는 한 문장으로 적는다.

- **Q1. 예약 층의 단계와 순서.** 작업 루프(표시 → 계산 → 파생 → 전이 → 커밋 → 통지 → 검증, ADR 0007)에서 각 `&` 키가 어느 단계에 놓이는가. 파생 단계 안에서 `&derived`·`&injectTo`·`&clearValue`의 순서, 같은 대상에 둘 이상이 쓸 때의 규칙, `&default` 채움과 다른 쓰기의 순서. 예산(라운드 상한)과 비수렴 시의 커밋(4.11 원본 B)이 새 목록에서도 그대로인가.
- **Q2. 값 조작 표.** 조작 셋(채움·변경·제거) × 시점(로드·노드 생성·런타임) × 주체(호출자·사용자·예약 층)의 표. 빈 칸이 있으면 축이 요구하는 장치가 빠진 것이다.
- **Q3. root·local·inherit 위계와 자식 집합 제어의 결합 규칙.** 루트 스키마의 `readOnly`·`disabled`(오늘: 루트 키 > 노드 키 > `computed.*` > `&*`, `checkComputedOptionFactory.ts:22-26`), Form 속성(오늘: OR, `SchemaNodeInput.tsx:111-112`), 조상의 조각 범위 제어, `&children`, 노드 자신의 키가 한 노드에 겹칠 때의 규칙. 후보 규칙: `active`·`visible`은 AND(모두 허용해야 켜짐), `readOnly`·`disabled`는 OR(하나라도 잠그면 잠김). `&children`의 값 형태 후보 둘(제어 종류별 대상+식 / 대상 집합별 제어 묶음)의 장단.
- **Q4. 노드의 유효 스키마 병합표(5항).** 검증 키워드(교차, 검증기의 것이므로 UI 힌트용), 주석 키워드(`title`·`description`·`readOnly`·`format`·`default`), 폼 전용 키(`FormTypeInput`, `options`, `&*`·`control.*`)의 세 부류에 대해, 본체·`allOf` 항목·켜진 `then`·켜진 분기의 순서로 어느 것이 이기는가. 오늘 코드는 두 규칙이 섞여 있다(`intersectSchema/utils/constants.ts:8-88`: `title`·`default`·`readOnly` 등은 먼저 이김, 나머지는 나중 이김). 8라운드의 5.3(D-29)은 이 표의 한 행이 된다. 유효 스키마가 바뀐 노드의 통지(4.9)도 포함.
- **Q5. 분기와 조각의 규칙 재서술.** §3.2의 컨벤션을 ADR 0002의 조각 표(가드·조각·문맥)로 다시 쓴다. 판별식 식별(ADR 0005 §4 E14)·값 가드·"판별 프로퍼티는 union 호스트가 소유"(E8)·상태 칸 `selection`·`setSelectedBranch`·초기 분기 추론·키 수 점수(4.4 D-14)·동점(5.5)이 지워지는지 하나씩 확인한다. 상태 칸이 원본과 `extras` 둘만 남는지. 2항(조건 프로퍼티는 `properties`에)을 컨벤션으로만 둘지 개발 모드에서 검사할지(검사하려면 `if`의 프로퍼티 이름을 읽어야 하므로 P1′와 닿는다).
- **Q6. 영향 목록.** `06-conclusions.md`의 3절·4절·5절·6절 항목마다 "그대로 / 바뀜 / 지워짐"과 이유. 특히 5.1(D-27 `fire`/`fill`), 5.2(D-11′ 에지/레벨), 5.3(D-29), 5.5(D-14′), 5.6 첫째(양방향 억제)가 열 항목에서 도출되는지. 편집자의 사전 판단은 5.5 지워짐, 5.1 `fire`, 5.2 에지, 5.3 켜진 조각이 덮음, 5.6 첫째 유지이며, 이것은 검토 대상이지 결론이 아니다. ADR 본문에서 바꿔야 할 문장 목록(`raw-round9-axis-mapping.md`의 14건에서 출발).
- **Q7. 남는 정책.** 5.4(예산 초과 시 제출 차단), 5.6의 `removeKey`·`findNodes`·`virtual`, `&pristine`의 새 이름, 그 밖에 이번 도출에서 새로 생기는 것.
- **Q8. 프로토타입.** `../spikes/round8/proto/loop-v4e.mjs`를 새 모델로 파생한 `loop-v5.mjs`: `selection` 칸 없음, 조각 게이트는 `if`(검증기 스텁) 또는 `&active`, 게이트 없는 조각은 무조건, 노드 생성 시 `&default` > `default` 채움, `&clearValue`·`&derived`·`&injectTo`는 에지, `&children`과 조각 범위 제어의 결합 규칙(Q3 후보), Q1의 단계 순서. 8라운드 회귀(`../spikes/round8/regress/`)를 다시 돌려 무엇이 달라지는지 표로 적는다.

## 7. 검증 뒤 정정 (2026-09-23, `raw-round9-verification.md` §4)

이 절은 도출 셋과 프로토타입이 §1–§4를 인용한 뒤에 덧붙였다. 앞 절의 줄 번호를 보존하려고 본문을 고치지 않고 여기에 적는다. **앞 절과 이 절이 충돌하면 이 절이 우선한다.**

1. **§3.1 채움의 단위(노드 단위).** "노드가 생긴다"는 그 노드가 직전 커밋의 형상에 없고 이번 정착의 최종 형상에 있다는 뜻이다. 본체, 게이트 없는 `allOf` 항목, 이미 켜져 있던 다른 조각이 두고 있던 노드는 새 조각이 켜져도 생기지 않으므로 다시 채우지 않는다. 프로토타입 v5의 첫 판은 조건부 조각끼리 공유한 노드(a1)와 게이트 없는 `allOf` 항목의 노드(a3)를 조각 단위로 다시 채워 이 문장과 어긋났다(검증 §2.4). 고친다.
2. **§3.1 노드 게이트는 조각 게이트와 같은 장치다.** §3.3의 통합 결정(한 장치, 두 범위)에 따라 노드 스키마의 `&active`가 거짓이면 그 노드는 형상에 없다(원본은 둔다, `getInactiveValues`로 읽는다). 그래서 로드 때 게이트가 거짓인 노드는 생기지 않아 채우지 않고, 거짓에서 참이 되는 것은 생김이므로 그때 없음이면 채운다. v5의 첫 판은 반대로 동작했다(로드 때 채우고, 켜질 때 채우지 않음). 고친다. 이것은 통합 결정의 귀결이므로 도출로 적되, 소유자가 읽고 확인한다.
3. **§3.2 표의 조건.** 표는 각 분기의 `if`가 조건 프로퍼티를 `required`에 넣은 스키마(`../spikes/round9/oneof-if.mjs:17`)의 결과다. `required`가 없으면 조건 프로퍼티가 없는 값에서 판정이 달라진다(검증 §2.3): `oneOf`/`anyOf` + `else: false`가 `{ x: 's' }`를 받아들이고, 빈 값 `{}`에서는 모든 가드가 참이 되어 폼이 모든 분기를 켠다. 그래서 컨벤션은 "`oneOf`/`anyOf`의 분기에 `if`를 쓸 때는 `else: false`와 `if`의 `required`가 함께 필수"다. "`if`에 `required`가 없음"을 개발 모드 경고에 넣을지는 `if`의 키 유무만 보므로 P1′ 안이지만, 작성자 의도(조건 프로퍼티가 없을 때 모든 분기를 켜고 싶을 수도 있음)를 단정하므로 정책으로 남긴다.
4. **§3.4 단계 열.** `&active`·`&visible`·`&readOnly`·`&disabled`·`&children`은 계산 단계, `&derived`·`&injectTo`·`&clearValue`는 파생 단계, `&default`·`default`의 채움은 전이 단계(노드 생성), `&pristine`은 커밋 단계(원본을 쓰지 않으므로, `adr/0007-settle-cycle.md:137`). `&pristine`의 부류는 "동작(전이 시점)"이 아니라 "동작(에지)"다.
5. **같은 대상 규칙.** 파생 단계는 라운드마다 후보를 모아 **대상별로 하나만** 적용한다. 차례로 적용하면 순환이 없는 스키마(`a`가 `t`에 주입, `t`는 `b`에서 파생)에서도 로드만으로 라운드 예산을 다 쓴다(검증 §2.5, 8라운드 프로토타입 재현). 채움은 가장 낮다(없음일 때만이므로). `&clearValue`는 채움을 이긴다(§3.1 "지운 값은 다시 채워지지 않는다"). `&derived`·`&injectTo`·`&clearValue` 사이의 순위는 소유자가 정한다.
6. **게이트 없는 `oneOf`·`anyOf` 분기의 유효 스키마.** 그런 분기는 노드의 존재만 더하고, 분기의 제약(`const` 등)은 공유 노드의 유효 스키마에 교차하지 않는다. 교차하면 `const 'a'`와 `const 'b'`가 공집합이 되어 검증기보다 좁은 힌트를 낸다. v5의 첫 판은 첫 선언의 스키마를 그대로 두어(`{const:'a'}`에 값 `'b'`) 틀린 힌트를 낸다. Q4 표의 한 행으로 적는다.
7. **Q3 루트 규칙의 변화 표시.** AND/OR 결합 후보는 오늘의 루트 우선 사슬(루트 `readOnly: false`가 노드의 식을 덮음, `checkComputedOptionFactory.ts:22-26`)을 바꾼다. 10항은 "기존과 같이"이므로 이 변화는 도출이 아니라 소유자 질문이다.
8. **바꿀 문장 하나 추가.** `adr/0008-event-system.md:60`의 배달 집합에 "유효 스키마가 바뀐 노드"가 없다. `06-conclusions.md` 4.9의 도출과 맞추려면 더한다.
