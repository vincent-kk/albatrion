2. **Q1·Q3·Q6은 좁혀지되 닫히지 않습니다.** 셋 모두 살아남은 두 선택지가 어느 축 문장과도 정면으로 부딪치지 않고, 서로 다른 목표 문장이 반대쪽으로 기웁니다. 남는 것은 각각 한 문장입니다.
3. **소유자의 반대 가치("작성자 선언 규칙이 로드한 데이터를 덮어써도 되는가")에 P2는 "된다(허용)"로 답합니다.** P2가 답하지 않는 것은 "로드가 그 규칙을 일으켜야 하는가"이고, 이것은 §3에서 `fire`로 도출됩니다. 반대 가치는 D-5 스위치의 범위로 호출 단위에서 실현되며, 이는 D-7(수락)이 `default`에 대해 같은 긴장을 푼 방식과 같습니다(§8).
4. **7라운드가 "D-27과 한 규칙"으로 묶은 Q1과 Q2의 결합은 `fire` 아래에서 풀립니다.** 로드 때 a1과 a2는 둘 다 파생 필드를 다시 계산하므로, Q1은 따로 정할 수 있습니다(§9).
5. **가설 여섯 가운데 Q2·Q4·Q5는 결론이 맞고 사슬이 다르며, Q1(레벨)은 도출되지 않고, Q3·Q6은 결론이 기울기와 같을 뿐 도출은 아닙니다**(§10).

1. **핵심은 같은 필드를 쓰는 정당한 주체 둘 사이의 순위입니다.** P2는 사용자 입력과 작성자의 선언 쓰기를 둘 다 정당한 주체로 열거하고 순위를 두지 않습니다(`03:10`). 축이 정한 순위는 둘뿐입니다. (α) 코어의 `default`는 있는 값을 덮지 않는다(`03:45`, `03:82`). (β) `injectTo`는 에지라서 원천이 다시 바뀔 때까지 사용자의 부분 쓰기를 되돌리지 않는다(`r7:34`, 증거 `adr/0007:79`). 어느 것도 "작성자 규칙 일반"의 순위로 적혀 있지 않습니다.
2. **G4는 a1을 지우지 못합니다.** G4 본문이 스스로 "여러 구문이 한 장치를 탄다"를 모범으로 듭니다(`00-goals:56`). a1에서 `&derived`와 `injectTo`는 선언 위치(대상 쪽 식 대 원천 쪽 함수, `inject-to.md:5-10,16,20`)만 다른 한 에지 장치의 두 구문입니다. a2에서는 두 개념에 두 장치입니다. 7라운드가 "G4가 반대 방향으로 쓰였다"고 본 것(`r7v:132`)은 이 두 합치 방식이 모두 G4에 맞기 때문입니다.
3. **G4가 지우는 것은 a2″입니다.** 입력 잠금에는 이미 `&readOnly`라는 장치가 있습니다(`expressions.md:3`). `&derived`가 입력도 잠그면 한 개념에 장치가 둘입니다. "잠금은 레벨의 귀결일 뿐 별도 장치가 아니다"라고 읽을 수도 있어 확신 중으로 적습니다.
4. **기울기는 서로 엇갈립니다.** a1 쪽은 직교성, 렌더러 준수에 기대지 않는 견고함, 코드 이주 없음입니다. a2 쪽은 값이 경로와 무관하다는 것입니다. 레벨 필드에서는 E3류의 배치 ≠ 순차 차이가 생기지 않습니다. 이 둘은 G4 한 문장(`00-goals:54`)의 "예측"을 서로 다른 대상(조합의 뜻 대 필드의 값)에 적용한 것이라, 어느 쪽도 지우지 못합니다.

### 2.3 분류와 남는 한 문장

**NARROWED.** 지워진 것: b(D-11 핵심), a2′(T-2), a2″(G4, 확신 중). 남은 것: a1, a2‴.

> "`&derived` 필드에 사용자나 호출자가 직접 쓴 값이 다음 의존 값 변화까지 남아도 되는가?" — 예 → a1, 아니오 → a2‴.

### 2.4 생각을 바꾸는 것

- 소유자가 G2의 "동적 표현식 시스템"을 **`&` 식 문자열에 한정**해 읽으면, a2는 식 체계의 표현력(덮어쓸 수 있는 식 파생)을 줄이므로 G2에서 탈락하고 a1이 도출됩니다.
- 소유자가 "계산 필드는 호출자의 직접 쓰기까지 이겨야 한다(불변식)"를 원리로 세우면 a2‴가 도출됩니다. `&readOnly`는 입력만 막고 `setValue`는 막지 않으므로(`types/jsonSchema.ts:332`) a1 + `&readOnly`로는 이것을 표현하지 못합니다.
- 소비자 스키마에서 파생 필드를 사용자가 고치는 사례가 흔한지, 문서의 "overwrites"에 기대는 사례가 흔한지의 조사(C8의 무게).
- `loop-v4e`의 `DERIVED_MODE='level'`이 새 비수렴이나 회귀를 보이면 a2 쪽 비용 근거가 됩니다.

### 2.5 귀결

- 어느 쪽이든: `adr/0013:41` "`&derived`는 원본을 쓰지 않는다"는 D-11 핵심에 따라 고쳐야 합니다(`r7:32`).
- **a1이면:**
  - `adr/0007:32`의 "`&derived`(읽기 전용)"에서 괄호를 지웁니다.
  - `expressions.md:47`과 `inject-to.md:3,8-9`를 "의존 값이 바뀔 때(그리고 로드 때 — §3) 다시 계산한다. 그 사이의 편집은 남는다. 잠그려면 `&readOnly`를 함께 쓴다"로 고칩니다.
  - C8: 코드 동작은 오늘과 같습니다(`AbstractNode.ts:541-551,556`). 이주 안내는 문서의 약속을 믿은 소비자를 위한 것입니다.
- **a2‴이면:**
  - `adr/0007:32`의 "읽기 전용"을 "작성자가 `&readOnly`를 함께 선언한다. 없으면 개발 모드 경고"로 적습니다.
  - C8: 오늘 사용자가 고칠 수 있던 파생 필드가 고칠 수 없게 됩니다. 이주 프롬프트는 "사용자가 고쳐야 하는 파생은 각 의존 필드의 `injectTo`로 옮긴다"입니다. `injectTo`는 함수여서 JSON으로 저장한 스키마에는 들어가지 않는다는 점도 적습니다(`inject-to.md:16,20`).
- 7라운드가 붙인 "D-27과 한 규칙"(`r7:57`)은 Q2가 `fire`이면 제약이 되지 않습니다(§9).

## 3. Q2 (D-27) — 마운트·`reset`·전체 교체에서 `injectTo`가 발화하는가

### 3.1 선택지와 오늘의 동작

| 기호 | 뜻 |
| ---- | -- |
| `fire` | 로드의 정착에서 기준점이 비어 있다. 방출에 값이 있는 원천은 모두 "없음에서 바뀐 것"이므로 발화하고, 대상을 전체 교체한다 |
| `skip` | 로드된 상태 자체가 기준점이다. 로드에서는 발화하지 않는다 |
| `fill` | 발화하되 **없음**인 대상에만 쓴다 |
| `ref` | 기준점은 로드 직전의 커밋이다 — 7라운드에서 탈락(`r7:63`) |
| 진입점별 규칙 | 오늘 코드. 7라운드에서 탈락(`r7:63`) |

오늘 코드는 진입점마다 다릅니다(Read로 확인, 실행하지 않음).

- **마운트는 발화합니다.** 생성자가 기본값을 `Default` 옵션으로 쓰는데(`StringNode.ts:117`) 그 옵션에는 `PreventInjection`이 없어 `inject`가 참입니다(`value.ts:51`, `StringNode.ts:46`). 테스트도 마운트 뒤 `'from:seed'`를 단언합니다(`core/__tests__/ObjectNode.branch.nullable.interface.test.ts:355,373`).
- **호출자의 `setValue(V)`도 발화합니다.** `Overwrite`에는 `PreventInjection`이 없고(`value.ts:63-65`), 부모가 같은 옵션으로 자식에 씁니다(`BranchStrategy.ts:273-274,293`).
- **노드의 `resetSubtree`는 발화하지 않습니다.** `StableReset`이 `Reset`을 거쳐 `PreventInjection`을 싣습니다(`AbstractNode.ts:1138-1144,1087-1092`, `value.ts:55,59`).
- **`FormHandle.reset`은 발화합니다.** 버전을 올려 트리를 다시 마운트합니다(`Form.tsx:151,186`).

### 3.2 도출 사슬

| 축 문장 (또는 증거) | `fire` | `skip` | `fill` | `ref` | 진입점별 |
| ------------------- | ------ | ------ | ------ | ----- | -------- |
| 로드는 한 사건이다: `03:42`(`setValue(V)`·`defaultValue`·`reset()`), `03:84` "셋 다 '전체 교체 뒤 로드 계약'의 사례", D-5 "`reset`·마운트 포함"(`HANDOFF:41`), D-7(`HANDOFF:43`), D-19 "통째로 받은 배열의 아이템과 `push()` 아이템은 로드"(`r7:38`); G4 `00-goals:54` | 통과 | 통과 | 통과 | 통과 | **탈락** |
| `03:83` 전체 교체는 이력을 읽지 않는다 | 통과 | 통과 | 통과 | **탈락** | — |
| G2 `00-goals:38`: 로드 때 "원천에서 대상 채우기" 능력 — 공개 문서의 용도 "Initial copy, default seeding"(`inject-to.md:10`), 오늘 마운트의 동작(위 테스트 `:373`) | 통과 | **탈락** | 통과(없음인 대상만) | | |
| `03:43` "injectTo — 전체 교체(대상에) — 위와 같다"(쓰기는 한 가지) + G4 `00-goals:54` 특수 경로 없음 | 통과 | 통과 | **탈락** — 로드에서만 쓰는 둘째 쓰기 방식 | | |
| P2 `03:10` + `03:45`·`03:82`의 범위 | 통과 — 작성자는 정당한 쓰기 주체 | — | fill의 근거가 될 문장은 "있는 값을 고치지 않는다"뿐인데, 그 문장은 코어 자신의 쓰기인 `default`에 딸려 있다 | | |

풀이는 다섯입니다.

1. **로드는 모두 한 규칙이어야 하고, 그 규칙은 로드 직전 상태를 읽을 수 없습니다.** 여기까지는 7라운드와 같습니다(`r7:63`). 남는 기준점은 이력과 무관한 둘뿐입니다. 비어 있음(`fire`)이거나 로드된 상태 자체(`skip`)이고, `fill`은 `fire`에 쓰기 거르개를 더한 것입니다.
2. **D-13만으로는 둘을 가르지 못합니다.** 마운트와 `push`는 **새 노드**를 만들고, 새 노드에는 직전 커밋이 아예 없습니다. D-13 "직전 커밋"(`r7:34`)을 새 노드에 문자 그대로 적용하면 두 완결이 모두 가능합니다. "없음에서 값으로 = 바뀜"으로 읽으면 `fire`이고, "비교할 것이 없음 = 에지 없음"으로 읽으면 `skip`입니다.
3. **`skip`은 G2가 지웁니다.** 로드 때 원천의 값으로 대상을 채우고 이후에는 편집할 수 있게 두는 능력은 오늘 공개 문서의 용도이자(`inject-to.md:10`) 오늘 마운트의 동작입니다(`:373`). 다른 FE 장치로는 대신하지 못합니다. 스키마 `default`는 정적이고, `&derived`는 a1이면 같은 규칙을 따르며 a2면 읽기 전용입니다. 부수 근거가 하나 있습니다. 로드 계약은 전체 교체 직후 없음인 키 모두에 `default`를 넣습니다(`03:45`). 증거 쪽 문장으로는 "전체 교체는 전이 기준을 비운다"입니다(F4, `adr/0007:79`). `skip`이면 같은 로드에서 전이의 기준점은 비고 `injectTo`의 기준점은 로드된 상태가 되어, 두 에지 방아쇠가 서로 다르게 초기화됩니다(G4 `00-goals:54`). codex는 둘을 같게 볼지가 선택이라고 경고했으므로(`codex:171-182`) 부수 근거로만 씁니다.
4. **`fill`은 G4가 지웁니다.** P2는 그 유일한 근거 후보를 떼어 냅니다. `injectTo`의 쓰기는 대상의 전체 교체 한 가지입니다(`03:43`). `fill`은 로드 정착에서만 쓰는 둘째 쓰기 방식을 더하므로, 7라운드가 진입점별 규칙을 지운 것과 같은 특수 경로입니다(`r7:63`). "없음인 키에만"과 "있는 값을 고치지 않는다"(`03:45`, `03:82`)는 로드 계약의 `default`, 곧 코어 자신의 쓰기에 딸린 문장입니다. P2는 작성자의 `injectTo`를 그것과 다른 정당한 주체로 열거합니다(`03:10`). 게다가 수렴된 D-13 아래에서 `injectTo`는 원천이 바뀔 때마다 대상의 있는 값을 덮습니다(`r7:34`, 증거 `adr/0007:79`). "작성자 규칙은 있는 값을 덮지 않는다"는 축의 규칙이 아닙니다.
5. **그러므로 `fire`입니다.** 로드 뒤 정착에서 투영된 방출(D-34 `r7:112`, 증거)에 값이 있는 원천은 모두 발화하고, 대상은 전체 교체되며, 비활성 대상에도 씁니다(D-28 `r7:106`, 증거). 로드 뒤의 정착은 다시 D-13의 직전 커밋 기준을 씁니다.

### 3.3 분류

**DERIVED — `fire`.** 사슬의 무게는 3단계(G2가 `skip`을 지움)에 실립니다.

### 3.4 생각을 바꾸는 것

- 소유자가 반대 가치를 **새 원리로** 세우는 경우입니다. "로드한 데이터는 기본적으로 작성자 규칙에 조작되지 않는다"이면 `fill`(없는 대상은 여전히 채우고 싶을 때)이나 `skip`이 됩니다. 이것은 P2의 읽기가 아니라 축에 새 문장을 더하는 일입니다(§8).
- 소유자가 G2를 **`injectTo`(함수)에 적용하지 않는다**고 읽으면 `skip`이 지워지지 않습니다. 그러면 `fire`와 `skip`이 남는 NARROWED가 됩니다. `fill`은 여전히 지워집니다.
- 소유자가 아래 3.5의 스위치 범위 확장을 거부하면 `fire`의 비용(저장된 레코드를 덮어쓰기)을 호출 단위로 피할 길이 없어집니다. 그때는 `fill`을 가치로 고를 이유가 커집니다.

### 3.5 귀결

- **D-5 스위치의 범위 — 소유자 확인 필요.** 소유자가 정한 스위치의 뜻은 "초기값 조작 비활성화"입니다(`HANDOFF:41`). `fire` 아래에서는 로드 정착의 `injectTo`·`&derived` 발화가 초기값 조작입니다. 한편 `03:45` "끄는 스위치는 이 하나만 끈다"와 `03:82` "유일한 자동 쓰기를 끄는 것"은 `default`가 유일한 자동 쓰기라는 옛 P2(`03:10`)를 전제로 합니다. 그 전제는 D-11 핵심(`r7:32`)과 7라운드 §4-2의 P2 문구(`r7:75`)로 바뀌었습니다. G4와 소유자의 뜻을 따르면 스위치는 "로드 정착은 자동 쓰기를 하지 않는다"(`default`·`injectTo`·`&derived` 모두)가 됩니다. 그래야 D-7(수락)의 이유 "form에 값을 씌우는 경우와 기본값을 설정하는 경우가 다르다"(`adr/0013:59`, 증거)가 `injectTo` 대상에도 지켜집니다. 이름(`disableDefaultInjection`은 좁아진다)은 D-18의 몫입니다.
- **`setValue(getValue())`**: 스위치 없이 부르면 사용자가 고친 `injectTo` 대상도 f(원천)으로 돌아갑니다. D-7이 받아들인 비멱등이 `default`에서 `injectTo` 대상까지 넓어집니다. 문서화 대상입니다.
- **같은 대상에 여러 원천이 같은 로드에서 쓰는 경우**가 흔해집니다. 그 순서는 Q3와 같은 모양의 위치 규칙을 요구합니다(§9). `injectTo`와 `default`가 한 대상에 겹치면 `injectTo`가 키를 채워 `default`(없음에만)가 지는데, 이는 P6 (i)의 최종 상태와 맞습니다(codex 모델 `codex:68`).
- **고칠 문장:**
  - `adr/0007:79`(F11) 옆에 "로드(전체 교체) 뒤 정착에서 기준점은 비어 있다"를 적습니다.
  - `r4s:34`("`reset()`은 `injectTo`를 일으킨다")는 그대로 맞습니다.
  - `inject-to.md:3,9`의 "once per change"를 "로드 때, 그리고 원천이 바뀔 때마다"로 고칩니다.
  - 스위치 범위 문장 `03:45`, `03:82`, `adr/0013:54`, `adr/0007:76`을 고칩니다.
- **열린 세부**: `injectTo`가 호스트 대상에 한 전체 교체가 "로드"인지가 증거 안에서 갈립니다. `03:43`은 호출자의 전체 교체와 같다고 쓰고, `adr/0007:76`은 스위치 목적상 로드가 아니라고 씁니다. `default`·스위치·이 기준점 셋이 같은 답을 따라야 합니다(G4).
- **C8**: 오늘과 달라지는 곳은 노드 `resetSubtree` 하나입니다(`skip` → `fire`). 마운트·`setValue(V)`·`FormHandle.reset`은 오늘도 발화합니다. 같은 값 재쓰기의 발화(D-33)는 별개 항목입니다.

### 3.6 가설 검사

결론은 맞고 사슬이 다릅니다. F11/D-13을 `reset`에 문자 그대로 적용하면 `ref`(직전 커밋 기준)가 나오고, 그것은 `03:83`이 지웁니다. 그래서 "없음에서 바뀜"은 F11에서 나오지 않습니다. 로드 단일성과, G2가 `skip`을 지운 것에서 나옵니다. `r4s:34`는 3.1판의 의도를 보이는 증거이지 축이 아닙니다. "`fill`은 `injectTo`를 두 모드로 만든다"는 맞고(`03:43`, `00-goals:54`), 가설에 없던 `skip`의 탈락은 G2가 담당합니다.

## 4. Q3 (D-29) — 최종 활성 집합의 여러 조각이 한 자식에 `default`를 줄 때

### 4.1 선택지

- **먼저-승**: 오늘 코드입니다. `FIRST_WIN_FIELDS`에 `'default'`가 있고(`helpers/jsonSchema/processAllOfSchema/intersectSchema/utils/constants.ts:8-20`, `:13`), `processFirstWinFields.ts:16-27`가 기저가 먼저인 순서로 적용됩니다(`processAllOfSchema.ts:34-53`).
- **나중-승**: 프로토타입입니다(`r4s:36`, `LV4C:1121` — 직접 열지 않고 `r7v:244`로 인용).
- **그 밖:** JSON 키 순서, 가드 평가 순서, 가장 최근에 켜진 조각, 충돌 시 주입하지 않음.

### 4.2 도출 사슬

1. **기준은 도출돼 있습니다.** 승자는 최종 형상의 유효 스키마가 가진 `default`입니다(D-12 `r7:33`). 따라서 Q3는 유효 스키마 합성 장치(증거 `adr/0005:45` — `intersectSchema`를 "활성 연언 조각의 교차"로 승격)가 `default`에 쓰는 우선순위 하나를 묻는 질문입니다. 조각 종류마다 다른 규칙은 G4(`00-goals:56`)가 지웁니다.
2. **표준은 순서를 주지 않습니다.** Validation §9.2는 "SHOULD remove duplicates"만 말하고, Core §7.7.1.1은 "스키마 위치"로 응용이 고를 수 있다고 합니다(§1.4). G3의 위임(`00-goals:45-48`)으로는 정할 수 없고, 위치에 기댄 규칙이어야 합니다.
3. **위치의 정의가 지우는 것:**
   - JSON 키 순서: 2라운드 S13, 전순서로 대체됐습니다(증거 `adr/0002:51`).
   - 가드 평가 순서: F13 힌트는 제거됐습니다(`r7:43`). codex도 평가 순서를 우선순위로 쓰지 않습니다(`codex:65-67`).
   - "가장 최근에 켜진 조각이 이긴다": 이력을 방아쇠 밖에서 읽고(`03:11`), 있는 값을 덮어야 합니다(`03:82`).
   - "충돌 시 주입하지 않는다": 선언된 `default`가 있는데 로드 계약을 어깁니다(`03:45`).
4. **남는 것은 전순서의 처음과 끝입니다.** 이 둘을 가르는 축 문장은 없습니다. 다만 축이 이미 **시간 위의 순위**를 정해 두었습니다. `default`는 없음인 키에만 들어가고(`03:45`) 있는 값을 고치지 않습니다(`03:82`). 그래서 커밋된 `default`는 뒤에 켜진 조각의 `default`로 바뀌지 않습니다. 순차 활성화에서는 "먼저 채운 쪽"이 이깁니다(`codex:196-208`의 순차 결과, C1 `codex:234-236`).
5. **흔한 충돌에서의 비교.** 기저 `properties`는 전순서의 처음이고(`adr/0002:51`, 증거) 늘 활성입니다. 예로 기저 `x: {default: 1}`, `if c then x: {default: 2}`를 봅니다.

   | 경로 | 먼저-승 | 나중-승 |
   | ---- | ------- | ------- |
   | `load {c:true}` (한 정착에서 둘 다 활성, x 없음) | 1 | 2 |
   | `load {}` 뒤 `c=true` (x가 이미 1이므로 주입 없음) | 1 | 1 |

   먼저-승은 기저에 `default`가 있으면 경로와 무관합니다. 나중-승은 조건이 **채울 때** 켜져 있었는지에 따라 값이 갈립니다. 조건부끼리의 충돌(N7)은 두 규칙 모두 경로에 따라 갈립니다(`codex:196-208`: 쓰기 순서가 선언 순서와 같으면 먼저-승이, 반대면 나중-승이 순차와 일치). 나중-승이 뜻하는 "구체적인 것이 이긴다"는 `03:82` 때문에 정착을 넘어서는 지켜질 수 없습니다. 먼저-승의 뜻은 가장 흔한 기저-조건부 충돌에서 늘 지켜집니다. 이것이 G4 "읽는 사람이 예측할 수 있어야 한다"(`00-goals:54`)의 기울기입니다. 그러나 경로 의존은 축이 받아들인 귀결이므로(`r7:94` §5.1, `r7:74` §4-1) 나중-승을 지우지 못합니다.
6. **G8은 갈립니다.** `json-schema-merge-allof`(RJSF의 `allOf`)는 `default: first`로 부모가 먼저입니다. RJSF의 `if/then`은 조건부가 기저를 덮습니다(`mergeSchemas(base, then)`, 둘째가 이긴다). ajv는 없는 프로퍼티만 채우고 여러 `default`의 경우를 문서에 적지 않았습니다(§1.4). 보편 관행이 하나가 아니므로 G8의 결정 규칙이 작동하지 않습니다.
7. **장치 일관성 — 기울기 먼저-승.** 오늘의 장치는 표준 주석 키워드 전부(`title`·`description`·`default`·`readOnly`·`format` …)를 먼저-승으로(`constants.ts:8-20`), FE 키를 나중-승으로(`processOverwriteFields.ts:15-25`) 합칩니다. `default`만 나중-승으로 바꾸면 표준 주석 묶음이 둘로 갈립니다. 표준 주석 전부를 나중-승으로 바꾸는 것도 G4에 맞습니다. 표시용 주석은 매 정착 다시 계산되므로 경로 의존이 없고(P3 `03:11`), 경로 의존은 쓰기로 소비되는 `default`에만 생깁니다.

### 4.3 분류와 남는 한 문장

**NARROWED.** 지워진 것: JSON 키 순서, 가드 평가 순서, 최근 활성 우선, 충돌 시 무주입, 조각 종류마다 다른 규칙. 남은 것: 전순서의 먼저-승과 나중-승(한 규칙, 최종 활성 선언에서).

> "여러 활성 조각이 한 자식에 서로 다른 `default`를 줄 때, 전순서의 뒤(더 구체적인) 조각이 이겨야 하는가 — 그 조각이 키가 채워진 뒤에 켜지면 이기지 못하는(없음에만 주입) 경로 의존을 받아들이고?" — 예 → 나중-승, 아니오 → 먼저-승.

기울기는 먼저-승입니다(4.2의 5·7, 오늘 코드, `json-schema-merge-allof`).

### 4.4 생각을 바꾸는 것

- 소유자가 "조건부 `default`는 기저 `default`를 덮으려고 쓰는 것"이라고 하고 그 경로 의존을 받아들이면 나중-승입니다.

- 표시용 주석을 나중-승으로 바꾸기로 하면, `default`만 먼저-승으로 두는 근거(쓰기로 소비됨)를 명시해야 합니다.

### 4.5 귀결

## 5. Q4 (D-31) — 자동 쓰기의 고정점이 예산 안에 수렴하지 않을 때 무엇을 커밋하는가

   - N1(`codex:130-138`): `base x; F:(x≠1) ⇒ x default 1; load {}`는 {} ↔ {x:1}로 돌고 고정점이 없습니다. ## 6. Q5 (D-32) — `extras`(호스트가 받은 미선언 키)의 방출 순서

### 6.1 선택지

- (i) 받은 순서를 상태로 본다: 순서 있는 칸.
- (ii) 방출에서 결정적으로 정렬한다.
- (iii) 삽입 순서를 이력으로 본다: 칸은 순서가 없고, 방출은 도착 순서를 따른다.
- (iv) 저장할 때 정렬한다: 원본의 순서를 고쳐 쓴다.

### 6.2 도출 사슬

1. **(iii)은 P4가 지웁니다.** 방출은 원본과 형상의 투영입니다(`03:12`). 도착 순서가 상태(`03:34`)에 없으면, 그 순서로 내는 방출은 이력을 읽습니다. 6라운드 #44·C22의 "같은 상태가 다른 직렬화를 낸다"(`round-6-coherence.md:49`, `raw-round6-principles-inventory.md:112`)는 이 (iii)에서만 참인 결함입니다.
2. **(iv)는 P2가 지웁니다.** 코어가 스스로 원본을 고치는 일은 없습니다(`03:10`). 호출자가 쓴 키 순서를 저장 단계에서 바꾸는 것이 그것입니다.
3. **(i)과 (ii)는 둘 다 상태의 함수이므로 G8의 결정 규칙이 가릅니다**(`00-goals:92`).
   - 보편적인 방식은 (i)입니다. ECMAScript 열거 순서는 정수 모양 키를 오름차순으로 먼저 두고, 나머지 문자열 키는 생성 순서를 따릅니다(MDN `Object.keys`). 전개·`Object.assign`은 있는 키의 자리를 지키고 새 키를 뒤에 붙입니다. 오늘 코드도 선언 키를 스키마 순서로, 나머지를 원래 열거 순서로 둡니다(`sortObjectKeys.ts:274-289`, 호출 `BranchStrategy.ts:246`). `Merge`는 `{...base, ...draft}`입니다(`BranchStrategy.ts:236`).
   - (i)은 어느 목표도 해치지 않습니다.
     - G1: JSON 객체는 순서가 없는 모음이고, 순서에 기대지 않는 구현은 상호운용됩니다(RFC 8259 §1·§4). 검증기의 판정은 순서와 무관합니다.
     - G5: 같은 쓰기 순서는 같은 순서 있는 상태를 냅니다(`00-goals:65`).
     - P3: 형상은 `extras`의 순서를 읽지 않습니다(`03:11`).
     - 서로 다른 쓰기 경로가 서로 다른 순서를 내는 것은 축이 받아들인 경로 의존과 같은 종류입니다(`r7:94` §5.1).
     - G6: (i)은 할 일이 없고, (ii)는 `extras`가 바뀔 때마다 정렬합니다(`00-goals:75`).
   - 그러므로 G8이 (i)을 고릅니다. 7라운드가 배열 `Merge`를 G8로 닫은 것(`r7:38`)과 같은 절차입니다.
4. **보조 근거.** P4는 투영 규칙을 "작성자가 고른다"고 합니다(`03:12`). (ii)의 정렬은 작성자도, 어떤 쓰기 주체도 고르지 않은 투영 규칙입니다.

### 6.3 분류와 규칙

**DERIVED — (i).** 규칙은 쓰기 표(`03:41-43`)와 JS 의미에서 나옵니다.

| 사건 | `extras`의 순서 |
| ---- | --------------- |
| 전체 교체(`setValue(V)`, 마운트의 `defaultValue`, `reset()`, 호스트 대상의 `injectTo`) | V의 미선언 키를 V의 열거 순서로. 이전 순서는 기억하지 않는다(`03:83`) |
| `setValue(V, Merge)` | V의 미선언 키를 V의 순서로 훑는다. 있는 키는 제자리에서 값만 바꾸고, 새 키는 뒤에 붙인다 |
| `undefined`를 쓰는 `Merge`, `removeKey` | 키가 빠진다(없음, 증거 `adr/0013:40`). 다시 쓰면 뒤에 붙는다 |
| 비객체 V | `extras`가 빈다(증거 F27 `r4s:160`) |
| 방출 | 선언 키(스키마 선언 순서, 증거 `adr/0007:55`) 다음에 `extras`를 **가진 객체의 열거 순서**로 |

"삽입 순서"만으로 적으면 정수 모양 키에서 틀립니다(`{b:1,"2":2}`의 열거는 `"2"`, `b`). 문서에는 "JS 객체의 열거 순서(정수 모양 키가 오름차순으로 먼저)"로 적어야 합니다. `Map`으로 들면 진짜 삽입 순서를 지키지만, 방출하는 평범한 객체가 다시 정렬하므로(MDN 예) 얻는 것이 없습니다.

### 6.4 생각을 바꾸는 것

- 소유자가 "같은 키·값 집합은 쓰기 경로와 무관하게 같은 직렬화를 내야 한다"를 요구하는 경우입니다(내용 해시·ETag 등). G5 너머의 새 요구이고, 그러면 (ii)가 됩니다.
- JSON Schema 폼 라이브러리 가운데 미선언 키를 정렬하는 주요 사례가 나오는 경우입니다. G8이 갈립니다.
- 순서에 따라 **판정**이 달라지는 검증기 플러그인이 나오는 경우입니다. RFC 8259 §4로 보아 없을 것으로 봅니다.

### 6.5 귀결

- `adr/0007:55`의 "잠정"을 떼고 위 표를 적습니다. Q14(`open-questions.md:86-88`)의 `extras` 부분을 닫습니다.
- 6라운드 #44·C22의 "원리 위반(P3)"을 "(iii)을 전제한 판정이며, 순서 있는 칸에서는 결함이 아니다"로 되돌립니다.

- C8: 오늘 코드와 같습니다(`BranchStrategy.ts:236`, `sortObjectKeys.ts:284-289`). 이주 영향은 없습니다.

### 6.6 가설 검사

"받은 순서는 이력이 아니라 상태"는 맞습니다. 근거는 P4가 방출되는 순서를 상태로 두기를 요구하고 G8이 그것을 지키는 쪽을 고른다는 것입니다. "정렬은 값을 고쳐 쓴다(P2)"는 한 단계가 틀립니다. 방출 단계의 정렬은 원본을 건드리지 않고, JSON에서 순서는 값의 일부가 아닙니다(RFC 8259). 게다가 설계는 이미 선언 키를 받은 순서가 아니라 스키마 순서로 냅니다(`adr/0007:55`, 오늘 `sortObjectKeys.ts:274-289`). 순서 바꾸기가 P2 위반이라면 그 규칙도 위반이 됩니다. P2가 지우는 것은 저장 단계의 정렬 (iv)뿐입니다. "Merge 키는 뒤에 붙는다(G8)"는 맞습니다.

## 7. Q6 (D-22′의 일부) — `settle.status`가 `budget-exceeded`일 때 제출을 막는가

### 7.1 선택지

- 차단: 프로덕션에서 `onSubmit`을 부르지 않습니다.
- 신호만: 제출은 검증기의 판정만 따르고, 예산 초과는 관측 채널로만 알립니다.
- 변형 셋: 검증기 에러 목록에 가짜 에러를 넣어 막기 / 이유를 알리지 않고 막기 / 개발 모드에서만 막기.

오늘의 제출은 검증 에러가 있으면 `ValidationError`를 던지고 `onSubmit`을 부르지 않습니다(`Form.tsx:114-125`). 예산 개념은 없습니다.

### 7.2 도출 사슬

1. **P1은 차단을 지우지 못합니다.** P1은 "폼의 판정 = validator(작성된 스키마, 방출 값)"입니다(`03:9`). 그러나 G1은 "폼이 더 엄격해지는 것은 허용되지만, 표준 판정에 AND로 덧붙는 형태로만"이라고 명시합니다(`00-goals:23`). ADR은 이것을 `폼 판정 = validator(…) ∧ FE추가검사`로 적었습니다(증거 `adr/0001:23`). "정착이 예산을 넘지 않았다"는 판정 **밖**에 AND로 붙는 전제이므로 G1이 허용합니다. 가설의 지우개는 작동하지 않습니다.
2. **지워지는 변형은 셋입니다.**
   - 가짜 검증기 에러: 판정 안에 폼의 것을 섞으면 판정이 더는 validator(스키마, 방출)가 아닙니다(`03:9`, `00-goals:19`, 증거 `adr/0001:19` "검증용으로 값에 무엇을 더하지도 않는다").
   - 이유를 알리지 않는 차단: C2 "작성자 실수의 가시성"(`00-goals:103`)에 어긋납니다.
   - 개발 모드 차단: 이미 D-16이 진입 끝 throw로 다룹니다(`r7:36`). 남는 질문은 프로덕션뿐입니다.
3. **신호만은 삽니다.** D-22 최소가 루트 `settle` 읽기와 `UpdateSettle` 구독을 도출했으므로(`r7:40`), 소비자는 자기 `onSubmit`에서 직접 막을 수 있습니다.
4. **신호만 쪽 기울기:**
   - P1′ "폼은 그 판정을 보여 줄 뿐"(`03:15`).
   - 수락된 "에러를 보여준다"(`HANDOFF:27`)와 소유자 발언 "어지간하면 입력 등을 막지 않고 error를 보여주려고 한다"(증거 `adr/0013:12`).
   - 비목표 "작성자의 실수를 폼 내부 검증으로 메우지 않는다"(`00-goals:120`).
   - D-16의 모양: 예산 초과는 커밋·검증·`onChange`의 흐름을 바꾸지 않습니다(`r7:36`).
   - Q4가 B이면 제출되는 스냅숏은 명시적 쓰기만 담고, 그 스냅숏이 검증됩니다(증거 `adr/0001:32`). 차단이 막는 것은 검증기가 보지 못하는 **빠진** 자동 쓰기(낡은 파생값, 빠진 `default`)뿐입니다.
5. **차단 쪽 기울기:** 지원 범위 밖의 커밋은 "결정적이되 임의적"입니다(증거 `adr/0007:57`). 낡은 파생값을 담은 채 검증기를 통과한 값이 서버로 갈 수 있습니다.

### 7.3 분류와 남는 한 문장

**NARROWED.** 지워진 것: 가짜 검증기 에러, 이유 없는 차단(개발 모드 차단은 D-16이 이미 다룸). 남은 것: 차단(G1의 AND 전제, 이유는 진단 채널로), 신호만.

> "프로덕션에서 검증기가 통과시킨 값의 제출을 작성자 스키마의 `budget-exceeded`만을 이유로 막아야 하는가?" — 예 → 차단, 아니오 → 신호만.

기울기는 신호만입니다.

### 7.5 귀결

- 차단이면 제출이 던지는 에러를 검증 실패(`SCHEMA_VALIDATION_FAILED`, `Form.tsx:117-123`)와 다른 종류로 둡니다. 이유는 D-22′의 진단 채널로 싣습니다.

## 8. 소유자의 반대 가치 — "작성자가 선언한 규칙이 로드한 데이터를 덮어써도 되는가"

**어느 질문이 기대는가.**

| 질문 | 기대는가 | 이유 |
| ---- | -------- | ---- |
| Q2 | **직접** | `fire`는 로드된 대상 값을 덮고, `fill`·`skip`은 덮지 않는다 |
| Q1 | 일부 | a2는 로드 때를 포함해 매 정착 로드된 파생 값을 덮는다. a1은 Q2의 규칙을 따른다(`fire`면 덮고 `fill`이면 남긴다). "아니오"이면 a2가 탈락한다 |
| Q3 | 아니오 | `default`는 없음인 키에만 들어간다(`03:45`) |
| Q4 | 아니오 | B는 비수렴 로드에서 로드한 데이터를 그대로 커밋한다 — "아니오"와도 맞는다 |
| Q5, Q6 | 아니오 | — |

**P2가 이미 답하는가 — "허용"까지는 답합니다.**

- P2는 "작성자가 스키마에 선언한 `injectTo`"를 네 정당한 쓰기 주체의 하나로 열거하고, 금하는 것은 코어 스스로의 수정뿐입니다(`03:10`).
- "없음인 키에만 / 있는 값을 고치지 않는다"(`03:45`, `03:82`)는 코어 자신의 쓰기인 로드 계약의 `default`에 딸린 문장입니다.
- 수렴된 D-13 아래에서 작성자의 규칙은 원천이 바뀔 때마다 대상의 있는 값을 덮습니다(`r7:34`, `03:43`).

그러므로 "덮어써도 되는가"에 축은 **된다**고 답합니다. P2가 답하지 않는 것은 "로드가 그 규칙을 일으켜야 하는가"이고, §3이 이것을 `fire`로 도출합니다. 소유자의 답이 "아니오"라면 그것은 P2의 읽기가 아니라 새 원리입니다. "로드한(호출자의) 데이터는 로드 시점에 작성자의 규칙보다 앞선다" — 이 원리는 왜 로드가 뒤의 원천 변화보다 특별한지를 설명해야 합니다.

**반대 가치는 이미 있는 장치로 실현됩니다.** D-5 스위치의 소유자 뜻은 "초기값 조작 비활성화"이고(`HANDOFF:41`), D-7은 "값을 씌우는 경우와 기본값을 설정하는 경우가 다르다"는 이유로 호출 단위 억제를 받아들였습니다(`HANDOFF:43`, 증거 `adr/0013:59`). §3.5처럼 스위치를 "로드 정착은 자동 쓰기를 하지 않는다"로 읽으면, 저장된 레코드를 조작 없이 씌우는 일은 호출 단위의 선택이 되고 기본은 `fire`로 남습니다. D-7이 `default`에 대해 같은 긴장을 푼 방식과 같습니다. 곧 반대 가치는 기본 규칙의 질문이 아니라 **스위치 범위의 질문**이 됩니다. 증거 쪽에서 설계는 "아무것도 고치지 않고 저장해도 서버의 데이터가 사라진다"를 결함으로 다룹니다(`adr/0002:130`). 이 스위치 범위 확장을 Q2의 답에 붙여 소유자에게 확인받아야 하는 이유입니다.

## 9. 질문 사이의 결합

- **Q1 × Q2.** 7라운드는 둘을 한 규칙으로 정하라고 했습니다(`r7:57`, `HANDOFF:60`). `fire` 아래에서는 a1(로드가 발화)과 a2(정의상 늘 계산) 모두 로드 때 파생 필드를 다시 계산하므로 결합이 제약이 되지 않습니다. 모든 의존 값이 없음인 로드에서만 갈립니다(a1은 발화하지 않고, a2는 f(없음)을 씁니다). 소유자가 Q2를 `fill`·`skip`으로 뒤집으면 a2가 탈락하고 a1이 같은 규칙을 따라야 합니다.
- **Q4 × Q6.** Q4가 B이면 차단의 근거가 "빠진 자동 쓰기"로 줄어듭니다. A였다면 "임의로 커밋된 자동 쓰기"까지 막아야 했습니다.
- **Q2 × Q3.** `fire`는 같은 로드에서 여러 원천이 한 대상에 쓰는 일을 흔하게 만듭니다. 그 우선순위는 Q3와 같은 위치 규칙 질문이며, 새 항목으로 올릴 만합니다.
- **Q2 × D-5/D-18.** 스위치의 범위(§3.5)와 이름.
- **Q5 × D-36.** `removeKey` 뒤에 같은 키를 다시 쓰면 뒤에 붙습니다(§6.3).

## 11. 확인하지 못한 것

- **실행.** 어떤 스파이크도 돌리지 않았습니다. 실행 사실은 7라운드 기록(`codex`, `spike7`)과 그 재현 기록(`r7v` §1)에서 인용했습니다. 동시 진행 중인 `loop-v4e`는 머리말만 읽었습니다.
- **Q1의 G8.** 다른 폼 라이브러리의 계산 필드(SurveyJS, Formily, final-form-calculate 등)가 에지인지 레벨인지 조사하지 않았습니다. 그래서 Q1 표에서 G8을 판단에 쓰지 않았습니다.
- **ajv의 적용 순서.** `useDefaults`가 기저 `properties`와 `allOf`/`then`의 `default` 가운데 어느 것을 먼저 평가하는지 확인하지 못했습니다. 그래서 ajv를 Q3의 어느 쪽 근거로도 쓰지 않았습니다.
- **직접 열지 않은 인용.** `LV4C:1121`(`r7v:244`로 인용), `SchemaNodeInput.tsx:51`(`r7v:123`로 인용).
- **D-33.** 오늘 수·불리언·null 노드의 같은 값 재쓰기 발화 여부는 확인하지 않았습니다.
- **소비자 코퍼스.** 파생·`injectTo`를 실제로 어떻게 쓰는지(편집 여부, 로드한 대상 값의 흔함)는 조사하지 않았습니다. Q1·Q2·Q3의 "생각을 바꾸는 것"에 해당합니다.
