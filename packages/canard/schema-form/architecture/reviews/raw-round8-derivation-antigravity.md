### Q1 (D-11′). 사용자가 `&derived` 필드를 덮어쓸 수 있는가

- P2(`03:10`)는 원본을 쓰는 주체를 넷으로 열거하며, 7라운드 수렴(`round-7:32`)으로 `&derived`는 작성자의 정당한 쓰기로 편입됐다. 사용자 입력과 작성자의 `&derived`는 모두 P2상의 정당한 주체다.
- **(a1) 에지 검증.** 사용자 편집 시 의존성이 바뀌지 않아 에지가 없으므로 입력이 보존된다. 그러나 P3(`03:11` "이력을 읽지 않는다")와 충돌 가능성 — `raw`에 출처 태그가 없으므로(`round-7:94`) 값이 f(deps)와 불일치해도 재계산하지 않으려면 직전 커밋 대비 의존성 변경이라는 에지 이력을 대조해야 한다. 더 결정적으로 G4(`00-goals.md:52`)와 충돌 — 변경 시점에 1회 전파되고 이후 편집이 유지되는 동작은 이미 `injectTo`의 장치다(`inject-to.md:3`). `&derived`마저 에지면 역방향 문법 설탕에 불과해 한 개념에 두 장치가 된다.
- **(a2) 레벨 검증.** 값이 의존성에 의해 항상 지배된다. `HANDOFF.md:27`·`03:79`에 비추어 입력을 열어 둔 채 매번 덮어쓰면 비일관적 UX가 되므로, 레벨이 성립하려면 입력이 차단(read-only)되어야 한다. 공개 문서 `expressions.md:47`("`derived` continuously computes … and **overwrites user edits**"), `inject-to.md:3-10`("Always-computed values / Recalculated — user edits overwritten")이 정확히 (a2)를 약속한다.
- **도출의 한계.** 축은 작성자와 사용자를 모두 쓰기 주체로 인정하지만, 스키마의 수식이 사용자 입력을 원천 배제해야 하는지에 대해 명시적 선언이 없다.
- **분류: NARROWED.** 잔여 질문: "작성자가 `&derived`로 지정한 필드는 사용자의 수동 편집을 허용하지 않는 엄격한 읽기 전용 계산값(레벨)이어야 합니까?"
- 반전 조건: 소유자가 "스프레드시트처럼 공식이 걸려 있어도 사용자가 임시로 수정한 값이 상위 입력이 바뀌기 전까지 유지되는 UX가 필요하다"고 선언하면 (a1). 단 `injectTo`와의 중복(G4)을 정당화하는 별도 제품 정의가 필요하다.
- 파급: (a2)면 현재 코드(`ComputedPropertiesManager.ts:92,208,260`)에서 `&derived`에 `readOnly`가 걸리지 않던 불일치를 해소해 자동으로 `readOnly: true` 효과를 부여. 공개 문서는 그대로. 이주(C8): 파생 필드를 수동 편집하던 폼은 `injectTo`로 전환. (a1)이면 공개 문서의 "overwrites user edits"를 "only when dependencies change"로 개정.

### Q2 (D-27). 마운트·`reset`·전체 교체 시 `injectTo`가 발화하는가

- `03:42` "`setValue(V)`, `defaultValue`, `reset()`: 전체 교체", `03:43` "`injectTo`: 전체 교체(대상에) … 위와 같다", `03:82` "로드 시 default는 없음인 키에만 (D-5): **있는 값을 고치지 않는다**", `03:84` "null 복귀·`setValue(getValue())`·억제 스위치는 한 규칙".
- **`fire` 검증.** 순수한 상태 전이 논리다. 전체 교체는 모든 원천이 MISSING → V[source]로 바뀐 에지이므로 일관되게 발화한다(`round-4-spec.md:34` "reset()은 injectTo를 일으킨다"). 그러나 호출자가 `{ source: 'A', target: 'custom' }`을 로드했을 때 `fire`는 `target: 'custom'`을 f('A')로 파괴하며, 이는 `03:82` "있는 값을 고치지 않는다"와 정면 충돌한다.
- **`skip` 검증.** 로드 데이터를 완벽히 보호하지만, `{ source: 'A' }`만 로드하면 초기 복사(`inject-to.md:10` "Initial copy, default seeding")조차 없어 대상이 영구히 빈다.
- **`fill` 검증.** `default`의 로드 계약(`03:45` "없음인 키에만, 전체 교체 직후")과 정확히 같은 형태. 비판: 런타임에는 덮어쓰고 로드 시에는 MISSING에만 채우므로 `injectTo`가 두 모드가 되어 G4(`00-goals.md:54`)의 순수성이 희석된다.
- **분류: NARROWED.** 잔여 질문: "호출자가 전체 교체로 주입한 대상 필드의 명시적 데이터가 있을 때, 작성자의 `injectTo` 규칙이 이를 덮어쓰지 않고 보존해야 합니까?" (예 → `fill` 또는 `skip`, 아니오 → `fire`)
- 반전 조건: "로드된 데이터는 호출자의 소유이며 폼의 어떤 규칙도 이를 훼손하지 않는다"를 절대 가치로 선언하면 `fire` 기각, `fill` 확정.
- 파급: `fill`이면 `round-4-spec.md:34`를 "전체 교체 직후의 `injectTo`는 대상이 없음인 경우에만 주입"으로 개정, `inject-to.md:10`과 부합. `fire`면 "초기 로드 시 `injectTo` 대상 필드가 덮어써질 수 있음"을 이주 안내에 강력히 경고.

### Q3 (D-29). 같은 자식에 여러 조각의 `default`가 있을 때 승자

- 7라운드 D-12(`round-7:33`)로 "승자는 최종 형상의 유효 스키마가 가진 `default`"라는 상위 기준은 수렴됐다. 조각의 순서는 `03:56`·`adr/0002:51`의 정적 전순서 (감싸는 조각 순서, 키워드 순위 `properties < allOf[i] < if/then/else < oneOf/anyOf`, 배열 인덱스)이므로 먼저-승과 나중-승 모두 이력을 읽지 않는 결정론적 함수다.
- **먼저-승 검증.** 현재 코드(`processFirstWinFields.ts:16-27`). **치명적 결함**: 본체 `properties`가 `default`를 선언하면 전순서에서 가장 앞서므로, 조건부 조각(`then`, `oneOf` 분기)의 `default`가 영원히 무시된다. 조건부 조각의 표현력을 무력화한다.
- **나중-승 검증.** 프로토타입(`round-4-spec.md:36`). 뒤에 오는 구체적 조각이 기본 조각을 좁히거나 덮는 CSS·객체 스프레드(`{...base, ...override}`)의 보편 관행(G8 `00-goals.md:92`)과 일치. `adr/0005:109`는 `default`의 순서가 표준의 귀결이 아니라 폼의 쓰기 규칙임을 명시하고 소유자 질문으로 남겼다.
- **분류: NARROWED.** 잔여 질문: "조건부 조각이 선언한 기본값이 본체 `properties`의 기본값을 덮어쓸 수 있도록 병합 순서를 '나중 선언 승리'로 전환해야 합니까?"
- 반전 조건: "본체의 메타데이터 불변성이 조건부 오버레이보다 우선하며, 조건부 조각은 기본값이 없는 필드에만 보충한다"고 판단하면 먼저-승.
- 파급: 나중-승이면 `intersectSchema`의 `FIRST_WIN_FIELDS`에서 `'default'`를 제거해 오버라이트 필드로 이동, `round-4-spec.md:36`·ADR 0005 5차 본문에 확정. 이주(C8): 조건부 조각 안에 무의미하게 적혀 있던 `default`가 실제로 동작하게 되므로 의도치 않은 기본값 변경 가능.

## 4. 소유자 대립 가치 "작성자의 규칙이 로드된 데이터를 덮어쓸 수 있는가"

- **Q1과 Q2 둘 다 이 가치에 직접 의존한다.** Q3·Q4·Q5·Q6은 무관하다.
- **P2는 답하지 못한다.** P2(`03:10`)는 작성자의 쓰기가 정당한 원본 변경 권한을 가짐을 천명할 뿐, 호출자의 쓰기와 작성자의 쓰기가 충돌했을 때의 우선순위를 정하지 않는다. 축 안에서 두 가치가 맞선다: (1) `03:82`·`adr/0013:57` "있는 값을 고치지 않는다"(호출자의 데이터 주권), (2) G2 `00-goals.md:38` "지금의 동적 표현식 시스템이 주는 표현력은 줄어들지 않는다. 표현 층은 값을 바꿀 수는 있어도 판정에는 닿지 못한다."와 `expressions.md:47` "overwrites user edits"(작성자의 표현식 주권). 따라서 "호출자가 명시적으로 제공한 기존 데이터가 있을 때 작성자의 규칙이 이를 이기는가"라는 소유자의 명시적 확인이 선행되어야 한다.
