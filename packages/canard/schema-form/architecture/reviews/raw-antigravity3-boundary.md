## 1. C1: 세 종류의 쓰기 — 전체 교체 vs 부분 쓰기

### 판정
**반례** (동시에 C1의 분류 정의와 **모순**)

### 증거 및 구체적 반례 시나리오

#### 명세 인용 (`round-3-spec.md` C1)
> ```
> setValue(V)        전체 교체. 대상 노드의 원본을 — 활성·비활성·extra를 포함해 — V로 바꾼다.
>                    V에 없는 자식의 raw는 지워진다(초기값이 아니라 없음이 된다).
> 부분 쓰기          지정한 부분만 바꾼다. 나머지 원본은 그대로다. 사용자 입력이 여기에 속한다.
> 활성 집합의 변경   원본을 바꾸지 않는다. 방출에서만 빠진다.
> ```

#### 충돌의 핵심
C1은 모든 사용자 상호작용을 "부분 쓰기(나머지 원본은 그대로다)"로 귀속시키고, 부재 자식의 원본 삭제는 "전체 교체(`setValue(V)`)"에서만 일어난다고 엄격히 이분화했습니다. 그러나 실제 UI 컴포넌트에서는 단일 사용자 입력이 하위 키의 명시적 삭제 또는 객체 전체의 재직렬화를 수반하며, C1의 이분법은 이를 올바르게 처리하지 못해 사용자 관점에서 버그를 발생시킵니다.

#### 시나리오 1: JSON 에디터 컴포넌트에서 특정 키를 삭제하는 사용자 입력
1. **상태 구성**:
   - 객체 노드 `config`가 활성 필드 `host: "localhost"`, `port: 8080`을 가지고, 비활성 조건부 분기(예: `mode === 'advanced'`)의 잠복 필드 `clusterKey: "SECRET"`을 `raw`에 보관 중입니다.
   - UI는 `config` 객체를 전문적으로 편집할 수 있도록 Monaco 기반 JSON 에디터 컴포넌트로 렌더링하고 있습니다.
2. **사용자 행동**:
   - 사용자가 JSON 에디터 텍스트에서 `"port": 8080` 줄을 지우고 `{ "host": "localhost" }`로 수정한 뒤 에디터 포커스를 해제(blur)합니다. 이는 명백한 단일 **사용자 입력**입니다.
3. **분류에 따른 버그 발생**:
   - **경로 A: C1 원칙대로 "부분 쓰기"로 분류할 경우**
     - C1: "부분 쓰기는 지정한 부분만 바꾼다. 나머지 원본은 그대로다. 사용자 입력이 여기에 속한다."
     - JSON 에디터는 diff 연산 없이 파싱된 전체 객체 `{ host: "localhost" }`를 `onChange`로 전달합니다.
     - core가 이를 부분 쓰기로 해석하면, 전달된 객체에 없는 `port`는 '나머지 원본'으로 취급되어 보존됩니다.
     - **결과**: 사용자가 화면(에디터)에서 분명히 `port`를 지웠음에도 불구하고 `getValue()`는 여전히 `port: 8080`을 방출합니다. 사용자는 이를 명백한 삭제 실패 버그로 규정합니다.
   - **경로 B: 삭제를 반영하기 위해 `setValue(V)`(전체 교체)로 분류할 경우**
     - C1: "V에 없는 자식의 raw는 지워진다."
     - JSON 에디터에 노출되지 않았던 비활성 분기의 `clusterKey: "SECRET"`까지 `V`에 없다는 이유로 원본에서 영구 소멸합니다.
     - **결과**: 사용자가 단지 활성 필드 하나를 편집했을 뿐인데, 나중에 `mode`를 `'advanced'`로 바꿨을 때 이전에 입력해 둔 잠복 설정이 증발해 버리는 데이터 유실 버그가 발생합니다.

#### 시나리오 2: 서브폼의 "지우기(Clear)" 버튼 동작
1. **상태 구성**: 복합 주소 필드 `address: { street: "123 Main St", zip: "12345" }`에 "주소 초기화(Clear)" 버튼이 있습니다.
2. **사용자 행동**: 사용자가 "주소 초기화" 버튼을 클릭합니다. UI는 빈 객체 `{}` 또는 `undefined`를 해당 필드로 전달합니다.
3. **분류 충돌**:
   - 사용자의 직접 상호작용이므로 C1상 "사용자 입력"입니다.
   - 하지만 '부분 쓰기' 규칙을 적용하면 `{}`는 아무런 부분도 지정하지 않은 것이 되므로 하위 자식(`street`, `zip`)의 원본이 보존되어 지우기 버튼이 no-op이 됩니다.
   - 이를 해결하려면 `setValue({})`라는 전체 교체를 실행해야만 하는데, 이는 "사용자 입력이 부분 쓰기에 속한다"는 명세 문장과 모순됩니다.

#### 추론 (배열 아이템 삭제 및 레코드 붙여넣기)
- **배열 아이템 삭제(Array remove)**: `[A, B]`에서 0번 아이템을 삭제하여 `[B]`가 되는 것은 사용자 입력이지만, 1번 인덱스의 자식 raw 소멸을 필요로 하므로 단순 부분 쓰기(나머지 유지) 의미론으로 설명되지 않습니다.
- **레코드 붙여넣기(Paste record)**: 사용자가 클립보드에서 부분 JSON을 붙여넣었을 때, 기존 폼의 누락 필드를 유지(부분 쓰기)해야 하는지 전량 대체(전체 교체)해야 하는지 C1의 "사용자 입력 = 부분 쓰기"라는 단일 규칙으로는 구분할 수 없습니다.

## 2. C2: 로드 계약 — 로드 직후 V와 getValue()의 불일치 요인 전수 열거

### 판정
**통과** (명세가 허용하는 방출 차이 요인 및 작성자 회피 수단의 체계적 정리 완료)

### 증거 및 전수 열거 비교 (round-2 S6의 5개 원천과 비교)

`round-2.md` S6에서 지적한 5가지 원천:
1. 미선언 키(extra)가 빠짐
2. `''`가 `omitEmpty`로 빠져 `required` 위반
3. `{}`가 `omitEmpty`로 빠짐
4. 꺼진 조각(비활성 분기)의 키가 빠짐
5. 첫 활성의 기본값(`default`)이 추가됨

C2가 적용된 시스템에서 로드 직후 사용자 행위 없이 `V !== getValue()`가 되는 모든 잔여 요인은 다음과 같습니다.

| # | 차이 발생 원인 | 발생 현상 | 수용 가능 여부 | 작성자의 회피 방법 | round-2 S6 비교 |
|---|---|---|---|---|---|
| 1 | **미선언 키 (Extra keys)** | 스키마에 선언되지 않은 임의의 키 | **차이 없음 (해소)** | 별도 조치 불필요 (기본 보존 및 방출) | S6-1 해소: C2에서 호스트 raw 보관 및 기본 방출로 해결 |
| 2 | **방출 정책 (`omitEmpty`)** | V의 `''`, `{}`, `[]` 등이 방출에서 누락 | **수용 가능** (의도된 방출 정책) | 폼/필드 옵션에서 `omitEmpty: false` 설정 | S6-2, S6-3 대응: 원본 변경이 아닌 방출 정책으로 규정 |
| 3 | **방출 정책 (`omitTrailing`)** | 배열 끝의 `null`/빈 아이템 누락 | **수용 가능** (의도된 방출 정책) | 배열 옵션에서 `omitTrailing: false` 설정 | S6-2 연관 항목 |
| 4 | **비활성 조각 (Inactive fragments)** | V에 꺼진 분기 키가 포함된 경우 방출에서 제외 | **수용 가능** (코어의 기본 계약) | 공통 속성으로 스키마 승격 또는 상호 배타성 제거 | S6-4 대응: 원본은 보존되나 방출 제외는 JSON Schema 유효성을 위해 필수 |
| 5 | **누락 키의 기본값 주입 (`default`)** | V에 없는 키에 스키마 `default` 값이 추가됨 | **조건부 수용** (단, Q3의 PATCH/Sparse 문제 잔존) | 스키마에서 `default` 선언 제거 | S6-5 대응: C2는 누락 키에 한해 의도적으로 주입을 유지함 |
| 6 | **무효 판별식 (Invalid Discriminator)** | V의 판별식 값이 어떤 분기 가드와도 불일치 | **수용 가능** (비정상 데이터 보호) | 유효한 판별식 전달 또는 스키마에 폴백 분기 정의 | S6 "더 나쁜 예" 해결: 임의 분기로 떨어지지 않고 에러 노출 |
| 7 | **금지 조각 (Forbidden fragments)** | `not: { required: ['x'] }` 등으로 x가 방출 제외 | **수용 가능** (스키마 정책) | 스키마에서 금지 제약 제거 | 신규 (A3 5항 반영) |
| 8 | **파생 규칙 (`injectTo`)** | 로드 즉시 계산 루프에서 다른 필드로 값 주입 | **수용 가능** (작성자가 명시한 쓰기) | 스키마에서 `injectTo` 규칙 제거 | 신규 (A4 반영) |

## 3. C2의 preserveDefaultValue 옵션 불필요 선언에 대한 검토

### 판정
**반례** (소유자가 발의한 핵심 유스케이스 미커버 및 C2 단언의 오류)

### 증거 및 구체적 반례 시나리오

#### 명세 인용
- `round-3-spec.md` C2:
  > "로드한 값(V)에 **없는** 키에는 `default`를 넣는다. V에 **있는** 키는 그대로다... 따라서 `preserveDefaultValue` 옵션은 두지 않는다. 위 두 항목이 기본 계약이면 옵션이 살 자리가 없다."
- `adr/0013-core-does-not-rewrite-values.md` 맥락:
  > 소유자: "기본적으로 서버 값은 클라이언트가 보낸 값을 그대로 저장했다가 돌려준다고 믿어진다. global dirty / touched를 관리하는 것도 있다. 그래도 걸린다면, 최초 주입된 defaultValue를 form 내부에서 자동으로 값을 바꾸지 않는 옵션을 추가해도 좋다."
  > 의미 후보 (b): "노드 단위로 보존한다. 로드한 값에 없는 키에는 default를 넣지 않고..."

#### 반례 시나리오: Sparse 레코드(부분 데이터) 로드와 Dirty 판정 왜곡
1. **스키마 정의**:
   ```json
   {
     "type": "object",
     "properties": {
       "id": { "type": "number" },
       "title": { "type": "string" },
       "status": { "type": "string", "default": "DRAFT" },
       "isArchived": { "type": "boolean", "default": false }
     }
   }
   ```
2. **서버 응답 로드**:
   - 서버는 부분 수정(PATCH) 또는 경량 조회 엔드포인트를 통해 클라이언트가 저장했던 레코드 `V = { "id": 101, "title": "First Post" }`를 반환했습니다.
   - 서버에는 `status`와 `isArchived` 필드가 저장된 적이 없습니다.
3. **C2 동작**:
   - C2의 절대 규칙: "로드한 값(V)에 없는 키에는 default를 넣는다."
   - 결과적으로 폼 로드 직후 `status := "DRAFT"`, `isArchived := false`가 주입됩니다.
   - `getValue()`는 `{ "id": 101, "title": "First Post", "status": "DRAFT", "isArchived": false }`가 됩니다.
4. **문제 발생**:
   - **자동 Dirty 발생**: 클라이언트 애플리케이션이 `isDirty` 플래그를 계산하거나 로드 값 `V`와 현재 `getValue()`를 비교하여 저장 버튼을 활성화하는 아키텍처에서, 사용자가 아무런 입력을 하지 않았음에도 폼이 '수정됨' 상태가 됩니다. 사용자가 뒤로 가기를 누르면 "변경사항이 저장되지 않았습니다" 팝업이 뜹니다.
   - **서버 데이터 오염**: 저장 시 서버로 `status`와 `isArchived`가 전송되어, 의도치 않게 서버의 sparse 데이터 모델이 기본값으로 덮어써집니다.
   - **옵션의 부재**: 작성자가 "신규 생성 시에는 기본값을 채우되, 기존 서버 데이터를 로드할 때는 없는 키라도 폼이 임의로 채우지 말 것(ADR 0013 안 b)"을 원해도, C2가 `preserveDefaultValue` 옵션을 제거해 버렸기 때문에 이를 방지할 수단이 없습니다.

따라서 "옵션이 살 자리가 없다"는 C2의 주장은 거짓이며, 소유자가 우려한 서버 데이터 보존 케이스를 완벽히 놓치고 있습니다.

## 4. C3: 비객체 호스트의 raw=17과 자식 raw — 이중 소유권 충돌

### 판정
**미정의** 및 **모순** (동일 경로의 이중 소유자로 인한 읽기/쓰기 불일치 반례 성립)

### 증거 및 구체적 시퀀스 분석

#### 명세 인용 (`round-3-spec.md` C3)
> "호스트에 17이나 'broken'이 주입되면: 호스트의 raw := 17, 자식은 모두 비활성(조각 순회를 하지 않는다), local은 없고 emit := 17. 검증기가 type 에러를 낸다. 다음에 객체가 주입되거나 자식에 부분 쓰기가 오면 호스트의 raw는 비워지고 자식이 다시 산다. 부분 쓰기는 raw가 비객체인 호스트 아래로 내려갈 때 그 호스트의 raw를 비운다(자식 하나를 고치면 호스트는 객체가 된다)."

#### 시퀀스 1: 자식 노드의 직접 읽기(`node.value`)와 루트 방출(`getValue()`)의 모순
1. 객체 호스트 `user`에 자식 `user.name`이 있고, 초기값 `{ name: 'Alice' }`가 설정되어 있습니다 (`name.raw = 'Alice'`).
2. 외부에서 `user.setValue(17)` 주입:
   - C3에 따라 `user.raw := 17`, 자식 노드들은 비활성화됩니다. 자식의 `name.raw = 'Alice'`는 삭제되지 않고 잠복합니다.
3. 이 상태에서 값을 조회합니다:
   - 루트 조회: `getValue('/user')`는 호스트의 `emit`인 `17`을 반환합니다.
   - 자식 노드 조회: 렌더 계층이나 자식 컨트롤러가 `findNode('/user/name').value`를 호출합니다.
     - ADR 0006 결정 5 및 round-3 A8: "비활성 노드도 원본을 유지한다... `node.value`는 투영 전의 로컬 메모를 반환하며, 리프는 local = raw이다."
     - 따라서 `user.name.value`는 `'Alice'`를 반환합니다.
   - **모순**: 동일한 상태에서 부모는 `17`인데 하위 노드는 여전히 `'Alice'`를 자신의 실제 값으로 보고합니다. ADR 0006 결정 4("부모와 자식의 값이 어긋날 수 없다. 구조 공유이지 사본이 아니다")와 정면으로 모순됩니다.

#### 시퀀스 2: 의미 없는 자식 쓰기(no-op partial write)에 의해 서버 에러 원본(17)이 증발하는 반례
1. `user.setValue(17)` 주입 상태 (`user.raw = 17`, `user.name.raw = 'Alice'`).
2. 화면에 마운트된 자식 입력 폼에서 blur 이벤트 등이 발생하여 기존 값과 동일한 값 `'Alice'`로 부분 쓰기 `user.name.setValue('Alice')`가 전달됩니다.
3. C3 규칙 발동:
   > "부분 쓰기는 raw가 비객체인 호스트 아래로 내려갈 때 그 호스트의 raw를 비운다(자식 하나를 고치면 호스트는 객체가 된다)."
4. **결과**: 사용자는 값을 전혀 변경하지 않았음에도 호스트의 `user.raw = 17`이 즉시 비워지고, 호스트가 객체로 부활하여 `getValue('/user')`가 갑자기 `{ name: 'Alice' }`로 변경되며 검증기의 `type: 'object'` 에러가 사라집니다. 에러 상태를 보존해야 하는 core의 원칙이 깨집니다.

#### 시퀀스 3: 조건부 활성화 변경(Activation change) 시의 미정의
1. `user` 객체가 `if: { properties: { enabled: { const: true } } }` 조각 아래에 있습니다.
2. `user.raw = 17`인 상태에서 `enabled`가 `false`로 바뀌어 `user`가 비활성화됩니다.
3. 다시 `enabled`가 `true`로 바뀝니다. A3 계산 단계가 시작됩니다.
4. **미정의 (명세의 침묵)**:
   - A3 1~3단계에서 호스트는 무조건 조각부터 순회를 시작하며 `L := compose(A)`를 계산합니다.
   - A3 3항은 `H의 raw가 null이면 L은 {}다`만 명시했을 뿐, **H의 raw가 17인 경우 L을 어떻게 계산하는지 전혀 규정하지 않았습니다.**
   - 만약 자식들을 compose하면 잠복했던 `'Alice'`가 되살아나 `emit`이 `{ name: 'Alice' }`가 되어 `17`이 소멸하는지, 아니면 C3의 "자식은 모두 비활성"이 A3의 출발점 알고리즘을 덮어써서 조각 계산을 영구 중단하는지 명세상 정의되어 있지 않습니다.

#### 시퀀스 4: `null` 주입과의 관할 충돌 (A6 vs C3 모순)
- 호스트에 `setValue(null)`이 들어왔을 때:
  - `null`은 객체 호스트 입장에서 명백한 비객체(non-object) 값입니다.
  - A6: "부모가 null이 되면 자식의 raw는 유지된다... null 호스트의 가드는 L = {}로 평가한다. 계산 중 null 호스트는 조각을 켜되 emit은 null이다."
  - C3: "호스트에 17이나 'broken'이 주입되면: 호스트의 raw := 17, 자식은 모두 비활성(조각 순회를 하지 않는다), local은 없고 emit := 17."
  - 호스트의 비객체 값이 `null`일 때 조각 순회를 도는지(A6), 아니면 조각 순회를 하지 않는지(C3) 두 조항이 정면으로 충돌합니다.

## 5. C4: "원본을 바꾸는 예외는 없다; 방출은 정책이다" 문구의 정합성 검토

### 판정
**모순**

### 증거 및 ADR 0006 / ADR 0007 문구 비교

#### 명세 인용 (`round-3-spec.md` C4)
> `"core는 값을 고치지 않는다"의 예외는 **방출 정책**(비활성 제외, omit, 금지 조각의 제외)이며, 모두 원본을 건드리지 않는다. "예외는 하나"를 "원본을 바꾸는 예외는 없다. 방출은 정책이다"로 고친다.`

#### 정면 모순되는 조항들

1. **ADR 0007의 기본값 자동 쓰기 (`raw` 직접 변경)**
   - `adr/0007-settle-cycle.md` 제28행:
     > `처음 활성이 된 노드에 원본이 없으면 기본값을 넣는다(자동 쓰기).`
   - `round-3-spec.md` A3 3항 (제44행):
     > `f가 선언한 자식 가운데 이번에 처음 활성이 되는 것에는 default가 주입된다 — 이것은 raw 쓰기이므로 그 자식이 dirty가 되고, 즉시 그 자식의 계산을 완료시켜 emit을 얻는다.`
   - **모순점**: 기본값 주입은 방출 투영(projection)이 아니라 **core가 노드의 `raw` 슬롯에 값을 직접 써넣는 명백한 원본 쓰기(raw 쓰기)**입니다. C4에서 "원본을 바꾸는 예외는 없다"고 단언하는 것은 코어 루프의 가장 핵심적인 상태 전이인 "기본값 자동 쓰기"의 존재와 정면으로 충돌합니다.

2. **`injectTo`의 원본 쓰기 파생**
   - `adr/0007-settle-cycle.md` 제70행 & `round-3-spec.md` A4:
     > `injectTo의 쓰기는 표시로 돌아간다.`
   - **모순점**: `injectTo`는 스키마 규칙에 따라 계산 루프 안에서 다른 노드의 `raw`를 변경합니다. 이 역시 방출 정책이 아닌 원본 조작입니다.

3. **C1의 `setValue(V)`에 의한 부재 자식 raw 삭제**
   - `round-3-spec.md` C1:
     > `V에 없는 자식의 raw는 지워진다(초기값이 아니라 없음이 된다).`
   - **모순점**: 부재 자식의 원본을 삭제하여 `없음`으로 만드는 것은 명백한 원본 파괴(raw modification)입니다.

4. **C3의 비객체 호스트 raw 소거**
   - `round-3-spec.md` C3:
     > `부분 쓰기는 raw가 비객체인 호스트 아래로 내려갈 때 그 호스트의 raw를 비운다`
   - **모순점**: 자식 노드에 쓰기가 일어났다는 이유로 core가 부모의 `raw`를 자동으로 삭제(비움)하는 것 역시 원본 수정의 명백한 예외입니다.

#### 결론
C4의 `"원본을 바꾸는 예외는 없다. 방출은 정책이다"`라는 문구는 수사적으로는 깔끔해 보이나, core가 실제로 수행하는 **(1) 최초 활성화 시 기본값 raw 주입, (2) injectTo의 raw 쓰기, (3) 전체 교체 시 부재 자식 raw 소거, (4) 비객체 호스트 raw 소거**라는 4가지 핵심 원본 변경 동작을 모두 부정하는 거짓 명제가 됩니다.

정합성을 맞추려면 다음과 같이 수정되어야 합니다 (추론):
> `"core는 사용자가 입력한 편집 원본을 임의로 정제하거나 변환(coercion/trim)하지 않는다. 비활성화, omit, 금지 조각에 의한 제외는 원본을 변경하지 않는 방출 정책이다. 단, 스키마에 정의된 기본값 주입(A3), 전체 교체 시 부재 자식 소거(C1), injectTo(A4)는 명세된 라이프사이클 쓰기로서 raw를 갱신한다."`
