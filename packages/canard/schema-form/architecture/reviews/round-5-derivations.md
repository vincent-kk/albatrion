# 5라운드 후속 — 결정 항목의 원리에서의 도출

소유자의 지적(2026-09-23): "읽을 때 가장 무거운 것들은 조사와 구체화로 풀 수 없는가? 정책 판단의 영역인가? 충분히 명답을 찾을 수 있는 영역 같다." 맞다. `round-5-decisions.md` §11의 모순 11건 가운데 정책 판단은 하나(D-3의 전제)뿐이었고, 그것도 소유자가 원칙으로 답했다. 나머지는 원리 P1–P5(`../03-mental-model.md`)와 이미 내린 결정에서 도출되거나, 프로토타입으로 확인됐다. 이 문서는 그 도출과 확인을 적는다. 여전히 **결정은 소유자의 것**이며, 여기 적힌 것은 "원리를 받아들이면 이렇게 된다"이다.

## 0. 소유자가 원칙으로 답한 것 (2026-09-23)

> "schema form으로서 특정한 값을 주입했을 때 기대되는 값은 그 값을 '유효성 검사를 통과하는 것으로 교정'하는 건가? 그걸 바랐다면 ajv autofix 같은 걸 쓰지 않았을까. 나는 form이 값을 바꾸도록 이전에 설계했고, 이 방식이 사용자에게 혼란을 준다는 걸 느껴서, 값 수정은 안 하고 에러만 보여주는 걸 기본 동작으로 하려고 했다. 빼거나 지우는 건 모두 `&`로 시작하는 명령으로 조작해야 한다. 그러면 JSON Schema 문법을 form이 추적하며 구현할 필요는 없다. 노드 타입을 결정하는 일부 동작(튜플, `type: [number, string]`)과 가변 구성을 위한 `if-then-else` 같은 일부 문법만 차용한다."

이것을 원리로 옮기면 P1이 더 날카로워진다.

**P1′. 폼이 스키마에서 읽는 것은 노드 트리의 모양을 정하는 문법뿐이다.** 타입(`type`, 다중 타입, 튜플), 자식의 존재(`properties`, `items`, `prefixItems`), 조건부 존재(`if/then/else`, `allOf`, `oneOf`/`anyOf`의 분기)까지다. 값의 유효성을 정하는 문법(`required`, `false`, `not`, `additionalProperties`, 범위·패턴 …)은 검증기의 것이고, 폼은 그 판정을 **보여 줄 뿐** 값을 고치지 않는다. 값을 빼거나 지우는 것은 작성자의 `&` 명령뿐이다.

2라운드의 "값 조작은 알아야 값을 처리할 수 있다"는 이 뜻이었다 — 폼이 `&active`로 값을 뺄 때 그것을 안다는 것이지, 표준 금지 구문을 읽어 값을 빼라는 것이 아니었다. 제가 넓게 읽었다.

## 2. D-3의 도출 (정책 판단이었던 것)

소유자의 원칙(§0)에서 D-3은 (iii)로 **도출**된다. `properties: {x: false}`와 `not: {required: ['x']}`는 값의 유효성을 정하는 문법이지 노드의 모양을 정하는 문법이 아니므로 폼이 읽지 않는다. `then` 안의 `x: false`는 "x라는 자식이 존재한다"는 선언도 아니고(false는 아무것도 선언하지 않음) 값을 빼는 명령도 아니다. x가 본체에 선언돼 있으면 보통 필드로 보이고 검증기의 에러가 붙으며, 본체에 없으면 잔여 키다(C-4). 숨기려는 작성자는 `&active`를 쓴다.

실무 관행도 같은 방향이다(antigravity 조사, scout 대조 6건 중 5 확정·1 미확인). zod와 TypeBox는 `never`를 `{not:{}}`(거부)로 낸다(확정). pydantic은 불리언 스키마를 아예 내지 못한다(issue #9731 확정). RJSF는 `false` 속성에 "지원하지 않는 필드" 템플릿을 그린다(확정). SchemaStore의 `github-pages-jekyll.json`(`source: false` — "안전 모드에서는 쓸 수 없다")과 `openhab-5.1.json`(`then: {not: {required: ['dimension']}}`)은 거부와 상호 배타의 뜻이다(확정). "963건 전수 조사, 67건·181건"이라는 수치는 방법이 없어 **미확인**이다. 주요 스타일 가이드(Google AIP, Microsoft, Zalando)는 이 패턴 대신 `oneOf`를 권한다(미대조).

남는 정책 판단은 없다. 남는 것은 세부다: `not.required` 에러를 호스트에서 자식으로 옮기는 표시 규칙과 기본 문구, `formatError`의 `false schema` 번역, 잔여 키 UI를 기본 렌더러가 제공하는지 — 모두 렌더 계층의 일이다.

## 3. 이 도출로 D-1–D-6이 어떻게 보이는가

| 결정 | 원리에서의 도출 | 남는 것 |
| ---- | --------------- | ------- |
| D-1 | null은 키 없는 전체 교체(P2). 자식 원본이 없음이 되고 로드 계약이 빈 상태를 만든다. "null 아래 원본을 남긴다"는 P2의 "호출자가 '없다'고 쓴 것을 숨겨 둔다"이므로 원리에 어긋난다 | 실수로 누른 null의 되돌리기는 입력 컴포넌트의 몫(표준 예제). `setValue(undefined)`의 정의 |
| D-2 | 형상은 상태의 순수 함수(P3)이므로 출발점 고정 + 재평가. 고정점이 없는 스키마는 지원 범위 밖이고 `budget-exceeded`로 관측 가능 | 상한 초과 시 제출을 막는가(진단의 청중). 청사진의 정적 검사 |
| D-3 | §2 | 표시 규칙·문구 |
| D-4 | 쓰기의 종류는 호출자가 선언(P2). 기본은 오늘과 같은 Overwrite. Refresh는 출처로 판단(F7) | 배열 Merge의 뜻, 입력의 객체 전체 쓰기가 로드인지 |
| D-5 | default 주입은 core의 유일한 자동 쓰기(P2)이므로 끄는 스위치는 그 하나를 끈다. Form 속성 = 기본, 호출 옵션 = 양방향 재정의, `reset`·마운트 포함 | 이름. `push()`로 만든 아이템이 로드인지 |
| D-6 | 참조 그룹은 값을 소유하지 않으므로 P2–P4 밖이고 표현 계층의 것(P5). `required`를 고쳐 쓰는 전처리는 P1′ 위반이므로 사라진다 | (a)와 (b)는 둘 다 P5와 양립한다 — 차이는 다른 렌더러 이식 시 바인딩의 두께뿐. 이것은 취향이 아니라 비용 비교이며 4라운드에 있다 |
