2026-10-07. 07 작업자(전환, `546b8f537`, `verification/07-switch/performance.md`, 자료 `profile-114-g26/`)가 G26 보고서를 다시 쓰며 React 층과 번들을 새로 쟀다(Q114). ### 114C-01 (가) 배열 연산 세 행은 코어 몫과 React 층 몫으로 나눠 보고한다(측정과 계수만); (나) 1.0–1.2배의 갱신 행은 94C-02의 동률 규칙(세 회차 모두 1.0 초과일 때만 미달)을 먼저 적용하고, 남는 미달 행은 코어 몫과 React 층 몫으로 나눠 코어 몫이 104·110라운드가 받아들인 원인(쓰기당 고정비, 첫 갱신의 1회 비용)인지 밝힌 뒤 소유자에게 올린다 — 편집자가 수용으로 넓혀 읽지 않는다; (다) 번들은 TEST-075의 예산이다: 기준 37,023 B에서 늘면 "이유를 적고 Vincent가 받아들여야 병합"이므로 기록으로만 두지 않고, 비중 분해(settle·blueprint·dispatch의 어떤 모듈이 몇 바이트인가, 옛 판에 없던 기능이 차지하는 몫과 같은 기능의 구현 차이가 차지하는 몫)와 줄일 수 있는 자리의 상한을 붙여 소유자에게 올린다; 줄이는 일 자체는 소유자가 정한다

- 닫는 항목: TEST-075(보충), GOAL-011(보충)
- 결정:
  - 【추론】 React 층의 갱신 목표 1.0배는 94C-02가 "세 회차 모두 1.0을 넘을 때만 미달"로 정했으므로 1.01–1.04의 행은 그 규칙을 먼저 받는다. 남는 미달 행은 두 몫으로 나뉜다: 코어 몫(같은 폼의 코어 갱신 간극이 React wall에 그대로 실린 것)과 React 층 몫(렌더·커밋·바인딩). 07의 읽기대로 코어 몫이 104·110라운드가 받아들인 원인이라면 소유자가 그 수용을 React 층의 wall 행까지 넓힐지 정할 자리이고, React 층 몫이 새로 있다면 그것은 7단계의 코드 수준 대상이다 — 그 구분 없이는 어느 쪽인지 알 수 없으므로 분해가 먼저다(48C-01·49C-01: 수용은 적힌 원인까지). 배열 연산 세 행(1.35–1.65배)은 코어 표에 같은 행이 없으므로 더욱 분해가 먼저이며, 코어 몫이 크면 코어 표에 배열 연산 행을 더해 같은 규칙으로 판정한다. 번들은 다르다: TEST-075는 기준 37,023 B를 두고 "늘면 이유를 적고 Vincent가 받아들여야 병합"이라 했고 GOAL-011은 "번들 크기도 예산이다"라 했으므로, 2.17배는 기록으로 두는 것이 아니라 소유자의 수용이 필요한 사항이다. 올리기 전에 이유를 적을 수 있어야 한다: 비중 분해를 모듈 단위로(core/settle 43%의 안에서 단계별, core/blueprint 17%, dispatch 8%), 그리고 옛 판에 없던 기능(전체 문법 호환의 조각 열거, 게이트 고정점, 정적 분석, 개정 원장, 운영 모드 불변 보장)이 차지하는 몫과 같은 기능을 다르게 구현해 커진 몫을 나누어 적고, 코드 수준으로 줄일 수 있는 자리(죽은 내보내기, 중복 도우미, 개발 전용 코드가 운영 번들에 남은 것, 통째 재내보내기)의 상한을 붙인다. 줄이는 일을 7단계에서 할지 개선 단계로 보낼지는 소유자가 그 분해를 보고 정한다. 측정이 겹치지 않도록 (가)(나)의 분해는 분기 장부 작업의 첫 세션 앞에 붙이고, 번들 분해는 측정과 무관하므로 바로 한다.
