# 453라운드 닫기 — 분기 전환 단계의 개시: 단계의 자리, 설계 명제와 세 항 예산, 게이트 판정의 통일(검증기 분기 포함), 단계 구성과 관문, 에이전트 배정

2026-10-27. 소유자의 발언 셋(`reviews/round-453-owner-answers.md`)에 따라 분기 전환 단계를 열고 계획서(`plan/branch-switch/`)를 확정한 결정을 기록합니다. 본문의 "위 N행"은 그 문서의 소유자 발언을 가리킵니다.

## 편집자 결정

- **453C-01 (분기 전환 단계의 자리와 가지)**
  - 【추론】 452C-01이 분기 전환을 다음 단계의 유일한 주제로 넘겼고 소유자가 그 단계를 열었다(위 1행 "이제 분기 전환에 집중한다", 위 3행 "진행을 허가합니다"). 단계는 설계 최적화 단계 뒤, 9단계 앞이며 계획서는 `plan/branch-switch/`다. 가지 `feat/schema-form-branch-switch`는 설계 최적화 가지(`feat/schema-form-design-optimization`, b8db53997) 위에 쌓고, #472와 #445가 병합되면 base를 옮긴다. PR 규칙(가설 하나에 PR 하나, DETAIL 선행, 스쿼시 병합, 독립 검토, 원장 검사)은 LANDING-211·451C-04 그대로다. 보류한 D2-P5 가지 `perf/schema-form-d2-sibling-linear`(4681c0aff)는 이 단계의 B2 자료이며, 그 PR이 병합되거나 폐기될 때 지운다. 이 단계의 범위는 분기 전환뿐이고 마운트·일괄 입력의 추가 최적화는 하지 않는다(452라운드 위 3행 "분기전환 문제에만 집중").
- **453C-02 (설계 명제 — 게이트 전환의 비용은 O(G) 작은 상수항 + O(Δ) + 작은 바닥, 호스트 크기 항과 잠복 수 항은 없앤다)**
  - 【추론】 현재 src를 번들해 센 쓰기 한 번의 작업량(`plan/branch-switch/request.md` 사실 절)에서, `active` 호스트의 자식 선택은 이미 O(A+Δ)이고 형상은 매번 비게이트 baseline에서 처음부터 계산되어 바퀴 이전 구조와의 차분이 나감·들어옴이 된다(SETTLE-044·GOAL-029는 지금도 지켜진다). 변화량에 비례하지 않는 항은 선택 밖에 있다: 바퀴 준비의 O(G) 복사·검사 여러 번, 나가는 노드마다 루트 선언 D개를 훑는 나감 정책 읽기(쓰기당 12회), 자식 엔트리 E개 전수의 출력 재조립, 잠복 L개 전수를 다시 읽고 정렬하는 비활성 값 메모, 정착마다 다시 만드는 잠복 경로 색인, `[path, identity]` JSON 키의 stringify·parse 왕복. 측정값은 형제 0·분기 2 폼의 쓰기 하나가 0.100 ms(0.16.1은 0.031 ms), oneOf-80이 쓰기당 0.255 ms이므로 고정 바닥 약 100 µs와 분기당 약 1.9 µs의 호스트 크기 항으로 갈린다(0.16.1은 바닥 31 µs, 분기당 0.08 µs). 따라서 설계 명제는 "게이트 G개를 모두 다시 평가하되(BLUEPRINT-007 유지) 평가 하나를 입력 identity 비교 수준으로 내리고, 평가 밖의 장부는 Δ에만 비례시킨다"이며, 관문(쓰기당 56 µs)에 맞춘 예산은 바닥 40 µs 아래·게이트당 0.1 µs·노드당 1 µs다. 바꿀 것은 네 묶음이다: Ⅰ 게이트 판정의 통일(453C-03), Ⅱ 호스트 수명 준비물(바퀴 계획·엔트리별 나감 정책·정적 자식 준비물 SETTLE-052), Ⅲ 변화량 적용(노드가 드는 잠복 키, 증분 비활성 값 메모, 영속 색인만 사용, 활성 자식 A개만 걷는 조립, Δ 집합을 재사용하는 존재·재계산 등록), Ⅳ 남는 바닥. Ⅴ 설계 Ⅱ(NODE-060, 내부 레코드 유지와 수명별 핸들)는 Ⅰ~Ⅳ로 관문에 못 미칠 때만 B3의 수치로 소유자가 착수를 정한다. 0.16.1처럼 꺼진 분기의 공개 노드를 살려 두는 것(NODE-044 기각), 역색인, 정착 단계 순서·공개 겉면·시험 기대값 변경은 하지 않는다.
- **453C-03 (게이트 판정의 통일 — `if`·`active`·`discriminator`를 "읽기 목록 + 판정 함수" 하나로, 검증기 분기 포함, B1 최우선)**
  - 【추론】 소유자가 검증기(`if`/`then`)가 판정하는 분기 전환을 대상에 넣고 앞선 개선과 맞물리게 고치는 것을 최우선으로 하라고 했다(위 2행). 코드에서 게이트는 `if`(검증기 guard, `validation/utils/guard/readFieldNodeGuard.ts:15-38`이 `compileGuard`로 포인터마다 한 번 컴파일), `active`(식), `discriminator`(태그 값 집합) 셋이고 모두 `selectEntryStep.ts:100-135`의 `evaluateGate`를 거치므로 소유자의 "내부 경로는 동일하고 판정만 검증기"는 맞다. 다만 직접 선택 계획과 선택 표는 `active`에만 있어(`getDirectChildSelectionPlan.ts:102`) `if`·`discriminator` 호스트는 바퀴마다 모든 엔트리를 돌고 입력 일관성 검사가 실패해 전체 바퀴를 두 번 돌며 게이트마다 호스트 값을 복사한다(`evaluateGate.ts:51`). 분기 80개에서 쓰기당 엔진 호출이 `active` 2,752회, `if` 19,706회, `discriminator` 20,467회다. 그래서 B1은 청사진이 게이트마다 `GatePredicate { reads, evaluate }`를 컴파일하게 한다: `active`는 식 의존 목록, `discriminator`는 호스트의 태그 속성 하나(태그 값 → 엔트리 표로 O(1) 선택), `if`는 호스트 투영 객체 하나(identity 비교)와 extras를 `reads`로 두고 guard를 등록된 occurrence에 한 번 묶는다. 선택 계획·선택 표·게이트 입력 메모(BLUEPRINT-053)는 `reads`만 보고 동작해 세 종류가 같은 O(A+Δ) 선택을 타고, `if`·`discriminator`의 입력 객체는 호스트마다 라운드당 한 번만 만든다. 입력 메모는 입력이 모두 `Object.is`로 같을 때 직전 결과를 쓰는 순수 술어의 결과 재사용이라 GOAL-029·BLUEPRINT-007(모든 게이트 재평가, 역색인 없음)과 어긋나지 않으며, 던진 평가는 메모하지 않는다. 게이트 없는 oneOf/anyOf·allOf·virtual·배열은 분기 전환이 아니고 dependentSchemas는 경고만 내는 미지원이라 대상이 아니다. 검증기 분기의 관문은 같은 형상의 `active` 행에 게이트당 guard 호출 1회의 비용을 더한 값 안이며(편집자 수치, 대기열 68), 0.16.1에 같은 의미의 쌍이 있으면 그 쌍의 1.5배도 함께 적는다.
- **453C-04 (단계 구성 B0~B5와 관문, 447C-06 하한 추정의 정정)**
  - 【추론】 관문은 소유자가 유지했다(위 2행 "그래"): oneOf-80 왕복이 0.16.1의 1.5배 안이고 1 ms 아래(446C-06). 같은 형상의 `discriminator` 행도 같은 선, `if` 행은 453C-03의 선, 형제 1,000 전환이 형제 0의 작은 상수 배 안, 다른 canonical 행과 구독 경로 행은 TEST-073 선 안, B2 노드당 힙은 Node가 단계 시작 이하이고 Bun은 452라운드의 수용에 따르며 설계 Ⅱ는 보유 메모리 상한을 따로 적는다. 단계는 B0 측정 장부(쓰기 한 번의 단계별 µs와 할당 장부를 형제 0·oneOf-80·깊은 분기 하나에 대해 세 게이트 종류로 측정 장치에 추가, `switch-if-80`(AJV)·`switch-discriminator-80` 행 추가, 두 번째 바퀴의 원인 확인, 단계 시작 판 b8db53997과 0.16.1) → B1 게이트 통일 → B2 준비물과 Δ 적용(가설마다 PR 하나) → B3 관문 재측정 → (조건부) B4 설계 Ⅱ → B5 마감(통합 판 재측정, React `--equivalent`, B2 힙, 루트 PR, 설계 문서·ADR 반영)이다. B1~B3의 목표선은 B0의 장부로 측정 전에 고정한다(TEST-081). 447C-06의 "설계 Ⅰ만으로 쓰기 한 번 하한 약 61 µs, 설계 Ⅰ+Ⅱ로도 왕복 0.156~0.24 ms"는 도출 과정과 원자료가 기록되지 않았고(452라운드 자료 조사) 이번 작업량 추적이 그 가정과 다른 비용 구조를 보였으므로, 이 단계의 관문이나 착수 판단에 쓰지 않고 B0의 장부가 대체한다. 이것은 편집자의 이전 판단에 대한 정정이며 재검증 목록에 올린다. 측정 프로토콜은 그대로다(20 예열·100 표본·3 실행, 조용한 창, 폭 (다), 재측정 없음).
- **453C-05 (이 단계의 에이전트 배정 — PROCESS-069 적용, 멀티에이전트 진행)**
  - 【추론】 소유자가 멀티에이전트 작업으로 진행하라고 했다(위 3행). PROCESS-069와 `AGENT-POLICY.md`를 이 단계에 그대로 적용한다: Fable 오케스트레이터는 소유자 대화·설계·판단·원장·커밋만 맡고 코드를 고치지 않으며, 구현·게이트·측정·PR은 codex gpt-6.1-sol high(Orca `worker-start`), 독립 검토는 antigravity, 읽기·추적 보조는 Claude 하위 에이전트(이번 라운드의 작업량 추적이 그 예), 동시 워커는 둘까지, 전체 시험과 측정은 한 번에 하나다. 코디네이터 대기 규칙(PROCESS-073)과 워커 상태 알림 규칙도 그대로다.
