# 14라운드 — 오류 처리 기법 확장 조사 원문 (cennad antigravity, tier high)

2026-09-24. 소유자 지시("이 error 처리 기법에 대해서 확장 조사를 한번 해보세요 … 베스트케이스와 논리적 완결성을 지닌 방법을 찾으세요")에 따른 외부 조사 원문이다. 편집자는 고치지 않았다. 1차 응답에서 React의 개발 모드 경고 대 프로덕션 침묵 항목이 빠져 한 번 보완을 요청했다. 폼 엔진 비교표(1-나)는 조사자의 서술이며 행마다 출처가 붙어 있지 않아 편집자는 참고로만 쓴다. 판정과 반영은 `adr/0014-error-policy.md`.

# 폼 엔진 오류 처리 정책 조사 및 판정 보고서

## 1. 선행 사례 조사
### 가. 리액트(React) 및 검증 라이브러리 오류 처리 동작
| 대상 | 오류 처리 동작 | 설계 근거 및 메커니즘 (출처) |
| :--- | :--- | :--- |
| 리액트 개발 환경 경고 대 운영 환경 침묵·축약 (불변식 검사 및 컴포넌트 속성 검증) | 개발 환경에서는 상세한 콘솔 경고(`console.error` 및 `console.warn`)와 설명적인 불변식(`invariant`) 메시지를 노출하나, 운영 환경 빌드에서는 경고 로직이 완전히 제거(침묵)되거나 예외 메시지가 식별 번호와 URL 링크로 축약됨 | 운영 환경 번들 크기 축소와 실행 성능 극대화를 위해 불필요한 연산을 빌드 단계에서 사멸 코드 제거(Dead Code Elimination)로 배제하고, 불가피한 런타임 예외는 오류 해독기(Error Decoder) 웹페이지를 통해 역추적하도록 유도함 ([리액트 공식 문서: 오류 해독기](https://react.dev/errors), [리액트 공식 문서: 운영 환경 빌드를 통한 성능 최적화](https://legacy.reactjs.org/docs/optimizing-performance.html)) |
| 리액트 렌더 단계 예외 | 에러 바운더리 포착 또는 컴포넌트 트리 언마운트 | 손상된 사용자 인터페이스를 방치하는 것보다 완전히 내리는 것이 안전함 ([React 문서](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary)) |
| 리액트 이벤트 핸들러 예외 | 에러 바운더리 미포착, 전역 이벤트 전파 | 렌더링 수명주기 외부 동작이므로 기존 화면을 유지한 채 브라우저 전역 에러로 방출 |
| `reportError` | 실행 중단 없이 브라우저 전역 오류 보고 | 현재 스크립트 실행을 중단하지 않고 전역 감시 도구로 오류를 전달하는 표준 ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/reportError)) |
| 훅(Hook) 규칙 위반 | 즉시 치명적 예외 발생(throw) | 컴포넌트 상태 메모리 배열 순서의 붕괴 및 상태 오염을 원천 방지 ([React 문서](https://react.dev/warnings/invalid-hook-call-warning)) |
| 최대 갱신 깊이 초과 | 연속 갱신 제한(50회) 도달 시 즉시 예외 발생 | 무한 루프로 인한 브라우저 탭 멈춤 및 메모리 고갈 강제 차단 ([React 19 문서](https://react.dev/reference/react-dom/client/createRoot)) |
| Ajv 엄격 모드(Strict) | 알 수 없는 키워드 검출 시 기본 예외 발생(throw) | 조용한 위음성(False-Positive)으로 인한 데이터 오염과 보안 결함 차단 ([Ajv 문서](https://ajv.js.org/strict-mode.html)) |
| Zod / Valibot | `parse`(예외 발생) 대 `safeParse`(결과 객체 반환) | 조기 실패(Fail-Fast) 단언과 호출자의 안전 분기 처리를 위한 이중 표면 제공 ([Zod 문서](https://zod.dev/?id=safeparse)) |

## 2. 소프트웨어 공학 원리
| 공학 원리 | 핵심 논거 | 폼 엔진 적용 관점 및 출처 |
| :--- | :--- | :--- |
| 조기 실패(Fail-Fast) 대 점진적 저하 | 결함 발생 즉시 중단해야 상태 오염 확산을 방지함 | 잘못된 스키마로 지속 동작 시 데이터베이스에 오염된 데이터가 영구 적재됨 |
| 포스텔 법칙 비판 | 비표준 입력을 너그럽게 수용하면 결함이 표준화됨 | 모호한 스키마를 엔진이 임의 해석하면 잠재적 결함이 은폐됨 ([RFC 9413](https://www.rfc-editor.org/rfc/rfc9413.html)) |
| 충돌 전용(Crash-Only)·Let-it-crash | 불완전한 예외 복구 로직이 더 큰 버그를 유발함 | 복구 불가능한 상태는 즉시 중단하고 완전한 초기 상태로 복구함 ([Candea & Fox](https://www.usenix.org/legacy/events/hotos03/tech/full_papers/candea/candea.pdf)) |
| 사이트 신뢰성 공학 에러 예산 | 결함을 숨기면 연쇄 장애로 확대됨 | 시스템 오류는 투명하게 드러나야 통제 및 개선이 가능함 ([Google SRE 문서](https://sre.google/sre-book/error-budget-policy/)) |
| 운영 환경 로그의 위험성 | 조용한 데이터 손상(Silent Data Corruption) 발생 | 금융·행정 폼에서 결함 억제는 화면 멈춤보다 치명적인 법적·재정적 손실 초래 |
| 예외 은폐 금지 | 처리되지 않은 예외 무시는 상태 불일치를 유발함 | 노드제이에스(Node.js) 미처리 프로미스 거부의 프로세스 강제 종료 정책 ([Node.js 문서](https://nodejs.org/api/process.html#event-unhandledrejection)) |

## 3. 논리적 완결성을 가진 정책 후보 비교
오류의 세 축(주체: 작성자/호출자/소비자/사용자, 시점: 청사진/정착/통지/검증, 복구 가능성: 형상 파괴/값 계약 파괴/단순 입력값) 기반 비교입니다.

| 비교 항목 | 후보 1: 계약 무결성 엄격 실패 정책 | 후보 2: 단일 오류 채널 및 기본 투척 정책 |
| :--- | :--- | :--- |
| (a) 규칙 정의 | 폼 형상과 값 계약을 깨뜨리는 모든 시스템 오류는 환경 불문 최외곽 동기 진입 끝에서 예외를 던지고, 사용자 입력만 노드 진단으로 흘린다. | 모든 시스템·스키마·콜백 오류는 폼 루트의 단일 오류 채널(`onError`)로 보내며, 처리기가 등록되지 않으면 기본값으로 예외를 던진다. |
| (b) 청사진 오류 / 호출자 오류 | 즉시 예외 발생(throw) | `onError` 호출 후 미처리 시 즉시 예외 발생 |
| 청사진 경고 / 정착 경고 | 개발 환경 콘솔 경고 (운영 환경 침묵) | `onError`로 경고 객체 전달 또는 개발 환경 콘솔 |
| 정착 오류 (예산 초과) | 개발·운영 환경 불문 최외곽 진입 끝에서 예외 발생 | `onError`로 전달 후 미처리 시 예외 발생 |
| 리스너 오류 | `reportError` 전파 및 최외곽 진입 끝 예외 발생 | `onError`로 전달 후 미처리 시 예외 발생 |
| 검증기 오류 / 검증 결과 | 검증기 컴파일 실패는 예외 발생 / 사용자 검증 실패는 노드 오류 | 컴파일 실패는 `onError` / 검증 결과는 노드 오류 |
| (c) 취약 사례: 서버 사이드 렌더링 | 렌더링 중 예외 발생 시 서버 페이지 렌더링 중단(500 응답) | 오류 처리기가 없으면 서버 렌더링 중단 동일 |
| 취약 사례: 저장 리스너 실패 | 리스너 예외가 상위로 전파되어 동기 흐름 중단 | 오류 처리기가 오류를 무시하면 데이터 누락 은폐 |
| 취약 사례: 외부 스키마 수용 | 사소한 표준 미준수 키워드에도 폼 마운트 전면 실패 | 오류 처리기에서 경고로 완화 가능하나 렌더링 충돌 위험 |
| (d) 이벤트 핸들러 예외 시 사용자 화면 | 에러 바운더리가 미포착. 화면은 백지화되지 않고 직전 커밋 상태를 유지하며 콘솔에 미처리 오류 표시 | 처리기 미지정 시 후보 1과 동일. 처리기 지정 시 토스트·모달 안내 가능 |

## 4. 소유자 방향("안 되면 터뜨린다")에 대한 권고 및 비교
### 가. 세부 구현 방식 비교 (안 A 대 안 B)
| 비교 기준 | 안 A: 최외곽 진입 끝 단일 예외 던짐 + 커밋 값 유지 | 안 B: `onError` 단일 채널 통합 + 미처리 시 기본 예외 던짐 |
| :--- | :--- | :--- |
| 동작 방식 | 정착 루프를 완료하여 직전 유효 커밋을 유지한 후 최외곽 동기 진입 끝에서 1회 예외 발생 | 모든 오류를 `onError` 속성 하나로 전달하고, 핸들러가 없으면 기본 핸들러가 예외 발생 |
| 장점 | 엔진 내부 불완전 상태가 노출되지 않음. 데이터 무결성이 보장되며 제어 흐름이 명확함 | 상위 컴포넌트가 모니터링 도구 연동 및 사용자 피드백을 단일 지점에서 일괄 제어 가능 |
| 단점 | 상위 컴포넌트가 오류를 가로채 사용자 안내로 전환하려면 각 이벤트 호출부를 감싸야 함 | 소비자가 빈 핸들러(`onError={() => {}}`)를 주입하면 조용한 데이터 오염이 다시 발생함 |
| 논리적 완결성 | 높음: 프레임워크 계약을 온전히 준수하며 원자적 전이 실패를 명확히 단언함 | 중간: 소비자의 자의적 오류 은폐로 인해 조기 실패 철학이 훼손될 위험 존재 |

### 나. "운영 환경 신호만(기존 설계)" 대비 득실 판정
- **얻는 점**: 잘못된 스키마나 파생 순환으로 손상된 폼 데이터가 백엔드로 침묵 속에 전송되어 데이터베이스를 오염시키는 '조용한 데이터 훼손(Silent Data Corruption)'을 완벽히 차단합니다.
- **잃는 점**: 사용자 관점에서 일시적 순환이나 사소한 스키마 결함에도 입력 작업이 중단되므로 서비스 가용성 지표가 하락합니다.

### 다. 외부 조사자 최종 판정
**안 A(커밋 보존 후 최외곽 진입 끝 예외 발생)를 기본 원칙으로 채택하고, 브라우저 표준 `reportError`를 결합할 것을 권고합니다.**
안 B는 소비자가 오류를 고의로 삼킬 수 있어 조기 실패의 완결성을 파괴합니다. 폼 엔진의 최우선 가치는 '화면 유지'가 아니라 '정확한 데이터 계약의 수호'입니다. 리액트 이벤트 핸들러 내의 예외는 에러 바운더리를 발화시키지 않아 사용자 인터페이스를 백지화하지 않으면서도, 개발자 도구와 모니터링 체계에 즉시 장애를 각인시키므로 소유자의 목적에 가장 부합합니다.
