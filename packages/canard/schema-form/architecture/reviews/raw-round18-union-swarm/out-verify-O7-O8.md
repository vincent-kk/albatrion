# O7·O8 정합성 검증

검증 방법: `merged-v2.md` §1–§4·§7·§8 규칙 문장, 원장 BLUEPRINT-011/012/021/033, SCHEMA-001/007/008/044, SETTLE-001/003/007/010, VALUE-030, EVENT-045/064, WRITE-056/084, REACT-027 원문, 오늘 코드 `processAllOfSchema.ts`·`processSchemaType.ts`·`validateCompatibility.ts`·`winglet/json-schema/src/filters/isCompatibleSchemaType.ts`·`extractSchemaInfo.ts`·`getMergeSchemaHandler.ts`를 읽었습니다. `d-rule-a.mjs`의 `interpret`를 가져와 O7 전이와 O8 절차(2.6–2.10을 적힌 그대로)를 `$TMPDIR/o78/sim.mjs`로 실행했습니다. 아래 줄 번호는 `merged-v2.md`의 줄입니다.

## O7 판정: 정합하지 않음 — 원리는 JSON Schema와 맞습니다. 그러나 한 진입 안에서 게이트를 켜는 쓰기를 어느 목록으로 해석하는지가 정해져 있지 않습니다. 그래서 같은 `setValue(V)`가 직전 상태에 따라 다른 원본을 만듭니다(F1). 고칠 문장 1–3을 넣으면 정합합니다.

### 검사 1 — 표준 의미만 쓰는가
- 결론: 새 문법은 없습니다. 켜진 `then`은 연언으로 적용되므로 JSON Schema에서도 유효 형은 `schemaType ∩ then.type`입니다. ㄴ′는 이 교집합을 목록으로 쓸 뿐입니다. P1′가 폼이 읽도록 허용한 `type`만 읽고 `enum`은 읽지 않으므로 4.17(`enum:[1,'a']`의 `"1"`은 문자열로 남음)과도 모순이 없습니다. 둘의 차이는 P1′로 설명됩니다.
- JSON Schema가 말해 주지 않아 저자가 따로 알아야 할 것은 넷이며, 모두 동작이지 문법이 아닙니다.
  1. 변환(규칙 A)은 폼의 기능입니다.
  2. 입력 위젯과 `node.type`·`schemaType`은 게이트를 따라 바뀌지 않습니다. 위젯을 바꾸려면 필드를 `then`/`else` 안에만 선언해야 합니다(E27).
  3. 게이트가 켜지기 전에 들어온 값은 변환되지 않고 경고등만 켜집니다.
  4. 게이트가 `null`을 빼도 `nullable`과 비우기는 바뀌지 않습니다(편집자 12, 590행).

### 검사 2 — 노드 단위와 칸 단위
- 자리: `schemaType`과 `UnionSpec`은 칸마다 하나이며 배열 아이템이 공유합니다(3.1, 222행). 유효 목록은 덧씌움 집합마다 메모합니다(3.2, 226행). 이 메모는 유효 스키마 메모의 열쇠(BLUEPRINT-021, SCHEMA-007 "활성 덧씌움 집합마다")와 같습니다. 그래서 게이트 상태가 같은 아이템은 같은 참조를 받고, 다른 아이템은 다른 목록을 받습니다.
- 다시 계산하는 때: 계산 단계가 유효 스키마를 만들 때입니다(SETTLE-003). 경고등은 커밋 때 "원본이 바뀐 노드 ∪ 유효 스키마가 바뀐 노드"에서 다시 정합니다(3.14, 292행; 배달 집합은 SETTLE-007).
- 비용: 새 덧씌움 집합마다 O(k) 교집합 한 번(메모)이 듭니다. 유효 스키마가 바뀐 노드마다 경고등이 O(1)입니다(마스크).
- "같은 값을 두 번 읽으면 같은 참조" 약속: `schemaType`, Hint, 유효 스키마, 유효 목록 모두 지켜집니다. 다만 3.1은 "`kinds`는 `schemaType`과 같은 참조, 칸마다 얼림"이라고 말하고, 3.5(252행)는 `interpret(value, spec)`가 유효 목록을 쓴다고 말합니다. 두 문장이 서로 어긋납니다. spec을 덧씌움 집합마다 두어야 이 약속이 성립합니다(F2).
- 모름: 배열 아이템의 유효 스키마 메모가 칸 단위 공유인지 노드 단위인지는 원장에 없습니다. 어느 쪽이어도 참조 안정성은 같습니다.

### 검사 3 — 경고등
실행 결과(`schemaType` `['string','number']`, 게이트가 `number`로 좁힘):

| 전이 | 원본 | 경고등 전 → 후 | 쓰기 |
|---|---|---|---|
| 꺼짐→켜짐 | `"abc"` | false → true | 없음 |
| 켜짐→꺼짐 | `"abc"` | true → false | 없음 |
| 켜짐→꺼짐 | `42` | false → false | 없음 |
| 켜진 채 `"42"`를 침 | — | `interpret` = `42`(꺼짐이면 `"42"`) | 입력 쓰기 |

- 경고등은 쓰기 없이 켜지고 꺼집니다. 소급 변환은 없습니다. 그래야 하는 까닭은 넷입니다.
  1. 계산 단계는 원본을 읽기만 합니다(SETTLE-003 E1, SETTLE-010).
  2. `interpret`는 쓰기 경계에서만 돕니다(WRITE-056, 3.9 274행).
  3. 변환하면 게이트를 켰다 끄는 것만으로 `"42"`가 `42`로 남아 되돌릴 수 없게 됩니다.
  4. 게이트가 그 값을 읽으면 게이트 ↔ 값의 순환이 생깁니다.
- `VALUE_TYPE_MISMATCH`는 게이트 변화로 켜질 때도 보냅니다(3.15, 295행). 다만 그 기록의 `source` 값이 정해져 있지 않습니다(F8).
- 단일 종류 노드와의 일관성:
  - 게이트가 제약을 바꿔도 다시 해석하지 않는다는 축에서는 같습니다.
  - 경고등은 VALUE-002의 '계산' 칸이고 유효 목록이 그 입력이므로, 입력이 바뀔 때 다시 계산되는 것은 자연스럽습니다. 예측할 수 있습니다.
  - 그러나 단일 number 노드에 게이트 `then:{type:'integer'}`가 붙은 경우는 어긋납니다. O7 행(493)과 원장 변경 행 511은 "union 노드"로 한정하지만, 3.2와 3.6은 "단일 노드는 원소 하나인 경우"라고 말합니다. 그래서 `['number','string']`+게이트 `['integer','string']`에서는 `1.5`의 경고등이 켜지는데, `number`+게이트 `integer`에서는 켜지지 않습니다(F5).
- 알림: 쓰기 없이 경고등만 바뀐 노드는 `UpdateValue`가 아니라 유효 스키마 변경 비트(EVENT-064 `UpdateJsonSchema`)로 배달됩니다. VALUE-030의 "바뀌면 `UpdateValue`가 알린다"는 문구와 맞지 않습니다(F7). 루트는 게이트를 바꾼 쓰기 때문에 같은 커밋에서 `UpdateValue`를 받습니다. 코어에는 글로벌이 없어서 게이트는 값 변화로만 바뀌기 때문입니다(SETTLE-003).

### 검사 4 — 기본 입력의 초안
- 좁혀진 동안 `"abc"`를 치면 보내지 않고 초안으로 듭니다(4.13, 377행).
- 치는 도중에 게이트가 꺼지는 경우(외부 `setValue`나 다른 쓰기가 원인): 4.13은 흐려질 때 초안을 그 순간의 유효 목록으로 다시 해석하는지 말하지 않습니다. 옛 목록으로 판정하면 이제 유효한 `"abc"`가 되돌려집니다(F9).
- 기본 입력이 유효 목록을 어디서 얻는지도 정해져 있지 않습니다. Hint와 props(4.1–4.2, 337–338행)에는 `schemaType`과 `jsonSchema`만 있습니다.
- 반대 방향(켜짐 도중 `"ab"`는 이미 보냄, 이어서 `"abc"`): 원본 `"ab"`에 경고등이 켜지고, `"abc"`는 초안이며, 흐려지면 `"ab"`로 되돌아갑니다. 규칙대로이며 예측할 수 있습니다.

### 검사 5 — 중첩 게이트, `$ref`, null
- 게이트 안의 게이트: 2.19(150행)의 덮음 조건("u가 정적이거나 d를 감싸는 조각에 있으면")으로 정해집니다. 유효 목록은 켜진 선언 모두의 교집합이어야 합니다.
  - 3.2는 "켜진 유효 `jsonSchema.type`"을 거쳐 이를 정의합니다. 그런데 유효 스키마가 `type`을 교집합으로 합치는지 나중 선언이 이기는지는 원장에 없습니다. SCHEMA-008은 검증 키워드만 말하고, SCHEMA-001은 `type`을 "노드의 종류"로만 둡니다(F4).
- 게이트 `$ref`: 게이트 조각 안에 있으므로 같은 규칙을 따릅니다. 문제 없습니다.
- 서로소 선언(u와 서로소인 d): 2.20(153행)에 따라 켜지면 `SHARED_NODE_CONFLICT`입니다. 기존 규칙 그대로입니다.
- 빈틈 — 서로소인 두 게이트: 본체 `['string','number','boolean']`에 `then1 a:'string'`, `then2 a:'boolean'`이 붙는 경우입니다.
  - 각 d는 u의 진부분집합이라 2.19를 통과하고, d끼리는 비교하지 않습니다.
  - 둘 다 켜지면 유효 목록이 ∅이 되는데, 이때의 동작이 정의되어 있지 않습니다.
  - 본체가 없으면 같은 두 게이트는 `SHARED_NODE_CONFLICT`입니다(BLUEPRINT-012). 본체를 더하면 오류가 사라지는 셈이라 일관되지 않습니다(F3).
- null만 더하는 게이트(`['string','number']`+`then ['string','number','null']`):
  - fold가 같아 노드를 공유하고, nullable을 바꾸지 않습니다(2.18, 149행).
  - 연언이므로 JSON Schema에서도 변화가 없어 맞습니다. 유효 목록은 `schemaType`과 같은 참조입니다.
- null을 빼는 게이트:
  - 판정대로 nullable은 그대로이고, `null`은 경고등을 켜지 않지만 검증기는 기각합니다.
  - 모든 종류가 똑같이 동작하므로 일관되지만, 3.18(305행)의 "지금 받는 JSON 형"이라는 문구는 이것과 맞지 않습니다(F10).
- 호스트의 게이트 없는 분기: 편집자 5(583행)는 "유효 목록이 이 분기에도 같이 적용"된다고 말합니다.
  - SCHEMA-008("게이트 없는 분기는 존재만")과 SCHEMA-044에 따르면 그 분기의 `type`은 유효 스키마에 들어가지 않습니다. JSON Schema에서도 `oneOf`는 "또는"이라 좁히지 않는 것이 맞습니다.
  - 그래서 편집자 5의 문장은 틀렸습니다(F6).

### 검사 6 — (ㄴ)과의 비교
- (ㄴ)에서 깨지는 것(antigravity 장면): 게이트가 켜진 폼에서 기본 입력이나 문자열을 보내는 플러그인으로 친 `"42"`가 문자열로 저장되고, 검증기는 이를 늘 기각합니다. 입력으로는 빠져나갈 수 없습니다. 저자가 할 수 있는 우회는 필드를 `then`/`else`에만 선언하는 것(E27)뿐입니다.
- ㄴ′의 비용:
  1. VALUE-030 문구 변경(쓰기 없이 경고등이 바뀜)
  2. 덧씌움 집합마다 spec 메모: 작은 배열 하나, O(k)
  3. 유효 스키마가 바뀐 노드의 경고등 O(1)
  4. 경고 기록의 `source`·알림 경로 문구
  5. **한 진입의 쓰기를 어느 목록으로 해석하는지에 대한 규칙 하나** — 없으면 아래 실패
- 실패 사례(F1, 확인):
  - 게이트 `kind==='num'`이면 `a:number`인 스키마에서, 직전 `kind='text'` 상태로 `setValue({kind:'num', a:'42'})`를 부르면 `a="42"`가 되고 경고등이 켜집니다.
  - 직전이 `kind='num'`이었다면 같은 호출이 `a=42`가 되고 경고등도 꺼져 있습니다(실행 확인).
  - 그래서 같은 `setValue(V)`를 두 번 부르면 결과가 다릅니다.
  - 마운트와 `reset()`의 로드는 직전 커밋이 없어 어느 목록을 쓰는지부터 정해져 있지 않습니다.
  - 원인: 쓰기 경계(표시 단계, 3.9)는 게이트를 평가하는 계산 단계보다 앞에 있습니다(SETTLE-001/003).
- 판정: 고칠 문장 1을 넣으면 ㄴ′는 (ㄴ)보다 낫고 정합합니다. 넣지 않으면 예측 가능성 요구를 어깁니다.

### 고칠 문장
심각도 순입니다. [확인]은 문서나 실행으로 확인한 것이고, [개연]은 문서가 침묵해 생기는 것입니다.

1. **F1 [확인, 높음]** 3.2 끝에 더합니다. "한 진입에서 쓰인 원시 잎의 값은 쓰기 경계에서 직전 커밋의 유효 목록으로 해석하고, 그 진입의 전이 단계에서 최종 유효 목록으로 `interpret`를 한 번 더 적용합니다. `interpret`가 멱등이므로 이미 맞는 값은 그대로이며, 바뀐 값은 전이 쓰기로서 표시로 돌아갑니다(SETTLE-005, SETTLE-010). 진입 전부터 있던 값은 다시 해석하지 않습니다. 그래서 마운트·`reset()`·`setValue(V)`의 결과는 직전 상태에 기대지 않습니다." 원장 변경 표에 SETTLE-005 행("전이 단계가 이번 진입에서 쓰인 잎을 최종 유효 목록으로 다시 해석")을 더합니다.
   - 검증: `setValue({kind:'num',a:'42'})`를 직전 `kind`가 `'text'`일 때와 `'num'`일 때 각각 부르면 둘 다 `a===42`여야 합니다. 시험 행 535에 더합니다.
   - 대안: 이력 의존을 문서화합니다. 비권장입니다. 멱등이 아닌 `setValue`가 남습니다.
2. **F2 [확인, 중간]** 3.1(222행)의 "`kinds`는 그 칸의 `schemaType`과 같은 참조"를 이렇게 바꿉니다. "칸의 기본 spec의 `kinds`는 `schemaType`과 같은 참조입니다. 유효 목록이 좁혀진 덧씌움 집합마다 `UnionSpec { kinds: 유효 목록, mask, nullable }`을 유효 스키마 메모 항목에 함께 둡니다. `interpret`는 노드의 현재 spec을 받습니다."
3. **F3 [확인, 중간]** 2.19에 셋째 줄을 더합니다. "켜진 비정적 선언 가운데 fold가 비지 않고 서로소인 두 선언이 있으면 2.20의 '게이트 가진 선언이 실제로 동시에 켜짐'과 같이 `SHARED_NODE_CONFLICT`(정착 오류)입니다. fold가 빈 선언(`null`만)은 이 비교에서 뺍니다." 3.2에는 "유효 목록이 비면(`null`만 남는 게이트) 모든 null 아닌 값에 경고등이 켜지고, 기본 입력은 4.15처럼 빈 읽기 전용입니다"를 더합니다.
4. **F4 [개연, 중간]** 3.2 첫 줄의 "`schemaType` ∩ (그 `type`)"을 이렇게 바꿉니다. "`schemaType` ∩ (켜진 모든 선언의 A(d)를 2.4로 교집합한 것)이며, 유효 스키마 `type`의 병합 방식에 기대지 않습니다."
5. **F5 [개연, 중간]** O7 행(493)과 원장 변경 행 511의 "union 노드"를 "원시 잎(원소 하나인 경우 포함, 곧 number 노드에 게이트 `integer`)"으로 넓힙니다. 3.2 첫 문장에 "종류가 원시이거나 `union`인 노드에"를 더합니다.
   - 검증: `{type:'number'}`+게이트 `then:{type:'integer'}`가 켜진 동안 `1.5`의 경고등이 켜집니다.

## O8 판정: 정합하지 않음 — 앵커가 "전순서의 첫 `type` 선언"이라서 교환법칙이 성립하는 `allOf`의 항목 순서를 바꾸면 결과가 바뀝니다(G1). 또 2.8이 2.9보다 앞서 있어서, 서로소인 두 선언은 null과 함께면 통과하는데 겹치는 두 선언은 null과 함께여도 충돌합니다. 비단조입니다(G2).

### 검사 1 — `allOf`의 뜻 그대로인가
- 교집합 자체(2.7, 2.10)는 JSON Schema의 `allOf` 의미입니다. 그러나 "앵커의 부분집합이 아니면 충돌"(2.9, 123행)은 폼만의 제한입니다. JSON Schema는 겹침과 넓음을 모두 받아들이고, 교집합이 빌 때만 만족할 수 없습니다.
- 이 제한은 게이트 쪽 2.19/2.20("u의 진부분집합이면 공유, 아니면 충돌")과 짝을 이룬다는 논거가 있습니다.
- 그러나 앵커를 전순서의 첫째로 정한 것은 JSON Schema에 없는 순서 의미를 들여옵니다. 소유자가 원치 않는다고 한 "하위 전용 문법"에 가깝습니다.

### 검사 2 — 오늘 코드와 BLUEPRINT-011/012
- 오늘의 판정: `validateCompatibility`(`validateCompatibility.ts:21-25`) → `isCompatibleSchemaType`(`winglet/json-schema/src/filters/isCompatibleSchemaType.ts:39-84`)입니다.
  - 대칭 비교로, fold가 같아야 합니다(null 무시, number~integer). 순서와 무관합니다.
  - 어긋나면 `ALL_OF_TYPE_REDEFINITION`입니다(`processAllOfSchema.ts:45-50`).
  - 병합은 `processSchemaType.ts:57,65-67`(형이 있는 source의 nullable AND)과 `:70-73`(number∩integer=integer, 그 밖에는 base)이 합니다.
  - 원시 union 배열은 `extractSchemaInfo.ts:25,29`에서 `null`이 되어 union 자체가 오늘은 서지 않습니다.
  - 형 없는 본체에는 병합 핸들러가 없어 `allOf`를 합치지 않습니다(`getMergeSchemaHandler.ts:30-46` → `processAllOfSchema.ts:31-32`).
- 그대로인 것: E20, E36(integer), E21, E37(nullable AND), E23(서로소 충돌), E24(넓음 충돌).
- 바뀌는 것:
  - E18(진부분집합이 좁힘. 오늘은 union이 서지 않음)
  - E30(오늘은 오류, 새 설계는 null 노드, M11)
  - M10(형 없는 `{nullable:false}`)
  - **형 없는 본체 + `allOf`가 새로 종류를 정하게 되면서 생기는 순서 의존(G1).** 오늘은 대칭 비교라 이런 순서 의존이 없습니다.
- BLUEPRINT-011/012: 정적 선언끼리의 관계는 SCHEMA-008 보충("정적 연언의 교차가 공집합이면 청사진 오류")에 대한 변경이며, 행 507이 이를 적습니다. 게이트 쪽(2.19–2.20)은 O7의 몫입니다.

### 검사 3 — 경계 사례(2.6–2.10을 적힌 그대로 실행)

| 입력 | 결과 | 평가 |
|---|---|---|
| `['string','number']` + `allOf:[['string','boolean']]` (E31) | `ALL_OF_TYPE_REDEFINITION` | JSON Schema와 검증기는 `string`을 강제합니다. 저자는 `string`을 기대할 가능성이 높습니다. 같은 모양의 `oneOf:[s,n]`∧`anyOf:[n,b]`(E17, 2.14)는 교집합 `number`로 받아들입니다(G3). |
| `{allOf:[['string','number'],['string']]}` | string | — |
| `{allOf:[['string'],['string','number']]}` | `ALL_OF_TYPE_REDEFINITION` | **순서만 바꿨는데 결과가 다릅니다(G1)** |
| `['integer','null']` + `allOf:[number]` | number, `schemaType` `'integer'`, nullable false | 오늘과 같고 JSON Schema와도 맞습니다 |
| `{type:'integer'}` + `allOf:[number]` (E36) | number `'integer'` | 오늘과 같습니다 |
| `['string','null']` + `allOf:[['number','null']]` (E30) | null 노드 | 2.8이 먼저라서입니다 |
| `['string','number','null']` + `allOf:[['string','boolean','null']]` | `ALL_OF_TYPE_REDEFINITION` | **E30보다 더 호환되는데도 충돌입니다(G2)** |
| `$ref` 대상이 union(`['number','string','boolean']`)이고 본체가 `['string','number']` | `ALL_OF_TYPE_REDEFINITION`(넓음) | 본체와 `$ref` 대상의 전순서 자리는 SCHEMA-007의 키워드 순위에 없습니다. 어느 쪽이 앵커인지 **모름**이고, 앵커가 바뀌면 결과도 바뀝니다(G1과 같은 뿌리) |
| `{allOf:[{$ref:SN}, {type:'string'}]}` / 뒤집음 | string / 충돌 | G1 |

설계 가치로 본 논증: "일관되고 예측 가능"을 기준으로 하면, 선언 순서나 null 유무처럼 의미와 무관한 차이가 결과를 뒤집어서는 안 됩니다. 부분집합 규칙은 저자의 실수를 잡는다는 이점이 있습니다. 그러나 앵커에 대해서만 판정하므로, 앵커 아래에서 둘이 겹치는 경우(`[s,n,b]`+`[s,n]`+`[n,b]` → `number`)는 통과합니다. 그래서 믿을 만한 실수 검출기도 아닙니다.
