### 112C-01 (1) 그렇다 — EVENT-039는 Refresh를 "입력의 `key`를 바꿔 비제어 입력이 커밋된 값을 다시 읽게 한다", 버리는 것은 "그 입력의 캐럿·선택·IME 조합 상태", 범위는 "그 노드의 입력 하나"로 정했고 오류 경계는 그 범위에 없다; 경계까지 다시 마운트하던 것은 구현이 범위를 넘은 것이지 계약이 아니며, 실패한 필드가 Refresh로 되살아나던 동작은 어느 항목도 약속하지 않았으므로 바뀌어도 계약 변경이 아니다 — 경계는 고정하고 안의 입력만 generation으로 다시 마운트한다; (2) 실패 상태를 푸는 것은 EVENT-040의 RequestRemount("서브트리의 React 로컬 상태, 비제어 DOM 값, 이펙트 상태 전부"를 버림)와 폼 자체의 `key`(`<Form key>`)뿐이다; (3) 폐기다 — EVENT-070의 통과 조건은 "두 이펙트 모두에서 React가 순환을 끊는다(throw나 중단)"이고 그 메모는 원장에 들어오지 않았다

  - 【추론】 EVENT-039의 표가 Refresh의 전부를 정한다: 하는 일은 입력의 `key`를 바꾸어 비제어 입력이 커밋된 값을 다시 읽게 하는 것, 버리는 것은 그 입력의 캐럿·선택·IME 상태, 범위는 그 노드의 입력 하나. EVENT-041은 그것을 "범위가 좁은 리마운트"라 불렀다. 필드의 오류 경계(ERROR-088의 "사용자 주입 구성 요소의 필드 바운더리")는 입력을 감싸는 바인딩 계층의 장치이지 입력이 아니므로 Refresh의 범위 밖이고, `key={generation}`을 경계 바깥에 둔 것은 구현이 범위를 한 겹 넘은 것이다. 그 결과 (가) 피어의 쓰기마다 새 경계가 실패 상태를 잊어 EVENT-070이 요구한 중단("두 이펙트 모두에서 React가 순환을 끊는다")이 일어나지 않고, (나) 실패한 필드가 피어의 아무 쓰기로 되살아나는 관측 동작이 생겼는데 이것은 어느 항목도 약속한 적이 없다. 그러므로 경계는 고정하고 안의 입력만 generation으로 다시 마운트하는 것이 계약대로이며, (나)의 동작이 사라지는 것은 계약 변경이 아니라 구현의 정정이다. 실패 상태를 푸는 것은 둘이다: RequestRemount는 EVENT-040대로 서브트리의 React 로컬 상태와 이펙트 상태 전부를 버리므로 경계도 새로 만들어지고, 폼 자체의 `key`를 바꾸면 폼 전체가 새로 마운트된다. 자동 Refresh(EVENT-042)와 명시 `refresh`는 둘 다 EVENT-039의 범위이므로 실패 상태를 풀지 않는다. 81라운드 작업 메모의 "개발 모드 경고로 바꾸고 시험 통과 조건을 바꾼다"는 원장에 들어오지 않았고 이 HEAD의 EVENT-070과 ADR은 중단 계약을 그대로 두므로 폐기다 — 메모는 지우지 말고 "112C-01로 폐기"라고 적는다. 구현 조건: 공개 API·동기 정착·통지·사슬 정의·25파동 예산은 바뀌지 않는다; 시험은 원래 단언 여덟 건(두 판·두 이펙트)에 더해 (ㄱ) 실패한 필드가 피어의 쓰기로 되살아나지 않음, (ㄴ) RequestRemount와 `<Form key>`로는 되살아남, (ㄷ) 정상 입력의 Refresh 재마운트(캐럿·커밋된 값 다시 읽기)는 그대로임을 단언한다; 바인딩 계층의 DETAIL에 경계와 입력의 key 범위를 적는다. 고친 뒤 G29의 전체 시험을 돌린다.
