# 최종 결론 — 소유자 검토용

작성 2026-09-23. 검토 여섯 라운드(1–6)와 수렴 두 라운드(7–8)의 결과를 소유자가 통과 또는 반려할 수 있게 한 문서에 모았다. 근거 파일은 마지막 절에 있다. 이 문서는 새 결정을 만들지 않는다. 이미 나온 결론을 약어와 생략 없이 풀어 쓴 것이다.

## 0. 이 문서를 읽는 법

- **절 단위로 통과 또는 반려한다.** 3절(원리의 읽기 확인), 4절(도출로 닫힌 결정), 5절(소유자가 답할 가치 판단), 6절(이름과 표면), 7절(실험이 먼저인 것)이 판정 대상이다. 1절과 2절은 배경이고, 8절은 정정 기록, 9절은 통과 뒤에 일어나는 일이다.
- **항목의 구조.** 각 항목은 "질문 → 배경 → 결론 → 왜 그런가 → 무엇이 바뀌는가 → 소유자에게 남는 것" 순서로 적었다. 이해되지 않는 항목은 그 항목만 반려하면 된다.
- **번호의 뜻.** `D-12` 같은 번호는 검토 라운드가 결정 항목에 붙인 꼬리표다. 이 문서 안에서는 번호 옆에 언제나 풀어 쓴 이름을 함께 적었다. `P1`–`P5`는 설계의 다섯 원리, `G1`–`G8`은 목표 문서의 목표, `C2`·`C8`은 소유자가 추가로 채택한 목표다. 모두 2절에 전문이 있다.
- **"도출"과 "정책"의 뜻.** 도출은 "원리와 이미 수락된 결정만으로 답이 하나로 정해진다"는 뜻이다. 소유자는 그 답을 확인만 하면 되고, 다르게 정하려면 원리를 바꿔야 한다. 정책은 "원리가 두 답을 모두 허용한다"는 뜻이다. 소유자가 고른다.
- **"확신 중"의 뜻.** 도출이지만 근거가 좁거나(예: 조사한 선례가 하나뿐) 판정자가 확신을 낮춰 적은 것이다. 소유자가 읽고 받는다.

## 1. 용어

새 설계에서 쓰는 말이다. 본문의 모든 낱말은 여기의 뜻으로 읽는다.

| 용어 | 뜻 |
| ---- | -- |
| 노드 트리 | 스키마의 각 필드에 대응하는 노드 객체의 트리. 새 설계에서는 이 트리가 곧 폼의 상태이고 별도의 데이터 모델은 없다 |
| 원본 (raw) | 사용자가 입력했거나 호출자가 넣은 값 그대로. 리프 노드와 터미널 노드가 든다. 객체 노드는 "잘못된 종류의 값"(예: 객체 자리에 숫자)이 왔을 때만 원본을 든다 |
| 합성 값 (local) | 활성 자식의 방출 값을 합친 것. 투영 전이다. 계산 결과이지 상태가 아니다 |
| 방출 값 (emit) | 바깥으로 내보내는 값. `getValue()`와 `onChange`가 주는 값이다. 합성 값에 투영 규칙을 적용한 결과다 |
| 투영 | 원본을 건드리지 않고 방출 값을 만드는 규칙. 비활성 조각의 제외, 빈 문자열을 없음으로 보는 `omitEmpty`, 배열 끝의 빈 항목을 자르는 `omitTrailing`이 투영이다 |
| 조각 (fragment) | 스키마의 조건부 부분. `if/then/else`의 `then`과 `else`, `oneOf`·`anyOf`의 각 분기, `allOf`의 각 항목이 조각이다. 조각은 켜지거나 꺼진다 |
| 본체 | 조건 없이 늘 켜져 있는 조각. `properties`로 직접 선언한 부분이다 |
| 가드 (guard) | 조각을 켤지 정하는 조건. `if`의 조건과 `oneOf`의 판별식이 가드다. 폼이 해석하지 않고 검증기 플러그인이 컴파일한다 |
| 활성 집합 | 이번 커밋에서 켜진 조각의 집합. 원본에서 매번 계산되는 결과이지 상태가 아니다 |
| 형상 | 어떤 조각이 켜져 있고 어떤 자식이 존재하는가. 활성 집합이 정한다 |
| 정착 (settle) | 쓰기 하나가 들어온 뒤 트리가 안정 상태에 이르기까지의 처리 한 번. 단계는 표시, 계산, 파생, 전이, 커밋, 통지, 검증이다 |
| 바퀴 | 계산 단계 안에서 호스트가 가드를 반복 평가해 활성 집합이 더 바뀌지 않을 때까지 도는 것. 상한은 조건부 조각 수 + 1 |
| 라운드 | 파생이나 전이가 원본에 쓰면 표시 → 계산으로 다시 도는 한 회. 파생 라운드와 전이 라운드에 각각 상한이 있다 |
| 진입 | 바깥에서 들어온 쓰기 호출 하나. 사용자 입력 한 번, `setValue` 호출 한 번, `batch` 호출 한 번이 각각 진입 하나다. 리스너가 통지를 받고 다시 쓰는 것은 같은 진입 안이다 |
| 커밋 | 정착이 끝나 트리가 확정되는 순간. 직전 커밋은 바로 앞 정착이 확정한 트리다 |
| 전체 교체 | `setValue(V)`(기본), `defaultValue`, `reset()`처럼 값 전체를 바꾸는 쓰기. V에 없는 자식의 원본은 "없음"이 된다 |
| 부분 쓰기 | 사용자 입력이나 `setValue(V, Merge)`처럼 일부 키만 바꾸는 쓰기 |
| 없음 (MISSING) | 값이 아예 없는 상태. 빈 문자열이나 `null`과 다르다. 스키마의 `default`는 없음인 키에만 들어간다 |
| 로드 계약, `default` 주입 | 값이 없음인 키에 스키마의 `default`를 써 넣는 것. 전체 교체 직후와 조각이 꺼짐에서 켜짐으로 바뀐 직후에만 일어난다. 코어가 스스로 하는 유일한 자동 쓰기다 |
| 전이 주입 | 위의 둘째 경우. 조각이 꺼짐에서 켜짐으로 바뀔 때 그 조각이 선언한 `default`를 넣는 것 |
| `injectTo` | 스키마 작성자가 선언하는 명령. "이 노드(원천)의 값이 바뀌면 저 노드(대상)에 이 값을 써라" |
| `&derived` | 스키마 작성자가 선언하는 파생 값. 다른 노드의 값으로 계산한다 |
| 자동 쓰기 | 사용자나 호출자가 아니라 규칙이 원본에 쓰는 것. `default` 주입, `injectTo`, `&derived` 셋이다 |
| 에지 발화 | "값이 바뀌었을 때만" 규칙이 작동하는 방식. 무엇과 비교해 바뀌었다고 볼지, 그 기준점이 문제가 된다 |
| 레벨 | "언제나 이 값이어야 한다"는 방식. 바뀜과 무관하게 계산값을 유지한다 |
| `batch(fn)` | 여러 쓰기를 묶어 정착 한 번, 통지 한 번으로 처리하는 호출 |
| 예산 | 무한 루프 방어 상한. 호스트 바퀴(조건부 조각 수 + 1), 파생 라운드, 전이 라운드, 리스너 되먹임 파동, `onChange` 중첩의 다섯 종류가 있다 |
| 파동 | 쓰기, 통지, 리스너의 되쓰기가 되먹임하는 한 회 |
| `settle.status` | 정착의 결과 상태. 정상이면 `stable`, 예산에 걸리면 `budget-exceeded`. 이름은 6절에서 다시 정한다 |
| `extras` | 호스트 객체가 받았으나 어떤 조각에도 선언되지 않은 키. 상태 칸의 하나다 |
| `selection` | 판별식이 없는 union 호스트에서 사용자가 수동으로 고른 분기. 상태 칸의 하나다 |
| 상태 칸 | 노드가 실제로 소유하는 상태. 원본(`raw`), `selection`, `extras` 셋뿐이다. 나머지는 계산 결과다 |
| 고정점 | 자동 쓰기를 적용해 형상을 다시 계산해도 더 바뀌지 않는 상태. 자동 쓰기가 가드를 뒤집으면 고정점이 없거나 여럿일 수 있다 |
| 원본 B | 이번 정착의 자동 쓰기를 모두 뺀 원본. 사용자와 호출자가 명시적으로 쓴 값만 남은 상태 |
| 주석 키워드 | JSON Schema에서 값의 유효성이 아니라 부가 정보를 주는 키워드. `default`, `title`, `description`, `readOnly`, `format` 등 |
| 판별식 | `oneOf`의 분기를 고르는 `const`나 `enum` 값. 이것이 있으면 사용자가 분기를 고르지 않는다 |
| 프로토타입 | 설계를 검증하려고 만든 실행 가능한 모형. `loop-v4c`가 4라운드 명세에 5라운드의 D-10 변경을 더한 구현, `loop-v4d`가 7라운드에서 새 원리를 더한 것, `loop-v4e`가 8라운드에서 스위치를 더한 것이다 |
| 반례 | 프로토타입을 돌려 설계가 원하는 성질이 깨지는 것을 보인 사례. `E1`처럼 번호가 붙어 있다 |
| 이주 안내 | 새 버전으로 옮기는 사용자에게 무엇이 바뀌었는지 알리는 문서. 채택 목표 C8이 요구한다 |
| 반례·실험 번호 | E·X는 프로토타입 반례, N은 독립 모델(codex)의 실험이다. 6절의 이름 제안 N1–N7과 다르다 |

## 2. 축 — 결정을 낳는 원리와 목표

모든 결론은 아래에서 도출됐다. 여기에 없는 것은 누구의 권위도 아니다.

### 2.1 다섯 원리 (`03-mental-model.md` §1)

- **P1. 판정은 검증기의 것이다.** 폼은 스키마의 뜻을 해석하지 않는다. 폼의 판정은 검증기가 작성된 스키마와 방출 값을 받아 내는 결과와 같다. 폼이 스키마에서 읽는 것은 형상, 곧 어떤 필드가 있는가를 만드는 데 필요한 최소한이다.
- **P1′ (소유자, 2026-09-23).** 폼이 스키마에서 읽는 것은 노드 트리의 모양을 정하는 문법뿐이다. 타입(`type`, 다중 타입, 튜플), 자식의 존재(`properties`, `items`, `prefixItems`), 조건부 존재(`if/then/else`, `allOf`, `oneOf`·`anyOf`의 분기)가 그것이다. 값의 유효성을 정하는 문법(`required`, `false`, `not`, `additionalProperties`, 범위와 패턴)은 검증기의 것이고, 폼은 그 판정을 보여 줄 뿐 값을 고치지 않는다. 값을 빼거나 지우는 것은 작성자의 `&` 명령뿐이다.
- **P2. 원본은 호출자와 작성자만 쓴다.** 원본에 쓰는 주체는 사용자 입력, 호출자의 `setValue`와 `reset`, 작성자가 선언한 `injectTo`, 로드 계약의 `default` 넷뿐이다. 코어가 스스로 원본을 고치는 일은 없다. (7라운드에서 `&derived`가 다섯째 주체로 더해졌다. 4절 참조. P2–P5는 모두 소유자의 명시적 확인 대기 상태다(`03-mental-model.md` 107행).)
- **P3. 형상은 상태의 순수 함수다.** 어떤 조각이 켜져 있고 어떤 자식이 존재하는지는 스키마, 원본 전체, 선택 상태에서 매번 같은 절차로 계산된다. 이력을 읽지 않는다. 계산은 원본을 읽기만 한다.
- **P4. 방출은 정책이다.** 방출 값은 원본과 형상의 투영이다. 비활성 조각의 제외, `omitEmpty`, `omitTrailing`은 원본을 건드리지 않는 투영 규칙이며 작성자가 고른다.
- **P5. 코어는 렌더러를 모른다.** 코어는 노드 트리, 작업 루프, 통지만 안다. React도, 컴포넌트도, 화면의 명령도 모른다. 렌더 계층이 코어를 구독한다.

### 2.2 이 문서가 인용하는 목표 (`00-goals.md`)

- **G1. 스키마는 공유 계약이다.** 폼의 유효성 판정은 독립 표준 검증기가 내리는 판정과 같다. 폼이 더 엄격해지는 것은 허용되지만, 표준 판정에 AND로 덧붙는 형태로만이다.
- **G2. 표준이 형상을 말하고, FE가 표현을 더한다.** 지금의 동적 표현식 시스템이 주는 표현력은 줄어들지 않는다. 표현 층은 값을 바꿀 수는 있어도 판정에는 닿지 못한다.
- **G4. 하나의 개념에는 하나의 장치.** 특수 경로가 없고, 조건부로 형상을 바꾸는 모든 구문이 같은 장치와 같은 라이프사이클을 탄다.
- **G5. 한 장으로 설명되는 라이프사이클 — 결정성.** 같은 스키마와 같은 쓰기 순서는 타이밍과 무관하게 같은 상태를 낸다. 원인과 결과의 순서가 뒤집히지 않는다.
- **G6. 정밀한 고속 제어.** 비용은 변경에 비례한다. 계산할 필요가 없는 것은 계산하지 않는다.
- **G7. 반응의 척추를 보존한다.** 배치는 "쓰기 묶음 → 정착 1회 → 통지 1회"로 강해진다.
- **G8. 보편적인 관행을 따른다.** JSON Schema로 폼을 만드는 분야의 보편적이고 직관적인 관행을 조사해 흡수한다.
- **C2 (채택).** 작성자 실수의 가시성(폼 생성 시점의 오류, 개발 모드 경고, 주인 없는 검증 에러의 폼 수준 표시). 지금의 에러 구조를 확장한다.
- **C8 (채택).** 이행 경로로 릴리스 노트·배포 문서와, 그 수정을 수행할 수 있는 이주 프롬프트를 낸다.

### 2.3 이미 수락된 결정 (`HANDOFF.md` §1·§2)

검증기 입력 불변(폼은 스키마를 고치지 않는다), 조건부 장치는 "가드 → 조각" 하나의 모델, FE 전용 키워드는 `&` 네임스페이스, 검증기는 플러그인이고 동기 `compileGuard`를 더함, 노드 트리가 곧 상태, Form은 단일 스키마, 코어는 값을 고치지 않고 에러를 보여 줌, 코어는 React를 모름. 소유자가 확정한 것: `setValue(getValue())`도 전체 교체이며 로드 계약이 다시 적용된다(D-7), 판별 프로퍼티에 암묵 `default`는 없고 빈 값은 분기 없음(D-8), `RequestRemount`는 유지(D-9), 루트 `onChange`는 최외곽 동기 진입당 1회(D-10), 로드 시 `default`를 끄는 스위치는 "초기값 조작 비활성화"의 뜻이고 이름은 `disable…` 형태(D-5의 방향).

## 3. 원리의 읽기 확인 — 결정이 아니라 읽기다

아래 일곱은 원리 문장을 어떻게 읽는지의 확인이다. 하나라도 다르게 읽으면 4절의 해당 항목이 다시 열린다.

**3.1 G5의 "같은 쓰기 순서"는 정착 단위이고, `batch`는 쓰기 하나로 센다.**
`batch`는 타이밍이 아니라 호출자가 선언한 쓰기 단위다(G7, `adr/0008:72`). 이 읽기에서 "배치와 순차의 값 차이는 결함이 아니다"(4.3)가 나온다. 다르게 읽으면 "정착마다 없음인 `default`를 커밋한다"와 "커밋된 값은 뒤의 전환에서 덮지 않는다" 가운데 하나를 버려야 한다. 셋은 양립하지 않는다는 것이 독립 모델과 프로토타입 둘에서 실행으로 확인됐다.

**3.2 P2의 문구.** "코어의 자동 쓰기는 로드 계약(`default`)과 작성자가 선언한 쓰기(`injectTo`·`&derived`)뿐이다"로 `03-mental-model.md` 10행과 45행을 고친다. P2는 아직 명시적 확인 대기이므로, 이 문장의 확인이 곧 P2의 확인이다. 이 확인에는 5.1의 답(로드 우선순위 문장을 넣을지)이 함께 들어간다.

**3.3 G4를 좁힌다.** "트리의 형태는 렌더링 런타임에 좌우되지 않는다"로 `00-goals.md` 59행을 고친다. 소유자의 발언(114행, 입력 컴포넌트 유무로 노드 종류가 달라지는 것은 의도된 기능)이 근거다. 목표 문장의 변경이라 확인이 필요하다.

**3.4 P1′의 괄호.** "판별식 식별을 위한 `const`·`enum` 값 읽기는 형상 읽기에 든다"를 `03-mental-model.md` 15행에 더한다. 소유자 인용(`adr/0005:90`)이 근거다.

**3.5 `extras`는 순서 있는 칸이다.** `03-mental-model.md` 24행의 `extras` 정의를 "호스트가 받은, 어디에도 선언되지 않은 키와 그 순서"로 적는다. 이래야 방출 순서가 상태의 함수라는 P4가 성립한다(4.12). 정의의 보강이지 가치 판단이 아니다.

**3.6 원본으로만 지탱되는 조각과 `default`로만 지탱되는 조각은 다르다.** 원본은 상태이고 `default` 주입은 사건이다. 그래서 7절의 실험(D-15)이 S2(최소 고정점 뒤, 선언 키가 원본에 있는 꺼진 조각을 검증기 가드로 한 번 켜 봄)를 채택하더라도, "`default`만으로 자기 가드를 켜는 조각"은 켜지지 않는다(4.16). 이 비대칭을 한 문장으로 확인한다.

**3.7 편집자 단독 판정 일곱을 받는다.** 4.15–4.21은 실행이 드러낸 새 문제에 대한 편집자의 도출이며 독립 소스 둘의 일치를 거치지 않았다. 소유자가 읽고 받거나 되돌린다.

## 4. 도출로 닫힌 결정 — 확인만 남는다

### 4.1 `&derived`는 원본을 쓴다 (D-11 핵심)

- **질문.** `&derived`로 선언한 파생 값은 노드의 원본에 써지는가, 아니면 원본 없이 방출에만 나타나는 투영인가.
- **배경.** 문서 일곱 곳이 둘로 갈려 말했다. 현재 코드는 쓴다.
- **결론.** 쓴다. 작성자가 선언한 쓰기로 P2 주체 목록에 `injectTo`와 나란히 든다.
- **왜.** 투영으로 두면 P4의 정의 "방출은 원본과 형상의 투영"과 불변식 "부모의 방출 = 활성 자식 방출의 투영"이 깨지고, 가드가 파생값을 보아야 하므로 파생 계산을 형상 계산 바퀴 안으로 옮겨야 한다. 쓰기로 두면 P2 열거에 하나를 더할 뿐이고, `03-mental-model.md` 66행 "원본을 쓰는 것은 파생과 전이뿐"이 이미 품는다.
- **바뀌는 것.** ADR 0007 32행과 ADR 0013 41행의 "읽기 전용"을 고친다.
- **남는 것.** 사용자가 파생 필드를 덮어쓸 수 있는가는 5.2로 넘어간다.

### 4.2 전이 주입은 최종 활성 집합 기준이다 (D-12)

- **질문.** 조각이 켜질 때 그 조각의 `default`를 넣는 전이 주입은, 정착 라운드 도중의 형상에 대해 일어나는가, 정착이 끝난 최종 형상에 대해 일어나는가.
- **배경.** 반례 E1. 필드 `x`를 `then`(`default` `'T'`)과 `else`(`default` `'E'`)가 공유하고 `kind`에 `default` `'b'`가 있다. 빈 객체를 로드하면 첫 라운드에서 `kind`가 없어 `then`이 먼저 켜지고 `x`에 `'T'`가 들어간 뒤, `kind`에 `'b'`가 들어가 `else`로 바뀌어도 `x`는 이미 값이 있어 `'T'`가 남는다. `{kind: 'b'}`를 로드하면 `x`는 `'E'`다. 같은 최종 상태인데 값이 다르다.
- **결론.** 최종 활성 집합 기준. 중간 라운드에서 켜졌다 꺼진 조각의 주입은 커밋 전에 버린다. 승자(여러 조각이 같은 자식에 `default`를 선언할 때)는 최종 형상의 유효 스키마가 가진 `default`다.
- **왜.** P3 "이력을 읽지 않는다", G5. 프로토타입과 독립 모델 둘 다 이 규칙으로 E1이 사라졌다.
- **바뀌는 것.** ADR 0007 33행, 4라운드 명세 36행. 프로토타입에서 비용은 측정 오차 안이었다.
- **남는 것.** 여러 조각의 `default`가 맞붙을 때 어느 쪽이 이기는지는 5.3. 자동 쓰기가 가드를 뒤집어 고정점이 없거나 여럿인 경우는 4.15–4.17.

### 4.3 에지 발화의 기준점은 직전 커밋이고, 배치와 순차의 값 차이는 설계의 귀결이다 (D-13)

- **질문.** `injectTo`가 "원천이 바뀌었을 때만" 발화한다면, 무엇과 비교해 바뀌었다고 보는가. 6라운드는 "직전 커밋" 대신 "이 정착의 시작 상태"로 바꾸면 `batch`와 순차 호출의 결과가 같아진다고 권고했다.
- **배경.** 반례 E2. 분기 A는 `x`에 `default` `'A'`, 분기 B는 `'B'`. `kind`를 `a`로 쓴 뒤 `b`로 쓰면 순차는 `x = 'A'`(첫 정착에서 들어간 값이 남음), `batch`로 묶으면 `x = 'B'`(정착이 한 번이라 B만 켜짐). 반례 E3도 같은 모양이다.
- **결론.** 기준점은 직전 커밋이다. 6라운드가 권고한 "정착 시작 상태"는 문자 그대로 직전 커밋과 같은 상태를 가리키므로 아무것도 바꾸지 못한다. 배치와 순차의 값 차이는 결함이 아니라 축의 귀결이며 문서화한다.
- **왜.** 정착은 언제나 직전 커밋에서 출발하고, 순차 호출은 첫 정착에서 새로 켜진 조각의 `default`를 실제로 커밋하며, 커밋된 값은 뒤의 전환에서 덮지 않는다. 이 셋이 축이다. 같게 만드는 길은 셋뿐이고 모두 축과 부딪친다. 배치 안에서도 쓰기마다 정착하면 G7에 어긋나고, 원본마다 출처를 기록해 되돌리면 넷째 상태가 생겨 P3에 어긋나며, 이미 통지된 값을 뒤 정착이 철회하면 "코어는 받은 값을 고치지 않는다"에 어긋난다. 로컬 도출, 격리 세션, 독립 모델, 프로토타입 넷이 같은 결론이고, 반대한 소스 하나는 실행에 반증됐다.
- **바뀌는 것.** ADR 0007 79행, ADR 0013 41행, 4라운드 명세 144행. `batch`의 문서 주석에 "배치는 정착 횟수를 바꾸므로 전이 주입과 `injectTo`의 결과가 순차 호출과 다를 수 있다"를 적는다.
- **남는 것.** 3.1의 읽기 확인. 마운트와 `reset`처럼 직전 커밋이 없을 때의 규칙은 5.1.

### 4.4 초기 분기 선택에서 `required`를 읽지 않는다 (D-14)

- **질문.** 판별식이 없는 `oneOf`에서 값이 들어왔을 때 어느 분기를 켤지 정하는 규칙이 각 분기의 `required`를 읽어도 되는가.
- **결론.** 읽지 않는다. `dependentRequired`도, 판별식 식별 5단계의 "`required`에 포함"도 뺀다. 선언된 키 수와 선언 순서만 쓴다.
- **왜.** P1′이 `required`를 검증기의 것으로 분류했다. 게다가 `dependentRequired`는 기본 검증기 설정에서 조용히 무시되므로 "폼은 읽고 검증기는 안 읽는" 상태가 생긴다. 프로토타입은 이미 읽지 않는다.
- **바뀌는 것.** ADR 0002 127행 규칙 3, ADR 0005 81행.
- **남는 것.** 두 분기의 점수가 같을 때는 5.5.

### 4.5 예산 초과 시에도 `onChange`는 불린다 (D-16)

- **질문.** 개발 모드에서 예산 초과로 throw할 때 그 진입의 `onChange`와 검증을 건너뛰어도 되는가.
- **결론.** 개발 모드와 프로덕션 모두 커밋 → 검증 요청 → `onChange` 순서로 진행하고, 개발 모드의 throw는 최외곽 진입 끝에서 한다.
- **왜.** 소유자가 확정한 D-10(루트 `onChange`는 최외곽 진입당 1회)이 없앤 것이 바로 개발 모드와 프로덕션의 관측 차이였다. 6라운드 검증 #11의 "throw가 `onChange`를 취소" 처방은 기각한다.
- **바뀌는 것.** ADR 0007 52행.

### 4.6 리스너 되먹임만 거부하고, 파동 예산의 단위는 진입 사슬이다 (D-17)

- **질문.** 한 틱 안의 파동 상한(25)에 닿으면 리스너의 쓰기를 거부하는데, 이것이 사용자 입력까지 조용히 버리는가.
- **배경.** 권장 패턴인 스토어 리스너를 붙이면 파동을 두 배로 써서 13번째 쓰기부터 거부된다. 프로덕션에서 호출자의 `setValue`가 조용히 버려지는 유일한 자리다.
- **결론.** 사용자 입력과 호출자 쓰기는 결코 거부하지 않는다. 거부는 리스너 되먹임에만 적용하고, 거부 시 신호를 낸다. 파동 예산의 단위를 "틱"에서 "최외곽 진입의 되먹임 사슬"로 바꾼다.
- **왜.** ADR 0013 결정 1 "입력을 막지 않는다"와 P2. 틱은 타이밍이므로 G5에 어긋난다. 측정: 틱당 셈법이면 리스너 없이 25번째, 권장 리스너로 13번째 쓰기에서 상한에 닿고, 진입당 되먹임만 세면 30회 내내 닿지 않는다.
- **바뀌는 것.** ADR 0008 62행, 4라운드 명세 148행.
- **남는 것.** React 이펙트를 거친 진입 간 순환이 React 자체 한도에 막히는지는 실행하지 않았다(7절).

### 4.7 배열 `Merge`는 통째 교체다 (D-19)

- **질문.** `setValue(V, Merge)`에서 V의 키에 배열이 있으면 인덱스 단위로 병합하는가, 통째로 바꾸는가.
- **결론.** 통째 교체. `Merge`는 객체 키 단위이고, 키의 값이 배열이면 그 배열을 통째로 바꾼다. 통째로 받은 배열의 아이템과 `push()`로 만든 아이템은 로드로 취급해 `default`가 들어간다.
- **왜.** G8. RFC 7396(JSON Merge Patch)이 배열을 통째 교체로 정하고, 조사한 폼 라이브러리 셋(react-hook-form, Formik, Final Form) 모두 인덱스 병합을 명시하지 않으며, lodash의 `merge`만 인덱스 병합이다.
- **바뀌는 것.** `03-mental-model.md` 41행과 ADR 0013 55행의 "`Merge`는 로드가 아니다"를 "`Merge`는 V에 없는 키를 로드하지 않는다. V가 통째로 준 배열의 아이템은 로드다"로 고친다. ADR 0007 75행의 "`Merge` + 억제는 무해한 no-op이다"도 함께 고친다.

### 4.8 터미널 아래 경로는 노드가 없다 (D-21)

- **질문.** `find('/payload/amount')`에서 `/payload`가 터미널 노드(자식을 노드로 만들지 않는 객체 노드)일 때 무엇을 돌려주는가.
- **배경.** 오늘은 `/payload` 노드를 돌려준다(별칭). 거기에 `setValue(42)`를 하면 객체가 없어진다.
- **결론.** 노드가 없으므로 `null`을 돌려준다. 반환 타입 `SchemaNode | null`은 그대로다.
- **왜.** P2와 G4. 공개 API가 객체를 조용히 파괴하면 안 된다.
- **바뀌는 것.** `findNode.ts` 86행의 조기 반환을 마지막 세그먼트일 때만으로 바꾼다. **행동 변화이므로 이주 안내 대상이다.** 7라운드 문서가 처음에 "현행대로 `null`"이라 적은 것은 오독이었고 정정했다(8절). 항상 통과하는 테스트(`findNode.test.ts` 147–149행, `expect(x).toEqual(x)`)를 `toBeNull()`로 고친다.
- **남는 것.** 복수형 `findNodes`가 같은 경로에서 터미널을 남기는 동작을 맞출지는 6절 N7.

### 4.9 관측 채널의 최소 (D-22 최소)

- **질문.** 예산 초과, 리스너 throw, 검증 대기 같은 진단 신호를 어디로 내보내는가.
- **결론.** `onChange`의 payload에 싣는 것은 탈락. 코어 수준 관측(루트의 `settle` 칸 읽기와 그 변화 이벤트 구독)은 도출된다. 유효 스키마만 좁아진 노드의 통지(#19)는 채널 질문이 아니라 배달 집합에 넣는 것으로 도출된다.
- **왜.** ADR 0008 91행 "방출 참조가 바뀌지 않은 쓰기는 `onChange`를 내지 않는다"이므로 `onChange`로는 예산 초과가 보이지 않는다. C2.
- **남는 것.** Form 속성의 모양과 이름(6절 N4), 제출 차단 여부(5.4).

### 4.10 값의 세 읽기의 사상 (D-23 사상)

- **결론.** `getValue()`는 루트의 방출 값, `node.value`는 투영 전 합성 값, `enhancedValue`는 새 모델에 자리가 없다.
- **왜.** P1(판정은 방출 값에 대해), ADR 0006 48행. 생태계에 정규화 값을 위한 셋째 공개 층의 선례가 없다.
- **남는 것.** 이름(6절 N3).

### 4.11 수렴하지 않을 때는 원본 B를 커밋한다 (D-31)

- **질문.** 자동 쓰기(전이 주입, `injectTo`, `&derived`)를 포함한 고정점이 예산 안에 수렴하지 않으면 무엇을 커밋하는가.
- **배경.** 4.2를 채택하면 자동 쓰기가 가드를 뒤집는 스키마에서 고정점이 없거나 여럿이거나 반복으로 닿지 못할 수 있다. 4차 본문은 "마지막으로 완료된 라운드"를 커밋한다고 적었다.
- **결론.** 원본 B, 곧 그 정착의 자동 쓰기를 모두 뺀 원본과 그 형상을 커밋하고 `settle.status`를 예산 초과로 표시한다.
- **왜.** 마지막 완료 라운드를 지우는 문장은 4.2의 "중간 라운드의 주입은 커밋 전에 버린다"이다. 프로토타입에서 마지막 라운드 커밋은 상한이 24인지 25인지에 따라 결과가 달라졌고, 여섯 경우 중 넷이 최종 형상에서 꺼진 조각의 자동 쓰기를 커밋했다. 원본 B는 예산값과 무관하고 `default`를 뺀 스키마의 결과와 같다. 커밋 거부는 ADR 0013 27행 "형상 계산이 수렴하지 않을 때도 값은 받아들인다"에 걸린다. 진동 관여자만 골라내는 안은 가드의 뜻을 폼이 읽어야 해 P1′에 걸리고, 일관된 최대 부분집합은 지수 탐색이라 G6에 걸린다.
- **대가.** 지원 범위 밖 구석이 하나만 있어도 그 정착의 자동 쓰기가 트리 전체에서 빠진다. 관여하지 않은 필드의 `default`도 빠진다. 마운트라면 기본값 없는 폼이 된다. 이것은 예산 초과 신호로 드러나며, 공개 문서 `inject-to.md` 38행의 "earlier hops still apply"와 어긋나므로 이주 안내에 올린다.
- **바뀌는 것.** ADR 0007 41행.

### 4.12 `extras`의 방출 순서는 받은 순서다 (D-32)

- **질문.** 선언되지 않은 키를 방출할 때 받은 순서대로 내보내는가, 정렬하는가.
- **결론.** 받은 순서. 전체 교체는 V의 키 순서를 따르고, `Merge`는 있는 키를 제자리에 두고 새 키를 뒤에 붙인다.
- **왜.** 걸리는 원리는 P3가 아니라 P4(방출은 상태의 함수)다. 프로토타입에서 "같은 원본으로 끝나는 서로 다른 쓰기 열 셋"이 다른 순서를 냈으므로, 순서를 상태로 보지 않으면 P4가 깨진다. 그래서 3.5의 정의 보강이 필요하고, 그 정의를 고르는 근거는 G8이다. ECMAScript 객체는 순서 있는 맵이고, `JSON.parse`는 문서 순서를, 전개와 `Object.assign`은 "있는 키는 제자리, 새 키는 뒤"를 지킨다. 설치된 RJSF 6.6.1을 실행해 확인했고 오늘 코드도 같다. 정렬은 매 정착마다 비용이 들어 G6에 약하게 어긋난다.
- **제약.** 정수 모양 키(`"2"`, `"10"`)는 ECMAScript가 어떤 순서 규칙에서든 앞에 오름차순으로 놓는다. 규칙을 "ECMAScript own-key 순서"로 적고, ADR 0007 55행 "스키마 선언 순서, extra는 뒤"에 이 예외를 한 줄 더한다.
- **확신 정도.** 확신 중. 조사한 폼 라이브러리는 RJSF 하나다.

### 4.13 원리 제안 P6–P9의 처리

- **P6 (i) "자동 쓰기는 최종 형상의 함수다"** — 전이 주입에 채택(4.2). `injectTo`에도 적용해야 숨은 파생값 반례가 닫히고, 독립 모델의 N8 실험은 "`default`만 되돌리기"로는 부족함을 보였다.
- **P6 (ii) "이력은 방아쇠로만 읽는다"** — 기존 도출표의 재진술. **F13 순서 힌트(직전 커밋의 활성 집합을 가드 평가 순서로 쓰는 것)는 단서 복원이 아니라 제거한다.** 6라운드가 복원하라 한 단서 "고정점이 유일한 스키마에서만"은 폼이 가드의 뜻을 해석해야 판정할 수 있어 P1′에 걸린다. 힌트를 끄면 두 이력의 결과가 같아진다는 것을 실행으로 확인했다. 역순 사슬의 비용은 Q15(직전 커밋의 활성 집합을 출발 가설로 쓰는 최적화, `open-questions.md` 90행)에서 측정한다.
- **P6 (iii) "배치는 순차와 같다"** — 기각(4.3).
- **P7 "예산은 한 칸에 같은 모양으로 관측된다"** — 예산 다섯에 한해 G4의 재진술. 로드 값이 방출에서 빠지는 신호(D-15)는 새 내용이며 7절 실험 뒤 정한다.
- **P8 "코어의 공개 어휘는 렌더러 중립 의미로 정의된다"** — P5의 재진술. `refresh`와 `remount`의 의미를 React의 `key` 교체로 서술한 곳을 중립 의미로 고친다. `03-mental-model.md` 13행의 "화면의 명령도 모른다"는 소유자가 명령 어휘를 코어에 두기로 한 C3 세부 3과 맞게 고친다(소유자 확인).
- **P9 "상태 칸 하나에 공개 이름 하나"** — 칸마다 이름 하나(단사형)는 G4의 재진술. 이름마다 칸 하나(전단사형)는 새 내용이며 6절의 이름 제안이 그것을 따른다.

### 4.14 3라운드 결정 D-1–D-6 (5라운드 도출, 4차 본문에 이미 반영)

3라운드에 소유자 결정으로 올라왔고 5라운드에 원리에서 도출되어 ADR 4차 본문에 들어간 것이다(`reviews/round-5-derivations.md` §3). 확정은 `HANDOFF.md` §2대로 소유자가 ADR 4차 본문을 읽고 한다.
- **D-1** `setValue(null)`은 키 없는 전체 교체이고, 다시 객체가 될 때 로드 계약이 `default`로 빈 상태를 만든다(P2).
- **D-2** 조각 활성 계산은 출발점을 고정하고 비단조로 반복하며 상한을 둔다(P3).
- **D-3** 금지 조각(`x: false`, `not: {required}`)은 읽지 않는다. 값 유효성 문법이지 모양 문법이 아니다(P1′, P2). 잔여 키의 표시는 검증기 플러그인 계약 `rejectedKey`.
- **D-4** 쓰기 종류는 호출자가 선언한다. 코어는 추론하지 않는다(P2). 그릇은 6절 N1에서 비트마스크로 바뀌지만 "선언한다"는 실체는 그대로다.
- **D-5** 로드 시 `default`는 없음인 키에만 들어가고, 끄는 스위치는 이 하나만 끈다(P2). 이름은 6절 N1.
- **D-6** `virtual`은 참조 그룹 노드이고 튜플 값은 읽기 전용 파생이다(P5, P4). 도출은 아니다 — P5 아래에서 (a)·(b)가 모두 양립하고 차이는 비용이며, 비교 시점은 소유자 질문으로 남아 있다(`03-mental-model.md` 112행).

### 4.15 자동 쓰기를 포함한 고정점이 없을 때 (D-24, 편집자 판정)

- **배경.** 자기 가드를 끄는 `default`(`x != 1`이면 `x`에 `default` 1). 4.2 아래에서 `{}` → `{x:1}` → `{}`로 순환한다. 오늘 프로토타입에서는 이력에 기대어 `stable`이던 스키마다.
- **결론.** ADR 0007 57행 "고정점이 없는 스키마는 지원 범위 밖"과 D-2에 따라 예산 초과다. 4.11에 따라 원본 B를 커밋한다. **행동 변화이므로 이주 안내에 올린다.**

### 4.16 고정점이 여럿일 때 (D-25, 편집자 판정)

- **배경.** 자기 가드를 켜는 `default`(`x = 1`이면 `x`에 `default` 1). `{}`도 해이고 `{x:1}`도 해다.
- **결론.** 결과는 명시적 쓰기를 표시한 원본 B에서 시작한 반복의 극한, 곧 `{}`다. `default`는 "조각이 꺼짐에서 켜짐으로 바뀐 직후"의 사건이므로 자기 조각을 켜는 원인이 될 수 없고, 자기 지지 `default`는 상태에서 오지 않아 P3가 배제한다. 3.6의 확인이 이것이다.

### 4.17 해는 있으나 반복이 닿지 못할 때 (D-26, 편집자 판정)

- **결론.** 유일한 해가 자기 지지 `default`라면 4.16에서 허용되지 않으므로 4.15의 경우가 된다. ADR 0007 57행의 지원 범위를 "고정점의 존재"가 아니라 "원본 B에서 시작한 반복이 예산 안에 수렴하는가"로 다시 적는다. 그래야 판정이 절차로 정해지고 지수 탐색이 필요 없다(G6).

### 4.18 비활성 대상에도 `injectTo`가 쓴다 (D-28, 편집자 판정, 확신 중)

- **결론.** 쓴다(잠복 원본). 대상이 나중에 켜져도 원천이 바뀐 것이 아니므로 재발화하지 않는다.
- **왜.** `injectTo`는 호출자의 전체 교체와 같고(`03-mental-model.md` 43행), 전체 교체는 꺼진 조각의 노드까지 분배된다(ADR 0013 63행). 비활성화는 쓰기가 아니다. 이 규칙이면 독립 모델 N6의 네 경로가 모두 같은 값이 된다.

### 4.19 자동 쓰기 로그의 수명은 정착 범위다 (D-30, 편집자 판정)

- **결론.** 4.2를 구현하려면 자동 쓰기를 되돌릴 수 있는 로그가 필요한데, 그 수명은 정착 하나다. 진입 범위로 두면 이미 통지된 값을 뒤 정착이 철회하므로 "코어는 받은 값을 고치지 않는다"와 G5의 "원인과 결과의 순서"에 걸린다. 프로토타입에서 정착 범위 로그와 직전 커밋 기준(4.3)을 함께 쓰면 진입 안 순차가 4라운드 프로토타입과 같아진다.

### 4.20 "값이 바뀌었다"는 값 비교다 (D-33, 편집자 판정, 비용은 실험)

- **결론.** `injectTo`의 에지와 `onChange`의 "같은 값이면 통지 없음"은 한 장치이고(G4), 참조 비교가 아니라 값 비교다. 원본을 바꾸지 않은 사건이 자동 쓰기를 일으키면 결과가 이력에 달리기 때문이다. 현재 코드는 같은 값을 다시 써도 `injectTo`가 발화한다(문자열·객체 노드에서 확인, 수·불리언·null 노드는 미확인).
- **남는 것.** 객체 원천의 깊은 비교 비용은 7절.

### 4.21 원천이 비활성이면 `injectTo`는 없음을 읽는다 (D-34, 편집자 판정, 확신 중)

- **결론.** `injectTo`가 읽는 것은 원천의 방출 값이고(ADR 0007 79행), 비활성 노드는 방출에서 빠지므로(P4) 없음으로 읽는다. 프로토타입은 활성 여부를 무시하고 리프 값을 읽고 있어 고쳐야 한다.

## 5. 소유자가 답할 가치 판단

원리가 두 답을 모두 허용한다. 지워진 선택지와 살아남은 선택지를 나눴고, 답할 문장을 예/아니오로 답할 수 있게 적었다.

### 5.1 작성자가 선언한 규칙이 로드된 데이터를 덮어도 되는가 (D-27, 로드 시 `injectTo`)

- **장면.** 서버에서 `{ price: 100, total: 90 }`을 받았고, 스키마가 `price`를 `total`에 주입한다고(`injectTo`) 선언했다. 마운트, `reset()`, 호출자의 `setValue(V)` 전체 교체가 모두 이 장면이다.
- **살아남은 선택지.**
  - **`fire` (작성자가 위).** 전체 교체는 모든 원천을 "없음에서 바뀐 것"으로 만들므로 `injectTo`가 모두 발화하고 `total`은 100이 된다. 서버가 준 90은 사라진다. 스키마가 진실이다. 초안 원리 아래의 도출이다. 4.3의 직전 커밋 규칙을 마운트에 문자 그대로 적용하면 이것이 나오고, 4라운드 명세 34행 "`reset()`은 `injectTo`를 일으킨다"와 현재 코드의 마운트 동작과 같다.
  - **`fill` (데이터가 위).** 대상이 없음일 때만 채운다. 90이 남고, `price`가 바뀌는 순간부터 규칙이 작동한다. `default` 로드 계약과 같은 모양이다. 다만 `injectTo`가 "런타임에는 덮어쓰고 로드 때는 채우기만" 하는 두 모드가 되므로, 이것을 고르려면 P2에 "로드에서는 작성자가 선언한 규칙도 호스트가 준 값을 덮지 않는다"는 새 문장을 넣어야 한다. 그러면 특수 경로가 아니라 새 원리의 적용이 된다.
- **지워진 선택지.** `skip`(로드 때는 발화하지 않음)은 `{ source: 'A' }`만 로드했을 때 초기 복사조차 없어 원천이 다시 바뀔 때까지 대상이 빈다. 공개 문서가 `injectTo`의 용도를 "Initial copy, default seeding"이라 적고 오늘 코드도 마운트에서 원천의 `default`로 대상을 채우므로 G2(표현력은 줄지 않는다)에 걸린다. 이 탈락은 `injectTo`를 G2의 '동적 표현식 시스템'에 드는 것으로 읽는다는 전제에 선다. 리셋 전 이력과 비교하는 안은 P3에 걸린다. 마운트·노드 reset·`FormHandle.reset`에 서로 다른 규칙(현재 코드)은 G4에 걸린다.
- **원리가 말하는 것.** P2는 작성자를 정당한 쓰기 주체로 인정하므로 `fire`를 허용한다. "있는 값을 고치지 않는다"(`03-mental-model.md` 82행)는 코어 자신의 `default`에 대한 문장이지 작성자의 규칙에 대한 문장이 아니다. 그러나 허용과 선호는 다르다. 이것은 "스키마의 규칙이 진실인가, 받은 데이터가 진실인가"라는 제품의 가치다.
- **멱등성은 기준이 아니다.** `setValue(getValue())`가 모든 상태에서 멱등인 것은 `skip`뿐인데, 소유자가 이미 D-7에서 멱등을 버렸고(`default` 로드 계약도 같은 모양으로 비멱등이다), `skip`은 위에서 지워졌다.
- **`fire`를 고를 때 따라오는 귀결(확인 필요 — 격리 세션 claude 도출 §3.5 하나의 추론이며 실행·대조 검증을 거치지 않았다).** 4.14의 D-5 스위치("초기값 조작 비활성화", 6절 N1의 `DisableSchemaDefaults`)가 로드 정착의 자동 쓰기 전부, 곧 `default`뿐 아니라 `injectTo`와 `&derived`까지 꺼야 한다. 그래야 호출자가 "데이터가 위"를 호출 단위로 선택할 수 있다. D-7이 같은 긴장을 호출 단위 옵션으로 푼 것과 같은 방식이다. 받으면 4.14 D-5의 "이 하나만 끈다", `03-mental-model.md` 45·82행, ADR 0013 54행, ADR 0007 76행을 고친다.
- **답할 문장.** "로드(마운트·`reset`·호출자의 전체 교체)에서 작성자가 선언한 `injectTo`가 호출자가 준 대상 값을 덮는가?" 예 → `fire`. 아니오 → `fill`이며 P2에 위 문장을 넣는다.

### 5.2 사용자가 파생 필드를 덮어쓸 수 있는가 (D-11′)

- **장면.** `total`이 `&derived`로 `price * quantity`라 선언되어 있다. 사용자가 `total` 입력란에 직접 85를 쳤다.
- **살아남은 선택지.**
  - **에지.** 의존 값(`price`, `quantity`)이 바뀔 때만 다시 계산한다. 사용자의 85는 다음 의존 변화까지 남는다. 현재 코드의 동작이다. 스프레드시트에서 수식 셀에 값을 덮어쓰는 것과 같다.
  - **레벨.** `total`은 언제나 계산값이고 입력란은 읽기 전용이다. 공개 문서 `expressions.md` 47행 "`derived` continuously computes … and overwrites user edits"의 약속이다.
- **지워진 선택지.** 입력을 열어 둔 채 매번 덮어쓰는 레벨은 사용자 편집마다 입력을 리마운트하므로 계승 제약 T-2 "타이핑은 입력을 리마운트하지 않는다"에 걸린다(실행으로 확인). 쓴 주체에 따라 방아쇠를 가르는 혼합안은 G4 "특수 경로가 없다"에 걸린다. `injectTo`와 로드 규칙이 다른 에지는 G4에 걸린다.
- **원리가 말하는 것.** 두 답 모두 축과 양립한다. 편집자가 앞서 "에지는 `injectTo`와 같은 장치가 되므로 G4가 지운다"고 스케치했으나, G4의 단위는 구문이 아니라 장치이고(`00-goals.md` 52·56행), 에지에서 `&derived`와 `injectTo`는 한 장치 위의 두 구문이므로 성립하지 않는다. 56행은 형상 구문에 관한 문장이라 여기서는 유추 적용이다. 그 스케치의 근거였던 "G2가 `&derived`를 이름으로 든다"는 7라운드 antigravity 도출의 날조 인용(`00-goals.md` 38행과 `adr/0003` 21행을 섞은 것)에 기댄 것이었다(8절). 프로토타입에서 "커밋 트리가 스키마와 비파생 원본만의 함수"인 것은 레벨뿐이지만, 축은 그 성질을 요구하지 않는다. 그 성질을 원하는지가 곧 이 질문이다.
- **5.1과의 관계.** 5.1이 `fire`이면 로드 때 에지와 레벨 모두 파생 필드를 다시 계산하므로 이 질문은 따로 답할 수 있다. 5.1이 `fill`("데이터가 위")이면 레벨은 로드된 파생 값을 덮으므로 지워지고 에지만 남는다.
- **이주.** 어느 쪽을 골라도 공개 문서(레벨 약속)나 코드(에지 동작) 가운데 하나는 이주 안내 대상이다.
- **답할 문장.** "`&derived` 필드에 사용자나 호출자가 직접 쓴 값이 다음 의존 값 변화까지 남아도 되는가?" 예 → 에지. 아니오 → 레벨이며 그 입력은 읽기 전용이 된다.

### 5.3 조건부 조각의 주석 키워드가 본체를 덮는가 (D-29)

- **장면.** 본체 `properties`가 `x`에 `default` `'base'`를 선언하고, `then` 조각도 `x`에 `default` `'then'`을 선언한다. `then`이 켜져 있고 `x`가 없음이면 무엇이 들어가는가. `title`, `readOnly` 같은 다른 주석 키워드도 같은 질문이다.
- **살아남은 선택지.**
  - **먼저 선언된 것이 이긴다(F).** 본체가 전순서에서 가장 앞서므로 `'base'`. 오늘 코드가 `allOf`에 적용하는 규칙을 모든 조각으로 넓힌 것이다. 조건부 조각에서 다른 `default`를 주려면 본체에서 `default`를 빼고 `then`과 `else` 양쪽에 적어야 한다. 표현력은 줄지 않는다.
  - **조건부 조각이 켜지면 덮는다(C).** `then`이나 활성 `oneOf` 분기가 선언한 주석 키워드가 본체와 `allOf`를 덮고, 무조건 조각끼리는 먼저 선언된 것이 이긴다. 설치된 RJSF 6.6.1을 실행해 확인한 동작이 이것과 맞는다.
- **지워진 선택지.** `default` 하나만 다른 방향을 따르는 안. 오늘 코드도 `default`를 `title`·`readOnly`·`format`과 한 무리로 두고, RJSF도 키워드를 가리지 않는다. 따로 두면 G4의 특수 경로다. 4라운드 명세와 프로토타입의 "나중-승"은 `default` 하나에만 걸려 있어 이 탈락에 해당한다.
- **원리가 말하는 것.** 어느 쪽도 도출되지 않는다. "조건부 조각이 본체를 특수화한다"는 목표는 축에 없다. G8의 실행 증거(RJSF)는 (C) 쪽으로 기울고, G4는 조각 종류에 따라 방향이 갈리는 것에 저항한다. 오늘 코드에서는 이 대결 자체가 일어나지 않는다. `then`의 `default`를 읽는 코드가 없고, `oneOf` 분기가 본체 키를 다시 선언하면 오류를 던지기 때문이다. 새 설계에서 처음 생기는 질문이다.
- **어느 쪽이든 남는 것.** 배치와 순차의 차이(4.3)는 그대로다. "선언 순서"가 소스 순서인지 키워드 순위(`properties < allOf < if/then/else < oneOf/anyOf`)인지는 이 질문과 별개로 ADR에 정의해야 한다.
- **답할 문장.** "조건부 조각(`then`/`else`, `oneOf`·`anyOf`의 활성 분기)이 켜지면, 그 조각이 선언한 주석 키워드(`default`, `title`, `readOnly` 등)가 본체의 같은 키워드를 덮는가?" 예 → (C). 아니오 → (F).

### 5.4 예산 초과 시 제출을 막는가 (D-22′ 일부)

- **살아남은 선택지.**
  - **신호만.** `settle.status`와 진단 콜백으로 알리고, 제출은 검증기 판정에만 맡긴다. 호스트 애플리케이션이 원하면 콜백을 보고 제출 버튼을 끈다.
  - **Form 계층의 AND 차단.** 검증기 통과에 더해 "형상이 정착하지 않았다"는 폼 자신의 조건으로 제출을 거절한다. 형상 예산(호스트 바퀴, 파생, 전이)에만 적용한다.
- **지워진 선택지.** 검증 에러 목록에 섞는 차단(P1, G1). 코어가 막는 차단(제출은 Form 바인딩의 API이고 코어는 그것을 모른다, P5). 통지 예산(파동, `onChange` 중첩)에서도 막는 차단(그 예산은 커밋된 방출 값을 바꾸지 않는다).
- **원리가 말하는 것.** G1은 "폼이 더 엄격해지는 것을 표준 판정에 AND로 덧붙는 형태로만 허용"하므로 AND 차단은 축 안이다. 축 문서 자신이 이 질문을 소유자 질문으로 남겼다(`03-mental-model.md` 112행). 기울기는 신호만 쪽이다. 4.11에 따라 비수렴 폼은 기본값 없는 상태가 되므로 두 답을 함께 읽어야 한다.
- **답할 문장.** "프로덕션에서 검증기가 통과시킨 값의 제출을, 형상 예산 초과만을 이유로 Form이 막아야 하는가?" 예 → AND 차단. 아니오 → 신호만.

### 5.5 비판별 union의 동점 (D-14′)

- **장면.** 분기 A가 `{name, age}`, 분기 B가 `{name, email}`을 선언하고 값이 `{name: 'x'}`이면 둘 다 1점이다.
- **선택지.** (가) 선언 순서의 첫 분기를 폼이 고른다. 그 분기의 `default`가 주입되고 사용자는 A의 필드를 본다. 프로토타입의 현재 동작이다. (나) 분기 없음. 빈 값과 같게 다루어 사용자가 선택기로 고를 때까지 비워 둔다. ADR 0010(`oneOf`/`anyOf` UX)이 첫 화면을 정해야 완성된다.
- **원리가 말하는 것.** 둘 다 축과 양립한다. 일관성은 "폼은 고르지 않는다"로 한 문장이 되는 (나) 쪽으로 기운다. 그러나 (가)를 고르면 사용자가 빈 선택기를 보지 않는다. 제품의 성격이다.
- **답할 문장.** "값이 어느 분기인지 폼이 알 수 없을 때, 폼이 첫 분기를 보여 주는가(가), 사용자가 고를 때까지 비워 두는가(나)?"

### 5.6 이름 제안에 섞인 작은 정책 넷 (6절에서 온 것)

- **`default` 억제를 양방향으로 유지하는가.** ADR 0013 52행은 "호출 옵션이 Form 속성을 양방향으로 이긴다"고 적었다. 유지하면 끄는 비트와 켜는 비트 둘이 필요하고, "호출은 끄기만 한다"로 좁히면 비트 하나로 충분하다.
- **`removeKey`를 흡수하는 규칙을 두는가.** "`Merge`로 `extras` 키에 `undefined`를 쓰면 그 키가 없어진다"를 규칙으로 두면 별도 API가 필요 없다. 이것은 리프 규칙 "`undefined`를 쓰면 없음"을 넓힌 것이라 뜻의 결정이다. 잔여 키 UI와 함께 정한다.
- **`findNodes`도 터미널 아래 경로에 같은 규칙을 적용하는가** (4.8의 복수형).
- **`virtual`과 `type: 'virtual'`의 새 형태.** D-6(참조 그룹 노드)의 귀결이며 키가 아니라 값이라 `&`를 붙일 수 없다.

## 6. 이름과 표면 — 제안표

소유자 규칙 "전체 일관성이 유지된다면 가독성 높고 명료한, 줄임말이 아닌 풀 네임"과 저장소의 기존 관례(속성 `showError`와 열거형 `ShowError`의 짝, 칸 `state`·이벤트 `UpdateState`·콜백 `onStateChange`의 삼중 짝, 쓸 수 있는 칸 `x`에는 `setX`)로 만든 제안이다. 인용 12건 중 11건이 확인됐고 하나는 근거가 약했다(문서 주석의 예시를 타입으로 인용). 통과하면 그대로 ADR에 적는다.

### N1. 쓰기 옵션 — 옵션 객체가 아니라 비트마스크

- **배경.** 설계 4차 본문은 옵션 객체 `{ mode?: 'Overwrite' | 'Merge'; disableDefaultInjection?: boolean }`를 적었으나, 소유자가 비트마스크를 택했다. 4.14의 D-4("호출자가 선언한다")는 그릇과 무관하게 그대로다. 비트마스크에서는 `mode`가 `validationMode`나 react-hook-form의 `mode`와 충돌하는 문제와 대문자 리터럴이 camelCase 불리언과 섞이는 문제가 함께 사라진다.
- **제안.** 공개 열거형 `SetValueOption`(내부 이름 `PublicSetValueOption`, 오늘과 같음)에 멤버 넷.

| 멤버 | 뜻 |
| ---- | -- |
| `Overwrite` | 전체 교체. 기본값. 오늘과 같다 |
| `Merge` | 부분 쓰기. 오늘과 같다. `Overwrite ⊇ Merge`를 유지해 둘을 함께 주면 `Overwrite`가 이긴다 |
| `DisableSchemaDefaults` | 이 쓰기에서는 스키마 `default`를 채우지 않는다 |
| `EnableSchemaDefaults` | Form 속성이 꺼 두었어도 이 쓰기에서는 채운다 |

둘 다 없으면 Form 속성 `disableSchemaDefaults`를 따르고, 둘 다 주면 억제가 이긴다(배치 규칙 "섞이면 억제가 이긴다"와 같은 판정). `reset(option?)`은 두 비트만 받는다. Form 속성은 `disableSchemaDefaults`. 공개 합성 멤버(`Reset`, `StableReset` 등)는 두지 않는다. 오늘의 `ResetOptions`(7필드)는 공개되지 않는 내부 타입이므로 이름 충돌이 아니다.
- **왜 `SchemaDefaults`인가.** "Injection"은 이 열거형 안에서 이미 `injectTo`를 뜻하고, "DefaultValue"는 Form의 초기값을 뜻하며, "Initial"은 마운트에만 듣는 것처럼 읽히는데 실제로는 뒤의 `setValue`와 `reset`에도 듣는다. "Load"는 설계 문서의 용어이고 공개 문서에 없다.
- **비트가 둘인 이유.** 상속·끄기·켜기 세 상태를 비트 하나로 담을 수 없다. 이름 짓기 보고서의 "기본이 켜진 긍정 비트는 비트마스크로 표현할 수 없다"는 과장이다(오늘 `setValue`의 기본값 `Overwrite`가 긍정 비트가 켜진 합성값이다). 정확한 제약은 "공개 관용구에 비트 빼기(`& ~X`)가 없다"이다.
- **이름이 말하지 못하는 범위.** 억제는 호출자의 전체 교체가 일으킨 정착에서만 듣고, 사용자 입력이 켠 조각의 전이 주입은 막지 못한다. 5.1에서 `fire`를 고르고 그 귀결을 받으면 `injectTo`와 `&derived`까지 끈다. 이 범위는 문서 주석에 적는다.
- **남는 정책.** 5.6의 양방향 유지 여부.

### N2. 분기 선택 명령

- **제안.** 명령 `setSelectedBranch(index)`, 상태 칸의 공개 이름 `selectedBranch`. 계산된 활성 분기는 `activeBranch` 하나로 오늘의 `oneOfIndex`와 `anyOfIndices`를 대체한다(새 모델에서는 `anyOf`도 한 분기만 활성).
- **왜.** 상태 칸의 쓰기는 이 저장소에서 늘 `set` + 속성 이름이었다(`setValue`, `setState`, `setErrors`). `select`는 오늘의 텍스트 선택 명령 `RequestSelect`와 충돌하고, `setSelection`은 DOM의 `setSelectionRange`와 겹친다. 2순위 `selectBranch`는 짧지만 명령 동사 계열이라 `setValue`와 모양이 달라진다.
- **남는 정책.** `setSelectedBranch`와 `selectBranch` 가운데 하나.

### N3. 값의 세 읽기

| 칸 | 공개 이름 | 비고 |
| -- | --------- | ---- |
| 원본 (`raw`) | 공개 이름 없음 | 소비자가 원본을 직접 읽을 이유가 없다. 꺼진 조각의 원본은 N6의 `getInactiveValues`가 열거한다 |
| 합성 값 (`local`) | `value` (유지) | 호스트 노드에서만 뜻이 "원본"에서 "합성 값"으로 바뀐다. README 1483행 "`node.value` stays raw"는 이주 안내 대상 |
| 방출 값 (`emit`) | `outputValue` | 오늘의 `normalizedValue`의 이름 변경. README가 이 투영을 "Array Output Filters"(배열 한정)라 부른다. `normalizedValue`는 무엇을 정규화했는지 말하지 않고 내부 비트 `Normalize`와 뜻이 다르다 |

`FormHandle.getValue()`는 유지하며 루트의 `outputValue`와 같다. 노드에 `getValue()` 메서드는 따로 두지 않는다(`node.value`와 뜻이 다르면 이름만 보고 속는다). `enhancedValue`는 사라진다(오늘도 내부 이름이다). `setValue(updater)`는 유지하고 `prev`는 `value`다.

### N4. 진단 표면

- **제안.** 노드 칸 `diagnostics`, 이벤트 `UpdateDiagnostics`, Form 속성 `onDiagnosticsChange`. 삼중 짝이 `state` / `UpdateState` / `onStateChange`와 같은 모양이다. 설계 용어 "settle"(정착)을 배우지 않아도 뜻이 읽힌다.
- **모양.**

```ts
diagnostics: {
  status: 'stable' | 'budgetExceeded';
  exceededBudget?: 'conditionalSchemas' | 'derivedValues' | 'transitionDefaults' | 'listenerFeedback' | 'onChangeNesting';
  iterations: number;
}
```

문서에 흩어진 리터럴 셋(`budget-exceeded`, `wave-cap-exceeded`, `onchange-cap-exceeded`)이 한 모양으로 모인다. 이것이 4.13의 P7이다. 리터럴은 코드 관례대로 camelCase다. 예산 이름은 소비자가 아는 말로 붙였다. 호스트 바퀴는 `conditionalSchemas`, 파생 라운드는 `derivedValues`, 전이 라운드는 `transitionDefaults`, 파동은 4.6에 따라 틱 단위가 아니므로 `listenerFeedback`, `onChange` 중첩은 `onChangeNesting`.
- **비워 둔 것.** 로드 값이 방출에서 빠지는 신호(7절 D-15 실험 뒤)는 예산이 아니므로 `status`의 새 값이 된다. 후보는 `'loadedValueDropped'`. 비수렴 커밋(4.11)은 예산 초과이므로 `'budgetExceeded'`와 해당 `exceededBudget`으로 알린다.
- **남는 정책.** 5.4의 결과에 따라 단일 콜백이면 `onDiagnostic(report)`, 분리 콜백이면 `onListenerError`를 더한다.

### N5. FE 전용 키 문법

- **제안.** 모든 FE 전용 키는 `&`로 시작하는 평면 키다. `computed` 컨테이너를 없앤다(오늘 `&active`와 `computed.active`가 같은 것을 두 문법으로 쓴다). `options`는 사용자 정의 키를 담는 열린 컨테이너라 `&options`로 두고 평면으로 풀지 않는다. 컴포넌트 키는 PascalCase를 유지한다(`&FormTypeInput`).
- **이름만 바뀌는 것(기계적 이주 가능).** `computed.*` → `&*`, `FormTypeInput` → `&FormTypeInput`, `FormTypeInputProps`, `FormTypeRendererProps`, `formType`, `terminal`, `errorMessages`, `options`, `injectTo`, `propertyKeys`에 `&` 접두. `&pristine`은 존속.
- **사람이 다시 써야 하는 것.** `&if`/`computed.if`(분기 가드로 다시 씀), `virtual`(뜻이 D-6으로 바뀜, 5.6).
- **부수 효과.** 오늘 키 여섯을 이름으로 나열하는 제거 목록이 "키워드 위치의 `&` 접두 키를 모두 지운다"는 한 규칙이 된다.

### N6. 공개 쓰기 API와 배열 API

- **제안.** `setValue(value | updater, option?)`, `setSelectedBranch(index)`, `push(value?)`(`unlimited` 인자는 뺀다 — 코어가 `maxItems` 초과를 막지 않으므로 무시할 제약이 없다), `pop()`, `update(index, value)`(2순위 `setItem`), `remove(index)`, `clear()`, `batch(callback)`(루트와 `FormHandle`), `reset(option?)`/`resetSubtree(option?)`.
- **명령.** `focus`, `select`(텍스트 선택), `refresh`, `remount`. `refresh`가 비용을 숨긴다는 지적이 있으나 오늘의 공개 이벤트 이름과 함께 바꿔야 하므로 유지가 1순위다.
- **읽기.** `getInactiveValues(path)`가 꺼진 조각의 원본을 열거한다. 가칭 `latent`를 대체한다.
- **`write`.** 공개 API로 필요 없다. 입력의 `onChange`가 부르는 `setValue`에 내부 출처 비트로 흡수된다.
- **`removeKey`.** 보류. 둔다면 `removeUndeclaredKey(key)`. 흡수 규칙은 5.6.

### N7. `find`의 반환

4.8의 결론. 이름은 바뀌지 않는다. `findNodes`의 정합은 5.6.

## 9. 통과 뒤에 일어나는 일

1. **ADR 5차 본문.** 4절의 결론과 5절의 답을 ADR 0002·0003·0005·0006·0007·0008·0011·0013에 반영한다. 변경 이력에 이 문서를 가리킨다.
2. **단조 수정 27건.** 6라운드 §7의 목록 가운데 지금 적용할 수 있는 8건(진입 깊이, 검증 스탬프, F13 힌트 제거, `&pristine` 존속, 출발점·상한 축약, Q9(`&` 키는 키워드 위치에서만 제거한다는 문구 수정), D-7 범위, 프로토타입 편차 백로그)과 4절을 받으면 적용할 수 있는 4건(파생 상한 throw 순서, 주입 시점, 관측 문장, `Merge`와 배열)을 먼저 적용한다. 부분 2건(Q14(`extras` 방출 순서) '잠정' 표시, 배열 API 목록 합치기)은 표시만 지금 한다. 나머지 13건은 각 행이 기다리는 것(3절의 읽기 확인, 5절의 답, 6절의 이름, 7절의 실험) 뒤에 적용한다.
3. **`02-target-overview.md` 다시 그리기.** 3차안 시점의 그림이며 5.1·5.4·7절이 닫힌 뒤 한 번에 그린다.
4. **ADR 0010 작성.** `oneOf`/`anyOf`의 UX. 5.5의 답이 첫 화면을 정한다.
5. **이주 안내 항목(C8).** 이 문서가 새로 올린 것: `find`의 터미널 별칭 제거(4.8), 배열 `Merge`의 통째 교체(4.7), 이력에 기대어 안정되던 스키마가 예산 초과가 되는 것(4.15), 비수렴 시 `default`가 모두 빠지는 것(4.11), 파생 필드의 문서와 코드 어긋남(5.2), `injectTo`의 로드 동작(5.1), 조건부 조각의 `default`가 동작하기 시작하는 것(5.3에서 (C)일 때), `normalizedValue` → `outputValue`(N3), `computed.*` → `&*`와 접두 없는 키의 `&` 접두(N5), `push`의 `unlimited` 제거(N6), README 1483행.
6. **실험 셋(7절)**은 5절과 무관하게 지금 시작할 수 있다.
