## 1. 목표와 가치

### 1.1 패키지 설계 가치

소유자가 14라운드에 핵심 가치 다섯을 이름 붙였다(GOAL-049). 목표(GOAL-003, GOAL-004, GOAL-005, GOAL-006, GOAL-009, GOAL-011, GOAL-012, GOAL-013의 G1(판정의 동치)–G8(보편 관행))와 원리(GOAL-025, GOAL-028, GOAL-029, GOAL-030, GOAL-031의 P1(판정은 검증기의 것이다)–P5(core는 렌더러를 모른다))가 어느 가치를 받치는지 적는다(GOAL-049).

(GOAL-049, GOAL-050)

| 가치 | 뜻 | 받치는 목표·원리 |
| --- | --- | --- |
| 일관성 | 같은 개념은 어디서나 같은 이름·같은 규칙·같은 우선순위다. 하나의 개념에는 하나의 장치 | G4(하나의 개념에 하나의 장치), G2(층의 분리), P3(형상은 순수 함수) |

### 1.3 목표 문장과 읽는 법

표준 JSON Schema를 **그대로** 받아, 표준 검증기와 **같은 판정**을 내리면서, 큰 폼을 **변경에 비례하는 비용**으로 움직이는, **한 장으로 설명되는** 폼 엔진(GOAL-001).

표기 주의(15라운드)(GOAL-002). `00-goals.md`의 `&키`·`control` 표기는 `controls.키` 그룹 표기로 바뀌었고, 조각 식의 기준점은 호스트(`./x`)가 되었으며, 맨 폼 전용 키는 `options`·`presentation` 그룹으로 옮겨졌다(GOAL-002). `00-goals.md`는 그때의 기록이라 고치지 않는다(GOAL-002). 살아 있는 규칙과 결정은 CONTROLS-016, CONTROLS-043, GOAL-042에 있다(GOAL-002).

(GOAL-085)

| 용어 | 뜻 |
| --- | --- |
| 작성자 | 스키마를 쓰는 사람. 그룹 객체 셋과 표준 키워드를 적는다 |
| 호출자 | `<Form>`이나 core를 쓰는 코드. `setValue`·`reset`·Form 속성을 준다 |
| 사용자 | 입력란에 값을 넣는 사람 |

### 1.4 표준 판정과 층의 분리

폼의 유효성 판정은 독립 표준 검증기가 같은 스키마와 같은 값에 내리는 판정과 같다(GOAL-003). 폼이 통과시킨 값을 서버가 기각하는 일은 없다(GOAL-003). 이 성질은 기능별 규율이 아니라 구조로 보장된다(GOAL-003).

- 스키마의 소유자가 FE든 BE든 동작이 같다(GOAL-003).
- 폼에 들어오는 경로(`<Form>`이든 core를 직접 쓰든)가 달라도 계약이 같다(GOAL-003).
- 폼이 더 엄격해지는 것은 허용되지만, 표준 판정에 AND로 덧붙는 형태로만이다(GOAL-003).

→ ADR 0001(GOAL-003).

폼의 동작은 세 층으로 나뉘고, 아래층은 위층을 모른다(GOAL-004).

| 층 | 어휘 | 정하는 것 |
| -- | ---- | --------- |
| 유효성 | 표준 JSON Schema | 값이 옳은가 |
| 형상 | 표준 JSON Schema의 조건·합성 구문 (+ 사용자의 분기 선택) | 어떤 필드가 존재하는가, 각 필드의 제약은 무엇인가 |
| 표현 | FE 전용 어휘 (`&`) | 어떻게 보이고 어떻게 반응하는가 |

- BE가 선언한 스키마를 아무 가공 없이 넣어도 쓸 만한 폼이 나온다(GOAL-004).
- FE가 표현 층을 더하면 폭넓은 표현이 가능하다(GOAL-004). 지금의 동적 표현식 시스템이 주는 표현력은 줄어들지 않는다(GOAL-004). 표현 층은 값을 바꿀 수는 있어도 판정에는 닿지 못한다(GOAL-004).
- 무엇이 FE 전용인지는 기계적으로 가려진다(GOAL-004).

→ ADR 0002, 0003(GOAL-004).

`00-goals.md`의 `&키`·`control` 표기는 `controls.키` 그룹 표기로 바뀌었고, 조각 식의 기준점은 호스트(`./x`)가 되었으며, 맨 폼 전용 키는 `options`·`presentation` 그룹으로 옮겨졌다(GOAL-004).

값이 스키마를 만족하는지는 언제나 검증기 구현체가 답한다(GOAL-005). 폼은 스키마의 구조(무엇이 어디에 선언되어 있는가)만 읽는다(GOAL-005). 스펙 준수는 검증기의 책임이고 스키마 선언은 작성자의 책임이다(GOAL-005). 폼이 독자 스펙을 떠안지 않는다(GOAL-005).

- 검증기는 교체 가능한 플러그인으로 남는다(GOAL-005). 폼은 검증기를 내장하지 않는다(GOAL-005).
- 같은 개념을 평가하는 장치는 하나다(GOAL-005).

→ ADR 0004, 0005(GOAL-005).

### 1.5 구조와 라이프사이클

노드 트리의 구성, 특히 자식을 가진 노드(object·array)가 자식을 만들고 켜고 끄는 방식을 하나의 모델로 다시 짠다(GOAL-006). 합목적적이고, 특수 경로가 없고, 읽는 사람이 예측할 수 있어야 한다(GOAL-006).

- 조건부로 형상을 바꾸는 모든 구문이 같은 장치와 같은 라이프사이클을 탄다(GOAL-006).
- object와 array는 "자식의 집합이 어디서 오는가"만 다르고 나머지는 같은 모델을 따른다(GOAL-006).
- 값은 한 곳에만 있다(GOAL-006).

→ ADR 0005, 0006, 0011(GOAL-006).

**3.3 G4를 좁힌다.**(GOAL-008) "트리의 형태는 렌더링 런타임에 좌우되지 않는다"로 고친다(GOAL-008). 소유자의 발언(GOAL-016, 입력 컴포넌트 유무로 노드 종류가 달라지는 것은 의도된 기능)이 근거다(GOAL-008).

쓰기 하나가 정착된 상태에 이르는 길은 하나이고, 순서가 고정되어 있으며, 동기다(GOAL-009). 비동기는 경계(통지, 검증, React)에만 있다(GOAL-009). 같은 스키마와 같은 쓰기 순서는 타이밍과 무관하게 같은 상태를 낸다(GOAL-009).

- 소유자가 데이터의 흐름을 순서도 한 장으로 따라갈 수 있다(GOAL-009).
- 구독자는 정착된 상태만 본다(GOAL-009). 원인과 결과의 순서가 뒤집히지 않는다(GOAL-009).
- 핵심 동작을 타이머 없이 테스트할 수 있다(GOAL-009).

→ ADR 0007(GOAL-009).

**3.1 G5의 "같은 쓰기 순서"는 정착 단위이고, `batch`는 쓰기 하나로 센다.**(GOAL-010) `batch`는 타이밍이 아니라 호출자가 선언한 쓰기 단위다(G7, EVENT-013)(GOAL-010). 이 읽기에서 "배치와 순차의 값 차이는 결함이 아니다"(EVENT-019)가 나온다(GOAL-010). 다르게 읽으면 "정착마다 없음인 `default`를 커밋한다"와 "커밋된 값은 뒤의 전환에서 덮지 않는다" 가운데 하나를 버려야 한다(GOAL-010). 셋은 양립하지 않는다는 것이 독립 모델과 프로토타입 둘에서 실행으로 확인됐다(GOAL-010).

### 1.6 성능과 반응의 목표

패키지의 핵심 가치다(GOAL-011). 어떤 동작의 비용은 폼의 크기가 아니라 그 동작이 바꾼 것의 크기에 비례한다(GOAL-011). 계산할 필요가 없는 것은 계산하지 않는다(GOAL-011).

- 대상 상황: 대규모 쓰기, 배치 작업, 빠른 연속 입력, 화면 전환(분기 전환·마운트)(GOAL-011).
- 같은 값을 두 번 읽으면 같은 참조다(GOAL-011).
- 성능은 주장하지 않고 측정한다(GOAL-011). 기존 구현이 기준선이고, 예산과 시나리오는 설계의 일부다(GOAL-011).
- 번들 크기도 예산이다(GOAL-011). 번들 기준은 v0.16.0의 37,023 B(ESM 진입 minify + gzip -9, 의존성 외부)다(GOAL-011, TEST-075).

→ ADR 0009(GOAL-011).

노드 단위의 구독, 이벤트 시그널링, 배치 갱신은 노드 트리의 축이자 대규모 폼을 빠르게 움직이는 장치다(GOAL-012). 개편하되 없애지 않는다(GOAL-012). 배치는 통지의 묶음에서 "쓰기 묶음 → 정착 1회 → 통지 1회"로 강해진다(GOAL-012).

→ ADR 0008(GOAL-012).

JSON Schema로 폼을 만드는 분야의 보편적이고 직관적인 관행과 UX를 조사해 흡수한다(GOAL-013). 독자적인 방식은 보편적인 방식이 목표를 해칠 때에만 택한다(GOAL-013).

→ ADR 0010(작성 대기)(GOAL-013).

### 1.8 목표 사이의 긴장

- **목표 G3(의미는 위임한다) ↔ G6.**(GOAL-023) 가드를 검증기에 위임하면 호출 비용이 생기고, 폼이 `if`의 내부를 읽지 않으면 의존 경로를 모른다(GOAL-023). 측정(TEST-036): 루트에 걸린 가드 200개를 키 입력마다 전부 돌려도 7.9 µs이고, "가드가 걸린 객체의 참조가 그대로면 건너뛴다"는 루트 가드에 효과가 없다(GOAL-023). 유효한 것은 변경 경로 → 가드의 역색인뿐이며, 이것도 측정이 필요를 보일 때만 넣는다(GOAL-023).
- **G5 ↔ G6.**(GOAL-024) 동기 작업 루프는 쓰기 한 번의 작업량을 늘릴 수 있다(GOAL-024). 해소: 건너뛰기가 설계의 일부다 — 참조가 그대로인 가드, dirty 표시가 없는 서브트리, 의존 값이 그대로인 표현식(GOAL-024).

### 1.11 판정과 형상 문법

**P1′ (소유자, 2026-09-23).**(GOAL-026) 폼이 스키마에서 읽는 것은 **노드 트리의 모양을 정하는 문법뿐**이다 — 타입(`type`, 튜플. 다중 `type`은 BLUEPRINT-036의 설계 항목), 자식의 존재(`properties`, `items`, `prefixItems`), 조건부 존재(`if/then/else`, `allOf` 항목)(GOAL-026). 값의 유효성을 정하는 문법(`required`, `false`, `not`, `additionalProperties`, 범위·패턴)은 검증기의 것이고, 폼은 그 판정을 **보여 줄 뿐** 값을 고치지 않는다(GOAL-026). 값을 빼거나 지우는 것은 작성자의 `controls`의 명령과, 호출자가 Form 속성으로 켠 나감 정책뿐이다(GOAL-026). 둘 다 P2의 쓰기 주체다(GOAL-026). 폼이 스스로 지우는 일은 없다(GOAL-026). 소유자의 말: "그걸 바랐다면 ajv autofix 같은 걸 쓰지 않았을까. … 값 수정은 안 하고 에러만 보여주는 걸 기본 동작으로 하려고 했다."(GOAL-026).

**P1′의 분기 문장(10·11라운드).**(GOAL-027) 폼은 게이트 없이 분기를 고르지 않는다(GOAL-027). 게이트는 둘뿐이다 — `if`(검증기가 판정)와 `controls.active`(작성자의 식)(GOAL-027). `controls.discriminator`는 분기마다 `controls.active`를 적어 주는 설탕이며 게이트의 종류를 더하지 않는다(GOAL-027). 분기가 선언한 필드는 조각으로 읽어 노드로 만들고, 어느 분기가 유효한지는 검증기만 판정한다(GOAL-027). "읽는 것은 모양 문법뿐"의 유일한 예외는 `controls.discriminator` 아래의 `const`·`enum`이다(GOAL-034의 축 1항(폼은 JSON Schema 문법을 해석하지 않는다) 예외, BLUEPRINT-017)(GOAL-027). 소유자의 틀(답 3 "`if/then/else`는 예외적으로 분기를 결정한다", 답 22)과 같은 뜻이다: 예약 층 밖에서 형상을 조건부로 정하는 문법은 `if/then/else`뿐이고, 명시 없는 `oneOf`·`anyOf`는 모든 분기가 켜진다(GOAL-027). 오늘의 `const`·`enum` 자동 감지는 사라지므로 "현행과 같다"(답 22)는 아니며 이주 항목이다(11라운드 확인 목록)(GOAL-027).

### 1.12 소유자의 축과 스키마 경계

원리 위에 놓이며, 충돌하면 이 열 항목이 이긴다(GOAL-033). 요지만 적는다(GOAL-033).

1. 폼은 JSON Schema 문법을 해석하지 않는다(GOAL-034). `if` 블록은 그 블록이 지금 켜지는지만 본다(GOAL-034). `oneOf`·`anyOf`도 같다(GOAL-034). 스키마로 분기를 표현할 때는 `if` 블록이 컨벤션이고, `enum`·`const` 판별식은 쓰지 않는다(GOAL-034). **예외(10라운드, 소유자 동의):** 작성자가 `controls.discriminator`로 명시한 union은 분기의 `const`·`enum`을 읽어 분기별 `controls.active`로 바꾼다(GOAL-034). 추가할 근거가 있으면 상당한 이유와 함께 제안하라고 하셨다(GOAL-034).
2. 조건에 쓰는 프로퍼티는 `properties`에 선언되어야 한다(GOAL-035). 컨벤션이며 폼은 검사하지 않는다(소유자: "`if` 안에 `anyOf`·`oneOf`나 더 복잡한 스키마가 올 수 있어 관여하기로 하면 끝이 없다")(GOAL-035).
3. `then`·`oneOf`·`allOf`·`anyOf` 블록에서 프로퍼티 노드를 선언할 수 있다(GOAL-036). 축 2항은 컨벤션이며 폼은 검사하지 않는다(GOAL-036, GOAL-035, FRAGMENT-023).
4. JSON Schema 설정에 의한 폼 변환과 필드 노출 변환에서 값을 조작하지 않는다(GOAL-037). 읽기: 조각의 켜짐·꺼짐은 **있는 값을 바꾸거나 지우지 않는다**(나감의 비움은 JSON Schema 설정이 아니라 정책 키의 쓰기다, WRITE-037)(GOAL-037). 없음인 키를 채우는 것은 노드가 생기는 사건의 일부다(WRITE-090)(GOAL-037).
5. 각 노드가 지금 가진 제약(JSON Schema 조건)을 최신화해 제공할 의무는 폼이 진다(SCHEMA-007의 병합표)(GOAL-038).

### 1.13 값 제어와 설정의 축

6. `controls`의 키에는 완전히 다른 규칙이 적용된다(GOAL-039). 값을 바꾸고, 필드를 가리고, 상태 변화에 따라 값을 빼거나 바꾸거나 다른 노드에 영향을 준다(GOAL-039). "값을 제어하는" 층이다(15라운드 개정: `&` 축약을 없애고 `controls` 그룹으로 적는다)(GOAL-039).
7. JSON Schema 표현은 `controls` 표현으로 대체할 수 있어야 한다(15라운드 개정)(GOAL-040).
8. `controls`의 식과 `injectTo`는 폼을 제어하는 예약어이며 명확한 동작 위계와 이름 컨벤션을 가진다(15라운드 개정)(GOAL-041).
9. 폼 전용 키는 그룹 객체 셋(`controls`·`options`·`presentation`) 안에만 둔다(GOAL-042). 평면 `&` 축약과 `computed` 별칭은 두지 않는다(15라운드 개정)(GOAL-042). 이전 문장 "`computed`(새 이름 `control`)와 `&`의 동시 제공은 유지한다"를 뒤집었다(GOAL-042). 소유자: "숏컷을 모두 없애고 중첩 객체로 하는 게 빼기도 편하고 나중에 서버 스키마랑 클라이언트 스키마를 병합하기도 편하겠지"(GOAL-042).
10. 글로벌 설정과 로컬 설정의 동시 제공과 경합은 기존과 같이 제공한다(GOAL-044). 읽기(소유자, 10라운드): "props로 전달되는 글로벌 값이 개별 값을 덮는다. `rootJSONSchema`도 props와 동치."(GOAL-044). **개정(소유자, 13라운드):** "글로벌 readOnly나 disabled 같은 개념은 없애고 모든 control 필드는 자체 노드만 지원. children 그룹은 예외. 이건 검증의 영역이 아니라 react의 표현 영역."(GOAL-044). 곧 코어에는 글로벌 잠금이 없고, 루트 스키마 키는 루트 노드의 로컬 키이며, Form 속성 `readOnly`·`disabled`는 렌더 계층이 참일 때만 거는 전체 잠금(코어 밖, P5)이다(GOAL-044). 소유자 확인(13라운드): "props로 전달되는 글로벌 readOnly와 disabled만 특별 관리를 하자. 코어 트리와 유리된 전역 동작으로 읽으면 된다."(GOAL-044).

요약 발언: "최소한의 제약으로 jsonSchema를 최대한 반영. UI 제어는 최대한 `&`로. 값 변경도 전량 `&`와 `injectTo`로. JSON Schema는 사후 검증, 폼은 대상값을 만들면서 검증이라는 태생적 차이를 `&` 패밀리로 메우고, `if/then/else`를 함께 써서 JSON만으로도 동작하는 구조."(15라운드: 이 발언의 `&`는 `controls`로 읽는다)(GOAL-045).

- **읽기 1.**(GOAL-046) `oneOf`·`anyOf`는 형상 선언이 아니라 진짜 검증 조건이다(GOAL-046). 분기의 필드는 노드의 `controls.active`·`controls.visible`이나 부모의 자식 집합 제어로 다루고, JSON만으로 다루려면 분기 안에 `if/then/else`를 넣는다(GOAL-046). 순수한 `oneOf`·`anyOf`도 허용하되 그때는 작성자가 `controls`로 제어할 책임을 진다(GOAL-046).
- **읽기 2.**(GOAL-047) 없는 값 채우기, 있는 값 바꾸기, 있는 값 지우기는 모두 원리상 가능해야 한다(GOAL-047). 채움의 원천은 `controls.default` > `default` > 없음, 시점은 노드가 생길 때(A)(GOAL-047). 4항의 "값을 조작하지 않는다"에 없음인 키를 채우는 것도 든다(GOAL-047). 없는 값 채우기(표준 `default`, 호출자의 `defaultValue`, `controls.derived`·`controls.injectTo`, 표현식으로 계산한 기본값), 있는 값 바꾸기, 있는 값 지우기는 모두 원리상 가능해야 한다(GOAL-047, GOAL-042).
- **읽기 3.**(GOAL-048) 축 10항(글로벌과 로컬의 경합, 13라운드 개정)은 루트 스키마의 `readOnly`·`disabled` 같은 것을 가리켰으나 13라운드에 개정되었다: 코어의 상태 키는 그 노드에만 걸린다(로컬뿐)(GOAL-048). 조상의 상속도, 루트의 글로벌도 없다(GOAL-048). 자손을 거는 길은 부모의 `controls.children`(명시한 대상)과 켜진 조각의 `controls`뿐이다(GOAL-048). 나감의 비움 정책 `unsetOnInactive`만은 둘째 예외로, 나가는 객체·분기에 켠 정책이 함께 나가는 하위 트리로 내려간다(17라운드 소유자 답 R17-2 ㄴ, WRITE-033)(GOAL-048). 전체 잠금은 렌더 계층의 Form 속성이다(GOAL-048).

## 2. 검토 절차와 문서 규칙

### 2.1 결정의 주인과 도출 기준

여전히 **결정은 소유자의 것**이며, `reviews/round-5-derivations.md`에 적힌 것은 "원리를 받아들이면 이렇게 된다"이다(PROCESS-054).
