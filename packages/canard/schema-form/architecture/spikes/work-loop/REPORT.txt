ENVIRONMENT
  Node v24.20.0, darwin arm64 (Darwin 25.6.0). CPU model string is unreadable
  under the sandbox; reviews/round-1.md §2 records this machine as Apple M1 Max.
  ajv 8.17.1 (ajv/dist/2020, allErrors:false), resolved from
  packages/canard/schema-form-ajv8-plugin. Nothing was installed.
  Current library driven from src/ via vite-node, alias @/schema-form -> src.

METHOD (follows reviews/round-1.md §2)
  Calibrated internal batch (~25 ms) divided by its iteration count; >=2 s
  warm-up; 7-11 timed batches; median reported with the p25-p75 spread.
  Inputs are cycled and every result is consumed into a checksum. EVERY case
  runs in its OWN process. tinybench was deliberately not used (round-1 §2
  measured it 4-6x high below 100 ns; several numbers here are in that range).
  Confirming round-1's warning: running the prototype's self-checks in the same
  process as the measurement read S1 as 125 us instead of 1.29 us -- ~100x, the
  exact magnitude round-1 §2 reported. All numbers below are per-process.

  Prototype correctness gate (proto/selfcheck.mjs, ALL PASSING, run before
  measuring, in its own process): untouched siblings keep identical memo
  references; the root memo moves iff something emitted changed; deactivate ->
  reactivate restores the raw value; `if:{not:{required:['x']}}, then x
  default 1` hits the 25-pass cap, throws synchronously, and leaves the
  committed tree and the staged write untouched; a batch settles once; a guard
  flip toggles exactly the three fields its fragment declares.

LANES. The current write path is split in time, so it is reported in three:
  WRITE = synchronous setValue, reading the written leaf back.
  EMIT  = setValue + root.value -- where ObjectNode's lazy __composed__ actually
          rebuilds the emitted object. This is the lane comparable to flush().
  DRAIN = plus a macrotask drain, amortized over 100 writes as
          bench/event-cascade.bench.ts does (one drain is ~1 ms timer-bound).

FINDINGS
--------------------------------------------------------------------------------
1. The loop is clearly cheaper on the input path, by two orders of magnitude.
   A settled keystroke is 1.29 us vs 557 us (flat 1,000) and 3.23 us vs 533 us
   (10,000-item array). The win is not the loop's cleverness: it is that today
   recomposes the whole emitted object on the first read after a write, while
   the loop copies the previous memo and patches the one key that moved.

2. Its cost is dominated by the emitted-value copy, not by walking or guards.
   With the dirty-child list the walk visits 2-4 nodes per keystroke and the
   guards cost 7.7 us per 200 (matching round-1's 7.9 us). Everything else is
   the object/array copy. Passes matter less than feared: 1 pass when no guard
   input moves, 2 when it does, 3 for a fragment flip.

3. "Reads never compute" holds -- and it already holds today for SETTLED reads
   (3.6-9.4 ns). The redesign's gain is not cheaper reads but removing the
   recompose-on-first-read-after-write, and the staleness. Not a read-speed
   win; consistency at no read cost.

4. Two implementation choices decide whether the loop wins at all, and the ADR
   text currently implies the losing one. "recompute memo from active children"
   read literally is a full rebuild: 134 us vs 1.29 us, 104x. And a dirty FLAG
   scanned over children is O(tree): 55.5 us vs 3.23 us on a 10,000-item array,
   17x. The design must say: copy-and-patch the previous memo, and keep a
   per-node dirty-CHILD list. Neither is implied by the current wording.

5. What makes it lose on 10,000-item arrays: not the array copy (1.4 us for
   10,000 slots) but per-item work. A bulk root write is 5.72 ms (60,002 nodes
   touched); construction is 13.15 ms. Both are O(n) by nature -- ADR 0011's
   lazy node materialisation is the only lever.

6. A hard cliff nobody has costed: V8 cannot keep an object with more than 1,020
   own properties in fast mode. At 1,020 keys a copy-and-patch is 1.02 us; at
   1,021 it is 141 us -- 138x, a step, not a slope. S1 at 1,100 fields costs
   153 us per keystroke. This caps ONE object's key count, not the form's size,
   and it binds the current implementation too. Nesting stays cheap; a form with
   >1,020 sibling top-level fields does not. Worth stating as a documented limit.

7. omitEmpty has the same shape of problem. Removing a key from the emitted
   object forces `delete`, which drops V8 to dictionary mode; restoring fast mode
   costs a second full copy (~100 us at 800 keys). That is why the S3b flip is
   106 us while the S3a keystroke is 12 us. Emptying or filling a field is the
   expensive keystroke; typing inside a non-empty field is the cheap one.

8. The inverted index is the only guard-skipping strategy that works, confirming
   round-1 §2 exactly: 400 guard calls -> 0, 11.98 us -> 2.42 us. "Skip guards
   whose host emitted reference did not change" is worthless for root-hosted
   guards -- every write moves the root reference. Guard COMPILE, not guard
   calls, is the real cost: 22.4 ms for 200, and lazy compile makes it worse
   (29.2 ms) because priming evaluates every guard.

9. Where the redesign is clearly MORE expensive today: construction of a
   conditional form. 23.0 ms (585 us tree + 22.4 ms AJV compile) against 13.4 ms
   for the current `&`-expression compiler -- 1.7x worse. ADR 0004's choice to
   delegate guards to the validator is paid here, at form-creation time, on the
   main thread. This is the one budget the owner should set a number for.

--------------------------------------------------------------------------------
THREATS TO VALIDITY
--------------------------------------------------------------------------------
- The prototype is a LOWER BOUND, not a prediction. It has no validation, no
  events or subscribers, no React, no null contract, no schema parsing, no
  normalizedValue/omitTrailing, no array identity, no injectTo/derived, no
  error routing, no revision ledger. Each of these adds work to the same path.
- S3 is not apples-to-apples in either direction: the current library cannot
  express 200 independent root conditionals at all, and the analogue used
  (computed.active) needs 600 expressions against 200 guards. Read S3 as
  "different mechanisms, same user-visible feature", not as a speedup factor.
- Equivalence used: both sides must end with a consistent emitted root. So the
  current EMIT lane (recompose) is compared against the prototype's flush
  (commit). The WRITE lane alone (509 ns) is NOT comparable -- after it the tree
  has no emitted value. S2 uses the drained number because its sync read is
  stale, and that number includes event-cascade work the prototype never does.
  S5's unbatched current figure is timer-floor bound, not core cost.
- Desktop arm64 only. No mobile, no low-end device, no memory measurement, no
  React render cost. round-1's documented safe thresholds (<50 fields) were set
  on mobile and nothing here revises them.
- The V8 cliff and the dictionary-mode effects are V8-specific. JSC and
  SpiderMonkey have their own thresholds, unmeasured here.
- Guard compile time varies 70-270 us per guard across sources; 22.4 ms for 200
  is this machine, this AJV configuration, these trivial const guards.
