3. MECHANISM OBSERVED (react-dom 19.2.6, cjs/react-dom-client.development.js)
- ChangeEventPlugin enqueues the controlled target for restoration when it fires onChange
  (enqueueStateRestore, lines 3518-3522).
- batchedUpdates$1 (3251-3272) runs the handler, then in `finally`, ONLY IF a restore
  target exists: flushSyncWork$1() (16896) → then restoreStateOfTarget (3178) →
  updateInput (1644): `element.value !== "" + value && (element.value = ...)` (1666-1667),
  where `value` is the props currently attached to the DOM node (internalPropsKey).
- Mode A: onStoreChange runs inside the handler → forceStoreRerender (8260, SyncLane 2)
  → flushSyncWork$1 renders+commits BEFORE restore, so the attached props already carry
  the new value. For a plain input the committed value equals the DOM text, updateInput
  writes nothing, and the caret stays where the browser put it (case 2, 2c, 5).
- Mode B: nothing is scheduled inside the handler, so restore runs against the OLD props
  and writes the old value back into the DOM (jsdom, like browsers, moves the selection to
  the end on a value write). The microtask then notifies → forceStoreRerender → React's
  own microtask flush (scheduleImmediateRootScheduleTask, 18979) → commit writes the new
  value → caret to the end again. Two DOM writes per keystroke; between them the DOM shows
  the previous value (2c), and the next keystroke or the next composition step is applied
  on top of the reset text (2: "y" lands at the end; 5: DOM one step behind the IME).
- Batching (3/3b/3c): all 1,000 SyncLane updates coalesce into one root render and one
  commit in both modes (3: act flush; 3b: React's microtask flush — a click enqueues no
  restore target, so no in-handler flush happens; only onChange gets that). Sync notify
  does not cost 1,000 commits: React batches, the store need not.
- Re-entrancy (4): both waves run inside the same handler in mode A, so the single sync
  flush sees final values for a and b; getSnapshot (revision) is stable within a render,
  no tearing and no "getSnapshot should be cached" warning.

4. SUB-CASE WHERE MODE B DOES NOT FAIL, AND WHY
- 1a/1b (the library's own T-1 test shape: formatter + useLayoutEffect setSelectionRange):
  the bookkeeping repositions the caret at every commit, and under userEvent the
  microtask commit lands before the next key (userEvent awaits setTimeout(0) per key).
  So the caret assertion at the end of `form.type()` passes in BOTH modes — the existing
  test `controlled-interaction.render.test.tsx:340-368` does not discriminate sync from
  microtask notification. It also passes because the typed text reaches the end position.
- 1c shows the converse: with a value rewrite (dash insertion) and no bookkeeping the
  caret jumps to the end even in mode A, because updateInput writes the differing value.
  Sync notify buys "no DOM write when the value is unchanged"; formatting caret repair
  remains the input's job (T-1's bookkeeping) in either design.
- IME: user-event 14.6.1 has no composition API; case 5 uses fireEvent composition events
  plus native value writes. jsdom does not model the browser behaviour that a programmatic
  value write during composition cancels the composition; the observed DOM reset in mode
  B is the trigger of that cancellation, not the cancellation itself.

5. VERDICT
- B2-1: PASS with a precision fix. Sync notify inside the onChange handler is what keeps
  React's controlled-state restore from rewriting the DOM (cases 2, 2c, 5), and a microtask
  delay breaks it exactly as claimed — for plain controlled inputs and IME. The claim's
  wording "so the caret is preserved" holds only for edits that leave the committed value
  equal to the DOM text; a formatter that rewrites the value needs the layout-effect
  bookkeeping in both designs (1c), and with that bookkeeping the current T-1 acceptance
  test cannot tell the two designs apart (1a/1b). Recommend adding case 2 (plain controlled
  mid-text typing) and 2c (DOM value immediately after the event) to the T-1 acceptance
  criteria — they are the ones that go red under deferred notification.
- B2-2: PASS. 1,000 synchronous notifications in one handler → 1 commit, 1,000 component
  renders, 0 stale fields (3, 3b, 3c). Note the mechanism is React's SyncLane batching,
  not the store: for a click handler the commit happens in React's microtask, not inside
  the handler; only the onChange path flushes in-handler (via the restore-target branch).
- §B3-4 re-entrancy under sync notify: PASS — two waves inside one handler, one commit,
  no tearing (4).
