# 최종 결론 2판 — 소유자 검토용 (9라운드, 소유자의 축 열 항목 반영)

작성 2026-09-23. [`06-conclusions.md`](./06-conclusions.md)(8라운드까지의 결론)를 소유자가 검토하기 전에 소유자가 설계의 축에 열 항목을 더했고, 그 위에서 9라운드가 다시 도출했다. 이 문서가 06을 대체한다. 06에서 그대로인 항목은 한 줄로 요약하고 전문의 위치를 가리키며, 바뀌거나 새로 생긴 항목은 여기에 전문을 적는다. 이 문서는 새 결정을 만들지 않는다. 이미 나온 결론을 약어와 생략 없이 풀어 쓴 것이다.

## 0. 이 문서를 읽는 법

- **절 단위로 통과 또는 반려한다.** 3절(원리의 읽기 확인), 4절(도출로 닫힌 결정), 5절(소유자가 답할 것), 6절(이름과 표면), 7절(실측과 프로토타입, 실험)이 판정 대상이다. 1절과 2절은 배경이고, 8절은 정정 기록, 9절은 통과 뒤에 일어나는 일, 11절(개발 진입 평가)은 소유자의 질문에 대한 답이며, 5.1의 22 말고는 새 판정 대상을 만들지 않는다.
- **항목의 구조.** 바뀌거나 새로 생긴 항목은 "질문 → 배경 → 결론 → 왜 그런가 → 무엇이 바뀌는가 → 소유자에게 남는 것" 순서로 적었다. 이해되지 않는 항목은 그 항목만 반려하면 된다.
- **"도출"과 "정책"의 뜻.** 도출은 "축(원리, 목표, 소유자의 열 항목과 세 답)만으로 답이 하나로 정해진다"는 뜻이다. 소유자는 그 답을 확인만 하면 되고, 다르게 정하려면 축을 바꿔야 한다. 정책은 "축이 두 답을 모두 허용한다"는 뜻이다. 소유자가 고른다.
- **"확신 중"의 뜻.** 도출이지만 근거가 좁거나 판정자가 확신을 낮춰 적은 것이다. 소유자가 읽고 받는다.
- **번호의 뜻.** `D-12` 같은 번호는 검토 라운드가 결정 항목에 붙인 꼬리표이고, `Q1`–`Q8`은 9라운드 명세의 도출 과제 번호다. 번호 옆에 언제나 풀어 쓴 이름을 함께 적었다. `P1`–`P5`·`P1′`은 설계의 원리, `G1`–`G8`은 목표, 열 항목은 소유자가 이번에 더한 축이며 모두 2절에 있다.
- **06과의 관계.** 06의 항목마다 "그대로 / 바뀜 / 지워짐"을 표시했다. 06의 3절은 07 3절 첫 줄에, 4절은 4.0의 표에, 5절은 5.2 표 아래 문단(06의 5.2·5.5·5.6)과 5.1–5.4의 괄호에, 6절은 6.2의 표에, 7절은 7.3에 있다. 그대로인 항목의 전문은 06에 있고, 여기서는 결론 한 줄만 다시 적는다.

## 1. 용어

06의 용어표 위에 더하거나 바꾼 것이다. 나머지는 06 §1 그대로다.

| 용어 | 뜻 |
| --- | --- |
| JSON Schema 층 | 표준 키워드 전부. 검증기에 그대로 가며, 폼은 형상(어떤 노드가 있는가)을 만드는 최소한만 읽는다. 값을 채우지도 바꾸지도 지우지도 않는다. 표준 `default`는 노드가 생길 때 채움의 원천으로만 읽힌다(3.8) |
| 예약 층 | `&`로 시작하는 제어 키(게이트·잠금·숨김·값 규칙·자식 제어·판별)와 그 객체 표기(`control.*`). 값과 UI를 제어한다. 표현 키(`FormTypeInput`, `options` 등)는 접두 없이 두며 예약 층이 아니다(13라운드 답 3). 오늘의 `computed`·`&`·`injectTo`가 여기로 모인다 |
| `control` | 예약 층의 객체 표기 컨테이너. 오늘의 `computed`를 대신한다. `control.active`는 `&active`와 같은 것의 두 번째 철자다 |
| 조각 | 게이트가 켜고 끄는 선언 묶음. `then`·`else` 블록, `allOf` 항목, `oneOf`·`anyOf`의 분기. 게이트가 없는 조각은 늘 켜져 있다 |
| 게이트 | 조각이나 노드를 켜는 조건. JSON Schema 층의 게이트는 `if`(검증기 플러그인이 컴파일), 예약 층의 게이트는 `&active`(표현식). 노드 스키마에 쓰면 노드 게이트, 조각 객체에 쓰면 조각 게이트다. 한 장치의 두 범위다 |
| 노드가 생김 | 그 노드가 직전 커밋의 형상에 없고 이번 정착의 최종 형상에 있는 것. 로드로 처음 만들어질 때, 조각이나 노드 게이트가 꺼짐에서 켜짐으로 바뀔 때다. 본체나 다른 켜진 조각이 이미 두고 있던 노드는 새 조각이 켜져도 생기지 않는다 |
| 채움 | 노드가 생길 때 값이 없음이면 `&default`(표현식) > `default`(표준 키워드) > 없음의 순서로 한 번 넣는 것. 06의 "로드 계약"과 "전이 주입"이 이 한 사건으로 합쳐진다 |
| 상태 칸 | 노드가 실제로 소유하는 상태. 원본(`raw`)과 `extras` **둘뿐**이다. 06의 `selection`은 사라졌다 |
| 자동 쓰기 | 규칙이 원본에 쓰는 것. 채움, `&derived`, `&injectTo`, `&unsetValue`(옛 이름 `&clearValue`, 12라운드), 나감의 비움(정책 키를 켠 노드, 기본 꺼짐, 13라운드). 06의 셋에 `&unsetValue`와 나감의 비움이 더해졌다 |
| 같은 대상 규칙 | 파생 단계에서 여러 자동 쓰기가 한 노드에 쓰려 할 때 라운드마다 하나만 적용하는 규칙 |
| `&unsetValue` | 새 키. 표현식이 거짓에서 참이 되는 순간 노드의 값을 뺀다. 입력은 남는다. 없음으로 만드는 장치는 이것 하나이고 발화원이 둘이다. 하나는 식의 거짓→참이고, 다른 하나는 정책 키를 켠 노드의 나감이다(원장 §3) |
| `&resetInteraction` | `&pristine`의 새 이름(5.0의 5). 표현식이 참이 되면 `dirty`·`touched` 상태를 초기화한다. 값은 두지 않는다. 판정은 정착의 커밋 단계에서 한다 |
| 자식 집합 제어 | 부모가 자식 여럿에 한 번에 거는 제어(상태 키와 값 키, 5.0의 15). 두 형태가 있다. 조각 객체에 `&readOnly` 등을 두면 그 조각이 선언한 노드 전부에 걸리고(조각 범위 제어), 객체 노드의 `&children` 블록은 이름으로 가리킨 직계 자식에 걸린다 |
| 결합 규칙 | 한 노드에 상태 제어가 겹칠 때의 규칙(4.26, 소유자 답 13, 13라운드 답 1). 코어에는 글로벌이 없고 로컬(노드 자신의 키·`&` 식·`control.*`, 켜진 조각의 범위 제어, 부모의 `&children` 항목)만 있다. 조상의 상속은 없다. Form 속성 `readOnly`·`disabled`는 렌더 계층이 참일 때만 거는 전체 잠금이다(P5). 로컬 안에서는 `readOnly`·`disabled`는 하나라도 잠그면 잠기고 `active`·`visible`은 모두 허용해야 켜진다(편집자 판정, 소유자 확인 대상, 원장 §7) |

지워진 용어: 판별식, `selection`, 값 가드, 선택 가드, 전이 주입(채움으로 흡수), 로드 계약(채움으로 흡수).

## 2. 축 — 결정을 낳는 원리, 목표, 소유자의 열 항목

### 2.1 원리와 목표

06 §2.1·§2.2·§2.3 그대로다(P1–P5, P1′, G1·G2·G4–G8, C2·C8, 이미 수락된 결정). 다만 P2의 주체 목록은 열 항목으로 넓어지고(3.2), P1′의 판별식 괄호는 지워지며(3.4), §2.3의 수락 결정 가운데 D-8은 지워진다(4.0).

### 2.2 소유자의 열 항목 (2026-09-23, 원문은 `reviews/round-9-spec.md` §1)

원문을 줄이지 않고 옮기면 길어 요지만 적는다. 원문이 우선한다.

1. 폼은 JSON Schema 문법을 해석하지 않는다. `if` 블록은 그 블록이 지금 켜지는지만 본다. `oneOf`·`anyOf`도 같다. 스키마로 분기를 표현할 때는 `if` 블록을 쓰는 것이 컨벤션이고, `enum`·`const`를 판별식으로 쓰는 특수 문법은 쓰지 않는다. 추가할 근거가 있으면 상당한 이유와 함께 제안하라고 하셨다.
2. 조건에 쓰는 프로퍼티는 `properties`에 선언되어야 한다(제약).
3. `then`·`oneOf`·`allOf`·`anyOf` 블록에서 프로퍼티 노드를 선언할 수 있다. 제약은 2항뿐이다.
4. JSON Schema 설정에 의한 폼 변환과 필드 노출 변환에서 값을 조작하지 않는다.
5. 각 노드가 지금 가진 제약(JSON Schema 조건)을 최신화해 제공할 의무는 폼이 진다. 유효성 조건 밖의 커스텀 필드를 어떻게 병합할지는 고민해 볼 필요가 있다.
6. `&`로 시작하는 키에는 완전히 다른 규칙이 적용된다. 값을 바꾸고, 필드를 가리고, 상태 변화에 따라 값을 빼거나 바꾸거나 다른 노드에 영향을 주는 확장 조작을 허용한다. "값을 제어하는" 층이다.
7. JSON Schema 표현은 `&` 표현으로 대체할 수 있어야 한다.
8. `&` 표현식과 `injectTo`는 폼을 제어하는 예약어이며, 명확한 동작 위계와 이름 컨벤션을 가진다.
9. `computed`와 `&`를 함께 제공하는 쪽을 선호한다(제거해도 무방하다).
10. 글로벌 설정식과 로컬 설정식의 동시 제공과 경합은 기존과 같이 제공한다.

**개정(소유자, 13라운드):** 코어에는 글로벌 잠금이 없고 모든 제어 필드는 자체 노드만 지원한다. `&children` 그룹은 예외다. 전체 잠금은 렌더 계층의 Form 속성이다(원장 §1.2의 10항).

요약 발언의 요지(원문은 명세 §1 끝): 최소한의 제약으로 JSON Schema를 최대한 반영한다. UI 제어는 최대한 `&`로 하고, 노드 단위가 아니라 하위 노드를 한 번에 제어하는 문법도 설계한다. 값 변경도 전량 `&`와 `injectTo`로 하며, `injectTo`를 `&` 패밀리에 넣으면 `computed`의 이름을 바꾼다. JSON Schema는 사후 검증이고 폼은 대상값을 만들면서 검증한다는 태생적 차이를 `&` 패밀리로 메우고, `if/then/else`를 함께 써서 JSON만으로도 동작하는 구조를 만든다.

### 2.3 소유자의 답 셋 (원문은 `reviews/round-9-spec.md` §2)

- **읽기 1.** `oneOf`·`anyOf`는 형상 선언이 아니라 진짜 검증 조건이다. 분기의 필드는 노드의 `&active`·`&visible`이나 부모의 자식 집합 제어로 다루고, JSON만으로 다루려면 분기 안에 `if/then/else`를 넣는다. 순수한 `oneOf`·`anyOf`도 허용하되 그때는 작성자가 `&`로 제어할 책임을 진다.
- **읽기 2.** 4항의 "값을 조작하지 않는다"에 없음인 키를 채우는 것도 든다. 없는 값 채우기(표준 `default`, 호출자의 `defaultValue`, `&derived`·`injectTo`, 표현식으로 계산한 기본값), 있는 값 바꾸기, 있는 값 지우기는 모두 원리상 가능해야 한다. 채움의 원천은 `&default` > `default` > 없음이고, 시점은 **노드가 생길 때**(A)다.
- **읽기 3.** 10항은 루트 스키마의 `readOnly`·`disabled` 같은 것을 가리키며, root·local·inherit의 위계 전체가 설계 대상이다. **개정(13라운드):** 코어의 상태 키는 그 노드에만 걸린다. 조상의 상속도 루트의 글로벌도 없다(원장 §1.3).

## 3. 원리의 읽기 확인 — 결정이 아니라 읽기다

06의 일곱 가운데 3.1·3.3·3.5·3.6은 그대로다(전문은 06 §3). 아래는 바뀌거나 새로 생긴 것이다.

**3.2 P2의 문구(바뀜).** "원본에 쓰는 주체는 사용자 입력, 호출자의 `setValue`와 `reset`, 그리고 작성자가 선언한 규칙(노드가 생길 때의 채움과 그 원천인 예약 층의 `&default` 또는 표준 `default`, 그리고 예약 층의 `&derived`·`&injectTo`·`&unsetValue`)이다. 코어가 스스로 원본을 고치는 일은 없다"로 `03-mental-model.md` 10행과 45행을 고친다. 06은 작성자가 선언한 쓰기로는 `injectTo`와 `&derived`만 들었고, 6항이 "확장 조작"으로 넓혔다.

**3.4 P1′의 괄호(지워짐).** 06은 "판별식 식별을 위한 `const`·`enum` 값 읽기는 형상 읽기에 든다"를 더하자고 했다. 1항이 이것을 정면으로 뒤집으므로 더하지 않는다. P1′에 무엇을 대신 적을지는 9라운드 종합이 정하지 않았다. 편집자 문안은 "폼은 `oneOf`·`anyOf`로 분기를 고르지 않는다. 분기가 선언한 필드는 조각으로 읽어 노드로 만들고, 어느 분기가 맞는지는 검증기만 판정한다"이며, 원리 원장을 다시 쓸 때(9절의 1) 소유자 확인을 받는다.

**3.7 편집자 단독 판정(바뀜).** 06의 4.15–4.21은 편집자 판정으로 남되 4.15가 좁아진다. 채움을 노드가 생길 때 한 번으로 바꾸면 자기 가드를 끄는 `default`의 순환이 런타임에는 사라지고 로드에만 남는다(실행). 여기에 4.24("노드 게이트 `&active`는 조각 게이트와 같은 장치이므로, 거짓이면 그 노드는 형상에 없고(기본은 원본을 둔다. 나감 정책 키를 켜면 나갈 때 비운다, 13라운드 답 2) 거짓에서 참이 되면 노드가 생긴다")가 더해진다. 4.24는 통합 결정의 귀결이라 도출이지만, 명세 본문이 적지 않았고 프로토타입의 첫 판이 반대로 동작했으므로 소유자가 읽고 받는다.

**3.8 4항의 읽기(새것).** "JSON Schema 층은 값을 조작하지 않는다"는 "조각의 켜짐·꺼짐은 있는 값을 바꾸거나 지우지 않는다"로 읽는다. 없음인 키를 채우는 것은 노드가 생기는 사건의 일부이며(소유자의 답 A), 채움의 원천은 표준 `default`일 수도 있다(소유자: "표준 스키마 문법이니"). 그래서 "JSON Schema 층이 값을 조작하지 않는다"와 "`default`가 채운다"는 모순이 아니다. 채우는 주체는 노드 생성 사건이고, `default`는 그 원천일 뿐이다.

**3.9 5항의 읽기(새것).** "제약을 최신화해 제공한다"의 예시는 유효성 조건이고, 주석·커스텀 키워드에 대해서는 "고민해볼 필요가 있다"고 하셨다. 그래서 유효성 키워드의 교차는 도출이고, 주석·커스텀 키의 승자는 정책이다(4.27, 5.3의 7, 5.4의 16·18, 5.3의 17).

### 4.22 채움은 노드가 생길 때 한 번, 원천은 `&default` > `default` (06의 4.2와 D-12를 대체)

- **질문.** 없음인 키는 언제, 무엇으로 채워지는가.
- **배경.** 06은 로드 계약(전체 교체 직후)과 전이 주입(조각이 켜진 직후)을 따로 두었고, 전이 주입은 최종 활성 집합 기준이었다(반례 E1). 소유자가 답 A(노드가 생길 때 채운다)와 원천 순서를 정했다.
- **결론.** 채움은 **노드가 생길 때** 한 번 일어난다. 생김은 노드 단위다. 직전 커밋의 형상에 없고 이번 정착의 최종 형상에 있는 노드만 생긴 것이고, 본체·게이트 없는 `allOf` 항목·이미 켜져 있던 다른 조각이 두고 있던 노드는 새 조각이 켜져도 생기지 않는다. 원천은 `&default`(표현식) > `default`(표준 키워드) > 없음이다. 값이 빠질 때마다 채우지 않으므로 `&unsetValue`로 지운 값은 다시 채워지지 않는다.
- **왜.** 소유자의 답 A와 "값이 빠질 때마다 채우지 않는다". 06의 조각 단위 규칙(꺼짐에서 켜짐이 된 조각의 없음인 자식을 채움)은 여러 조각이 공유한 노드와 본체 노드를 조각이 켜질 때마다 다시 채워 이 문장과 어긋난다(실행으로 확인, `reviews/raw-round9-verification.md` §2.4). 최종 활성 집합 기준(E1의 해법)은 그대로 필요하다.
- **바뀌는 것.** `adr/0007:33`(전이 행), `adr/0007:66·81`, `adr/0013:38·57`, `03-mental-model.md:45·60`, 06의 용어 "로드 계약"·"전이 주입"(06 37–38행). 프로토타입 v5의 첫 판을 고쳤다(7절).
- **남는 것.** 여러 조각이 같은 노드에 다른 `default`를 선언할 때의 승자는 4.27의 병합표에서 정한다(생성 순간에만 문제가 된다).

### 4.23 예약 층의 단계와 같은 대상 규칙 (Q1, 새것)

- **질문.** 작업 루프(표시 → 계산 → 파생 → 전이 → 커밋 → 통지 → 검증)에서 각 `&` 키가 어느 단계에 놓이며, 여러 자동 쓰기가 한 노드에 쓰려 할 때 어떻게 하는가.
- **결론(단계).**

| 키 | 단계 | 왜 |
| --- | --- | --- |
| `&active`(노드·조각 게이트), 조각 범위와 `&children`의 `active` | 계산, 호스트 바퀴 안에서 `if` 가드와 같은 평가 | 방출 제외가 가드의 입력을 바꾸므로 바퀴 밖에 둘 수 없다(`adr/0007:39·50`) |
| `&visible`, `&readOnly`, `&disabled`, 표준 `readOnly` | 계산의 끝, 최종 트리에서 한 번 | 값·형상·방출을 바꾸지 않고 가드를 읽지 않으므로 라운드가 필요 없다 |
| `&watch` | 청사진(스키마를 분석해 만든 정적 구조, ADR 0005)과 표시 단계 | 의존 경로 선언일 뿐이다 |
| `&derived`, `&injectTo`, `&unsetValue` | 파생 | 셋 다 원본에 쓰는 에지 규칙이다 |
| 채움(`&default` > `default`) | 전이(노드 생성) | 4.22 |
| `&resetInteraction` | 커밋 | 원본에 쓰지 않는다(`adr/0007:137`) |
| 나감의 비움(정책 키, 기본 꺼짐) | 전이(노드 나감, 최종 형상 기준) | 원장 §3, 13라운드 답 2 |

- **결론(같은 대상 규칙, 실행으로 확인).** 파생 단계는 라운드마다 원하는 쓰기를 모아 **대상 노드마다 하나만** 적용한다. 규칙마다 차례로 쓰면 순환이 없는 스키마(`a`가 `t`에 주입하고 `t`는 `b`에서 파생, 로드 `{a:1, b:1, t:'orig'}`)에서도 두 쓰기가 라운드마다 서로를 되돌려 로드만으로 25라운드 예산을 다 쓴다. 8라운드 프로토타입에서 재현했고, 대상별로 하나만 고르는 v5는 2라운드에 수렴한다. 순위 가운데 도출되는 것은 둘이다. 채움은 가장 낮다(없음일 때만이므로). `&unsetValue`는 채움을 이긴다(지운 값은 다시 채워지지 않는다). `&derived`·`&injectTo`·`&unsetValue` 사이의 순위는 소유자가 정했다(5.0의 8·9): `&unsetValue` > `&derived` > `&injectTo` > 채움이고 같은 종류끼리는 원천(선언) 노드의 문서 순서에서 나중이 이긴다(13라운드 답 4). 진 쓰기는 버린다.
- **에지 기준점 (5.0의 21로 닫힘).** `&unsetValue`와 `&resetInteraction`의 에지는 식의 불리언이 직전 커밋에서 거짓이고 지금 참인 것이다. 노드 생성에는 직전 값이 없으므로 거짓에서 참으로 본다. 로드(마운트·전체 교체·`reset`)에서도 같게 보는 것은 5.3의 6에서 `fire`를 고를 때와 같은 읽기다. 프로토타입 v5는 생성 때는 이 규칙대로 지우지만, 조건이 참인 채 `reset`하면 에지로 보지 않고 값을 남긴다(`spikes/round9/r9.mjs:165`). 소유자 답 21로 닫혔다: 로드(마운트·전체 교체·`reset`)에서는 로드된 값으로 평가해 참이면 지우고, 런타임에는 거짓→참 경계에서만 지우며 참→거짓은 아무 일도 하지 않는다.
- **예산.** 그대로. 호스트 바퀴의 상한은 노드 게이트도 뒤집힐 수 있으므로 "게이트 가진 조각 수 + 노드 게이트 수 + 1"이 된다. 비수렴 시 원본 B 커밋(06의 4.11)은 그대로다.
- **바뀌는 것.** `adr/0007:32`(파생 행에 `&unsetValue`와 대상별 해소), `:51`(상한), `03-mental-model.md:59`.

### 4.24 노드 게이트는 조각 게이트와 같은 장치다 (도출, 소유자 확인)

- **결론.** 노드 스키마의 `&active`가 거짓이면 그 노드는 형상에 없다(기본은 원본을 둔다, `getInactiveValues`로 읽는다. 나감 정책 키를 켜면 나갈 때 비운다, 13라운드 답 2). 로드 때 게이트가 거짓인 노드는 생기지 않아 채우지 않고, 거짓에서 참이 되면 노드가 생기므로 그때 없음이면 채운다. `&visible`의 전환은 생성이 아니다.
- **왜.** `&if`를 `&active`로 통합한 결정(한 장치, 두 범위)의 귀결이다. 조각 게이트와 노드 게이트가 다르게 동작하면 G4(하나의 개념에는 하나의 장치)에 걸린다. 프로토타입 v5의 첫 판은 반대로 동작했고(로드 때 꺼진 노드를 채우고, 켜질 때 채우지 않음) 고쳤다.

### 4.25 폼은 분기를 고르지 않는다 — 지워지는 장치와 컨벤션 (Q5, 새것)

- **결론.** 폼은 `oneOf`·`anyOf`로 분기를 고르지 않는다(예외: 작성자가 `&discriminator`를 명시한 union, 5.0의 22). 분기의 필드는 노드가 되고, 그 노드를 언제 보이고 방출할지는 (가) 분기 안의 `if/then/else` 조각, (나) 예약 층(`&active` 등, 조각 범위 제어, `&children`), (다) 둘 다 없으면 작성자 책임, 셋 가운데 하나다. 다음이 지워진다. 판별식 식별(ADR 0005 §4 E14), 값 가드, "판별 프로퍼티는 union 호스트가 소유"(E8), 상태 칸 `selection`, `setSelectedBranch`(06의 N2), 초기 분기 추론과 키 수 점수(06의 4.4 D-14), 동점(06의 5.5). 상태 칸은 원본과 `extras` 둘만 남는다. 세 도출이 모두 일치했고 프로토타입에 칸·API·점수가 없다.
- **조각 표(ADR 0002 표 39–40행을 대체).** 표의 "연언"은 모든 조각의 제약이 함께 적용되는 "그리고" 문맥, "선언"은 분기 가운데 하나만 맞으면 되는 "또는" 문맥이다. 4.27의 "전순서"는 스키마 안에서 조각이 놓인 순서(본체 < `allOf` 항목 < `if/then/else` < 분기, 같은 종류 안에서는 소스 순서)다.

| 구문 | 게이트 | 조각 | 문맥 |
| --- | --- | --- | --- |
| 최상위·`allOf` 항목·분기 안의 `if/then/else` | `if`(검증기 플러그인이 컴파일) | `then` / `else` | 연언(분기 안이면 그 분기의 문맥) |
| 게이트 없는 `properties`·`allOf` 항목 | 항상 참 | 블록 전체 | 연언 |
| `&active`를 가진 조각 객체 | `&active`(표현식) | 그 조각이 선언한 노드 집합 | 연언 |
| 게이트 없는 `oneOf`·`anyOf` 분기 | 항상 참(존재만) | 분기 전체 | 선언. 제약은 교차하지 않음(4.27) |

- **컨벤션(실측, 7절).** `oneOf`·`anyOf`의 분기에 `if`를 쓸 때는 **`else: false`와 `if`의 `required: [조건 프로퍼티]`가 함께 필수**다. `else: false`가 없으면 `if`가 거짓인 분기가 공허하게 통과해 분기로 세어진다(`oneOf`는 올바른 값을 거부하고 `anyOf`는 모든 값을 통과시킨다). `required`가 없으면 조건 프로퍼티가 없는 값에서 `else: false`를 붙여도 `{ x: 's' }`가 통과하고, 빈 값에서 모든 가드가 참이 되어 폼이 모든 분기를 켠다. `allOf` 항목과 최상위 `if/then`은 `else` 없이 되지만 어느 조건에도 맞지 않는 값을 거르지 못하며, 그 제약이 필요하면 작성자가 `enum`이나 `oneOf` + `else: false`를 쓴다. 이것은 검증기의 뜻이지 폼의 일이 아니다.
- **개발 모드 경고(모두 `if`의 내용을 읽지 않는다).** 소유자 답으로 확정: 같은 `oneOf`에서 게이트 가진 분기가 둘 이상 동시에 켜짐(5.0의 20)은 경고한다. 소유자가 12라운드에 확정: `oneOf`·`anyOf` 분기에 `if`는 있고 `else: false`가 없음. 같은 대상에 규칙이 둘 와도 경고하지 않는다(13라운드 답 4: 순위와 문서 순서로 푼다). 순수 분기끼리 같은 이름·다른 종류의 필드는 청사진 경고(노드 공유 충돌)로 드러난다(원장 §5). `if`에 `required`가 없음(5.0의 23)과 2항의 검사(5.0의 19)는 하지 않는다. 폼은 `if`의 내용에 관여하지 않는다.
- **바뀌는 것.** `adr/0002:17·39-40·107-108·112-133·126`, `adr/0005:67·71-90`, `03-mental-model.md:23·34·77-78·87`, `adr/0007:47·90`, `02-target-overview.md:51`, `05-before-after.md:18·26·191`. 오늘 코드의 `const`/`enum` 자동 감지(`getExpressionFromSchema.ts:35-51`)는 이주 안내 대상이다.

### 4.26 결합 규칙 — 13라운드에 "코어에 글로벌 없음, 상태 키는 그 노드에만"으로 확정 (Q3)

> **소유자 답 반영(5.0의 12·13, 13라운드 답 1).** 아래의 AND/OR 후보는 소유자가 받지 않았다. 5.0의 12(글로벌 > 로컬, 루트 스키마 키는 정의되면 `false`여도 덮음)는 13라운드에 개정되었다. 코어에는 글로벌 잠금이 없고, 루트 스키마 키는 루트 노드의 로컬 키이며, 표준 `readOnly`·`&` 식·`control.*`는 그 노드에만 걸린다. Form 속성 `readOnly`·`disabled`는 렌더 계층이 참일 때만 거는 전체 잠금이다(P5). 조상 상속은 없고, 자손을 거는 길은 부모의 `&children`과 켜진 조각의 `control`뿐이다. 오늘 루트 키 다섯(`readOnly`·`disabled`·`active`·`visible`·`pristine`)의 특수 처리는 이주 항목이다. 로컬 선언끼리는 잠금 OR, 표시 AND다(편집자 판정, 원장 §7). 아래 본문은 답하기 전의 도출 기록이다.

- **결론.** 한 노드에 여러 층의 상태 제어가 겹칠 때 `active`·`visible`은 AND(모두 허용해야 켜짐), `readOnly`·`disabled`는 OR(하나라도 잠그면 잠김)이다. 결합이 교환·결합 법칙을 따르므로 층 사이의 우선순위가 필요 없다.
  - `active = 존재(형상) ∧ 자기 ∧ 조상들 ∧ 조상의 &children 항목 ∧ 켜진 조각의 범위 제어`
  - `readOnly = Form 속성 ∨ 표준 readOnly ∨ 노드 자신의 &readOnly ∨ 조상들 ∨ &children 항목 ∨ 켜진 조각의 범위 제어`
- **왜.** 존재는 활성 조각의 합집합이고(`adr/0002:52`) 제약은 연언 조각끼리 교차한다(`adr/0002:53`). 상태 키도 제한이므로 같은 원리다. 8항의 "명확한 동작 위계"를 순서 규칙 없이 만족한다. 프로토타입에서 AND/OR와 "가장 가까운 선언이 이김"은 정반대 결과를 냈다.
- **택일과 결합.** `&readOnly`와 `control.readOnly`는 한 선언의 두 철자이므로 `control`이 이긴다(오늘 `computed`가 이기던 규칙). 표준 `readOnly`와 `&readOnly`는 다른 층의 두 선언이므로 OR다. Form 속성은 오늘대로 OR다.
- **조각 객체의 키.** 조각 객체의 `&active`는 게이트다. 거짓이면 그 조각의 선언과 제약이 빠지지만 다른 켜진 조각이 선언한 같은 노드는 존재한다. 조각 객체의 `&visible`·`&readOnly`·`&disabled`는 그 조각이 선언한 노드 집합에 거는 제한이며, 조각이 켜진 동안만 결합에 들어간다.
- **남는 것.** 루트 스키마의 `readOnly: false`가 잠금을 푸는 오늘의 동작(루트 키가 노드의 식을 덮음, `checkComputedOptionFactory.ts:22-26`)을 버릴지, 중간 객체의 잠금이 자손에 내려갈지는 10항 "기존과 같이"와 닿아 정책이다(5.1의 12, 5.4의 13). `&children`의 값 형태는 5.3의 14.

### 4.30 한 정착 안에서 한 규칙의 에지는 한 번만 소비된다 (편집자 판정, 실행, 소유자 확인)

- **배경.** 10라운드에서 드러났다. `t`에 `&derived`(`dep × 10`)와 `&unsetValue: t > 50`을 함께 두고 `dep`를 1에서 6으로 바꾸면, 프로토타입 v5에서는 같은 대상 규칙의 어느 순위에서도 의도대로 끝나지 않는다. `&unsetValue`가 이기면 파생(60)과 지움이 번갈아 돌아 25라운드 예산 초과가 나고 원본 B 커밋이 옛 값 `t = 10`을 남긴다. 지면 지움이 조용히 사라진다. 원인은 v5가 에지를 직전 커밋과 비교하므로 한 정착 안에서 이미 적용한 에지가 라운드마다 다시 발화하는 것이다(교차 검증 재현).
- **결론.** 한 규칙은 원천 값의 한 번의 변화에 대해 한 정착 안에서 한 번만 쓴다. 같은 정착의 다음 라운드에서 같은 변화로 다시 쓰지 않는다. 곧 파생 단계에서 원천 값 변화로 생긴 한 규칙의 에지는 그 정착 안에서 한 번만 소비된다. 실험 모델 v6가 이 규칙을 쓰며, 같은 장면이 네 조합 모두 3라운드에 안정되고 `t`가 지워진 채 끝난다.
- **왜.** 4.3의 에지 기준점(직전 커밋)은 정착 사이의 규칙이지 정착 안의 재발화를 허락하는 문장이 아니다. G5·G6은 같은 사건으로 같은 규칙을 반복 적용하는 것을 지지하지 않는다. 원본 B 커밋이 옛 값을 남기는 것은 값을 고치지 않는다는 점에는 맞지만 작성자의 의도(지움)를 잃는다.
- **바뀌는 것.** 4.23의 같은 대상 규칙에 이 문장을 더한다. 11.2의 "같은 대상 규칙의 세부"(진 쓰기의 운명, 에지 소비)의 한 답이다. 프로토타입 v5는 슬라이스 3 전에 이 규칙으로 고친다.
- **닫힘.** 진 쓰기는 버리고 그 에지도 소비한다(실험의 `LOSER_FATE`·`EDGE_CONSUMED_ON_LOSS`). 소유자 답 9(`&derived`가 이김)에서 도출된다: 진 규칙의 에지를 소비하지 않으면 다음 라운드에 진 규칙이 이겨 순위가 무의미해진다(원장 §4). 두 스위치를 함께 봐야 하는 이유가 있다. 버리되 소비하지 않으면 진 쓰기가 다음 라운드에 다시 시도된다. 실험에서 두 스위치의 값은 예산 초과(48)와 조용한 손실(0)에서 같았다. 선언 의존은 달랐다. 진 쓰기를 버리면 8건, 다시 넣으면 16건이었다(`spikes/round10/REPORT.txt` 57–69행).

### 6.1 소유자가 동의한 이름 (세 곳의 추천 원문: `reviews/raw-round9-naming-{antigravity,codex,local}.md`)

| 대상 | 이름 | 비고 |
| --- | --- | --- |
| `computed`를 대신할 컨테이너 | `control` | 세 곳 일치. `control.active`, `control.injectTo`. `&키`와 `control.키`는 같은 것의 두 철자(9항). 같은 노드에 둘 다 있으면 `control`이 이긴다(오늘 `computed`가 이기던 규칙) |
| 값 지우기 | `&unsetValue` | 새 키. 거짓에서 참으로의 전이에서 값을 뺀다. 입력은 남는다. 동사와 목적어 꼴이라 참이 되는 순간의 한 번 동작으로 읽히고, 같은 동사 꼴인 `injectTo`를 따른다(`raw-round9-naming-local.md:14`). `When`을 붙인 두 추천(antigravity의 `&clearWhen`, codex의 `&clearValueWhen`) 대신 소유자가 `&clearValue`에 동의했고, 12라운드에 `&unsetValue`로 이름을 바꿨다(`setValue`와 짝) |
| `dirty`·`touched` 초기화 | `&resetInteraction`(옛 `&pristine`) | 5.0의 5 |
| 로드 시 예약 층의 자동 쓰기 억제 | `SetValueOption.DisableAutomaticWrites` / `SetValueOption.EnableAutomaticWrites`, Form 속성 `disableAutomaticWrites` | 06의 `DisableSchemaDefaults`를 대체. 오늘 내부 플래그 `Automatic`("폼이 스스로 쓴 값")의 어휘. 범위는 그 호출(로드와 `Merge`)이 일으킨 예약 층의 쓰기 전부(채움, `&derived`, `&injectTo`, `&unsetValue`, 나감의 비움)이고 로드 값 자체는 막지 않는다. `&active`의 방출 제외는 쓰기가 아니라 투영이므로 범위 밖이고, 정책 키를 켠 노드의 나감 비움은 범위 안이다. 둘 다 없으면 Form 속성을 따르고 둘 다 주면 억제가 이긴다 |
| 조각 게이트 | `&active`로 통합, `&if` 은퇴 | 노드 스키마에 쓰면 노드 게이트, 조각 객체에 쓰면 조각 게이트. JSON의 `if`가 이미 조각 게이트이므로 `&if`는 같은 게이트의 셋째 철자가 되어 G4에 걸린다. 이주 항목 |
| 없음인 키 채우기 | `&default` | 세 곳 일치. "`&키`는 표준 키워드의 표현식 판"이라는 규칙 그대로. `&defaultValue`는 Form 속성과 층위가 섞여 제외 |
| 다른 노드 쓰기 | `&injectTo` | 예약 층에 편입 |
| 자식 집합 제어 | 조각 범위 제어와 `&children` 블록 둘 다 | 소유자 답(5.0의 14·15): `'&children': [{ targets: ['name', 'email'], control: { readOnly: '../locked', unsetValue: '...' } }]`. `targets`와 `control`을 나누고, `control`에는 상태 키뿐 아니라 값 키(`unsetValue`, `default`, `resetInteraction`)도 허용한다 |
| `dirty`·`touched` 초기화의 새 이름 | `&resetInteraction` | 소유자 동의(5.0의 5). `&pristine`을 대체. 이주 항목 |
| 명시 판별 | `&discriminator` | 소유자 동의(5.0의 22). union 호스트에 키 이름을 적으면 청사진이 분기별 `&active`로 바꾼다 |

읽기 예:

```ts
{
  '&children': [{ targets: ['name', 'email'], control: { readOnly: '../locked' } }], // 5.0의 14
  properties: {
    discount: {
      '&active': "../kind === 'vip'",
      '&default': '../baseRate',
      '&unsetValue': '../resetDiscount === true',
      '&injectTo': (value) => ({ '../summary': value }),
    },
  },
  oneOf: [{ '&active': "../kind === 'A'", properties: {} }],

<Form disableAutomaticWrites />
```

문법이 세 부류로 나뉘고 이 구분이 곧 예측 규칙이다. 형용사(`active`, `visible`, `readOnly`, `disabled`)는 참인 동안 유지되는 상태, 명사(`default`, `derived`)는 값의 출처, 동사(`unsetValue`, `injectTo`)는 참이 되는 순간의 동작이다.

## 7. 실측, 프로토타입, 실험

### 7.1 실측: `oneOf`·`anyOf` 안의 `if` (ajv 8.17.1, draft-07과 2020-12 판정 동일)

파일: `spikes/round9/oneof-if.mjs`, `oneof-if-output.txt`, `REPORT.txt`. 각 분기의 `if`는 `{ properties: { kind: { const } }, required: ['kind'] }`다.

| 배치 | 올바른 값 `{kind:'a', x:'s'}` | 누락 값 `{kind:'a'}` | 어느 조건에도 맞지 않는 값 `{kind:'c'}` | 조건 프로퍼티 없음 `{x:'s'}` |
| --- | --- | --- | --- | --- |
| `oneOf` 분기에 `if/then`만 | 거부 | 통과 | 거부 | 거부 |
| `oneOf` 분기에 `if/then` + `else: false` | 통과 | 거부 | 거부 | 거부 |
| `anyOf` 분기에 `if/then`만 | 통과 | 통과 | 통과 | 통과 |
| `anyOf` 분기에 `if/then` + `else: false` | 통과 | 거부 | 거부 | 거부 |
| `allOf` 항목에 `if/then`만 | 통과 | 거부 | 통과 | 통과 |
| 최상위 `if/then` 하나 | 통과 | 거부 | 통과 | 통과 |
| 오늘 방식(`const` 판별식) | 통과 | 거부 | 거부 | 거부 |

`if`에서 `required`를 빼면 `else: false`를 붙인 `oneOf`·`anyOf`가 `{x:'s'}`를 통과시키고, 빈 값에서 가드 단독 판정이 모두 참이 된다(검증 §2.3). 그래서 4.25의 컨벤션이 "`else: false`와 `required` 함께"다.

### 7.2 프로토타입 v5 (`spikes/round9/proto/loop-v5.mjs`)

8라운드 `loop-v4e.mjs`에서 59개 정확 치환(검증 뒤 수정 포함)으로 파생했고 재생성이 바이트 단위로 같다. 상태 칸은 원본과 `extras`뿐이며, 조각은 `if`(검증기 스텁) 또는 `&active`로 켜지고, 게이트 없는 조각은 무조건이다. 재실행은 `spikes/round9/`에서 `node regress/run.mjs`다.

프로토타입 보고서의 사실(`spikes/round9/REPORT-proto.txt`). 교차 검증(`reviews/raw-round9-verification.md` §2)은 회귀·프로브의 합계 단언을 재실행해 재현했고, 채움 단위와 같은 대상 충돌은 탐침으로 하나씩 재현했다:

- 이식한 8라운드 회귀 63개 단언이 두 모드에서 모두 통과했다. v4e 자신의 기존 실패 셋 가운데 A4c와 A4-cap은 "같은 값을 다시 써도 에지를 발화하지 않는다"는 규칙으로, A4b는 "최종 형상에 없는 노드의 중간 채움은 남기지 않는다"는 규칙으로 기대가 바뀌어 통과한다(`regress/CHANGES.txt`).
- Q8 프로브 108개 단언과 경계 26개가 통과했다.
- 로드에서는 `&default`가 `default`를 이겼고, 나중에 켜진 조각의 새 노드도 채워졌다.
- `&unsetValue`는 값을 지우고 입력을 남겼으며, 그 뒤 다시 채워지지 않았다. 자기 삭제로 조건이 거짓이 되어도 삭제를 철회하지 않는다.
- `else: false`가 없는 분기 둘에서 개발 모드 경고 둘이 났다. 게이트 없는 순수 `oneOf`·`anyOf`는 두 분기를 모두 켰다.
- 자식 집합 결합에서 AND/OR와 "가장 가까운 선언이 이김"은 정반대 결과를 냈다.
- `&derived`와 `&injectTo`의 같은 대상 충돌은 대상별로 하나만 적용해 2라운드에 수렴했다. 순위는 스위치다.
- `disableAutomaticWrites`는 채움·`&derived`·`&injectTo`·`&unsetValue`를 모두 막고 로드 값은 그대로 두었으며, 그 뒤 사용자 입력에서는 자동 쓰기가 다시 일어났다. 호출 단위 지정이 Form 속성을 덮었다.
- 비수렴 `&derived`·`&injectTo` 쌍은 라운드 상한 5·6·25 모두에서 예산 초과이고, 원본 B 커밋이면 `{a:0, b:0}`, 마지막 라운드 커밋이면 상한 직전의 값(상한 25에서 `{a:24, b:24}`, 상한 5에서 `{a:4, b:4}`)이다.

교차 검증이 첫 판에서 명세와 어긋나는 곳 셋을 찾았고 같은 codex 세션에서 고쳤다. 채움 단위(본체에만 노드 단위였고 공유 노드와 게이트 없는 `allOf` 항목은 조각 단위로 다시 채움), 노드 게이트(로드 때 꺼진 노드를 채우고 켜질 때 채우지 않음), 게이트 없는 분기의 공유 노드에 첫 선언 스키마를 힌트로 남김. 고치는 과정에서 넷째 빈틈이 재현으로 드러났다(`{seed:1, on:1}`, `REPORT-proto.txt` 325행). 중간 라운드에 채운 값이 뒤 라운드에서 형상에서 빠진 노드의 원본에 남는 문제로, "생김"을 정착이 수렴한 뒤의 최종 형상으로 판정하고 최종 형상에 없는 노드의 채움 후보는 철회하도록 고쳤다(06 4.2의 "중간 라운드의 주입은 커밋 전에 버린다"의 실행 확인). 고친 뒤의 결과는 `spikes/round9/REPORT-proto.txt`의 "5. 검증 뒤 수정" 절과 `spikes/round9/r9b-output.txt`(단언 52개, 탐침 13개, 실패 0)에 있다.

고친 뒤 달라진 회귀 기대는 "이미 있던 노드는 다시 채우지 않는다", "최종 형상에 없는 노드의 중간 채움은 남기지 않는다", "게이트가 거짓인 노드는 생기지 않는다(4.24)"에서 온다. 8라운드 회귀 이식의 바뀐 요약은 17행이다. 7라운드 사례 X16(자기 주입으로 자기 조각을 끄는 스키마)은 에지 모드의 두 구성에서, 이전에 중간 원본 보존으로 `stable`이던 것이 예산 초과가 된다. 레벨 모드는 `t='from-undefined'`로 2라운드에 수렴한다. 에지 모드의 결과는 4.15(자기 가드를 끄는 자동 쓰기는 예산 초과)와 같은 판정이다.

### 11.3 위험 (다시 짜게 만들 수 있는 곳)

1. **생성기가 만든 스키마.** pydantic·zod·OpenAPI의 판별 union은 `const` 태그만 두고 `if`나 `else: false`를 두지 않는다. 이 모델에서는 그런 스키마의 모든 분기가 동시에 켜지고, 분기끼리 같은 이름·다른 종류(`value: string`과 `value: number`)를 두면 노드 공유 규칙의 충돌이 된다. 소유자의 앞선 발언 "분기를 수동으로 고르는 기능이 아예 없는 건 애매하다. 서버에서는 oneOf anyOf를 실제로 많이 쓴다"(`adr/0002:141`)와 닿는다. 이 발언은 명세 §2의 읽기 1("oneOf anyOf는 jsonSchema의 분기 선언문이 아니라, 진짜 검증조건")이 대체한 것으로 읽되, 그 대체를 소유자가 확인해야 한다(5.1의 22가 그 자리다). 현장 요구로 판별식을 코어에 되돌리면 상태 칸과 루프를 다시 짜야 하므로, 되돌리더라도 청사진 단계의 변환(예약 층 선언 → 분기별 `&active`)으로 되돌릴 수 있는 길을 먼저 확인한다(11.1의 3, 5.1의 22).
2. **`else: false`와 `required` 컨벤션.** 실측 일곱 배치 가운데 둘(`else: false`가 없는 `oneOf`·`anyOf`)은 틀리게 판정하고, 둘(`allOf` 항목과 최상위 `if/then`)은 어느 조건에도 맞지 않는 값을 거르지 못한다. 틀리기 쉬운 규칙이며, 오늘 `&if`나 `const` 판별식을 쓰는 스키마는 모두 다시 써야 한다. 개발 모드 경고(5.4의 19, 5.2의 20)와 ADR 0010이 완화책이다.
3. **컴파일 가드의 비용.** 컨벤션이 분기마다 `if`를 요구해 가드 수가 늘고, 바퀴 상한에 노드 게이트 수가 더해진다. 인터프리터형 검증기는 약 70배 느리다. 예산 수치가 있어야 판정할 수 있다.
4. **로컬 결합과 글로벌 제거.** 루트 스키마 키 다섯의 특수 처리는 사라진다. 루트 `readOnly: false`가 잠금을 풀던 동작과, 루트 `active: true`가 모든 `&active: false`를 무력화하던 동작이 여기에 든다. "표준 `readOnly`가 `&readOnly`를 이김"도 사라진다. 폼 전체 잠금은 Form 속성(렌더 계층)으로 옮긴다. 소비자에게 보이지만 계산 단계 끝의 함수 하나에 갇혀 다시 짤 위험은 낮다.
5. **React 바인딩의 검토 깊이.** ADR 0011은 제안이고, 모든 분기가 켜진 채 그려지는 화면을 검토한 라운드가 없다. 실제 브라우저의 IME 확인도 남았다.

## 12. 10라운드 — 남은 정책의 추정 결과 (소유자 지시에 따른 것)

소유자가 "원칙에서 추정 가능한 것과 정말 내가 결정해야 하는 것을 나누고, 추정 가능한 것은 추정 라운드와 검증을 돌려라. 그래도 결정이 안 나면 내가 직접 보겠다"고 지시했다. 명세는 `reviews/round-10-spec.md`, 종합은 `reviews/round-10-derivation.md`다.

- **방법.** 스물셋 가운데 소유자만 정할 것 셋(22, 12, 1)과 확인만 받을 것(10)을 빼고, 열아홉을 독립 추정 셋(로컬 opus, cennad claude, cennad antigravity)에 넘겼다. 실험(cennad codex)은 8·9·21의 후보를 스위치 다섯·48조합·결과 2,904건으로 돌렸다. 교차 검증이 인용 약 243건을 대조하고(날조 없음, 확인되지 않은 인용 열 개는 줄 어긋남 넷·부적합 다섯·파일 이름 오류 하나, antigravity의 ADR 파일 이름 오기 넷), 로컬의 실행 주장 둘을 재현하고, 실험을 다시 돌려 산출물이 바이트 단위로 같음을 확인했다.
- **채택 규칙.** 셋이 같은 답에 같은 표기 "추정"으로 닿고 인용이 확인된 항목만 추정 완료. 선호와 다수결은 추정이 아니다.
- **결과.** 추정 완료 하나(3, 4.29로 옮김). 검증자 판정은 추정이나 셋이 같은 표기에 닿지 못한 것 넷(11, 15, 20, 2. 5.2에 확인 후보로 둠). 셋이 같은 방향으로 기운 것 넷(6, 7, 14, 17. 5.3에 둠). 수렴하지 않은 것 열(5.4). 실험은 8·9·21의 후보가 예산·손실·순서 의존에서 갈리지 않음을 보였고, "선언 순서" 후보만 선언 의존을 새로 만든다.
- **새로 드러난 것.** 정착 안의 에지 소비 규칙(4.30). 07의 정정 셋(5.3의 7 예시, 4.27의 오늘 코드 서술, 9절 이주 항목 하나).
- **남는 것.** 5절의 스물둘(3은 닫힘)을 소유자가 답한다. 5.2의 다섯은 확인만, 5.3의 넷은 권고에 동의하시면 "예" 한 마디로 끝나고, 5.4의 열은 권고를 적어 두었다.

## 13. 11라운드 — 소유자 답의 정합성 검증 (소유자 지시에 따른 것)

소유자의 요청("나의 응답을 다시 정합성 검증을 돌려. 나는 나 자신조차 정합성을 깨는걸 원치 않는다")으로 답 26개를 검증자(claude, 코드까지 대조)와 antigravity(교차검증)에게 독립으로 맡겼다. 둘 다 조건부 통과다. 판정과 반영은 `reviews/round-11-owner-answers-check.md`, 원문은 `reviews/raw-round11-owner-answers-{claude,antigravity}.md`다.
