# 목표 구조 개관

상태: 제안. 각 부분의 결정과 상태는 해당 ADR에 있다. 이 문서는 부분들이 어떻게 맞물리는지만 보여 준다.

## 1. 한 장 그림

```
                       ┌──────────────── 검증기 플러그인 (교체 가능) ────────────────┐
                       │ compile(schema)      → 전체 검증, 에러 수집 (비동기 허용)   │
                       │ compileGuard(schema) → 동기 boolean, 첫 실패에서 중단       │
                       └───────▲─────────────────────────────▲───────────────────────┘
                               │ 가드 평가 (방출 값을 본다)    │ 작성된 스키마 + 방출 값 (변형 없음)
 작성된 스키마 ─┬─────────────────────────────────────────────┘
 (불변)         │
                ▼
        ① 분석 (순수 함수, 1회)          스키마의 구조만 읽는다. 의미는 평가하지 않는다.
        스키마 → 청사진                  ObjectBlueprint { base, fragments[] }
                │                        Fragment { id, guard, declares, constrains, children }
                ▼
        ② 노드 트리 = 상태               별도의 데이터 모델이 없다. React Fiber처럼 노드가 상태를 든다.
           자식 없는 노드: 원본(편집 상태)을 저장한다 — 터미널 타입, 터미널 전략의 object·array
           자식 있는 노드: 자식들로부터 계산한 방출 값을 메모한다
           루트의 메모 = 커밋된 스냅숏. 각 노드의 메모는 그 스냅숏의 부분과 같은 참조다.
                │
                ▼
        ③ 작업 루프 (동기 · 단방향 · 고정 순서)
           표시   쓰기를 받은 노드 → 조상으로 dirty
           계산   begin ↓ 가드·활성 집합   complete ↑ 방출 값 메모   (dirty 없는 서브트리는 건너뛴다)
                  방출 값이 바뀌면 패스를 되풀이. 상한을 넘으면 계산을 버리고 동기로 throw
           커밋   메모 확정, 바뀐 노드를 트리 순서로 수집
                │
 ─ ─ ─ ─ ─ ─ ─ ─│─ ─ ─ ─ ─ ─ ─ ─ ─ ─  여기까지 동기, 아래는 경계 ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
                ▼
        ④ 통지     루트 디스패처가 위 → 아래로 1회 방출 (subscribe · revision · 시그널링)
        ⑤ 검증     validator(작성된 스키마, 방출 값). 판정은 값의 revision에 묶인다.
                   에러를 노드로 분배하고, 주인 없는 에러는 폼 수준으로
                │
                ▼
        ⑥ React 바인딩  useSyncExternalStore(node.revision(mask))

   읽기(node.value, node.visible, node.jsonSchema)는 어디서든 메모된 참조의 필드 접근이다. 계산하지 않는다.
```

## 2. 세 층

| 층 | 무엇이 정하는가 | 누구의 어휘인가 | 검증에 미치는 영향 |
| -- | --------------- | --------------- | ------------------ |
| L0 유효성 | `validator(작성된 스키마, 방출 값)` | 표준 JSON Schema | 이것이 판정 그 자체다 |
| L1 형상 | 활성 조각의 집합 → 노드의 존재와 유효 스키마 | 표준 JSON Schema (`if`/`then`/`else`, `allOf`, 판별식 `oneOf`/`anyOf`) + 폼 상태(비판별 분기의 수동 선택) | 방출 값을 바꿀 수 있다(꺼진 조각의 제외). 판정 함수는 바꾸지 못한다 |
| L2 표현 | `&` 키워드 (`&visible`, `&readOnly`, `&disabled`, `&derived`, `&active`, …) | FE 전용 | 위와 같다 |

L1과 L2가 무엇을 하든 L0의 판정 함수에는 닿지 못한다. 계약은 기능별 규율이 아니라 이 구조로 보장된다 (ADR 0001).

## 3. 부분과 ADR

| 부분 | 핵심 | ADR |
| ---- | ---- | --- |
| 검증기 입력 | 작성된 스키마와 방출 값만 본다. 폼이 파생한 스키마는 폼 전용이다 | 0001 |
| 조건부 모델 | `if`/`then`/`else`·`allOf`·판별식 `oneOf`/`anyOf`·비판별 분기를 "가드 → 조각" 하나로 | 0002 |
| FE 전용 어휘 | `&` 접두 하나로 통일. 기본은 제거하지 않는다 — 검증기가 미지 키워드를 무시한다 | 0003 |
| 검증기 플러그인 | 내장하지 않는다. 동기 `compileGuard`를 계약에 더한다 | 0004 |
| 분석 단계 | 스키마 → 청사진. 같은 이름 필드의 노드 공유 규칙 | 0005 |
| 값 소유 | 노드 트리가 곧 상태. 저장은 자식 없는 노드에만, 나머지는 메모된 계산 | 0006 |
| 라이프사이클 | 표시 → 계산(begin↓ · complete↑) → 커밋. 순환은 패스 상한으로 드러낸다 | 0007 |
| 이벤트 | 통지 전용. 루트 단일 디스패처가 위 → 아래로 배달한다 | 0008 |
| 성능 | 기존 구현을 기준선으로 한 예산과 벤치 시나리오 | 0009 |
| union UX | 판별식 자동 선택, 비판별 수동 선택 | 0010 (작성 대기) |
| branch 노드 구성 | object와 array는 자식 집합의 출처만 다르다. 노드를 필요할 때 만들 수 있는지가 핵심 미결 | 0011 (제안 초안) |

## 4. 현재 구조와의 대응

| 현재 (관찰, `01-current-structure.md`) | 목표 |
| -------------------------------------- | ---- |
| D1 스키마를 변형해 마커를 심는다 | 작성된 스키마는 불변. 분석 결과는 별도 구조(청사진)에 둔다 |
| D2 모든 분기 자식 사전 생성 | 유지. 조각은 스키마에서 정적으로 열거된다 |
| D4 값을 레벨마다 사본으로 든다 | 저장은 자식 없는 노드에만. 위쪽은 같은 참조를 공유하는 메모 |
| D5 값 전파와 알림 전파가 다른 그래프 | 값은 작업 루프가, 알림은 루트 디스패처가 맡는다. 역할이 겹치지 않는다 |
| D6 10비트 `SetValueOption` | 미결 (`open-questions.md` Q6). 작업 루프에서 대부분의 비트는 존재 이유를 잃는다 |
| D7 루트 단독 검증 + enhancer | 루트 단독 검증은 유지. enhancer는 제거 |
| D8 composition = 값 필터 + 마커 | 조각의 활성 집합. 꺼진 조각은 방출에서 빠지고 노드의 원본은 남는다. 마커 없음 |
| D9 `type` 유무로 판별식 구분 | 선언 위치 규칙으로 대체 (ADR 0005) |
| D10 `new Function` 표현식 | L2(`&`) 전용으로 남는다. L1의 조건은 검증기가 평가한다 |
| 7개 조건부 장치, 평가기 4개 | 가드/조각 하나 + `&` 표현식 하나 |
| `oneOf`와 `active`가 서로 다른 라이프사이클 | 같은 begin/complete |

## 5. 검증 전략

기존 테스트는 동작이 달라져 회귀 오라클로 쓸 수 없다. 새 불변식이 오라클이 된다.

1. **차등 테스트.** 임의의 (스키마, 상호작용 시퀀스)에 대해 `form.validate()`의 판정 ≡ 독립 검증기(작성된 스키마, `form.getValue()`)의 판정. 이슈 #342 §2의 표가 시드다. 독립 검증기는 폼이 쓰는 플러그인과 **다른 구현**이어야 하고, 값은 JSON으로 직렬화한 뒤에 넣는다 — 같은 플러그인에 같은 메모리 값을 넣으면 동어반복이다(`reviews/round-1.md` §7-8).
2. **분석 단계 테이블 테스트.** 스키마 → 청사진은 순수 함수다. 조각 열거, 중첩, 타입 충돌 throw.
3. **작업 루프 테스트.** 쓰기 → 커밋된 상태. 표시·계산·커밋이 동기이므로 타이머 flush 없이 단언한다.
4. **`renderForm` 시나리오.** 하니스(`src/__tests__/renderForm.tsx`)는 API 수준이라 재사용한다. 기존 시나리오의 기대값은 버리고 상황 목록(null 분기 위치, 배열 제거·추가, 활성 0→1→0, 복수 활성, 배열 항목 재인덱싱)은 자산으로 옮긴다. 최종 스펙 동작은 렌더 시나리오로 단언한다는 패키지 규칙은 그대로다.
5. **성능.** 기존 구현의 `bench:baseline` 결과가 기준선이다 (ADR 0009).

이슈 #342 §4의 교훈도 옮긴다: 숨은 키 누출 검사를 `JSON.stringify(...).not.toContain(KEY)`로 하면 제어 문자가 이스케이프되어 절대 실패하지 않는다. 목표 구조에는 숨은 키가 없으므로 이 검사 자체가 필요 없어지지만, "절대 실패하지 않는 단언"을 경계하는 원칙은 남긴다.
