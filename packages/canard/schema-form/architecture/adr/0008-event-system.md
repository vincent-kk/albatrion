# ADR 0008 — 이벤트 시스템 개편: 통지 전용 척추

상태: 제안. 개편을 범위에 넣는 것은 소유자가 허용했다. 구체안은 성능 현황 조사(ADR 0009) 뒤에 다듬는다.

## 변경 이력

- 2026-09-22 — 2라운드(`reviews/round-2.md`)의 S10을 "확인된 결함" 절에 적었다.
- 2026-09-22 — 미결이던 통지 시점을 **동기**로 닫았다. 근거는 제어 컴포넌트의 캐럿 보존(`04-inherited-constraints.md` T-1). 소유자의 지적: "루트로 옮긴다"만으로는 수렴·배치·전파 통제가 설명되지 않는다 — 수렴은 ADR 0007의 파생 단계, 배치는 `batch()`, 전파는 dirty 목록과 단일 순회로 답하고, 이벤트 시스템 전체를 4라운드 공격 대상에 올렸다(`HANDOFF.md` §3).

## 맥락

소유자의 설명:

- `EventCascade`를 쓴 이유는 `setValue`나 전체 값 변경을 배치 처리하기 위해서였는데 충분한 효과를 보지 못했다. 이벤트를 편하게 발행하는 정도의 장점이 있었고, 꼭 필요한 경우의 배치 이벤트와 동기성 이벤트를 혼용하고 있다.
- 그러나 노드 간 pub-sub, event signaling, batch update는 node tree의 축이자 대규모 폼 고속 동작의 척추이므로 되도록 유지하고 싶다(G7).

관찰(`01-current-structure.md` §5): `UpdateValue`만 동기 발행이고 나머지는 마이크로태스크 배치다. 재진입 디스패치로 인과가 뒤집히고, 한 번의 쓰기가 두 번 배달되며, 배치 머지는 타입별 last-write-wins라 중간 payload가 사라진다.

배치가 충분한 효과를 내지 못한 이유에 대한 해석: 지금은 **통지만** 배치되고 **상태 계산은 쓰기마다** 반복된다.

## 결정

이벤트 시스템을 **통지 전용**으로 다시 정의한다. 역할은 셋이다.

1. **상태 통지** — 작업 루프의 커밋 뒤에 1회 방출한다(ADR 0007). 구독자는 언제나 정착된 상태만 본다.
2. **`revision(mask)` 원장** — 리스너 유무와 무관한 단조 카운터. `useSyncExternalStore` 스냅숏으로 쓰는 현재 방식(`hooks/useSchemaNodeTracker.ts:36-49`)은 유지한다. React의 render→commit 갭을 메우는 검증된 장치다.
3. **명령 시그널** — `RequestFocus`/`RequestSelect`/`RequestRefresh`처럼 상태가 아니라 렌더 계층에 대한 요청인 것. 상태 통지와 성격이 다르므로 구분한다.

유지: `node.subscribe()`, 이벤트 타입 비트마스크, `revision`, 비제어 입력 계약(입력이 값을 다시 읽게 하는 것은 `RequestRefresh` 하나).

바뀜: 내부 상태 전이가 이벤트를 타지 않는다. 배치의 단위가 "통지"에서 "쓰기 묶음 → 정착 1회 → 통지 1회"로 올라간다. 동기 발행과 배치 발행의 혼용이 사라진다 — 상태 통지는 모두 같은 시점에 나간다.

### 디스패처의 위치 — 루트 단일 디스패처

상태: 제안. 소유자가 발의했다 — "event cascade가 각 노드별로 있는데, 이걸 root 노드에만 두고 각 노드들의 이벤트를 개별 배치하는 방법은 어떤지. 노드 깊이별 이벤트 반영 순서가 꼬여서 고생했던 기억이 있다." 적대적 검토에서 조건부로 통과했다(아래).

관찰: 현재는 노드마다 `EventCascadeManager`가 있고 노드마다 마이크로태스크를 따로 예약한다. 마이크로태스크는 예약된 순서대로 실행되므로 노드 간 배달 순서는 트리의 순서가 아니라 **그 틱에 각 노드가 처음 publish한 순서**다. 노드 간 순서 보장이 없고, 배달 도중의 publish는 큐 뒤에 붙어 깊이별 순서가 서로 끼어들며, 즉시 발행은 리스너 루프 안의 중첩 디스패치가 되어 결과가 원인보다 먼저 배달된다(`01-current-structure.md` §5).

제안: 디스패처를 루트에 하나만 둔다.

- 노드에는 "이번 정착에서 켜진 이벤트 타입"의 비트마스크, 타입별 payload, `revision` 원장만 남는다. 스케줄링은 하지 않는다.
- 루트가 이번 정착에서 바뀐 노드의 집합을 들고 **정해진 순서**로 배달한다. 후보는 문서 순서의 위 → 아래다. 작업 루프의 begin이 이미 위에서 아래로 트리를 걸으므로(ADR 0007) 그 순회에서 수집하면 정렬 없이 순서가 나온다.
- **재진입은 다음 파동으로 미룬다.** 리스너가 배달 도중에 쓰기를 하면 그 쓰기의 통지는 현재 파동이 끝난 뒤에 나간다. 같은 파동의 리스너는 모두 같은 스냅숏을 본다. 중첩 디스패치가 없으므로 인과가 뒤집히지 않는다. 노드별 디스패처로는 표현할 수 없는 성질이다.
- 대량 쓰기로 노드 1,000개가 바뀌어도 예약되는 마이크로태스크는 하나다. 무한 루프 감지도 한 곳에서 한다.

이 제안은 ADR 0007과 같은 방향이다. 정착을 루트가 주관하면 "정착 1회 → 통지 1회"의 통지 주체도 루트일 수밖에 없다.

React 구독자에게 배달 순서는 렌더 결과에 영향을 주지 않는다(같은 틱의 갱신은 묶여서 렌더된다). 순서가 의미를 갖는 것은 소비자가 직접 건 `subscribe`와, 현재 구조에서 이벤트를 구독해 상태를 움직이던 내부 로직이다. 후자는 새 구조에서 사라진다.

#### 적대적 검토의 결과 (`reviews/round-1.md` R17)

진단은 현재 코드에서 실측으로 확인됐다. 3단 트리(`/` → `mid` → `mid/leaf`)에서 리프에 쓰면 `/` → `mid` 순으로, 루트에 쓰면 `mid` → `/` 순으로 배달된다 — 같은 트리, 같은 구독자인데 깊이 순서가 정반대다. 리스너가 배달 도중에 한 쓰기의 `UpdateValue`는 먼저 예약된 이벤트를 앞질러 현재 파동 안에 끼어든다.

방향은 옳다. 다만 명세 없이 옮기면 지금보다 나쁜 실패를 얻는다. 안전한 최소 명세:

1. **순서** — 작업 루프의 begin 순회에서 얻는 문서 순서의 위 → 아래. 값 변화 없이 시그널만 가진 노드는 publish 순서로 뒤에 붙인다. 정착이 끝난 뒤에 통지하므로 어떤 순서도 반쯤 정착된 트리를 드러내지 않는다. 위 → 아래는 수집 비용이 없고, 같은 결과를 내는 쓰기들 사이에서 안정적이며, React의 렌더 순서와 같다. 현재의 루트 쓰기 순서를 뒤집으므로 소비자에게 보이는 변경이다.
2. **배달 집합** — (이번 정착에서 바뀐 노드) ∪ (시그널 비트가 대기 중인 노드). `RequestFocus`/`RequestSelect`는 값 변화 없이 임의의 노드에 발행되고(`components/Form/Form.tsx:148,150`), 가상화는 지연 마운트와 같은 태스크에 포커스가 떨어지도록 즉시 발행한다(`DeferrableNodeProxy.tsx:55,57`). "바뀐 노드"만으로는 이들을 담지 못한다.
3. **`revision`** — 노드 X의 리스너를 호출하기 **직전에** X의 원장을 올린다. 현재도 publish가 아니라 배달 시점에 올린다(`EventCascadeManager.ts:211`). 미리 일괄로 올리면 아직 통지되지 않은 노드의 revision이 먼저 읽히고, 나중에 올리면 강제 재동기화 중의 `getSnapshot`이 옛 값을 읽어 리렌더를 건너뛴 채 영구히 stale해진다.
4. **파동** — 고정된 스냅숏을 순회한다. 배달 도중의 쓰기는 즉시 정착하되 통지는 다음 파동에 나간다. 틱당 파동 수에 상한을 두고, 그 에러는 마이크로태스크 밖에서 올린다. 현재의 노드별 루프 상한(`EventCascadeManager.ts:83,95`)은 리스너 둘이 파동마다 한 번씩 쓰는 경우를 세지 못한다.
5. **분리된 노드** — 예약 뒤에 정리되거나 부모를 잃은 노드는 건너뛰고 대기 비트를 지운다. 배열 제거는 틱 도중에 아이템 서브트리 전체를 정리한다(`ArrayNode/…/BranchStrategy.ts:457-459`).
6. **에러** — 리스너 호출을 하나씩 격리한다. 보고하고 계속한다. 현재 리스너 루프에는 try/catch가 없어(`EventCascadeManager.ts:207-213`) throw가 그 노드의 나머지 리스너만 멈추지만, 루프가 루트 하나로 합쳐지면 뒤의 모든 노드가 통지를 못 받고 원장도 오르지 않는다. `subscribe`는 공개 API이므로 소비자 코드 한 줄이 폼 전체를 조용히 멈출 수 있다.

순서의 제약: 루트 디스패처는 ADR 0007보다 먼저 들어갈 수 없다. 현재 `UpdateValue`는 열 개 노드 타입 모두에서 동기 발행이고, computed 의존성(`AbstractNode.ts:526-535`)과 `VirtualNode`(`VirtualNode.ts:118-135`)가 그 동기성에 기댄다. 내부 로직이 이벤트에서 떨어져 나온 뒤에야 디스패처를 옮길 수 있다.

배열의 `push`/`remove`/`pop`/`clear`가 돌려주는 Promise는 마이크로태스크 하나 뒤에 풀린다. 파동이 둘 이상이면 `await arr.push(x)`가 "구독자가 이미 봤다"를 뜻하지 않게 된다. 동기 API로 바꾼다(ADR 0007의 미결과 같은 결론).


### 통지의 시점 — 동기 (결정, 2026-09-22)

**규칙 하나: 쓰기 하나는 동기로 정착하고 동기로 통지한다. 배치는 그 끝에 한 번 그렇게 한다.** 마이크로태스크 배치는 없다. 별도의 "즉시" 옵션도 없다.

근거는 현재 코드가 지키는 제약이다(`04-inherited-constraints.md` T-1). 노드가 초기화된 뒤 `UpdateValue`만 동기로 발행하는 이유는 제어 컴포넌트의 캐럿 보존이다 — 입력의 `onChange` → `setValue` → 동기 `UpdateValue` → `useSyncExternalStore`의 구독 콜백 → **같은 React 이벤트 핸들러 안에서** 리렌더 → `value` 속성이 DOM과 같아진다(`AbstractNode.ts:891-900`, `hooks/useSchemaNodeTracker.ts:36-44`, `SchemaNodeInput.tsx:116`). 통지가 한 틱 늦으면 포맷팅 입력에서 캐럿이 끝으로 튄다(`__tests__/scenarios/controlled-interaction.render.test.tsx:340-368`이 고정한다).

새 설계에서는 표시 → 계산 → 파생 → 커밋이 모두 동기이므로(ADR 0007) 통지도 동기로 낼 수 있고, 그러면 오늘의 "UpdateValue만 동기, 나머지는 배치"라는 예외가 사라진다. 모든 상태 통지가 같은 시점에 나간다. React는 한 이벤트 핸들러 안의 갱신을 묶어 렌더하므로 노드 1,000개의 동기 통지도 렌더는 한 번이다. 핸들러 밖(타이머, 네트워크 콜백)에서의 쓰기는 React 18 이상에서도 자동 배치된다.

배치 API: 여러 쓰기를 묶는 `batch(fn)`은 fn 안의 쓰기를 표시만 하고, fn이 끝날 때 정착 한 번·통지 한 파동을 낸다. 스파이크의 `batch()`가 이 모양이다(`spikes/work-loop/proto/loop.mjs:510`). 배열의 `push`/`remove`/`pop`/`clear`는 동기 API가 되고 Promise를 돌려주지 않는다.

리스너 안의 쓰기: 즉시 동기로 정착·커밋되고 통지는 현재 파동이 끝난 뒤의 다음 파동이다(위 4항). 같은 파동의 리스너가 같은 것을 본다는 보장은 payload에 한정한다(`reviews/round-3.md` E11).

## 미결

- **중간 payload.** 현재 `UpdateValue`의 payload는 `{ previous, current }`다. 정착 1회당 통지 1회면 `previous`는 "직전 정착 상태"가 된다. 중간값에 의존하는 소비자가 있는지 확인이 필요하다.
- **루트 `onChange`와 검증의 디바운스.** 현재는 이전 태스크를 취소하는 매크로태스크다. 경계의 정책으로 남길지, 소비자에게 맡길지.
- **`UpdatePath`.** 배열 재인덱싱 시 경로 변경 통지. 노드 identity와 경로의 대응은 새 구조에서도 남는다.
- **`globalState`.** 현재는 OR 누적이어서 내릴 수 없고 출처를 알 수 없다. 이번 개편에서 함께 고칠지.
- **`RequestRemount`.** 프로덕션에서 한 번도 발행되지 않는다. 제거 후보.
- core가 렌더 계층의 명령 어휘를 소유하는 현재 경계를 유지할지 — `open-questions.md` Q8.

## 되돌림 가능성

중간. `subscribe`와 이벤트 타입은 공개 API다. 통지 시점의 변경은 소비자의 타이밍 가정에 영향을 준다.

## 확인된 결함 (2라운드, 미반영)

- **S10 스냅숏의 모순** — "같은 파동의 리스너는 같은 스냅숏을 본다"와 "배달 도중의 쓰기는 즉시 정착"이 양립하지 않는다. 뒤쪽 리스너가 `node.value`를 읽으면 새 커밋을 본다(codex 모델 실행: `1 → 2 → 2`). 해소안: 같은 스냅숏의 보장을 payload에 한정한다(`reviews/round-3-spec.md` A7).
