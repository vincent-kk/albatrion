# ADR 0013 — core는 값을 고치지 않는다

상태: 제안. 원칙은 소유자가 발의했다. 값을 통째로 주입할 때의 책임 경계는 소유자 스스로 확신이 없다고 밝혔고, 교차검증이 진행 중이다.

## 변경 이력

- 2026-09-22 — codex 교차검증의 요지를 적었다. 규칙화는 `reviews/round-3-spec.md` C.

## 맥락

소유자: "현재 스펙은 form이 좀 적극적으로 값을 바꾸고 있다. 앞으로는 field가 가려지면서 node가 deactive 되면서 값을 빼내는 걸 제외하고는, 어지간하면 입력 등을 막지 않고 error를 보여주려고 한다. array 같은 경우 min/max length 같은 처리는 FormTypeInput에서 구현하도록 위임할까 한다. core가 값을 바꿔버리는 건 예외 상황이 너무 많다."

이어서: "문제가 되는 게 setValue로 값을 주입하는 경우일 텐데, 이때는 form의 노출과 형태를 특정 값으로 수렴시킨 다음에, 보이지 않는 필드는 제거(숨김 필드 및 extra field는 제외)하고 나머지는 값에 따라 에러 메시지 등을 보여줘야 하지 않나 싶다. 확신이 없다. 책임 경계를 어떻게 해야 할지."

현재 core가 값을 바꾸는 곳(구조 추적에서 확인된 것, 전수 조사는 아님): 배열을 `minItems`까지 채우기, `maxItems`를 넘는 `push`의 차단, 타입별 파서의 강제 변환, `Normalize` 플래그의 미선언 키 제거, nullable이 아닌 객체에 `null`을 넣으면 `{}`로 바꾸기(S7), `options.trim`, `computed.derived`의 쓰기, `injectTo`, 분기 전환과 `active` 전이의 reset.

## 결정 (제안)

1. **core는 받은 값을 고치지 않는다.** 유효하지 않은 값은 그대로 들어가고 에러로 보인다. 입력을 막지 않는다.
2. **예외는 하나다 — 비활성 노드의 값은 방출에서 빠진다.** 이것도 노드의 원본을 지우는 것이 아니라 방출 값을 계산할 때의 제외다(ADR 0006, 0007).
3. **제약을 입력 단계에서 강제하는 일은 입력 컴포넌트에 위임한다.** 배열의 최소·최대 길이에 따른 추가·삭제 버튼의 비활성화 같은 것. core는 제약을 유효 스키마로 노출하고(`node.jsonSchema`), 위반은 검증이 알린다.
4. 형상 계산이 수렴하지 않을 때도 값은 받아들인다(ADR 0007).

## 값을 통째로 주입할 때 (`setValue`, `defaultValue`) — 교차검증 중

1차 제안: **제거하지 않는다.**

- 주입된 값은 모든 노드의 원본으로 분배된다. 꺼진 조각의 노드도 포함한다.
- 형상은 그 값으로 수렴한다.
- 꺼진 조각의 값은 **방출에서** 빠진다. 원본을 지우지는 않는다.
- `&visible: false`로 숨긴 필드와 스키마가 선언하지 않은 키(extra)는 방출된다. 숨김은 렌더링에만 닿는다.
- 나머지는 검증이 에러로 알린다.

이렇게 하면 사용자 입력, 로드, 프로그램적 주입이 같은 규칙 하나를 탄다. 걸리는 점: 주입했던 값이 나중에 분기를 바꿀 때 되살아난다 — 기능인가, 사고인가.

## 초기값 보존 옵션 — 교차검증 중

소유자: "기본적으로 서버 값은 클라이언트가 보낸 값을 그대로 저장했다가 돌려준다고 믿어진다. global dirty / touched를 관리하는 것도 있다. 그래도 걸린다면, 최초 주입된 defaultValue를 form 내부에서 자동으로 값을 바꾸지 않는 옵션을 추가해도 좋다."

이름의 제안: `preserveDefaultValue` (기존 prop `defaultValue`와 옵션들의 동사 + 대상 형식 — `omitEmpty`, `omitTrailing` — 에 맞췄다).

의미의 후보:

- (a) 첫 의도된 쓰기 전까지 `getValue()`가 주입된 값을 그대로 돌려준다. 단순하다. 첫 편집에서 기본값이 나타나고 미선언 키가 빠지는 점프가 생긴다.
- (b) 노드 단위로 보존한다. 로드한 값에 없는 키에는 `default`를 넣지 않고, 미선언 키를 보관하고, 손대지 않은 값에는 `omitEmpty`·`omitTrailing`을 적용하지 않는다. 점프가 없다. 규칙이 는다.

## 열려 있는 것

- 위 목록의 각 항목을 어떻게 할지 — 특히 파서의 강제 변환(문자열 입력 → 숫자), S7, `options.trim`. "값을 고치지 않는다"와 "입력을 값으로 해석한다"의 경계.
- `minItems`까지 채우지 않으면 빈 폼에서 필수 배열의 입력 칸이 하나도 보이지 않는다. 생성 시점의 초기 상태를 만드는 것은 "값을 고치는 것"인가.
- `computed.derived`와 `injectTo`는 작성자가 명시한 쓰기다. 이 원칙의 대상이 아니라고 본다.

## 교차검증 결과 — codex (2라운드 §6)

claude의 답은 받지 못했고 antigravity는 빈 응답이었다. codex 하나의 의견이며 요지는 다음과 같다. 전문은 `reviews/round-2.md` §6.

- **비활성화와 전체 교체를 구분하라.** 비활성화는 원본을 보존하고 방출에서만 뺀다. `setValue(V)`·명시적 삭제·`reset()`은 원본에도 적용되는 명령이다. 1차 제안("절대 제거하지 않는다")은 같은 Form에 레코드 A 뒤에 레코드 B를 로드하면 A의 잠복 값이 분기 전환에서 되살아나는 결함이 있다.
- `getValue(setValue(V)) = V`는 어느 정책에서도 성립하지 않는다. 성립하는 계약은 "`getValue()` = 현재 원본과 활성 집합의 투영"이다.
- `preserveDefaultValue`의 (a)는 권하지 않는다. (b)는 셋으로 나뉜다 — 로드한 값에 없는 키에만 `default`를 넣는 것과 extra의 보존은 기본 계약으로 삼고, "손대지 않은 값에는 omit을 건너뛴다"만이 이력 의존 정책이다. 앞의 둘이 기본이면 옵션의 대부분이 필요 없다.
- 자식으로만 값을 합성하는 object 노드는 주입된 `17`을 들 수 있어야 한다.
- 현재 core가 값을 바꾸는 곳의 전수 조사와 새 원칙에서의 분류(입력 컴포넌트로 옮긴다 / 버린다 / 방출에서만 적용한다 / 남긴다)는 `reviews/round-2.md` §6의 표.

이 권고를 규칙으로 옮긴 것이 `reviews/round-3-spec.md` C이며 3라운드의 공격 대상이다.
