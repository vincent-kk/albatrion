# ADR 0002 — 조건부 장치를 "가드 → 조각" 단일 모델로 통합

상태: 제안(4차 본문). 모델과 아래 "합의 근거"의 항목은 소유자가 확인했다. D-8(판별 프로퍼티에 암묵 default 없음)은 **수락**(2026-09-22, `reviews/round-4.md` §4). D-2(출발점 고정·비단조 재평가)와 D-3(금지 조각을 읽지 않는다)은 **원리에서 도출**(`reviews/round-5-derivations.md` §2·§3), 소유자 확정 대기.

## 맥락

소유자의 방향:

- 폼의 표시 제어는 `&` 키워드로 모으고 FE에 귀속시킨다. 유효성 검증을 포함하는 표시 제어는 JSON Schema 표준으로 한다.
- `if`/`then`/`else`의 기존 방식(조건부 `required`로 `active`를 조절)은 완전히 제거한다. `if` 블록의 스키마로 값을 검증해, 통과하면 `then` 절을 자식에 적용한다. 컨디션은 `if`, 적용은 `then`으로 완전히 분리하고 `else`는 반대 동작으로 허용한다.
- `oneOf`/`anyOf`는 `const`/`enum`을 쓰는 제한적 적용만 지원한다.
- `allOf`의 기존 병합은 유지한다.

현재는 조건부 장치가 7개, 평가기가 4개이고(`01-current-structure.md` §3), `oneOf`와 `active`가 서로 다른 라이프사이클을 탄다.

## 폼이 스키마에서 읽는 것 (P1′)

`03-mental-model.md`의 P1을 소유자의 원칙(2026-09-23)이 날카롭게 한 것이 P1′다. 원문은 ADR 0013 "합의 근거"와 `reviews/round-5-derivations.md` §0에 있다.

> 폼이 스키마에서 읽는 것은 **노드 트리의 모양을 정하는 문법뿐**이다 — 타입(`type`, 다중 타입, 튜플), 자식의 존재(`properties`, `items`, `prefixItems`), 조건부 존재(`if`/`then`/`else`, `allOf`, `oneOf`/`anyOf`의 분기). 값의 유효성을 정하는 문법(`required`, `false`, `not`, `additionalProperties`, 범위·패턴)은 검증기의 것이고, 폼은 그 판정을 **보여 줄 뿐** 값을 고치지 않는다. 값을 빼거나 지우는 것은 작성자의 `&` 명령뿐이다.

2라운드의 소유자 발언 "값 조작은 알아야 값을 처리할 수 있다"를 이 문서는 "표준 금지 구문을 읽어 값을 뺀다"로 넓게 읽었다. 실제 뜻은 폼이 `&active`로 값을 뺄 때 그것을 안다는 것이었다(정정, derivations §0).

## 결정

조건부로 형상을 바꾸는 모든 표준 구문을 하나의 내부 표현으로 환원한다.

| 구문 | 가드 | 조각 (가드가 참일 때 얹는 스키마) | 문맥 |
| ---- | ---- | -------------------------------- | ---- |
| `if`/`then`/`else` | `if` / `if`의 부정 | `then` / `else` | 연언 |
| `allOf: [{ if, then }, …]` | 각 항목의 `if` | 각 항목의 `then` | 연언 |
| `allOf`의 무조건 항목 | 항상 참 | 그 항목 | 연언 |
| 판별식이 있는 `oneOf`/`anyOf`의 분기 | 분기의 판별식 부분 + 그 프로퍼티의 `required` (**값 가드**) | 분기의 나머지 | 선언 |
| 판별식이 없는 `oneOf`/`anyOf`의 분기 | `selection === i` (**선택 가드**, 폼 상태) | 분기 전체 | 선언 |

가드의 종류는 둘이다.

- **값 가드**: 스키마다. 검증기 플러그인의 `compileGuard`로 동기 평가하고(ADR 0004), 투영된 값을 본다.
- **선택 가드**: 폼 상태다. `selection` 칸이 분기를 고른다(E2). 판별식이 있으면 이 칸이 없다.

### 조각은 트리다 (E3)

- 조각은 자기가 나온 구문의 문맥(연언인가 선언인가)과 소속(어느 `oneOf`/`anyOf`의 분기인가)을 든다.
- **중첩 조각은 감싸는 조각이 활성일 때만 순회한다.**
- 전순서 = (감싸는 조각의 순서, 키워드 순위 `properties` < `allOf[i]` < `if`/`then`/`else` < `oneOf`/`anyOf`, 배열 인덱스). 2라운드 S13("나중 선언이 이긴다"가 JSON 키 순서에 기댄다)은 이 전순서로 닫힌다.
- **존재(어떤 프로퍼티가 있는가)는 활성 조각의 합집합이다.** 문맥과 무관하다.
- **제약(기존 프로퍼티에 얹는 overlay)은 연언 문맥의 조각끼리만 교차한다.**
- 같은 `oneOf`/`anyOf`의 분기는 둘 이상 활성이 될 수 없다 — 판별식 가드는 서로소이고(ADR 0005 §4) 선택 가드는 하나만 고른다. 2라운드 S14의 예외 절("둘 이상 활성이면 overlay를 뺀다")은 도달하지 않으므로 삭제한다.

유효 스키마는 폼 전용이고 검증기에 가지 않으므로(ADR 0001) 영향은 UI 힌트(select의 선택지, min/max)에 한정된다.

### 가드는 투영 후 값을 본다 (E5)

- 가드의 입력 `G`는 **검증기가 볼 값**이다 — 현재의 활성 집합으로 합성한 로컬에 투영(`omitEmpty`·`omitTrailing`·null)을 적용한 것. 형상과 판정이 어긋나지 않게 하는 조건이다(P1).
- 예외는 하나다: 호스트 자신의 원본이 객체가 아니면 `G = {}`. 2라운드 S8(`properties`·`required`가 `null`·`undefined`에서 공허하게 참)은 이 예외로 닫히고, 빈 중첩 union도 자기 `{}`로 자기 조각을 결정하므로 전 분기가 켜지지 않는다.
- 끌어올린 가드가 `{addr: null}`에서 참인 것은 검증기도 같으므로 계약 위반이 아니다(`00-goals.md` G1).

### 출발점은 고정이고 재평가는 비단조다 (E6, D-2)

상태: 원리에서 도출(`reviews/round-5-derivations.md` §3), 소유자 확정 대기.

1. 출발점 `A := 무조건 조각 ∪ union의 판별 프로퍼티 ∪ 조상에서 상속된 overlay`. **직전 커밋의 활성 집합은 읽지 않는다** — 형상이 이력을 읽으면 같은 원본이 다른 형상이 된다(P3). 직전 커밋은 전이(`default` 주입)를 계산할 때만 쓴다.
2. 한 바퀴에 **모든** 조각의 가드를 평가한다. 참이면 켜고 거짓이면 **끈다**. 한 바퀴 안의 켜짐·꺼짐은 뒤의 가드에 즉시 반영된다(가우스-자이델, F3).
3. `A`가 바뀌면 다시 돈다. 상한 = 조건부 조각 수 + 1. 넘으면 마지막 바퀴의 `A`로 고정하고 `settle.status := 'budget-exceeded'`로 **프로덕션에서도 관측 가능하게** 남긴다(개발 모드에서는 커밋 뒤 throw). 자식의 `budget-exceeded`는 조상으로 전파된다(F12).
4. 지원 범위 밖은 "자기 부정 스키마"가 아니라 그 일반형이다: **가드 의존 관계에 부정을 포함한 순환**이 있으면 고정점이 없을 수 있고, 결과는 상한에서 결정적이되 임의적이다(F3). 1라운드 R6이 철회한 "순환이 없다"의 자리가 이것이다.
5. 직전 커밋의 활성 집합은 **바퀴의 평가 순서 힌트로만** 쓴다(F13). 출발점 자체를 바꾸는 최적화는 `open-questions.md` Q15.

비용: 정순 의존 체인은 2바퀴, 역순 N단은 N+1바퀴다(E4). 이 셈은 원본이 이미 있는 계산에 한정되며, `default`로 이어지는 체인은 링크마다 전이 라운드를 쓴다(F2, ADR 0007).

### 금지 조각은 없다 (D-3 = (iii))

상태: 원리에서 도출(`reviews/round-5-derivations.md` §2), 소유자 확정 대기.

`properties: { x: false }`, `not: { required: [...] }`, `additionalProperties: false`는 값의 유효성을 정하는 문법이므로 **폼이 읽지 않는다**(P1′). `false`는 아무것도 선언하지 않으므로 "x라는 자식이 존재한다"는 선언도, 값을 빼는 명령도 아니다.

| 상황 | 폼의 동작 |
| ---- | -------- |
| x가 본체(`properties`)에 선언돼 있다 | 보통 필드로 보이고 검증기의 에러가 붙는다 |
| x가 본체에 없다 | 입력 노드가 없는 **잔여 키**다 (아래) |
| 작성자가 숨기려 한다 | `&active`를 쓴다 (ADR 0003) |

2라운드 S5(금지 조각의 순환 — `if required a → properties a: false`에 고정점이 없다)는 읽지 않으므로 사라진다. 3라운드 D-3의 (i)("비활성화와 같다")도 폐기된다 — BE가 거부하려던 값을 폼이 조용히 지우는 것은 P2 위반이다.

**잔여 키의 표시는 검증기 플러그인의 계약이다**(C-4). 정규화된 에러에 선택 필드 `rejectedKey?: string`을 두고 플러그인이 채운다. core는 `rejectedKey`가 있는 호스트 에러만 모으므로 형상 규칙을 갖지 않는다.

| 기각 형태 | 누가 키를 대는가 |
| -------- | --------------- |
| `false` 스키마 (`properties`·`patternProperties`·분기 안) | 에러만으로 — `instancePath`가 곧 키 |
| `additionalProperties`·`unevaluatedProperties`·`propertyNames` | 에러만으로 — `params` |
| 단일 이름 `not: { required: ['x'] }` | 플러그인이 자기 스키마를 읽는다 |
| 두 이름 이상의 `not: { required: [...] }` | 아무도 못 댄다 — 호스트 에러로 남는다(F8) |

ajv 6·7·8 × 드래프트 6종에서 결과가 같고, 현재 에러 타입이 이미 `dataPath`·`schemaPath`·`keyword`·`details`를 싣는다(`spikes/guard-cost/rejected-keys/REPORT.txt`, `src/types/error.ts:242-301`).

실무 관행도 같은 방향이다(derivations §2). zod와 TypeBox는 `never`를 `{ not: {} }`(거부)로 낸다(확정). pydantic은 불리언 스키마를 내지 못한다(확정). RJSF는 `false` 속성에 "지원하지 않는 필드" 템플릿을 그린다(확정). SchemaStore의 `github-pages-jekyll.json`·`openhab-5.1.json`은 거부와 상호 배타의 뜻이다(확정). 주요 스타일 가이드는 이 패턴 대신 `oneOf`를 권한다(미대조).

### 따라 나오는 규칙

1. **중첩은 재귀로 다룬다.** 조각도 스키마다. 판별식이 있는 분기 **안의** `if`/`then`도 같다. 순환은 생길 수 있고 비단조 재평가와 상한으로 드러난다(위, ADR 0007).
2. **`allOf` 안의 `if`/`then`은 필수 지원이다.** 스키마 객체 하나에 `if`는 하나뿐이어서, 독립 조건 여럿을 쓰는 표준 관용구가 이것이다.
3. **`if`만으로 분기를 구분한 `oneOf`/`anyOf`는 값 가드가 되지 못한다.** `oneOf: [{ if A then X }, { if B then Y }]`에서 `if`가 거짓이고 `else`가 없는 분기는 공허하게 통과하므로 둘 다 통과해 `oneOf`가 기각된다. 이런 분기에는 판별식이 없으므로 선택 가드가 된다. 분기 안의 `if`/`then` 자체는 규칙 1대로 다룬다.
4. **형상을 정하는 기준은 결정 가능성이다.** 연언은 "전부 적용"이어서 형상이 결정된다. 선언은 값만 보고 분기가 결정될 때(판별식)이거나 사용자가 고를 때(선택 가드)만 형상을 정한다.
5. **존재는 선언 위치로, 필수성은 `required`로 가른다.** 조각 안에서만 선언된 프로퍼티는 조건부로 존재한다. 기본 `properties`에 선언된 프로퍼티는 **항상 존재한다** — 끄는 조각이 없다. `required`는 말 그대로 required다.
6. **다른 서브트리를 보는 조건은 `if`를 공통 조상으로 끌어올려 표현한다 — 상속 overlay**(E12). 끌어올린 조각의 `then`이 손자를 선언하면 청사진이 그 선언을 자식 호스트의 **상속 overlay**로 귀속시키되 가드는 조상의 것이다. 자식의 계산 입력은 (원본, `selection`, 상속 overlay 집합)이고, 부모의 바퀴가 overlay 집합을 바꾸면 자식을 **그 바퀴 안에서** 재계산한다 — 부모 가드가 자식의 방출을 읽으므로 뒤로 미룰 수 없다. 같은 입력이면 재계산하지 않도록 메모한다(F5). 조건의 입력이 값 밖(`@` 컨텍스트, 사용자 권한)에 있으면 서버가 원리적으로 검증할 수 없으므로 `&`로만 쓴다. 비용은 ADR 0009.

### 판별식 가드에는 `required`를 더한다

OpenAPI에서 흔한 모양은 `required: ['kind']`가 분기가 아니라 기본 스키마 쪽에 있다. 분기의 판별식 부분만 떼어낸 `{ properties: { kind: { const: 'a' } } }`는 `kind`가 없을 때 **모든 분기에서 참**이다(실측, `reviews/round-1.md` R11-a). 그래서 판별식 가드는 `{ properties: { kind: <분기의 제약> }, required: ['kind'] }`로 만든다.

- 이것은 형상용 가드이지 판정이 아니다. 검증기에는 작성된 스키마가 그대로 간다(ADR 0001). 폼이 `const`를 해석하지 않고 여전히 검증기가 평가한다.
- **판별 프로퍼티는 union 호스트가 소유한다**(E8). 2라운드 S2(판별 필드 교착 — 분기와 프로퍼티가 서로의 존재를 기다린다)는 이 소유 규칙으로 닫힌다. 식별 알고리즘과 에러 라우팅은 ADR 0005 §4.
- **암묵 default는 없다**(D-8, 수락 2026-09-22, `reviews/round-4.md` §4). "명시된 default가 없으면 전순서 첫 분기의 값"이라는 3라운드 E8은 철회한다. 값이 비어 있으면 어느 분기도 활성이 아니고 판별 필드만 존재한다 — 현재 구현과 같다(`ComputedPropertiesManager.ts:106`, `BranchStrategy.ts:735-739`). 폼은 값을 만들지 않는다.
- `if` 가드에는 `required`를 더하지 않는다. `if`는 서버와 똑같이 평가한다 — `kind`가 없을 때 `if`가 참인 것은 표준의 동작이고, 개발 모드 경고는 Q10.

### 선택 가드의 초기 선택 (F6, E17)

기존 값을 로드할 때 어느 분기를 고른 것으로 볼지:

1. **값이 분기가 선언한 키를 하나도 갖고 있지 않으면 분기 없음이다** — `selection` 없음, 어느 조각도 켜지지 않는다(C-1·C-7). 여분 키만 있는 값이나 무조건 자식의 키만 있는 값도 "분기 키 없음"이다 — 이 확장은 원리에서의 도출이며(`reviews/round-5-derivations.md` §1 C-1·C-7) **프로토타입 `loop-v4b`는 아직 반대로 돈다**(`{zzz:1}`에 첫 분기를 고름, `spikes/work-loop/REPORT-v4b.txt` §5 U-1). 소유자 확정 대기. 폼은 값을 만들지 않는다(D-8과 같은 이유).
2. 그렇지 않으면 **값의 키 가운데 가장 많이 선언한 통과 분기**를 고른다. 동점이면 앞의 분기. 통과하는 분기가 없으면 앞의 분기이고 에러는 검증기가 낸다.
3. 호스트의 `required`/`dependentRequired`가 비활성 조각의 키를 가리키면 그 키를 선언한 조각에 가중한다(E17).
4. `Overwrite`는 `selection`을 새 값으로 다시 정하고 `reset()`은 초기 선택으로 되돌린다. 초기 선택은 노드의 원본을 바꾸지 않는다.

"처음 통과하는 분기"는 더 좁은 분기를 골라 나머지 키를 방출에서 빼 버린다 — 아무것도 고치지 않고 저장해도 서버의 데이터가 사라진다(R9, 실측).

프로토타입 실행: `{}`·`undefined`에서 분기 없음·주입 0, 키를 가진 값에서 규칙 2, 새 시나리오 14/14, 기존 63 회귀 0(`spikes/work-loop/REPORT-v4b.txt`).

### 수동 분기 선택이 계약을 깨지 않는 이유

마커의 문제는 분기를 폼 상태로 고른 것이 아니라 **검증기 입력을 바꾼 것**이었다. 판정이 `validator(작성된 스키마, 방출 값)`으로 고정되면(ADR 0001) 선택기는 어떤 조각의 형상을 그릴지만 고른다. 사용자가 B를 골라 채웠는데 검증기가 "2개 매치"라고 하면 폼은 그 에러를 객체 노드 수준에 그대로 보인다. 그것은 스키마 작성자의 문제다.

## 합의 근거

- 조각이 `properties` 밖에서 새 노드를 선언할 수 있다 — 소유자: "then / else에서 신규 노드를 선언할 수 있어. object 노드를 기준으로 한다면 properties 외에도 노드가 있을 수 있는거지."
- 비판별 분기의 수동 선택이 필요하다 — 소유자: "분기를 수동으로 고르는 기능이 아예 없는 건 애매하다. 서버에서는 oneOf anyOf를 실제로 많이 쓴다."
- 값 가드는 동기로 평가하고 방출 값을 본다 — 소유자: "가드는 동기로 해도 될 것 같다." / "가드는 방출 값을 보는 게 맞다."
- 스키마 선언의 책임은 작성자에게 있다 — 소유자: "JSON Schema 스펙을 잘 따르는 구현체를 쓰면 되는 거고, 실제 스키마 선언 책임은 사용자에게 있다."
- 조각이 꺼지면 방출 값에서 빠지고 노드의 원본은 남는다 — ADR 0006, 0007.
- 폼이 읽는 것은 형상 문법뿐이다 — ADR 0013 "합의 근거"의 원문(2026-09-23).

## 결과

- 조건부 장치 7개와 평가기 4개가 "가드/조각 하나 + `&` 표현식 하나"로 줄어든다.
- `if`/`then`, `oneOf`, `&active`가 같은 정착을 탄다(ADR 0007).
- #340이 부수적으로 풀린다. 분기마다 `kind: { const }`가 있으면 비활성 분기가 `const`에서 떨어지므로 `anyOf`의 판정이 곧 활성 분기의 판정이 된다(이슈 #342 §2 케이스 9).
- 분기 선택기라는 새 UI 표면이 생긴다. UX 세부는 ADR 0010.
- 값이 비어 있으면 분기가 하나도 켜지지 않으므로, 판별 필드와 선택기만 보이는 상태가 정상 상태가 된다.

## 미결

- 판별식을 식별하는 규칙 — ADR 0005 §4.
- `dependentSchemas`/`dependentRequired`/`dependencies`를 같은 모델로 환원할지 — Q7. 환원한다면 `dependentSchemas: { k: S }`의 가드는 `{ required: ['k'] }`다.
- 잔여 키의 표시 규칙과 기본 문구, `formatError`의 `false schema` 번역, 잔여 키 UI를 기본 렌더러가 제공하는지 — 모두 렌더 계층의 일이다(derivations §2).
- 플러그인 세 개가 루트 `dataPath`로 `'/'`를 내는데 `src/types/error.ts:247`은 `''`로 적는다. 잔여 목록이 포인터를 이으려면 어느 쪽인지 정해야 한다(`spikes/guard-cost/rejected-keys/REPORT.txt` §3).
- `if`의 공허한 참에 개발 모드 경고를 낼지 — Q10. 경고하려면 `if` 내부를 읽어야 하므로 P1′와 닿는다.
- 여분 키만 있는 값(`{zzz:1}`)에서 선택 가드 union이 분기 없음이어야 하는가 — 규칙 1의 도출은 그렇다고 하지만 `loop-v4b`는 첫 분기를 고른다(`spikes/work-loop/REPORT-v4b.txt` §5 U-1). 소유자 결정 뒤 프로토타입을 맞춘다.
- 어느 분기도 켜지지 않은 선택 가드 호스트에 부분 쓰기가 오면 그 키를 선언한 분기를 켜는가 — 미정의(`spikes/work-loop/REPORT-v4b.txt` §5 U-2).
- 초기 선택은 선택 가드에만 닿고 `if`/`then` 조각에는 닿지 않는다(E16). 가드가 거짓이면 그 키는 검증기에도 미선언 키이므로 손실은 스키마의 뜻이라고 보았으나, 2라운드 S6 패턴의 실행 반례가 남아 있다.
- 사용자가 분기를 바꿀 때 이전 분기의 값 — Q1, ADR 0010.
