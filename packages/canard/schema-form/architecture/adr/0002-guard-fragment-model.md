# ADR 0002 — 조건부 장치를 "가드 → 조각" 단일 모델로 통합

상태: 제안. 소유자는 이 모델 위에서 논의를 이어 갔고, 세부 가운데 일부에 명시적으로 동의했다("합의 근거"). 2026-09-22의 개정분(합성 문맥, 금지하는 조각, 판별식 가드의 `required`, 초기 분기 추론)은 아직 소유자의 확인을 받지 않았다.

## 변경 이력

- 2026-09-22 — 적대적 검토 1라운드(`reviews/round-1.md`)를 반영했다. R6: "가드는 값을 보므로 순환이 없다"를 철회. R10: 활성 조각을 전부 교차하던 것을 **합성 문맥을 보존하는** 규칙으로 바꾸고, 금지하는 조각을 더했다. R11-a: 판별식 가드가 빈 폼에서 전부 참이 되는 문제에 대해 가드에 `required`를 더했다. R9: 초기 분기 추론을 "처음 통과하는 분기"에서 "값을 가장 많이 덮는 분기"로 바꿨다. 규칙 3의 문구를 고쳤다.
- 2026-09-22 — 적대적 검토 2라운드(`reviews/round-2.md`)의 S2·S4·S5·S8·S14를 "확인된 결함" 절에 적었다. 본문은 3라운드 뒤에 고친다.

## 맥락

소유자의 방향:

- 폼의 표시 제어는 `&` 키워드로 모으고 FE에 귀속시킨다. 유효성 검증을 포함하는 표시 제어는 JSON Schema 표준으로 한다.
- `if`/`then`/`else`의 기존 방식(조건부 `required`로 `active`를 조절)은 완전히 제거한다. `if` 블록의 스키마로 값을 검증해, 통과하면 `then` 절을 자식에 적용한다. 컨디션은 `if`, 적용은 `then`으로 완전히 분리하고 `else`는 반대 동작으로 허용한다.
- `oneOf`/`anyOf`는 `const`/`enum`을 쓰는 제한적 적용만 지원한다.
- `allOf`의 기존 병합은 유지한다.

현재는 조건부 장치가 7개, 평가기가 4개이고(`01-current-structure.md` §3), `oneOf`와 `active`가 서로 다른 라이프사이클을 탄다.

## 결정

조건부로 형상을 바꾸는 모든 표준 구문을 하나의 내부 표현으로 환원한다.

| 구문 | 가드 | 조각 (가드가 참일 때 얹는 스키마) | 문맥 |
| ---- | ---- | -------------------------------- | ---- |
| `if`/`then`/`else` | `if` / `if`의 부정 | `then` / `else` | 연언 |
| `allOf: [{ if, then }, …]` | 각 항목의 `if` | 각 항목의 `then` | 연언 |
| `allOf`의 무조건 항목 | 항상 참 | 그 항목 | 연언 |
| 판별식이 있는 `oneOf`/`anyOf`의 분기 | 분기의 판별식 부분 + 그 프로퍼티의 `required` (**값 가드**) | 분기의 나머지 | 선언 |
| 판별식이 없는 `oneOf`/`anyOf`의 분기 | `selected === i` (**선택 가드**, 폼 상태) | 분기 전체 | 선언 |

가드의 종류는 둘이다.

- **값 가드**: 스키마다. 검증기 플러그인의 `compileGuard`로 동기 평가하고(ADR 0004), 방출 값을 본다(ADR 0007). 폼은 가드의 의미를 직접 해석하지 않는다.
- **선택 가드**: 폼 상태다. 사용자가 분기를 고른다.

### 조각은 실행 단위이고, 합성 문맥은 지워지지 않는다

조각은 자기가 나온 구문의 문맥(연언인가 선언인가)과 소속(어느 `oneOf`/`anyOf`의 분기인가)을 든다. 유효 스키마를 만들 때:

- **존재(어떤 프로퍼티가 있는가)는 활성 조각들의 합집합이다.** 문맥과 무관하다.
- **제약(기존 프로퍼티에 얹는 overlay)은 연언 문맥의 조각끼리만 교차한다.**
- **같은 `oneOf`/`anyOf`에 속한 분기가 둘 이상 활성이면, 그 분기들의 제약 overlay는 유효 스키마에 넣지 않는다.** `anyOf`는 "활성인 모든 분기의 제약을 만족하라"가 아니다. 판정은 검증기가 한다. 분기가 정확히 하나만 활성이면(판별식이 있는 통상의 경우) 그 분기의 overlay를 넣는다.

유효 스키마는 폼 전용이고 검증기에 가지 않으므로(ADR 0001), 넣지 않은 overlay 때문에 판정이 달라지지는 않는다. 영향은 UI 힌트(select의 선택지, min/max)에 한정된다.

### 금지하는 조각

조각은 더하기만 하지 않는다. 다음 두 모양은 **기본 프로퍼티를 끈다** — 조각이 활성인 동안 그 이름의 노드는 비활성이고 방출에서 빠진다(원본은 남는다).

- `properties: { x: false }` — 불리언 스키마 `false`
- `not: { required: ['x'] }` — 정확히 이 모양이고 **이름이 하나일 때만**. 이름이 둘 이상이면 "전부 동시에 있으면 안 된다"는 뜻이지 "전부 끈다"가 아니다(2라운드 검토, AJV 실행으로 확인). 그 경우는 검증기가 판정하고 폼은 에러를 보인다

그 밖의 부정(`not` 안의 일반 스키마, `maxProperties`, `propertyNames`)은 형상으로 표현하지 못한다. 검증기는 그대로 판정하고, 그 에러는 폼 수준으로 간다(ADR 0001). 한계로 문서화한다.

### 따라 나오는 규칙

1. **중첩은 재귀로 다룬다.** 조각도 스키마다. 판별식이 있는 분기 **안의** `if`/`then`도 같다. 순환은 생길 수 있다 — 가드가 읽는 값을 조각의 기본값이 바꾸는 경우(`if: { not: { required: ['x'] } }, then: { properties: { x: { default: 1 } } }`). 작업 루프의 패스 상한으로 드러낸다(ADR 0007).
2. **`allOf` 안의 `if`/`then`은 필수 지원이다.** 스키마 객체 하나에 `if`는 하나뿐이어서, 독립 조건 여럿을 쓰는 표준 관용구가 이것이다.
3. **`if`만으로 분기를 구분한 `oneOf`/`anyOf`는 값 가드가 되지 못한다.** `oneOf: [{ if A then X }, { if B then Y }]`에서 `if`가 거짓이고 `else`가 없는 분기는 공허하게 통과하므로 둘 다 통과해 `oneOf`가 기각된다. 이런 분기에는 판별식이 없으므로 선택 가드가 된다. 분기 안의 `if`/`then` 자체는 규칙 1대로 다룬다.
4. **형상을 정하는 기준은 결정 가능성이다.** 연언은 "전부 적용"이어서 형상이 결정된다. 선언은 값만 보고 분기가 결정될 때(판별식)이거나 사용자가 고를 때(선택 가드)만 형상을 정한다.
5. **존재는 선언 위치로, 필수성은 `required`로 가른다.** 조각 안에서만 선언된 프로퍼티는 조건부로 존재한다. 기본 `properties`에 선언된 프로퍼티는 (금지하는 조각이 끄지 않는 한) 항상 존재한다. `required`는 말 그대로 required다.
6. **다른 서브트리를 보는 조건은 `if`를 공통 조상으로 끌어올려 표현한다.** `then`은 직계 자식이 아닌 자손에도 조각을 얹을 수 있어야 한다. 조건의 입력이 값 밖(`@` 컨텍스트, 사용자 권한)에 있으면 서버가 원리적으로 검증할 수 없으므로 `&`로만 쓴다. 끌어올린 가드는 어디를 입력하든 다시 평가된다 — 비용은 ADR 0009.

### 판별식 가드에는 `required`를 더한다

OpenAPI에서 흔한 모양은 `required: ['kind']`가 분기가 아니라 기본 스키마 쪽에 있다. 분기의 판별식 부분만 떼어낸 `{ properties: { kind: { const: 'a' } } }`는 `kind`가 없을 때 **모든 분기에서 참**이다(실측, `reviews/round-1.md` R11-a). 그래서 판별식 가드는 `{ properties: { kind: <분기의 제약> }, required: ['kind'] }`로 만든다.

- 이것은 형상용 가드이지 판정이 아니다. 검증기에는 작성된 스키마가 그대로 간다(ADR 0001).
- 여전히 검증기가 평가한다. 폼이 `const`를 해석하지 않는다.
- 결과: 판별 필드를 고르기 전에는 어느 분기도 보이지 않는다.
- `if` 가드에는 `required`를 더하지 않는다. `if`는 서버와 똑같이 평가한다 — `kind`가 없을 때 `if`가 참인 것은 표준의 동작이고, 개발 모드 경고로 알린다(`00-goals.md` C2).

### 선택 가드의 초기 선택

기존 값을 로드할 때 어느 분기를 고른 것으로 볼지: 값을 통과시키는 분기 가운데 **값에 있는 키를 가장 많이 선언한 분기**를 고른다. 같으면 앞의 분기. 통과하는 분기가 없으면 같은 기준을 전체 분기에 적용한다.

- "처음 통과하는 분기"는 더 좁은 분기를 골라 나머지 키를 방출에서 빼 버린다 — 아무것도 고치지 않고 저장해도 서버의 데이터가 사라진다(R9, 실측).
- 초기 선택은 노드의 원본을 바꾸지 않는다.
- 사용자가 분기를 바꿀 때 이전 분기의 값을 어떻게 할지는 `open-questions.md` Q1과 ADR 0010.

### 수동 분기 선택이 계약을 깨지 않는 이유

마커의 문제는 분기를 폼 상태로 고른 것이 아니라 **검증기 입력을 바꾼 것**이었다. 판정이 `validator(작성된 스키마, 방출 값)`으로 고정되면(ADR 0001) 선택기는 어떤 조각의 형상을 그릴지만 고른다. 사용자가 B를 골라 채웠는데 검증기가 "2개 매치"라고 하면 폼은 그 에러를 객체 노드 수준에 그대로 보인다. 그것은 스키마 작성자의 문제다.

## 합의 근거

- 조각이 `properties` 밖에서 새 노드를 선언할 수 있다 — 소유자: "then / else에서 신규 노드를 선언할 수 있어. object 노드를 기준으로 한다면 properties 외에도 노드가 있을 수 있는거지."
- 비판별 분기의 수동 선택이 필요하다 — 소유자: "분기를 수동으로 고르는 기능이 아예 없는 건 애매하다. 서버에서는 oneOf anyOf를 실제로 많이 쓴다."
- 값 가드는 동기로 평가하고 방출 값을 본다 — 소유자: "가드는 동기로 해도 될 것 같다." / "가드는 방출 값을 보는 게 맞다."
- 스키마 선언의 책임은 작성자에게 있다 — 소유자: "JSON Schema 스펙을 잘 따르는 구현체를 쓰면 되는 거고, 실제 스키마 선언 책임은 사용자에게 있다."
- 조각이 꺼지면 방출 값에서 빠지고 노드의 원본은 남는다 — ADR 0006, 0007.

## 결과

- 조건부 장치 7개와 평가기 4개가 "가드/조각 하나 + `&` 표현식 하나"로 줄어든다.
- `if`/`then`, `oneOf`, `&active`가 같은 begin/complete를 탄다(ADR 0007).
- #340이 부수적으로 풀린다. 분기마다 `kind: { const }`가 있으면 비활성 분기가 `const`에서 떨어지므로 `anyOf`의 판정이 곧 활성 분기의 판정이 된다(이슈 #342 §2 케이스 9).
- 분기 선택기라는 새 UI 표면이 생긴다. UX 세부는 ADR 0010.

## 미결

- 판별식을 식별하는 규칙 — ADR 0005 §4.
- `dependentSchemas`/`dependentRequired`/`dependencies`를 같은 모델로 환원할지 — `open-questions.md` Q7. 환원한다면 `dependentSchemas: { k: S }`의 가드는 `{ required: ['k'] }`다.
- 금지하는 조각의 두 모양을 폼이 읽는 것은 구조 읽기의 범위를 넓힌다(G3). 소유자의 확인이 필요하다.

## 확인된 결함 (2라운드, 미반영)

`reviews/round-2.md` §4에서 실행으로 확인됐고 아직 본문에 반영하지 않았다. 해소안은 `reviews/round-3-spec.md`에 있으며 3라운드 검토 뒤에 본문을 고쳐 쓴다.

- **S2 판별 필드 교착** — 판별 프로퍼티가 분기에서만 선언되면 분기와 프로퍼티가 서로의 존재를 기다린다. 해소안: 판별 프로퍼티를 union이 소유한다(`round-3-spec.md` A5).
- **S4 판별식 식별** — `allOf: [{$ref}, {properties}]` 분기, null 분기, OpenAPI 3.0 `mapping`을 놓친다. 해소안: `round-3-spec.md` B.
- **S5 금지 조각의 순환** — 가드가 방출 값을 보면 `if required a → properties a:false`에 고정점이 없다. 해소안: 금지는 되먹임에서 제외하고 투영에서만 적용한다(`round-3-spec.md` A3-5).
- **S8 비객체 호스트의 공허한 참** — `properties`·`required`는 `null`·`undefined`에서 통과한다. 해소안: 가드의 입력은 투영 전 로컬 메모이고 null 호스트는 `{}`로 평가한다(`round-3-spec.md` A3-3, A6).
- **S14 도달할 수 없는 절** — "같은 union의 분기가 둘 이상 활성이면 overlay를 뺀다"는 S8이 풀리면 도달하지 않는다. 삭제 후보.
