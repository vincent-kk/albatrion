# ADR 0001 — 검증기 입력 불변

> **5차 주(2026-09-23).** 이 문서는 4차 본문이다. 5차 원장 `03-mental-model.md`와 다른 곳은 원장이 우선한다: (1) `if`에 `required`를 넣으라는 개발 모드 경고는 없다 — 폼은 `if`의 내용을 검사하지 않는다(소유자 답 23). (2) `&if`는 `&active`에 흡수되었다. (3) "판정의 revision"은 커밋 번호다. (4) `virtual`의 처리는 12라운드에 닫힘: `virtual`은 검증기 앞 제거 목록에 들고 `required` 재작성은 버린다(원장 §1.4)(검증기에는 작성된 스키마를 그대로 넘기는가). (5) "활성 조각 아래의 에러만 노드에"는 게이트 없는 분기가 모두 활성이므로 원장 §6에서 다시 정한다. (6) 검증기 앞 제거는 규칙 둘이다. 하나는 키워드 위치의 `&` 키·`control`·`virtual`이고, 다른 하나는 형상·투영 키와 표현 키의 닫힌 목록(원장 §1.4)이다. 본문의 "폼 전용 키"는 제어 키(`&`)와 표현 키(접두 없음)로 나뉜다(원장 §1.4, 13라운드 답 3). (4)의 `virtual` 처리는 12라운드에 닫혔다: `virtual`은 제거 목록에 들고 `required` 재작성은 버린다.

상태: 제안. 방향("client에서 통과한 데이터는 서버에서 온전히 통과해야 한다", "유효성 검증에 개입하는 처리는 JSON Schema 스펙을 충실히 따른다")은 소유자가 발의했다. 아래 정식화는 그 방향을 구조로 옮긴 제안이며, 소유자는 이 정식화를 전제로 이후 논의를 이어 갔으나 문구 자체에 대한 명시적 동의는 아직 없다. 검증기 설정에 관한 부분은 수락 — 소유자: "플러그인에서 인스턴스를 수정하거나 설정을 주입할 수 있게 되어 있다. 기본값이 그런 거고. 플러그인 기본값을 바꿔도 되지만 그건 사용자가 의지적으로 켜야 한다. 나는 & 말고도 커스텀 필드를 많이 써서 무분별하게 열긴 좀 그렇다."

## 변경 이력

- 2026-09-22 — 2라운드 S1을 반영했다. 1라운드 개정에서 "기본은 스키마를 변형하지 않는다"로 바꿨던 것을 되돌렸다 — 폼 전용 키를 컴파일 전에 지우는 현행 동작은 판정 때문이 아니라 검증기의 컴파일을 지키는 보호였다.
- 2026-09-22 — 적대적 검토 1라운드(R1–R5)를 반영했다. 계약을 "같은 설정의 검증기"로 한정하고, 판정의 revision, 방출 값의 직렬화 동치, `None`의 의미를 더했다. "`&` 키 제거가 유일하게 허용되는 변형"을 "기본은 변형하지 않는다"로 바꿨다 — 제거 규칙이 키워드 위치와 데이터 위치를 구분하지 못한다는 지적(R4)과, strict 모드를 기본으로 두지 않는다는 소유자의 결정에 따른 것이다.

## 맥락

핵심 계약은 "폼이 통과시킨 값을 독립 JSON Schema 검증기가 기각하는 일은 없다"이다. 현재 구조는 이 계약을 기능별 규율로 지키려 했고, 네 군데에서 샜다(`01-current-structure.md` §4): 스키마에 주입하는 마커, 값에 덮는 enhancer, `allOf` 병합본을 검증기에 넘기는 것, `virtual`의 `required` 재작성.

"`&` 키워드는 검증에 개입하지 않게 한다"를 규율로만 두면 같은 일이 다시 일어난다.

## 결정

> **폼의 판정 = `validator(작성된 스키마, 방출되는 값)`.**
> 검증기는 이 둘만 본다. 폼이 내부에서 파생한 스키마(`allOf` 병합, 조각을 얹은 유효 스키마)는 폼 전용이며 검증기에 전달하지 않는다. 검증용으로 값에 무엇을 더하지도 않는다.

**허용되는 스키마 변형은 하나다 — 폼 전용 키를 키워드 위치에서만 제거하는 것.** 현재 `stripSchemaExtensions`가 하는 일이고(`JSONSchemaScanner`로 위치를 구분한다) 그대로 둔다(목록은 넓어진다, ADR 0003 §7). 표준에서 미지 키워드는 무시되므로 이 제거는 판정을 바꾸지 않는다. 제거가 필요한 이유는 판정이 아니라 **검증기의 컴파일**이다: 폼 전용 키의 값에 순환하거나 깊은 객체가 있으면(`FormTypeInputProps`의 자기 참조, 개발 빌드의 React 엘리먼트) `ajv.compile`이 스택 초과로 죽는다(`reviews/round-2.md` S1, 실행). 소비자의 커스텀 키는 라이브러리가 열거할 수 없으므로 지우지 않는다 — strict 모드는 기본이 아니다(ADR 0003).

FE 전용으로 더 강하게 검증하고 싶으면 추가 검사를 AND로만 붙인다: `폼 판정 = validator(…) ∧ FE추가검사`. 어떤 추가 검사를 붙여도 "폼 통과 ⇒ 서버 통과"는 유지된다.

### 이 불변식이 보장하는 범위 (`reviews/round-1.md` R1–R5)

이 불변식은 검증기의 **입력**을 고정한다. 검증기 **함수**는 고정하지 못한다. 그래서 계약은 이렇게 읽는다:

> 폼이 통과시킨 값은, **같은 설정의 검증기**도 통과시킨다.

- **같은 설정**은 방언, format을 검사하는지, 커스텀 키워드·포맷, 값을 바꾸는 옵션(`coerceTypes` 등)을 쓰지 않는 것을 뜻한다. 기본 ajv8 플러그인은 draft-07 엔트리에 `validateFormats: false`다(`schema-form-ajv8-plugin/src/default/validatorPlugin.ts:15-19`). 이 기본값에서 `$schema` 없는 2020-12 스키마의 `dependentRequired`·`unevaluatedProperties`는 조용히 무시되고 `format`은 항상 통과한다. 서버와 설정을 맞추는 것은 소비자의 책임이고 수단은 이미 있다 — 플러그인의 `bind(instance)`로 Ajv 인스턴스를 주입한다. 기본값은 바꾸지 않는다(ADR 0004).
- **판정은 값의 revision에 묶인다.** 비동기 검증의 결과가 도착했을 때 값이 이미 바뀌었으면 그 결과는 버린다. `isValid`는 판정의 revision이 현재와 같을 때만 참이다. 제출은 캐시된 판정이 아니라 **실제로 보내는 스냅숏**을 검증한다.
- **방출 값은 JSON으로 직렬화했을 때와 같은 값이어야 한다.** 값이 `undefined`인 키, 배열 중간의 `undefined`는 메모리에서의 판정과 전송 후의 판정을 갈라놓는다(`{minProperties:3}`에 `{a:1,b:2,c:undefined}`).
- **`ValidationMode.None`은 "판정을 제공하지 않음"이다.** 통과가 아니다.
- 에러 라우팅이 실제 실패를 숨기는지로 공격받았으나 살아남았다. 라우팅은 에러가 어디에 보일지만 정하고 판정을 바꾸지 않는다.

## 결과

- `&active`가 값을 지우든 `&derived`가 값을 쓰든 계약은 깨지지 않는다. 그 키워드들이 바꿀 수 있는 것은 값뿐이고, 그 값이 곧 서버가 받을 값이기 때문이다.
- `ENHANCED_KEY`, enhancer, `preprocessSchema`의 마커 주입, `__processCompositionValue__`의 마커 기록, `transformErrors`의 마커 필터가 모두 사라진다. 이슈 #342 §3.1·§3.3·§3.4가 함께 사라진다.
- 에러 라우팅은 마커 없이 한다. 폼이 활성 조각을 알고 있으므로 `schemaPath`가 활성 조각 아래인 에러만 해당 노드에 표시한다. 이것은 표시 필터이고 판정을 바꾸지 않는다. 현재도 variant 노드의 `schemaPath` 접두사 매칭이 있다(`ValidationManager/utils/matchesSchemaPath.ts:33-37`).
- 검증기 에러 가운데 `instancePath`에 해당하는 노드가 없는 것이 생긴다(꺼진 조각의 필드가 기본 `required`에 걸린 경우 등). **주인 없는 에러를 모으는 폼 수준 sink**가 필요하다. 작성자의 실수를 폼이 가리지 않는다.
- `nodeFromJSONSchema`를 직접 부르는 경로와 `<Form>` 경로가 같은 계약을 갖게 된다(지금은 다르다).

## 비용

- `&if`만으로 분기를 구분한 기존 스키마는 폼에서도 invalid가 된다. 의도된 파괴적 변경이다.
- `virtual`이 표준 `required`에 가상 이름을 올리는 현재 방식은 이 결정과 충돌한다. `open-questions.md` Q5.
- 스펙의 함정을 그대로 따르게 된다. `if: { properties: { kind: { const: 'a' } } }`는 `kind`가 없을 때 참이다. 빈 폼에서 `then`이 켜진다. 서버와 똑같이 동작하는 대신, 폼은 `if`의 내용을 검사하지 않는다(소유자 답 23, 원장 §5). 분기 컨벤션(`else: false`, `if`의 `required`)은 ADR 0010에 적는다.
