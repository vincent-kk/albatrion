# ADR 0004 — 검증기는 플러그인 유지, 동기 `compileGuard` 추가

> **5차 주(2026-09-23).** 이 문서는 4차 본문이다. 5차 원장과 다른 곳은 원장이 우선한다: (1) 변경 경로 → 가드의 역색인은 ADR 0005 §2와 0006이 기각했다(E13). (2) ADR 0010은 분기 관행 문서다(외부 조사 항목 아님).

상태: 수락.

## 변경 이력

- 2026-09-24 — 16라운드(`09-landing-and-test-strategy.md` §2.1): 가드 계약을 `compileGuard(root, pointer)`로 정하고, 사본과 가드 캐시는 코어가 검증기 인스턴스마다 WeakMap<작성 루트, { 사본, 가드 표 }>로, 사본 루트의 등록은 플러그인의 검증기 인스턴스가 들게 했다.
- 2026-09-24 — 15라운드(`reviews/round-15-decisions.md`): `&` 축약을 `controls` 그룹 표기로, 조각 식의 기준점을 호스트로, 맨 폼 전용 키를 `options`·`presentation` 그룹으로 바꿨다.

## 맥락

`if`를 스키마로 평가하려면(ADR 0002) 폼이 형상을 정하는 데 검증기가 필요해진다. 소유자는 검증기를 내장해야 한다고 보고 가장 작은 구현체로 알려진 `@cfworker/json-schema`를 검토했으나, 검증기를 플러그인으로 분리한 장점을 잃는 것을 우려했다.

관찰:

- 플러그인 계약에는 이미 `compile(schema)`가 있다(`src/app/plugin/type.ts:246-248`).
- 검증은 본래 동기다. AJV의 `ajv.compile(schema)`가 돌려주는 함수는 동기 boolean이고 `$async: true`일 때만 비동기다. 현재 ajv8 플러그인이 스키마에 `$async: true`를 직접 넣고 `async`로 감싸고 있다(`packages/canard/schema-form-ajv8-plugin/src/validator/createValidatorFactory.ts:19-25`). 비동기는 검증기의 성질이 아니라 그 플러그인의 선택이다.
- 폼 쪽 타입은 이미 동기 반환을 허용한다: `Promise<JSONSchemaError[] | null> | JSONSchemaError[] | null`(`src/types/error.ts:209-212`).

## 결정

검증기를 내장하지 않는다. 플러그인 계약에 동기 술어 컴파일을 더한다.

```ts
compile(schema):      (value) => Promise<Errors | null> | Errors | null  // 전체 검증, 에러 수집
compileGuard(root, pointer): (value) => boolean                           // 동기, 첫 실패에서 중단
```

- 가드는 **동기 전용**이다. 비동기 포맷·키워드는 가드에서 지원하지 않는다고 계약에 명시한다.
- 가드 안의 `$ref`가 루트 정의를 가리킬 수 있으므로 루트 문맥에서 컴파일한다. 떼어 낸 `if`는 `$ref` 때문에 단독 컴파일이 실패하므로 가드는 사본(작성 스키마에서 키워드 위치의 그룹 객체 셋을 지운 복사본, 08 §3.4)의 루트와 위치를 받는다(아래 '가드를 컴파일하는 방식', 16라운드 실행 확인).
- 캐시는 코어가 검증기 인스턴스마다 WeakMap<작성 루트, { 사본, 가드 표 }>로 든다(16라운드 편집자 결정, 답 10으로 확정). 캐시의 키가 작성 루트이므로 같은 검증기 인스턴스를 쓰고 같은 스키마 객체로 만든 폼 인스턴스들이 컴파일을 공유한다(`validatorFactory`로 폼마다 다른 인스턴스를 주면 공유하지 않는다). 플러그인의 `compileGuard`는 가드 캐시를 들지 않고, 사본 루트의 등록(루트마다 한 번의 `addSchema`와 고유 키 배정)은 플러그인의 검증기 인스턴스가 든다(ajv는 같은 키의 재등록에 실패한다). `$id`가 있는 사본 루트는 고유 키를 주어도 `$id`로 충돌하며(ajv 8.17.1 실행 확인), 그 처리는 PR-4가 정한다(08 §17.2).
- 조건부 스키마를 쓰는 폼에서 검증기가 등록되지 않았으면 조건부 장치는 동작하지 않고 경고를 낸다(ADR 0014 제안 3판이 대체한다. 확정 뒤 갱신). `ValidationMode.None`인 폼도 조건부를 쓰려면 플러그인 등록이 필요하다.
- 플러그인 패키지들이 변경 범위에 들어간다.
- Form 속성 `validatorFactory`는 유지하고 넓힌다(14라운드 답 O-7: '플러그인을 통한 전역 속성이 아니라 특정 커스텀 검증기 등을 추가한 커스텀 인스턴스 주입기'). 플러그인은 전역 기본이고 속성은 그 폼의 검증기 인스턴스이며, 같은 계약(`compile` + `compileGuard`)을 받고 플러그인보다 앞선다. 미등록 판정은 둘을 함께 본다.

### 검증기의 설정 (`reviews/round-1.md` R1)

- 서버와 검증기 설정(방언, format 검사, 커스텀 키워드)을 맞추는 것은 소비자의 책임이다. 수단은 이미 있는 `bind(instance)`다. 기본값(`allErrors`, `strictSchema: false`, `validateFormats: false`)은 바꾸지 않는다. format 검사는 소비자가 의지적으로 켠다.
- 제안(미수락): 플러그인이 자기 방언을 선택적으로 선언하고, 스키마의 `$schema`와 어긋나면 개발 모드에서 **경고만** 낸다. `$schema` 없는 2020-12 스키마의 `dependentRequired`가 draft-07 엔트리에서 조용히 무시되는 부류의 사고를 싸게 잡는다.

### 가드의 컴파일 비용 (`reviews/round-1.md` §2, R18)

AJV에서 가드의 호출은 싸고(좁은 가드 5–58 ns, 루트에 걸린 가드 200개를 키 입력마다 전부 돌려 7.9 µs) 비싼 것은 **컴파일**이다(가드 하나에 70–270 µs, 200개면 폼 생성 시점에 14–54 ms). 컴파일은 늦추고(가드가 처음 필요해질 때), 중복을 없애고, 같은 스키마로 만든 폼 인스턴스들이 공유해야 한다(ADR 0014 제안 3판이 대체한다. 확정 뒤 갱신). 가드를 떼어낸 새 객체로 컴파일하면 검증기의 객체 identity 캐시가 빗나가므로, 작성된 스키마 안의 위치로 식별한다(위 '결정' 절) — `$id` 기저 URI와 `$dynamicRef`의 문맥 문제도 함께 걸려 있다(`reviews/round-1.md` §7-6).

인터프리터형 검증기는 같은 작업이 약 70배 느리고 호스트 객체의 폭에 비례한다(`@cfworker/json-schema`: 가드 200개에 578 µs, 아이템 10,000개를 훑는 `contains` 가드 하나에 4.5 ms). 플러그인으로 허용하되 성능 예산은 AJV를 기준으로 잡는다(ADR 0009).

## 합의 근거

- 검증기 설정은 소비자의 책임 — 소유자: "플러그인에서 인스턴스를 수정하거나 설정을 주입할 수 있게 되어 있다. 기본값이 그런 거고. 기본값을 바꿔도 되지만 그건 사용자가 의지적으로 켜야 한다."

- 검증기 미등록 시 "조건부 비활성 + 경고" — 소유자: "동의. 단, 그럼 플러그인도 변경 범위에 포함해서, error 처리를 생략한 단순 검증 기능도 제공하도록 하자."
- 가드는 동기 전용 — 소유자: "가드는 동기로 해도 될 것 같다."

## 기각한 대안

- **작은 검증기를 내장하고 플러그인이 있으면 그것을 쓴다.** 같은 개념에 평가기가 둘이면 서로 다른 답을 낼 수 있다. 현재 구조에서 이미 확인된 문제다(`requiredFactory`와 표현식 컴파일러, `01-current-structure.md` §3).
- **AJV 내장.** 번들이 커지고 플러그인 분리의 장점이 없어진다(소유자의 판단).

## 결과

- `@cfworker/json-schema`는 내장 후보가 아니라 플러그인 구현체 후보 가운데 하나가 된다. codegen이 없는 인터프리터여서 CSP 환경에서 이점이 있다. 다만 현재 `&` 표현식이 `new Function`을 쓰므로 그 이점은 표현식 쪽을 함께 해결할 때만 온전하다. CSP-safe 검증기의 비교는 ADR 0010의 외부 조사 항목이다.
- 가드 평가 비용은 측정했다(위의 "가드의 컴파일 비용" 절, `reviews/round-1.md` §2). AJV에서는 호출이 아니라 컴파일이 비용이다. 초안에 적었던 "가드가 걸린 객체의 참조가 바뀌었을 때만 재평가한다"는 루트에 걸린 가드에 대해 **효과가 없다** — 어떤 쓰기든 루트의 참조를 바꾼다. 효과가 있는 것은 변경 경로 → 가드의 역색인이고, 그것이 필요한지는 검증기에 달려 있다(ADR 0005 §2, 0009).

## 되돌림 가능성

중간. 계약에 메서드를 더하는 것이므로 되돌리기는 쉽지만, ADR 0002가 이 메서드에 기댄다.

## 가드를 컴파일하는 방식 (`reviews/round-2.md` S12)

가드를 스키마에서 **떼어 내** 컴파일하면 실제 스키마에서 throw한다: 떼어 낸 가드 안의 `$ref: '#/$defs/…'`는 풀리지 않고, 루트를 `$id`로 다시 등록하면 "already exists"가 난다(같은 스키마로 만든 폼 N개, `reset()`으로 트리를 다시 만들 때). 동작이 확인된 방식은 루트를 한 번 등록하고 가드를 **루트 안의 위치로** 가리키는 것이다 — `addSchema(root)` 뒤에 `compile({ $ref: 'root#/allOf/0/if' })`. 공허한 참의 의미도 보존된다(실행). 플러그인 계약은 떼어 낸 서브스키마가 아니라 (루트 스키마, 위치)를 받는 형태가 되어야 하고, 컴파일 결과는 작성된 스키마 객체를 키로 폼 인스턴스 사이에 공유한다.

함께 확인된 것:

- 가드용 인스턴스는 첫 실패에서 멈춰야 하는데(`allErrors: false`) Ajv에서 그것은 인스턴스 옵션이다. 검증용과 가드용 인스턴스의 나머지 설정(format, 커스텀 키워드, 방언)을 같게 유지하는 규칙을 플러그인이 가져야 한다. `bind`는 모듈 전역이어서 설정의 단위가 폼이 아니라 프로세스다.
- 컴파일의 실패(지원하지 않는 정규식 등)를 폼 생성의 실패로 둘 것인가. Python 정규식 `(?i)…`은 Ajv 컴파일이 throw한다.
- 조건부 폼의 생성은 현재 구현보다 1.7배 느리다 — 가드 200개에 22.4 ms(ADR 0009).
