# ADR 0007 — 작업 루프: 표시 → 계산 → 커밋, 그 뒤에 통지와 검증

상태: 일부 수락. 가드가 보는 값과 순환의 처리는 수락. 단계의 구성은 제안(소유자가 방향 — Fiber 방식, 라이프사이클의 단일화 — 에 동의했고 세부 단계 구성에 대한 명시적 동의는 아직 없다).

## 변경 이력

- 2026-09-22 — 상한에 걸렸을 때의 처리를 "쓰기를 버리고 throw"에서 "값은 받아들이고 형상만 고정, 개발 모드에서 에러"로 바꿨다. 이유: 2라운드 검토에서 세 리뷰어가 독립적으로 "비제어 입력의 DOM은 이미 바뀌었는데 트리만 되돌아간다"를 지적했고, 소유자가 입력을 막지 않는다는 원칙을 밝혔다.
- 2026-09-22 — 1차안("Write → Resolve → Reconcile → Derive → Commit을 고정점에 이를 때까지 도는 사이클, 가지치기는 값의 삭제")을 대체했다. 이유: 적대적 검토 R6(진동), R7(형제 순서에 따른 결과), R8(입력 도중의 데이터 파괴)(`reviews/round-1.md`). 검토가 제안한 정적 순환 금지에 대해 소유자는 런타임 상한을 택했다.

## 합의 근거

- 라이프사이클 — 소유자: "마이크로태스크와 매크로태스크 기반의 라이프사이클을 노드 내부에서만큼은 원칙에 맞는 직관적인 데이터 흐름을 가졌으면 한다. 지금은 서로 막 주고받는 게 많다." / "react 파이버처럼 node가 동작하도록."
- 가드가 보는 값 — 소유자: "가드는 방출 값을 보는 게 맞다. 빈 문자열을 '있다'고 보는 게 오히려 이상하다. 그렇게 처리할 거면 omitEmpty를 끄면 되고, 그럼 방출값으로 통일해도 일정하다."
- 순환 — 소유자: "injectTo의 무한루프나 derived 무한루프 방어처럼 했으면 한다. 미리 알고 처리한다기보단, 몇 회 루프를 돌면 경고하고 error를 throw하도록. react의 hook처럼. 추가적인 방어를 해도 되는데 애드훅하게 하는 것보단 돌려보고 터지는 걸 개발 단계에서 알려주는 게 낫다."

## 맥락

현재 복잡함의 원인은 내부 로직이 이벤트를 구독해서 상태를 움직인다는 점이다(`01-current-structure.md` §5). BranchStrategy가 자기 host의 `UpdateComputedProperties`를 구독해 분기를 바꾸고, computed 의존성은 `UpdateValue`를 구독하며, `oneOf`와 `active`가 서로 다른 라이프사이클을 탄다. 이를 막으려고 불린 여섯 개가 쌓였고, 결과가 원인보다 먼저 배달되는 역전이 실측됐다.

## 결정

쓰기(또는 쓰기의 묶음)마다 다음을 **동기로, 한 곳에서, 고정된 순서로** 돈다.

```
1. 표시      쓰기를 받은 노드의 원본을 보류 상태로 바꾸고, 조상 방향으로 dirty를 올린다.
2. 계산      (패스) dirty가 있는 서브트리만 방문한다.
   begin     위 → 아래. 입력의 참조가 바뀐 가드만 다시 평가해 활성 자식 집합을 정한다.
             처음 활성이 된 노드에 원본이 없으면 기본값을 넣는다(자동 쓰기).
   complete  아래 → 위. 활성 자식만으로 방출 값을 메모한다(omitEmpty·omitTrailing 등의 정제 포함).
             바뀐 자식이 없으면 이전 참조를 그대로 둔다. & 식도 여기서 계산한다.
   가드는 방출 값을 본다. 한 패스가 방출 값을 바꾸면 그 값으로 가드를 다시 본다 — 패스를 되풀이한다.
   패스 수가 상한을 넘으면 값은 받아들이고 형상만 직전 커밋의 활성 집합으로 고정한다. 개발 모드에서는 에러를 낸다.
3. 커밋      보류된 원본과 새 메모를 확정한다. 바뀐 노드를 트리 순서로 모은다.
───────────────────── 여기까지 동기. 아래는 경계 ─────────────────────
4. 통지      루트 디스패처가 1회 방출한다 (ADR 0008). 구독자는 언제나 커밋된 상태만 본다.
5. 검증      validator(작성된 스키마, 방출 값). 비동기 허용. 판정은 그 값의 revision에 묶인다.
```

### 원칙

- **노드 내부(1–3)는 동기·단방향·고정 순서다.** 비동기는 경계(4–5, React, `onChange`)에만 있다. `setValue`가 반환되면 트리는 커밋된 상태다.
- **이벤트는 출력 전용이다.** 어떤 내부 로직도 이벤트를 구독해서 상태를 바꾸지 않는다.
- **`if`/`then`, `oneOf`/`anyOf`, `&active`는 모두 같은 begin/complete를 탄다.** 라이프사이클이 하나다.
- **비활성화는 값의 삭제가 아니라 방출에서의 제외다**(ADR 0006). 조각이 꺼져도 노드의 원본은 남는다.
- **가드는 방출 값을 본다.** 검증기가 보는 값과 같다. 형상과 판정이 어긋날 수 없다. 빈 문자열을 "있다"로 다루고 싶은 작성자는 `omitEmpty`를 끈다.
- **배치**는 표시 N번에 계산·커밋 1번이다.

### 순환

정적 분석으로 막지 않는다. `injectTo`·derived의 무한 루프 방어, React의 "Too many re-renders"와 같은 방식이다.

- 패스 수에 상한을 둔다. 상한은 **형상 계산**(어떤 조각이 켜져 있는가)이 수렴하지 않을 때만 걸린다. 유효성 위반과는 무관하다 — 유효하지 않은 값은 언제나 그대로 들어가고 에러로 보인다.
- **상한에 걸려도 쓰기를 버리지 않는다.** 값(원본)은 받아들이고, 형상만 직전 커밋의 활성 집합으로 고정해 커밋한다. 비제어 입력의 DOM과 노드의 원본이 어긋나지 않고, 쓰기를 거부했다는 신호를 따로 둘 필요가 없다. 소유자: "상한 초과가 되면 쓰기가 막히나? 값은 들어가고 유효성 검증 오류가 나는 것 아닌가." / "어지간하면 입력을 막지 않고 error를 보여주려고 한다."
- 개발 모드에서는 **어느 가드가 계속 뒤집혔는지**를 담아 에러를 낸다(커밋한 뒤에, 동기로). 프로덕션에서는 throw하지 않고 콘솔 에러만 남긴다. 소유자: "당연히 개발 모드 한정. 어차피 터지면 리얼에 나가면 안 된다." 현재의 `INFINITE_LOOP_DETECTED`는 마이크로태스크 안에서 터져 호출자의 `try/catch`가 잡지 못한다(R6, 실측).
- 대표적인 진동: `if: { not: { required: ['x'] } }, then: { properties: { x: { default: 1 } } }` — 가드가 자기가 존재를 정하는 필드를 읽는다.

**알려진 한계 (R7).** 고정점이 둘 이상인 스키마는 터지지 않고 하나로 정착한다 — `a.active = b가 없을 때`, `b.active = a가 없을 때`는 형제의 선언 순서에 따라 `{a}` 또는 `{b}`가 된다. 결과는 선언 순서에 대해 결정적이지만 유일하지 않다. 원본은 노드에 남으므로 사용자 데이터가 파괴되지는 않는다. 추가 방어가 필요하면 개발 모드에서 형제 순서를 뒤집어 한 번 더 돌려 결과가 갈리는지 알리는 방법이 있다(검토의 제안, 미채택).

## 결과

- 잠금용 불린들이 필요했던 이유가 없어진다.
- 노드 트리 테스트에서 마이크로태스크를 flush할 필요가 없다.
- "한 번의 쓰기가 두 번 배달된다", "결과가 원인보다 먼저 배달된다"가 구조적으로 사라진다.
- 소유자가 라이프사이클을 위의 그림 한 장으로 읽을 수 있다(G5).
- Q3(편집 중 상태와 가드가 보는 값)이 닫혔다.

## 미결

- **값이 아닌 입구 (R15).** `setState`(dirty/touched — `Touched`는 `requestAnimationFrame` 콜백에서 온다)와 명령 시그널은 쓰기가 아니다. 1단계 옆으로 들어와 계산을 건너뛰고 커밋에서 집계하는 안이 있다. `globalState`의 OR 누적을 플래그별 카운터로 바꿀지.
- **`RequestRefresh`의 규칙 (제안).** 소유자: "비제어 컴포넌트에 이미 작성된 값이나 데이터를 reset하는 인터페이스가 이미 있다. 강제로 tick 버전을 올려서 해결하는 방법. 방법은 있다. 잘 설계해 보라." → 규칙 하나로 둔다: **커밋된 원본이 "그 노드의 입력이 방금 보고한 값"과 다른 노드에만 `RequestRefresh`를 보낸다.** 타이핑은 같으므로 보내지 않는다(캐럿·IME 보존). 외부 `setValue`·reset·기본값 주입·`derived`·`injectTo`가 바꾼 노드에는 보낸다. 타이핑한 키 입력이 다른 노드의 조각을 뒤집어도 타이핑한 노드는 리마운트되지 않는다. 호출자가 `Refresh` 비트를 실어 보낼 필요가 없어진다 — core가 누가 그 노드의 값을 바꿨는지로 판단한다(R15, `open-questions.md` Q6). 상한에 걸린 경우는 값을 받아들이므로 DOM과 원본이 같고 Refresh가 필요 없다.
- **유효 스키마의 변경을 알리는 이벤트가 없다.** `NodeEventType`에 추가할지.
- **검증은 폼 전체 크기에 비례한다 (R19).** 입력 경로에서 어떻게 떼어 낼지 — 디바운스, 유휴 시간, 제출 시의 새 검증. `isValid`는 판정의 revision이 현재와 같을 때만 참이다(R2).
- **배열 구조 변경 API**(`push`/`remove`/`clear`)는 지금 Promise를 돌려준다. 1–3이 동기이므로 동기 API가 된다. 파괴적 변경이다.
- `injectTo`는 파생이 아니라 쓰기다. 작업 루프의 어디로 들어오는가.
- 패스 상한의 값.
