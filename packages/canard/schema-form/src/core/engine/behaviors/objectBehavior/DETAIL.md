# objectBehavior 계약

## Requirements

branch와 terminal은 같은 객체 종류의 서로 다른 소유 방식입니다. branch는 선언된 자식의 방출을 합성하고, terminal은 통째 값을 불투명하게 취급합니다. 전략을 바꾸어 값 내부의 선언을 실행하면 입력 수명과 검증 전용 스키마의 의미가 달라집니다.

## API Contracts

행의 공통 경계는 [behaviors 계약](../DETAIL.md)을 따릅니다. 분배·부분 쓰기·비객체 조상의 승격과 채움은 [settle 계약](../../settle/DETAIL.md)이 소유하며, 이 행의 투영에서 대신 수행하지 않습니다.

## Acceptance Criteria

### NODE-021 — 객체의 자식은 선언에서 옵니다

객체 branch의 자식 선언은 값의 키와 독립적입니다. 비객체 원본 아래에도 계산할 자식이 있지만, 투영은 그 원본을 그대로 방출하고 자식 방출을 섞지 않습니다. null을 빈 객체로 바꾸거나 화면의 자식이 존재한다는 이유로 부모 값을 복구하면 입력자가 준 값이 말없이 달라집니다.

### VALUE-034 — 생략은 방출만 바꿉니다

branch의 빈 합성은 빈 객체이며, omitEmpty가 켜져 있을 때 빈 객체 방출을 생략합니다. 생략 때문에 원본·자식 상태를 지우지 않습니다. 비객체 원본은 이 빈 객체 합성과 구별해 그대로 투영해야 null 같은 명시 값이 사라지지 않습니다.

### object-branch — 키 순서는 값 계약입니다

propertyOrder, 각 이름의 첫 선언 전순서, 남은 extras의 own-key 순서를 지킵니다. 정수 모양 키는 ECMAScript의 열거 규칙을 따릅니다. 현재 활성 template의 위치를 이름의 첫 위치로 대신하면 동명 이종 분기를 바꿀 때 키 순서까지 흔들립니다. 선언 밖 키를 버리거나 활성 자식이 생략한 키를 extras로 되살리지 않습니다.

같은 키와 값에는 이전 합성 참조를 재사용합니다. 형상·유효 스키마·extras의 동일성이 증명될 때만 재계산 자식을 검사하고, 변경 시 얕은 사본을 만듭니다. 검사량이 재계산 자식 수에 비례해도 사본의 시간과 메모리는 객체 키 수에 비례합니다. 키 집합이나 순서의 증명이 깨지면 전체 순서 합성으로 돌아가 누락·삽입을 놓치지 않습니다.

### object-active-order — 기존 순서 색인은 증명으로만 사용합니다

기존 이름 색인이 활성 이름을 모두 포함할 때만 활성 이름을 첫 선언 순위로 정렬합니다. 색인이 없거나 불완전하면 선언 전체를 순회합니다. 이 선택은 비활성 선언 방문을 줄이기 위한 것이며, 별도의 상주 색인을 만들거나 preferred·extras·예약 키·NaN·같은 결과 참조를 바꾸는 근거가 아닙니다.

### object-first-assembly — 최초 합성도 같은 순서를 지킵니다

원본 합성·extras·선호 순서가 없고 선언과 자식의 이름·순서가 맞는 최초 합성은 한 번의 순회로 결과와 증명을 만듭니다. 선언도 자식도 없는 extras 전용 최초 합성도 중간 이름 집합 없이 직접 조립합니다. 증명이 없으면 일반 합성으로 돌아가야 Map·Set 할당 절감 때문에 생략과 키 순서가 달라지지 않습니다.

### object-key-identity — 예약 이름은 데이터입니다

자기 `__proto__` 키도 데이터 속성으로 보존합니다. 일반 대입으로 프로토타입을 바꾸거나 복사 최적화에서 키를 잃지 않습니다. 얕은 복사의 V8 빠른 속성 한계는 엔진별 최적화 이유이며, 사본의 키·순서·값 계약을 바꾸는 기준이 아닙니다.

### object-terminal — 통째 값의 내부는 정규화하지 않습니다

terminal은 자식을 만들지 않고, 생략되지 않는 통째 원본의 참조를 유지합니다. 내부 undefined·비유한 값 등을 고쳐 JSON 왕복을 맞추지 않습니다. 내부까지 교정하면 호출자 값과 편집 상태가 달라지며, 메모리 값과 직렬화 뒤 검증이 다를 수 있는 한계는 [validation 계약](../../validation/DETAIL.md)에 둡니다.
