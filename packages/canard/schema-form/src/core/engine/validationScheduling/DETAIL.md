# validationScheduling

## Requirements

로드의 일회성 슬롯과 쓰기의 연속 입력 주기는 화면에 실행 기회를 양보하는 같은 시간 정책을 사용합니다. 시간 정책을 검증 상태와 분리하여 표시 보류·요청 대상·최신성 판단이 프레임 제어에 섞이지 않게 합니다. 단조 시계는 호출자가 제공하고 호스트의 프레임 지원·가시성은 예약 시점마다 확인합니다.

디바운스는 FieldInput이 소유합니다. 엔진은 입력 종료만 기다리지 않고 연속 입력 중에도 실제 실행 시작 기준 100ms 상한을 검사하여 판정을 무기한 미루지 않습니다. 동기 값 정착·사건·onChange를 늦추는 정책으로 확대하지 않습니다.

## API Contracts

run의 boolean은 실제 작업 시작 여부이며 비동기 판정의 완료 여부가 아닙니다. false인 호출은 마지막 시작 시각을 옮기지 않아, 실행하지 못한 시도로 상한을 계속 연장하지 않게 합니다. 콜백의 실패를 입력 판정으로 바꾸거나 삼키지 않으며 실패 보고는 호출자가 소유합니다.

시간 계층은 검증 모드·stamp·노드·커밋·오류·요청 대상을 읽지 않습니다. [검증 계약](../validation/DETAIL.md)이 검증 요청의 유효성과 결과 수명을, [루트 로드 계약](../../../providers/RootNodeContext/DETAIL.md)이 슬롯의 로드 정체성과 모드별 작업을 소유합니다. 일회성 슬롯은 외부 취소 핸들을 반환하지 않으므로, 더는 유효하지 않은 로드의 실행을 막는 일도 호출자에게 남깁니다.

### scheduling-cancel-owner — 실행 설정 수명

cancel은 영구 취소입니다. 재활성화할 호출자는 취소한 cadence 참조를 버리고 새 인스턴스를 만듭니다. load와 activation의 단일 유효 슬롯·토큰·mode·epoch는 호출자가 소유하며 이 모듈에 노드나 모드 지식을 넣지 않습니다.

## Acceptance Criteria

### VALIDATE-052 — 연속 입력에서 실행 기회와 최신 요청을 함께 보존합니다

idle의 첫 요청은 다음 프레임 뒤 매크로태스크로 선행 실행합니다. 실행 직전까지 온 요청도 그 실행에 포함하고 연속 입력으로 다시 세지 않습니다. 실행 뒤 watch 프레임에 새 요청이 없으면 관찰을 끝내어 단일 입력에 추가 판정을 붙이지 않습니다.

실행 뒤 요청이 있으면 carry로 넘어가 요청이 계속된 프레임을 이월하고 첫 무요청 프레임 뒤 후행 실행합니다. watch에서 carry로 처음 넘어가는 프레임부터 마지막 실제 자동 실행 시작 이후 100ms를 검사하며, 상한 실행 뒤에도 watch로 돌아갑니다. 상한 실행이 마지막 요청을 포함했다면 다음 quiet 프레임에서 중복 실행하지 않습니다. 한 작업의 여러 쓰기를 합치면서 연속 입력의 후행 판정을 잃지 않기 위한 정책입니다.

### scheduling-slot — 일회성 실행의 경주를 한 번으로 닫습니다

보이는 문서에 프레임 요청·취소 API가 모두 있으면 프레임 뒤 매크로태스크와 100ms 타이머를 경주시켜 먼저 도착한 경로에서 한 번 실행합니다. 승자는 패자의 프레임·타이머·게시한 작업을 취소하며, 전역 API가 바뀌어도 예약한 호스트의 취소 함수를 사용합니다. 프레임이 오지 않아 로드 준비가 영구히 대기하거나 늦은 콜백이 같은 작업을 다시 실행하는 일을 막습니다.

### scheduling-cadence — fallback과 취소는 남은 작업을 제한합니다

요청 시 문서가 숨겨졌거나 프레임 요청·취소 API 중 하나라도 없으면 매크로태스크 하나로 합치고 carry를 하지 않습니다. 예약 뒤 프레임이 멈추면 100ms 타이머로 남은 요청을 처리하되, 새 요청 없는 watch는 실행 없이 끝냅니다. cadence의 cancel은 영구적이며 소유한 프레임·타이머·매크로태스크와 늦은 콜백을 무효화하여 폐기한 실행 수명이 되살아나지 않게 합니다.

### scheduling-limits — 예약 상한을 완료 시한으로 해석하지 않습니다

100ms는 실행 기회를 고르는 기준이며 입력부터 판정 완료·화면 표시까지의 최대 지연이 아닙니다. 느린 동기 검증기의 계산, 비동기 판정 시간, 메인 스레드 점유와 숨김 탭의 타이머 제한은 남습니다. 프레임 뒤 매크로태스크도 실제 paint 완료를 확인하는 장치가 아니므로 화면이 반드시 먼저 그려졌다고 약속하지 않습니다. worker·실행 분할·검증기 최적화를 이 시간 계층에 추가하지 않습니다.

매크로태스크는 winglet scheduler의 호스트 지원을 따릅니다. 네이티브 setImmediate·clearImmediate 쌍도 MessageChannel도 없는 환경을 자체 타이머 대체로 지원하지 않습니다. if 가드의 동기 컴파일과 명시적 validate·submit은 이 주기의 제어 밖이므로 자동 쓰기 예약을 개선했다고 그 비용까지 사라진 것으로 판단하지 않습니다.
