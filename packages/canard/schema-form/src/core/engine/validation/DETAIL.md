# validation 계약

## Requirements

같은 객체가 스키마와 데이터 위치에 함께 나타나도 변환 문맥별 복사본을 분리합니다. 각 문맥 안의 공유·순환 참조는 유지하며, 객체당 최대 네 문맥의 캐시 비용으로 데이터의 폼 그룹이 제거되거나 스키마 그룹이 남는 것을 막습니다.

검증은 작성 스키마와 방출 값의 관계를 판정합니다. 화면에 필요한 유효 스키마는 필드를 구성하기 위한 것이므로 검증의 기준으로 바꾸지 않습니다. 검증용 사본은 폼 전용 선언을 걷어 내되 작성자가 부여한 의미를 보존하는 경계입니다.

가드는 어떤 필드가 참여할지 정착 중에 답하고, 전체 검증은 그 결과로 만들어진 값을 판정합니다. 두 답의 의미는 같아야 하지만 필요한 시점은 다릅니다. 가드만 필요한 순간에 전체 검증까지 준비하면 화면 구성에 불필요한 일을 끌어들이므로 컴파일 수요를 분리합니다.

입력에 따른 자동 검증은 여러 요청을 묶어 실행할 수 있습니다. 실행 주기는 예약을 맡고, 이 도메인은 어떤 입력과 대상에 대한 답인지를 책임집니다. 뒤늦게 도착한 결과가 새 입력을 덮거나, 실행을 합치는 과정에서 먼저 요청된 대상이 빠져서는 안 됩니다.

화면에서 사라진 분기의 오류나 주인을 찾지 못한 오류를 표시에서 제외할 수 있어도, 그 이유로 검증기가 내린 판정을 통과로 바꿀 수는 없습니다.

오류가 존재하는 것과 보여도 되는 것은 별개의 사실입니다. 자동 검증을 기다리는 동안 표시 자격이 새로 생기면 묵은 오류가 새 입력의 답처럼 보일 수 있으므로 표시를 보류합니다. 검증 결과의 배달과 표시 보류의 해제는 React 렌더 횟수에 기대지 않고 엔진에서 관리합니다.

하지 않는 것: 대체 검증기나 AJV를 코어에 내장하지 않습니다. 동일한 조건을 서로 다른 평가기가 해석하면 필드 참여와 검증 판정이 갈라지며, AJV 내장은 번들 비용과 검증기 선택을 애플리케이션에 남겨 둔 플러그인 경계를 없애기 때문입니다.

인터프리터형 검증기도 같은 플러그인 계약으로 사용할 수 있지만 검증기 자체의 실행 비용은 그 구현이 책임집니다. 폼의 성능 판단은 AJV 기준과 구분해야 하며, 느린 검증기를 보완하려고 이 도메인에 조건의 의미를 다시 판정하는 장치를 두지 않습니다.

## API Contracts

검증 캐시 항목과 가드 결과의 선언은 검증 타입 계층이 소유합니다. 저장소와 읽기 함수가 같은 데이터 계약을 참조하여 저장소가 읽기 구현으로 되돌아가는 타입 순환을 막습니다.

검증 캐시를 공유하는 폼도 요청의 최신성과 실패 보고는 각자 소유합니다. 컴파일 실패를 공유한다는 이유로 다른 폼의 보고를 생략하거나, 하나의 폼을 해제하면서 다른 폼이 쓰는 등록을 제거해서는 안 됩니다.

명시적 검증의 호출자는 호출 시점 값의 판정을 기다립니다. 화면에 배정할 수 없을 만큼 오래된 답과 호출자에게 돌려줄 답을 구별해야, 비동기 검증 중 편집이 계속되어도 호출의 의미가 유지됩니다. 결과의 사건 배달은 요청자의 콜백에 맡겨 쓰기와 검증의 사건 순서를 각 요청자가 유지하게 합니다.

OnChange의 표시는 마지막 보류 해제 이후 계속 적격이었던 오류만 유지하고, 중간에 부적격이 되면 다음 해제를 기다립니다. 숨김은 즉시 적용하며 조용한 변경도 판정 없이 영구히 대기하지 않습니다. 해제 알림에서 새 쓰기가 시작될 수 있으므로, 그 쓰기의 표시 이력을 같은 해제에서 지우지 않습니다.

검증의 실패는 입력의 오류 목록과 분리합니다. 판정할 수 없다는 사실을 빈 목록으로 바꾸면 호출자는 정상 입력과 실행 실패를 구별할 수 없고, 필드 오류로 바꾸면 사용자가 입력을 고쳐 해결할 수 있는 문제처럼 보이기 때문입니다.

### validation-mode-lifetime — 실행 설정 수명

실효 모드는 off·manual·automatic으로 비교합니다. 같은 모드와 OnChange 비트 조합 replay는 raw 값만 저장하며 epoch·cadence·compile·오류 참조를 유지합니다. 다른 모드로 전환하면 epoch와 stamp를 올리고 cadence를 cancel한 뒤 참조·run·pending 대상·running·entry stamp를 비웁니다. OnChange 이탈은 표시 이력과 quiet token을 지우고 새 불투명 정책을 설치한 뒤 release를 알립니다. None은 검증이 만든 오류만 비우며 외부 오류를 유지합니다. 다른 전환은 오류를 유지합니다. 결과 게시에는 시작 root·load·epoch·stamp·commit을 검사하고 release 뒤 최종 배달 직전 다시 검사합니다. 명시적 검증과 로드·활성화 실행 실패의 보고 수명은 시작 root와 실효 모드 epoch입니다. 루트가 교체·은퇴하거나 epoch가 바뀌면 늦은 실패를 보고하지 않으며, 같은 루트·epoch의 요청 대체나 같은 루트 reset만으로 기존 실패 보고를 막지 않습니다. 자동 cadence의 기존 최신 요청 선택과 컴파일 실패의 로드별 상태 보호는 유지합니다. 명시적 Promise는 게시·보고 여부와 별개로 자체 결과나 거부로 정착합니다. compile 실패·보고 상태와 캐시는 mode toggle로 초기화하지 않습니다.

## Acceptance Criteria

### VALIDATE-001 — 작성한 의미를 기준으로 판정합니다

검증에는 작성 스키마의 검증용 사본과 방출 값을 사용하고, 화면에서 병합한 스키마나 검증만을 위한 추가 값을 사용하지 않습니다. 추가 검사를 두더라도 원래 검증의 실패를 성공으로 바꾸지 않아야 같은 검증 설정의 외부 소비자와 판정이 어긋나지 않습니다.

### VALIDATE-003 — 검증기 설정은 소비자가 맞춥니다

서버와 방언·포맷·사용자 키워드를 맞추는 일은 소비자의 책임이며, bind(instance)로 선택한 검증기 설정을 전달합니다. 플러그인은 모든 오류를 수집하고 엄격한 스키마 검사와 포맷 검사를 끈 기본값을 유지하며, 포맷 검사는 소비자가 명시적으로 켜도록 하여 폼 계층이 검증 범위를 임의로 바꾸지 않게 합니다.

### VALIDATE-004 — 사본의 제거 범위를 닫아 둡니다

폼 전용 선언은 검증 규칙이 아니라 화면 객체를 담을 수 있으므로, 검증기의 컴파일이 순환 참조나 React 값까지 처리하지 않도록 키워드 위치의 controls·options·presentation만 사본에서 제거합니다. 알 수 없는 소비자 키워드는 검증기의 확장일 수 있어 제거하지 않으며, 데이터 위치의 같은 이름도 검증 규칙으로 해석하지 않습니다.

### VALIDATE-007 — 전송과 메모리 판정의 차이를 숨기지 않습니다

방출 값을 직렬화한 뒤에도 같은 판정이 나도록 입력을 구성해야 하지만, 터미널 객체·배열과 union이 통째로 보관하는 값의 내부를 검증 계층이 정규화하지는 않습니다. 내부의 undefined나 JSON으로 표현되지 않는 값 때문에 두 판정이 달라질 수 있다는 한계를 남겨, 검증 과정에 값 변환을 끼워 넣어 편집 상태를 바꾸지 않게 합니다.

### VALIDATE-016 — 가드는 정착을 기다리게 하지 않습니다

가드는 동기 boolean으로 답하며 비동기 포맷·키워드를 지원하지 않습니다. 필드 참여를 결정하는 중에 비동기 결과를 기다리면 같은 쓰기의 값과 형상이 서로 다른 시점에 확정되기 때문입니다.

### VALIDATE-017 — 가드의 참조 문맥을 보존합니다

코어는 가드 컴파일에 사본 루트와 작성 위치를 함께 제공하여 상대 참조와 루트 정의의 문맥을 보존합니다. 플러그인이 문맥에 의존하지 않는 조건을 직접 컴파일하는 최적화를 하더라도, 부분 스키마의 모양만으로 바깥 문맥을 버려도 된다고 판단해서는 안 됩니다.

### VALIDATE-018 — 사본과 가드의 캐시는 코어가 소유합니다

코어는 검증기 인스턴스마다 작성 루트 객체를 기준으로 사본과 가드를 공유합니다. 조회용 색인은 작성 루트를 약한 참조로 가지므로 색인 때문에 스키마가 살아남지는 않습니다. 반면 커밋된 트리가 쓰는 루트와 최근에 해제한 루트는 재마운트 때 다시 컴파일하지 않도록 수명 원장이 일부러 강한 참조로 붙잡으며, 그 상한과 해제 조건은 VALIDATE-021과 VALIDATE-045가 정합니다. 폼마다 같은 준비를 반복하지 않게 하려는 경계입니다.

### VALIDATE-019 — 가드의 재사용과 검증기의 등록을 구별합니다

가드의 재사용은 코어가 맡고, 사본 루트를 검증기 인스턴스에 등록하고 해제하는 일은 플러그인이 맡습니다. 전체 검증·가드·해제에 같은 사본을 건네어, 등록이 중복되거나 해제 대상이 실제 등록과 달라지지 않게 합니다.

### VALIDATE-021 — 재마운트 비용과 등록 수명을 함께 제한합니다

커밋된 트리가 쓰는 루트는 유지하고 마지막 사용이 끝난 루트는 제한된 최근 해제 목록에 보관합니다. 코어의 약한 참조만으로는 플러그인의 강한 등록을 회수할 수 없으므로 명시적으로 함께 해제하며, 짧은 재마운트마다 같은 스키마를 다시 컴파일하지 않게 합니다. 실행이 보장되지 않는 가비지 수거 알림을 등록 해제의 기본 경로로 삼지 않아 메모리 회수가 런타임의 수거 시점에 종속되지 않게 합니다.

### VALIDATE-026 — 알 수 없는 방언을 추정하지 않습니다

스키마와 검증기가 모두 방언을 선언했을 때만 불일치를 판단합니다. 선언이 없는 쪽을 추정하면 검증기가 지원하는 확장이나 기본 방언을 폼 계층이 잘못 제한할 수 있습니다.

### VALIDATE-033 — 가드와 전체 검증은 같은 의미를 사용합니다

플러그인은 가드에서 첫 실패에 멈추고 루트 메타 스키마 검사는 전체 컴파일에 맡기되, 포맷·사용자 키워드·방언·소비자의 엄격 옵션은 전체 검증과 같게 유지합니다. 검증 준비의 비용을 나누는 일이 필드 참여 조건을 몰래 완화하는 일이 되어서는 안 됩니다. 엄격 옵션 때문에 일부 가드가 컴파일에 실패하여 분기가 꺼질 수 있어도 이를 피하려고 가드에서만 엄격 옵션을 끄지 않습니다.

### VALIDATE-034 — 화면의 묶음을 검증 규칙으로 바꾸지 않습니다

사본은 작성된 required를 보존합니다. 가상 필드의 화면 구성을 검증 규칙으로 번역하면 서버와 공유하는 스키마의 의미까지 달라지므로, 필수 항목에는 화면의 가상 이름이 아니라 실제 저장 필드를 선언해야 합니다.

### VALIDATE-045 — 일반 축출과 같은 식별자 교체의 보호 범위를 구별합니다

검증기마다 최근 해제 루트는 일반 축출 시 여덟 개 이하로 줄이되, 커밋된 트리가 사용하거나 검증이 실행 중인 루트와 지금 항목을 설치하는 루트는 보존하고 보호에 따른 일시 초과를 허용합니다. 다만 같은 식별자의 새 등록이나 재시도를 위해 이미 해제된 루트를 정리할 때에는 실행 중 보호를 적용하지 않으므로 진행 중인 검증이 실패할 수 있으며, 이는 기존 등록이 새 등록을 막지 않게 하기 위한 예외입니다. 플러그인 등록과 코어 캐시를 함께 제거하여 해제된 자원이 재사용되지 않게 합니다.

### VALIDATE-046 — 같은 식별자가 다른 루트의 의미를 덮지 않습니다

같은 $id의 서로 다른 살아 있는 루트는 각각 자기 스키마로 판정하며, 플러그인이 등록을 격리하고 코어는 식별자를 고치지 않습니다. 새 트리의 채택은 전체 컴파일의 성공을 기다리지 않으므로 컴파일 실패를 이유로 이미 채택한 트리를 되돌리지 않습니다. 등록 격리는 참조 해석을 보존하기 위한 것이며, 컴파일 실패의 보고는 트리 교체와 별도의 책임입니다.

### VALIDATE-047 — 분리한 가드는 전체 검증의 조건과 동등합니다

가드가 쓰는 동적 앵커의 최초 바인딩이 모든 진입에서 같고, 작성 위치까지의 자원 사슬이 같은 동기 검증 문맥을 재현할 때 전체 검증의 if와 같은 답을 보장합니다. 한 위치를 서로 다른 동적 문맥으로 사용하는 경우나 최초 바인딩이 사슬 밖에 있는 경우까지 위치당 하나인 가드로 지원한다고 약속하지 않으며, 묶이지 않는 직접 참조와 비동기 선언은 거부될 수 있습니다. 플러그인이 명시한 앵커 해석의 지원 범위와 AJV 자체의 편차를 코어가 재해석으로 메우지 않아야, 하나의 캐시 항목을 서로 다른 조건의 판정에 잘못 재사용하지 않습니다.

### VALIDATE-048 — 공유의 단위는 구조가 아니라 정체성입니다

같은 검증기 인스턴스와 같은 작성 루트 객체를 사용하는 폼은 사본·가드·전체 컴파일의 결과와 실패를 공유하고, 구조가 같은 다른 객체는 공유하지 않습니다. 구조 비교로 합치면 소비자가 독립적으로 등록하거나 해제하려는 루트까지 같은 자원으로 취급하게 됩니다.

### VALIDATE-050 — 검증은 입력을 수리하지 않습니다

검증기와 가드는 참조로 받은 값과 사본을 변경하지 않으며, AJV 플러그인은 값 변환·기본값 삽입·추가 속성 제거 옵션을 켠 인스턴스의 바인딩을 거부합니다. 변경하는 사용자 키워드까지 런타임에 판별하지는 않으므로 소비자가 이를 피해야 하며, 이 경계를 유지해야 검증 전후 값과 정착 결과가 일치합니다.

### VALIDATE-051 — 값 전체를 보관하는 노드에도 내부 오류를 전달합니다

union의 형 오류와 자식 노드 없이 보관하는 값의 내부 오류는 해당 값을 편집하는 노드가 받으며 원래 오류 경로는 보존합니다. 비어 있지 않은 오류 경로는 절대 포인터여야 하며, 탐색을 멈출 때까지 확인하는 각 조각은 속성 이름 문자열로 파싱되어야 합니다. 조각 검사는 현재 노드가 터미널인지 확인하기 전에 하므로, `#/*/na%me`의 `*`나 같은 위치의 `..` 같은 연산자는 터미널 루트에서도 배정을 막고 오류는 전체 목록에 남깁니다. 이 조건을 통과한 내부 오류는 루트 여부와 관계없이 값 전체를 보관하는 노드가 받으며, `#/na%me`처럼 해독할 수 없는 퍼센트 이스케이프가 든 경로도 그대로 받습니다. 존재하지 않는 내부 입력을 만들거나 오류를 버리는 대신 편집 단위에 연결하되, 형 이외의 제약에 대한 판정은 검증기에 남겨 둡니다. 가지 노드만 거쳐 가는 경로에서 해석할 수 없는 경로의 오류는 어느 노드에도 배정하지 않고 `getErrors()`의 전체 목록에만 남깁니다(`utils/route/routeValidationIssues.ts`).

비어 있지 않은 `rejectedKey`를 가진 오류는 값 전체를 보관하는 노드에서 가장 가까운 가지 노드 조상으로 올라가 배정됩니다(`utils/route/routeValidationIssues.ts`). 그래서 루트가 아닌 터미널 객체는 거부된 키의 오류를 받지 않고 그 부모가 받으며, 같은 위치의 `rejectedKey` 없는 오류와 빈 문자열 `rejectedKey`를 가진 오류는 터미널 객체가 받습니다. 터미널 루트는 올라갈 부모가 없으므로 `rejectedKey`를 가진 오류도 루트가 받습니다.

### FRAGMENT-020 — 거부한 키의 해석은 플러그인이 맡습니다

거부된 키를 특정할 수 있을 때 플러그인이 rejectedKey를 제공하고, 특정할 수 없으면 호스트 오류로 남깁니다. 코어가 검증기별 오류 모양이나 스키마를 역해석하면 검증 방언마다 다른 형상 규칙을 중복 소유하게 됩니다.

### FRAGMENT-053 — 루트와 빈 이름 필드를 구별합니다

오류 경로의 빈 문자열은 루트이고 슬래시 하나는 빈 이름 자식이며, 없는 자식의 오류를 루트로 대신 배정하지 않습니다. 둘을 같은 주소로 취급하면 빈 이름 필드가 있는 스키마의 오류가 다른 편집 대상에 표시되므로, 정규화 뒤에도 이 차이를 보존합니다.

### ERROR-039 — 실행 실패를 입력 판정으로 전달하지 않습니다

검증기의 throw는 명시적 호출의 거부로 전달하고, 자동 실행에서는 오류 기록과 호출자 없는 실패 통로로 보고합니다. 실패를 onValidate의 입력 오류로 보내거나 코어가 소유한 프로미스를 미처리 거부로 남기지 않아야, 소비자가 입력 수정과 검증기 복구를 구별할 수 있습니다.

### ERROR-147 — 검증기 부재를 경고로 알립니다

검증 모드가 None이 아닌데 검증기가 없으면 개발 모드 콘솔과 등록된 onError의 경고 기록으로 알립니다. 검증을 수행하지 않은 상태를 유효한 입력으로 오해하지 않게 하되, 검증기를 생략한 폼 자체를 실행 실패로 처리하지 않기 위한 구분입니다.

### ERROR-148 — 검증기 부재는 트리마다 한 번 알립니다

검증기 부재 경고는 마운트나 트리를 재생성하는 reset에서 트리마다 한 번 전달하며, setValue나 같은 스키마의 reset으로 반복하지 않습니다. 값 변경은 검증기 구성을 바꾸지 않으므로 같은 설정 문제를 입력마다 새 경고로 보고하지 않게 합니다.

### ERROR-149 — 검증기 부재는 트리 준비 뒤에 전달합니다

마운트의 검증기 부재 경고는 준비 이펙트에서, 트리를 재생성하는 reset의 경고는 reset 사슬 끝에서 전달합니다. 경고를 받는 소비자가 준비되지 않은 트리나 reset 도중의 상태를 관찰하지 않게 하기 위한 시점입니다.

### ERROR-150 — 검증기 부재는 프로덕션 기본 출력을 만들지 않습니다

검증기 부재 경고는 프로덕션에서 기본 콘솔 출력을 만들지 않습니다. 애플리케이션이 검증기를 생략할 수 있으므로, 배포 환경의 진단 수집과 출력 여부는 소비자가 결정하게 합니다.

### ERROR-154 — 검증기 없이 조건을 임의로 통과시키지 않습니다

검증기가 없으면 if 조각을 끄고 트리마다 경고하여 조건을 평가하지 못했음을 드러냅니다. 대체 평가로 일부 키워드만 이해한 답을 내면 지원하지 않는 조건까지 정상적으로 판정한 것처럼 보이기 때문입니다.

### ERROR-155 — 컴파일 실패는 로드의 검증 불가 상태입니다

전체 컴파일 실패는 같은 로드에서 같은 거부 객체를 유지하고, 자동 수요의 오류 기록과 호스트 보고를 중복하지 않습니다. 명시적 호출에는 거부를 돌려주어 판정 부재를 숨기지 않되, 같은 원인 때문에 반복되는 실행을 새로운 장애처럼 보고하지 않습니다.

### ERROR-156 — 입력 변경으로 컴파일 실패를 재시도하지 않습니다

검증 불가인 로드에서는 OnChange 검증을 계속 예약하지 않습니다. 입력을 고치는 일로 스키마 컴파일의 실패가 해결되지는 않으므로, 복구는 등록 충돌 해소처럼 정의된 수요와 조건에서만 시도합니다.

### ERROR-157 — 검증 불가를 필드 오류에 섞지 않습니다

컴파일 실패는 노드의 errors에 넣지 않습니다. 사용자가 값을 수정하면 고칠 수 있는 오류와 검증 기반이 작동하지 않는 오류는 소비자가 다른 방식으로 처리해야 하기 때문입니다.

### ERROR-188 — 방언 경고가 실행 가능성을 단정하지 않습니다

선언된 방언의 불일치는 개발 모드의 경고로 알리고 프로덕션의 기본 출력이나 실행 거부로 바꾸지 않습니다. 선언 차이는 잘못된 설정을 찾는 단서이지만, 그 자체로 검증기가 해당 스키마를 평가할 수 없다는 증거는 아닙니다.

### ERROR-198 — 조건의 내용을 읽어 새 경고를 만들지 않습니다

공허하게 참이 되는 if를 폼이 찾아내어 경고하지 않습니다. 조건의 의미는 검증기가 소유하므로, 폼이 조건을 정적으로 해석하기 시작하면 별도의 불완전한 검증기를 갖게 됩니다.

### ERROR-201 — 등록 충돌과 다른 컴파일 실패를 구별합니다

중복 식별자 원인은 같은 루트 식별자를 보유한 다른 루트와 AJV 중복 등록 문구가 함께 확인될 때만 분류하고, 단어 duplicate만으로 추정하지 않습니다. 충돌이 해소된 뒤 전체 검증 수요에서 한 번 재시도하되 실패하면 원래 거부를 유지하며, 성공해도 다른 원인의 가드 실패나 이미 제공한 가드는 지우지 않아야 복구가 별개의 장애를 숨기지 않습니다. 문구의 부분 일치로 오분류될 수 있는 한계는 남으며, 원인 분류를 검증기의 일반적인 복구 가능성 보장으로 확대하지 않습니다. None과 OnRequest에서는 첫 전체 검증 수요가 오기 전까지 캐시된 중복 가드 실패가 남습니다.

### validation-guard — 조건을 평가하는 일과 진단을 분리합니다

가드의 실패를 저장하더라도 그 실패를 관찰할 폼의 진단 책임까지 캐시에 합치지 않습니다. 동일한 스키마를 재사용하는 폼이 자신의 조건 평가 실패를 놓치지 않아야 합니다.

### validation-route — 오류가 같아도 편집 대상은 다시 확인합니다

깊이 같은 판정에는 기존 오류 참조를 재사용하지만, 분기 전환이나 배열 이동으로 바뀐 배정 대상은 다시 확인합니다. 결과의 동일성과 화면의 동일성은 다르므로, 불필요한 알림을 줄이면서도 새 편집 대상의 오류는 갱신해야 합니다.

### validation-lifetime — 결과의 최신성과 요청 범위를 함께 보존합니다

오래된 결과는 배정하지 않으며, 대체된 실행의 요청 대상은 후속 실행에 인계합니다. 하위 검증이나 일부 대상의 초기화가 다른 영역의 판정까지 완료한 것으로 처리되면 아직 검증을 기다리는 필드가 누락되기 때문입니다.
