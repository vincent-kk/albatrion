# 네이티브 검증 연결 계약

## Requirements

주입한 인스턴스의 검증 의미를 보존하며 폼의 루트 수명은 애플리케이션의 스키마 등록 수명과 구별합니다.

## API Contracts

키워드가 던지거나 거부한 값은 컴파일에 사용하는 AJV 인스턴스의 생성자가 제공하는 ValidationError의 인스턴스일 때만 검증 issue로 변환합니다. errors라는 속성이나 AJV 표지 속성은 클래스의 정체성을 대신하지 않습니다. 다른 오류와 오류가 아닌 값은 같은 값으로 호출자에게 전달하여 실행 실패를 검증 실패로 숨기지 않습니다. 별도 설치된 같은 AJV 버전의 인스턴스를 주입해도 그 생성자의 ValidationError를 사용하므로 설치 사본에 따라 의미가 바뀌지 않습니다.

### 루트 소유권 상태 모델

애플리케이션 AJV는 플러그인에 대해 읽기 전용입니다. 폼 루트와 가드는 모두 플러그인 소유 컴파일러에서 컴파일하며 애플리케이션의 getSchema·compile·validate·addSchema·removeSchema·validateSchema를 호출하지 않습니다. 애플리케이션의 레지스트리·캐시·오류·생성 코드·규칙 객체는 폼의 생성과 해제로 바뀌지 않습니다. 폼 루트의 $id는 애플리케이션 getSchema에 나타나지 않으며 애플리케이션 removeSchema는 이미 만든 폼 함수를 제거하지 않습니다.

| 상태 | 소유자와 수명 | 불변식 |
| --- | --- | --- |
| 애플리케이션 프로필과 스키마 | 애플리케이션 인스턴스 | 플러그인은 레지스트리와 작성 스키마를 읽기만 합니다. |
| 인스턴스 원장 | realm의 인스턴스별 WeakMap | 같은 프로토콜의 사본·방언·어댑터가 등록 번호·finalizer·살아 있는 식별자 목록·풀을 공유합니다. |
| 등록 전 루트 | 호출자의 객체 identity | 어댑터 생성만으로 네이티브 컴파일러를 만들지 않습니다. |
| 등록된 루트 | 어댑터의 weak identity 표와 원장 | 작성 루트의 스냅숏, 전용 또는 풀 컴파일러, 선택적 가드 컴파일러를 보유합니다. 원장은 루트나 어댑터를 강하게 소유하지 않습니다. |
| 검증 완료 루트 | 해당 등록 | 성공한 검증 함수는 같은 객체의 재컴파일에 같은 함수로 반환합니다. |
| 해제된 루트 | 등록 없음 | 명시적 해제는 등록과 private 자원을 동기적으로 제거하며 반복 해제는 아무 일도 하지 않습니다. |
| 외부 스키마 수입 기록 | private 컴파일러 | 출처 레지스트리 항목과 스키마를 기록하고 다음 네이티브 컴파일 전 현재 출처와 대조합니다. |

| 이벤트 | 상태 전이와 공개 보장 |
| --- | --- |
| createValidator·bind | 어댑터 또는 선택만 준비하며 애플리케이션 인스턴스와 그 생성 코드 수는 변하지 않습니다. 거부된 bind는 기존 선택을 유지합니다. |
| compile(root), 첫 성공 | 현재 프로필을 private 컴파일러에 반영하고 충돌과 외부 수입을 검증한 뒤 스냅숏을 컴파일하고 함수를 캐시합니다. 실패는 캐시하지 않으며 애플리케이션 상태를 그대로 둡니다. |
| compile(root), 성공 후 반복 | release 전까지 같은 루트 identity의 캐시 함수를 반환합니다. 애플리케이션의 후속 변경을 재컴파일로 해석하지 않습니다. |
| compileGuard(root, pointer) | compile의 선행 여부와 관계없이 private 가드 컴파일러로 조건만 평가합니다. 루트 메타 스키마 검증은 전체 compile에서만 수행하며 guard의 기존 직접·문맥·동적 범위 한계를 유지합니다. |
| public createValidatorFactory | 호출자가 제공한 애플리케이션 인스턴스를 읽기 전용으로 다루며 공개 네이티브 비동기 의미와 오류 정규화를 유지합니다. |
| release(root) | 이 등록의 private 자원만 제거합니다. 이미 반환한 함수는 실행 가능하며 다른 살아 있는 루트나 애플리케이션 등록을 건드리지 않습니다. |
| 어댑터 또는 루트 수거 | 인스턴스 원장의 finalizer가 도달 불가능한 루트의 자원을 정리합니다. 수거 전에도 같은 $id의 새 폼은 충돌 격리 컴파일러를 사용하므로 성공 여부가 GC 시점에 의존하지 않습니다. |
| 새 등록 | 죽은 weak 참조를 정리합니다. 풀은 private 컴파일러 하나당 최대 64개의 서로 다른 루트를 허용하며 이후 새 컴파일러로 회전합니다. 같은 객체의 캐시 적중은 한도를 소비하지 않습니다. |
| 애플리케이션의 후속 등록·제거·교체 | 다음 실제 컴파일은 현재 규칙과 레지스트리를 읽습니다. 제거·교체된 외부 문서에 연결된 전이 참조와 생성 코드도 재사용하지 않도록 관련 컴파일 환경을 무효화합니다. 기존 반환 함수의 의미는 유지합니다. |

### 관찰 불변식

I1: 애플리케이션 연산만 실행한 쌍둥이 인스턴스와, 같은 연산 사이에 폼 연산을 끼운 인스턴스는 각 애플리케이션 연산의 반환·예외 종류와 메시지·errors 및 레지스트리 순서·캐시·생성 코드 크기가 같습니다. 플러그인은 애플리케이션이 아직 컴파일하지 않은 환경과 메타 검증 함수를 빌려 실행하지 않습니다. native 컴파일이 errors 등을 쓰는 규칙 정의와 검증 함수는 private 사본에서 준비하고 다음 컴파일 전 동기화합니다. 규칙 객체를 공유하는 최적화는 설치된 버전에서 이 불변식을 입증한 읽기 전용 부분에만 적용합니다.

I2: 실제 컴파일은 그 시점의 애플리케이션 옵션·format·keyword·메타 스키마·외부 자원을 봅니다. 문자열 별칭과 compound 문서의 embedded 자원은 애플리케이션을 컴파일하지 않고 레지스트리에서 해석하며 순환 별칭은 종료합니다. 이미 수입한 문서의 identity와 별칭 출처를 재확인하여 제거·교체된 문서와 그 전이 캐시를 쓰지 않습니다. 전체 애플리케이션 데이터 스키마를 매번 복사하지 않고 필요한 자원만 수입합니다.

현재 애플리케이션이 가진 정규화된 root 또는 embedded id와 폼 자원이 충돌하면 내용이 같을 때만 허용합니다. 다른 root 내용은 중복 id 오류, 다른 embedded 내용은 모호한 참조 오류로 거부합니다. 애플리케이션이 먼저 제거한 id는 충돌하지 않습니다. schemaId가 선택하는 legacy id 해석도 이 비교를 따릅니다.

I3: 폼 연산으로 애플리케이션에 남는 등록·캐시·생성 코드는 0개입니다. 풀·finalizer·id 충돌 정보는 어댑터보다 오래 사는 인스턴스 원장이 소유합니다. 폼끼리 같은 id를 가진 살아 있는 스냅숏은 private 컴파일러를 분리하여 모두 유지합니다. 명시적 해제는 GC를 기다리지 않으며, finalizer가 없거나 아직 실행하지 않은 호스트에서도 남은 등록은 다음 폼의 컴파일을 막지 않습니다.

### 유지하는 한계

- 작성 루트는 컴파일 후 변경하지 않습니다. 이미 반환한 validator와 guard 및 같은 객체의 캐시 함수는 스냅숏이므로 애플리케이션의 후속 규칙·스키마 변경을 반영하지 않습니다.
- FinalizationRegistry가 없으면 자동 정리를 보장하지 않습니다. release가 필요한 호스트에서는 호출자가 명시적으로 해제하며 죽은 weak 항목은 다음 등록에서 정리합니다. WeakRef도 없으면 명시적 수명 관리만 보장합니다.
- 코어의 어댑터별 8개 recent 루트 정책은 유지합니다. 플러그인은 코어 캐시를 합치거나 어댑터별 옵션을 덮어쓰지 않습니다.
- 사용자가 제공한 callback이 외부 closure나 전역 상태에 쓰는 부수효과는 사용자 코드의 실행 의미이며 격리하지 않습니다. 플러그인과 native compiler가 수행하는 상태 변경은 I1의 private 소유 경계를 따릅니다.

## Acceptance Criteria

### keyword-exception-identity — 실행 오류와 검증 실패를 구별합니다

- 동기·비동기 키워드와 공개 진입점에서 네이티브 ValidationError만 issue로 변환합니다.
- errors 배열·배열이 아닌 errors·표지를 가진 일반 객체는 같은 값으로 거부합니다.
- 다른 설치 사본의 AJV 인스턴스도 자기 네이티브 오류를 인식합니다.

### ownership-observation — 애플리케이션 관찰 동등성

- 애플리케이션 연산과 폼 수명을 교차한 생성 시퀀스는 각 단계에서 I1·I2·I3을 쌍둥이 oracle과 비교합니다.
- 직접 compile·validate의 캐시, embedded 별칭, 늦은 등록·제거·교체, 같은 루트 재컴파일, 여러 어댑터·사본·방언, 비동기 규칙과 64개 풀 경계를 포함합니다.
- seed를 실패에 남기며 1–5라운드의 고정 입력과 GC 없는 재방문도 재현합니다.
