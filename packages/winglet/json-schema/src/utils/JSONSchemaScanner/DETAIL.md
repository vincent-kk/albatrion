# JSONSchemaScanner contract

## Requirements

- 동기·비동기 드라이버와 내장 해소기는 이 모듈의 organ에 있는 방언 판별·어휘 컴파일·복제·오류·상한 구현을 함께 사용한다.
- 이 진입점은 패키지 루트와 `resolveReference`가 쓰는 스캐너·해소기 이름과 공개 형만 내보내고, 구현 헬퍼는 내보내지 않는다.

## API Contracts

내장 해소기는 이 모듈 밖의 코드(`resolveReference`와 패키지 루트)만 사용하지만 이 모듈의 하위 모듈로 둡니다. 해소기는 스캐너가 선언한 해소기 프로토콜을 구현하고, 동기 스캐너로 문서를 색인하며, 방언 판별·어휘 컴파일·복제·오류를 스캐너와 공유하는 파생 구현이기 때문입니다. 사용하는 쪽의 최저 공통 모듈을 기준으로 배치하면 해소기와 이 공유 구현이 패키지 루트로 올라가고, 루트의 organ이 이 모듈 내부의 형을 가져다 쓰는 역방향 의존이 생깁니다.

기본 키워드 선언은 keyword 모듈에, 그 선언을 컴파일한 기본 키워드 표는 이 모듈의 organ에 둡니다. 표는 모듈을 불러오는 순간 만들어지므로, 선언과 한 파일에 두면 선언만 쓰는 소비자도 컴파일 코드를 불러오게 됩니다.

## Acceptance Criteria

### scanner-sync — 동기 스캐너 순회·참조 해석 계약

- exit 방문자에서 `references` 결과로 참조 위치를 확인하고 내장 해소기로 순회하면 `getValue()`가 참조를 인라인한 최종 스키마를 반환한다.
- 중첩된 `$defs`(정의 내부에 또 다른 정의가 있는 경우)도 각각 고유한 JSON 포인터 경로로 구분되어 해석된다.
- 자기 자신 또는 상위 정의를 가리키는 순환 `$ref`가 있어도 순회는 종료하며, 순환된 지점은 1레벨만 해석되고 더 깊은 재귀 지점은 `$ref` 그대로 남는다 — 무한 루프 미발생을 별도 케이스로도 확인한다.
- `oneOf` 등 구성 키워드 내부에 중첩된 `$ref`도 탐지·해석 대상이며, 해석 후에도 `additionalProperties`처럼 관련 없는 키워드는 원본 그대로 보존된다.

### scanner-async — 비동기 스캐너 콜백·참조 해석 계약

- 동기 스캐너와 동일한 실제 데이터 시나리오(중첩 `$defs`, 순환 참조, `oneOf` 내부 참조, 무관한 키워드 보존)를 `await scan()` 경로로도 동일하게 재현한다.
- 방문자 콜백이 동기 함수여도(async로 감싸지 않아도) 정상 동작하며, `enter`가 각 노드의 경로·깊이·키워드 정보를 담아 호출된다.
- 해소기의 resolve가 resolved 태그를 반환하면 `references`에 성공과 정규 URI를 기록하며, skipped 태그의 unresolved 결과는 원본 참조를 보존한다. 비동기 스캐너는 태그 결과를 기다린다.
- 방문자의 `enter`/`exit`가 각각 프로미스를 반환하면 `scan()`은 각 콜백이 완료될 때까지 순서대로 기다린 뒤 다음 단계로 진행한다(호출 순서로 검증).
- `scan()` 이전의 `getValue()`는 `undefined`를 반환하고, 참조가 없는 스키마를 스캔한 뒤의 `getValue()`는 원본 스키마와 동일한 값을 반환한다.

### entry-surface — 진입점과 공개 하위 경로의 관계

- 패키지 루트가 내보내는 스캐너·해소기·오류·참조 결과 이름은 모두 이 진입점에서 가져온다.
- `scanner`·`async-scanner` 하위 경로가 다시 내보내는 스키마 선언은 keyword 모듈이 내보내는 것과 같은 객체다.

### shared-implementation — 드라이버와 해소기의 공유 구현

- 해소기와 두 드라이버는 방언 판별·어휘 컴파일·복제를 이 모듈의 같은 organ 파일에서 가져오며, 같은 구현을 하위 모듈 안에 다시 두지 않는다.

## Last Updated
