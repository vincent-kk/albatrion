# createReferenceResolver contract

## Requirements

참조는 정규 위치의 유일한 대상으로 해석하거나 명시적인 이유를 남깁니다. 주소를 찾았다는 사실과 그 대상을 현재 호스트에 옮길 수 있다는 판단을 구분해 잘못된 인라인을 막습니다. 삭제·재배치가 기존의 유효한 참조 주소를 바꿀 수 있고 안전을 증명하지 못하면 원래 참조를 보존합니다.

## API Contracts

스캐너의 순회는 동기 스캐너 진입점으로, 방언과 기본 어휘 선언은 keyword 모듈 진입점으로 사용합니다. 오류·방언 판별·어휘 구성과 공통 복제는 상위 스캐너 모듈의 organ에서 가져와 내부 헬퍼를 공개 scanner API에 추가하지 않습니다.

URI 참조 해석과 절대 URI 판별은 자식 프랙탈 `utils/resolveURI`의 진입점으로만 씁니다. RFC 3986 해석은 JSON Schema 개념과 무관한 자기 계약이라 경계를 따로 두며, 해소기가 그 내부 단계에 기대지 않아야 해석 규칙을 바꿀 때 영향 범위를 진입점의 이름만으로 가늠할 수 있습니다.

색인 저장소 `ResolverStore`와 비동기 생성 함수 `createReferenceResolverAsync`도 자식 프랙탈이고, 서로와 `resolveURI`를 진입점으로만 씁니다. 저장소 루트 CLAUDE.md의 Imports follow lineage 원칙은 organ이 소유 프랙탈의 자식 프랙탈을 가져오지 못하게 해 organ → 자식 → organ 순환을 막으므로, `resolveURI`를 쓰는 저장소와 저장소를 쓰는 비동기 생성 함수는 organ으로 둘 수 없습니다.

문맥은 불투명하게 전달해 색인 구조의 변경이 공개 계약으로 번지지 않게 합니다.

루트 문서는 생성 때 색인하고 등록 문서는 최초 조회 때 색인합니다. 어떤 키도 가리키지 않는 절대 문서 주소를 처음 조회하면, 아직 색인하지 않은 등록 문서를 모두 한 번 색인한 뒤 다시 찾습니다. 등록 문서에 내장된 식별자는 그 문서를 색인해야 알 수 있으므로, 이 단계가 없으면 내장 자원을 가리키는 참조가 그 문서를 먼저 참조했는지에 따라 해석되거나 남고, 비동기 해소기는 등록 문서가 이미 담은 주소를 `load`로 읽습니다. 그 결과 관련 없는 등록 문서의 식별자 충돌도 첫 미스 때 오류가 됩니다. 등록 문서를 이미 색인했는지는 그 주소로 `index`를 호출했는지로만 판단하고, 다른 문서가 그 주소를 내장 식별자로 선언했다는 사실로 판단하지 않습니다. 후자로 판단하면 그 주소를 내장한 문서를 먼저 색인했을 때만 등록 문서를 건너뛰어, 같은 충돌이 키 순서에 따라 오류가 되거나 내장 자원으로 조용히 해석됩니다. 같은 이유로, 이미 알려진 주소를 조회해도 그 주소로 색인한 적이 없고 `resources`가 있으면, 그 주소가 아직 색인하지 않은 등록 키인지 확인해 색인합니다. 이 확인이 없으면 다른 등록 문서가 내장한 주소를 먼저 색인했는지에 따라, 같은 참조가 내장 자원으로 해석되거나 충돌 오류가 됩니다. 이 확인은 쓴 그대로의 키와, 앞선 미스가 이미 만든 정규화 키만 봅니다. 정규화는 키마다 URI 해석을 하므로 등록 문서 60개에서 수백 마이크로초가 들고, 내장 자원 조회마다 그 비용을 처음 한 번 치르면 일반 해석이 느려지기 때문입니다. 그래서 정규 철자가 아닌 키는 정규화 키가 만들어지기 전의 알려진 주소 조회에서 충돌을 놓칠 수 있고, 이 한계는 사양에 적습니다. 키가 직접 맞는 조회와 이미 색인한 주소의 조회는 그 문서만 다룹니다. 등록 문서의 키는 참조와 같은 해석(`resolveURI`)으로 정규화한 주소로 찾습니다. 참조는 스킴·호스트를 소문자로 바꾼 정규 주소로 해석되므로, 키를 쓴 그대로만 비교하면 `https://Ex.Example/a.json` 같은 키는 어떤 참조로도 찾을 수 없습니다. 정규화는 쓴 그대로의 키가 맞지 않는 첫 조회 때 한 번만 하므로, 정규 철자로 쓴 키의 조회에는 비용이 더해지지 않습니다. 서로 다른 두 키가 같은 주소로 정규화되면 같은 문서 객체일 때만 별칭이고, 다른 문서면 두 키를 담은 식별자 충돌 오류입니다. 방언의 스키마 위치와 구방언 참조 옆의 정의 주소 컨테이너만 식별자를 등록합니다. 다른 inert 형제의 식별자는 등록하지 않습니다. 방언에서 inert인 위치와 그 후손을 가리키는 참조는 같은 자원의 식별자 없는 사본 최적화보다 먼저 relocation으로 보존합니다. 색인에서 스키마 위치로 확인되지 않은 포인터 대상과 inert 영역은 기준 URI·방언·식별자의 의미를 증명할 수 없으므로 같은 이동 불가 조건으로 다룹니다. 구방언 참조 옆의 식별자 자체는 무시합니다.

포인터 조각은 퍼센트 디코딩을 한 번 한 뒤 빈 값·포인터·앵커로 분류합니다. 포인터 토큰은 기존 JSON Pointer 해제를 재사용하며 상속 속성은 읽지 않습니다. 정규 위치가 같으면 앵커와 포인터 표기는 같은 순환 정체성을 가집니다. 동적 앵커로 향하는 동적 참조는 정적 인라인 대상이 아닙니다. [자원 검증](__tests__/createReferenceResolver.resources.test.ts)이 정적 대상과 동적 대상의 구분을 확인합니다. URI에 노출하는 포인터는 퍼센트와 조각 구분자를 인코딩해 재조회해도 같은 대상을 가리킵니다.

같은 대상과 호스트 쌍의 템플릿을 재사용합니다. 같은 자원의 식별자 없는 대상은 그대로 복제하고, 그 밖에는 방문·필터·깊이와 무관하게 전체 대상을 조사해 식별자를 제거하고 참조 URI를 원래 범위에서 재작성합니다. 제거하는 키워드는 각 위치가 속한 자원의 방언에서 식별자인 것뿐입니다. 모든 방언의 `$schema`, draft-04의 `id`, draft-06 이후의 `$id`, 2019-09·2020-12의 `$anchor`·`$vocabulary`, 2019-09의 `$recursiveAnchor`, 2020-12의 `$dynamicAnchor`입니다. 다른 방언의 같은 이름(2020-12의 `id`, draft-07의 `$anchor`)은 알 수 없는 키워드인 주석이라, 지우면 인라인한 출력에서 주석이 조용히 사라집니다. 색인에서 위치가 확인되지 않은 항목은 모든 방언의 이름으로 판단해 이동 불가 조건을 놓치지 않습니다. 방언이 바뀌거나 동적 범위를 지우거나 재작성할 수 없는 위치가 있으면 relocation입니다. [이동 검증](__tests__/createReferenceResolver.relocation.test.ts)과 [미인식 위치 검증](__tests__/createReferenceResolver.positions.test.ts)이 이 보존 경계를 확인합니다. 데이터 키워드의 값은 재작성하지 않습니다.

비동기 해소기는 사용자 load가 있을 때만 읽고 문서의 성공·미발견과 진행 중 요청을 절대 URI별로 공유합니다. 사용자 로드의 예외는 호출자에게 전파합니다. 조각 식별자가 이름을 등록한 문서도 등록되어 있지 않으면 load로 읽습니다. 동기 해소기는 등록 문서를 먼저 색인해 같은 이름의 두 번째 선언을 식별자 충돌로 잡으므로, 읽기를 건너뛰면 두 해소기의 결과가 갈라집니다. [비동기 공급 검증](__tests__/createReferenceResolver.async.test.ts)이 요청 합치기와 공급 결과를 확인합니다.

## Acceptance Criteria

### addresses — 자원과 조각의 정확한 조회

- 기준 URI·식별자·앵커·내장 자원·빈 포인터·퍼센트 조각을 정확한 위치로 해석합니다.
- 참조와 식별자는 RFC 3986 5.2절대로 해석합니다. 계층 URI 기준에서는 URL 해석기의 결과와 정규화를 쓰고, 기준이 없거나 상대이거나 `urn:`·`tag:`처럼 계층이 없는 기준에서는 스킴이 있는 참조를 기준 없이 그 자체로 읽고 스킴이 없는 참조에 같은 알고리즘을 직접 적용합니다. 루트의 `baseURI`도 같은 해석을 거쳐 루트 주소가 됩니다. 기준이 없는 문서는 알 수 없는 기본 기준을 쓰므로 상대 값은 상대 주소로 남고(JSON Schema 2020-12 9.1.1절, draft-04 7.1절), 그런 기준에서 `..`가 기준의 시작보다 위로 올라가면 버리지 않고 남겨 기본 기준이 채울 수 있게 합니다. 점 구간을 지운 경로가 비거나, 첫 구간에 `:`가 남거나, 빈 구간 때문에 `/`로 시작하게 되면 앞에 `./`를 붙이고, `/`로 시작하던 경로가 `//`로 시작하게 되면 앞에 `/.`를 붙입니다. 빈 경로는 기준 문서 자신을(RFC 3986 5.2.2절), 첫 구간의 `:`는 스킴을, 맨 앞의 `//`는 권한을(4.2절) 뜻하므로, 붙이지 않으면 `./`가 기준 문서와 충돌하고 `x/../urn:a`가 다른 절대 URI로, `x/..//a`가 루트 경로 `/a`로, `/.//a`가 호스트 `a`로 바뀝니다. 계층 없는 기준의 상대 경로는 RFC 8141 4.3절대로 `urn:child.json` 같은 주소가 됩니다. 그런 기준에는 이 접두사 규칙을 적용하지 않으므로, 점 구간이 맨 앞 구간을 지우거나 빈 구간을 맨 앞에 남기면 RFC 3986 5.2.4절의 단계별 결과와 다릅니다(`../c` + `urn:example:a/b`는 `urn:c`, `x/..//a` + `urn:example:root`는 `urn:/a`). URN 경로에는 계층이 없고 RFC 8141 4.3절이 그런 참조를 피하라고 하기 때문입니다. URL 해석기만 쓰면 이런 기준에서 빈 참조와 상대 식별자를 거절하고 상대 기준에서는 절대 참조까지 거절해, 같은 스키마의 내장 자원과 자기 참조가 기준 URI에 따라 사라집니다.
- 써 있는 참조와 식별자의 제어 문자·공백·역슬래시는 해석 전에 퍼센트 인코딩하고, 스킴 자리가 스킴 문법에 맞지 않으면 무효로 둡니다. URL 해석기는 앞뒤 공백과 탭·줄바꿈을 지우고 특수 스킴에서 역슬래시를 `/`로 바꾸므로, 그대로 넘기면 `" "`가 빈 참조가 되는 식으로 같은 문자열이 기준에 따라 다른 참조가 됩니다.
- 절대 URI가 아닌 문서 주소는 등록 문서(`resources`)나 `load`로 찾지 않습니다. 기본 기준을 알 수 없는 주소는 조회 주소가 아니기 때문입니다.
- 식별자 키워드는 그 스키마 자신의 방언이 정합니다. draft-04는 `id`만, draft-06 이후는 `$id`만 식별자로 읽고, 구방언의 `$ref` 옆 식별자는 바깥 자원의 방언으로 판단해 무시합니다. draft-04 사양에는 `$id`가 없으므로 두 키워드를 함께 읽으면 알 수 없는 키워드가 자원을 만들고, 하위 스키마의 `$schema`를 보지 않으면 다른 방언으로 선언한 내장 자원을 놓칩니다.
- 하위 스키마의 빈 식별자와 빈 조각만 있는 식별자(`""`, `#`, 바로 바깥 자원의 주소 뒤에 `#`)는 기준 URI의 종류와 관계없이 그 자리의 기준 문서 주소를 선언합니다. 바로 바깥 자원이 그 주소를 이미 선언했으므로 식별자 충돌 오류이고, 조각 식별자가 기준만 바꾼 하위 트리 안에서는 그 문서를 선언한 스키마가 없으면 새 선언입니다. 2020-12는 빈 조각 형태를 조각이 없는 형태와 같은 자원으로 정의하고, draft-04·06·07에서 빈 조각은 문서 루트를 가리키는 포인터입니다. 이 규칙이 없으면 같은 스키마가 기준 URI에 따라 통과하거나 실패하고, 통과할 때 그 하위 스키마 안의 참조가 바깥 자원을 기준으로 해석됩니다. 주소가 없는 문서는 오류 메시지에 `#`로 표시합니다.
- 비어 있지 않은 조각을 가진 식별자는 자원을 선언하지 않습니다. 2019-09·2020-12에서는 사양이 금지한 형태이므로 아무것도 선언하지 않고, draft-04·06·07에서는 이름 조각을 그 식별자가 가리키는 문서의 위치 독립 식별자로 등록하며 하위 스키마 안의 참조를 그 문서를 기준으로 해석합니다(draft-04 7.2.2절). 조각을 버리고 문서를 선언하면 바깥 문서나 나중에 선언되는 같은 문서와 거짓 충돌이 나고, 문서의 루트가 아닌 하위 스키마가 문서 주소를 차지합니다. 그래서 위치 독립 식별자는 자원이 아니라 문서 주소별로 보관하고, 조회는 쓰인 문서 주소를 먼저, 등록 문서의 정규 주소를 다음으로 봅니다. 기준만 바꾼 하위 스키마의 정규 URI는 가장 가까운 선언된 자원에서 계산하고, 이름 충돌 메시지는 서로 다른 문서의 위치를 구분하도록 문서 주소를 붙입니다.
- 중복 식별자를 거절하고 같은 위치의 별칭을 허용합니다.

### relocation — 위치를 옮겨도 판정을 유지하는 사본

- 미방문 후손을 포함한 이동에서 참조 의미와 데이터 값을 보존합니다.
- 방언·동적 범위·미인식 위치가 안전하지 않으면 원래 참조를 남깁니다.
- 절대 URI가 아닌 자원의 대상을 다른 자원으로 옮기면 원래 참조를 남깁니다. 상대 주소는 다른 기준에서 다른 문서를 가리키기 때문입니다.

### async-loading — 명시적인 비동기 문서 공급

- 등록 문서를 먼저 사용하고, 같은 절대 문서 요청은 한 번만 호출합니다.
